## 协议简介

VNC（Virtual Network Computing）是一个远程桌面协议栈，由 AT&T 实验室在 1998 年开发。核心思路是**在服务器端捕获帧缓冲区（framebuffer）的像素变化，压缩后传给客户端渲染**。

## 协议分层

VNC 不是单一协议，而是一组协议的协作：

```
┌─────────────────────────────────────┐
│  RFB 协议 (Remote Framebuffer)      │  ← 核心协议 (RFC 6143)
├─────────────────────────────────────┤
│  传输层：通常是 TCP                  │  ← 默认端口 5900 (或 5901, 5902...)
└─────────────────────────────────────┘
```

## 连接流程（RFB 握手）

```
Client                          Server
  │  ─── TCP Connect (5900) ───→   │
  │  ←── Protocol Version ──────   │   "RFB 003.008\n"
  │  ─── Security Type ────────→   │   协商认证方式 (None/VNC/DES/RA2)
  │  ←── Security Result ──────    │   认证结果
  │  ─── ClientInit (shared) ──→   │   是否共享会话
  │  ←── ServerInit ───────────    │   桌面名称、分辨率、像素格式
  │  ═══════════════════════════    │
  │  ←── FramebufferUpdate ────    │   像素数据持续推送
  │  ─── KeyEvent / PointerEvent → │  客户端输入事件
  │  ─── FramebufferUpdateRequest→│  请求更新特定区域
  │  ─── SetEncodings ─────────→   │   协商编码方式
```

## 为什么能用来连接远程机器/虚拟机

1. **不依赖操作系统 GUI 框架** — VNC 工作在 framebuffer 层级，直接读取显存中的像素，不需要 X11/Wayland/DirectX 的参与。虚拟机（KVM/QEMU）直接导出虚拟显卡的 framebuffer
2. **服务端极轻量** — 只需一个 VNC Server 进程（如 `x11vnc`、`QEMU 内置 VNC`、`TightVNC`），不需要完整的桌面环境也能工作
3. **跨平台** — 协议本身与 OS 无关，Linux/Windows/macOS 都有实现
4. **虚拟机原生支持** — QEMU/KVM、VirtualBox、VMware 都内置 VNC Server，因为虚拟机管理器天然拥有虚拟 framebuffer 的访问权，VNC 是最简单的导出方式

## 流量特征

VNC 流量**特征非常明显**，容易被识别。这也是为什么它通常不直接暴露在公网上的原因。

### 协议级指纹

| 特征 | 值 | 说明 |
|------|-----|------|
| 默认端口 | 5900+N | 5900 是 display :0，5901 是 :1 |
| 协议版本字符串 | `RFB 003.003\n` / `RFB 003.007\n` / `RFB 003.008\n` | 握手第一个包就是明文 |
| 加密 | 无（或仅认证阶段 DES） | RFB 协议本身不加密传输 |
| 认证方式 | 1=None, 2=VNC Authentication | 握手阶段明文协商 |

### 抓包层面可见的特征

```bash
# TCP 连接后，服务器立即发送版本字符串
"RFB 003.008\n"     ← 12 字节明文，这是最显著的指纹

# 客户端回复版本
"RFB 003.008\n"

# 安全类型协商（明文）
\x01 \x01            ← 1种安全类型：类型1(None)
\x01 \x02            ← 1种安全类型：类型2(VNC Auth)
```

### 流量统计特征（即使加密后也能识别）

即使通过 TLS/SSH 隧道传输，VNC 流量仍然有统计特征：

1. **非对称流量比** — 服务端→客户端的数据量远大于客户端→服务端（屏幕更新 vs 鼠标键盘事件），通常 10:1 到 50:1
2. **持续的大块数据传输** — FramebufferUpdate 包含大量矩形区域的像素数据，产生规律的突发流量
3. **帧率模式** — 更新频率与用户操作节奏相关，有明显的交互模式（操作时突发、静止时低频心跳）
4. **包大小分布** — 客户端发包小（PointerEvent ~6字节，KeyEvent ~8字节），服务端发包大（矩形像素数据，可达数十KB）
5. **固定端口行为** — 即使换了端口，长连接 + 持续双向流的模式仍然可识别

### 编码方式也留下痕迹

VNC 支持多种编码（Raw、CopyRect、RRE、Hextile、ZRLE、Tight），不同编码的压缩数据有不同特征：

- **Raw 编码** — 未压缩像素，高度可识别
- **Tight 编码** — 使用 zlib 压缩，包内 zlib 头可见
- **ZRLE 编码** — 也用 zlib，但有特定的子编码标记字节

## 检测与识别方法

```bash
# 1. 端口扫描
nmap -p 5900-5910 --script vnc-info <target>

# 2. 抓包看协议指纹
tcpdump -i any port 5900 -A -c 5
# 输出中会看到 "RFB 003.008"

# 3. DPI/IDS 规则（Snort/Suricata 示例）
# alert tcp any any -> any 5900 (content:"RFB 003"; sid:1000001;)
```

## 与 SSH 的对比：延伸终端 vs 延伸显示器

SSH 和 VNC 是两种截然不同的远程访问思路，本质区别在于**数据源不同**：

```
┌─ SSH ──────────────────────────────────────────────┐
│                                                     │
│  你的键盘 ──字符──→ 本地 SSH Client                  │
│                          │                          │
│                    加密 + 认证                        │
│                          │                          │
│  远程 SSH Server ──字符──→ bash/sshd (pty)           │
│                          │                          │
│                    执行命令                          │
│                          │                          │
│                    stdout 字符流                     │
│                          │                          │
│                    加密 ──→ 你的终端显示               │
│                                                     │
│  传输内容：纯文本字节流，每秒几百字节                   │
│  等价于：把一根串口线拉长了几千公里                     │
└─────────────────────────────────────────────────────┘

┌─ VNC ──────────────────────────────────────────────┐
│                                                     │
│  VNC Server ──读──→ 显存（GPU VRAM / 虚拟显存）      │
│                          │                          │
│                    对比脏区域                        │
│                          │                          │
│                    像素编码压缩                       │
│                          │                          │
│                    TCP 发送                         │
│                          │                          │
│  VNC Client ──解码──→ 渲染到本地屏幕                  │
│                          │                          │
│  你的鼠标/键盘 ──事件──→ VNC Server ──注入──→ Guest   │
│                                                     │
│  传输内容：像素矩形，每秒数 MB                         │
│  等价于：把一根 HDMI 线拉长了几千公里                  │
└─────────────────────────────────────────────────────┘
```

| 维度 | SSH | VNC |
|------|-----|-----|
| 数据源 | shell 的 pty（终端设备） | 显卡的 framebuffer |
| 传输内容 | 字符字节流 | 像素矩形块 |
| 方向 | 双向对称（输入/输出都是文本） | 非对称（下传大图像，上传小事件） |
| 带宽 | 极低，几十 B/s | 高，几 MB/s |
| 延迟敏感度 | 低，敲一个字等几十 ms 无感 | 高，拖窗口卡顿会很明显 |
| 能力边界 | 只能做命令行能做的事 | 能做 GUI 能做的任何事 |
| Guest 网络依赖 | 依赖 Guest SSH 服务 + 网络正常 | 不依赖（QEMU 场景下） |
| 适用场景 | 日常运维、部署、排障 | 装系统、进 GRUB、网络断了救急 |

一句话总结：**SSH 延伸了终端，VNC 延伸了显示器**。

## 实际应用场景

远程连接 Linux 服务器，绝大多数场景不需要图形界面：

- **日常运维、部署、排障** → SSH，命令行足够，延迟低，带宽小
- **K8s 节点管理** → `kubectl exec`，容器编排不需要桌面
- **集中监控** → Grafana/ELK，比登录机器看高效

VNC 实际用到的场景很窄：

- **虚拟机管理控制台** — QEMU `-vnc` 参数，装系统、进 GRUB、网络断了之后救急
- QEMU 的 VNC 监听的是**宿主机的端口**，流量完全不走 Guest 的网络栈，所以即使 Guest 断网也能连上
- **Windows 远程桌面替代** — 某些 Linux 桌面应用必须图形操作
- **嵌入式设备** — 工控机、瘦客户端有少量 GUI 需求

而且即使救急场景，现在也更倾向于用 **SPICE**（QEMU 推荐替代）或 **serial console**（`virsh console`），带外管理走 **IPMI/iDRAC/iLO**。VNC 更像是一个最低限度的通用兜底方案。

## 总结

VNC 的优势在于**简单、通用、与 OS 无关**，这使它成为虚拟机管理的标配。但这些优势同时也是它流量特征明显的原因——明文握手、无传输加密、非对称流量模式，使其在网络流量分析面前几乎没有隐蔽性。生产环境通常通过 SSH 隧道或 VPN 来保护 VNC 流量。
