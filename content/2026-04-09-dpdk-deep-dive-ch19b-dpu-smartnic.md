## 1. 概述：为什么需要 DPU？

### 1.1 云计算场景下的 CPU 瓶颈

想象一个云服务器机房里的一台物理机：

```
一台物理机的 CPU 在干什么？
══════════════════════════════════════════════════════════════════════════════

  ┌──────────────────────────────────────────────────────────────────┐
  │  物理机 (96 核 CPU)                                              │
  │                                                                  │
  │  ┌─────────┐ ┌─────────┐ ┌─────────┐       ┌─────────┐          │
  │  │  VM #1  │ │  VM #2  │ │  VM #3  │  ...  │ VM #50  │          │
  │  │ (用户 A) │ │ (用户 B) │ │ (用户 C) │       │ (用户 Z) │         │
  │  └─────────┘ └─────────┘ └─────────┘       └─────────┘          │
  │                                                                  │
  │  用户的 VM 只需要 CPU 做业务计算（跑 Web 服务、数据库等）          │
  │  但实际上 CPU 还在做这些事：                                      │
  │                                                                  │
  │  ┌─────────────────────────────────────────────────────┐        │
  │  │  网络处理    │  虚拟化开销   │  存储处理   │ 安全策略  │        │
  │  │  OVS 转发    │  KVM/QEMU     │  分布式存储  │ 防火墙   │        │
  │  │  virtio 模拟 │  中断注入     │  Ceph 客户端 │ 加解密   │        │
  │  │  包检查      │  内存映射     │  iSCSI      │ 密钥管理  │        │
  │  │  负载均衡    │  I/O 模拟     │  数据压缩    │审计日志   │        │
  │  └─────────────────────────────────────────────────────┘        │
  │                                                                  │
  │  这些"基础设施任务"吃掉了 20-30% 的 CPU！                         │
  │  用户为这些 CPU 付费，但它们并没有为用户创造业务价值               │
  └──────────────────────────────────────────────────────────────────┘
```

这就是 DPU 要解决的核心问题：**把基础设施任务从 Host CPU 搬到专门的硬件上，让 Host CPU 100% 用于用户业务**。

> [!note] 一个类比
> 想象一家餐厅：
>
> - **Host CPU** = 厨师（应该专注于做菜）
> - **基础设施任务** = 洗菜、切菜、洗碗、收银、打扫卫生
> - **DPU** = 请一个专门的帮厨团队来做这些杂活
>
> 厨师不再需要自己洗碗，可以全部精力放在做菜上。对餐厅来说，同样的厨师可以服务更多客人。

### 1.2 DPU 的核心思想

```
没有 DPU                          有 DPU
────────                          ──────

┌──────────────────────┐          ┌──────────────────────┐
│    Host CPU (96核)    │          │    Host CPU (96核)    │
│                      │          │                      │
│  70% 业务计算         │          │  100% 业务计算        │
│  20% 网络处理         │          │                      │
│  10% 存储和安全       │          │                      │
│                      │          └──────────┬───────────┘
│                      │                     │ PCIe
│                      │                     │
└──────────┬───────────┘          ┌──────────▼───────────┐
           │                      │      DPU (SmartNIC)   │
           │                      │                       │
┌──────────▼───────────┐          │  网络转发、存储、安全   │
│     普通 NIC         │          │  全部在 DPU 上完成     │
│   (只做收发)          │          │                       │
└──────────────────────┘          └──────────────────────┘
```

### 1.3 三个术语：SmartNIC、DPU、IPU

这三个词经常混用，但来源不同：

| 术语         | 全称                           | 谁起的 | 含义                               |
| ------------ | ------------------------------ | ------ | ---------------------------------- |
| **SmartNIC** | Smart Network Interface Card   | 通用   | 带可编程能力的网卡                 |
| **DPU**      | Data Processing Unit           | NVIDIA | 强调"数据处理"，比 SmartNIC 更通用 |
| **IPU**      | Infrastructure Processing Unit | Intel  | 强调"基础设施处理"，定位类似       |

> [!note] 怎么理解它们的区别？
> 可以认为 SmartNIC 是大类，DPU 和 IPU 是两家公司给自己的 SmartNIC 起的品牌名。就像"智能手机"是通用词，"iPhone"和"Galaxy"是品牌。本文统一用 **DPU** 指代这一类产品。

## 2. 从网卡到 DPU：演进之路

### 2.1 四代网卡

```
第一代：传统 NIC (1G/10G 时代)
═════════════════════════════════

    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │   CPU    │───►│  Kernel  │───►│   NIC    │───► 网络
    │          │    │ (协议栈) │    │ (只收发) │
    └──────────┘    └──────────┘    └──────────┘

    NIC 什么活都不干，纯粹是"收发天线"。
    所有协议处理（TCP/IP、校验和、分片）全靠 CPU。


第二代：Offload NIC (10G/40G 时代)
═════════════════════════════════════

    ┌──────────┐    ┌──────────┐    ┌──────────────────┐
    │   CPU    │───►│  Kernel  │───►│  Offload NIC      │───► 网络
    │          │    │ (协议栈) │    │  - checksum       │
    │          │    │          │    │  - TSO/GRO        │
    │          │    │          │    │  - RSS (多队列)   │
    └──────────┘    └──────────┘    └──────────────────┘

    NIC 开始帮忙干一些固定的小活（校验和、大包分片）。
    但只能做硬件写死的操作，不能编程。


第三代：SmartNIC (25G/100G 时代)
═══════════════════════════════════

    ┌──────────┐    ┌──────────────────────────────────────────┐
    │   CPU    │───►│  SmartNIC                                │───► 网络
    │          │    │  ┌──────────┐  ┌──────────────────────┐  │
    │          │    │  │ 网络加速  │  │  可编程 (FPGA/ASIC)  │  │
    │          │    │  │ (固定)   │  │  流表匹配、封装卸载   │  │
    └──────────┘    │  └──────────┘  └──────────────────────┘  │
                   └──────────────────────────────────────────┘

    NIC 有了可编程能力（FPGA 或网络处理器）。
    可以做流表匹配、VXLAN 封装/解封装等自定义逻辑。
    但没有完整的 CPU，无法运行复杂软件。


第四代：DPU (100G/400G 时代)
════════════════════════════════

    ┌──────────┐    ┌──────────────────────────────────────────────┐
    │   CPU    │───►│  DPU (Data Processing Unit)                  │───► 网络
    │          │    │  ┌────────────────────────────────────────┐  │
    │          │    │  │  ARM CPU (完整的处理器)                 │  │
    │          │    │  │  + DDR 内存 (16GB)                     │  │
    │          │    │  │  + 独立 Linux 操作系统                  │  │
    │          │    │  ├────────────────────────────────────────┤  │
    │          │    │  │  硬件加速引擎                           │  │
    │          │    │  │  - 网络加速 (crypto/compress/RDMA)      │  │
    │          │    │  │  - 存储加速 (NVMe)                      │  │
    │          │    │  │  - 正则匹配 (DPI)                      │  │
    └──────────┘    │  └────────────────────────────────────────┘  │
                   └──────────────────────────────────────────────┘

    DPU = SmartNIC + 完整的 CPU + 内存 + 操作系统。
    不只是"可编程网卡"，而是"网卡上的一台小电脑"。
    可以独立运行 OVS、防火墙、存储客户端等完整软件。
```

### 2.2 每一代解决了什么

| 世代            | 解决的问题                      | 新引入的问题                     |
| --------------- | ------------------------------- | -------------------------------- |
| **传统 NIC**    | 基础网络连通                    | CPU 瓶颈，10G 以下不明显         |
| **Offload NIC** | 减少 CPU 的重复劳动（校验和等） | 40G+ 时仍不够                    |
| **SmartNIC**    | 自定义网络处理逻辑              | 编程复杂（FPGA），无通用软件生态 |
| **DPU**         | 运行完整软件栈，通用可编程      | 开发复杂度、管理成本、设备成本   |
|                 |                                 |                                  |

> [!note] 关键数字
>
> - **8 个 ARM A72 核心**：性能约等于一颗低端手机 SoC，足以运行 OVS-DPDK
> - **16GB DDR4 内存**：DPU 自己的内存，独立于 Host 内存
> - **2 x 25GbE 网口**：面向外部网络
> - **PCIe Gen4 x16**：与 Host 的数据通道，带宽 ~32GB/s
> - **功耗 ~25W**：比一张高端 GPU (350W) 低得多

### 3.2 双宿主模式（Dual-Host）

DPU 最独特的设计是"双宿主"——它同时连接两个世界：

```
┌─────────────────────────────────────────────────────────────────────┐
│                          物理服务器                                  │
│                                                                     │
│  ┌─────────────────────────┐         ┌───────────────────────────┐  │
│  │      Host 端             │  PCIe   │      DPU 端               │  │
│  │                         │◄───────►│                           │  │
│  │  Host CPU (x86)         │  Gen4   │  ARM CPU                 │  │
│  │  Host 内存 (256GB)      │  x16    │  DPU 内存 (16GB)          │  │
│  │  QEMU / KVM             │         │  DPU Linux (独立内核)      │  │
│  │  VM #1, VM #2, ...      │         │  OVS-DPDK / SPDK          │  │
│  │  用户业务进程            │         │  防火墙 / 存储客户端       │  │
│  │                         │         │                           │  │
│  │  看到的是:               │         │  看到的是:                │  │
│  │  - 普通 PCIe 网卡        │         │  - 从 Host 收到的包        │  │
│  │  - 标准 virtio 设备      │         │  - 外部网络               │  │
│  │  - 不知道 DPU 存在       │         │  - 管理所有网络/存储逻辑    │  │
│  └─────────────────────────┘         └─────────────┬─────────────┘  │
│                                                      │               │
│                                              100Gbps 网口            │
│                                                      │               │
└──────────────────────────────────────────────────────┼───────────────┘
                                                       │
                                                  外部网络
                                              (Internet / DCN)
```

> [!note] Host 完全无感知
> Host 看到的是一张普通网卡（或一组 virtio 设备），完全不知道背后有一个 ARM CPU 在处理所有逻辑。这就是 DPU 的精髓——**透明卸载**。

> [!note] DPU 有自己的 Linux
> 这是最反直觉的一点：DPU 跑着独立的 Linux 内核。你甚至可以 SSH 登录到 DPU，在上面装包、改配置、跑程序。它本质上就是一台 ARM 小电脑，只不过这台电脑插在 PCIe 插槽上，自带两个网口。

### 4.2 Host 和 DPU 怎么通信

```
Host-DPU 通信方式

  │  ┌───────────────┐  │   PCIe VF          │  ┌───────────────┐  │
  │  │ VF (虚拟功能)  │◄─┼────────────────────┼─►│ VF 驱动       │  │
  │  │ 分配给 VM 的   │  │  SR-IOV            │  │ (representor) │  │
  │  │ "直通网卡"     │  │                    │  │               │  │
  │  └───────────────┘  │                    │  └───────────────┘  │
  │                     │                    │                     │
  │  ┌───────────────┐  │   Mailbox          │  ┌───────────────┐  │
  │  │ PF 管理接口    │◄─┼────────────────────┼─►│ DPU Agent     │  │
  │  │ (配置/查询)    │  │  控制面通道         │  │ (gRPC/CLI)    │  │
  │  └───────────────┘  │                    │  └───────────────┘  │
  │                     │                    │                     │
  │  ┌───────────────┐  │   共享内存          │  ┌───────────────┐  │
  │  │ VFIO 映射      │◄─┼────────────────────┼─►│ virtio rings  │  │
  │  │ (DMA 直通)     │  │  数据共享           │  │ (vhost-vdpa)  │  │
  │  └───────────────┘  │                    │  └───────────────┘  │
  └─────────────────────┘                    └─────────────────────┘

  通信方式总结:

  ┌──────────────────┬──────────────────────────────────────────────┐
  │  PCIe 数据通道    │  Host 和 DPU 之间的高速数据通路 (32GB/s)     │
  │  SR-IOV VF       │  VM 直通网络，绕过 Host 内核                  │
  │  Mailbox         │  Host 向 DPU 发控制命令（配置路由、查询状态）  │
  │  VFIO + 共享内存  │  VDPA/virtio 数据路径，DMA 直通 VM 内存      │
  └──────────────────┴──────────────────────────────────────────────┘
```

## 6. DPU 与 DPDK 的关系

### 6.1 DPDK 跑在 DPU 上

DPDK 是用户态网络框架，DPU 上的 ARM 核心也能跑 DPDK：

```
DPDK on DPU 的典型部署
══════════════════════════════════════════════════════════════════════════════

┌──────────────────────────────────────────────────────────────────────┐
│                        物理服务器                                    │
│                                                                      │
│  ┌─────────────────────────┐         ┌─────────────────────────────┐ │
│  │       Host 端            │         │        DPU 端               │ │
│  │                         │         │                             │ │
│  │  ┌─────────┐            │         │  ┌───────────────────────┐  │ │
│  │  │  VM #1  │            │  SR-IOV │  │  OVS-DPDK             │  │ │
│  │  │ virtio  │◄───────────┼─ VF ───►│  (运行在 DPU ARM 上)    │  │ │
│  │  └─────────┘            │         │  │                       │  │ │
│  │                         │         │  │  ┌─────────────────┐  │  │ │
│  │  ┌─────────┐            │         │  │  │  DPDK PMD       │  │  │ │
│  │  │  VM #2  │            │  SR-IOV │  │  │  (mlx5_pmd)     │  │  │ │
│  │  │ virtio  │◄───────────┼─ VF ───►│  │  └────────┬────────┘  │  │ │
│  │  └─────────┘            │         │  │           │           │  │ │
│  │                         │         │  │           ▼           │  │ │
│  │  Host CPU:              │         │  │  ┌─────────────────┐  │  │ │
│  │  只跑业务，不跑网络      │         │  │  │  DPU 硬件加速   │  │  │ │
│  │                         │         │  │  │  (ConnectX Dx)  │  │  │ │
│  └─────────────────────────┘         │  │  └────────┬────────┘  │  │ │
│                                       │  │           │           │  │ │
│                                       │  │           ▼           │  │ │
│                                       │  │     外部网络 100G     │  │ │
│                                       │  └───────────────────────┘  │ │
│                                       └─────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────┘

  数据路径 (VM #1 → VM #2):
  ─────────────────────────

  VM#1 ──► virtio ──► VF ──► DPU ──► OVS-DPDK ──► VF ──► virtio ──► VM#2
                                        │
                                  整个过程 Host CPU 不参与！
                                  OVS-DPDK 跑在 DPU ARM 上
```

### 6.2 DPDK 开发者为什么要关心 DPU

```
传统部署 vs DPU 部署 — DPDK 开发者的视角
══════════════════════════════════════════════════════════════════════════════

  传统部署 (DPDK on Host):
  ─────────────────────────

  你写的 DPDK 程序跑在 Host x86 CPU 上：
  - 用 rte_eth_rx_burst() 从网卡收包
  - 在 Host CPU 上处理 (L2/L3 转发、NAT、防火墙...)
  - 用 rte_eth_tx_burst() 发送到网卡
  - 问题：占用了本可以给 VM 用的 CPU 核


  DPU 部署 (DPDK on DPU):
  ──────────────────────────

  同样的 DPDK 程序，交叉编译后跑在 DPU ARM 上：
  - 用 rte_eth_rx_burst() 从 DPU 网口收包
  - 在 DPU ARM 上处理
  - 用 rte_eth_tx_burst() 发送到 DPU 网口
  - 好处：释放了 Host CPU，网络处理对 VM 完全透明

  ┌──────────────────────────────────────────────────────────┐
  │  DPDK API 基本不变！                                      │
  │                                                          │
  │  传统: rte_eth_dev_configure("0000:01:00.0");            │
  │  DPU:  rte_eth_dev_configure("0000:01:00.0");            │
  │                                                          │
  │  区别只在于编译环境和目标平台 (x86 → ARM64)。              │
  │  你的 DPDK 网络处理代码不需要改。                          │
  └──────────────────────────────────────────────────────────┘
```

## 7. DPU 与 VDPA 的关系

### 7.1 VDPA 是 DPU 给 VM 提供网络的标准方式

回顾 [[2026-04-09-dpdk-deep-dive-ch19-vdpa|ch19 VDPA]] 中的完整场景，现在用 DPU 视角重新理解：

```
VDPA 场景的 DPU 内部视图
══════════════════════════════════════════════════════════════════════════════
```

### 7.2 为什么不用 DPDK 软件转发？

```
同一个 DPU 上，两种给 VM 提供网络的方式:
══════════════════════════════════════════════════════════════════════════════

  方式 A: OVS-DPDK (软件转发)
  ────────────────────────────

  VM → virtio → VF → DPU ARM → OVS-DPDK → DPU 网口 → 外部网络
                                  │
                            ARM CPU 处理每个包
                            (查找流表、修改包头、转发决策)
                            吞吐量受 ARM 性能限制 (~10-20 Mpps)

  方式 B: VDPA (硬件转发)
  ──────────────────────────

  VM → virtio → VF → DPU 硬件 → DMA → DPU 网口 → 外部网络
                        │
                  硬件 Virtqueue Walker 处理
                  不占用 ARM CPU
                  吞吐量可达 ~30+ Mpps

  ┌──────────────────────────────────────────────────────────┐
  │  方式 A (OVS-DPDK) 更灵活：可以做任意复杂的流表规则        │
  │  方式 B (VDPA) 更快：硬件直通，但只支持标准 virtio 转发   │
  │                                                          │
  │  实际部署中两种方式可以共存：                              │
  │  - 简单 L2 转发 → VDPA (性能优先)                        │
  │  - 复杂策略 (NAT、LB、ACL) → OVS-DPDK (功能优先)         │
  └──────────────────────────────────────────────────────────┘
```

## 8. 谁在用 DPU？

### 8.1 云厂商

| 厂商       | 产品            | DPU 做什么                               |
| ---------- | --------------- | ---------------------------------------- |
| **AWS**    | Nitro Card      | 网络虚拟化 (ENI)、EBS 存储加速、安全隔离 |
| **Azure**  | SmartNIC (FPGA) | SDN 转发、分布式防火墙、存储加速         |
| **阿里云** | eRDMA / 神龙    | ERDMA 协议卸载、存储网络加速、安全       |

### 8.2 典型使用场景

```
场景 1: 公有云网络虚拟化 (AWS Nitro 为例)
═══════════════════════════════════════════════

  之前 (所有东西跑在 Host 上):
  ┌─────────────────────────────────────────────────┐
  │  Host CPU:                                       │
  │  - Xen/KVM 虚拟化开销                             │
  │  - 虚拟交换 (OVS)                                │
  │  - 虚拟存储网关 (iSCSI)                           │
  │  - 安全组规则匹配                                 │
  │  - 监控数据采集                                   │
  │  → 只有 60-70% CPU 可以卖给用户                   │
  └─────────────────────────────────────────────────┘

  现在 (Nitro Card / DPU):
  ┌─────────────────────────────────────────────────┐
  │  Host CPU:                                       │
  │  - KVM 虚拟化 (精简版)                            │
  │  - 其他全卸载到 Nitro Card                        │
  │  → 95%+ CPU 可以卖给用户                          │
  │  → 用户 VM 性能接近裸金属                         │
  └─────────────────────────────────────────────────┘


场景 2: 电信 5G UPF (用户面功能)
═══════════════════════════════════

  传统: UPF 跑在 x86 服务器上，DPDK 处理 GTP 隧道
  → 每台服务器处理几十 Gbps

  DPU: UPF 的 GTP 封装/解封装卸载到 DPU
  → 同样服务器处理几百 Gbps
  → 更重要的是：5G UPF 通常部署在边缘机房，CPU 资源非常宝贵


场景 3: 企业零信任安全
═══════════════════════

  DPU 上跑微分段防火墙 (Micro-segmentation):
  - 每个 VM 的东西向流量都经过 DPU 上的防火墙
  - Host CPU 完全不参与
  - 即使 VM 被攻破，攻击者也无法绕过 DPU 上的安全策略
```

### 9.1 DPU 的定位

```
DPDK 生态中的 DPU 定位
══════════════════════════════════════════════════════════════════════════════

  DPDK 技术栈:

  ┌─────────────────────────────────────────────────────────────┐
  │  应用层: 防火墙、负载均衡、网关、存储网关                    │
  ├─────────────────────────────────────────────────────────────┤
  │  框架层: OVS-DPDK、SPDK、VPP                                │
  ├─────────────────────────────────────────────────────────────┤
  │  抽象层: DPDK (PMD、mbuf、ring、mempool)                    │
  ├─────────────────────────────────────────────────────────────┤
  │  跑在哪里？                                                  │
  │                                                              │
  │  ┌──────────────┐        ┌──────────────┐                  │
  │  │  Host x86     │        │  DPU ARM     │                  │
  │  │  (传统部署)    │        │  (卸载部署)   │                  │
  │  │              │        │              │                  │
  │  │  适用: 小规模  │        │  适用: 大规模  │                  │
  │  │  简单场景      │        │  云/电信场景   │                  │
  │  │  开发调试方便  │        │  性能极致要求  │                  │
  │  └──────────────┘        └──────────────┘                  │
  ├─────────────────────────────────────────────────────────────┤
  │  硬件层: NIC / SmartNIC / DPU                                │
  └─────────────────────────────────────────────────────────────┘
```

### 9.2 DPU 不是万能的

| 适合 DPU                    | 不适合 DPU                       |
| --------------------------- | -------------------------------- |
| 大规模虚拟化（几十+ VM/机） | 单机或少量 VM                    |
| 云/电信基础设施             | 边缘计算（功耗/成本敏感）        |
| 网络密集型应用              | 计算密集型应用（DPU ARM 性能弱） |
| 安全/合规要求高             | 开发测试环境                     |
| 需要 100Gbps+ 线速          | 1G/10G 小带宽场景                |

### 9.3 DPU vs FPGA

|              | DPU                     | FPGA                           |
| ------------ | ----------------------- | ------------------------------ |
| **编程方式** | C/Python (Linux API)    | Verilog/VHDL (硬件描述语言)    |
| **开发门槛** | 低（会 Linux 编程即可） | 高（需要硬件设计经验）         |
| **灵活性**   | 高（随时更新软件）      | 极高（可重新编程硬件逻辑）     |
| **性能**     | 高（有专用加速引擎）    | 极高（精确到纳秒级时序控制）   |
| **生态**     | 快速成长中              | 成熟但小众                     |
| **典型用途** | 通用基础设施卸载        | 协议解析、低延迟交易、网络测试 |

### 9.4 核心要点回顾

1. **DPU 是什么**：带独立 CPU 和操作系统的网卡，能运行完整的网络/存储/安全软件
2. **为什么需要**：云计算中基础设施任务吃掉 20-30% Host CPU，DPU 把这些任务搬走
3. **怎么工作**：ARM CPU + 独立内存 + 硬件加速引擎，通过 PCIe 连接 Host
4. **和 DPDK 的关系**：DPDK 可以跑在 DPU ARM 上，API 基本不变
5. **和 VDPA 的关系**：VDPA 是 DPU 给 VM 提供 virtio 后端的标准方式，数据路径完全硬件化
6. **谁在用**：AWS Nitro、Azure SmartNIC、阿里云神龙等
