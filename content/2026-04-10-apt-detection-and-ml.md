# APT检测与机器学习：实战方法论

## 1. APT是什么？

**APT = Advanced Persistent Threat**（高级持续性威胁）

由组织化的攻击者（通常是国家级或大型网络犯罪集团）对特定目标进行的长期、隐蔽、高度定制化的攻击。

### APT的三个关键词

| 关键词 | 含义 |
|--------|------|
| **Advanced** | 使用0day漏洞、定制恶意软件、社会工程学等高级攻击技术 |
| **Persistent** | 长期潜伏，持续数月甚至数年，难以被发现 |
| **Threat** | 有组织、有目标的威胁，不随机 |

### APT攻击链 (Kill Chain)

```
情报搜集 → 武器构建 → 传输投递 → 漏洞利用 → 持久化植入 → 命令控制 → 目标达成
```

### APT检测的核心挑战

```
问题:
├── 攻击者会适应检测 (对抗性)
├── 网络环境会变化 (新业务/新协议)
├── 基线会漂移 (正常行为也在变)
└── 平均潜伏期约197天，传统设备检测不到这种"慢速隐形攻击"
```

## 2. APT检测需要什么？

### 2.1 数据采集层（全量流量可见性）

```
┌─────────────────────────────────────────────┐
│           网络流量采集                        │
├─────────────────────────────────────────────┤
│  Full Packet Capture (pcap存储)             │
│  NetFlow/IPFIX (流记录)                      │
│  Zeek Logs (结构化日志)                      │
│  DNS/HTTP/SMTP等协议日志                      │
│  终端Telemetry (OSquery、WMI、ETW)           │
└─────────────────────────────────────────────┘
```

### 2.2 分析引擎层

| 工具 | 用途 |
|------|------|
| **Suricata/caracal** | 规则检测（已知威胁签名） |
| **Zeek** | 协议解析，生成结构化日志 |
| **RITA** | Beaconing检测（C2通信模式） |
| **Elastic ML** | 异常检测模型 |
| **MISP** | 威胁情报共享 |

### 2.3 核心检测场景

1. **C2通信检测（Beaconing）**：请求间隔规律性分析
2. **横向移动检测**：SMB/SSH/RDP异常认证
3. **数据外泄检测**：DNS隧道、异常外发流量
4. **持久化检测**：计划任务、Registry修改

## 3. Suricata vs Zeek：检测引擎的分工

### Suricata的设计定位

```
Suricata: 规则匹配引擎
├── 优点: 多线程、高性能、并发流处理
├── 擅长: 已知威胁签名匹配 (规则驱动)
└── 局限: 无状态检测，无法跟踪"行为序列"
```

**Suricata能做到的**：检查单个数据包/流是否符合规则定义的特征

**Suricata做不到的**：

| 场景 | Suricata能检测吗 | 为什么 |
|------|-----------------|--------|
| 同一IP在24小时内请求了200个不同域名 | ❌ | 需要时间窗口聚合统计 |
| beaconing: 请求间隔呈60s周期性规律 | ❌ | 需要傅里叶变换/熵分析 |
| 横向移动: 同一用户24h内登录10+台主机 | ❌ | 需要跨流状态关联 |
| 异常行为基线: 该主机平时不产生DNS流量 | ❌ | 需要历史基线对比 |

### Zeek的解析原理

Zeek的核心是一个**被动协议解析器**，不是基于签名匹配，而是**理解协议结构**。

```
pcap二进制数据
      │
      ▼
┌─────────────────────────────────┐
│ 1. Packet Analysis (packet分析) │
│    - IP fragmentation reassembly│
│    - TCP stream reassembly      │
└─────────────────────────────────┘
      │
      ▼
┌─────────────────────────────────┐
│ 2. Protocol State Machine       │
│    - 按协议规范解析每个字段       │
└─────────────────────────────────┘
      │
      ▼
结构化日志文件 (.log)
```

### 两者互补

```bash
# 最佳实践：同时使用
zeek -r capture.pcap           # 生成结构化日志
suricata -r capture.pcap       # 生成告警
```

## 4. 机器学习在APT检测中的应用

### 4.1 流量特征工程

```python
# 流量特征示例 (可用于随机森林/XGBoost)
features = {
    # 统计特征
    'flow_duration': 流量持续时间,
    'packet_count': 数据包数量,
    'byte_count': 字节总数,
    'mean_packet_size': 平均包大小,
    
    # 时序特征
    'inter_arrival_time_entropy': 到达间隔熵,
    
    # DNS专有特征  
    'unique_domains': 不同域名数,
    'domain_query_count': DNS查询次数,
}
```

### 4.2 主流算法

| 算法 | 适用场景 | 优缺点 |
|------|----------|--------|
| Random Forest | 流量分类、恶意流量检测 | 抗噪声、可解释 |
| XGBoost/LightGBM | 大规模流量分类 | 高精度、速度快 |
| Isolation Forest | 异常检测(无监督) | 不需要标签，适合未知威胁 |
| LSTM/GRU | Beaconing时序分析 | 捕获间隔规律性 |

### 4.3 训练代价

```
传统ML (RF/XGBoost):
  - 数据量: 10万~1000万流记录
  - 训练时间: 5分钟 ~ 2小时
  - GPU需求: CPU即可

深度学习 (1D-CNN/LSTM):
  - 数据量: 100万~1亿流记录
  - 训练时间: 2小时 ~ 3天
  - GPU需求: 1张GPU (RTX 3080级别)
```

**结论**：网络流量特征相对简单，**不需要GPT级别的大模型**。

## 6. 误报问题：ML落地APT检测的核心痛点

```
黑盒模型的悲剧:

1000条告警
   │
   ├── 950条误报 (正常行为被标记异常)
   ├── 45条可疑 (需要人工研判)
   └── 5条真APT (往往被淹没在噪音里)
```

### 误报率高的原因

1. **正常≠异常**：正常行为也有波动/噪声
2. **边界模糊**：真实流量是软边界，中间地带误判
3. **训练数据偏差**：公开数据集不代表你的网络
4. **对抗性**：攻击者可以慢慢适应，降低请求频率躲避检测

### 解决方案

| 方案 | 解决什么问题 |
|------|-------------|
| XAI (SHAP/LIME) | 告诉分析师"为什么报警" |
| 分层过滤 | 规则过滤噪音，ML处理剩余 |
| 知识图谱 | 攻击链上下文辅助研判 |
| 阈值调优 | 可控的误报率 |

## 7. 模型会"过期"

```
一次性（训练阶段）:
  数据收集 → 特征工程 → 模型训练 → 验证测试 → 部署
       │
       └─────────────────┘
              ↓
        模型文件(.pt/.pkl)
        一次性产出
       
持续运营（推理阶段）:
  实时流量 → 特征提取 → 模型推理 → 告警
       │
       └──── 定期重训练 ◄───┘
              ↑
         模型漂移
         (攻击手法变了)
```

## 10. 内网横向移动检测

### 10.1 什么是横向移动

攻击者突破边界后，在内网中**从一台主机横向渗透到另一台主机**的过程。

```
传统攻击链:
Initial Compromise → Privilege Escalation → [Lateral Movement] → Goal

真实场景:
外部攻击者
      │
      ▼
  边界突破 (钓鱼/漏洞/RCE)
      │
      ▼
  第一台服务器 (Web服务器/邮件服务器)
      │
      ▼ ← 横向移动 ←────────────────┐
  第二台主机 (域控制器/数据库)        │
      │                              │
      ▼                              │
  第三台主机 (核心业务系统)───────────┘
```

### 10.2 横向移动核心手法

#### 凭证传递

| 技术 | 说明 |
|------|------|
| **Pass-the-Hash (PtH)** | 使用NTLM Hash而非明文密码认证 |
| **Pass-the-Ticket (PtT)** | 使用Kerberos票据冒充用户 |
| **Kerberoasting** | 请求服务票据并离线破解 |

#### 远程服务/协议

| 协议 | 用途 |
|------|------|
| **SMB/WSMAN** | 远程执行命令 |
| **RDP** | 远程桌面 |
| **SSH** | 远程Shell |
| **WinRM** | Windows远程管理 |
| **DCOM/PSRemoting** | PowerShell远程执行 |

#### 常用工具

| 工具 | 用途 |
|------|------|
| **Mimikatz** | 凭证提取/PtH/PtT |
| **Cobalt Strike** | C2 + 横向移动 |
| **CrackMapExec** | 多协议横向测试 |
| **BloodHound** | AD攻击路径分析 |
| **Impacket** | SMB/WMI/ADC攻击套件 |

### 10.3 Zeek日志检测横向移动

Zeek全流量解析是横向移动检测的**数据源泉**。

```
Zeek能做的:
├── connection.log    (会话)
├── smb_mapping.log    (SMB访问)
├── smb_files.log     (SMB传输)
├── rdp.log           (RDP会话)
├── ssh.log           (SSH连接)
├── kerberos.log      (Kerberos票据)
└── auth.log          (认证)
```

#### SMB横向检测

```bash
# 检测: 同一源主机访问大量不同目标 (枚举行为)
zeek-cut orig_h resp_p resp_h < smb_mapping.log \
  | awk '{print $1, $3}' | sort | uniq \
  | cut -d' ' -f1 | sort | uniq -c \
  | sort -rn | head -10

# 检测: SMB文件传输大量数据
zeek-cut filename fuid tx_host rx_host bytes_total \
  < smb_files.log \
  | awk '$5 > 10485760 {print}'  # >10MB
```

#### RDP横向检测

```bash
# 检测: 同一客户端连接多个不同服务器 (RDP跳转)
zeek-cut id.orig_h id.resp_h cookie < rdp.log \
  | cut -d' ' -f1,3 | sort | uniq \
  | cut -d' ' -f1 | sort | uniq -c \
  | sort -rn | head -10
```

#### SSH/RDP暴力破解检测

```bash
# 检测: SSH暴力破解
zeek-cut id.orig_h id.resp_h auth.success auth.failure \
  < ssh.log \
  | awk '{if($3==0 && $4>10) print "SSH Brute:", $1, "->", $2}'

# 检测: 同一用户从多IP登录
zeek-cut id.orig_h id.resp_h username \
  < auth.log 2>/dev/null \
  | awk '{print $3}' | sort | uniq -c | sort -rn
```

### 10.4 横向移动流量特征

```
真实横向移动流量中会出现的协议组合:

Protocol Mix:
├── SMB (445)      ← 文件共享/远程执行
├── RDP (3389)     ← 远程桌面
├── SSH (22)       ← Linux横向
├── WinRM (5985/5986)  ← Windows远程管理
├── DCERPC (135)   ← 端点间通信
└── Kerberos (88)  ← 域认证

典型时序:
T0: 攻击者 -> 跳板机 (初始入侵)
T1: 跳板机 -> 域控 (Kerberos认证，获取票据)
T2: 跳板机 -> 文件服务器 (SMB访问，横向移动)
T3: 跳板机 -> 数据库 (凭证传递，数据窃取)
```

### 10.5 横向移动检测矩阵

| 检测维度 | 技术手段 | 难度 |
|----------|----------|------|
| 网络流量 | SMB/RDP/SSH异常 | 中 |
| 认证日志 | 事件ID分析 | 低 |
| 进程行为 | Sysmon/EDR | 高 |
| 票据痕迹 | Kerberos日志 | 中 |
| 资产关系 | BloodHound | 低 |

### 10.6 横向移动数据集

| 数据集 | 说明 |
|--------|------|
| **CICIDS2017** | SMB枚举/RDP暴力，入门首选 |
| **DARPA TC** | 最高质量，需申请 |
| **Mordor** | ATT&CK映射，贴近实战 |
| **Caldera模拟** | 最高真实感，可控 |

### 10.7 Zeek脚本示例：横向移动检测

```zeek
# 检测: 同一源IP在短时间内连接多个不同目标445端口
global smb_conns: set[addr] = {};

event smb_mapping(c: connection, path: string, share_type: string) {
    if (c$id$resp_p == 445/tcp) {
        add smb_conns[c$id$resp_h];
        
        # 5分钟内连接超过10台不同主机 = 可疑
        if (|smb_conns| > 10) {
            print fmt("Potential SMB Lateral Movement from %s: %d hosts",
                      c$id$orig_h, |smb_conns|);
        }
    }
}
```

### 10.8 检测总结

```
横向移动的本质: 凭证/身份的跨主机使用

检测核心: 关联分析
├── 同一主体的行为串起来看
├── 而不是孤立的单点告警
└── 时间窗口 + 跨主机关联

Zeek是数据源泉，检测闭环还需要:
1. Zeek脚本 → 简单时间窗口检测
2. SIEM规则 → 跨日志关联分析
3. 威胁情报 → IoC匹配
4. 人工研判 → 最终判断
```

## 11. 数据泄漏检测

### 11.1 数据泄漏是APT的最终目的

```
APT攻击链最后阶段:
Initial Compromise → Privilege Escalation → Lateral Movement → [Data Exfiltration]

攻击者前期所有工作都是为了这一刻:
├── 横向移动获取更多主机权限
├── 提权获取高权限账户
└── 找到敏感数据位置 (数据库/文件服务器/邮件)
        │
        ▼
   数据打包 + 外传
```

### 11.2 数据泄漏主要途径

#### 网络通道

| 通道 | 原理 | 检测难度 |
|------|------|----------|
| **DNS隧道** | 数据编码在DNS查询中外传 | 高 (正常DNS也很多) |
| **ICMP隧道** | 数据封装在ICMP包中 | 中 |
| **HTTP/HTTPS上传** | 直接外发 | 低 (但量大难分辨) |
| **TLS加密通道** | 隐蔽的C2通道 | 高 |
| **FTP/SFTP** | 文件传输 | 中 |

#### 隐蔽通道

```
├── DNS隧道 (数据编码在子域名中)
├── Steganography (图片隐写)
├── 同源性攻击 (域前置/云API)
└── 协议封装 (IPv6隧道/VPN)
```

### 11.3 DNS隧道检测

**DNS隧道原理**:

```
正常DNS: client -> "google.com" -> server
DNS隧道: client -> "data.base64encoded.data.google.com" -> server
                    ↑ 敏感数据编码在子域名中
```

```bash
# 特征: DNS查询域名异常长 (>50字符)
tshark -r capture.pcap -Y "dns.qry.name.len > 50" \
  -T fields -e dns.qry.name -e ip.src

# 特征: DNS响应异常大 (>200字节)
tshark -r capture.pcap -Y "dns.resp.len > 200" \
  -T fields -e dns.resp.name -e dns.resp.addr

# 特征: TXT记录查询 (DNS隧道常用)
tshark -r capture.pcap -Y "dns.qry.type == 16" \
  -T fields -e dns.qry.name

# 特征: 同一IP大量不同DNS查询 (域旋转)
zeek-cut id.orig_h query_count \
  < dns.log 2>/dev/null \
  | awk '$2 > 1000 {print "High DNS Query:", $1, $2}'
```

### 11.4 大文件外传检测

```bash
# 检测: 单个大文件上传 (>100MB)
zeek-cut tx_host rx_host filename bytes_total \
  < smb_files.log http_files.log 2>/dev/null \
  | awk '$4 > 104857600 {print}'  # >100MB

# 检测: 短时间内大量数据外传
zeek-cut id.orig_h id.resp_h orig_bytes resp_bytes \
  < connection.log \
  | awk '{if($3 > 10485760 || $4 > 10485760) print}'  # >10MB

# 检测: 非工作时间大量上传
# 正常: 工作日9-18点
# 可疑: 凌晨3点大量数据外传
```

### 11.5 HTTP/HTTPS异常检测

```bash
# 检测: 上传数据量明显大于下载
zeek-cut id.orig_h id.resp_h resp_bytes orig_bytes \
  < http.log 2>/dev/null \
  | awk '{if($3 > 0 && $4/$3 > 10) print "High Upload Ratio:", $1, "->", $2}'

# 检测: User-Agent异常
zeek-cut user_agent host uri \
  < http.log 2>/dev/null \
  | awk '{print $1}' | sort | uniq -c | sort -rn

# 检测: POST到非常见目的地
zeek-cut host method uri \
  < http.log 2>/dev/null \
  | awk '$2 == "POST" {print}' | head -20
```

### 11.6 DNS隧道 Zeek 脚本检测

```zeek
# DNS隧道检测: 同一源IP短时间内大量不同域名查询
global dns_queries: set[string] = {};

event dns_query(c: connection, msg: dns_msg, query: string) {
    # 超过50字符的域名 = 可疑
    if (|query| > 50) {
        print fmt("Long DNS Query: %s -> %s (%d chars)", 
                  c$id$orig_h, query, |query|);
    }
    
    # 大量子域名查询 = 域旋转
    add dns_queries[query];
    if (|dns_queries| > 500) {
        print fmt("Potential DNS Tunneling from %s: %d unique queries",
                  c$id$orig_h, |dns_queries|);
    }
}
```

### 11.7 数据泄漏检测矩阵

| 检测维度 | 技术手段 | 说明 |
|----------|----------|------|
| DNS隧道 | 域名长度/熵/频率 | 隐蔽性强，难检测 |
| 大量数据外传 | NetFlow/Zeek | 明显但量大难分析 |
| 非工作时间传输 | 时间分析 | 简单有效 |
| 加密通道 | JA3/TLS指纹 | 需威胁情报配合 |
| 协议异常 | 协议解析 + 基线对比 | 需建立正常基线 |

### 11.8 数据泄漏典型告警

```
告警1: DNS隧道怀疑
  源IP: 192.168.1.100
  特征: 查询域名长度>80字符，含Base64字符集
  频率: 1000次/分钟
  结论: 高度可疑

告警2: 大量数据外传
  源IP: 192.168.1.50
  目标: 1.2.3.4 (非已知服务IP)
  流量: 上行500MB/小时
  时间: 凌晨03:00

告警3: 非标准协议外传
  协议: FTP到外部IP
  用户: backup_svc
  文件: customer_db_2026.sql (2.3GB)
  时间: 周六02:00
```

### 11.9 数据泄漏数据集

| 数据集 | 说明 |
|--------|------|
| **CICIDS2017** | Web数据外泄，入门首选 |
| **ISCX-VPN** | VPN隧道数据外泄检测 |
| **ISCX-Tor** | Tor匿名网络数据外泄 |
| **USTC-TFC** | 加密流量数据外泄 |
| **DNS隧道自模拟** | 自定义DNS隧道场景 |

### 11.10 数据泄漏流量特征

```
DNS隧道典型特征:
├── 查询域名长度: 100-500字符 (正常: <30)
├── 同一客户端大量TXT/NULL查询
├── 域名Base64字符集分布异常
└── 请求频率: 1000+/分钟

HTTP外泄典型特征:
├── POST流量远超GET
├── Content-Type异常
├── User-Agent与业务不符
└── 上传目标IP非已知服务

加密外泄典型特征:
├── JA3指纹非主流浏览器
├── 证书异常 (自签名/新注册域名)
├── 流量到已知恶意IP
└── 连接时长异常 (长驻留)
```

### 11.11 数据泄漏检测总结

```
数据泄漏检测核心:

1. DNS隧道 → 域名特征 + 请求频率
2. 大量外传 → NetFlow + 时间分析
3. 加密通道 → TLS指纹 + 威胁情报
4. 协议异常 → 协议解析 + 基线对比

最佳实践:
├── 正常业务基线建立 (平时流量什么样)
├── 异常阈值设置 (多大算异常)
├── 多维度关联 (单一特征不足以告警)
└── 人工研判确认 (避免误报)

核心本质: 数据泄漏检测是异常流量模式发现
         正常业务不应该有大量数据外传
```

## 12. 异常外联检测

### 12.1 什么是异常外联

**异常外联** = 内网主机主动连接**不应该或不需要联系**的外部网络的行为。

```
正常外联:
┌──────────┐         ┌──────────┐
│  内网主机 │ ──────> │  互联网   │
└──────────┘         │  正常服务  │
                      │ (百度/钉钉)│
                      └──────────┘

异常外联:
┌──────────┐         ┌──────────┐
│  内网主机 │ ──────> │  境外IP   │ ← 不应该联系
└──────────┘         │  TOR出口  │
                      │  C2服务器  │ ← 恶意地址
                      │  扫描器   │
                      └──────────┘
```

### 12.2 正常外联 vs 异常外联

| 维度 | 正常外联 | 异常外联 |
|------|----------|----------|
| 目的地 | 已知服务 (百度/阿里云/企业SaaS) | 未知IP/境外/黑名单 |
| 频率 | 稳定可预测 | 突发/异常时段 |
| 端口 | 80/443/业务端口 | 非标准端口 |
| 数据量 | 符合业务模型 | 异常大或异常小 |
| 响应 | 正常的Response | 异常响应/无响应 |
| TLS证书 | 正常CA签发 | 自签名/新注册 |

### 12.3 异常外联典型场景

#### 恶意软件外联 (最常见)

```
主机被植入木马/后门:
├── 木马启动 → 连接C2服务器
├── 报告失陷状态 → 等待指令
├── 下载更多恶意组件
└── 外传窃取的数据

特征:
├── 连接到已知恶意IP/域名
├── 连接到新注册域名 (刚注册1周内)
├── 非工作时间连接
└── TLS JA3指纹匹配已知恶意软件
```

#### 僵尸网络通信 (Botnet C2)

```
受控主机 (Bot):
├── 定期向C2服务器发送Beacon
├── 等待指令 (DDoS/挖矿/垃圾邮件)
└── 攻击其他目标 (作为Botnet一部分)

特征:
├── 周期性请求间隔
├── 连接到TOR出口节点
├── 连接到IRC/C2协议端口
└── 异常的上行流量比例
```

#### 数据外泄前奏

```
攻击者远程下载敏感数据:
├── 横向移动到数据库服务器
├── 打包数据
└── 通过异常外联外传

特征:
├── 大量上行数据
├── 连接到境外IP
├── 非工作时间
└── 连接到云存储服务 (非常用)
```

#### 扫描/探测行为

```
内网主机被控后探测外网:
├── 扫描外网IP段
├── 扫描特定端口
├── 暴力破解外网服务
└── 作为攻击跳板

特征:
├── 大量短连接
├── 连接多个不同IP
├── SYN扫描特征
└── 无正常应用层交互
```

### 12.4 异常外联检测方法

#### 威胁情报匹配

```bash
# 连接已知恶意IP
zeek-cut id.orig_h id.resp_h id.resp_p \
  < connection.log \
  | grep -E "^(境外IP|TOR出口|C2服务器)"

# JA3指纹匹配恶意软件
# ssl.log中的 ja3 字段对比黑名单

# 新注册域名检测
# 连接注册时间 < 30天的新域名
```

#### 基线对比

```bash
# 正常外联基线 (企业已知的正常互联网服务)
正常外联:
  - *.baidu.com, *.aliyun.com, *.钉钉.com
  - AWS/GCP/Azure 中国区
  - 企业自建SaaS服务

# 检测: 超出基线的外联
zeek-cut id.orig_h id.resp_h id.resp_p \
  < connection.log \
  | awk '不符合基线规则 {print}'
```

#### 统计异常

```bash
# 检测: 主机外联IP数量异常
zeek-cut id.orig_h id.resp_h \
  < connection.log \
  | awk '{print $1}' | sort | uniq \
  | while read host; do
    count=$(grep "^$host" connection.log | wc -l)
    if [ $count -gt 阈值 ]; then echo "$host: $count"; fi
done

# 检测: 非工作时间外联
# 正常: 工作日9:00-18:00
# 异常: 凌晨3点大量外联
```

### 12.5 异常外联检测框架

```
┌─────────────────────────────────────────┐
│         内网主机外联流量                  │
└─────────────────────────────────────────┘
                    │
                    ▼
┌─────────────────────────────────────────┐
│         威胁情报匹配 (第一层)              │
│  ├── 黑名单IP (威胁情报Feed)             │
│  ├── 黑名单域名 (MISP/OTX)              │
│  └── JA3指纹黑名单                      │
└─────────────────────────────────────────┘
                    │ 无匹配
                    ▼
┌─────────────────────────────────────────┐
│         基线对比 (第二层)                  │
│  ├── 正常服务白名单                      │
│  ├── 已知可信IP段                        │
│  └── 业务基线对比                        │
└─────────────────────────────────────────┘
                    │ 超出基线
                    ▼
┌─────────────────────────────────────────┐
│         统计异常检测 (第三层)              │
│  ├── 外联IP数量/频率异常                 │
│  ├── 流量大小异常                        │
│  └── 时间维度异常                        │
└─────────────────────────────────────────┘
                    │ 异常
                    ▼
              告警 + 研判
```

### 12.6 典型告警

```
告警1: 恶意软件C2通信
  主机: 192.168.1.100
  目标: 185.234.x.x (已知C2 IP)
  端口: 443
  时间: 凌晨03:00
  频率: 每30秒一次
  结论: 高度可疑

告警2: 新注册域名通信
  主机: 192.168.1.50
  目标域名: xj3k4h7.com (注册7天)
  端口: 80
  结论: 新注册域名，联系威胁情报

告警3: 境外连接
  主机: 192.168.1.80
  目标: 俄罗斯/乌克兰IP段
  端口: 443
  结论: 跨境非常用连接，需确认业务必要性
```

### 12.7 异常外联 vs 数据泄漏

```
异常外联 = 检测阶段 (主机不应该联系外部)
    │
    ├── 恶意软件C2
    ├── 僵尸网络通信
    └── 扫描探测行为

数据泄漏 = 结果阶段 (数据正在外传)
    │
    ├── DNS隧道外泄
    ├── HTTP上传外泄
    └── 加密通道外泄

关系:
异常外联可能是数据泄漏的前奏
但异常外联 ≠ 一定是数据泄漏
数据泄漏也不一定伴随异常外联 (也可能通过正常外联)
```

### 12.8 异常外联数据集

| 数据集 | 说明 |
|--------|------|
| **Malware Traffic Analysis** | 持续更新真实C2流量，最实用 |
| **CTU-13** | 13个僵尸网络家族，含C2通信模式 |
| **C2数据库** | abuse.ch，Zeek日志格式的C2流量 |
| **CICIDS2017** | 含部分恶意通信 |
| **Caldera自模拟** | 完全可控的C2场景 |

### 12.9 异常外联流量特征

```
典型C2通信特征:
├── 固定间隔请求 (beaconing)
├── 无浏览器特征的HTTP请求
├── 非标准端口的TLS
├── 连接到新注册域名
├── JA3指纹匹配已知恶意软件
├── 连接到TOR出口节点
└── 异常的时间间隔

典型Botnet特征:
├── 周期性请求
├── IRC/C2协议
├── 大量短连接
└── 僵尸网络控制命令
```

### 12.10 异常外联检测总结

```
异常外联本质: 主机行为偏离预期

检测核心:
1. 威胁情报 (已知恶意)
2. 基线对比 (已知正常)
3. 统计异常 (未知恶意)

最佳实践:
├── 建立正常外联基线 (白名单服务)
├── 接入高质量威胁情报 (MISP/商业TI)
├── 监控非工作时间外联
├── 关注JA3指纹异常
└── 定期审计外联IP分布
```

## 13. 总结

| 观点 | 说明 |
|------|------|
| **规则+TI是基础** | 持续运营，70-80%覆盖 |
| **ML是补充** | 不是替代，而是异常发现 |
| **分层检测架构** | 规则前置过滤 + ML处理剩余 + 人工研判 |
| **黑盒ML不能单独用** | 必须配合XAI解释 + 反馈闭环 |
| **模型是一次性的** | 训练一次，重训练是持续运营成本 |
| **横向移动检测** | Zeek全流量 + 关联分析 + 跨主机行为关联 |
| **数据泄漏检测** | 基线对比 + 多维特征 + 时间/流量/协议关联 |
| **异常外联检测** | 威胁情报 + 基线对比 + 统计异常 |

**核心观点**：黑盒ML不是不能用，而是**不能单独用**。必须配合规则前置过滤 + XAI解释 + 人工反馈闭环，才能真正落地。

横向移动检测的核心是**关联分析**——把同一主体的行为串起来看，而不是孤立的单点告警。

数据泄漏检测的核心是**异常流量模式发现**——正常业务不应该有大量数据外传、不应该有DNS隧道、不应该在凌晨3点有流量。

异常外联检测的核心是**主机行为偏离预期**——建立正常外联基线，超出基线的行为即为可疑。
