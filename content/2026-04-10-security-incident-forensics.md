# 安全事件溯源与取证：实战方法论

## 1. 溯源与取证的定义

### 1.1 溯源 (Threat Hunting / Attribution)

```
什么: 找出攻击的来源、路径、影响范围
目的: 理解攻击是怎么发生的
问题: 谁攻击了我? 从哪里来的? 用了什么手法?
```

### 1.2 取证 (Digital Forensics)

```
什么: 收集、固定、分析电子证据
目的: 证明发生了什么，为法律/合规提供证据
问题: 如何在法庭上证明这件事?
```

### 1.3 溯源 vs 取证对比

| 维度 | 溯源 | 取证 |
|------|------|------|
| **目的** | 理解攻击过程 | 固定法律证据 |
| **重心** | 技术还原 | 证据链完整性 |
| **要求** | 快，准，全 | 合法，完整，可信 |
| **输出** | 攻击链还原 | 取证报告 |
| **时间要求** | 实时/尽快 | 事后，讲究时效性 |

### 1.4 两者关系

```
溯源 = 回答"攻击是怎么发生的?"
取证 = 回答"如何证明这件事?"

好的溯源必须同时满足取证要求
```

## 5. 取证原则

```
取证四大原则:

1. 证据完整性 (Integrity)
   └── 取证过程不能改变原始证据
   └── 哈希校验 (MD5/SHA256)

2. 证据可追溯 (Chain of Custody)
   └── 谁在什么时候用什么工具做了什么
   └── 全程记录，审计日志

3. 取证合法性 (Legal)
   └── 授权取证 (员工隐私/数据保护)
   └── 符合司法管辖区规定

4. 分析可靠性 (Reliability)
   └── 工具校验
   └── 多人交叉验证
```

## 10. 适配工作量分析

### 10.1 适配阶段

```
适配工作量评估:

Phase 1: 基础部署 (1-2周)
├── 工具安装部署: 各工具官方文档
├── 数据源对接: Filebeat/Agent配置
└── 基本可视化: Kibana Dashboard

Phase 2: 数据关联 (2-4周)
├── 日志标准化: 字段映射统一
├── 时间同步: NTP + 日志时间戳对齐
├── 主机标识: hostname/uuid统一
└── 告警归一: 统一告警格式

Phase 3: 自动化 (4-8周)
├── 告警触发自动取证
├── 时间线自动构建
├── ATT&CK映射自动化
└── 报告自动生成

Phase 4: 持续优化 (持续)
├── 新工具集成
├── 规则调优
└── 流程完善
```

### 10.2 关键适配点

```
适配难点及工作量:

1. 数据标准化 (工作量: 中)
   ├── 问题: 各工具日志格式不同
   ├── 解决: ECS (Elastic Common Schema)
   └── 例子: Zeek的duration vs Suricata的flow.age

2. 时间线关联 (工作量: 高)
   ├── 问题: 跨主机/跨工具时间对齐
   ├── 解决: 统一时间戳 + 主机时钟同步
   └── 工具: Timesketch / Plaso

3. 证据完整性 (工作量: 高)
   ├── 问题: 取证要求哈希校验/链式证据
   ├── 解决: 自动化哈希计算 + 操作审计
   └── 要求: 取证合规必须

4. ATT&CK映射 (工作量: 低-中)
   ├── 问题: 将告警映射到战术框架
   ├── 解决: MITRE ATT&CK工具/规则库
   └── 工具: ATT&CK Navigator / sigma规则

5. 自动化取证 (工作量: 高)
   ├── 问题: 告警触发后自动固定证据
   ├── 解决: SOAR/Playbook
   └── 工具: Shuffle / TheHive / Velociraptor
```

## 12. 典型案例：一次安全事件溯源

```
事件背景: 某公司服务器被攻陷，数据外泄

溯源过程:

Step 1: 发现异常
├── IDS告警: 某主机连接境外IP (异常外联)
├── DNS日志: 该主机查询了大量非常见域名
└── 流量监控: 该主机凌晨有大量上行流量

Step 2: 主机取证
├── 内存镜像: 发现恶意进程 msedgeupdate.exe
├── 硬盘镜像: 发现计划任务恶意脚本
├── 注册表: 发现Run键持久化
└── 浏览器: 发现用户曾访问钓鱼网站

Step 3: 网络流量分析
├── Zeek解析: 木马连接C2域名 (新注册域名)
├── 流量重建: 确认数据外泄内容 (客户数据库)
└── C2关联: 该域名被标记为某APT组织

Step 4: 横向路径还原
├── 认证日志: 发现攻击者使用RDP横向
├── 文件日志: SMB传输了敏感文件
└── 时间线: 攻击者周末登录多台服务器

Step 5: 攻击者画像
├── IP归属: 攻击源IP位于东欧
├── 工具特征: 使用的木马与某APT组织特征吻合
├── TTPs: 符合APT29/APT41的攻击手法
└── 动机: 商业间谍可能性高

溯源结论:
攻击者通过钓鱼邮件获取员工凭证
```
