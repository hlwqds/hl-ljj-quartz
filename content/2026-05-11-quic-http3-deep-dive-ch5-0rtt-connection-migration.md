## 2. 0-RTT 详解

### 2.1 0-RTT 原理

```
0-RTT 原理：

┌──────────────────────────────────────────────────────────────────────┐
│                        0-RTT 数据                                    │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   前提：                                                            │
│   · 客户端有之前会话的 PSK (Pre-Shared Key)                         │
│   · 服务器有相同的 resumption ticket                                │
│                                                                      │
│   原理：                                                            │
│   · PSK 直接派生 0-RTT 密钥                                        │
│   · 无需等待 ServerHello                                           │
│   · 可以在首个 RTT 内发送应用数据                                   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘

与 1-RTT 对比：

┌──────────────────────────────────────────────────────────────────────┐
│                        1-RTT vs 0-RTT                              │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   1-RTT:                                                          │
│   Client ── Initial[CH] ────────────────────────────────────────►   │
│         ◄── Initial[SH] ────────────────────────────────────────   │
│         ◄── Handshake[SFIN] ────────────────────────────────────   │
│   Client ── 1-RTT[data] ────────────────────────────────────────►   │
│                                                                      │
│   Total: 1 RTT (数据传输)                                          │
│   Delay: 1 RTT (握手) + 1 RTT (数据) = 2 RTT                      │
│                                                                      │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   0-RTT:                                                          │
│   Client ── Initial[CH] + 0-RTT[data] ──────────────────────────►   │
│         ◄── Initial[SH] ────────────────────────────────────────   │
│         ◄── Handshake[SFIN] ────────────────────────────────────   │
│   Client ── 1-RTT[data] ────────────────────────────────────────►   │
│                                                                      │
│   Total: 0 RTT (数据传输，在首个包中)                                │
│   Delay: 1 RTT (握手) + 0 RTT (数据) = 1 RTT                      │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### 2.2 PSK 和 Ticket

```
PSK 与 Ticket：

┌──────────────────────────────────────────────────────────────────────┐
│                        Session Ticket                                │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   服务器在 TLS Finished 后发送 session ticket：                       │
│                                                                      │
│   Session Ticket 结构：                                             │
│   ┌────────────────────────────────────────────────────────────┐     │
│   │  ticket_lifetime: 票据有效期                                 │     │
│   │  ticket_age_add: 混淆 ticket age                           │     │
│   │  ticket_nonce: 防重放                                       │     │
│   │  ticket: 加密的 ticket 数据                                 │     │
│   │    └── 包含:                                                │     │
│   │        · resumption_secret                                 │     │
│   │        · cipher_suite                                      │     │
│   │        · client_random                                     │     │
│   │        · server_config                                     │     │
│   └────────────────────────────────────────────────────────────┘     │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘

PSK 导出：

  // 从 ticket 导出 PSK
  early_secret = HKDF-Extract(
      salt = "QUIC 0-RTT",
      IKM = resumption_secret
  )

  // 派生 0-RTT 密钥
  0-RTT Client Write Key = HKDF-Expand-Label(
      early_secret,
      "quic 0rtt client 1rtt",
      "",
      16
  )

  0-RTT Client Write IV = HKDF-Expand-Label(
      early_secret,
      "quic 0rtt iv",
      "",
      12
  )
```

## 3. 0-RTT 重放风险

### 3.1 重放攻击场景

```
0-RTT 重放风险：

┌──────────────────────────────────────────────────────────────────────┐
│                        重放攻击场景                                  │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   1. 录制攻击                                                       │
│      Attacker ──── Initial[CH, 0-RTT[GET /order]] ────► Server     │
│                        │                                            │
│                        ◄────── Initial[SH]                          │
│                        ◄────── Handshake[SFIN]                      │
│                                                                      │
│   2. 重放给服务器                                                   │
│      Attacker ──── Initial[CH, 0-RTT[GET /order]] ────► Server     │
│                        (same 0-RTT data!)                            │
│                                                                      │
│   影响：                                                            │
│   · GET 请求被重放                                                  │
│   · POST 请求有更大问题                                             │
│   · 缓存污染攻击                                                   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### 3.2 重放防护

```
重放防护措施：

┌──────────────────────────────────────────────────────────────────────┐
│                        0-RTT 重放防护                               │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   服务端措施：                                                      │
│   1. Anti-replay cache                                             │
│      · 记录收到的 0-RTT ClientHello hashes                          │
│      · 拒绝重复的 hash                                             │
│      · TTL = ticket_lifetime                                       │
│                                                                      │
│   2. One-time tickets                                              │
│      · Ticket 只能使用一次                                          │
│      · 使用后立即失效                                              │
│                                                                      │
│   3. 限制 0-RTT 用途                                               │
│      · HTTP/3: 只允许 idempotent 请求 (GET, HEAD, etc.)            │
│      · 禁止 POST, PUT, DELETE                                       │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘

Anti-replay Cache：

  // 服务端
  struct anti_replay {
      // 布隆过滤器或其他结构
      uint64_t seen_hashes[1024];

      // 添加 hash
      void add(uint64_t hash) {
          // 标记为已见
      }

      // 检查是否已见
      bool contains(uint64_t hash) {
          // 查询
      }
  };

  // 处理 0-RTT
  int handle_0rtt(struct connection *conn,
                 struct client_hello *ch) {
      uint64_t hash = sha256(ch);

      if (!anti_replay.contains(hash)) {
          // 首次见到，接受
          anti_replay.add(hash);
          return accept_0rtt;
      } else {
          // 重放，拒绝
          return reject_0rtt;
      }
  }
```

### 3.3 0-RTT Rejected

```
0-RTT 被拒绝的处理：

┌──────────────────────────────────────────────────────────────────────┐
│                        0-RTT Rejected                               │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   服务器发送 HelloRetryRequest：                                     │
│                                                                      │
│   Client ── Initial[CH, 0-RTT[data]] ──────────────────────────►   │
│   Client ── 0-RTT[data] ────────────────────────────────────────►   │
│                                                                      │
│              ◄── Initial[SH + HelloRetryRequest]                   │
│                                                                      │
│   客户端收到 HelloRetryRequest：                                     │
│   · 必须丢弃 0-RTT 密钥                                             │
│   · 必须丢弃 0-RTT 数据                                             │
│   · 重新发送 Initial (无 0-RTT)                                    │
│   · 发送 1-RTT 数据                                                │
│                                                                      │
│   最终结果：2 RTT (退化到 1-RTT)                                    │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

## 4. 连接迁移原理

### 4.1 为什么需要连接迁移

```
连接迁移需求：

┌──────────────────────────────────────────────────────────────────────┐
│                        网络切换场景                                  │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   移动设备网络切换：                                                │
│   · WiFi ──► 4G/5G                                               │
│   · 4G ──► WiFi                                                  │
│   · 同一网络切换 AP                                               │
│                                                                      │
│   IP 变化：                                                         │
│   · NAT 映射变化                                                   │

│                                                                      │
│   QUIC 解决方案：                                                   │
│   · 使用 Connection ID                                            │

### 4.2 Connection ID

```
Connection ID 机制：

┌──────────────────────────────────────────────────────────────────────┐
│                        Connection ID                                 │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   QUIC 使用 CID 而不是 4-tuple：                                    │
│   · src_connection_id: 发送方的 CID                                │
│   · dst_connection_id: 接收方的 CID                                │
│                                                                      │
│   优点：                                                            │
│   · 允许 IP/Port 变化                                             │
│   · 支持多路径                                                     │
│   · 防止流量窃听                                                   │
│                                                                      │
│   ┌────────────────────────────────────────────────────────────┐     │
│   │                                                            │     │
│   │  旧路径:                                                    │     │
│   │  Client (192.168.1.1:54321)                               │     │
│   │    └──► Server (1.2.3.4:443) CID=0xA1B2C3D4              │     │
│   │                                                            │     │
│   │  新路径:                                                    │     │
│   │  Client (10.0.0.50:65432)                                 │     │
│   │    └──► Server (1.2.3.4:443) CID=0xA1B2C3D4              │     │
│   │                                                            │     │
│   │  Connection ID 不变！连接保持！                           │     │
│   │                                                            │     │
│   └────────────────────────────────────────────────────────────┘     │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘

多 CID 设计：

  ┌─────────────────────────────────────────────────────────────────┐
  │                      多 Connection ID                           │
  ├─────────────────────────────────────────────────────────────────┤
  │                                                                  │
  │  服务器可以提供多个 CID：                                        │
  │  · 每个 CID 可以路由到不同的服务器进程                          │
  │  · 客户端使用不同的 CID 发送                                   │
  │  · 负载均衡                                                   │
  │                                                                  │
  │  NEW_CONNECTION_ID Frame:                                       │
  │  ┌─────────────────────────────────────────────────────────┐    │
  │  │  Sequence: varint (CID 序号)                           │    │
  │  │  Retire Prior To: varint (废弃的序号)                   │    │
  │  │  Connection ID: bytes                                   │    │
  │  │  Stateless Reset Token: 64 bytes                       │    │
  │  └─────────────────────────────────────────────────────────┘    │
  │                                                                  │
  └─────────────────────────────────────────────────────────────────┘
```

## 6. Stateless Reset

### 6.1 什么是 Stateless Reset

```
Stateless Reset：

┌──────────────────────────────────────────────────────────────────────┐
│                        Stateless Reset                               │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   背景：                                                            │
│   · 服务器无状态 (stateless)                                        │
│   · 服务器重启后不认识之前的连接                                    │
│   · 需要通知客户端连接已失效                                        │
│                                                                      │
│   解决方案：                                                        │
│   · 服务器发送带 token 的特殊包                                     │
│   · 客户端收到后识别为 stateless reset                               │
│   · 客户端重新建立连接                                              │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

### 6.2 Stateless Reset Token

```
Stateless Reset Token：

┌──────────────────────────────────────────────────────────────────────┐
│                        Reset Token                                  │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   生成：                                                            │
│   · 服务器为每个 CID 生成随机 token                                 │
│   · 存储 token 与 CID 的映射                                        │
│   · 通过 NEW_CONNECTION_ID 发送给客户端                             │
│                                                                      │
│   格式：                                                           │
│   ┌────────────────────────────────────────────────────────────┐     │
│   │  Token: 32 bytes (256 bits)                                │     │
│   └────────────────────────────────────────────────────────────┘     │
│                                                                      │
│   使用：                                                            │
│   · 当收到可疑包时，发送带 token 的短 header 包                     │
│   · Token 格式正确 → 客户端识别为 reset                            │
│   · Token 不正确 → 忽略                                            │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘

Stateless Reset 检测：

  // 客户端收到包
  bool detect_stateless_reset(u8 *packet, size_t len) {
      if (len < 21)  // 最小 QUIC 包长度
          return false;

      // 检查是否是短 header
      if (!(packet[0] & 0x80))
          return false;

      // 检查 token
      u8 *token = packet + len - 32;
      if (matches_known_token(token)) {
          // 这是 stateless reset!
          return true;
      }

      return false;
  }
```

### 6.3 Stateless Reset 发送条件

```
发送 Stateless Reset 的条件：

┌──────────────────────────────────────────────────────────────────────┐
│                        触发条件                                     │
├──────────────────────────────────────────────────────────────────────┤

│   服务器在以下情况发送 stateless reset：                           │

## 7. 迁移场景

### 7.1 WiFi 到 4G 迁移

```
WiFi 到 4G 迁移：

┌──────────────────────────────────────────────────────────────────────┐
│                        迁移场景                                     │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   1. 初始状态                                                      │
│      Client (WiFi: 192.168.1.100:54321)                           │
│        └──► Server (1.2.3.4:443) CID=0xAABBCCDD                  │
│                                                                      │
│   2. 检测到 WiFi 弱信号                                            │
│      · 发送 PATH_CHALLENGE                                        │
│      · 继续通过 WiFi 通信                                          │
│                                                                      │
│   3. WiFi 断开                                                     │
│      · Client 切换到 4G                                            │
│      · 新地址: 10.20.30.40:65432                                  │
│                                                                      │
│   4. 路径验证                                                      │
│      Client ── PATH_CHALLENGE ────────────────────────────► Server │
│        (从新地址发送)                                               │
│                                                              │
│         ◄─── PATH_RESPONSE (Server 从新地址回复)                   │
│                                                              │

## 9. 小结

```
QUIC Ch5 总结：

0-RTT:
  · PSK 导出 0-RTT 密钥
  · 无需等待 ServerHello
  · 首个 RTT 即可发送数据
  · 有重放风险
  · HTTP/3 只允许 idempotent 请求

重放防护:
  · Anti-replay cache
  · One-time tickets
  · HelloRetryRequest 拒绝
  · 0-RTT rejected → 退化到 1-RTT

连接迁移:
  · 使用 Connection ID (非 4-tuple)
  · IP/Port 变化不影响连接
  · 支持 WiFi↔4G 切换

路径验证:
  · PATH_CHALLENGE/PATH_RESPONSE
  · 验证新路径可达性
  · 超时重试机制

Stateless Reset:
  · 服务器无状态时的连接终止
  · 带 token 的特殊包
  · 客户端识别并重建连接
