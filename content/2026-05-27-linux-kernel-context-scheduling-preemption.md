# Linux 内核上下文、调度与抢占：完整图解

## 1. 什么是"执行上下文"

Linux 内核中，代码总是在某个"上下文"中执行。上下文决定了当前代码能做什么、不能做什么——能不能睡眠、能不能被抢占、能不能访问用户态内存。

这是理解 RCU、锁、中断处理等一切内核机制的基础。

### 1.1 两种核心上下文

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Linux 内核的执行上下文                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│                    ┌──────────────────────┐                             │
│                    │   进程上下文          │                             │
│                    │  (Process Context)    │                             │
│                    │                      │                             │
│                    │  代表某个进程/线程     │                             │
│                    │  执行系统调用或内核    │                             │
│                    │  例: sys_read()       │                             │
│                    └──────────┬───────────┘                             │
│                               │                                         │
│                    ┌──────────┴───────────┐                             │
│                    │   中断上下文          │                             │
│                    │ (Interrupt Context)   │                             │
│                    │                      │                             │
│                    │  不代表任何进程        │                             │
│                    │  由硬件中断或软件触发  │                             │
│                    │  例: 网卡收包中断      │                             │
│                    └──────────────────────┘                             │
│                                                                         │
│  最本质的区别:                                                         │
│  ┌──────────────────┬─────────────────────────────────────────┐         │
│  │                  │  进程上下文          │  中断上下文        │         │
│  ├──────────────────┼─────────────────────┼───────────────────┤         │
│  │ 代表谁           │ 某个进程/线程      │ 没有人（不属于任何  │         │
│  │                  │                     │   进程）           │         │
│  ├──────────────────┼─────────────────────┼───────────────────┤         │
│  │ current 指针     │ 指向当前进程       │ 指向被中断的进程   │         │
│  │                  │ （有效）           │ （但"不代表"它）   │         │
│  ├──────────────────┼─────────────────────┼───────────────────┤         │
│  │ 能否睡眠         │ 能                 │ 绝对不能           │         │
│  │                  │                     │                   │         │
│  ├──────────────────┼─────────────────────┼───────────────────┤         │
│  │ 能否被调度       │ 能（可能被抢占）   │ 不能               │         │
│  │                  │                     │                   │         │
│  ├──────────────────┼─────────────────────┼───────────────────┤         │
│  │ 能否访问用户内存 │ 能（需要 check）   │ 不能               │         │
│  │                  │                     │ （可能无效）       │         │
│  ├──────────────────┼─────────────────────┼───────────────────┤         │
│  │ 触发方式         │ 系统调用/异常/异常  │ 硬件中断/软中断    │         │
│  │                  │ 返回内核           │ /定时器           │         │
│  ├──────────────────┼─────────────────────┼───────────────────┤         │
│  │ 执行时间限制     │ 可长时间执行       │ 必须尽快完成       │         │
│  │                  │                     │ （影响系统响应）   │         │
│  └──────────────────┴─────────────────────┴───────────────────┘         │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 2. 进程上下文详解

### 2.1 进程在内核中的执行

当用户程序发起系统调用（如 `read()`、`write()`、`ioctl()`），CPU 从用户态切换到内核态，开始在**进程上下文**中执行内核代码。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    进程上下文的执行流程                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  用户进程 A:                                                            │
│                                                                         │
│  ┌────────────────────────────────────────────────────────────────┐     │
│  │ User Space                                                     │     │
│  │                                                                │     │
│  │  fd = open("file", O_RDONLY);     ← 系统调用                 │     │
│  │  ── syscall instruction ──                                     │     │
│  └────────────────────────────┬───────────────────────────────────┘     │
│                               │ CPU 特权级切换                           │
│                               │ Ring 3 → Ring 0                         │
│                               ▼                                        │
│  ┌────────────────────────────────────────────────────────────────┐     │
│  │ Kernel Space  (进程上下文)                                     │     │
│  │                                                                │     │
│  │  entry_SYSCALL_64:       ← 系统调用入口                       │     │
│  │    保存用户态寄存器到 pt_regs                                   │     │
│  │    设置 current = task A                                        │     │
│  │                                                                │     │
│  │  sys_open("file", O_RDONLY):  ← 真正的系统调用处理           │     │
│  │    getname()          → 可能访问用户内存                      │     │
│  │    vfs_open()         → 可能睡眠等 I/O                       │     │
│  │    filp_open()        → 调用文件系统                          │     │
│  │                                                                │     │
│  │  返回用户态:                                                    │     │
│  │    检查 need_resched → 如果需要，调用 schedule()              │     │
│  │    恢复用户态寄存器                                             │     │
│  │    iret / sysret 指令 → 回到 Ring 3                            │     │
│  └────────────────────────────┬───────────────────────────────────┘     │
│                               │ Ring 0 → Ring 3                         │
│                               ▼                                        │
│  ┌────────────────────────────────────────────────────────────────┐     │
│  │ User Space                                                     │     │
│  │  // fd 拿到了，继续执行                                      │     │
│  └────────────────────────────────────────────────────────────────┘     │
│                                                                         │
│  关键:                                                                  │
│  1. 内核代码执行时，current 始终指向 task A                          │
│  2. 如果 sys_open 中睡眠，调度器会切走 task A，运行其他任务         │
│  3. task A 恢复后，从睡眠点继续执行                                 │
│  4. 整个过程中内核代码"代表"task A 运行                            │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 2.2 进程上下文中可以做什么

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    进程上下文的能力                                     │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ✅ 可以:                                                              │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │  睡眠 (schedule())                                          │       │
│  │    → 等待 I/O、等待锁、等待事件                             │       │
│  │    → 调度器会切换到其他任务                                  │       │
│  │                                                              │       │
│  │  访问用户态内存                                              │       │
│  │    → copy_from_user() / copy_to_user()                       │       │
│  │    → 必须检查指针有效性 (access_ok())                       │       │
│  │                                                              │       │
│  │  持有互斥锁 (mutex)                                         │       │
│  │    → mutex_lock() 可能睡眠，所以只能用在进程上下文           │       │
│  │                                                              │       │
│  │  使用大块内存 (GFP_KERNEL)                                  │       │
│  │    → kmalloc(GFP_KERNEL) 可以睡眠等内存                     │       │
│  │                                                              │       │
│  │  长时间执行                                                  │       │
│  │    → 没有时间限制                                          │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  ⚠️ 注意:                                                              │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │  持有自旋锁期间不能睡眠                                       │       │
│  │  → spinlock 期间 current 不会被调度走                      │       │
│  │  → 如果在 spinlock 里睡眠 → 死锁!                          │       │
│  │                                                              │       │
│  │  禁用抢占期间不能睡眠                                        │       │
│  │  → preempt_disable() 后也不能 schedule()                    │       │
│  │  → 同理可能死锁                                             │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 3. 中断上下文详解

### 3.1 中断的分类

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    中断的完整分类                                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│                          中断 (Interrupt)                               │
│                        ┌──────┴──────┐                                  │
│                   硬中断            软中断                               │
│               (Hardware IRQ)    (Soft IRQ)                              │
│                 │    │              │                                    │
│          外部设备  CPU 异常      内核软件触发                            │
│          (网卡/磁盘) (缺页/除零)                                         │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  硬中断 (Hardware IRQ):                                     │       │
│  │  ═══════════════════════                                      │       │
│  │  - 由外部硬件设备触发                                       │       │
│  │  - 通过中断控制器 (APIC) 送达 CPU                            │       │
│  │  - CPU 立即响应，打断当前执行                               │       │
│  │  - 每个 IRQ 有编号 (0-255)                                  │       │
│  │  - 同一个 IRQ 在多个 CPU 上不能同时执行（默认）             │       │
│  │  - 执行时 preempt_count 自动增加 → 不能抢占                 │       │
│  │                                                              │       │
│  │  常见硬件中断:                                              │       │
│  │  - 网卡收包中断 (eth0 Rx interrupt)                         │       │
│  │  - 磁盘 I/O 完成中断 (NVMe completion)                      │       │
│  │  - 定时器中断 (Local APIC timer, HZ=250/1000)               │       │
│  │  - 键盘/鼠标中断                                            │       │
│  │                                                              │       │
│  ├──────────────────────────────────────────────────────────────┤       │
│  │                                                              │       │
│  │  软中断 (Soft IRQ):                                         │       │
│  │  ═════════════════════                                       │       │
│  │  - 由内核代码触发 (raise_softirq())                         │       │
│  │  - 在硬中断处理完成后、返回进程前执行                       │       │
│  │  - 同一个 softirq 可以在不同 CPU 上并行执行                 │       │
│  │  - 仍然在中断上下文中（不能睡眠）                           │       │
│  │                                                              │       │
│  │  预定义的 softirq 类型:                                     │       │
│  │  ┌────────────────────┬──────────────────────────────┐       │       │
│  │  │ HI_SOFTIRQ         │ 高优先级 tasklet              │       │       │
│  │  │ TIMER_SOFTIRQ      │ 定时器软中断                  │       │       │
│  │  │ NET_TX_SOFTIRQ     │ 网络发送                      │       │       │
│  │  │ NET_RX_SOFTIRQ     │ 网络接收 (napi_poll)         │       │       │
│  │  │ BLOCK_SOFTIRQ      │ 块设备 I/O                    │       │       │
│  │  │ IRQ_POLL_SOFTIRQ   │ I/O 轮询                      │       │       │
│  │  │ TASKLET_SOFTIRQ    │ 普通 tasklet                   │       │       │
│  │  │ SCHED_SOFTIRQ      │ 调度器                         │       │       │
│  │  │ HRTIMER_SOFTIRQ    │ 高精度定时器                   │       │       │
│  │  │ RCU_SOFTIRQ        │ RCU 回调执行                   │       │       │
│  │  └────────────────────┴──────────────────────────────┘       │       │
│  │                                                              │       │
│  ├──────────────────────────────────────────────────────────────┤       │
│  │                                                              │       │
│  │  Tasklet (基于 softirq):                                     │       │
│  │  ═════════════════════════                                    │       │
│  │  - 更易用的软中断封装                                       │       │
│  │  - 同一个 tasklet 不会同时在多个 CPU 上执行                 │       │
│  │  - 不同 tasklet 可以并行                                    │       │
│  │  - 仍在中断上下文（不能睡眠）                               │       │
│  │                                                              │       │
│  │  Workqueue (工作队列):                                       │       │
│  │  ═══════════════════                                           │       │
│  │  - 在进程上下文中执行！                                      │       │
│  │  - 由内核线程 (kworker) 执行                                 │       │
│  │  - 可以睡眠、可以长时间执行                                 │       │
│  │  - 适合把中断中的重活推迟到进程上下文                       │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.2 中断处理的完整流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    网卡收包的完整中断流程                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  时间线 ─────────────────────────────────────────────────────────►      │
│                                                                         │
│  CPU 0 正在执行进程 A 的 sys_read():                                    │
│                                                                         │
│  ────[进程 A: sys_read() 执行中]────────────────────────────             │
│                    │                                                    │
│                    │ ⚡ 网卡收到一个包                                  │
│                    │ 物理中断信号 → APIC → CPU 0                         │
│                    ▼                                                    │
│  ────[Hard IRQ handler]───                                             │
│  │  1. CPU 保存当前寄存器 (包括进程 A 的状态)                         │
│  │  2. preempt_count += HARDIRQ_OFFSET  (变成中断上下文)               │
│  │  3. 查找 IRQ handler: eth0_rx_interrupt()                          │
│  │  4. eth0_rx_interrupt():                                          │
│  │     - 从网卡 DMA 环形缓冲区取数据                                 │
│  │     - 分配 skb                                                    │
│  │     - 挂到 input_pkt_queue                                       │
│  │     - raise_softirq(NET_RX_SOFTIRQ)  ← 触发软中断                │
│  │     - napi_schedule()                                            │
│  │  5. acknowledge 中断给网卡                                       │
│  │  6. preempt_count -= HARDIRQ_OFFSET                              │
│  ────[硬中断结束]─────────                                             │
│                    │                                                    │
│                    │ 即将返回进程 A，但先检查 softirq pending            │
│                    ▼                                                    │
│  ────[Soft IRQ: NET_RX_SOFTIRQ]──                                     │
│  │  7. napi_poll() 执行                                              │
│  │     - 批量处理网卡队列中的包                                     │
│  │     - netif_receive_skb() → ip_rcv() → tcp_v4_rcv()              │
│  │     - 协议栈处理                                                 │
│  │  8. 所有 pending softirq 处理完                                   │
│  ────[软中断结束]─────────                                             │
│                    │                                                    │
│                    │ 检查 need_resched                                 │
│                    │ 如果有更高优先级任务就调度                         │
│                    ▼                                                    │
│  ────[进程 A: sys_read() 继续执行]───────────────────────               │
│                                                                         │
│  (进程 A 对这一切完全无感知)                                            │
│                                                                         │
│  额外说明: 如果软中断处理太慢:                                        │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  ksoftirqd/N 内核线程会接管                                  │         │
│  │  → 把 softirq 处理从硬中断返回路径移到独立线程             │         │
│  │  → 避免硬中断返回延迟过大                                   │         │
│  │  → ksoftirqd 仍然是进程上下文，可以被调度/抢占              │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.3 中断上下文的能力限制

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    中断上下文的限制                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ❌ 绝对不能做:                                                        │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  1. 睡眠 (schedule / mutex_lock / wait_event)               │       │
│  │     为什么？                                                │       │
│  │     - 没有可以调度的 task_struct                             │       │
│  │     - 如果睡眠，调度器不知道该把 CPU 给谁                  │       │
│  │     - 而且 current 指向的是被中断的进程，不是中断处理程序     │       │
│  │     - 内核有 might_sleep() 检查，会触发 WARNING              │       │
│  │                                                              │       │
│  │  2. 访问用户态内存                                          │       │
│  │     为什么？                                                │       │
│  │     - 当前正在中断上下文，不知道是哪个进程的用户空间          │       │
│  │     - 用户页表可能无效                                       │       │
│  │     - copy_from_user / copy_to_user 会导致缺页异常           │       │
│  │                                                              │       │
│  │  3. 持有互斥锁 (mutex)                                      │       │
│  │     为什么？                                                │       │
│  │     → mutex_lock() 内部可能睡眠                             │       │
│  │     → 只能用 spinlock（自旋等待，不睡眠）                   │       │
│  │                                                              │       │
│  │  4. 使用 GFP_KERNEL 分配内存                                 │       │
│  │     为什么？                                                │       │
│  │     → kmalloc(GFP_KERNEL) 在内存不足时会睡眠等待回收         │       │
│  │     → 必须用 GFP_ATOMIC（不睡眠，直接成功或失败）            │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  ✅ 可以做:                                                            │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │  - 使用自旋锁 (spinlock)                                    │       │
│  │    → 自旋等待，不睡眠，适合中断上下文                       │       │
│  │                                                              │       │
│  │  - 使用 GFP_ATOMIC 分配内存                                  │       │
│  │    → 从预分配的紧急内存池分配，不睡眠                       │       │
│  │    → 可能失败，需要检查返回值                               │       │
│  │                                                              │       │
│  │  - 注册软中断 / tasklet（推迟工作）                         │       │
│  │    → 硬中断中做最少的工作，重的活交给下半部                │       │
│  │                                                              │       │
│  │  - 使用 per-CPU 变量                                        │       │
│  │    → 不需要锁，天然受中断保护                               │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 4. 上半部与下半部

### 4.1 为什么需要分半

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    上半部 vs 下半部                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  问题: 硬中断会屏蔽同级中断                                            │
│  ─────────────────────────────                                          │
│                                                                         │
│  如果硬中断处理程序执行太久:                                            │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  Time ──────────────────────────────────────────────────►    │       │
│  │                                                              │       │
│  │  IRQ #17 (网卡):  ════════════════════════════════════════  │       │
│  │                  │  处理 500us! 太久了                       │       │
│  │                                                              │       │
│  │  包 2 到达 ──→ 被屏蔽，延迟了 500us!                       │       │
│  │  包 3 到达 ──→ 被屏蔽，延迟了 400us!                       │       │
│  │  包 4 到达 ──→ 被屏蔽，延迟了 300us!                       │       │
│  │                                                              │       │
│  │  → 吞吐量下降、延迟抖动                                    │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  解决: 上半部只做最少的工作，重活推迟到下半部                          │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  Time ──────────────────────────────────────────────────►    │       │
│  │                                                              │       │
│  │  上半部 (硬中断):                                            │       │
│  │  ══╤═══╤═══╤═══╤═══                                           │       │
│  │    │10us│10us│10us│10us  快速响应，不积压                   │       │
│  │                                                              │       │
│  │  下半部 (软中断/tasklet/workqueue):                          │       │
│  │  ────────╤════════════════╤═══════════                     │       │
│  │          │ 批量处理         │ 批量处理                       │       │
│  │          │ (可被打断)       │ (可被打断)                     │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 4.3 中断嵌套

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    中断嵌套规则                                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  硬中断嵌套:                                                           │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  正在处理 IRQ #17 (网卡):                                   │       │
│  │  ═══════════════════════════                                 │       │
│  │                                                              │       │
│  │  IRQ #3 (定时器) 到达:                                       │       │
│  │  → 如果优先级更高 → 可以嵌套进入 ✅                         │       │
│  │                                                              │       │
│  │  IRQ #17 (网卡) 再次到达:                                    │       │
│  │  → 同级 IRQ 默认被屏蔽 ❌ (除非 IRQF_SHARED)                 │       │
│  │                                                              │       │
│  │  Linux 的 IRQ 线程化 (CONFIG_IRQ_FORCED_THREADING):          │       │
│  │  ─────────────────────────────────────────────                 │       │
│  │  PREEMPT_RT 下，硬中断处理程序被变成内核线程                │       │
│  │  → 中断线程化后，可以被抢占、可以睡眠                      │       │
│  │  → 只保留极少量的硬中断代码 (ack + wake_up_thread)          │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  软中断嵌套:                                                           │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  正在执行 NET_RX_SOFTIRQ:                                   │       │
│  │  ──────────────────────────                                 │       │
│  │                                                              │       │
│  │  如果硬中断到达 → 可以嵌套进入硬中断 ✅                     │       │
│  │  硬中断中 raise_softirq(TIMER_SOFTIRQ) → 加入 pending 列表   │       │
│  │  硬中断返回后继续处理当前 softirq                           │       │
│  │  当前 softirq 处理完后，再处理 TIMER_SOFTIRQ                │       │
│  │                                                              │       │
│  │  软中断不能嵌套软中断                                       │       │
│  │  → local_bh_disable() / local_bh_enable() 控制              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  preempt_count 在嵌套中的变化:                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  进程执行中:  preempt_count = 0         ← 可抢占             │       │
│  │       │                                                      │       │
│  │       │ 硬中断进入                                          │       │
│  │       ▼                                                      │       │
│  │  硬中断中:    preempt_count = HARDIRQ (256)  ← 不可抢占     │       │
│  │       │                                                      │       │
│  │       │ 软中断执行                                          │       │
│  │       ▼                                                      │       │
│  │  软中断中:    preempt_count = HARDIRQ + SOFTIRQ (512)       │       │
│  │       │                                                      │       │
│  │       │ 软中断结束                                          │       │
│  │       ▼                                                      │       │
│  │  硬中断中:    preempt_count = HARDIRQ (256)                  │       │
│  │       │                                                      │       │
│  │       │ 硬中断退出                                          │       │
│  │       ▼                                                      │       │
│  │  进程执行中:  preempt_count = 0         ← 恢复可抢占         │       │
│  │                                                              │       │
│  │  → 每一层嵌套都会增加 preempt_count                        │       │
│  │  → 只有最外层退出后 preempt_count 才回到 0                  │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 5. 调度器

### 5.1 调度器在什么时候介入

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    调度器介入的时机                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  调度器 (scheduler) 决定"下一个在 CPU 上运行的进程是谁"。             │
│  它在以下时机被调用:                                                   │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  时机 1: 主动让出 CPU                                       │       │
│  │  ─────────────────────                                      │       │
│  │  - 进程调用 schedule()                                      │       │
│  │  - 进程调用 sleep() / wait_event()                          │       │
│  │  - 进程调用 mutex_lock() 且锁被持有                        │       │
│  │  → "我需要等待，先调度给别人"                              │       │
│  │                                                              │       │
│  │  时机 2: 从系统调用返回用户态                               │       │
│  │  ─────────────────────────────                              │       │
│  │  - syscall 返回路径检查 TIF_NEED_RESCHED                    │       │
│  │  - 如果有更高优先级进程就切换                               │       │
│  │  → "系统调用做完了，看看有没有更重要的任务"                 │       │
│  │                                                              │       │
│  │  时机 3: 从中断/异常返回                                   │       │
│  │  ───────────────────────────────                            │       │
│  │  - 中断处理完成后，检查是否需要重新调度                     │       │
│  │  - 只在进程上下文中（preempt_count == 0）才切换             │       │
│  │  → "中断处理完了，看看需不需要切换"                         │       │
│  │                                                              │       │
│  │  时机 4: 唤醒更高优先级进程                                 │       │
│  │  ───────────────────────────────                            │       │
│  │  - wake_up() / wake_up_process()                           │       │
│  │  - 如果被唤醒的进程优先级高于当前                          │       │
│  │  - 设置 need_resched = 1                                   │       │
│  │  - 在下一个检查点触发 schedule()                            │       │
│  │  → "有更重要的任务醒了，标记需要调度"                       │       │
│  │                                                              │       │
│  │  时机 5: preempt_enable() 时                                │       │
│  │  ───────────────────────────                                │       │
│  │  - 释放抢占禁用时，如果 need_resched == 1                   │       │
│  │  - 立即调用 schedule()                                      │       │
│  │  → "解锁了，如果有需要调度的就立即调度"                     │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 5.2 上下文切换过程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    上下文切换 (Context Switch)                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  进程 A → 进程 B 的完整上下文切换:                                      │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  CPU 0:                                                      │       │
│  │                                                              │       │
│  │  ┌─────────────┐                      ┌─────────────┐       │       │
│  │  │  进程 A      │  schedule()         │  进程 B      │       │       │
│  │  │             │ ──────────────►    │             │       │       │
│  │  │  寄存器状态  │  保存 A 的状态     │  寄存器状态  │       │       │
│  │  │  栈指针     │  ────────────      │  栈指针     │       │       │
│  │  │  PC 指针    │  恢复 B 的状态     │  PC 指针    │       │       │
│  │  │  页表基址   │  ────────────      │  页表基址   │       │       │
│  │  └─────────────┘  切换地址空间      └─────────────┘       │       │
│  │                      │                                      │       │
│  │                      ▼                                      │       │
│  │              switch_mm() 切换 CR3                           │       │
│  │              (TLB 刷新，新的用户地址空间)                    │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  详细步骤:                                                              │
│                                                                         │
│  ┌─ A 正在运行 ──────────────────────────────────────────────────┐     │
│  │                                                                 │     │
│  │  1. 中断/系统调用触发 schedule()                               │     │
│  │  2. schedule() → context_switch(A, B)                         │     │
│  │                                                                 │     │
│  │  保存进程 A 的状态 (struct thread_info / pt_regs):             │     │
│  │  ┌────────────────────────────────────────────────────────┐   │     │
│  │  │  CPU 寄存器 (RAX, RBX, RCX, ... R15)                   │   │     │
│  │  │  栈指针 (RSP)                                          │   │     │
│  │  │  指令指针 (RIP)                                         │   │     │
│  │  │  段寄存器                                               │   │     │
│  │  │  FPU/SSE 状态                                           │   │     │
│  │  │  → 全部保存到 A 的 task_struct → thread_struct           │   │     │
│  │  └────────────────────────────────────────────────────────┘   │     │
│  │                                                                 │     │
│  │  恢复进程 B 的状态:                                            │     │
│  │  ┌────────────────────────────────────────────────────────┐   │     │
│  │  │  switch_mm():                                           │   │     │
│  │  │    CR3 = B->mm->pgd   // 切换页表                       │   │     │
│  │  │    flush_tlb()          // TLB 刷新                      │   │     │
│  │  │                                                         │   │     │
│  │  │  switch_to():                                           │   │     │
│  │  │    从 B 的 task_struct 恢复所有寄存器                    │   │     │
│  │  │    RSP = B 的内核栈                                     │   │     │
│  │  │    RIP = B 上次被切换走时的指令地址                      │   │     │
│  │  └────────────────────────────────────────────────────────┘   │     │
│  │                                                                 │     │
│  │  3. CPU 从 B 上次被切走的地方继续执行                         │     │
│  │                                                                 │     │
│  └─────────────────────────────────────────────────────────────────┘     │
│                                                                         │
│  注意:                                                                  │
│  - 内核线程共享内核地址空间，不需要切换 CR3（0 号地址空间）          │
│  - 用户进程有不同的地址空间，切换时 TLB 刷新代价较大                │
│  - ARM64 的地址空间切换优化: ASID (Address Space ID) 避免 TLB 全刷  │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 6. 抢占机制

### 6.1 抢占与调度的区别

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    调度 vs 抢占                                         │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  调度 (Scheduling):                                                     │
│  ───────────────────                                                     │
│  - 决定"下一个运行的进程是谁"                                         │
│  - 主动触发：进程自愿让出 CPU (schedule)                               │
│  - 被动触发：从系统调用/中断返回时检查                                 │
│  - 所有内核配置都有调度                                                │
│                                                                         │
│  抢占 (Preemption):                                                     │
│  ─────────────────                                                       │
│  - 在内核代码执行中强行切换进程                                       │
│  - 不需要进程主动调用 schedule()                                       │
│  - 只在 CONFIG_PREEMPT / CONFIG_PREEMPT_RT 中启用                     │
│  - 本质: 在中断返回内核态时，如果需要就切换                           │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  不可抢占内核 (PREEMPT_NONE):                                │       │
│  │  ═════════════════════════════                                │       │
│  │                                                              │       │
│  │  进程 A:                                                    │       │
│  │  ┌──────────────────────────────────────────────────┐        │       │
│  │  │ sys_write() ─── 一直执行 ─── 完整返回用户态      │        │       │
│  │  └──────────────────────────────────────────────────┘        │       │
│  │                                                  ↑          │       │
│  │  即使中间有更高优先级进程就绪，也 │ 只能在这里切换        │       │
│  │  不能打断 sys_write() 的执行          │                   │       │
│  │                                                          │       │
│  │  时钟中断到来 → 标记 need_resched → 但不立即调度          │       │
│  │  → 等到 sys_write() 返回时才检查并调度                     │       │
│  │                                                              │       │
│  ├──────────────────────────────────────────────────────────────┤       │
│  │                                                              │       │
│  │  可抢占内核 (PREEMPT):                                      │       │
│  │  ═══════════════════════                                     │       │
│  │                                                              │       │
│  │  进程 A:                                                    │       │
│  │  ┌──────────────────────────────────────────────────┐        │       │
│  │  │ sys_write() ──── 被打断! ──── (暂停)              │        │       │
│  │  └──────────────────────────────────────────────────┘        │       │
│  │                              │                                │       │
│  │  进程 B (高优先级):           │                                │       │
│  │  ┌────────────────────────────┘                                │       │
│  │  │ 执行高优先级任务 ─── 完成或阻塞                          │       │
│  │  └──────────────────────────────────────────────────┐        │       │
│  │                                                   │        │       │
│  │  进程 A:                                    ┌──────┘        │       │
│  │  ┌───────────────────────────────────────┘               │       │
│  │  │ sys_write() ─── 从暂停点继续执行                       │       │
│  │  └──────────────────────────────────────────────────┐        │       │
│  │                                                   │        │       │
│  │  抢占检查点 (在中断返回时):                            │       │
│  │  if (need_resched && preempt_count == 0)             │       │
│  │      schedule();  // 立即切换                          │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
```

### 6.2 preempt_count 在各种场景中的变化

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    preempt_count 变化全景                               │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  场景: 一个进程在内核中，经历各种事件                                  │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  ① 进程执行:       preempt_count = 0     可抢占 ✅           │       │
│  │         │                                                    │       │
│  │         │ preempt_disable()                                  │       │
│  │  ② 禁用抢占后:   preempt_count = 1     不可抢占 ❌          │       │
│  │         │                                                    │       │
│  │         │ spin_lock() → 间接 preempt_disable()              │       │
│  │  ③ 持有自旋锁:   preempt_count = 2     不可抢占 ❌          │       │
│  │         │                                                    │       │
│  │         │ ⚡ 硬中断到达!                                   │       │
│  │  ④ 硬中断中:     preempt_count = 2+256 不可抢占 ❌          │       │
│  │         │                                                    │       │
│  │         │ 软中断执行                                        │       │
│  │  ⑤ 软中断中:     preempt_count = 2+256+256 不可抢占 ❌     │       │
│  │         │                                                    │       │
│  │         │ 软中断结束                                        │       │
│  │  ⑥ 回到硬中断:   preempt_count = 2+256 不可抢占 ❌          │       │
│  │         │                                                    │       │
│  │         │ 硬中断结束                                        │       │
│  │  ⑦ 回到持有锁:   preempt_count = 2     不可抢占 ❌          │       │
│  │         │                                                    │       │
│  │         │ spin_unlock() → 间接 preempt_enable()             │       │
│  │  ⑧ 释放锁后:     preempt_count = 1     不可抢占 ❌          │       │
│  │         │                                                    │       │
│  │         │ preempt_enable()                                   │       │
│  │  ⑨ 恢复抢占:     preempt_count = 0     可抢占 ✅            │       │
│  │         │                                                    │       │
│  │         │ 如果此时 need_resched == 1 → schedule()           │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  关键规则:                                                              │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  1. preempt_count > 0 → 绝对不能调度                       │       │
│  │     → 在自旋锁中、硬中断中、软中断中都不能切换进程          │       │
│  │                                                              │       │
│  │  2. 每一层嵌套独立计数                                      │       │
│  │     → 进入中断 +256，退出 -256                               │       │
│  │     → preempt_disable() +1，preempt_enable() -1              │       │
│  │                                                              │       │
│  │  3. 只有回到最外层 (preempt_count == 0) 才可能触发抢占      │       │
│  │     → 内层怎么标记 need_resched 都没用                      │       │
│  │     → 等到最外层 enable 时才检查                            │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 7. 全景图：所有执行上下文的关系

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Linux 内核执行上下文全景图                            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │                     进程上下文                                  │    │
│  │                 (Process Context)                              │    │
│  │                                                                  │    │
│  │  代表进程: Task A / Task B / kworker / ...                     │    │
│  │  current 指针: 有效，指向当前进程                              │    │
│  │  能睡眠: ✅ schedule() / mutex_lock() / wait_event()           │    │
│  │  能访问用户内存: ✅ copy_from_user() / copy_to_user()          │    │
│  │  能用 GFP_KERNEL: ✅                                         │    │
│  │  能用 mutex: ✅                                                │    │
│  │  能被抢占: 取决于 preempt_count 和内核配置                    │    │
│  │                                                                  │    │
│  │  示例:                                                         │    │
│  │  - sys_read() / sys_write() / sys_ioctl()                     │    │
│  │  - VFS 操作                                                   │    │
│  │  - 文件系统操作                                               │    │
│  │  - 网络协议栈下半部                                           │    │
│  │  - kworker 执行 workqueue 回调                                │    │
│  │                                                                  │    │
│  └──────────────────────────┬──────────────────────────────────────┘    │
│                             │                                           │
│             硬件中断到达 (IRQ)                                          │
│                             │                                           │
│                             ▼                                           │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │              中断上下文 (Interrupt Context)                     │    │
│  │                                                                  │    │
│  │  ┌───────────────────────────────────────────────────────────┐ │    │
│  │  │  上半部: 硬中断 (Hardware IRQ Handler)                    │ │    │
│  │  │                                                           │ │    │
│  │  │  不代表任何进程                                           │ │    │
│  │  │  current 指针: 指向被中断的进程（但"不代表"它）         │ │    │
│  │  │  能睡眠: ❌                                                │ │    │
│  │  │  能访问用户内存: ❌                                       │ │    │
│  │  │  能用 GFP_KERNEL: ❌ 只能用 GFP_ATOMIC                   │ │    │
│  │  │  能用 mutex: ❌ 只能用 spinlock                            │ │    │
│  │  │  能被抢占: ❌ (preempt_count > 0)                         │ │    │
│  │  │                                                           │ │    │
│  │  │  示例:                                                    │ │    │
│  │  │  - eth0_rx_interrupt()     网卡收包硬中断                │ │    │
│  │  │  - nvme_irq_handler()      NVMe 完成中断                 │ │    │
│  │  │  - timer_interrupt()       定时器中断                    │ │    │
│  │  └───────────────────────┬───────────────────────────────────┘ │    │
│  │                          │                                     │    │
│  │         raise_softirq() / tasklet_schedule()                 │    │
│  │                          │                                     │    │
│  │                          ▼                                     │    │
│  │  ┌───────────────────────────────────────────────────────────┐ │    │
│  │  │  下半部: 软中断 (Soft IRQ)                               │ │    │
│  │  │                                                           │ │    │
│  │  │  仍然在中断上下文                                        │ │    │
│  │  │  能睡眠: ❌                                                │ │    │
│  │  │  能被抢占: ❌                                            │ │    │
│  │  │                                                           │ │    │
│  │  │  示例:                                                    │ │    │
│  │  │  - NET_RX_SOFTIRQ   → napi_poll() 网络收包批量处理      │ │    │
│  │  │  - NET_TX_SOFTIRQ   → 网络发送                          │ │    │
│  │  │  - RCU_SOFTIRQ      → RCU 回调执行                      │ │    │
│  │  │  - TASKLET_SOFTIRQ  → tasklet 回调                       │ │    │
│  │  │  - TIMER_SOFTIRQ    → 定时器回调                        │ │    │
│  │  └───────────────────────┬───────────────────────────────────┘ │    │
│  │                          │                                     │    │
│  │         如果软中断太慢 → ksoftirqd 线程接管                  │    │
│  │          (仍是中断上下文语义，但变成可调度线程)               │    │
│  │                                                                  │    │
│  └──────────────────────────┬──────────────────────────────────────┘    │
│                             │                                           │
│             中断处理完成，返回进程上下文                               │
│                             │                                           │
│                             ▼                                           │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │              从中断返回                                         │    │
│  │                                                                  │    │
│  │  1. 检查 pending softirq → 如果有，先执行                      │    │
│  │  2. 检查 need_resched && preempt_count == 0                    │    │
│  │     → 如果需要抢占，调用 schedule() 切换进程                   │    │
│  │  3. 否则返回原来的进程继续执行                                │    │
│  │                                                                  │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
│                                                                         │
│  特殊路径: Workqueue                                                   │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │                                                                  │    │
│  │  中断处理 → queue_work() → 把工作放入队列                      │    │
│  │                              │                                  │    │
│  │                              ▼                                  │    │
│  │              kworker/uX:Y (内核线程)                            │    │
│  │              ┌─────────────────────────────────────┐           │    │
│  │              │  在进程上下文中执行!                │           │    │
│  │              │  能睡眠 ✅  能用 mutex ✅           │           │    │
│  │              │  能访问用户内存 ✅                   │           │    │
│  │              │  能被抢占 ✅ (取决于 preempt_count)  │           │    │
│  │              └─────────────────────────────────────┘           │    │
│  │                                                                  │    │
│  │  这是"从中断上下文逃逸到进程上下文"的桥梁                    │    │
│  │  → 把需要睡眠的重活从中断上下文挪到 workqueue               │    │
│  │                                                                  │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 9. 一句话总结

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                         │
│  进程上下文 = 代表某个进程，能睡眠、能抢占、能用所有 API              │
│                                                                         │
│  中断上下文 = 不代表任何进程，不能睡眠、不能抢占、只能用"不睡眠"的 API│
│                                                                         │
│  调度 = 决定下一个运行的进程是谁                                      │
│  抢占 = 在内核代码执行中强制切换进程（可配置是否开启）                │
│                                                                         │
│  preempt_count = 控制能否抢占/调度的计数器                              │
│                > 0 时绝对不能切换，每一层嵌套独立计数                  │
│                                                                         │
│  Workqueue = 从中断上下文"逃逸"到进程上下文的桥梁                    │
│               把需要睡眠的工作推迟到 kworker 线程执行                 │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```
