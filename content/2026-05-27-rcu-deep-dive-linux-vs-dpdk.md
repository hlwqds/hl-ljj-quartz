# RCU 原理深度解析：Linux 内核与 DPDK 实现对比

## 1. RCU 是什么

RCU（Read-Copy-Update）是一种**读端几乎零开销**的同步机制。核心思想：

- **读者不加锁**，直接读共享数据，没有任何原子操作、内存屏障或自旋等待
- **写者不覆盖**，而是创建副本（Copy），修改副本后原子替换指针
- **延迟释放**，等所有旧读者退出后，再回收旧数据

本质上是一种**乐观并发**：假设读多写少，让读路径极快，把代价全部推给写者。

### 1.1 一个直觉的比喻

想象一个餐厅的菜单（共享数据）：

1. **顾客（读者）** 进来时看一眼菜单，点菜。看菜单不需要任何锁
2. **厨师（写者）** 想更新菜单：他不会在原菜单上涂改，而是印一份新菜单
3. 新菜单放到前台后，新顾客看到新菜单
4. 但旧顾客手里还拿着旧菜单在点菜，**厨师不能把旧菜单撕掉**
5. 等所有旧顾客都点完菜离开后，旧菜单才能安全销毁

"等所有旧顾客离开"这个等待过程就是 **Grace Period（宽限期）**。

### 1.2 RCU 的三个角色

| 角色                    | 职责                          | 开销     |
| ----------------------- | ----------------------------- | -------- |
| **Reader（读者）**      | 读共享数据                    | 几乎为零 |
| **Updater（写者）**     | 创建副本，替换指针，注册回调  | 中等     |
| **Reclaimer（回收者）** | Grace Period 结束后释放旧数据 | 低       |

### 1.3 核心问题

整个 RCU 机制围绕一个核心问题展开：**写者如何知道所有旧读者都已经退出了？**

Linux 和 DPDK 给出了完全不同的答案，这也是两者实现差异的根本来源。

## 2. RCU 的基础机制

在深入具体实现之前，先理解 RCU 的通用原语。

### 2.1 读取端原语

```c
// 进入 RCU 临界区
rcu_read_lock();

// 安全地读取 RCU 保护的指针
ptr = rcu_dereference(gp);
use(ptr->field);

// 退出 RCU 临界区
rcu_read_unlock();
```

关键：`rcu_read_lock()` / `rcu_read_unlock()` 的开销必须极低，否则 RCU 就失去了意义。不同实现中这对原语做的事完全不同。

### 2.2 写入端原语

```c
// 发布新数据：确保新节点内容在指针更新之前对读者可见
rcu_assign_pointer(gp, new);

// 等待所有旧读者退出（阻塞）
synchronize_rcu();

// 或者异步注册回调（非阻塞）
call_rcu(&old->rcu_head, free_callback);
```

### 2.3 宽限期（Grace Period）

宽限期是 RCU 中最核心的概念：

```
         写者替换指针                 宽限期结束
              │                          │
              ▼                          ▼
Time ─────────┼──────────────────────────┼──────────►
              │                          │
Reader A: ──[lock]────[use old]────[unlock]───────────
Reader B: ──[lock]────[use old]───────────[unlock]───
Reader C: ──────────────[lock]────[use new]──[unlock]─
                                      │
                                      │
                              所有旧读者都退出了
                              → 可以安全释放旧数据
```

宽限期保证：在 `synchronize_rcu()` 返回时（或 `call_rcu` 的回调执行时），所有在替换指针之前进入临界区的读者都已经退出。

## 3. Linux 内核抢占机制及其对 RCU 的影响

> [!tip] 前置知识
>
> 本节讨论抢占、中断上下文、进程上下文等概念。如果想系统了解这些内核基础概念——包括硬中断/软中断的完整流程、调度器何时介入、preempt_count 如何控制抢占、各上下文的能力限制——请先参阅：[[2026-05-27-linux-kernel-context-scheduling-preemption|Linux 内核上下文、调度与抢占：完整图解]]

在理解 Linux RCU 的具体实现之前，必须先理解 Linux 内核的抢占机制。抢占机制直接决定了 RCU 读取端的实现方式——这是 Linux RCU 与 DPDK RCU 的根本设计差异来源。

### 3.1 什么是内核抢占

**内核抢占（Kernel Preemption）** 是指：一个内核线程在执行内核代码时，可以被更高优先级的任务（包括另一个内核线程或中断处理）打断并切换出去。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    内核抢占 vs 用户态抢占                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  用户态抢占（始终开启，无法关闭）:                                     │
│  ═══════════════════════════════════════                               │
│                                                                         │
│  用户进程 A: ──[执行用户代码]─────────────────────────                   │
│                         │                                               │
│                         │ 时钟中断到来，检查优先级                     │
│                         │ 高优先级进程 B 等待                           │
│                         ▼                                               │
│  用户进程 B: ───────────────[执行用户代码]───                           │
│                                         │                               │
│                                         │ 时间片用完                   │
│                                         ▼                               │
│  用户进程 A: ────────────────────────────────[继续执行]─────────        │
│                                                                         │
│  → 这就是普通的抢占式调度，从 Unix 时代就有                           │
│  → 内核对此没有选择权，中断一定会发生                                  │
│                                                                         │
│  ──────────────────────────────────────────────────────────────────     │
│                                                                         │
│  内核抢占（可选，由内核配置控制）:                                      │
│  ═══════════════════════════════════                                       │
│                                                                         │
│  内核线程: ──[在内核中处理系统调用]────────────                         │
│                         │                                               │
│                         │ 时钟中断到来                                  │
│                         │ 内核抢占开启?                                 │
│                         │   是 → 可以打断，切换到其他任务              │
│                         │   否 → 中断返回后继续执行原线程             │
│                         ▼                                               │
│  情况 1 (抢占开启):                                                     │
│  ─────────────────                                                     │
│  内核线程: ──[sys_read()──]──被打断──                                 │
│  其他任务: ─────────────────[执行]───                                  │
│  内核线程: ───────────────────────[继续 sys_read()]────────────       │
│                                         │                               │
│                                         │ 注意: sys_read() 中间被打断  │
│                                         │ 它持有的所有内核状态必须安全  │
│                                                                         │
│  情况 2 (抢占关闭):                                                     │
│  ─────────────────                                                     │
│  内核线程: ──[sys_read()──────────────────]──                          │
│  (即使时钟中断到来，也只是处理中断本身，不切换任务)                    │
│  → 完整执行完 sys_read()，返回用户态后才可能切换                      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Linux 抢占的四个级别

Linux 内核通过编译选项控制抢占行为，形成四个级别：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                Linux 内核抢占的四个级别                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Level 0: CONFIG_PREEMPT_NONE (服务器默认)                             │
│  ══════════════════════════════════════════                             │
│                                                                         │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  内核代码:    完全不可抢占                                │         │
│  │  返回用户态:   此时可调度                                 │         │
│  │  异常/中断返回: 此时可调度                                 │         │
│  │                                                             │         │
│  │  什么时候抢占？                                             │         │
│  │  - 内核线程主动调用 schedule()                             │         │
│  │  - 从系统调用返回用户态时                                 │         │
│  │  - 从中断处理返回时（如果 need_resched）                   │         │
│  │                                                             │         │
│  │  特点:                                                     │         │
│  │  - 吞吐量最高（内核代码不被打断）                          │         │
│  │  - 延迟最高（实时性差）                                    │         │
│  │  - 内核临界区天然安全（不可能被抢占）                      │         │
│  │  - 适用于: 数据库服务器、HPC 集群                          │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  Level 1: CONFIG_PREEMPT_VOLUNTARY (桌面默认)                          │
│  ═══════════════════════════════════════════════                       │
│                                                                         │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  内核代码:    可自愿抢占                                   │         │
│  │  返回用户态:   此时可调度                                 │         │
│  │  异常/中断返回: 此时可调度                                 │         │
│  │                                                             │         │
│  │  什么时候抢占？                                             │         │
│  │  - 内核代码中调用 cond_resched() 时                       │         │
│  │    (在安全点自愿让出 CPU)                                   │         │
│  │  - 从系统调用/中断返回时                                  │         │
│  │                                                             │         │
│  │  特点:                                                     │         │
│  │  - 在内核代码中主动检查的几个点可以抢占                    │         │
│  │  - 比纯服务器内核响应更快                                  │         │
│  │  - 需要开发者标记 cond_resched()                           │         │
│  │  - 适用于: 桌面 Linux 发行版                               │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  Level 2: CONFIG_PREEMPT (嵌入式/低延迟)                                │
│  ══════════════════════════════════════════                             │
│                                                                         │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  内核代码:    可抢占（除少数临界区外）                     │         │
│  │  返回用户态:   此时可调度                                 │         │
│  │  异常/中断返回: 此时可调度                                 │         │
│  │                                                             │         │
│  │  什么时候抢占？                                             │         │
│  │  - 几乎任何时候，包括内核代码执行中                        │         │
│  │  - 除非: preempt_count > 0（显示持有锁等）                │         │
│  │                                                             │         │
│  │  特点:                                                     │         │
│  │  - 响应延迟最低                                           │         │
│  │  - 需要大量 preempt_disable/enable 保护临界区             │         │
│  │  - 自旋锁自动禁用抢占 (spin_lock → preempt_disable)       │         │
│  │  - 适用于: 嵌入式、低延迟交易系统                          │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  Level 3: CONFIG_PREEMPT_RT (实时内核 / PREEMPT_RT)                     │
│  ═════════════════════════════════════════════════════════════           │
│                                                                         │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  内核代码:    几乎完全可抢占                              │         │
│  │  中断处理:    线程化（中断处理程序变成内核线程）          │         │
│  │  自旋锁:      变成可睡眠的 mutex（无自旋等待）            │         │
│  │  软中断:      线程化                                      │         │
│  │                                                             │         │
│  │  特点:                                                     │         │
│  │  - 整个内核几乎都可在任意点被抢占                         │         │
│  │  - 最严格的实时保证                                       │         │
│  │  - 自旋锁不再禁用抢占                                     │         │
│  │  - 适用于: 工业控制、高频交易、实时通信                   │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  对比总结:                                                             │
│  ┌──────────────────┬────────────┬────────────┬────────────────┐        │
│  │                  │ 吞吐量     │ 延迟       │ 抢占范围       │        │
│  ├──────────────────┼────────────┼────────────┼────────────────┤        │
│  │ PREEMPT_NONE     │ 最高       │ 最高       │ 仅用户态       │        │
│  │ PREEMPT_VOLUNTARY│ 高         │ 中         │ 安全点         │        │
│  │ PREEMPT          │ 中         │ 低         │ 大部分内核代码 │        │
│  │ PREEMPT_RT       │ 较低       │ 最低       │ 几乎全部       │        │
│  └──────────────────┴────────────┴────────────┴────────────────┘        │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.3 现代内核的 RCU 抢占配置：CONFIG_PREEMPT_RCU

前面讨论了 `CONFIG_PREEMPT` 的四个级别，但还有一个独立的、容易混淆的配置项：

```
┌─────────────────────────────────────────────────────────────────────────┐
│          CONFIG_PREEMPT vs CONFIG_PREEMPT_RCU                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  CONFIG_PREEMPT (内核抢占)                                             │
│  ══════════════════════════                                             │
│  控制整个内核是否可以被抢占                                            │
│                                                                         │
│  CONFIG_PREEMPT_RCU (仅 RCU 子系统的抢占支持)                         │
│  ════════════════════════════════════════════                           │
│  独立于内核抢占，只影响 RCU 的读取端实现                             │
│  从 Linux 5.x 起成为独立配置项                                         │
│                                                                         │
│  ──────────────────────────────────────────────────────────────────     │
│                                                                         │
│  关键点: 这两个配置是完全独立的!                                       │
│                                                                         │
│  ┌──────────────────────┬─────────────┬────────────────────────────┐   │
│  │  内核配置            │ PREEMPT     │ PREEMPT_RCU               │   │
│  ├──────────────────────┼─────────────┼────────────────────────────┤   │
│  │ 服务器默认           │ NONE        │ ✅ y (默认开启)           │   │
│  │ 桌面默认             │ VOLUNTARY   │ ✅ y (默认开启)           │   │
│  │ 手动开启抢占         │ y           │ ✅ y (默认开启)           │   │
│  │ 实时内核 (RT)        │ RT          │ ✅ y (默认开启)           │   │
│  └──────────────────────┴─────────────┴────────────────────────────┘   │
│                                                                         │
│  注意: CONFIG_PREEMPT=NONE (不可抢占内核)                              │
│        但 CONFIG_PREEMPT_RCU=y (RCU 使用 nesting 计数)               │
│                                                                         │
│  这意味着即使在"不可抢占"的服务器内核上:                                │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  内核抢占: 关闭 → preempt_disable/enable 仍然有效            │       │
│  │  但 RCU 读取端: 使用 nesting 计数 (不是 preempt_disable)    │       │
│  │                                                              │       │
│  │  即 rcu_read_lock() 不再等价于 preempt_disable()             │       │
│  │  而是: current->rcu_read_lock_nesting++                       │       │
│  │                                                              │       │
│  │  → 和 PREEMPT=NONE + Classic RCU 的假设不同!                │       │
│  │  → 现代内核的 RCU 读取端几乎都是 Preemptible 的             │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  ──────────────────────────────────────────────────────────────────     │
│                                                                         │
│  为什么不可抢占内核也需要 Preemptible RCU？                            │
│                                                                         │
│  1. 内核内部有些子系统天然在可抢占上下文中使用 RCU                    │
│     → ksoftirqd 内核线程 (进程上下文，可被调度)                       │
│     → kworker 线程 (进程上下文，可被调度)                              │
│     → rcu_nocb_kthread (回调执行线程，可被调度)                        │
│     这些线程执行 RCU 临界区时，是可能被抢占的                        │
│                                                                         │
│  2. CPU 热插拔和 CPU 离线                                          │
│     → CPU 离线时需要等待该 CPU 上的 RCU 读者退出                     │
│     → 需要 nesting 追踪来精确判断                                    │
│                                                                         │
│  3. CONFIG_PREEMPT_DYNAMIC (Linux 5.12+)                             │
│     → 允许运行时动态切换内核抢占行为                                │
│     → 如果 RCU 仍绑定 Classic (preempt_disable)，动态切换会出问题   │
│     → 所以 RCU 必须始终使用 nesting 计数                            │
│                                                                         │
│  ──────────────────────────────────────────────────────────────────     │
│                                                                         │
│  实际影响:                                                              │
│                                                                         │
│  上一节讨论的 Classic RCU (preempt_disable → 上下文切换=QS → 纯批量) │
│  在现代内核中已经越来越少了。                                         │
│                                                                         │
│  大多数生产服务器实际运行的是:                                         │
│  PREEMPT=NONE + PREEMPT_RCU=y                                        │
│  → 不可抢占内核 + Preemptible RCU                                     │
│  → RCU 读取端使用 nesting 计数 + 双路径 QS 上报                    │
│  → schedule() 中条件批量 + unlock 中补漏                            │
│                                                                         │
│  Classic RCU 更多存在于:                                              │
│  - 老旧内核 (5.x 之前，PREEMPT_RCU 不是独立配置)                   │
│  - 嵌入式设备 (显式关闭 PREEMPT_RCU 以减少开销)                    │
│  - 某些极端性能优化的场景                                            │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.4 preempt_count：抢占计数器

`preempt_count` 是理解内核抢占的核心变量，位于每个 CPU 的 `current_thread_info` 中：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                preempt_count 抢占计数器                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  struct thread_info {                                                   │
│      int preempt_count;   // 每个线程的抢占计数器                      │
│  };                                                                     │
│                                                                         │
│  判定规则:                                                              │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │                                                             │         │
│  │  preempt_count == 0  →  可以抢占 ✅                        │         │
│  │  preempt_count >  0  →  不可抢占 ❌                        │         │
│  │                                                             │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  preempt_count 的构成 (位域):                                           │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  31                     16 15           8 7            0  │         │
│  │  ├─────────────────────────┼───────────────┼──────────────┤  │         │
│  │  │ PREEMPT_ACTIVE (8 bits) │ SOFTIRQ (8b)  │ HARDIRQ/NEST│  │         │
│  │  │                         │               │ (8 bits)     │  │         │
│  │  └─────────────────────────┴───────────────┴──────────────┘  │         │
│  │                                                             │         │
│  │  HARDIRQ_MASK: 硬中断嵌套计数                               │         │
│  │  SOFTIRQ_MASK: 软中断嵌套计数                               │         │
│  │  PREEMPT_MASK: 抢占禁用计数                                 │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  谁会增加 preempt_count:                                                │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │  preempt_disable()   → preempt_count += 1                   │       │
│  │  spin_lock()         → preempt_disable() (间接)             │       │
│  │  硬中断进入           → preempt_count += HARDIRQ_OFFSET     │       │
│  │  软中断进入           → preempt_count += SOFTIRQ_OFFSET     │       │
│  │  mutex_lock()        → 不增加 preempt_count（RT 内核）      │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  关键机制: preempt_count 的检查点                                       │
│  ════════════════════════════════════                                   │
│  内核在以下时机检查 preempt_count 是否为 0:                            │
│  - 从中断返回内核态时: 如果 need_resched 且 preempt_count==0 → 抢占   │
│  - 从系统调用返回用户态时: 始终检查 need_resched                       │
│  - 调用 preempt_enable() 时: 如果 need_resched → 立即调度             │
│                                                                         │
│  时序示例:                                                              │
│  ─────────                                                              │
│  Task A 在内核中:                                                       │
│                                                                         │
│  Task A: ──[spin_lock]──[修改数据]──[spin_unlock]──                    │
│              │ p_count++  │           │ p_count--                       │
│              │ p_count=1  │           │ p_count=0                       │
│              │            │           │ 检查 need_resched              │
│              │ 不可抢占❌  │           │ 如需要→抢占→切换到 B           │
│                                                                         │
│  高优先级 Task B 就绪                                                   │
│  (中断标记 need_resched = 1)                                           │
│                                                                         │
│  如果抢占关闭 (PREEMPT_NONE):                                           │
│  Task A: ──[spin_lock]──[修改数据]──[spin_unlock]──[继续执行]──[返回]  │
│                                                          │              │
│                                                          │ 返回用户态  │
│                                                          │ 时才切换到 B │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.5 抢占对 RCU 的根本影响

这是理解 Linux RCU 设计的关键。抢占机制直接改变了 RCU 静默状态的检测方式。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                抢占为什么影响 RCU？                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  核心问题: 当读者被抢占后，会发生什么？                                 │
│                                                                         │
│  ────────────────────────────────────────────────                        │
│  场景 1: 不可抢占内核 (PREEMPT_NONE)                                   │
│  ────────────────────────────────────────────────                        │
│                                                                         │
│  CPU 0:                                                                 │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │ rcu_read_lock();     // preempt_disable()                    │       │
│  │ ptr = rcu_dereference(gp);                                   │       │
│  │ use(ptr->field);                                              │       │
│  │ // ← 此时 preempt_count = 1，不可抢占                       │       │
│  │ // ← 这个 CPU 一定会完整执行完这段代码                     │       │
│  │ // ← 不会被切换到其他任务                                   │       │
│  │ rcu_read_unlock();   // preempt_enable()                     │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  → 读者一定在同一次"内核执行窗口"内完成                               │
│  → 只要这个 CPU 发生了上下文切换，说明读者一定已经退出了               │
│  → QS = 上下文切换                                                     │
│  → 简单、可靠、安全                                                    │
│                                                                         │
│  ────────────────────────────────────────────────                        │
│  场景 2: 可抢占内核 (PREEMPT)                                          │
│  ────────────────────────────────────────────────                        │
│                                                                         │
│  CPU 0:                                                                 │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │ Task A:                                                      │       │
│  │ rcu_read_lock();     // nesting++ (preempt_count 不变!)     │       │
│  │ ptr = rcu_dereference(gp);                                   │       │
│  │ use(ptr->field);                                              │       │
│  │   ↑                                                          │       │
│  │   │ 时钟中断! need_resched = 1                              │       │
│  │   │ preempt_count == 0 → 抢占!                              │       │
│  │   ▼                                                          │       │
│  │ ──── 被切换出去 ────                                         │       │
│  │   (Task A 还在 RCU 临界区中! nesting > 0)                    │       │
│  │   (Task A 持有旧指针 ptr)                                    │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  CPU 0:                                                                 │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │ Task B:                                                      │       │
│  │ (在 CPU 0 上运行，但 Task A 的 RCU 临界区还在挂着)          │       │
│  │ ...                                                          │       │
│  │ schedule()  → 上下文切换                                     │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  CPU 0:                                                                 │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │ Task A 恢复:                                                 │       │
│  │ (从被抢占的位置继续执行)                                     │       │
│  │ use(ptr->field);    // ← 还在用旧指针!                       │       │
│  │ rcu_read_unlock();   // nesting-- → 0                        │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  ❌ 问题:                                                               │
│  1. CPU 0 发生了上下文切换 (Task B → Task A)                           │
│  2. 如果按"上下文切换 = QS" 的逻辑判断                                │
│  3. 会认为 CPU 0 已退出 RCU 临界区                                    │
│  4. 但 Task A 实际上还在 RCU 临界区中（被抢占时没退出）               │
│  5. 如果此时释放旧数据 → Task A 恢复后 use-after-free!                │
│                                                                         │
│  → "上下文切换 = QS" 这个假设在可抢占内核中不成立!                    │
│  → 必须有新的 QS 检测方式                                            │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.6 解决方案：不同抢占级别下的 RCU 读取端

```
┌─────────────────────────────────────────────────────────────────────────┐
│          不同抢占级别下的 RCU 读取端实现                                 │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │ PREEMPT_NONE / PREEMPT_VOLUNTARY:  Classic RCU             │         │
│  │                                                            │         │
│  │  rcu_read_lock():                                         │         │
│  │    preempt_disable();                                      │         │
│  │    // preempt_count++ → 当前任务不会被抢占                 │         │
│  │    // 读者在同一次 CPU 占用内完成                          │         │
│  │                                                            │         │
│  │  rcu_read_unlock():                                       │         │
│  │    preempt_enable();                                       │         │
│  │    // preempt_count-- → 可能被抢占                         │         │
│  │    // 如果正好让出 CPU，这就是一个 QS                      │         │
│  │                                                            │         │
│  │  QS 检测:                                                 │         │
│  │    上下文切换 → QS（因为 rcu_read_lock 期间不可能切换）    │         │
│  │    idle 循环 → QS（idle 不在临界区中）                     │         │
│  │    用户态 → QS（用户代码不调用 rcu_read_lock）             │         │
│  │                                                            │         │
│  │  开销: preempt_disable/enable ≈ 1-2 ns                    │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │ PREEMPT:  Preemptible RCU                                  │         │
│  │                                                            │         │
│  │  rcu_read_lock():                                         │         │
│  │    current->rcu_read_lock_nesting++;                       │         │
│  │    barrier();  // 编译器屏障                               │         │
│  │    // 不禁用抢占! 只是增加嵌套计数                        │         │
│  │    // 读者可以被抢占和调度到其他 CPU                      │         │
│  │                                                            │         │
│  │  rcu_read_unlock():                                       │         │
│  │    nesting--;                                              │         │
│  │    barrier();                                              │         │
│  │    if (nesting == 0 &&                                    │         │
│  │        unlikely(current->rcu_read_unlock_special)) {      │         │
│  │        // 特殊路径: 可能需要报告 QS 或唤醒 GP kthread     │         │
│  │        rcu_read_unlock_special();                           │         │
│  │    }                                                       │         │
│  │                                                            │         │
│  │  QS 检测:                                                 │         │
│  │    不再依赖"上下文切换 = QS"!                             │         │
│  │    而是: 当 nesting 从 >0 变为 ==0 时，该任务已退出临界区  │         │
│  │    加上: 该任务被调度走后，其 CPU 的 qs 相关信息需要追踪  │         │
│  │                                                            │         │
│  │  开销: 计数器 ++/-- + 条件检查 ≈ 2-5 ns                  │         │
│  │  比 Classic RCU 略高，但仍然极低                           │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │ PREEMPT_RT:  RT RCU (最严格的可抢占 RCU)                   │         │
│  │                                                            │         │
│  │  与 PREEMPT 的 Preemptible RCU 类似                       │         │
│  │  但有以下额外复杂性:                                      │         │
│  │                                                            │         │
│  │  1. 中断处理程序也是可抢占的                               │         │
│  │     → 中断处理中也使用 RCU 临界区                          │         │
│  │     → 中断上下文中的 nesting 也需要追踪                    │         │
│  │                                                            │         │
│  │  2. 自旋锁变成了 mutex                                     │         │
│  │     → spin_lock 不再禁用抢占                               │         │
│  │     → 不能再依赖 preempt_count 保护 RCU 读者              │         │
│  │     → 必须完全依赖 nesting 计数                            │         │
│  │                                                            │         │
│  │  3. 回调执行也需要考虑实时性                               │         │
│  │     → 回调可能被抢占                                       │         │
│  │     → 使用 per-CPU 回调队列 + kthread 执行                 │         │
│  │                                                            │         │
│  │  开销: 与 PREEMPT 相当，但路径更多                         │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  关键区别总结:                                                          │
│  ┌────────────────┬─────────────────────────┬─────────────────────────┐ │
│  │                │ Classic RCU             │ Preemptible RCU          │ │
│  ├────────────────┼─────────────────────────┼─────────────────────────┤ │
│  │ rcu_read_lock  │ preempt_disable()      │ nesting++               │ │
│  │ 实际效果       │ 禁用抢占               │ 不禁用抢占             │ │
│  │ 读者可被抢占?  │ 否                     │ 是                     │ │
│  │ QS 检测方式    │ 上下文切换 = QS        │ nesting==0 + 调度追踪  │ │
│  │ 复杂度         │ 低                     │ 高                     │ │
│  │ 适用内核       │ PREEMPT_NONE/VOLUNTARY │ PREEMPT/RT             │ │
│  └────────────────┴─────────────────────────┴─────────────────────────┘ │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.7 为什么不能统一成手动上报：批量合并的思路

一个自然的问题是：Classic RCU 为什么不在 `rcu_read_unlock()` 里也手动上报 QS（像 Preemptible RCU 那样），而非要依赖 `schedule()`？

答案：**Classic RCU 的 QS 上报本质上是批量合并。**

```
┌─────────────────────────────────────────────────────────────────────────┐
│          Classic RCU 的 QS 上报：批量合并                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  一个宽限期（几毫秒）内:                                               │
│                                                                         │
│  rcu_read_unlock() 被调用:  数千次 ~ 数百万次                         │
│  schedule() 被调用:       几次 ~ 几十次                                 │
│                                                                         │
│  Classic RCU 的做法（批量）:                                           │
│  ────────────────────────────                                          │
│                                                                         │
│  unlock → unlock → unlock → ... → unlock → schedule() → report QS     │
│                                             │                          │
│                                             │ Q 次 unlock 的 QS       │
│                                             │ 合并为 schedule() 中的   │
│                                             │ 1 次上报                │
│                                                                         │
│  读者路径开销:                                                          │
│  rcu_read_lock()   → preempt_disable()   → 1 条指令                  │
│  rcu_read_unlock() → preempt_enable()    → 1 条指令                  │
│  schedule() 中     → 写一个 QS flag       → 几十次，"免费"的        │
│                                                                         │
│  如果改成手动上报（每次都上报）:                                       │
│  ─────────────────────────────────────                                       │
│                                                                         │
│  unlock → report → unlock → report → unlock → report → ...            │
│                                                                         │
│  读者路径开销:                                                          │
│  rcu_read_unlock() → nesting--;                                        │
│                    → 检查 pending GP                                   │
│                    → 更新 per-CPU QS 状态                              │
│                    → 可能需要内存屏障                                   │
│                    → 每次解锁多了 5~10 条指令                          │
│                                                                         │
│  额外开销: 每秒百万次 × 几条指令 = 可观的 CPU 时间                    │
│  换来: 只是代码风格统一，没有正确性收益                              │
│                                                                         │
│  ──────────────────────────────────────────────────────────────────     │
│                                                                         │
│  反过来想: Preemptible RCU 为什么"不得不"在 unlock 里上报？          │
│  ────────────────────────────────────────────────────────────────     │
│                                                                         │
│  不是"选择"在 unlock 里上报，而是"不得不"这么做:                    │
│                                                                         │
│  1. rcu_read_lock() 不再禁用抢占                                     │
│  2. 读者可能带着 nesting > 0 被抢占切走                              │
│  3. schedule() 到来时 nesting 可能 > 0 → 不能标记 QS                │
│  4. 只能在 nesting 真正归零时（unlock 中）才能确定安全上报         │
│                                                                         │
│  这是正确性（correctness）逼出来的代价，不是性能选择                 │
│  → Preemptible RCU 的读者路径比 Classic RCU 慢，就是抢占的代价      │
│  → Classic RCU 有 preempt_disable 保护，所以享受了批量合并的优化    │
│                                                                         │
│  ──────────────────────────────────────────────────────────────────     │
│                                                                         │
│  与其他批量技术的类比:                                                │
│                                                                         │
│  ┌──────────────────────┬────────────────────────────────────┐          │
│  │ Classic RCU QS 上报  │ 多次 unlock 合并为 1 次 schedule()  │          │
│  │ NAPI (网络收包)       │ 多次中断合并为 1 次轮询批量处理   │          │
│  │ 数据库 Group Commit  │ 多次写入合并为 1 次 I/O            │          │
│  │ Write Combine (CPU)   │ 多次 store 合并为 1 次 cache line 写│          │
│  └──────────────────────┴────────────────────────────────────┘          │
│                                                                         │
│  核心模式相同: 高频事件攒着，低频时一起处理                          │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.8 Preemptible RCU 的双路径 QS 上报详解

Preemptible RCU 有两个 QS 上报点：`schedule()` 中条件批量 + `unlock()` 中补漏。下面用完整图例解释两个路径如何协作。

```
┌─────────────────────────────────────────────────────────────────────────┐
│          两个 QS 上报点的作用                                          │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  路径 A: schedule() 中的条件批量上报                                   │
│  ═════════════════════════════════════                                 │
│                                                                         │
│  rcu_note_context_switch(prev_cpu) {                                   │
│      if (prev->nesting == 0)                                          │
│          rcu_qs();          // nesting 碰好为 0 → 直接报 QS           │
│      else                                                         │
│          prev->blocked = true;  // nesting > 0 → 标记被阻塞，不报    │
│  }                                                                      │
│                                                                         │
│  适用: 读者在临界区外被调度（最常见的情况）                            │
│  开销: 只多一个 if 分支判断                                          │
│                                                                         │
│  路径 B: rcu_read_unlock() 中的补漏上报                               │
│  ════════════════════════════════════════════                           │
│                                                                         │
│  __rcu_read_unlock() {                                                 │
│      nesting--;                                                         │
│      if (nesting == 0 && unlikely(special)) {                          │
│          if (special.blocked)                                          │
│              rcu_report_qs();  // 之前被抢占 → 现在退出 → 补报 QS     │
│      }                                                                  │
│  }                                                                      │
│                                                                         │
│  适用: 读者在临界区中被抢占，恢复后退出（少数情况）                  │
│  开销: 只在被抢占过的情况下才触发                                      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 场景 1: 正常路径 — schedule() 批量上报（路径 A）

```
┌─────────────────────────────────────────────────────────────────────────┐
│  场景 1: 读者没有被抢占，在临界区外被调度                            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Time ──────────────────────────────────────────────────────────►       │
│                                                                         │
│  Task A:                                                                 │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │ rcu_read_lock()  →  nesting: 0→1                              │    │
│  │ use(old_ptr)                                                   │    │
│  │ rcu_read_unlock()→  nesting: 1→0                              │    │
│  │                   (nesting→0 但 blocked=false → 路径B不触发)   │    │
│  │                                                                 │    │
│  │ rcu_read_lock()  →  nesting: 0→1                              │    │
│  │ use(old_ptr)                                                   │    │
│  │ rcu_read_unlock()→  nesting: 1→0                              │    │
│  │                   (blocked=false → 路径B不触发)               │    │
│  │                                                                 │    │
│  │ rcu_read_lock()  →  nesting: 0→1                              │    │
│  │ use(old_ptr)                                                   │    │
│  │ rcu_read_unlock()→  nesting: 1→0                              │    │
│  │                   (blocked=false → 路径B不触发)               │    │
│  │                                                                 │    │
│  │ schedule() ──► 切换到 Task B                                   │    │
│  │    │                                                            │    │
│  │    └── rcu_note_context_switch():                              │    │
│  │          nesting == 0                                          │    │
│  │          blocked == false                                      │    │
│  │          → rcu_qs()  ✅  路径A: 批量上报 QS                    │    │
│  │                                                                 │    │
│  │  3 次 lock/unlock 的 QS 合并为 schedule() 中的 1 次上报       │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
│  关键: 每次 unlock 时 blocked 都是 false（没被抢占过）               │
│  所以路径 B 从未触发，所有 QS 由路径 A 在 schedule() 中批量完成     │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 场景 2: 抢占路径 — unlock() 补漏上报（路径 B）

```
┌─────────────────────────────────────────────────────────────────────────┐
│  场景 2: 读者在临界区中被抢占，恢复后退出                            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Time ──────────────────────────────────────────────────────────►       │
│                                                                         │
│  CPU 0, Task A:                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │ rcu_read_lock()  →  nesting: 0→1                              │    │
│  │ use(old_ptr)     ← 正在读旧数据                               │    │
│  │    │                                                            │    │
│  │    │ ⚡ 时钟中断! need_resched=1                              │    │
│  │    │ nesting=1 > 0 → 抢占!                                   │    │
│  │    ▼                                                            │    │
│  │ ──── schedule() ─────────────────────────────────────────────   │    │
│  │    │                                                            │    │
│  │    └── rcu_note_context_switch():                              │    │
│  │          nesting = 1 > 0  ❌ 不能报 QS                        │    │
│  │          → blocked = true  ← 标记: 此任务在临界区中被抢占     │    │
│  │                                                                 │    │
│  │ ════════ 被切换出去 ════════                                  │    │
│  │ (Task A 挂在就绪队列上，nesting=1, blocked=true)              │    │
│  │ (Task A 仍持有 old_ptr 的引用)                                 │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
│  CPU 0, Task B:                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │ (使用 CPU 0 运行一段时间)                                      │    │
│  │ ...                                                            │    │
│  │ schedule() ──► 切换到 Task A                                   │    │
│  │    │                                                            │    │
│  │    └── rcu_note_context_switch():                              │    │
│  │          (这里是 Task B 的状态，不是 Task A)                    │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
│  CPU 0, Task A 恢复:                                                   │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │ (从被抢占的位置继续)                                          │    │
│  │ use(old_ptr)     ← 还在用旧数据!                              │    │
│  │ rcu_read_unlock()                                               │    │
│  │    │                                                            │    │
│  │    └── __rcu_read_unlock():                                   │    │
│  │          nesting: 1→0                                           │    │
│  │          blocked == true  ← 之前被抢占过!                      │    │
│  │          → rcu_report_qs()  ✅  路径B: 补漏上报 QS              │    │
│  │          → blocked = false  ← 清除标记                        │    │
│  │                                                                 │    │
│  │ (此时才安全: nesting=0 且已经退出临界区)                      │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
│  为什么 schedule() 中不能报 QS?                                      │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │                                                               │    │
│  │  调度发生时:  nesting=1, Task A 还在临界区中                  │    │
│  │                                                               │    │
│  │  如果此时报 QS → GP 可能提前结束                              │    │
│  │  → Writer 释放 old_ptr                                        │    │
│  │  → Task A 恢复后 use(old_ptr) → use-after-free!               │    │
│  │                                                               │    │
│  │  所以只能记 blocked=true，等 unlock 时 nesting 归零再补报    │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 场景 3: 混合 — 两条路径都触发

```
┌─────────────────────────────────────────────────────────────────────────┐
│  场景 3: 多次临界区，中间一次被抢占                                  │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Time ──────────────────────────────────────────────────────────►       │
│                                                                         │
│  Task A:                                                                 │
│                                                                         │
│  ──[lock nest=1]──[use]──[unlock nest=0]──  blocked=false (正常)       │
│                                                          路径B: 不触发  │
│                                                                         │
│  ──[lock nest=1]──[use]──                                                  │
│                          │                                               │
│                          │ ⚡ 被抢占!                                    │
│                          ▼                                               │
│                    schedule():                                            │
│                      nesting=1 > 0                                       │
│                      blocked = true  ← 标记                               │
│                          │                                               │
│                          ══ 挂起 ══                                      │
│                          │                                               │
│                    恢复:                                                  │
│                          │                                               │
│                          ▼                                               │
│  ────────────────[unlock nest=0]──                                        │
│                      nesting→0                                           │
│                      blocked=true                                       │
│                      → rcu_report_qs() ✅  路径B: 补漏上报               │
│                      blocked = false                                     │
│                                                                         │
│  ──[lock nest=1]──[use]──[unlock nest=0]──  blocked=false (已清除)      │
│                                                          路径B: 不触发  │
│                                                                         │
│  ──[lock nest=1]──[use]──[unlock nest=0]──  blocked=false              │
│                                                          路径B: 不触发  │
│                                                                         │
│  ── schedule() ─────────────────────────────────────────────────          │
│         │                                                                │
│         └── nesting == 0, blocked == false                              │
│            → rcu_qs() ✅  路径A: 批量上报                              │
│                                                                         │
│  ──────────────────────────────────────────────────────────────────     │
│                                                                         │
│  5 次 unlock 中:                                                        │
│  - 1 次触发路径 B (被抢占后恢复的那次)                                │
│  - 4 次路径 B 不触发 (blocked=false)                                   │
│  - 1 次 schedule() 触发路径 A (收尾的批量上报)                         │
│                                                                         │
│  路径 B 是"不得不做"的精确上报                                       │
│  路径 A 仍然是批量合并，处理剩下的大多数 QS                           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 总结：blocked 标志位的作用

```
┌─────────────────────────────────────────────────────────────────────────┐
│          blocked 标志位: 路径 A 和路径 B 的桥梁                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  blocked 含义: "我在临界区中被抢占过，schedule() 没能替我报 QS"      │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  rcu_read_lock():                                          │       │
│  │    nesting++                                                 │       │
│  │    // 不碰 blocked                                         │       │
│  │                                                              │       │
│  │  schedule() 被调用时:                                       │       │
│  │    if (nesting > 0) blocked = true   ← 临走前设标记         │       │
│  │    if (nesting == 0) rcu_qs()       ← 没在临界区，直接报   │       │
│  │                                                              │       │
│  │  rcu_read_unlock():                                         │       │
│  │    nesting--                                                 │       │
│  │    if (nesting == 0 && blocked)                            │       │
│  │        rcu_report_qs()   ← 补报之前漏掉的 QS              │       │
│  │        blocked = false    ← 清除标记                       │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  blocked 的完整生命周期:                                                │
│                                                                         │
│  lock() → schedule() → unlock()                                        │
│    │          │            │                                         │
│  nest=1    blocked=true   nest=0                                      │
│            (被抢占)       blocked=true                                 │
│                           → 补报 QS                                    │
│                           → blocked=false                              │
│                                                                         │
│  lock() → schedule() → unlock() → schedule()                           │
│    │          │            │           │                              │
│  nest=1    blocked=true   nest=0      nest=0                          │
│            (被抢占)       blocked=true blocked=false                    │
│                           → 补报 QS    → 路径A 批量报                  │
│                           → blocked=false(幂等，不重复报)              │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.9 Preemptible RCU 的 rcu_node 挂载机制

上一节讲了 `blocked` 标志位和双路径 QS 上报。本节说明被抢占的任务挂在 Tree RCU 的哪个节点上，以及 GP 状态机如何检查这些被阻塞的任务。

```
┌─────────────────────────────────────────────────────────────────────────┐
│          被抢占任务的 rcu_node 挂载                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  任务被挂在抢占发生时所在 CPU 对应的叶子 rcu_node 上                   │
│                                                                         │
│  rcu_note_context_switch(cpu) 做了两件事:                               │
│                                                                         │
│  1. prev->blocked = true                                                │
│     标记任务本身（跟着 task_struct 走）                                │
│                                                                         │
│  2. 把 prev 挂到当前 CPU 对应的叶子 rcu_node 的 blkd_tasks 链表上       │
│     ← 关键：挂在抢占发生时的 CPU 对应的节点上                          │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │                                                                  │    │
│  │  Tree RCU 结构:                                                  │    │
│  │                                                                  │    │
│  │         rcu_node[root]                                          │    │
│  │         blkd_tasks: 空                                          │    │
│  │              │                                                   │    │
│  │       ┌──────┴──────┐                                           │    │
│  │       │             │                                            │    │
│  │  rcu_node[L1-0]  rcu_node[L1-1]                                  │    │
│  │  (CPU 0-3)       (CPU 4-7)                                       │    │
│  │                                                                  │    │
│  │  ┌─────────────────────────────────┐                             │    │
│  │  │ rcu_node[L1-0] (CPU 0-3):      │                             │    │
│  │  │                                 │                             │    │
│  │  │ blkd_tasks:                     │                             │    │
│  │  │   → Task A (nesting=1, CPU 0)  │ ← 在 CPU 0 上被抢占        │    │
│  │  │   → Task D (nesting=2, CPU 2)  │ ← 在 CPU 2 上被抢占        │    │
│  │  │                                 │                             │    │
│  │  │ CPU 0: Task C 在运行           │                             │    │
│  │  │ CPU 1: Task B 在运行 (nest=0)  │                             │    │
│  │  │ CPU 2: Task E 在运行           │                             │    │
│  │  │ CPU 3: idle                    │                             │    │
│  │  └─────────────────────────────────┘                             │    │
│  │                                                                  │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 任务恢复后的处理

```
┌─────────────────────────────────────────────────────────────────────────┐
│          任务恢复、unlock、从 blkd_tasks 移除                           │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  情况 A: Task A 在 CPU 0 上恢复 (同一个 CPU)                          │
│  ──────────────────────────────────────────────                        │
│                                                                         │
│  CPU 0: Task A 恢复 → unlock → nesting=0                               │
│    → rcu_read_unlock_special():                                        │
│        blocked == true                                                 │
│        → 从 rcu_node[L1-0] 的 blkd_tasks 链表中移除 Task A            │
│        → rcu_report_qs() 上报                                          │
│        → blocked = false                                               │
│    → 此时 rcu_node[L1-0] 只剩 Task D，还不到空                       │
│                                                                         │
│  情况 B: Task A 在 CPU 3 上恢复 (不同 CPU，但同一个 rcu_node)        │
│  ──────────────────────────────────────────────────────                │
│                                                                         │
│  CPU 3 属于同一个 rcu_node[L1-0]                                      │
│  → blkd_tasks 链表是同组 CPU 共享的，直接移除                        │
│  → 没有问题                                                            │
│                                                                         │
│  情况 C: Task A 在 CPU 5 上恢复 (不同 rcu_node!)                      │
│  ──────────────────────────────────────────────                        │
│                                                                         │
│  CPU 5 属于 rcu_node[L1-1]                                            │
│  但 Task A 挂在 rcu_node[L1-0] 上                                     │
│                                                                         │
│  Task A 恢复 → unlock → nesting=0                                      │
│    → 仍然从 rcu_node[L1-0] 移除                                       │
│    → Task A 的 task_struct 里记录了 rcu_node 指针                    │
│    → 不管在哪个 CPU 上 unlock，都能找到正确的节点移除                 │
│    → 可能需要跨节点操作（持有对应 rcu_node 的锁）                    │
│                                                                         │
│  时序:                                                                  │
│  ─────                                                                  │
│                                                                         │
│  CPU 0: Task A lock(nest=1) → 被抢占                                  │
│         schedule(): nesting>0 → 挂入 rcu_node[L1-0].blkd_tasks        │
│         │                                                              │
│         │ (Task A 在就绪队列上等)                                     │
│         │                                                              │
│  CPU 5: Task A 被调度到 CPU 5 上恢复                                   │
│         (因为负载均衡把 Task A 迁移了)                                 │
│         │                                                              │
│         unlock(nest=0): blocked=true                                   │
│         → 从 rcu_node[L1-0].blkd_tasks 移除                           │
│         → rcu_report_qs() 上报                                         │
│         → blocked=false                                                │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### GP 状态机的完整判定逻辑

```
┌─────────────────────────────────────────────────────────────────────────┐
│          rcu_node 的 QS 判定: 常规 QS + blkd_tasks 都要检查            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  rcu_node[L1-0] 可以向上报告"全部完成"的条件:                       │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │                                                              │       │
│  │  条件 1: 本组所有 CPU 都上报了常规 QS                       │       │
│  │    CPU 0: ✅                                                 │       │
│  │    CPU 1: ✅                                                 │       │
│  │    CPU 2: ✅                                                 │       │
│  │    CPU 3: ✅                                                 │       │
│  │                                                              │       │
│  │  条件 2: blkd_tasks 链表为空                                │       │
│  │    → 没有被抢占的任务还挂着                               │       │
│  │    → 即使所有 CPU 常规 QS 了，如果链表不为空              │       │
│  │      这个节点也不能向上报告                                │       │
│  │                                                              │       │
│  │  两个条件都满足 → 向上报告 → 父节点/根节点检查所有子节点    │       │
│  │  所有子节点都完成 → GP 结束                                │       │
│  │                                                              │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  blkd_tasks 是 Preemptible RCU 对 Classic RCU 的关键扩展:             │
│                                                                         │
│  Classic RCU:                                                           │
│    不可能有被抢占的读者 → blkd_tasks 永远为空 → 只检查常规 QS         │
│                                                                         │
│  Preemptible RCU:                                                       │
│    读者可能被抢占 → blkd_tasks 可能有内容 → 必须额外检查              │
│    检查两个条件: 常规 QS 完成 AND blkd_tasks 清空                      │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.10 Preemptible RCU 的 QS 检测：boost 机制

可抢占内核中，RCU 读者可能被抢占且长时间不被调度回来。这会导致 GP 无限延长。内核用 **boost 机制**解决这个问题：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                Preemptible RCU 的 Boost 机制                            │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  问题场景:                                                              │
│                                                                         │
│  CPU 0: ────[Task A 在 RCU 临界区中被抢占]────────────────────        │
│                                                                         │
│  CPU 1: ────[Task B 在 RCU 临界区中被抢占]────────────────────        │
│            (Task B 优先级低，没有 CPU 愿意运行它)                       │
│                                                                         │
│  Writer: ────[call_rcu]──[GP 开始]────────────────────── 一直在等...    │
│                                                   GP 无法结束!         │
│                                                                         │
│  原因: Task A 和 Task B 都在 RCU 临界区中被抢占                      │
│        低优先级 → 调度器不急于恢复它们                                │
│        但 GP 必须等它们 nesting 降到 0 才能结束                       │
│                                                                         │
│  ────────────────────────────────────────────────                       │
│  Boost 机制:                                                            │
│  ────────────────────────────────────────────────                       │
│                                                                         │
│  Step 1: GP kthread 发现 GP 长时间不结束                             │
│                                                                         │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │  rcu_boost_kthread (per-CPU):                               │       │
│  │                                                              │       │
│  │  while (1) {                                                 │       │
│  │      // 检查是否有被抢占的 RCU 读者需要 boost                 │       │
│  │      for each blocked reader on this CPU:                   │       │
│  │                                                              │       │
│  │          if (reader 在 RCU 临界区中 && 被抢占时间过长) {    │       │
│  │              // 临时提高该读者的优先级                        │       │
│  │              rt_mutex_setprio(reader_task, RCU_BOOST_PRIO);  │       │
│  │          }                                                   │       │
│  │                                                              │       │
│  │      schedule();  // 让 boost 生效                           │       │
│  │  }                                                           │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  Step 2: 被提升优先级的读者被调度执行                                 │
│                                                                         │
│  CPU 0: ────[Task A 恢复执行]──[rcu_read_unlock]──[恢复正常优先级]──  │
│                     ↑                                                  │
│                     │ boost 生效，高优先级立即调度                    │
│                     │                                                  │
│  Step 3: nesting 降到 0 → QS 完成 → GP 可能结束                      │
│                                                                         │
│  时序:                                                                  │
│  ─────                                                                  │
│                                                                         │
│  Time: ───────────────────────────────────────────────────────►        │
│                                                                         │
│  Task A: ──[lock]────被抢占──────boost!────恢复──[unlock]──────        │
│          │         │              │         │           │               │
│          │  低优先级│   高优先级   │  正常优先级│                   │
│          │  长时间等待│   立即调度  │         │           │               │
│          │         │              │         │           │               │
│  Writer: ──[替换]──[GP开始]──────────────────────────[GP结束][free]──  │
│                                              ↑                         │
│                                              │ Task A 终于 unlock      │
│                                              │ QS 完成                 │
│                                                                         │
│  注意: boost 是 CONFIG_PREEMPT_RT 的专有特性                           │
│  对于 CONFIG_PREEMPT（非 RT），也有类似机制但更简单                    │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.11 CPU QS 上报延迟与超时处理

前面的讨论假设所有 CPU 都会及时上报 QS。实际上 CPU 可能因为各种原因延迟上报，甚至卡住不报。内核有三层机制应对这种情况。

```
┌─────────────────────────────────────────────────────────────────────────┐
│          CPU QS 上报延迟的两种情况                                     │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  情况 A: CPU 就是忙，还没经过 QS (正常)                              │
│  ══════════════════════════════════════════════                         │
│                                                                         │
│  CPU 3 在执行很长的内核代码 (不涉及 RCU)                              │
│  → 没有上下文切换、没有 idle、没有用户态切换                          │
│  → GP 就是应该等这个 CPU，这是正常行为                               │
│                                                                         │
│  情况 B: CPU 在 RCU 临界区中执行太久 (异常)                          │
│  ═══════════════════════════════════════════                           │
│                                                                         │
│  CPU 3 在 rcu_read_lock() 和 rcu_read_unlock() 之间跑了很久          │
│  → nesting 一直 > 0 → 无法上报 QS                                    │
│  → 通常意味着代码有 bug（临界区不应该很长）                           │
│                                                                         │
│  情况 C: CPU 离线 (hotplug)                                           │
│  ═════════════════════════                                             │
│                                                                         │
│  CPU 被热拔出 → 永远不会再报 QS                                      │
│  → _cpu_down() 中调用 rcu_report_dead()                              │
│  → 强制标记该 CPU 的 QS 完成 → GP 不再等它                           │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 第一层：时钟中断兜底

```
┌─────────────────────────────────────────────────────────────────────────┐
│          时钟中断: 兜底 QS 上报                                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  即使 CPU 一直在执行内核代码不主动上报，时钟中断也会定期检查         │
│                                                                         │
│  CPU 3 在执行很长的内核代码:                                           │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────────┐    │
│  │                                                                  │    │
│  │  长内核代码:  ════════════════════════════════════════════════  │    │
│  │                                                                  │    │
│  │  时钟中断 1: ──┤                                               │    │
│  │    rcu_check_callbacks():                                       │    │
│  │      preempt_count == 0? nesting == 0?                          │    │
│  │      → 不在临界区 → 标记 QS → 上报 rcu_node ✅                 │    │
│  │                                                                  │    │
│  │  时钟中断 2: ──────────────┤                                   │    │
│  │    (重复检查，幂等)                                              │    │
│  │                                                                  │    │
│  └─────────────────────────────────────────────────────────────────┘    │
│                                                                         │
│  最大延迟 = 1 个时钟中断周期:                                         │
│  CONFIG_HZ=250  → 4ms                                                  │
│  CONFIG_HZ=1000 → 1ms                                                  │
│                                                                         │
│  如果 CPU 在 RCU 临界区中 (nesting > 0):                              │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │  时钟中断 → rcu_check_callbacks():                           │       │
│  │    nesting > 0 → 还在临界区 → 不报 QS                       │       │
│  │    → 等下次时钟中断再检查                                    │       │
│  │                                                              │       │
│  │  这是唯一能让 GP 等很久的情况                               │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 第二层：GP kthread 超时诊断

```
┌─────────────────────────────────────────────────────────────────────────┐
│          rcu_gp_kthread 的超时检查                                      │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  rcu_gp_kthread() {                                                    │
│      while (1) {                                                        │
│          // 启动 GP                                                    │
│          start_new_grace_period();                                      │
│                                                                         │
│          // 等待所有 CPU QS，有超时                                    │
│          for (;;) {                                                     │
│              ret = wait_event_interruptible_timeout(                    │
│                  gp_wq,                                                 │
│                  all_cpus_reported_qs(),                                │
│                  timeout);                                              │
│                                                                         │
│              if (all_cpus_reported_qs())                                │
│                  break;  // 正常完成                                    │
│                                                                         │
│              if (ret == 0) {  // 超时                                  │
│                  // 打印哪些 CPU 还没报                               │
│                  dump_fqs_info();                                       │
│              }                                                          │
│          }                                                              │
│      }                                                                  │
│  }                                                                      │
│                                                                         │
│  GP kthread 只负责等待和诊断，不强制推进                              │
│  → QS 上报只能由 CPU 自己完成，别人无法替代                          │
│  → 因为只有 CPU 自己知道是否还在 RCU 临界区中                       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 第三层：RCU Stall Warning

```
┌─────────────────────────────────────────────────────────────────────────┐
│          RCU Stall Warning: 告警而不是修复                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  GP 超过一定时间没结束 (默认 21 秒):                                  │
│                                                                         │
│  rcu: INFO: rcu_preempt detected stalls on CPUs/tasks:                 │
│  { 3 }  (detected by 0, t=5252 jiffies, g=709, q=710)                  │
│                                                                         │
│  含义: CPU 3 超过 21 秒没上报 QS，由 CPU 0 检测到                    │
│                                                                         │
│  常见原因:                                                              │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │  1. CPU 3 在 RCU 临界区中死循环 (代码 bug)                   │       │
│  │  2. CPU 3 被关中断太久 (长时间 cli / spin_lock_irq)          │       │
│  │  3. CPU 3 在执行极长计算 (加密/压缩/大量内存操作)            │       │
│  │  4. 虚拟化环境下 CPU 3 被 hypervisor 拿走 (steal time)      │       │
│  │  5. 实时内核中高优先级任务霸占 CPU 3                         │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  内核只能告警，不能强制推进:                                           │
│  → CPU 3 可能真的还在临界区中 → 强制结束 GP → use-after-free         │
│  → 所以只能等，同时告警让开发者修复                                  │
│                                                                         │
│  配置:                                                                  │
│  CONFIG_RCU_CPU_STALL_TIMEOUT=21   // 默认 21 秒                       │
│  rcupdate.rcu_cpu_stall_timeout=60  // 启动参数可覆盖                  │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

#### 三层机制总结

```
┌─────────────────────────────────────────────────────────────────────────┐
│                                                                         │
│  1. 时钟中断兜底 (1~4ms)                                              │
│     → 即使 CPU 不主动上报，时钟中断也会定期检查并上报                 │
│     → 覆盖绝大多数情况                                               │
│                                                                         │
│  2. GP kthread 超时诊断                                                │
│     → wait_event_timeout 检测卡住的 CPU                              │
│     → 打印诊断信息，帮助定位问题                                     │
│                                                                         │
│  3. RCU Stall Warning (21 秒)                                         │
│     → 告警：某个 CPU 可能有问题                                      │
│     → 不修复：不能强制推进，否则会 use-after-free                    │
│     → 通常意味着代码有 bug（临界区太长）                             │
│                                                                         │
│  核心原则: QS 上报只能由 CPU 自己完成，别人无法替代                  │
│  因为只有 CPU 自己知道是否还在 RCU 临界区中                         │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.12 抢占机制在内核中的其他影响和注意点

抢占机制不仅仅影响 RCU，它还深刻影响着 Linux 内核的其他许多方面：

```
┌─────────────────────────────────────────────────────────────────────────┐
│          抢占机制对内核其他子系统的广泛影响                              │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  1. 自旋锁 (spinlock)                                                   │
│  ══════════════════                                                     │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  PREEMPT_NONE:                                            │         │
│  │  spin_lock() → preempt_disable()                          │         │
│  │  持有 spinlock 期间，当前任务不会被抢占                    │         │
│  │  → 不会死锁（不可能有两个任务在同一 CPU 上争同一把锁）    │         │
│  │                                                            │         │
│  │  PREEMPT_RT:                                              │         │
│  │  spinlock → 变成了 mutex (rt_mutex)                       │         │
│  │  持有"自旋锁"的线程可以被抢占                            │         │
│  │  其他等待者不会被饿死                                     │         │
│  │  但不能在中断上下文中使用（mutex 可睡眠）                  │         │
│  │  → 原来的 spin_lock_irq() 变成了 rt_spin_lock()           │         │
│  │  → 需要禁用本地中断来保护中断上下文中的锁                  │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  2. 完成量 (completion) / 等待队列 (wait_queue)                         │
│  ═══════════════════════════════════════════════                       │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  PREEMPT_NONE:                                            │         │
│  │  等待者在内核中 sleep，当前代码不可抢占                    │         │
│  │  唤醒时可能不会立即调度                                   │         │
│  │                                                            │         │
│  │  PREEMPT / RT:                                            │         │
│  │  等待者被唤醒后可能立即抢占当前任务                        │         │
│  │  → wake_up() 路径中可能触发调度                            │         │
│  │  → 需要注意在持锁期间不能调用可能导致调度的操作            │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  3. 中断处理                                                            │
│  ══════════════                                                         │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  PREEMPT_NONE:                                            │         │
│  │  中断处理期间 preempt_count 增大 → 不可抢占               │         │
│  │  中断处理程序可以安全访问 per-CPU 数据                    │         │
│  │                                                            │         │
│  │  PREEMPT_RT:                                              │         │
│  │  硬中断处理程序变成内核线程 (中断线程化)                   │         │
│  │  中断线程可以被抢占、可以睡眠                              │         │
│  │  只保留少量真正的硬中断代码（ack + 唤醒线程）              │         │
│  │  → 中断处理延迟增加，但避免了长中断阻塞高优先级任务       │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  4. per-CPU 数据                                                        │
│  ══════════════                                                         │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  PREEMPT_NONE:                                            │         │
│  │  访问 per-CPU 数据天然安全（不会被抢占）                  │         │
│  │  不需要额外保护                                          │         │
│  │                                                            │         │
│  │  PREEMPT:                                                 │         │
│  │  访问 per-CPU 数据时可能被抢占                           │         │
│  │  被抢占后迁移到其他 CPU → per-CPU 数据不再是"当前CPU的"  │         │
│  │  → 需要 preempt_disable/enable 保护                       │         │
│  │  → 或者使用 this_cpu_* 操作（内部带 preempt_disable）      │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  5. 定时器和延迟                                                        │
│  ════════════════                                                       │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  PREEMPT_NONE:                                            │         │
│  │  ndelay/udelay/mdelay: 忙等待（占着 CPU）                 │         │
│  │  不必担心被抢占导致延迟不准确                              │         │
│  │                                                            │         │
│  │  PREEMPT_RT:                                              │         │
│  │  短延迟: 仍可忙等待                                       │         │
│  │  长延迟: 可能被抢占，延迟可能超过预期                      │         │
│  │  → 某些驱动需要改用 schedule_timeout() 代替 mdelay()      │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
│  6. 锁的嵌套规则                                                       │
│  ════════════════                                                       │
│  ┌────────────────────────────────────────────────────────────┐         │
│  │  规则: 在持锁期间，禁止调用可能睡眠的函数                  │         │
│  │                                                            │         │
│  │  PREEMPT_NONE:                                            │         │
│  │  spin_lock() 自动禁用抢占                                 │         │
│  │  → 在 spinlock 中调用 kmalloc(GFP_KERNEL) 不会真的睡眠   │         │
│  │  → 因为不会被调度走                                       │         │
│  │  (但这仍然是 bad practice)                                 │         │
│  │                                                            │         │
│  │  PREEMPT:                                                 │         │
│  │  spin_lock 仍然禁用抢占                                   │         │
│  │  → 同上                                                    │         │
│  │                                                            │         │
│  │  PREEMPT_RT:                                              │         │
│  │  spinlock → mutex，可睡眠                                 │         │
│  │  → 嵌套规则完全改变                                       │         │
│  │  → 必须审查所有持锁路径                                   │         │
│  │  → 很多原来"安全"的代码变得不安全                        │         │
│  │  → 这是 RT 内核移植最大的工作量和风险来源                  │         │
│  └────────────────────────────────────────────────────────────┘         │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 3.13 为什么 DPDK 不需要考虑抢占

```
┌─────────────────────────────────────────────────────────────────────────┐
│                DPDK 为什么不需要考虑抢占                                │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  DPDK 运行环境的本质:                                                   │
│                                                                         │
│  1. 绑定 CPU 核心 (CPU affinity)                                       │
│     ┌────────────────────────────────────────────────────────────┐       │
│     │  rte_eal_init() 后，每个 lcore 绑定到固定 CPU            │       │
│     │  使用 sched_setaffinity() 锁定                           │       │
│     │  → 线程永远不会被调度到其他 CPU                         │       │
│     │  → per-CPU 数据天然安全                                 │       │
│     └────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  2. 轮询模式 (Poll Mode)                                               │
│     ┌────────────────────────────────────────────────────────────┐       │
│     │  每个 lcore 运行 while (!quit) { rx_burst(); process(); }│       │
│     │  从不调用 sleep()、从不让出 CPU                          │       │
│     │  → OS 调度器认为这个 CPU "很忙"                         │       │
│     │  → 不会主动切换走（除非 nice 值/优先级设置问题）         │       │
│     │  → 即使时钟中断到来，中断处理完就回到 poll loop          │       │
│     └────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  3. 独占 CPU (isolcpus / nohz_full)                                    │
│     ┌────────────────────────────────────────────────────────────┐       │
│     │  Linux 内核启动参数:                                     │       │
│     │  isolcpus=2-5        将 CPU 2-5 从调度器中隔离          │       │
│     │  nohz_full=2-5       这些 CPU 不接收周期性时钟中断       │       │
│     │  rcu_nocbs=2-5       RCU 回调不在这些 CPU 上执行        │       │
│     │  irqaffinity=0,1      中断只路由到 CPU 0,1               │       │
│     │                                                            │       │
│     │  → DPDK 的 lcore 2-5 几乎完全没有内核干扰              │       │
│     │  → 没有 OS 调度 → 没有抢占                             │       │
│     │  → 没有 OS 时钟中断 → 没有自动 QS 检测时机              │       │
│     └────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  结果:                                                                  │
│  ─────                                                                  │
│  ┌────────────────┬──────────────────────────────────────────┐          │
│  │ 不存在抢占     │ 不需要 preempt_disable/enable            │          │
│  │ 不存在上下文切换 │ "上下文切换 = QS" 不适用               │          │
│  │ 不存在 idle     │ "idle = QS" 不适用                      │          │
│  │ 不存在用户态切换 │ "用户态 = QS" 不适用                   │          │
│  └────────────────┴──────────────────────────────────────────┘          │
│                                                                         │
│  → 没有任何"天然的"静默状态事件                                        │
│  → 必须让线程自己说"我安全了"                                         │
│  → 这就是 QSBR 存在的根本原因                                          │
│                                                                         │
│  反过来看:                                                              │
│  Linux 有抢占 → 需要处理"读者被抢占"的问题 → Preemptible RCU           │
│  Linux 有调度器 → 自动检测 QS → 读者负担轻                             │
│  DPDK 无抢占 → 读者不可能被中途打断 → 但也没有自动 QS                 │
│  DPDK 无调度器 → 必须手动 QS → 设计更简单但需开发者自律               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 4. Linux 内核 RCU 实现（Tree RCU）

Linux 内核的 RCU 是目前最复杂、最成熟的 RCU 实现。上一节讨论的抢占机制直接决定了 RCU 读取端的形式，本节聚焦于 Linux RCU 的写入端和宽限期检测（Tree RCU 状态机）。

### 4.1 设计约束

Linux 内核面临的环境：

- **抢占式调度**：读者可能被抢占，调度到其他 CPU 上运行
- **CPU 数量庞大**：服务器可能有几百个 CPU，逐个检查太慢
- **CPU 热插拔**：CPU 可能随时上线/下线
- **多种 RCU 变体**：不可抢占 RCU、可抢占 RCU（Preemptible RCU / SRCU）
- **性能要求**：读者路径必须极致轻量

### 4.2 读取端实现

```
┌─────────────────────────────────────────────────────────────────┐
│                Linux RCU 读取端                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  不可抢占内核 (CONFIG_PREEMPT_NONE):                            │
│  ─────────────────────────────────                              │
│  rcu_read_lock()  →  preempt_disable()                         │
│                     // 只是关闭抢占，没有原子操作               │
│                                                                 │
│  rcu_read_unlock() →  preempt_enable()                         │
│                                                                 │
│  可抢占内核 (CONFIG_PREEMPT / CONFIG_PREEMPT_RT):               │
│  ──────────────────────────────────────────                     │
│  rcu_read_lock()  →  __rcu_read_lock()                         │
│                     // current->rcu_read_lock_nesting++         │
│                     // 增加 per-task 嵌套计数                   │
│                                                                 │
│  rcu_read_unlock() →  __rcu_read_unlock()                      │
│                     // nesting--                                │
│                     // 如果 nesting == 0，检查是否需要报告 QS   │
│                                                                 │
│  rcu_dereference(ptr):                                          │
│  ──────────────────────                                         │
│  // READ_ONCE + smp_barrier_dependent                          │
│  // 确保编译器不会优化掉读取，且依赖顺序正确                   │
│                                                                 │
│  开销分析:                                                      │
│  ┌──────────────────┬────────────────────────────────┐          │
│  │ 不可抢占内核     │ preempt_disable/enable          │          │
│  │                  │ ≈ 几个时钟周期                  │          │
│  ├──────────────────┼────────────────────────────────┤          │
│  │ 可抢占内核       │ per-task 计数器 ++/--           │          │
│  │                  │ ≈ 几个时钟周期                  │          │
│  └──────────────────┴────────────────────────────────┘          │
│                                                                 │
│  共同特点：零原子操作、零内存屏障、零自旋等待                    │
└─────────────────────────────────────────────────────────────────┘
```

### 4.3 写入端实现

```
┌─────────────────────────────────────────────────────────────────┐
│                Linux RCU 写入端                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  方式一：同步等待                                               │
│  ────────────────                                               │
│  void update_data(void)                                         │
│  {                                                              │
│      struct data *old = rcu_dereference(gp);                    │
│      struct data *new = kmalloc(sizeof(*new), GFP_KERNEL);      │
│                                                                 │
│      *new = *old;                                               │
│      new->field = updated_value;                                │
│                                                                 │
│      rcu_assign_pointer(gp, new);  // 原子发布新指针           │
│                                                                 │
│      synchronize_rcu();  // 阻塞，等待宽限期                   │
│      // 可能等几毫秒到几百毫秒                                 │
│                                                                 │
│      kfree(old);  // 安全释放                                   │
│  }                                                              │
│                                                                 │
│  方式二：异步回调（更常用）                                     │
│  ──────────────────────────────                                 │
│  void update_data_async(void)                                   │
│  {                                                              │
│      struct data *old = rcu_dereference(gp);                    │
│      struct data *new = kmalloc(sizeof(*new), GFP_KERNEL);      │
│                                                                 │
│      *new = *old;                                               │
│      new->field = updated_value;                                │
│                                                                 │
│      rcu_assign_pointer(gp, new);                               │
│                                                                 │
│      // 非阻塞！将回调挂入队列                                 │
│      // 宽限期结束后由软中断自动调用                            │
│      call_rcu(&old->rcu_head, free_old_callback);               │
│  }                                                              │
│                                                                 │
│  void free_old_callback(struct rcu_head *head)                  │
│  {                                                              │
│      struct data *old = container_of(head, struct data, rcu_head│
│      kfree(old);                                                │
│  }                                                              │
└─────────────────────────────────────────────────────────────────┘
```

### 4.4 宽限期检测：Tree RCU 状态机

这是 Linux RCU 最精妙也最复杂的部分。核心问题：**内核如何检测"所有 CPU 都经过了静默状态"？**

```
┌─────────────────────────────────────────────────────────────────────────┐
│                什么是 Quiescent State (静默状态)?                       │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Quiescent State = CPU 当前不在 RCU 临界区中                           │
│                                                                         │
│  触发条件（任选其一即可）:                                             │
│  ┌──────────────────────────────────────────────────────────────┐       │
│  │ 1. 上下文切换 (context switch / schedule)                    │       │
│  │    → 旧任务必须先 rcu_read_unlock()，此时一定不在临界区     │       │
│  │                                                              │       │
│  │ 2. 进入 idle 循环 (CPU 空闲)                                 │       │
│  │    → idle 线程不在 RCU 临界区中                              │       │
│  │                                                              │       │
│  │ 3. 从用户态返回内核 (user → kernel transition)               │       │
│  │    → 用户态代码不调用 rcu_read_lock()                       │       │
│  │                                                              │       │
│  │ 4. CPU 热插拔下线                                            │       │
│  │    → 该 CPU 不再运行，自然不在临界区                         │       │
│  └──────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  核心洞察:                                                               │
│  只要 CPU 经历了以上任一事件，                                          │
│  它在此之前的所有 RCU 临界区都已结束                                    │
│  → 可以安全地认为该 CPU "已通过静默状态"                               │
└─────────────────────────────────────────────────────────────────────────┘
```

但问题是：Linux 服务器可能有 896 个 CPU（如 AMD EPYC 服务器），逐个检查效率太低。所以内核采用了 **Tree RCU** —— 一个分层的静默状态上报结构：

```
┌─────────────────────────────────────────────────────────────────────────┐
│                Tree RCU 层级结构                                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  层级 0 (叶节点): 每个 CPU 直接报告自己的 QS                           │
│                                                                         │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐   ┌──────┐ ┌──────┐ ┌──────┐     │
│  │CPU 0 │ │CPU 1 │ │CPU 2 │ │CPU 3 │...│CPU 4 │ │CPU 5 │ │CPU 6 │     │
│  │ qs=N │ │ qs=N │ │ qs=N │ │ qs=N │   │ qs=N │ │ qs=N │ │ qs=N │     │
│  └──┬───┘ └──┬───┘ └──┬───┘ └──┬───┘   └──┬───┘ └──┬───┘ └──┬───┘     │
│     │        │        │        │           │        │        │          │
│     ▼        ▼        ▼        ▼           ▼        ▼        ▼          │
│  层级 1 (中间节点): 每 4 个 CPU 合并为一个 rcu_node                     │
│                                                                         │
│  ┌─────────────────────────┐         ┌─────────────────────────┐        │
│  │  rcu_node[0]            │         │  rcu_node[1]            │        │
│  │  CPU 0-3 的 QS 汇总    │         │  CPU 4-7 的 QS 汇总    │        │
│  │  all_qs = true?         │         │  all_qs = true?         │        │
│  └───────────┬─────────────┘         └───────────┬─────────────┘        │
│              │                                    │                     │
│              ▼                                    ▼                     │
│  层级 2 (根节点): 所有中间节点向上合并                                  │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────┐       │
│  │  rcu_node[root]                                               │       │
│  │  所有 CPU 都报告 QS → 宽限期结束                             │       │
│  │  → 触发回调执行 (rcu_do_batch)                               │       │
│  └───────────────────────────────────────────────────────────────┘       │
│                                                                         │
│  类比:                                                                   │
│  就像公司的层层汇报:                                                   │
│  - 每个 CPU 像员工，完成工作后向组长报告                              │
│  - 组长 (rcu_node L1) 收齐组内所有成员的报告后，向部门经理汇报       │
│  - 部门经理 (rcu_node L2) 收齐所有组长报告后，向总经理汇报           │
│  - 总经理 (root node) 确认全员完成 → 宽限期结束                      │
│                                                                         │
│  优势:                                                                   │
│  - 每个节点只检查自己子节点的状态，O(log N) 复杂度                    │
│  - 锁争用分散到各层，根节点锁竞争大幅降低                              │
│  - 适合大规模系统 (数百 CPU)                                           │
└─────────────────────────────────────────────────────────────────────────┘
```

### 4.5 完整时序

```
Time ─────────────────────────────────────────────────────────────────►

CPU 0: ──[rcu_read_lock]────[use old]────[rcu_read_unlock]──────
                                             ↑
CPU 1: ──[rcu_read_lock]────[use old]──────────[schedule]───────
                                                             ↑ QS!
CPU 2: ──[user mode]─────────────[syscall entry]────────────────
                                     ↑ QS!
CPU 3: ──[idle]────────────────[wake up]────────────────────────
                ↑ QS!

Updater: ──[替换指针]──[call_rcu]──[GP 开始]────────────[GP 结束]──[callback: kfree]──
                               │                         │
                               └─── Grace Period ────────┘
                                    等待所有 CPU 至少一次 QS

详细步骤:
1. t0: Updater 调用 rcu_assign_pointer(gp, new)，替换指针
2. t0: Updater 调用 call_rcu(&old->rcu_head, callback)，注册回调
3. t0+ε: 内核启动新的 Grace Period，记录当前 GP 编号
4. t1-t3: 各 CPU 在正常运行中经过 QS（上下文切换/idle/用户态）
5. t1-t3: 各 CPU 的 QS 上报到 Tree RCU 对应的 rcu_node
6. t3+: 根节点确认所有 CPU 都已上报 QS → GP 结束
7. t4: 内核软中断 (rcu_softirq) 执行回调: callback(old) → kfree(old)
```

### 4.6 GP 状态机的驱动

Linux 内核的 GP 检测是**自动的**，由内核基础设施驱动，不需要应用线程主动参与：

| 驱动源       | 机制                            | 作用                               |
| ------------ | ------------------------------- | ---------------------------------- |
| 时钟中断     | `CONFIG_HZ`（通常 250/1000 Hz） | 周期性触发 `rcu_check_callbacks()` |
| 软中断       | `RCU_SOFTIRQ`                   | 处理 QS 上报、GP 推进、回调执行    |
| 上下文切换   | `schedule()`                    | 标记当前 CPU 通过 QS               |
| kthread      | `rcu_gp_kthread`                | 管理 GP 状态机（启动/推进/结束）   |
| NOCB kthread | `rcu_nocb_kthread`              | 卸载回调执行到专用 CPU             |

## 5. DPDK QSBR RCU 实现

DPDK 运行在用户态，每个线程轮询（poll-mode）绑定一个 CPU 核心。没有操作系统调度器介入，线程永远不会被抢占或上下文切换。这意味着 Linux 的"检测上下文切换"机制完全不适用。

DPDK 采用了 **QSBR（Quiescent-State-Based Reclamation）** 方案：每个线程**主动报告**自己的静默状态。

### 5.1 设计约束

DPDK 面对的环境：

- **无抢占**：每个 lcore 运行 poll loop，不会主动让出 CPU
- **固定核绑定**：线程与 CPU 一一对应，不会迁移
- **确定性延迟**：数据面要求可预测的延迟
- **少量线程**：通常 4~32 个 worker，不需要复杂层级

### 5.2 核心数据结构

```c
struct rte_rcu_qsbr {
    uint64_t token __rte_cache_aligned;
    // 全局版本号（当前 Grace Period 的 token）
    // 写者调用 synchronize 时递增

    uint32_t max_threads;
    // 注册的线程总数

    struct rte_rcu_qsbr_cnt {
        uint64_t cnt;
        // 该线程上次报告的 token 值
        // cnt >= token 表示该线程已通过当前 GP
        uint8_t locked;
        // 该线程是否在 RCU 临界区中
    } var[0] __rte_cache_aligned;
    // 柔性数组，每个线程一个计数器
    // cache line 对齐，避免 false sharing
};
```

内存布局（假设 4 个线程）：

```
┌─────────────────────────────────────────────────────────────────┐
│  struct rte_rcu_qsbr 内存布局                                   │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  ┌──────────────────────────┐ ← cache line 对齐                │
│  │  token = 3               │ 全局版本号                       │
│  │  max_threads = 4         │                                  │
│  └──────────────────────────┘                                  │
│                                                                 │
│  ┌──────────────────────────┐ ← cache line 对齐                │
│  │  var[0].cnt = 3  ✅      │ lcore 0: 已追上 token            │
│  │  var[0].locked = 0       │                                  │
│  └──────────────────────────┘                                  │
│                                                                 │
│  ┌──────────────────────────┐ ← cache line 对齐                │
│  │  var[1].cnt = 2  ⏳      │ lcore 1: 还没报告到 token=3     │
│  │  var[1].locked = 0       │                                  │
│  └──────────────────────────┘                                  │
│                                                                 │
│  ┌──────────────────────────┐ ← cache line 对齐                │
│  │  var[2].cnt = 3  ✅      │ lcore 2: 已追上                  │
│  │  var[2].locked = 0       │                                  │
│  └──────────────────────────┘                                  │
│                                                                 │
│  ┌──────────────────────────┐ ← cache line 对齐                │
│  │  var[3].cnt = 1  ⏳      │ lcore 3: 严重落后               │
│  │  var[3].locked = 0       │                                  │
│  └──────────────────────────┘                                  │
│                                                                 │
│  宽限期判定: ∀i ∈ [0,3], var[i].cnt >= token                   │
│  当前: Thread 0,2 通过，Thread 1,3 未通过 → GP 未结束          │
└─────────────────────────────────────────────────────────────────┘
```

### 5.3 初始化

```c
// 创建 QSBR 变量，最多支持 4 个线程
struct rte_rcu_qsbr *q = rte_rcu_qsbr_create(socket_id, 4);

// 每个 lcore 注册
rte_rcu_qsbr_thread_register(q, 0);  // lcore 0
rte_rcu_qsbr_thread_register(q, 1);  // lcore 1
rte_rcu_qsbr_thread_register(q, 2);  // lcore 2
rte_rcu_qsbr_thread_register(q, 3);  // lcore 3

// 每个 lcore 上线（标记为活跃）
rte_rcu_qsbr_thread_online(q, lcore_id);
```

```
┌─────────────────────────────────────────────────────────────────┐
│                DPDK QSBR 读取路径                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  Worker 线程的 main loop:                                      │
│                                                                 │
│  while (!quit) {                                                │
│                                                                 │
│      ╔═══════════════════════════════════════════════════════╗  │

│      ║  rte_rcu_qsbr_lock(q, thread_id);                    ║  │

│                                                                 │

│      ║  rte_rcu_qsbr_unlock(q, thread_id);                  ║  │

│      tx_burst(port, burst, nb_tx);                              │
│                                                                 │
│      ╔═══════════════════════════════════════════════════════╗  │
│      ║  Step 3: 报告静默状态                                 ║  │
│      ║  rte_rcu_qsbr_quiescent(q, thread_id);               ║  │
│      ║  // 内部实现:                                         ║  │
│      ║  // var[thread_id].cnt = token;                       ║  │
│      ║  // "我已经不在临界区了，我看到的 token 是这个"      ║  │
│      ╚═══════════════════════════════════════════════════════╝  │
│  }                                                              │
│                                                                 │
│  lock/unlock 开销: 写一个 cache line 对齐的 per-thread 变量    │
│  ≈ 一次 L1 cache 命中（快速路径）或一次 cache line 写回       │

```

### 5.5 写入路径

```
┌─────────────────────────────────────────────────────────────────┐
│                DPDK QSBR 写入路径                                │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  // 通常在控制面线程执行                                       │
│                                                                 │
│  // Step 1: 创建新数据                                        │
│  new = rte_malloc(socket_id, sizeof(*new), 0);                  │
│  new->field = updated_value;                                    │
│                                                                 │
│  // Step 2: 原子替换指针                                      │
│  old = shared_data;                                             │
│  rte_wmb();                    // 写屏障：保证 new 内容可见    │
│  shared_data = new;            // 新读者看到 new               │
│                                                                 │
│  // Step 3: 启动宽限期，等待所有旧读者退出                    │
│                                                                 │
│  // 方式 A: 阻塞等待（简单但可能卡住）                        │
│  rte_rcu_qsbr_synchronize(q, thread_id, token);                │
│  │                                                              │
│  │  synchronize 内部:                                          │
│  │  ┌────────────────────────────────────────────────────┐      │
│  │  │  token = __atomic_add_fetch(&q->token, 1, relaxed) │      │
│  │  │  // token: 3 → 4                                   │      │
│  │  │                                                     │      │
│  │  │  for (i = 0; i < max_threads; i++) {                │      │
│  │  │      // 等待每个线程的 cnt 追上 token               │      │
│  │  │      while (var[i].cnt < token) {                   │      │
│  │  │          rte_pause();  // CPU hint: 低功耗自旋     │      │
│  │  │      }                                              │      │
│  │  │  }                                                  │      │
│  │  │  // 所有线程 cnt >= token → GP 结束               │      │
│  │  └────────────────────────────────────────────────────┘      │
│  │                                                              │
│  ▼                                                              │
│                                                                 │
│  // 方式 B: 非阻塞轮询（推荐，不阻塞写者线程）                │
│  token = rte_rcu_qsbr_start(q);                                │
│  // ... 做其他工作 ...                                         │
│  if (rte_rcu_qsbr_check(q, token, false)) {                    │
│      // false = 非阻塞，立即返回                               │
│      // GP 结束了，可以安全释放                                │
│      rte_free(old);                                             │
│  }                                                              │
│  // 下次 loop 再 check                                         │
│                                                                 │
│  // Step 4: 安全释放旧数据                                    │
│  rte_free(old);                                                 │
└─────────────────────────────────────────────────────────────────┘
```

```
┌─────────────────────────────────────────────────────────────────────────┐
│                DPDK QSBR RCU 完整时序                                   │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  === 第一轮 Grace Period ===                                            │
│                                                                         │
│  Time:    t0        t1        t2        t3        t4        t5         │
│           │         │         │         │         │         │           │

│  Thread 2: ────[lock][read old]──────────────[unlock][quiescent=1]─    │
│  Thread 3: [lock][read old][unlock]──[quiescent cnt=1]────────────     │
│                    │                                    │               │
│  Writer: ──[替换指针]──[start: token=1]────────────[check OK][free]──  │
│            t0        t0+1      │                     t4      t5       │
│                               │                                        │
│                    等待 var[0..3].cnt >= 1                              │
│                                                                         │
│  === 第二轮 Grace Period ===                                            │
│                                                                         │
│  Time:    t6        t7        t8        t9        t10       t11        │
│           │         │         │         │         │         │           │
│  Thread 0: [lock][read new][unlock]──[quiescent cnt=2]────────────     │
│  Thread 1: [lock][read new][unlock]──[quiescent cnt=2]────────────     │
│  Thread 2: ────[lock][read new]──────────────[unlock][quiescent=2]─    │
│  Thread 3: [lock][read new][unlock]──[quiescent cnt=2]────────────     │
│                    │                                    │               │

│                                                                         │
│  每次 synchronize/check 的含义:                                        │
│  1. token++ (递增全局版本号)                                           │
│  2. 等所有线程的 var[i].cnt >= token                                   │
│  3. cnt >= token 意味着该线程至少经过了一次 quiescent                  │
│  4. 即该线程已经 unlock → 不再持有旧指针 → 可以安全释放               │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

### 5.7 DPDK 中的典型使用场景

**场景：哈希表的 RCU 保护**

```c
// DPDK 哈希表配合 RCU 的典型用法
struct rte_hash *hash;
struct rte_rcu_qsbr *q;

// 注册 RCU 回调到哈希表
rte_hash_rcu_qsbr_add(hash, q);

// 删除哈希条目时:
// 1. 从哈希表中移除 key
// 2. 等待宽限期
// 3. 自动释放旧内存
rte_hash_del_key(hash, &key);
// RCU 机制保证：正在使用该条目的 worker 都退出临界区后，才回收内存
```

**场景：路由表的 RCU 保护**

```c
// 控制面更新路由
void update_route(uint32_t ip, struct route_entry *new_route)
{
    struct route_entry *old_route;

    old_route = rte_hash_lookup_data(route_hash, &ip, NULL);

    // 原子替换
    rte_hash_update_data(route_hash, &ip, new_route, (void **)&old_route);

    // 等宽限期后释放旧路由
    rte_rcu_qsbr_synchronize(q, rte_lcore_id(), token);
    rte_free(old_route);
}
```

## 6. Linux vs DPDK RCU 全面对比

### 6.1 架构对比

```
┌─────────────────────────────────────────────────────────────────────────┐
│             架构对比：Linux Tree RCU vs DPDK QSBR RCU                   │
```

### 6.2 详细特性对比

| 维度             | Linux Tree RCU                                          | DPDK QSBR RCU                                   |
| ---------------- | ------------------------------------------------------- | ----------------------------------------------- |
| **静默状态检测** | 自动（调度器/时钟中断检测上下文切换、idle、用户态切换） | 手动（线程主动调用 `rte_rcu_qsbr_quiescent()`） |
| **读者开销**     | `preempt_disable/enable` 或 per-task 嵌套计数           | 写一个 per-thread `locked` 标志                 |
| **写者等待**     | `call_rcu()` 异步回调 或 `synchronize_rcu()` 阻塞       | `synchronize()` 阻塞 或 `check()` 非阻塞轮询    |
| **GP 检测粒度**  | 全系统所有 CPU                                          | 仅注册的线程                                    |
| **GP 检测架构**  | Tree RCU 分层（`rcu_node` 树，O(log N)）                | 直接遍历 per-thread 计数器（O(N)）              |
| **回调执行**     | 内核软中断 `RCU_SOFTIRQ` 或 NOCB kthread                | 写者线程自己执行或在 `check()` 后执行           |
| **抢占支持**     | 支持（Preemptible RCU）                                 | 不需要（无抢占环境）                            |
| **适用场景**     | 通用内核代码（文件系统、网络协议栈、驱动）              | DPDK 数据面（固定核绑定的 poll-mode 线程）      |
| **代码规模**     | ~10000+ 行                                              | ~500 行                                         |
| **CPU 热插拔**   | 支持                                                    | 不支持                                          |
| **内存屏障**     | `rcu_dereference` 包含依赖屏障                          | 读者无需屏障（同核绑定）                        |

### 6.3 根本差异

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         根本差异                                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                         │
│  Linux:  靠调度器自动检测静默状态                                       │
│  DPDK:   靠线程主动上报静默状态                                         │
│                                                                         │
│  ┌─────────────────────────────────────────────────────────────┐        │
│  │                    为什么不同？                               │        │
│  ├─────────────────────────────────────────────────────────────┤        │
│  │                                                             │        │
│  │  Linux 环境:                                                │        │
│  │  - 有 OS 调度器，线程会被抢占                              │        │
│  │  - 有上下文切换，CPU 会进入 idle                           │        │
│  │  - 有用户态/内核态切换                                     │        │
│  │  → 这些事件天然标记"静默状态"                             │        │
│  │  → 内核可以自动检测                                       │        │
│  │                                                             │        │
│  │  DPDK 环境:                                                │        │
│  │  - 没有 OS 调度器介入（轮询模式）                         │        │
│  │  - 没有上下文切换（线程独占 CPU）                         │        │
│  │  - 没有用户态/内核态切换（纯用户态）                     │        │
│  │  → 不存在"天然的"静默状态事件                            │        │
│  │  → 必须由线程主动报告                                     │        │
│  │                                                             │        │
│  └─────────────────────────────────────────────────────────────┘        │
│                                                                         │
│  这个差异带来了一系列连锁效应:                                         │
│                                                                         │
│  1. 读者开销不同                                                       │
│     Linux 需要禁用抢占/维护嵌套计数                                    │
│     DPDK 只需写一个 per-thread 标志                                    │
│                                                                         │
│  2. GP 检测架构不同                                                    │
│     Linux 需要 Tree RCU 分层（因为 CPU 数多且争用严重）               │
│     DPDK 直接遍历数组即可（线程少，无锁争用）                         │
│                                                                         │
│  3. 回调执行方式不同                                                   │
│     Linux 用内核软中断（因为写者可能已经不在运行）                    │
│     DPDK 由写者直接释放（因为写者通常还在运行）                       │
│                                                                         │
└─────────────────────────────────────────────────────────────────────────┘
```

## 8. 总结

### 8.1 核心要点

1. **RCU 的本质**：读端零开销的乐观并发机制。写者创建副本，原子替换指针，等待所有旧读者退出后回收旧数据

2. **抢占机制是 RCU 设计的分水岭**：不可抢占内核中 `rcu_read_lock` 等价于 `preempt_disable`，读者不会被中途打断，"上下文切换 = QS" 的假设成立。可抢占内核中读者可能被抢占，必须用 nesting 计数追踪，QS 检测逻辑完全不同

3. **Grace Period 是关键**：宽限期保证"替换指针之前的读者都已完成"。如何检测宽限期是 Linux 和 DPDK 的根本差异

4. **Linux Tree RCU**：利用 OS 调度器自动检测静默状态（上下文切换、idle、用户态切换），通过分层 `rcu_node` 树支持数百 CPU。可抢占内核还依赖 boost 机制防止低优先级读者饿死 GP

5. **DPDK QSBR RCU**：因为无 OS 调度器介入（CPU 绑定 + 轮询模式 + isolcpus），线程不可能被抢占，但也没有"天然的"静默状态事件，必须主动调用 `quiescent()` 上报

6. **最本质的区别**：Linux 靠调度器自动检测，DPDK 靠线程主动上报。这个差异来自运行环境的根本不同——有/无抢占、有/无调度器

### 8.2 选择建议

| 场景                 | 推荐                                        |
| -------------------- | ------------------------------------------- |
| Linux 内核开发       | Tree RCU（`rcu_read_lock` / `call_rcu`）    |
| DPDK 数据面          | QSBR RCU（`rte_rcu_qsbr` + defer queue）    |
| 用户态通用程序       | `liburcu`（userspace RCU 库，提供多种变体） |
| 读多写少、延迟敏感   | RCU 通常是好选择                            |
| 写多读少、写延迟敏感 | RCU 不合适，考虑读写锁或 SeqLock            |
