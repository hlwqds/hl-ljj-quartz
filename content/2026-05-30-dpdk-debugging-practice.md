## 1. 实战概览

### 1.1 5 类典型 bug

```
buggy_l2fwd.c 中故意植入:

  Bug 1: mbuf 完整性损坏 (use-after-free)
  Bug 2: 数组越界 (OOB read/write)
  Bug 3: 整数溢出 (回绕到 0)
  Bug 4: 自定义 signal handler 吃掉 core dump
  Bug 5: 高频路径 RTE_LOG 拖垮性能

每个 bug 对应一种调试工具, 演示不同诊断手段.
```

### 1.2 文件清单

```
practice/dpdk_debugging/
├── buggy_l2fwd.c         # 故意带 5 类 bug 的代码
├── fixed_l2fwd.c         # 修复版 (对照)
├── buggy_l2fwd.gdb       # GDB 调试脚本 (含 DPDK 漂亮打印命令)
├── build.sh              # 编译脚本
```

## 2. 编译 buggy / fixed 版本

### 2.1 编译

```bash
cd practice/dpdk_debugging

export RTE_SDK=/opt/dpdk
./build.sh

# 产出:
ls -lh build/
# buggy_l2fwd   80K
# fixed_l2fwd   85K
```

build.sh 内部用 gcc 显式 -I 指定 DPDK 头文件路径. 也可以用 DPDK 自带的 meson:

```bash
# 替代方式: 用 DPDK 的 example skeleton
cp /opt/dpdk/examples/helloworld/Makefile .
sed -i 's/SRCS-y := helloworld.c/SRCS-y := buggy_l2fwd.c/' Makefile
make
```

### 2.2 ASan 编译 (Bug 1 检测利器)

```bash
# ASan 编译 buggy 版本, 可以更早发现 use-after-free
gcc -O0 -g -fsanitize=address \
    -I$RTE_SDK/lib/eal/include ... \
    buggy_l2fwd.c \
    -fsanitize=address \
    -o build/buggy_l2fwd_asan

# 关闭 hugepage (ASan 不能用 hugepage)
./build/buggy_l2fwd_asan --no-huge
```

### 2.3 mbuf debug 编译 (Bug 1/2 检测利器)

```bash
# 启用 mbuf debug, sanity check 才会生效
gcc -O0 -g -DRTE_LIBRTE_MBUF_DEBUG \
    -I$RTE_SDK/lib/eal/include ... \
    buggy_l2fwd.c \
    -o build/buggy_l2fwd_mbufdebug
```

### 2.4 三个版本的对比

```
版本                 编译选项                          检测能力
────────────────────────────────────────────────────────────
buggy_l2fwd         默认 -O0                          跑一会才 crash
buggy_l2fwd_asan    -fsanitize=address                立即报 UAF
buggy_l2fwd_mbufdebug -DRTE_LIBRTE_MBUF_DEBUG         立即报 mbuf 损坏
fixed_l2fwd         默认 -O2                          正常工作
```

## 3. Bug 1 复现: use-after-free

### 3.1 Bug 现场

`buggy_l2fwd.c` 的循环里:

```c
for (int i = 0; i < nb_rx; i++) {
    if (i == nb_rx - 1) {
        rte_pktmbuf_free(bufs[i]);      // 释放最后一个 mbuf
        RTE_LOG(INFO, APP_LOG,           // 然后还在用 bufs[i]
            "Free'd mbuf data_len=%u\n",
            bufs[i]->data_len);          // ← UAF 读
    }
    port_pkt_count[port]++;
}
```

释放后再读 mbuf 字段, 是经典的 use-after-free.

### 3.2 诊断方法 A: 默认编译, 跑一会儿 crash

```bash
ulimit -c unlimited
echo '/tmp/core-%e-%p-%t' | sudo tee /proc/sys/kernel/core_pattern

# 但 buggy_l2fwd 装了 no_op handler, 会**吃掉** core dump!
./build/buggy_l2fwd

# 收到 SIGSEGV 时 no_op handler 调 _exit(1)
# core dump 不会生成
ls /tmp/core-* 2>/dev/null
# 啥也没有 ← 这就是 Bug 4
```

**先解 Bug 4** (删 no_op handler), 再跑就能拿到 core:

```c
/* 删掉 buggy_l2fwd.c 里这些: */
// signal(SIGSEGV, no_op_handler);  ← 删
// signal(SIGABRT, no_op_handler);  ← 删
// signal(SIGBUS,  no_op_handler);  ← 删
```

### 3.3 诊断方法 B: ASan 直接定位

ASan 在 free 时会把内存放到 quarantine 列表, 后续访问立即被拦:

```bash
# 跑 ASan 版本
./build/buggy_l2fwd_asan --no-huge

# 输出:
# ==12345==ERROR: AddressSanitizer: heap-use-after-free
# READ of size 4 at 0x7f1234560000 thread T0
#     #0 0x4abcd in lcore_main /path/buggy_l2fwd.c:108
#     #1 0x4efgh in eal_thread_loop /opt/dpdk/lib/eal/...
#
# 0x7f1234560000 is located 16 bytes inside of 128-byte region
# freed by thread T0 here:
#     #0 0x1234 in __asan_report_free
#     #1 0x4abce in lcore_main /path/buggy_l2fwd.c:107
#
# SUMMARY: AddressSanitizer: heap-use-after-free /path/buggy_l2fwd.c:108
```

**关键信息**:

- 第 108 行是 `bufs[i]->data_len` 读取
- 第 107 行是 `rte_pktmbuf_free()` 释放
- ASan 直接告诉你 free 在哪、use 在哪

### 3.4 诊断方法 C: GDB post-mortem

```bash
# 1. 拿到 core (用解了 Bug 4 的版本)
./build/buggy_l2fwd  # 跑崩, 产生 /tmp/core-buggy_l2fwd-PID-TIMESTAMP

# 2. 加载
gdb -x buggy_l2fwd.gdb ./build/buggy_l2fwd /tmp/core-buggy_l2fwd-*

# GDB 输出:
# Reading symbols from ./build/buggy_l2fwd...
# Core was generated by `./build/buggy_l2fwd'
# Program terminated with signal SIGSEGV, Segmentation fault.

# 3. 一键诊断
(gdb) crash-triage

# #0  0x00004abcd in lcore_main (buggy_l2fwd.c:108)
# #1  0x00004efgh in eal_thread_loop (...)
# #2  0x00007f...  in start_thread (...)
#
# 关键变量 (frame 0):
# i = 31
# nb_rx = 32
# port = 0
# bufs = {0x7f..., 0x7f..., ..., 0x7f...}  ← 最后一个是 freed

# 4. 验证 mbuf 是否已经 free
(gdb) frame 0
(gdb) print bufs[31]->refcnt
# 应该看到 refcnt=0, 表示已释放, 但还在读 → UAF

# 5. 看 mbuf 详情
(gdb) dpdk-mbuf bufs[31]
# === rte_mbuf 0x7f1234560000 ===
#   buf_addr    = 0x7f123455f000
#   data_off    = 60
#   data_len    = 64         ← ASan 还能看到原值
#   refcnt      = 0          ← 但 refcnt=0 说明已 free
```

### 3.5 修复

`fixed_l2fwd.c` 的修复:

```c
/* 错误 ❌: 在循环里 free 然后继续用 */
for (int i = 0; i < nb_rx; i++) {
    if (i == nb_rx - 1) {
        rte_pktmbuf_free(bufs[i]);
        printf("data_len=%u\n", bufs[i]->data_len);  // UAF
    }
}

/* 正确 ✓: use 全部完成后才 free, 而且只 free 真正失败的 */
const uint16_t nb_tx = rte_eth_tx_burst(port ^ 1, 0, bufs, nb_rx);
if (unlikely(nb_tx < nb_rx)) {
    rte_pktmbuf_free_bulk(&bufs[nb_tx], nb_rx - nb_tx);
    // 注意: nb_tx 之前的 bufs[0..nb_tx-1] 已经成功发出去,
    //       后续不该再访问
}
```

## 4. Bug 2 复现: 数组越界

### 4.1 Bug 现场

```c
#define MAX_PORTS_BUGGY 4   /* 假设有 4 个端口 */

/* 循环用 RTE_MAX_ETHPORTS (64) 但数组只有 4 元素 */
for (port = 0; port < RTE_MAX_ETHPORTS && port < MAX_PORTS_BUGGY; port++) {
    static uint64_t port_pkt_count[4];   /* ← 只有 4 元素 */
    port_pkt_count[port]++;              /* port >= 4 时越界 */
}
```

当系统有 5+ 端口时 (但循环用 `port < MAX_PORTS_BUGGY` 卡死, 实际不会触发), **更隐蔽的越界**是:

```c
/* 类似的, 用 4 元素数组存所有端口的统计 */
static uint64_t port_pkt_count[4];
port_pkt_count[port]++;  /* 即使 port < 4, 但实际只有 4 个端口在用 */
```

这类问题需要 fuzzer / valgrind 才能稳定发现.

### 4.2 诊断方法: ASan

```bash
./build/buggy_l2fwd_asan --no-huge
# 启动时遍历 5 个端口, 立即报:
# ==12345==ERROR: AddressSanitizer: stack-buffer-overflow
# WRITE of size 8 at 0x7ffc... thread T0
#     #0 0x4abcd in lcore_main /path/buggy_l2fwd.c:115
# 0x7ffc... is located in stack of thread T0 at offset 96
#   'port_pkt_count' (declared at /path/buggy_l2fwd.c:114) < 32 bytes>
# SUMMARY: stack-buffer-overflow
```

### 4.3 诊断方法: GDB watchpoint

```c
/* GDB 脚本里加: 监控 port_pkt_count 数组 */

(gdb) break lcore_main
(gdb) run
(gdb) watch -l port_pkt_count[4]   /* 监视越界位置 */
# Hardware watchpoint 4: -location port_pkt_count[4]
# Continuing.
# Hardware watchpoint 4: -location port_pkt_count[4]
#
# Old value = <uninitialized>
# New value = 1
#
# 0x... in lcore_main (buggy_l2fwd.c:115)  ← 命中
# 115         port_pkt_count[port]++;
```

### 4.4 修复

```c
/* 错误 ❌: 写死小数组 */
static uint64_t port_pkt_count[4];

/* 正确 ✓: 用 RTE_MAX_ETHPORTS 大小, 或干脆用 per-lcore 计数 */
/* 方案 1: 数组大小对齐到 RTE_MAX_ETHPORTS */
static uint64_t port_pkt_count[RTE_MAX_ETHPORTS];

/* 方案 2: 改用 per-lcore 统计, 不需要按端口分 */
struct lcore_stats {
    uint64_t rx;
    uint64_t tx;
} __rte_cache_aligned;
static struct lcore_stats g_stats[RTE_MAX_LCORE];
```

## 5. Bug 3 复现: 整数溢出

### 5.1 Bug 现场

```c
static inline uint16_t
bad_next_index(uint16_t cur, uint16_t burst)
{
    return cur + burst;  /* uint16_t 加法, 65536 时回绕到 0 */
}
```

当 `cur = 65000, burst = 1000` 时, 结果是 `65000 + 1000 = 66000`, 但因为是 `uint16_t`, 实际存的是 `66000 - 65536 = 464`. **索引跳回前面**, 导致包错乱.

### 5.2 诊断方法: GDB 跑一段观察

```bash
# 1. 启用 trace point (trace point 默认 no-op, 不影响性能)
./build/buggy_l2fwd --log-level=app:debug

# 输出:
# [app] tx_idx=32
# [app] tx_idx=64
# [app] tx_idx=96
# ...
# [app] tx_idx=65520
# [app] tx_idx=464    ← 看到回绕!
# [app] tx_idx=496
# ...

# 2. GDB 加断点
(gdb) break buggy_l2fwd.c:99
(gdb) condition 1 (new_idx < g_tx_idx)
(gdb) continue

# 命中时:
# Breakpoint 1, bad_next_index (cur=65000, burst=464) at buggy_l2fwd.c:99
# 99          return cur + burst;
# (gdb) print (uint32_t)cur + burst
# $1 = 65464   ← 应该 65000 + 464 = 65464, 没溢出
# (gdb) continue
# Breakpoint 1, bad_next_index (cur=65520, burst=1000) at buggy_l2fwd.c:99
# 99          return cur + burst;
# (gdb) print (uint32_t)cur + burst
# $2 = 66520
# (gdb) next
# 100      }
# (gdb) print new_idx
# $3 = 984   ← 66520 mod 65536 = 984, 看到了!
```

### 5.3 修复

```c
/* 错误 ❌ */
static inline uint16_t
bad_next_index(uint16_t cur, uint16_t burst)
{
    return cur + burst;  /* 溢出回绕 */
}

/* 正确 ✓ */
static inline uint16_t
safe_next_index(uint16_t cur, uint16_t burst, uint16_t ring_size)
{
    uint32_t sum = (uint32_t)cur + burst;  /* 提升到 32 位 */
    return (uint16_t)(sum % ring_size);    /* 显式 mod */
}
```

## 6. Bug 4 复现: signal handler 吃掉 core

### 6.1 Bug 现场

```c
static void
no_op_handler(int sig)
{
    fprintf(stderr, "Got signal %d, exiting\n", sig);
    _exit(1);  /* 直接 _exit, 不 dump core */
}

signal(SIGSEGV, no_op_handler);  /* ← 装上后, SIGSEGV 不产生 core */
signal(SIGABRT, no_op_handler);
signal(SIGBUS,  no_op_handler);
```

**结果**: 即使 `ulimit -c unlimited` 配了, 也拿不到 core dump.

### 6.2 验证

```bash
# 1. 配置允许 core
ulimit -c unlimited
echo '/tmp/core-%e-%p-%t' | sudo tee /proc/sys/kernel/core_pattern

# 2. 写一个最小崩溃程序
cat > /tmp/sig.c <<EOF
#include <signal.h>
#include <stdio.h>
void h(int s) { fprintf(stderr, "sig=%d\n", s); _exit(1); }
int main() { signal(SIGSEGV, h); *(volatile int*)0 = 0; return 0; }
EOF
gcc -O0 -g /tmp/sig.c -o /tmp/sig
/tmp/sig
ls /tmp/core-* 2>/dev/null
# 没有 ← 装 handler 后 core 不出来

# 3. 删掉 handler 再跑
sed -i 's|signal.*|/* & */|' /tmp/sig.c
gcc -O0 -g /tmp/sig.c -o /tmp/sig
/tmp/sig
ls /tmp/core-*
# /tmp/core-sig-XXX-XXX  ← core 出来了
```

### 6.3 修复

```c
/* 错误 ❌: 自定义 handler _exit 吃掉 core */
/* signal(SIGSEGV, no_op_handler); */

/* 正确 ✓: 完全删掉, 走默认行为 */
/* 不装 handler, abort() 自然产生 core */

/* 或者: handler 里重新抛信号, 让系统处理 */
static void
reraise_handler(int sig)
{
    signal(sig, SIG_DFL);  /* 恢复默认 */
    raise(sig);            /* 重新触发 */
}
```

## 7. Bug 5 复现: 高频路径 RTE_LOG

### 7.1 性能对比

```bash
# 1. 跑 buggy 版本, 看 pps
./build/buggy_l2fwd --no-pci  # 用 pcap PMD, 自环流量
# pps: 0.05 Mpps   ← 因为每包都 RTE_LOG(INFO)

# 2. 跑 fixed 版本
./build/fixed_l2fwd --no-pci
# pps: 14.8 Mpps   ← 正常
```

性能差 300x, 原因在 `buggy_l2fwd.c`:

```c
/* 错误 ❌: 每包都 RTE_LOG(INFO), 触发格式化+IO */
while (1) {
    for (port = 0; ...) {
        RTE_LOG(INFO, APP_LOG, "Polling port %u ...\n", port, ...);  /* 慢 */
        const uint16_t nb_rx = rte_eth_rx_burst(...);
        ...
    }
}
```

### 7.2 perf 抓热点

```bash
# 1. perf top
sudo perf top -p $(pidof buggy_l2fwd)

# 输出 (片段):
#  12.34%  libc-2.31.so      [.] __vfprintf_internal
#   8.91%  buggy_l2fwd       [.] lcore_main
#   7.12%  libc-2.31.so      [.] _IO_file_xsputn
#   6.45%  libc-2.31.so      [.] __GI___libc_write
#   5.23%  libdpdk.so        [.] rte_log
#
# 关键: __vfprintf_internal 占 12% ← RTE_LOG 调 fprintf

# 2. 录制 + report
sudo perf record -g -p $(pidof buggy_l2fwd) -- sleep 10
sudo perf report --stdio

# Samples: 100K
#   35%  lcore_main
#    └─ 30%  RTE_LOG(INFO, ...)
#         └─ 25%  rte_log
#              └─ 20%  __vfprintf_internal
#                   └─ 18%  __GI___libc_write
#                          └─ 17%  syscall
```

### 7.3 修复: 用 rte_trace 替代

```c
/* fixed_l2fwd.c 的修复 */

/* 1. 头文件定义 trace point */
RTE_TRACE_POINT(app_trace_rx,
    RTE_TRACE_POINT_ARGS(uint16_t port, uint16_t nb_rx));

/* 2. 数据路径埋点 (默认 no-op, 零开销) */
rte_trace_point(app_trace_rx, port, nb_rx);

/* 3. 启动时注册 */
RTE_TRACE_POINT_REGISTER(app_trace_rx);

/* 4. 用 --trace 参数启用 */
./build/fixed_l2fwd --trace=app.* --trace-dir=/tmp/traces
# 关闭 trace 时性能零损耗
./build/fixed_l2fwd
# pps: 14.8 Mpps (和 buggy 一样), 因为 trace 默认不开
```

`rte_trace` vs `RTE_LOG` 性能对比:

```
                     RTE_LOG(INFO)    RTE_LOG(DEBUG)   rte_trace (off)   rte_trace (on)
数据面开销/包         500 ns           50 ns            < 5 ns            20 ns
```

## 8. 综合诊断流程

### 8.1 拿到一个 core dump 后

```bash
# 1. 加载
gdb -x buggy_l2fwd.gdb ./build/buggy_l2fwd /tmp/core-buggy_l2fwd-*

# 2. 一键诊断
(gdb) crash-triage
# bt full + locals + registers

# 3. 看 mbuf 异常
(gdb) mbuf-debug bufs[31]
# fields + data hex dump

# 4. 看 mempool 状态
(gdb) dpdk-mempool g_mbuf_pool
# size=8191, cache_size=250, populated=8191

# 5. 看所有 lcore 在干嘛 (core 可能是 1 个 lcore 崩的, 但要查其他 lcore 是否也有问题)
(gdb) dpdk-all-stacks
```

### 8.2 拿到 ASan 报告后

```
报告:
==12345==ERROR: AddressSanitizer: heap-use-after-free
READ of size 4 at 0x7f1234560000 thread T0
    #0 0x4abcd in lcore_main /path/buggy_l2fwd.c:108
    #1 0x4efgh in eal_thread_loop /opt/dpdk/lib/eal/...
0x7f1234560000 is located 16 bytes inside of 128-byte region
freed by thread T0 here:
    #0 0x1234 in __asan_report_free
    #1 0x4abce in lcore_main /path/buggy_l2fwd.c:107

诊断步骤:
1. 看 READ 行: lcore_main:108  ← use 在 108 行
2. 看 freed 行: lcore_main:107  ← free 在 107 行
3. 翻代码, 108 行在 free 之后 → use-after-free
4. 修复: 调整 free 时机, 见 fixed_l2fwd.c

附加信息:
- 0x7f1234560000 附近内存: ASan 报 "is located 16 bytes inside of 128-byte region"
  128 字节 = rte_mbuf 大小, 16 字节 = data_off
  → 确认是 mbuf 释放后被读
```

### 8.3 性能塌方后

```
步骤 1: perf top 看热点
  → __vfprintf_internal 占 12% ← RTE_LOG 太多

步骤 2: 检查代码, 找出高频 RTE_LOG
  → 数据面 polling 循环里

步骤 3: 改用 rte_trace, 或者:
  - 把 RTE_LOG(INFO) 改成 RTE_LOG(DEBUG) (默认不输出)
  - 加条件: if (slow_path_condition) RTE_LOG(...)

步骤 4: 重新 perf 验证
  → __vfprintf_internal < 0.1% ← 修好
```

## 9. 现场诊断脚本

`diagnose.sh` 是部署后跑现场诊断的脚本:

```bash
#!/bin/bash
# diagnose.sh — DPDK 应用现场诊断 (Bug 修复版, 安全用)
#
# 用法:
#   ./diagnose.sh <dpdk_app_pid>
#
# 检查项:
#   - core dump 配置
#   - signal handler 是否被覆盖
#   - RTE_LOG 频率
#   - mbuf pool 状态

set -e
PID=${1:?"Usage: $0 <pid>"}

echo "=== DPDK Live Diagnosis (PID=$PID) ==="

# 1. core dump 配置
echo "--- core dump ---"
echo "ulimit -c: $(ulimit -c)"
echo "core pattern: $(cat /proc/sys/kernel/core_pattern)"

# 2. 检查是否装了 signal handler
echo ""
echo "--- signal handlers in /proc/$PID/status ---"
grep -E "Sig(Ign|Cgt)" /proc/$PID/status || echo "(read /proc/PID/status failed)"

# 3. CPU 占用
echo ""
echo "--- CPU usage ---"
top -b -n 1 -p $PID -H | head -20

# 4. mmap 区域 (看 hugepage 分配)
echo ""
echo "--- memory maps (hugepage) ---"
grep huge /proc/$PID/smaps 2>/dev/null | head -20 || echo "(no hugepage or no permission)"

# 5. 最近一次 rte_log
echo ""
echo "--- recent log (read /proc/$PID/fd/2 if accessible) ---"
timeout 1 tail -f /proc/$PID/fd/2 2>/dev/null || echo "(log not redirected to stderr, check log file)"

# 6. perf 抓 5 秒
echo ""
echo "--- perf top 5s ---"
if command -v perf >/dev/null; then
    timeout 5 perf top -p $PID -n -b 2>&1 | head -30 || echo "(perf failed, need root or perf_event_paranoid)"
else
    echo "(perf not installed)"
fi
```

## 10. 5 个 bug 修复对照表

| Bug               | 触发                     | 工具                      | 修复                                  |
| ----------------- | ------------------------ | ------------------------- | ------------------------------------- |
| **1. UAF**        | mbuf free 后继续读       | ASan 立即报 / core 后 GDB | 调整 free 时机, 用 free_bulk 一次完成 |
| **2. 越界**       | 访问超过数组大小的 index | ASan / GDB watchpoint     | 数组大小用 RTE_MAX_ETHPORTS           |
| **3. 溢出**       | uint16_t 加法回绕        | GDB 条件断点 / 单元测试   | 提升到 uint32_t 后 mod                |
| **4. 吞 core**    | 自定义 handler 调 \_exit | 测试程序验证              | 删掉 handler / 重新抛信号             |
| **5. RTE_LOG 慢** | 数据面 INFO 级日志       | perf top 看 \_\_vfprintf  | 改 rte_trace / 降到 DEBUG             |

## 11. 一句话总结

DPDK 调试的实战要点:

1. **core dump 永远开着**, 别装多余的 signal handler
2. **ASan 编译一次**, 能挡掉 50% 的内存 bug (UAF/OOB)
3. **mbuf debug 编译一次**, 抓到 80% 的 mbuf 损坏
4. **rte_trace 替代 RTE_LOG(INFO)**, 性能不掉还能事后分析
5. **GDB 脚本沉淀**, `dpdk-mbuf` 这种命令 5 秒看一个 mbuf
