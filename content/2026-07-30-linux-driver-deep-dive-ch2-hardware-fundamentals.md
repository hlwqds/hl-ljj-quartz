# Linux 设备驱动开发详解（二）：驱动设计的硬件基础

第一章从软件视角看了驱动——它是硬件抽象层，在裸机和有 OS 时分别长什么样。这一章换到硬件视角：驱动要驱动的"设备"到底是什么？CPU 怎么找到它们？数据怎么在 CPU 和设备之间流动？

理解这些硬件基础，才能理解驱动为什么用 `ioremap` 映射寄存器、为什么要处理中断、为什么有 DMA。每个驱动机制都对应一个硬件事实。

## 2.1 处理器

驱动跑在处理器上，处理器是所有操作的中心。理解处理器的执行模型、特权级、以及它如何与外设交互，是理解驱动行为的基础。

### 2.1.1 通用处理器

#### 1. 什么是通用处理器

通用处理器（General-Purpose Processor，GPP）是设计来执行**任意**程序的——它不知道自己要跑什么，靠读取指令序列来决定行为。你的 PC 的 CPU、手机的 SoC、我们实验用的 vexpress-a9 的 Cortex-A9，都是通用处理器。

"通用"的含义：

- CPU 本身只认识**指令集**（ISA），不认识任何具体设备。
- CPU 的核心能力只有两种：**执行指令** 和 **读写地址**。
- 一切硬件操作——点 LED、发网络包、写磁盘——最终都翻译成对特定地址的读写。

从驱动的角度看，CPU 是一个"只会读写地址和执行指令"的执行器。驱动代码告诉它"往这个地址写这个值"，它就照做；硬件那一端发生什么，由外设自己的逻辑决定。

#### 2. 冯·诺伊曼与哈佛结构

处理器内部怎么组织指令和数据，是计算机体系结构的经典分类：

| 架构 | 指令和数据 | 特点 | 典型处理器 |
| --- | --- | --- | --- |
| **冯·诺伊曼** | 共享同一存储和总线 | 简单，但取指和访存不能同时（总线竞争） | 早期 x86、多数通用 CPU 的逻辑模型 |
| **哈佛** | 分开存储和总线 | 取指和访存走独立通路，减少结构冲突；硬件复杂 | 多数 DSP、部分 MCU（如 AVR） |
| **改进型哈佛** | 统一地址空间但缓存/数据路径分离 | 编程模型统一；I-Cache/D-Cache 独立减少取指与访存的结构冲突，但缓存未命中时仍争用下级互连 | 现代 Cortex-A（含 vexpress-a9 的 Cortex-A9） |

这组分类主要作背景知识——驱动开发者不会因为知道 CPU 是哈佛还是冯·诺伊曼就写出不同的代码。真正影响驱动实现的是架构的**可观察后果**，以及 Linux API 如何封装它们：

| 架构差异（可观察后果） | 对驱动的影响 | Linux 怎么封装 |
| --- | --- | --- |
| 统一编址 vs 独立 I/O 空间 | ARM 所有外设是 MMIO（没有 Port I/O）；x86 两者都有 | `ioremap` + `ioread32`/`iowrite32` |
| 字节序、访问宽度、未对齐访问 | 写寄存器时数据布局依赖架构和设备 | 按设备寄存器字节序选 `readl`/`writel`（小端）或 `ioread32be`/`iowrite32be`（大端）；accessor 不自动统一字节序 |
| MMIO 访问顺序 | 乱序执行、写缓冲可能导致操作重排 | accessor 提供该架构定义的基础 MMIO 顺序保证（`*_relaxed` 更弱）；跨 DMA/设备/普通内存的复杂场景仍需按需加屏障 `wmb`/`rmb`/`mb` 或写后读回 |
| 缓存一致性 | DMA 涉及的内存可能需要显式同步 | `dma_sync_*`、`dma_map_single` 等 DMA API |
| 地址宽度 | 32 位 vs 64 位影响可寻址范围和 DMA 掩码 | `dma_mask`、`dma_set_mask` |
| 中断模型 | 中断控制器、中断号、中断触发方式依架构而异 | `request_irq`、设备树中断描述 |

换句话说：驱动开发者不关心 CPU 内部是哈佛还是冯·诺伊曼，但**必须关心上表中的可观察差异**，并通过对应的 Linux API 正确处理。

> [!note] x86 的特殊之处
> x86 支持 **Port I/O**（`in`/`out` 指令，独立于内存地址空间的 64KB I/O 空间）和 MMIO 两种方式。ARM 只有 MMIO，没有 Port I/O。本系列基于 ARM，所有外设访问都是内存映射的。

#### 3. 指令集与执行模型


通用处理器按固定周期工作：

```text
取指（Fetch） → 译码（Decode） → 执行（Execute） → 访存（Memory） → 写回（Write Back）
     ↑                                                              │
     └────────────── 下一条指令 ←──────────────────────────────────────┘
```

驱动代码（C 编译成的机器指令）就跑在这个流水线上。但驱动用到的几类操作值得注意：

| 操作 | 机器指令 | 驱动里对应什么 |
| --- | --- | --- |
| 读写内存 | `LDR` / `STR`（ARM） | 访问 RAM 里的数据结构 |
| 读写 I/O | `LDR` / `STR` 到 MMIO 地址 | `ioread32` / `iowrite32`（见 1.6.2） |
| 算术逻辑 | `ADD` / `CMP` / `AND` | 驱动里的判断、计算 |
| 跳转 | `B` / `BL` | 函数调用、循环 |
| 特殊寄存器 | `MRS` / `MSR` | 访问 CPU 状态（中断屏蔽等，后续章节） |

注意"读写内存"和"读写 I/O"在 ARM 上是**同一条指令**（`LDR`/`STR`）——区别只在地址落在哪个区域。这就是**统一编址**（memory-mapped I/O），vexpress-a9 和大多数现代 ARM SoC 都用这种方式。

#### 4. 特权级

第一章讲过有 OS 时"内核态/用户态"的隔离。这对应的硬件事实是：**处理器有多个特权级**，不同级别能执行的指令和能访问的地址不同。

ARM 的特权级模型（以 Cortex-A9 为例）：

| 特权级 | ARM 模式 | 谁运行在这里 | 能做什么 |
| --- | --- | --- | --- |
| 非特权 | User | 用户态应用 | 受限：不能访问 MMIO、不能关中断 |
| 特权 | Supervisor (SVC) | **内核**（含驱动） | 全部：读写 MMIO、配置中断、改页表 |
| 特权 | IRQ | 中断处理 | 处理硬件中断（后续章节） |
| 特权 | Abort | 异常处理 | 处理缺页等 |


> [!note] 关于 ARM 特权级的限定
> 上表描述的是传统 ARMv7 非虚拟化配置。启用了虚拟化扩展（Hyp mode）时，特权级层次更复杂；此外中断和异常入口会短暂使用 IRQ/Abort 等模式。本系列不涉及虚拟化扩展，按 SVC 为内核主体模式来理解即可。
驱动运行在**特权级**。这正是驱动能直接操作硬件寄存器的根本原因——用户态应用不能写 `0x10000008`，因为用户页表不提供该 MMIO 地址的映射（触发权限异常）；内核驱动通过 `ioremap` 或设备子系统取得设备映射后才能访问（见 1.6.2）。裸机没有 MMU（或 MMU 关闭），所有地址直接可见，没有这层隔离。

从硬件角度看，1.6.1 的裸机程序在本实验的启动路径下运行在 SVC 模式（具体复位后进入哪个模式由平台和启动固件决定）。1.6.2 的内核模块也运行在特权级，但它的权限是内核给的，受内核的调度和资源管理约束。

#### 5. 处理器怎么"看到"外设

通用处理器本身不认识任何外设，它只认识地址。外设能被 CPU 操作，是因为外设的寄存器被映射到了处理器的**地址空间**里。

本实验涉及的关键地址（vexpress-a9，非完整地址图）。每个外设的寄存器是**独立映射窗口**，不一定连续：

| 地址 | 对象 | 说明 |
| --- | --- | --- |
| `0x10000008` | SYS_LED | 主板 sysreg 内的 LED 寄存器（1.6.1/1.6.2 用的） |
| `0x10009000` | UART0 | PL011 串口寄存器 |
| `0x4e000000` | SMSC LAN9118 | 网卡寄存器（独立映射窗口，不与 sysreg 连续） |
| `0x60000000`–`0x7fffffff` | RAM | DTB 声明 1GB（`0x60000000` 起 1GiB），本实验 qemu `-m 512M` 截断为 512MB；裸机程序和内核都加载到这里 |

CPU 不知道 `0x10000008` 是 LED——它只知道"写这个地址会触发某种硬件行为"。是**设备树**（或平台代码）告诉内核"`0x10000008` 是 sysreg LED"，内核再告诉驱动。

这就是第一章讲的"设备从哪里来"的硬件层映射：外设的寄存器被映射到地址空间 → 设备树描述映射关系 → 内核解析设备树 → 驱动拿到地址 → 操作寄存器。

#### 6. 通用处理器的局限

通用处理器很强，但它不擅长所有事：

| 场景 | 通用处理器的问题 | 硬件的解法 |
| --- | --- | --- |
| 大批量数据搬运（磁盘/网络） | CPU 逐字节搬运太慢 | **DMA**：让外设自己搬，CPU 只管发命令（后续章节） |
| 实时响应（按键/中断） | CPU 可能在忙别的 | **中断**：外设主动通知 CPU（后续章节） |
| 信号处理（音频/视频编解码） | CPU 逐帧算太慢 | **专用协处理器/DSP** |
| 固定协议处理（加密/网络校验） | CPU 算不划算 | **硬件加速器** |

这些"解法"就是后续硬件主题的内容：DMA、中断、总线。每一样都对应驱动里的特定机制。

理解通用处理器的这些局限，才能理解为什么驱动要处理中断（而不是轮询）、为什么要配置 DMA（而不是 CPU 搬数据）、为什么有总线控制器（而不是 CPU 直接连每个设备）。

### 2.1.2 数字信号处理器

上一节讲到通用处理器不擅长信号处理（音频/视频编解码）。数字信号处理器（Digital Signal Processor，DSP）就是为了补这个短板而诞生的专用处理器。

#### 1. DSP 和通用处理器的区别

| 维度 | 通用处理器（GPP） | 数字信号处理器（DSP） |
| --- | --- | --- |
| 设计目标 | 通用计算——什么都能跑 | 专精信号处理——FFT、滤波、矩阵运算 |
| 核心能力 | 灵活的指令集，复杂控制流 | 单周期乘加（MAC）、零开销循环、SIMD |
| 典型负载 | OS、应用、驱动 | 音频编解码、基带处理、电机控制、图像处理 |
| 架构 | 通常冯·诺伊曼或改进型哈佛 | 通常哈佛（指令和数据独立存储，保证 MAC 吞吐） |
| 可编程性 | 高（C/C++/Rust/...） | 较低（专用工具链，有时只有汇编或厂商 SDK） |

最本质的区别：DSP 的指令集**为信号处理算法量身定制**。一个 1024 点 FFT，通用处理器可能要几千条指令；DSP 靠专用的 MAC 单元和零开销循环，几百周期就完成。

#### 2. DSP 在系统中的位置

现代嵌入式系统里，DSP 通常不孤立存在，而是以几种形态出现：

```text
形态 A：独立 DSP 芯片
  CPU ──(总线)── DSP ──(专用数据通路)── ADC/DAC
  驱动：CPU 上的驱动负责往 DSP 加载固件、配置参数、搬运数据

形态 B：SoC 内集成 DSP 核
  ┌─────── SoC ───────┐
  │ ARM 核（跑 Linux）  │
  │ DSP 核（跑固件）    │ ← 共享内存或邮箱通信
  │ 硬件加速器          │
  └────────────────────┘
  驱动：ARM 核上的驱动通过共享内存/mailbox 与 DSP 核通信

形态 C：DSP 作为协处理器
  CPU ──(专用指令)── DSP 单元
  驱动：通常不需要专门驱动，编译器/OS 自动调度
```

从驱动开发者的角度，最可能遇到的是**形态 B**——SoC 里集成了一颗 DSP 核。比如高通骁龙的 Hexagon DSP、TI OMAP 的 C64x+ DSP。你的 ARM 核跑 Linux，DSP 核跑厂商提供的固件，两者通过共享内存通信。

#### 3. 驱动和 DSP 的关系

大部分情况下，驱动开发者**不写 DSP 的固件**——那是厂商用专用工具链做的事。驱动要关心的是 CPU 和 DSP 之间的**通信接口**：

| 通信方式 | 驱动做什么 | 典型场景 |
| --- | --- | --- |
| 共享内存（shm） | 在 CPU 和 DSP 之间分配共享缓冲区，管理数据帧的入队/出队 | 音频/视频数据流 |
| 邮箱/中断（mailbox） | 发送控制消息（启动/停止/参数配置），接收 DSP 的完成通知 | 控制 DSP 启停 |
| remoteproc / rpmsg | Linux 的远程处理器框架：加载 DSP 固件、建立 virtio 通信通道 | 高通/TI 平台的 DSP 管理 |

Linux 内核有专门处理这类异构多核的子系统：

- **remoteproc**：加载和管理 DSP/MCU 固件的生命周期（启动、停止、崩溃恢复）。
- **rpmsg**：基于 virtio 的核间消息传递，CPU 和 DSP 之间的"快递通道"。
- **rpmb**：Replay Protected Memory Block，某些 DSP/安全处理器使用的受控存储。

这些子系统在普通驱动开发中不常遇到，但在**音频驱动、多媒体驱动、基带驱动**里很常见。

#### 4. 什么时候需要了解 DSP

对大多数驱动开发者来说，DSP 是"透明的"——厂商固件搞定一切，你只管调标准 API。但以下场景需要深入：

- **音频驱动**：ALSA 驱动经常要把音频数据送给 DSP 编解码，需要理解 DMA + 共享内存的交互。
- **GPU/显示驱动**：GPU 本质上是高度并行的信号处理器，驱动通过命令缓冲区和它通信。
- **基带/调制解调器**：手机里的基带 DSP 有自己的固件，Linux 侧的驱动通过共享内存控制它。
- **自定义硬件加速**：如果你的 SoC 有专用硬件加速器（加密、图像 ISP），驱动逻辑和 DSP 通信类似。

vexpress-a9 实验环境没有 DSP，但理解"CPU 不直接做信号处理、而是通过共享内存/中断和专用处理器协作"这个模型，对后续理解 DMA 和中断很有帮助——它们都是"CPU 发命令、硬件自己干活"的模式。

## 2.2 存储器

驱动操作硬件，最终都是在读写各种存储——寄存器、RAM、Flash、DMA 缓冲区。理解这些存储器的特性和差异，才能理解驱动为什么用 `ioremap` 而不是直接解引用、为什么 DMA 缓冲区要特殊处理、为什么 Flash 要先擦后写。

### 2.2.1 存储器分类

#### 1. 按易失性分类

| 类型 | 断电后 | 速度 | 作用 | 驱动里在哪遇到 |
| --- | --- | --- | --- | --- |
| **RAM**（易失性） | 数据丢失 | 快 | 运行时数据（变量、栈、缓冲区） | `kmalloc` 分配的内存、DMA 缓冲区 |
| **ROM/Flash**（非易失性） | 数据保留 | 慢 | 固件、配置、Bootloader | 加载设备固件（`request_firmware`）、MTD 子系统 |

RAM 掉电就空——这就是为什么内核启动后要重新初始化所有数据结构，为什么驱动每次加载都要重新配置寄存器。Flash 掉电不丢——所以固件、U-Boot、设备树都存在 Flash 里。

#### 2. RAM 的种类

RAM 内部又分几种，速度和成本递减：

| 类型 | 速度 | 成本 | 用途 | 在 SoC 里的角色 |
| --- | --- | --- | --- | --- |
| **SRAM** | 最快 | 最高 | Cache、片上 TCM | CPU 的 L1/L2 Cache，vexpress-a9 的 L2C-310 |
| **DRAM** | 中等 | 中等 | 主内存（系统 RAM） | DDR SDRAM，vexpress-a9 的 512MB 主存 |
| **SDRAM** | DRAM 的一种，同步时钟 | 中等 | 主内存 | 现代 SoC 主存的标准形态（DDR = 双倍速率 SDRAM） |

对驱动开发者来说，主要打交道的是 **DRAM（主内存）**——`kmalloc`/`vmalloc` 分配的内存都来自 DRAM。SRAM 是 CPU 内部 Cache，驱动一般不直接操作（缓存一致性由硬件或 DMA API 保证）。

#### 3. Flash 的种类

非易失性存储也有细分，它们的行为差异直接影响驱动怎么写：

| 类型 | 特点 | 写入方式 | 典型用途 | 驱动子系统 |
| --- | --- | --- | --- | --- |
| **NOR Flash** | 随机读取（像 RAM），可片内执行（XIP） | 按字节/字写，需先擦除 | Bootloader、固件存储 | MTD（`mtdblock`） |
| **NAND Flash** | 页/块为单位读写，不能 XIP | 按页写，按块擦除，有坏块 | 大容量存储（U盘/eMMC/SSD） | MTD 或 block 层（UBI/UBIFS/jffs2） |
| **eMMC/UFS** | 内含控制器的 Flash，对外是块设备 | 控制器管理磨损均衡和坏块 | 手机/嵌入式存储 | block 子系统（标准块设备） |

关键差异：**NOR Flash 可以像 RAM 一样随机读**（所以 Bootloader 可以在 NOR 里直接执行——XIP），但 **NAND Flash 必须按页读写**，且要处理坏块。这个差异决定了驱动用哪种子系统（MTD vs block）。

vexpress-a9 设备树里有 `physmap-flash` 节点（NOR Flash），但 qemu 的实现有限——后续章节在 MTD 主题里会展开。

#### 4. 驱动开发者的视角

从驱动的角度，存储器按**访问方式**分成三组更实用：

| 访问方式 | 存储类型 | 驱动怎么访问 | 示例 |
| --- | --- | --- | --- |
| **内核内存** | DRAM（`kmalloc`/`vmalloc`） | 普通指针解引用 | 驱动里的数据结构、缓冲区 |
| **MMIO 寄存器** | 外设控制寄存器 | `ioremap` + `readl`/`writel` | LED 寄存器（1.6.2）、UART 寄存器 |
| **DMA 内存** | DRAM（但给设备用） | `dma_alloc`/`dma_map` + 共享 | 网卡收发包缓冲区 |

这三组的区别是第一章驱动开发"三件事"中"数据搬运"的硬件基础：

- 内核内存是 CPU 自己用的。
- MMIO 是 CPU 控制设备的"控制面板"。
- DMA 内存是 CPU 和设备**共享**的数据区域——这块内存两边都能访问，所以要特殊管理（缓存一致性、物理地址映射）。

这种"按访问方式分组"的视角，比按 SRAM/DRAM/NOR/NAND 分类更贴近驱动开发实际。后续 DMA 章节会深入展开"为什么 DMA 缓冲区不能随便用 `kmalloc`"。
