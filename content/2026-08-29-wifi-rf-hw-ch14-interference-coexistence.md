# WiFi 射频硬件入门（十四）：干扰与被干扰

> 下一章：[[2026-08-29-wifi-rf-hw-ch15-hands-on-measurements|第十五章：零仪器实验套装]]

第十三章把自家板子摆明白了：走线、地平面、净空。但 WiFi 的空口从来不是你一个人的——2.4 GHz 是一条全球免许可的共享总线（[[2026-08-29-wifi-rf-hw-ch02-radio-and-spectrum|第二章]]），任何人插上就能用。这一章回答硬件工程师那句口头禅「这不行，会干扰」到底在说什么，而且有两个方向：**被别人干扰**（邻居 AP、微波炉、USB3、别人的蓝牙坏你的事）与**干扰别人**（你的带外辐射落到别人频段——这不只是礼仪问题，是认证与法规问题）。

核心类比两条，都是软件工程师的老朋友：

1. **干扰 = 共享介质上的邻居流量**。回收第二章的结论：信道=总线、同信道干扰=共享冲突域——老式共享以太网里所有机器同抢一根线，无线电 2.4 GHz 上所有人同抢一段频谱。
2. **共存 = 单核上的任务调度仲裁**。ESP32 只有一套 RF，WiFi 与蓝牙像两个任务分时复用一颗单核 CPU；`esp_coex` 组件就是那个调度器——优先级、时间片、申请与释放，概念一一对应，你写 RTOS 时已经全部学过。

## 14.1 干扰的三种身份

把「干扰」当一个人是没法定罪的，先上户口。按「谁在干扰你、它守不守规矩」分三类：

**身份一：同信道邻居**。邻居 AP 与它的客户端和你在同一个 20 MHz 信道里，这就是第二章讲过的**共享冲突域**：大家都说 802.11、都守 CSMA/CA——先听后说、撞了退避。这类干扰的伤害方式是**抢时间**：信道就一个，邻居发包你就得等，退避与重传的空口开销对双方都是纯损失。它是「守规矩的堵车」。

**身份二：邻信道泄漏**。隔壁信道的发射机在自己的信道上完全合法，但你的接收滤波器不是砖墙（[[2026-08-29-wifi-rf-hw-ch10-rf-front-end-fem|第十章]]的带通滤波器只有数十 dB 带外抑制），强邻频信号会漏进你的接收带宽；更糟的是**前端被强信号压饱和**。机理拆开看（回收第五章的链路图）：带通滤波在 LNA 之前，只挡「2.4G 之外的世界」，挡不住隔壁信道的 2.4G 自己人；漏进来的强邻频信号与你的信号一起过 LNA，**AGC 看的是总功率、不区分信道**——邻频太强，AGC 就把整体增益压低（第五章的「自动量程」被别人拉走了量程），你自己信道里的弱信号被压到 ADC 量程底部，等效灵敏度直线下滑。这类伤害方式是**抬底噪/压灵敏度**。1/6/11 互不重叠的信道纪律（第二章）就是为它立的。

**身份三：非 WiFi 源**。微波炉、USB3 线缆、有问题的电机——它们**不说 802.11 语言**：不载波侦听、不退避、不等 ACK、全天候发射。你的 CSMA/CA 对它们毫无约束力，因为协议里根本没有它们。类比：共享总线上挂了一台**不接仲裁线的广播干扰台**，持续往介质上灌垃圾数据——再礼貌的排队算法也拿它没办法，因为它听不懂「请让让」。这是最纯粹的一类干扰：**抬噪声底**。

| 身份 \| 谁在干扰你 \| 守不守规矩 \| 伤害方式 \| 典型对策                                                                     |
| ---------------------------------------------------------------------------------------------------------------------------- |
| 同信道 \| 邻居 AP 及其客户端 \| 守：同说 802.11，排队退避 \| 抢空口时间（退避重试开销） \| 换到更空的信道、降 AP 密度        |
| 邻信道 \| 隔壁信道的强发射机 \| 半守：在别的信道合法发射 \| 泄漏抬底噪、强信号压饱和前端 \| 信道拉开（1/6/11）、离大功率远点 |
| 非 WiFi 源 \| 微波炉、USB3、劣质电机 \| 不守：不在协议内，不排队不退避 \| 宽带噪声直接抬底噪 \| 物理隔离：距离、屏蔽、换口   |

## 14.2 噪声底视角：三种身份统一成一笔账

三种身份看起来很不同，但落到你的接收机上只有一笔账。回收 [[2026-08-29-wifi-rf-hw-ch05-rx-chain-sensitivity|第五章]]的两个结论：噪声底 = -174 dBm/Hz + 10·log10(BW)，20 MHz 信道约 **-101 dBm**；SNR = 信号功率 − 噪声功率，而**灵敏度是一张阶梯表**（HT20 MCS7 约需 26.8 dB，MCS0 约 8.4 dB，同芯相差 27 dB）。干扰只需要干一件事——往「噪声」那一栏加数：

```text
SNR = 信号功率 − (热噪声底 + 干扰功率)
                ↑ 物理学定死     ↑ 邻居/微波炉/USB3 往这加
```

拿第五章的阶梯表算一笔演示账（演示用数字，非实测）：

```text
安静信道：   信号 -65 dBm，底噪 -101 dBm → SNR 36 dB → MCS7 敞开跑
干扰抬 10 dB：信号 -65 dBm，底噪  -91 dBm → SNR 26 dB → MCS7 出局，降档
干扰抬 20 dB：信号 -65 dBm，底噪  -81 dBm → SNR 14 dB → 只剩低阶 MCS + 重传
```

这就解开了「**App 信号强度不变、网速却塌了**」的秘密：手机 App 显示的信号强度来自 RSSI，RSSI 只量分子（信号功率）；干扰动的是分母（噪声+干扰）。信号满格与速率掉档完全不矛盾。USB3 的量级参考：Intel 白皮书实测外接 USB3 硬盘能把 2.4 GHz 频段噪声底抬**近 20 dB**（14.3）——正好是上面第三行的现实版。

再细分一下「伤害方式」，排查时方向完全不同：

| 伤害类型 \| 主角 \| 机制 \| 观察到的症状                                                 |
| ---------------------------------------------------------------------------------------- |
| 抢时间 \| 同信道邻居 \| CSMA/CA 退避与重传吃掉空口时间 \| 满格但测速塌、延迟抖动大       |
| 抬底噪 \| 邻频泄漏与非 WiFi 源 \| 干扰功率叠在热噪声上，SNR 塌 \| 满格、速率档位整体下移 |

两类伤害经常同时发生（邻居 AP 既抢时间、它的旁瓣也漏过来），但主次分清才能对症：同信道问题换信道最有效（人少时间就多），底噪问题要找干扰源（挪走它）。

## 14.3 经典干扰源档案

### 1. 微波炉：ISM 频段的本源用户

微波炉不是「跑到」2.4 GHz 的入侵者——**ISM 频段本来就是给这类设备划的**（Industrial/Scientific/Medical，2.400~2.4835 GHz 全球 ISM 划分，第二章），磁控管工作在 **2.45 GHz** 附近，WiFi 才是后来借地盘的。它的泄漏是宽带连续噪声，重心落在 2.45 GHz 一带（对应 WiFi 高段信道，业界通识量级），所以微波炉一开往往高频信道先遭殃。

「泄漏」不是故障才有的：法规明文允许微量泄漏——美国 FDA 法规 **21 CFR 1030.10** 原文口径：距外表面 5 cm 处的等效平面波功率密度，**售前不得超过 1 mW/cm²，售后不得超过 5 mW/cm²**。设计前提就是「允许有，别太多」；炉门密封条老化后泄漏变大是常见劣化路径。

### 2. USB3：白皮书钉死的名案

著名的 Intel 白皮书《USB 3.0 Radio Frequency Interference Impact on 2.4 GHz Wireless Devices》（2012-04，文档号 327216-001）用近场探头实测钉死了这个案子。机制：USB3 SuperSpeed 差分对上的 **5 Gbit/s 数据频谱**是宽带 sinc 形，能量从直流铺到 5 GHz 以上，**2.4~2.5 GHz 整段落在它的旁瓣里**——不是某个谐波恰好命中 2.4G，而是宽带噪声罩住整个 ISM 频段。白皮书的关键实测数字：

| 量测对象 \| 结果（近场探头口径） \| 出处                                    |
| --------------------------------------------------------------------------- |
| 外接 USB3 硬盘工作时 \| 2.4 GHz 频段噪声底抬**近 20 dB** \| Intel 白皮书 §4 |
| 笔记本 USB3 插座本身 \| 约 **25 dB** \| Intel 白皮书 §5                     |
| 对硬盘做完全屏蔽 \| 辐射噪声降约 **12 dB** \| Intel 白皮书 §5               |
| 插座屏蔽与接地改进 \| 再压 **≥10 dB** \| Intel 白皮书 §5                    |

最狠的一条结论：**这种带内宽带噪声无法用滤波器滤除**——它就落在你的工作频段里，滤它等于滤自己。白皮书还做了无线鼠标实验：接收器垂直叠在 USB3 口正上方时**全距离无响应**；用 USB2 延长线把接收器挪到机身另一侧，立刻恢复。对策只有物理三招：**挪远、换口（经 USB2 延长）、屏蔽**。

### 3. 蓝牙：跳频的室友

经典蓝牙把 2.4G 切成 **79 个 1 MHz 信道、每秒跳 1600 次**；BLE 用 40 个 2 MHz 信道（蓝牙核心规范通识）。关键机制是 **AFH（Adaptive Frequency Hopping，自适应跳频）**：主设备持续统计各信道的丢包质量，把「坏信道」从跳频表里剔除——蓝牙避让 WiFi 的方式不是硬碰，是**绕道**。第二章误区表里那句「蓝牙与 WiFi 同住 2.4G、靠 AFH 避让（第十四章）」在此兑现。对 WiFi 而言，邻居家的蓝牙是低占空比的脉冲噪声，通常不致命；**同一颗芯片里的蓝牙**则根本不走空口竞争，走下一节的分时仲裁。

### 4. Zigbee/Thread：缝隙里的住户

IEEE 802.15.4 在 2.4 GHz 放 **16 个信道（编号 11~26）**，间隔 5 MHz、每信道占 2 MHz（规范通识）。信道 15/20/25 的中心频率分别是 2425/2450/2475 MHz——**恰好落在 WiFi 1/6/11 的缝隙里**（信道 1 占 2401~2423、6 占 2426~2448、11 占 2451~2473，中间各留 2 MHz 缝）。这是教科书级的共存配对：Zigbee 网用 15/20/25，WiFi 锁 1/6/11，物理上错开。功率上 802.15.4 设备只有 mW 级，单台不凶，但传感器网部署密度高。ESP-IDF 官方共存文档对单 RF 芯片有明确警告：WiFi/BLE 流量增加会导致 Thread/Zigbee **丢包率上升**；要做 Thread 边界路由器或 Zigbee 网关，官方推荐**双 SoC 方案**（如 ESP32-S3 管 WiFi + ESP32-H2 管 802.15.4，各配独立 RF）。

四类汇总成一张档案表：

| 干扰源 \| 机制 \| 频谱形态 \| 对 WiFi 的影响 \| 对策                                                               |
| ------------------------------------------------------------------------------------------------------------------ |
| 微波炉 \| 2.45 GHz 磁控管泄漏 \| 宽带连续，重心 2.45 GHz \| 高段信道底噪抬、SNR 塌 \| 换信道 1、拉开距离、上 5G    |
| USB3 \| 5 Gbit/s 数据宽带频谱旁瓣 \| DC~5 GHz 宽带罩住 ISM 段 \| 底噪抬近 20 dB（实测） \| 挪远、USB2 延长、屏蔽线 |
| 蓝牙 \| 79 信道跳频 + AFH 避让 \| 低占空比窄脉冲 \| 零星碰撞，通常不致命 \| 保持 AFH 开启；同机走共存仲裁          |
| Zigbee/Thread \| 16 信道固定驻留 \| 窄带驻留（2 MHz） \| 同缝则互卡，错缝则相安 \| WiFi 1/6/11 + Zigbee 15/20/25   |

## 14.4 共存：一套 RF 上的任务调度

前面都是「被别人干扰」。还有一类特殊的干扰源住在你自己板子上：**ESP32 同时开 WiFi 和蓝牙时，它俩谁干扰谁？** 都不是——它们不打架，因为有调度器。

### 1. 问题：一套 RF，两个租户

官方文档《RF 共存》（`docs/zh_CN/api-guides/coexist.rst`）开篇就说死：「**每款芯片只支持一路被多个射频收发模块共享的 RF，不同模块无法同时使用 RF 收发数据，因此采用时分复用的方法调节不同模块的数据包收发**」。WiFi、BLE、经典 BT、802.15.4 最多三种射频模块，抢的是同一个射频前端、同一根天线（第五章见过 `LNA_IN` 收发复用同一引脚；第七章的 SoC 框图里也只有一套 RF 链）。

### 2. 类比展开：esp_coex 就是那个调度器

软件工程师最熟的模型来了：**单核 CPU 上跑两个任务**。WiFi 任务和 BT 任务都要独占「RF 这颗 CPU」——物理上半双工，同一时刻只能一个人用。谁来仲裁？`esp_coex` 组件。调度器的每个概念都能对上号：

```c
/* components/esp_coex/include/esp_coexist.h —— prefer 枚举（本机 IDF v6.0.2 原文） */
typedef enum {
    ESP_COEX_PREFER_WIFI = 0,  /*!< Prefer to WiFi, WiFi will have more
                                     opportunity to use RF */
    ESP_COEX_PREFER_BT,        /*!< Prefer to bluetooth, bluetooth will have
                                     more opportunity to use RF */
    ESP_COEX_PREFER_BALANCE,   /*!< Do balance of WiFi and bluetooth */
} esp_coex_prefer_t;
```

「**more opportunity to use RF**」是字面意义的时隙分配。`esp_coex_preference_set()` 的文档注释还给了业务例子：偏好 BT 时 A2DP（经典蓝牙音频）更流畅，默认是平衡——这就是调度策略旋钮。调度器的「申请资源」接口在内部头文件里，签名本身就是证据：

```c
/* components/esp_coex/include/private/esp_coexist_internal.h（原文注释摘引） */
int coex_wifi_request(uint32_t event, uint32_t latency, uint32_t duration);
/*   latency : WiFi will request coexistence after latency
     duration : duration for WiFi to request coexistence            */
int coex_bt_request(uint32_t event, uint32_t latency, uint32_t duration);
int coex_wifi_release(uint32_t event);
int coex_bt_release(uint32_t event);
```

`latency/duration` 两个参数翻译过来：**「我能容忍等多久、我要用多久」**——几乎就是实时系统里带截止期约束的资源申请。对照表钉死全部映射：

| 你熟悉的调度概念 \| esp_coex 里的对应物 \| 出处                                       |
| ------------------------------------------------------------------------------------- |
| 时间片轮转 \| 共存周期内按 Wi-Fi/BT/BLE 划分时间片 \| 官方共存文档                    |
| 调度策略旋钮 \| prefer 三档（WiFi/BT/平衡），默认平衡 \| esp_coexist.h                |
| 优先级抢占 \| 每 N 个广播事件一次高优先级，可抢 WiFi 时间片 \| 官方共存文档           |
| 场景化调度模板 \| 「共存模板」：WiFi 与 BLE 均 CONNECTED 时各占 50% \| 官方共存文档   |
| 应用申报负载特征 \| esp_coex_status_bit_set（BLE MESH 三状态） \| esp_coexist.h       |
| 调度器黑盒、旋钮开放 \| libcoexist.a 预编译，经 adapter 索取 OS 原语 \| 本机 IDF 实查 |

官方文档对时间片的描述完全是调度器语言：共存周期与各时间片占比**按 WiFi 状态分四类**（IDLE 时 RF 归蓝牙模块管；CONNECTED 时周期以 TBTT 信标点为起点、大于 100 ms——TBTT 就是「下一个信标预定发送时刻」，蓝牙的分时窗口围着 WiFi 的信标节奏排班，[[2026-08-26-esp32-s3-box-3-ch16-wifi-events|BOX-3（十六）]]讲过的 beacon/DTIM 是同一条时间轴；SCAN 与 CONNECTING 时 WiFi 时间片加长、蓝牙时间片相应调整）；「共存模板」按使用场景选择——WiFi CONNECTED + BLE CONNECTED 的模板里**一个周期内 WiFi 与 BLE 时间片各占 50%**。动态优先级也在此：蓝牙并非永远让路，每 N 个广播事件里有一个用高优先级，若它落在 WiFi 时间片内，**RF 会被 BLE 抢占**。

### 3. 黑盒边界：闭源的调度器，开放的原语

和 `libnet80211.a` 同款架构（[[2026-08-26-lwip-deep-dive-ch18-esp32-wifi-lwip-integration|lwIP（十八）]]的黑盒口径）：调度策略本体在预编译库 **`libcoexist.a`** 里（本机 `components/esp_coex/lib/esp32*/libcoexist.a`，逐目标各一份，实查存在），它通过 adapter 向开放侧索取操作系统原语——`esp_coex_adapter.c` 里是一排 FreeRTOS 包装：自旋锁创建（`spin_lock_create`）、临界区进出（`int_disable/restore`）、计数信号量（`semphr_create/take/give`）、ISR 内 yield。**调度器闭源，但它跑在你给的锁和信号量上**；两协议栈何时切换 RF 的策略细节属于库内实现，本文不虚构。

### 4. 真实键名与 BOX-3 的沉默配置

软件共存由 Kconfig 开关控制，**真实键名是 `CONFIG_ESP_COEX_SW_COEXIST_ENABLE`**（grep 核实；老教程里常见的 `CONFIG_SW_COEXIST_ENABLE`、`CONFIG_ESP_WIFI_SW_COEXIST_ENABLE` 都是历史旧名，`sdkconfig.rename` 里统一映射到新键）：

```yaml
# components/esp_coex/Kconfig（本机 IDF v6.0.2 原文摘录）
config ESP_COEX_SW_COEXIST_ENABLE
bool "Software controls WiFi/Bluetooth coexistence"
depends on (ESP_WIFI_ENABLED && BT_ENABLED) || \
(ESP_WIFI_ENABLED && IEEE802154_ENABLED) || \
(IEEE802154_ENABLED && BT_ENABLED)
default y # WiFi+BT（或 +802.15.4）同时启用时，默认自动开
```

再看 BOX-3 的真实工程（本机 `~/esp/esp-box/examples/factory_demo/sdkconfig.defaults` 实查摘录）：

```yaml
CONFIG_BT_ENABLED=y
CONFIG_BT_NIMBLE_ENABLED=y
CONFIG_BT_NIMBLE_MAX_CONNECTIONS=1
CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM=3
CONFIG_ESP_WIFI_DYNAMIC_RX_BUFFER_NUM=4
CONFIG_ESP_WIFI_TX_BA_WIN=4
```

BLE（NimBLE 配网与伴侣连接）与 WiFi 同时开着，**整份默认配置里没有一个 COEX 键**——因为 `default y`，两协议栈并存时软件共存自动生效。这份沉默本身就是最好的证据：在 ESP32 上 BLE+WiFi 共存不是要特意打开的功能，是默认状态。官方补了两条使用建议：共存时把 WiFi 协议栈 task 与蓝牙 controller/host task **分到不同 CPU 核**（S3 双核正好一边一个）；只有纯蓝牙应用才建议关掉共存省体积（Kconfig help 原文）。

### 5. 代价与外部共存

分时不是免费的：**RF 时间被切走，吞吐上限直接打折**——50/50 模板下 WiFi 的空口时间先砍一半，再算重传与降速。「BLE 一开 WiFi 吞吐掉一截」的物理原因就在这，不是 bug。这套仲裁发生在驱动与 PHY 之下，**lwIP 与应用层对它无感知**，只看到吞吐变化与延迟毛刺——软件栈边界与任务模型见 lwIP（十八），连接事件层见 [[2026-08-26-esp32-s3-box-3-ch16-wifi-events|BOX-3（十六）]]，本章只管 RF 这一层。

顺带一瞥**外部共存**（`CONFIG_ESP_COEX_EXTERNAL_COEXIST_ENABLE`，默认关）：给「WiFi 模组 + 独立蓝牙芯片」的双芯片设计用，两颗芯片间拉 1~3 根 GPIO 握手线，信号名叫 **request / priority / grant**（leader/follower 主从角色）——这就是总线仲裁的 DMA REQ/ACK 模型原样搬到了芯片间：从设备申请线、主设备授权线。单芯片内的 esp_coex 做的事，和这三根线在协议层做的事，是同一个词：仲裁。

## 14.5 对策清单

排查顺序建议自下而上：先看是不是自己板子的老毛病（电源纹波见 [[2026-08-29-wifi-rf-hw-ch12-power-supply|第十二章]]、失配见 [[2026-08-29-wifi-rf-hw-ch09-impedance-matching|第九章]]），再怀疑邻居。对症下药表：

| 症状/场景 \| 首选对策 \| 原理                                                             |
| ----------------------------------------------------------------------------------------- |
| 邻居全挤在信道 6 \| 换到 1/6/11 里最空的一个（App 数 AP） \| 同信道是抢时间，人少时间才多 |
| 微波炉一开就卡 \| 换信道 1、拉距离、能上 5G 就上 \| 泄漏重心 2.45 GHz，高段信道先受害     |
| USB3 硬盘拷贝时断流 \| 挪远、经 USB2 口延长、屏蔽线 \| 带内宽带噪声滤不掉，只能物理隔离   |
| Zigbee 与 WiFi 互卡 \| WiFi 锁 1/6/11，Zigbee 用 15/20/25 \| 信道缝隙错开，物理不重叠     |
| 自家多 AP 互相拖慢 \| AP 间也用 1/6/11 错开、降发射功率 \| 邻道泄漏随距离与功率变化       |
| 满格但速率掉档 \| 查底噪：App 看信道图是否整体变亮 \| 干扰动的是分母，RSSI 不知情         |

三条实操注解：

- **换信道怎么选**：手机 App 的信道视图里数每个信道上的 AP 个数与最强信号——1/6/11 三选一，挑 AP 少且信号弱的；第二章的结论仍然成立：邻居信道 6 挤满了就别选 6，同信道退避开销对双方都是纯损失。
- **5G 逃离的边界**：5 GHz 邻居少、没有微波炉和 USB3 的宽带噪声，但波长短穿墙弱（第二章频段地图），适合「同房间/近距高吞吐」场景；设备在墙后老老实实回 2.4G。
- **物理隔离是最后的手段也是最强手段**：辐射功率随距离按 1/r² 衰减（第十五章实测验证），USB3 硬盘挪开一米就是数十分贝的衰减——比任何软件参数都有效，因为带内宽带噪声滤不掉。

「被干扰」要治，「干扰别人」也要自觉——你也是别人的邻居：2.4 GHz 别开 40 MHz（一个信道占掉三分之二频段，第二章已算账）；别私换高增益天线加大功率——发射机的**带外杂散辐射**是认证测试的硬性限值项，超标不只是干扰邻居，是**认证不过、不得销售**的法规问题。为什么违法、各国有何差异，第十七章（认证与法规一瞥）展开。

## 14.6 观察实验（待真机验证）

> [!warning] 待真机验证
> 以下两个实验的步骤与预期均为设计稿，真机到货后实测回填数据；不预设具体读数，只给预期方向。

### 实验一：微波炉烧水前后（约 15 分钟）

器材：微波炉、一大杯水（**必须放**——空载运行伤磁控管）、手机 WiFi 分析仪 App、ESP32（STA 连家里 2.4G AP）、同网电脑一台。

| 步骤 \| 操作 \| 记录什么                                                         |
| -------------------------------------------------------------------------------- |
| 1 \| 基线：炉关。App 看自家信道与整段 2.4G 底噪形态 \| 哪些信道亮、自家 RSSI     |
| 2 \| 同状态，电脑 ping ESP32 约 300 个包 \| p50/p99、丢包数                      |
| 3 \| 炉内放水最高档 60 s，同位置重复步骤 1~2 \| 同上三项                         |
| 4 \| 若 AP 可换信道：分别在信道 1 与信道 11 重复 \| 高频信道是否更伤（预期方向） |

预期（方向性，不预设数值）：App 频谱图上 **2.4G 中高频段整段抬亮**（宽带噪声的形态是「一片亮」，不是某根尖峰）；自家 AP 的 RSSI 读数基本不动（±1~2 dB）；ping 的 p50 轻微上升、**p99 与丢包明显恶化**。分子没变、分母塌了——14.2 那笔账的厨房现场版。第五章 5.6 的微波炉实验用 iperf 看吞吐，本实验改看延迟分布与频谱形态，两者互补。

### 实验二：USB3 硬盘拷贝对照（约 10 分钟）

器材：USB3 移动硬盘（或任意 USB3 外设）、电脑、同上 ESP32 与 App。

| 步骤 \| 操作 \| 记录什么                                               |
| ---------------------------------------------------------------------- |
| 1 \| 基线：硬盘未接，ping 300 包 + App 底噪 \| p50/p99、信道图形态     |
| 2 \| 贴脸：ESP32 紧贴正在拷大文件的硬盘与线缆 \| 同上                  |
| 3 \| 隔离：硬盘原地，ESP32 挪开 1 m 以上（或硬盘改接 USB2 口） \| 同上 |

预期：贴脸相位 2.4~2.5 GHz 整段底噪抬亮、ping 尾部恶化；挪开后回落。白皮书里「接收器叠在 USB3 口上全距离无响应」的鼠标实验是极端对照组——你的板子离 USB3 口越近，越接近那个情形。

口径两条：微波炉实验不拆机、不空载；App 读数只做**同一台手机的前后形态对照**（RSSI 跨设备不可比，第五章 5.5 的标定差异口径）。

## 14.7 常见误区表与小结

| 误区 \| 错在哪 \| 正确姿势                                                                                   |
| ------------------------------------------------------------------------------------------------------------ |
| 「信号强就没干扰」 \| RSSI 只量分子，干扰动的是分母 \| 看吞吐/p99/App 信道图整体亮度，别看格数               |
| 「干扰就是信号变弱」 \| 三种身份里没有一种主要在削弱信号 \| 用 SNR 视角统一：抬底噪、抢时间（14.2）          |
| 「蓝牙和 WiFi 天生互斥」 \| 同频段但 AFH 绕道、同芯走分时仲裁 \| 共存可用，代价是吞吐打折（14.3/14.4）       |
| 「微波炉坏了才泄漏」 \| 法规允许售前 1、售后 5 mW/cm²@5cm 的泄漏 \| 微量泄漏是设计内状态（21 CFR 1030.10）   |
| 「USB3 干扰是玄学」 \| Intel 白皮书实测抬底噪近 20 dB \| 档案表 + 实验二可复现方向                           |
| 「同信道干扰也是噪声」 \| 同信道主要抢时间，邻频/非 WiFi 才抬底噪 \| 两类伤害分开排查（14.2 的表）           |
| 「开了软件共存就零损失」 \| 分时复用=RF 时间被切走，50/50 模板先砍一半 \| 共存是「都能用」，不是「都全速」   |
| 「上 5G 一劳永逸」 \| 逃离 2.4G 邻居与微波炉/USB3，但穿墙弱覆盖小 \| 按距离/障碍场景选频段（第二章频段地图） |

**小结**：

- 干扰有三种身份：**同信道**（守规矩的邻居，抢空口时间）、**邻信道**（合法但泄漏，抬底噪压前端）、**非 WiFi 源**（不排队不退避的「广播干扰台」，纯抬底噪）——核心类比回收第二章：干扰就是共享介质上的邻居流量。
- 三种身份统一到第五章的噪声底账上：**SNR = 信号 −（热噪声 + 干扰）**。干扰抬底噪 → SNR 塌 → 沿灵敏度阶梯降档 → 重传吃掉吞吐——而 RSSI 全程不动，这就是「满格却掉速」的秘密。
- 档案四件套：微波炉（2.45 GHz 磁控管，泄漏限值 1/5 mW/cm²@5cm 是法规明文）、USB3（5 Gbps 宽带频谱罩住 ISM 段，实测抬底噪近 20 dB，带内噪声滤不掉只能物理隔离）、蓝牙（AFH 跳频避让）、Zigbee（15/20/25 与 WiFi 1/6/11 缝隙错开）。
- **共存=单核上的任务调度仲裁**：一套 RF 分时复用，`esp_coex` 是调度器——prefer 三档是调度策略、`coex_wifi_request` 的 latency/duration 是带截止期的资源申请、共存模板与动态优先级是抢占式时间片；调度器本体闭源（`libcoexist.a`），旋钮开放。
- BOX-3 的 factory_demo 没有一行 COEX 配置——`CONFIG_ESP_COEX_SW_COEXIST_ENABLE` 在 WiFi+BT 并存时 `default y` 自动生效；代价是 RF 时间被切走、WiFi 吞吐上限打折，而 lwIP 与应用层对此无感（软件栈边界见 lwIP 十八）。
- 对策按伤害类型对症：抢时间→换更空的信道；抬底噪→找到并物理隔离干扰源。你也是别人的邻居：慎开 40 MHz、别私改功率——带外辐射超标是认证问题，第十七章展开。
