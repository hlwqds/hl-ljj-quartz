## 目标（先说结论）

- `xTaskCreate()` 第三个参数（栈深）在 Vanilla FreeRTOS（官方原版内核，相对乐鑫魔改版）的
  单位是**字**（word）：CM4F 端口
  `StackType_t = uint32_t`，1 字 = 4 字节。工程里那句 `xTaskCreate(fast_task, "fast", 256, ...)` 给的是
  **256 字 = 1024 字节**，不是 256 字节。
- ESP-IDF（乐鑫 ESP32 官方开发框架，内核为魔改版 FreeRTOS）里同一个参数的单位是**字节**
  （`StackType_t = uint8_t`）。这是
  [[2026-08-26-freertos-deep-dive-ch1-from-bare-metal-to-rtos|FreeRTOS（一）：从裸机到 RTOS]]
  讲的第一个端口差异——**本章用三层实验把它实测兑现**，是给 IDF 用户除雷的章。
- 三层实验：① 在 256 字栈的任务里放 `volatile char pad[900]` → 能跑（余量只剩几个字）、`pad[1100]` → 越界爆栈；
  ② 用 `uxTaskGetStackHighWaterMark()` 实测序章工程现成的 fast/slow 真实余量；③ 反向坑算账——
  把 IDF 的 2048 抄过来 = 8192 字节/任务，64KB 的 heap_4（FreeRTOS 官方堆方案之四，见下文
  术语卡）撑不了几个任务。
- 本工程 `configMINIMAL_STACK_SIZE = 128` 的语义也在此定罪：**128 字 = 512 字节**，它是 Idle
  任务（空闲任务：所有任务都在睡时调度器跑的兜底）的栈深，
  不是「128 字节」也不是「最小可用人间值」。

> 📖 **术语卡：字（word）**
> **是什么**：CPU 一次能搬运/运算的天然宽度。32 位 Cortex-M 上 1 字=4 字节；8 位机上 1 字=1 字节；64 位机常指 8 字节。FreeRTOS 的「栈深单位是字」在 CM4F 上即 ×4。
> **为什么存在**：栈的压入/弹出以字为单位最自然（SP 按字移动）；历史习惯让这套 API 沿用字计数而不是字节。
> **类比**：你的主场：字节 vs 内存页——malloc 论字节、物理内存论页，单位看错差的不止一点。
> ⚠️ 类比边界：页大小有 `getconf PAGE_SIZE` 明着查，而「字是几字节」藏在移植层头文件的一行 typedef 里（下节案发现场），不翻源码看不见。

> 📖 **术语卡：栈与栈帧（stack / stack frame）**
> **是什么**：栈=每个任务私有的一块后进先出内存，存函数调用现场；栈帧=一次函数调用在栈上占的那一块（返回地址、保存的寄存器、局部变量）。`portSTACK_GROWTH = -1` 表示栈**向下生长**：用得越多，栈顶指针 SP 越往低地址走；「爆栈」=SP 越过栈的低地址界，写入下方邻居。
> **为什么存在**：函数调用/返回天然后进先出，用栈自动回收局部变量零成本；每个任务各配一栈，才能随时切走再原样切回（上下文切换=把 CPU 现场从一个任务搬到另一个）。
> **类比**：叠盘子：放/取只能最上面；爆栈=盘子摞太高，压坏了下面桌上别人的东西。
> ⚠️ 类比边界：盘子摞高只是压坏自己，栈越界是**真写入**紧邻内存——毁掉的是堆邻居/别的任务的账本（实验 A 的 pad[1100] 干的就是这个）。

## 差异的实现现场：一行 typedef 定罪

主系列在[[2026-08-26-freertos-deep-dive-ch21-stack-and-memory-layout|FreeRTOS（廿一）：栈与内存布局]]
里给过 IDF 侧的现场（`portSTACK_TYPE uint8_t`）。本工程引用的上游内核
（`~/stm32/FreeRTOS-Kernel`，`V11.1.0+`，`tskKERNEL_VERSION_NUMBER` 见 `include/task.h:57`）CM4F 端口是另一行：

```c
/* portable/GCC/ARM_CM4F/portmacro.h:55-58 —— 本工程的实现现场 */
#define portSTACK_TYPE    uint32_t   /* 55 行：字的宽度 */
typedef portSTACK_TYPE   StackType_t; /* 58 行：从此 StackType_t = 4 字节 */

/* portable/GCC/ARM_CM4F/portmacro.h:81 */
#define portSTACK_GROWTH  ( - 1 )     /* 栈向下生长：溢出方向是低地址 */
```

**portmacro.h 走读**（上文代码块逐行拆；portmacro.h=移植层宏文件，把内核适配到具体 CPU 架构的那层）：

| 行                                    | 作用                                                            |
| ------------------------------------- | --------------------------------------------------------------- |
| `#define portSTACK_TYPE uint32_t`     | 把「栈的宽度单位」定为 32 位——**1 字=4 字节**的判决书           |
| `typedef portSTACK_TYPE StackType_t;` | 起别名 StackType_t：内核所有栈计数从此以它为单位                |
| `portSTACK_GROWTH ( - 1 )`            | 栈向下生长标志：负值=往低地址长，溢出方向在低地址端（CM4 惯例） |

单位陷阱的「案发动作」在 `tasks.c` 的任务创建路径里，栈内存按**字节数 = 字深 × 字宽**申请：

```c
/* tasks.c:1650-1663（prvCreateTask，portSTACK_GROWTH < 0 分支）：
 * 先 pvPortMalloc 一块 TCB，再单独 pvPortMalloc 一块栈——两次独立分配 */
pxNewTCB = ( TCB_t * ) pvPortMalloc( sizeof( TCB_t ) );
...
pxNewTCB->pxStack = ( StackType_t * ) pvPortMallocStack(
    ( ( size_t ) uxStackDepth ) * sizeof( StackType_t ) );  /* ← 256 在这里 ×4 = 1024 */
```

> 📖 **术语卡：TCB（任务控制块）**
> **是什么**：Task Control Block：内核为每个任务建的「户口本」结构体——栈顶指针、优先级、任务名、挂就绪/阻塞队列用的链表节点等全在里面；上下文切换的第一步就是从当前 TCB 存/取栈顶。
> **为什么存在**：调度器要能随时暂停任何一个任务再原样恢复，全部状态必须集中记账。
> **类比**：你的主场：`task_struct` 的迷你版——同一物种，小两个数量级（本配置估值 ~110–130B，待核对#4 实测定谳）。
> ⚠️ 类比边界：`task_struct` 由 slab 分配、与内核栈分开管理；FreeRTOS 的 TCB 和任务栈是 heap_4 里**两次独立的分配**——谁也不挨着谁，爆栈先砸到谁看运气。

**tasks.c 创建路径走读：**

| 行                                                          | 作用                                                             |
| ----------------------------------------------------------- | ---------------------------------------------------------------- |
| `pvPortMalloc( sizeof( TCB_t ) )`                           | 从 heap_4 申请任务户口本——独立一笔                               |
| `pvPortMallocStack( uxStackDepth * sizeof( StackType_t ) )` | 申请栈：字节数=你给的数字×字宽——**256 在这里 ×4=1024**，案发动线 |
| 两次独立分配                                                | TCB 与栈不保证相邻——越界写穿先毁到谁，实验 A 候选表#2 的悬念     |

于是同一个数字在两个生态里的真实含义：

| 你写的数字 | 本工程（Vanilla/CM4F，字）     | ESP-IDF（字节）                          |
| ---------- | ------------------------------ | ---------------------------------------- |
| `128`      | 512 B（Idle 任务的规格）       | 512 字节都不够一个含 printf 的任务起步   |
| `256`      | **1024 B**（序章工程现值）     | 256 B——**必爆**（连任务入口帧都放不下）  |
| `2048`     | 8192 B（本板属奢侈，见实验 C） | 2048 B（IDF 含 printf 任务的保守起步值） |

栈从哪来：heap_4。注意一个容易以讹传讹的细节——heap_4 的 64KB **不是**链接器 `_end`/`_heap_end` 划出的
`sbrk` 区（sbrk=libc 动态抬高堆顶的经典调用、`_end`=链接脚本里 bss 尾符号，你的主场；链接脚本 `STM32F429IG.ld:57-63` 那个 `.heap (NOLOAD)` 段是给 libc malloc 留的，本工程未用），
而是一个静态数组：

```c
/* portable/MemMang/heap_4.c:93-95 —— 64KB 静态数组，落在主 SRAM 的 .bss */
PRIVILEGED_DATA static uint8_t ucHeap[ configTOTAL_HEAP_SIZE ];
```

> 📖 **术语卡：heap_4**
> **是什么**：FreeRTOS 官方四套堆方案（heap_1~4）之四：一块静态数组 `ucHeap[64KB]` 打底，`pvPortMalloc`/`vPortFree` 在里面切分；每块前挂 8 字节块头、按 8 字节对齐，free 时把**相邻空闲块合并**成大块。
> **为什么存在**：裸机没有现成 malloc；heap_4 兼顾「可释放」与「抗碎片」（合并相邻空闲块），是常用默认。
> **类比**：你的主场：微缩的 slab/buddy 混合体——块头记账+空闲链+合并，只是全塞在一个静态数组里。
> ⚠️ 类比边界：64KB 是**编译期定死**的数组大小（`configTOTAL_HEAP_SIZE`），不是可增长的 sbrk 区——用完直接返回 NULL（实验 C 第 8 个任务的下场）。

链接脚本头部注释（`STM32F429IG.ld:3-4`）写明：堆本可放 CCM（DMA 不可及、最安全），本工程为教学简单放主
SRAM。每次分配还要加 8 字节块头并对齐到 8（`heap_4.c:158` 的 `xHeapStructSize`、`heap_4.c:186-199` 的取整）——
这笔小账在实验 C 里会放大到肉眼可见。

## 实验 A：pad 逼近边界——900 能活，1100 必爆

先做算术（这就是预期值的来历）：

```text
栈深 256 字 = 1024 字节
任务入口已用：CM4F 端口 pxPortInitialiseStack 摆好的初始上下文 ≈ 16 字 = 64 字节
             （硬件帧 8 字 + R4–R11 8 字；单步亲见是本系列 ch17 的戏）
任务函数可用余量 ≈ 1024 − 64 = 960 字节
pad[900]：900 + 帧杂项（保存 LR/局部 i 等，−O0 下帧肥，估 16–48 字节）≈ 916–948 → 界内，余量个位数
pad[1100]：1100 + 帧杂项 ≈ 1116–1148 → SP 越过栈基约 150–190 字节 → 写穿到堆里邻居
```

**算术走读**（上面预期值的来历，逐项拆）：

| 项                    | 拆解                                                                                               |
| --------------------- | -------------------------------------------------------------------------------------------------- |
| 1024 字节             | 256 字 ×4：这块栈的可用总量                                                                        |
| 硬件帧 8 字=64B       | Cortex-M 异常进入时**硬件自动**压栈的 R0-R3、R12、LR、PC、xPSR 共 8 个字——任务「出生姿势」的一部分 |
| R4–R11 8 字           | 这 8 个寄存器硬件不自动压，由 FreeRTOS 的 PendSV 路径**软件**补压——首次启动也得先摆好              |
| pxPortInitialiseStack | 端口函数：手工伪造一个「像刚被打断」的初始栈帧，任务第一次被调度就从函数入口跑（ch17 单步亲见）    |
| 帧杂项 16–48B         | `-O0`（不优化）下局部变量、保存的 LR 都老实占栈——「帧肥」=不优化导致栈帧虚胖                       |

实验代码（加进 `main.c`，栈深沿用 256 字；pad 放**内层作用域**，写完就出界让栈复用——打印在块外做，
观测点才干净）：

```c
static void pad_task(void *arg)
{
    (void)arg;
    uart_puts("[pad] start\r\n");
    {
        volatile char pad[900];              /* 换成 1100 再烧一次 */
        for (unsigned i = 0; i < sizeof(pad); i++) {
            pad[i] = (char)i;                /* 写满：每个字节都要真的落栈 */
        }
        uart_puts("[pad] wrote all bytes\r\n");
    }                                        /* 出作用域：帧弹出，SP 回高位 */
    uart_puts("[pad] survived\r\n");
    for (;;) { vTaskDelay(pdMS_TO_TICKS(1000)); }
}

/* main() 里追加：单位是字！256 = 1024 字节 */
xTaskCreate(pad_task, "pad", 256, NULL, 1, NULL);
```

**实验 A 代码走读：**

| 行                                            | 作用                                                    | 值得注意                                   |
| --------------------------------------------- | ------------------------------------------------------- | ------------------------------------------ |
| 内层 `{ volatile char pad[900]; }`            | pad 放内层作用域                                        | 出块即弹栈复用；打印放块外，观测点才干净   |
| 写满循环 `pad[i] = (char)i;`                  | 每个字节都真写                                          | 只写头尾可能恰好躲开栈基魔数（设计意图 1） |
| `vTaskDelay(pdMS_TO_TICKS(1000))`             | 睡 1 秒（把毫秒换算成 tick 数再睡）                     | 让任务活着但不抢 CPU                       |
| `xTaskCreate(入口, 名字, 256, 参数, 1, NULL)` | 六参数：入口函数/名字/栈深（字！）/入参/优先级/句柄出参 | 256 字=1024B——本篇主犯就在第 3 个参数      |

两个设计意图必须说破：

1. **为什么要写满**：栈溢出检测方法二（ch16 主角）只盯栈基 16 字节魔数；只写 `pad[0]`/`pad[899]` 的话，
   落在魔数区的那几个字节可能恰好没被写，越界了也验不出尸。写满 = 证据链完整。
2. **为什么 volatile**：不给 `volatile`，优化器（虽然本工程 `-O0`）可以把没人读的数组整个蒸发——
   「爆栈实验怎么不爆」的第一嫌疑人永远是编译器。

## 实验 B：序章工程现成的高水位实测

工程 `FreeRTOSConfig.h:59` 已开 `INCLUDE_uxTaskGetStackHighWaterMark 1`——这个开关本身就触发栈创建时的
0xA5 涂料（往整块新栈刷 0xA5「未动用」标记字节，任务用掉一个少一个——高水位就是数还剩几个连着的
0xA5；机制在 ch16 拆），所以序章工程的 fast/slow 不用改创建参数就能量。

动手前先排一个坑：**`uxTaskGetStackHighWaterMark(NULL)` 只量「当前任务自己」**——在 monitor 任务里传
NULL，量出来的是 monitor 的栈，跟 fast/slow 毫无关系。要量别人，创建任务时必须把第 6 个参数从 `NULL`
换成句柄指针，监控任务再拿着句柄去问：

```c
static TaskHandle_t h_fast, h_slow;
xTaskCreate(fast_task, "fast", 256, NULL, 2, &h_fast);
xTaskCreate(slow_task, "slow", 256, NULL, 1, &h_slow);

static void monitor_task(void *arg)
{
    (void)arg;
    for (;;) {
        uart_puts("[mon] fast=");
        uart_putdec(uxTaskGetStackHighWaterMark(h_fast)); /* 返回单位：字！ */
        uart_puts(" slow=");
        uart_putdec(uxTaskGetStackHighWaterMark(h_slow));
        uart_puts("\r\n");
        vTaskDelay(pdMS_TO_TICKS(2000));
    }
}
```

**返回值单位也是字**：`tasks.c:6480` 的 `uxCount /= sizeof( StackType_t )` 把字节数换算回字——
CM4F 上除以 4，IDF 上除以 1。同一份监控代码搬去 ESP32，数字含义直接差 4 倍。

> 📖 **术语卡：uxTaskGetStackHighWaterMark（高水位）**
> **是什么**：量「这块栈从创建至今，历史上最少时剩多少」的 API：建栈时整块刷 0xA5，之后从栈的低地址端向上数还**连续**剩几个 0xA5，换算成**字**返回。返回值=历史最小余量，不是瞬时余量。
> **为什么存在**：栈不够是「哪一刻最深哪一刻爆」的小概率事件，瞬时看不出；高水位给出最坏刻度的余量，是配栈深的依据。
> **类比**：河道洪水线：平时水面看不出什么，退潮后岸上的水痕才是历史最高水位。
> ⚠️ 类比边界：它只对「已经发生过的最深」负责——未来更深的调用路径没跑过就量不到；已用区域被恰好写回 0xA5 会漏报（低概率）。

**monitor 代码走读：**

| 行                                    | 作用                                                                |
| ------------------------------------- | ------------------------------------------------------------------- |
| `TaskHandle_t h_fast, h_slow;`        | 任务句柄变量：创建任务时内核回填的「任务身份证」                    |
| `xTaskCreate(..., &h_fast)`           | 第 6 参数从 NULL 换成句柄指针——事后才量得到**别人**的栈             |
| `uxTaskGetStackHighWaterMark(h_fast)` | 按句柄量指定任务；传 NULL 只量「当前任务自己」（上文排过的坑）      |
| 返回值                                | 单位是**字**（tasks.c:6480 除以 sizeof(StackType_t)）——IDF 上是字节 |

`configMINIMAL_STACK_SIZE` 的语义顺带定罪：`FreeRTOSConfig.h:17` 写着 `128`（注释自带「单位：字！」），
Idle 任务创建时就用它（`tasks.c:3704`，静态版在 `tasks.c:8860`）——即 Idle 栈 = 128 字 = 512 字节。
把它当「任务的最低可用栈深」抄进业务任务，512 字节在含 uart 打印的调用链上同样能爆。

## 实验 C：反向坑——把两边的习惯互相抄

**方向一：把这里的 256 抄进 IDF 工程 → 256 字节 → 必崩。** IDF 的 `task.h` 文档原话（主系列廿一章引过）：
"The size of the task stack specified as the NUMBER OF BYTES. **Note that this differs from vanilla FreeRTOS.**"
256 字节连 newlib（嵌入式常用 C 库实现）printf 的第一层格式化帧都铺不开；就算像本工程不用 printf，任务入口 64 字节 +
两层调用也所剩无几。这正是[[2026-08-26-freertos-deep-dive-ch1-from-bare-metal-to-rtos|FreeRTOS（一）]]
1.5 节翻车表里「栈大小给成 128 → 运行崩溃」那条的本板镜像。

**方向二：把 IDF 的 2048 抄进本工程 → 8192 字节 → 不崩，但白吃 7KB。** 单任务 8192B 在 PC 语境无感，
在这块板上是**整个内核堆的 1/8**。把账算足（每任务 = 栈 + TCB + 两次 heap_4 块头与对齐）：

```text
栈申请：2048 字 × 4 = 8192 B，heap_4 加块头 8 B → 8200 B
TCB：sizeof(TCB_t)（本配置待实测，估 ~100–120 B）+ 块头 8 B ≈ 110–130 B
每任务合计 ≈ 8.3 KB；Idle（128 字）+ 头 ≈ 0.6 KB 常驻
configTOTAL_HEAP_SIZE = 64 KB = 65536 B（FreeRTOSConfig.h:18，heap_4 静态数组）
```

| 任务数（每个 2048 字） | 堆占用    | 占 64KB | 下场                                          |
| ---------------------- | --------- | ------- | --------------------------------------------- |
| 2（fast/slow 抄 2048） | ≈ 16.9 KB | 26%     | 能跑，白亏 14KB                               |
| 5                      | ≈ 41.6 KB | 64%     | 吃紧：再加队列/缓冲就开始抠边界               |
| 7                      | ≈ 58.2 KB | 89%     | 剩余 6.6KB，第 8 个任务创建失败               |
| 8                      | > 64 KB   | —       | `pvPortMalloc` 返回 NULL → malloc failed hook |

第 8 行的下场不是猜测：`configUSE_MALLOC_FAILED_HOOK=1`（`FreeRTOSConfig.h:33`）+ `main.c:79-83` 的
`vApplicationMallocFailedHook()` 会打印 `[HOOK] malloc failed!` 并死循环——**爆堆和爆栈在这块板上有不同的
死亡证明书**（ch16 专讲爆栈那份）。给三五个任务各抄一个 2048，就吃掉一半内存——「不崩但白吃」在
[[2026-08-26-freertos-deep-dive-ch19-heap-allocators-comparison|FreeRTOS（十九）]]的分配器语境里还有第二层
代价：heap_4 的空闲链是按块切分的，大块栈让碎片化提前到来（ch19 的碎片实验在 ch18 之后做）。

> 📖 **术语卡：hook（钩子）——两份死亡证明书**
> **是什么**：FreeRTOS 出事时回调你实现的函数：`vApplicationMallocFailedHook()`（`pvPortMalloc` 返回 NULL 时调）与 `vApplicationStackOverflowHook()`（检测到栈越界时调，检测方法 ch16 拆）。相应开关（`configUSE_MALLOC_FAILED_HOOK` 等）置 1 才编入。
> **为什么存在**：嵌入式没有 stderr/init 进程接管后事，死前留一句话全靠钩子；不注册=黑箱猝死。
> **类比**：你的主场：panic notifier / oops 回调链——出事时把控制权交给你注册的处理函数。
> ⚠️ 类比边界：hook 跑在出错现场，必须最短路径（打印+停机）——不能指望它还能正常分配内存或用复杂功能。
