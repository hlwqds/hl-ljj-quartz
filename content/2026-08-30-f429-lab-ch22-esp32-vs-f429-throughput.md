## 目标（先说结论）

- 22 章的积累折算成一句话：**同一条「应用→协议栈→MAC→介质」的路径，F429 上你拥有全部产权，
  ESP32 上你拥有上半截**——两块板跑的是**同一颗 lwIP**，差别全在封装深度。本章用四个维度把这句话
  铺成大表：网络路径、内存、代码量与可控性、调试可达性。
- 吞吐实验的诚实声明（也是教学点）：**WiFi 与以太网的物理层不可比**（空口损耗/重传/聚合（WiFi 把
  多个帧拼成一个大块再发的 A-MPDU 机制）vs 双绞线
  全双工），所以同负载对比量的是「系统级」差异——整机+介质+栈——而**控制变量是协议栈本身**：
  两边同为 lwIP、同 UDP echo 负载、同一台 RPi 做对端。这正是「控制了什么、没控制什么」的实验设计课。
- 收束：三块板（F429/RPi/ESP32）在学习体系里各就各位——两个系列索引的定位宣言在结尾合流。

## 维度一：网络路径——同一颗 lwIP，两种封装深度

| 层                  | ESP32（lwIP 主系列的主场）                                                                     | F429（本系列）                                                                 |
| ------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 介质                | 802.11n 2.4G 空口                                                                              | 100BASE-TX（百兆双绞线电口标准）；RJ45 磁性件=内置网络变压器的网口插座（ch20） |
| 物理层              | RF（射频前端）+BB（基带），闭源 `libnet80211.a`（术语卡见下）                                  | PHY 芯片（LAN8720/8742 待核对），MDIO 可直读（术语卡见下）                     |
| MAC 层              | WiFi MAC 固件闭源；802.11→802.3 转换在黑盒内                                                   | EMAC 寄存器全自写（ch20：MACCR/描述符环全在手）                                |
| 帧交接              | `esp_wifi_internal_tx`（copy 语义，黑盒边界）                                                  | `low_level_output`：pbuf→memcpy→描述符 OWN=1                                   |
| 驱动层              | `wlanif.c`/esp_eth（乐鑫写好）                                                                 | 自写 ethernetif 约 100 行（ch21）                                              |
| 协议栈              | lwIP 2.2.0-dev（IDF 捆绑，Kconfig 裁剪（menuconfig 菜单系统，与内核 Kconfig 同源——你的主场）） | lwIP 2.2.0 同族（自裁 lwipopts.h，ch21）                                       |
| 栈内（pbuf 及以上） | 完全相同的一套源码                                                                             | 同左——**这就是控制变量**                                                       |
| MTU                 | 1500                                                                                           | 1500                                                                           |

> 📖 **术语卡：libnet80211——ESP32 的 WiFi 黑盒固件**
> **是什么**：乐鑫预编译的静态库（.a 文件）：WiFi 的 MAC 层处理+基带（BB，Baseband：把比特映射成 2.4GHz 空口波形的数字部分）+射频（RF，模拟前端）控制全在里面，只留 API 给 esp_wifi 调。
> **为什么存在**：802.11 协议（信标/关联/重传/聚合/省电）复杂且涉射频法规认证，厂商以二进制交付核心，节省 Flash 且合规省事。
> **类比**：显卡/网卡的闭源固件 blob——你能调用它，不能看它。
> ⚠️ 类比边界：服务器网卡固件只是数据面加速，协议仍在内核里；libnet80211 连 802.11→802.3 的帧转换都在盒内，协议下半截整个不可见。

> 📖 **术语卡：MDIO/MDC——PHY 的管理总线**
> **是什么**：两条线的小总线（MDC 时钟+MDIO 数据），IEEE 802.3 定义，用来读写 PHY 芯片内部寄存器：链路在不在、速率多少、自协商结果全在里面。
> **为什么存在**：RMII 只搬数据，PHY 的配置与状态查询需要独立通道——相当于 PHY 的「控制台口」。
> **类比**：ethtool 查链路信息的底层：内核 mdio_bus 框架走的就是这条总线（你的主场在服务器侧天天间接用）。
> ⚠️ 类比边界：内核 mdio_bus 是带设备模型的框架；裸机上 MDIO 是 F429 按时序位拼出来的几行读写代码（ch20 手法）。

读法：从下往上是「产权分界线」的连续下移——ESP32 用户从 pbuf 开始拥有（
[[2026-08-26-lwip-deep-dive-ch4-pbuf-anatomy|lwIP（四）：pbuf]]及以上），F429 用户从 RJ45 变压器
开始拥有。「第四弹」顿悟：ESP32 上 `esp_wifi_internal_tx`（ESP32 上帧进入 WiFi 固件的那扇门，函数名直译「WiFi 内部发送」）那次 copy（lwIP ch18 走读的重点），在
F429 上是你自己 `memcpy` 进 `tx_b[i]` 的那一行——**同一个设计决策（TX 拷贝保生命周期），一边在
闭源库里，一边在你手写代码里**。

> ⚠️ **类比边界**：「产权」是学习视角的说法：ESP32 的「下半截」并非禁地——gdb 还能 attach、黑盒的
> 导出符号还在、menuconfig 选项还在，只是停在 API 合同层；F429 的「全产权」也只到硅皮为止——MAC 是
> 硬核 IP，内部的硬件逻辑同样不可见。产权深度是连续谱，不是二进制。

## 同负载吞吐测量方案（全部待实测）

| 步骤 | 内容                                                                                  | 工具（RPi ch08）                |
| ---- | ------------------------------------------------------------------------------------- | ------------------------------- |
| 0    | 链路基线：笔记本↔RPi 千兆直连打满                                                     | `iperf3 -u -b 0`（TCP 对照）    |
| 1    | F429：自研 UDP 发送器定速打流（裸机无 iperf3 客户端）                                 | RPi `tcpdump -w` 抓满离线算     |
| 2    | ESP32：IDF 自带 iperf 组件真连 RPi 服务端                                             | `iperf3 -s`（协议兼容性待实测） |
| 3    | 反向：RPi 打流，两板各自回 echo，测收向                                               | 自定长 UDP 回显                 |
| 4    | RTT：双向 ping + F429 侧 DWT（CPU 周期计数器，ch21 已开卡）周期计时（ch21 手搓 ping） | tcpdump 时间戳交叉验证          |

**命令拆解：** `iperf3 -u -b 0 -c <对端IP>`（你的主场，但 `-b 0` 这个坑值得点名）

| 部分      | 作用                                                        |
| --------- | ----------------------------------------------------------- |
| `iperf3`  | 打流测速工具：主动发包、按秒报速率——步骤 0 用它量链路基线   |
| `-u`      | 用 UDP 而非默认 TCP——与两板实验同负载，口径对齐             |
| `-b 0`    | 目标带宽 0=不限速（UDP 默认只打 1Mbit/s，不显式放开就白测） |
| `-c <IP>` | client 模式，对端 IP（笔记本↔RPi 互为两端）                 |
| TCP 对照  | 同命令去掉 `-u -b 0`：默认 TCP 单流，量链路的另一个极限     |

**iperf3 报告字段速查（UDP 模式）**：

| 字段                   | 含义                                                  |
| ---------------------- | ----------------------------------------------------- |
| `Interval`             | 统计区间（默认每秒一行）                              |
| `Transfer` / `Bitrate` | 该区间的字节数 / 折算速率——吞吐表要填的数             |
| `Jitter`               | 相邻包到达时间差的平滑均值（仅接收端一行有）          |
| `Lost/Total Datagrams` | 丢包数/总包数与丢包率（仅接收端）——UDP 实验的核心指标 |
| `Retr`                 | TCP 重传次数——TCP 对照行才出现                        |

**命令拆解：** `iperf3 -s`（RPi 侧服务端）

| 部分     | 作用                                                 |
| -------- | ---------------------------------------------------- |
| `iperf3` | 同上                                                 |
| `-s`     | server 模式：监听默认 5201 端口，等两板/笔记本来打流 |

**注意**：ESP32 IDF 自带的是 iperf（2 代协议）组件，与 iperf3 服务端**不保证互通**——待核对 #2 正是它。

**命令拆解：** `sudo tcpdump -i eth0 -n -w f429-udp.pcap udp`（你的主场，这次 tcpdump 当测量仪不是看戏）

| 部分               | 作用                                               |
| ------------------ | -------------------------------------------------- |
| `tcpdump`          | 抓包神器：这里不是打印给人看，是原样落盘给实验记账 |
| `-i eth0`          | 听 RPi 的有线口                                    |
| `-n`               | 不做 DNS 反查                                      |
| `-w f429-udp.pcap` | 不打印，写 pcap 文件，事后离线统计                 |
| `udp`              | 只留 UDP——F429 自研发送器打的就是 UDP              |

**离线对账**：`tcpdump -r f429-udp.pcap | wc -l` 数出收到的包数，与 F429 串口自报的发送数相减=丢帧率。

预期**形态**（不给数值）：F429 百兆线速的理论天花板 94.1Mbps（100M 全双工单向；口径=以太成帧开销折算后的有效载荷上限，精确值随帧长与统计口径微差，对账时再核）；lwIP 小内存配置
（PBUF_POOL 8 深、自旋等环）大概率先于线速见顶——瓶颈逐层归因的方法正是 lwIP ch17 实验d 的管道
公式（吞吐上限=ISR 提交速度与消费速度的最小值）。ESP32 侧对照 lwIP ch18 的官方口径表（屏蔽箱 UDP
85Mbit/s、开放环境 30Mbit/s）——它比 F429 高还是低不重要，重要的是**每边都知道自己的瓶颈在哪一层**。
F429 的丢帧有发票（DMASR 的 RBU 位），ESP32 的丢帧在空口无凭据——可观测性差异本身就是结论。

> 📖 **术语卡：DMASR 的 RBU 位——丢帧的发票**
> **是什么**：ETH 外设 DMA 状态寄存器（DMA Status Register）里的一格：接收环上已无可还的描述符（CPU 还没腾出槽）时硬件置位，含义是「收包时环空了，这帧丢了」。
> **为什么存在**：以太网是尽力而为的介质，硬件不替你重试——丢就丢，但留下一个可统计的凭据。
> **类比**：`ip -s link` 里的 RX-dropped/`nospace`：Ring buffer 满，内核丢帧——你的主场。
> ⚠️ 类比边界：Linux 侧有 ethtool -S 的整棵指标树；裸机只有 DMASR 几个状态位，且写 1 清除，得自己攒成计数器。

## 维度二：内存——两套地址空间的世界观

| 维度          | F429                                                                       | ESP32                                                                                                                     |
| ------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 主 RAM        | 192KB SRAM（三块拼成，矩阵共享，ch05）                                     | 约 520KB DRAM（IDF 典型可用堆约 300KB 量级，待实测）                                                                      |
| 特殊 RAM      | 64KB CCM：CPU 专属，**ETH DMA 不可达**（ch13）                             | PSRAM（外挂伪静态 RAM，走 SPI/QSPI 总线：容量大、慢一档；板上若有）：caps 分配，WiFi 缓冲可入（lwIP ch18 的 by_ref 路径） |
| DMA 缓冲选址  | 描述符+帧缓冲钉死 .bss（SRAM），CCM 是毒药（ch21 铁律）                    | `heap_caps_calloc(MALLOC_CAP_DMA)`（lwIP ch17 同款方言）                                                                  |
| lwIP 内存模式 | 裸机默认静态池：`PBUF_POOL_SIZE` 数组编译期定死                            | IDF 全堆化：`MEM_LIBC_MALLOC=1`（lwIP 的 mem 堆直接用 libc malloc）+`MEMP_MEM_MALLOC=1`（memp 各池也并入堆）（lwIP ch5）  |
| 测量手段      | map 文件（链接器输出的符号/地址/大小清单）+ `lwip_stats`（`LWIP_STATS=1`） | `esp_get_free_heap_size()`（查剩余堆总量）/`heap_caps_print_heap_info`（按 caps 分类打印各堆用量）                        |
| 网络栈成本    | 待实测：移植前后 `mem_free`/池余量差                                       | 待实测：esp_wifi start 前后 heap 差（几十 KB 量级，lwIP ch18 口径待复测）                                                 |

> 📖 **术语卡：IDF heap_caps——带能力标签的内存分配**
> **是什么**：乐鑫 IDF 的多堆分配器：把物理上分散的内存（内部 DRAM、DMA 可达区、PSRAM……）注册成多个堆，分配时按「能力掩码」挑堆——`heap_caps_calloc(n, size, MALLOC_CAP_DMA)` 只会从 DMA 可达的内存里拿。
> **为什么存在**：ESP32 的内存不在一个平坦地址空间——DMA 能到哪、几位总线、能否执行，因块而异；标签让驱动开发者用一句参数声明需求，「放哪」变成一行代码。
> **类比**：`kmalloc(GFP_DMA)` 的近亲：按约束挑内存区域（服务器侧你的主场）。
> ⚠️ 类比边界：GFP\_\* 是一组互斥方向标志；caps 是多个正交能力的位掩码（DMA 可达/内部/SPIRAM/可执行……），可一次要求多个组合。

两行结构性差异值得背下来：**F429 的内存问题是「放哪」（拓扑），ESP32 的内存问题是「够不够」（容量）**
——CCM 的存在让「缓冲放哪」变成总线可达性问题；而 ESP32 的 caps 体系让「放哪」变成一行参数，
代价是你不再感知底下发生了什么。这正是[[2026-08-26-freertos-deep-dive-ch20-idf-heap-and-caps|FreeRTOS（二十）：IDF 堆与 caps]]
与 ch05 两章合起来读才完整的地图。

测量方案：`cloc` 分层统计两工程（F429：`~/stm32/f429-freertos/src`+自移植 lwip 排除协议栈本体；
ESP32：主系列 lwip-labs 工程 + `components/` 只计调用不重编的量），全部待实测，框架如下：

**命令拆解：** `cloc ~/stm32/f429-freertos/src --csv`（建议形态，两工程各跑一次）

| 部分     | 作用                                                   |
| -------- | ------------------------------------------------------ |
| `cloc`   | count lines of code：按语言统计文件数/空行/注释/代码行 |
| `<目录>` | 要统计的工程目录（分层口径按下表）                     |
| `--csv`  | 输出 CSV，方便并进对照表                               |

| 件            | F429 行数（待统计）  | ESP32 行数（待统计）                                                       | 谁写的       |
| ------------- | -------------------- | -------------------------------------------------------------------------- | ------------ |
| MAC/PHY 驱动  | ch20 约 200 行       | 0（esp_eth 内置/闭源库）                                                   | 你 vs 乐鑫   |
| ethernetif    | ch21 约 100 行       | 0（wlanif.c）                                                              | 你 vs 乐鑫   |
| sys_arch      | ch21 升级版约 100 行 | 0（IDF 集成）                                                              | 你 vs 乐鑫   |
| bring-up 应用 | 约 50 行             | 约 15 行（esp_netif 一条龙——IDF 的网络接口管家：WiFi/以太网/PPP 统一收口） | 你 vs IDF 宏 |
| 协议栈本体    | lwIP 数万行（同款）  | lwIP 数万行（同款）                                                        | 两边同源     |
| 射频/MAC 固件 | 无此物               | `libnet80211.a`（MB 级预编译，闭源）                                       | 不可见       |

可控性的量化读法：**你的代码/运行在你板上的代码** 这个比值。F429 上分母几乎全是可见源码；ESP32
上分母包含一个 MB 级黑盒。没有对错——产品工程选后者的生产率，学习路径需要前者的透明度。

## 维度四：调试可达性——从单步进自己代码到黑盒标注

| 维度       | F429                                                                                                          | ESP32                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 单步       | DAP 进自己写的 `mdio_read`/`low_level_output`（[[2026-08-30-f429-lab-ch17-pendsv-single-step\|ch17]] 方法论） | 进不去 libnet80211；openeth（QEMU 里模拟出来的以太网 MAC 外设——仿真外设无黑盒）可单步（QEMU）                  |
| 寄存器体检 | `mdw 0x40028000/0x40029000` 活体读（ch20 表）                                                                 | WiFi MAC 寄存器不可见，仅 esp_wifi API 层                                                                      |
| 环可视化   | 描述符环可 `mdw` 快照（OWN 位串逐槽读）                                                                       | 只能在 `linkoutput` 外包一层观察点（lwIP ch17/18 手法）                                                        |
| 物理层证据 | piscope（RPi GPIO 当逻辑分析仪用的采样软件）/LA（logic analyzer，逻辑分析仪）抓 MDC/MDIO（≤2.5MHz 可采）      | 空口抓包需专门设备（RF 系列范畴）                                                                              |
| 波形对照   | ch09 的穷人 LA 直接复用                                                                                       | 无线侧无对应物                                                                                                 |
| 方法论     | 序章七条 + 断点二分全程适用                                                                                   | lwIP ch18 的「黑盒标注法」（nm 符号边界——nm=ELF 符号表列举器，你的主场：黑盒没源码但符号可查，以符号名划地界） |

**命令拆解：** `mdw 0x40029000`（OpenOCD 会话；gdb 里等价 `x/1wx 0x40029000`）

| 部分         | 作用                                                                 |
| ------------ | -------------------------------------------------------------------- |
| `mdw`        | memory display word：按 32 位字读内存/外设寄存器（活体读，不打断点） |
| `0x40029000` | ETH 外设 DMA 侧寄存器基址（0x40028000 起=MAC 侧——ch20 表）           |

**你会看到**：描述符 OWN 位串——每个 d0 字的最高位 1=DMA 占着、0=CPU 的，逐槽扫一遍就是环的活照片。

一句话：**F429 的排障是「往里走」（一直走到描述符位），ESP32 的排障是「划边界」（黑盒之外全查清，
黑盒之内只认符号和日志）**——序章+ch17 的方法论与 lwIP ch18 的方法学在这里殊途同归：先分层判尸，
再决定往哪层下钻。

## 三块板的角色收束

- **F429——完全产权的实验机**：从 VOS（内核电压档位——内部稳压器的输出档，主频上不去先查它）到 DMA 描述符 OWN 位，出任何事都能剥到底。五阶段走完，
  它教会的是「下界」：一切 SDK 便利的下面，寄存器和总线到底长什么样。
- **RPi——仪器与对端**：i2cdetect（I2C 总线设备扫描——你的主场）主机、piscope 波形、tcpdump/iperf3 网络之眼——它是 Linux 全栈世界
  派来的「另一方」，从[[2026-08-30-rpi-lab-ch05-request-irq-vs-nvic|RPi ch05 的 request_irq]]到本章
  tcpdump，你在两套世界观（寄存器/内核）之间反复翻译。
- **ESP32——生产力平台**：闭源射频固件+厚 SDK，两天出产品，底层黑盒。FreeRTOS 系列教「任务怎么
  跑起来」，lwIP 系列教「包怎么飞起来」——都以它为舞台；本系列补上「地板下面是什么」。

三个系列的定位宣言合流：本系列索引第一行写的是「从寄存器到 RTOS 的对照之路」——此刻对照完成，
你已经拥有同一条包路径的三种产权深度：**在 F429 上能修到最后一层，在 ESP32 上能讲清哪层修不了，
在 RPi 上能把两者都抓包作证**。这就是 22 章想交付的全部。
