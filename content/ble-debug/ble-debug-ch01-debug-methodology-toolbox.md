## 1.1 三个现场：换了对象，换了哪些坑

先看三个现场（**教学复盘案例，取材自常见故障模式综述**——团队与产品均属合成，把多起常见故障折进同一条叙述线，便于提炼方法）。

**现场 A：iPhone 扫不到，Android 扫得到**。某团队的新款传感器，App 团队反馈 iPhone 上列表里死活不出现，Android 手机上却一直好好的。固件团队把广播数据逐字节审了两周，坚称「包是对的——Android 能看到就是证明」。最后用 nRF Connect 在 iPhone 上打开「按广播类型过滤」一看：App 默认只显示名称完整的设备，而这颗固件的广播包里**设备名被放在 Scan Response 里，且 iOS 扫描默认更「懒」**（后台扫描不主动发扫描请求），名字永远回不来。这是广播结构与手机扫描策略的合谋（第四章的案例类型），不是「包是错的」。

**现场 B：量产遥控器随机失联**。电视遥控器（BLE HID）在办公室好好的，到用户家里隔一会儿就没反应，放回桌上又自己恢复。主机侧日志显示周期性 supervision timeout，复现毫无规律。最后空口抓包结合现场勘查给出答案：2.4 GHz 频段在用户家里的路由器信道切换、微波炉启动时段被大量占用，而固件的连接参数把重试余量压得太紧——链路层没有给对抗丢包留出时间预算（第五、七、八章的案例类型）。

**现场 C：电池产品续航差五倍**。规格书承诺一颗 CR2032 用一年，实测样品三周就没电。软件侧查了睡眠代码、任务调度、外设时钟，全部「看起来睡着了」。功耗仪一挂真相大白：广播间隔配置与规格不符（固件里两处代码打架，配置被后者覆盖），设备实际在以 20 ms 间隔狂发广播——每一处都「在正常工作」，只是工作得太勤快（第十章的案例类型）。

三个现场的共同点：团队最先动用的都是软件侧排查——而且都不算白干。把三类症状的两侧排查对照成表（与 [[wifi-hw-debug-ch01-debug-methodology-toolbox|WiFi 调试（一）]] 同款框架，对象换成 BLE）：

| 症状                     | 软件侧你排到底时查过的     | 硬件侧/空口侧剩下的真相                       | 本系列哪章     |
| ------------------------ | -------------------------- | --------------------------------------------- | -------------- |
| iPhone 扫不到            | 广播数据逐字节审、App 重装 | 广播结构 vs 手机扫描策略、Tx 功率与天线、信道 | 第四、八章     |
| 随机失联                 | 重连逻辑、保活、日志反复审 | 2.4G 占用、链路预算、连接参数余量             | 第五、七、八章 |
| 续航差一个量级           | 睡眠代码、任务调度审查     | 广播/连接参数占空比、DCDC 配置、漏电流        | 第十章         |
| 点连接就失败（偶发成功） | 重试逻辑、加密配置审查     | 连接请求被空口丢包吞掉、频偏/灵敏度边缘       | 第五、八章     |

与 WiFi 调试系列的分工，一张表钉死：

| 维度     | [[wifi-hw-debug-ch01-debug-methodology-toolbox\|WiFi 调试（一）]] | 本系列                                         |
| -------- | ----------------------------------------------------------------- | ---------------------------------------------- |

| 方法     | 症状分类 × 分层取证 × 证据链                                      | **完全同源**，直接移植                         |
| 主力工具 | iw/wpa_cli/tcpdump                                                | bluetoothctl/btmon/nRF Sniffer + Wireshark     |
| 特有变量 | 驱动与固件版本                                                    | **手机机型与系统版本**（它既是测试仪又是变量） |

## 1.2 症状五分类：把「蓝牙不行」翻译成排查路径

用户说「蓝牙连不上/不好使」没有排查价值，第一步是翻译。可感知症状归成五类（与 [[ble-debug|系列索引]] 的章节地图一致），每类给「第一反应动作」与「最容易走的弯路」：

| 症状分类      | 典型表现                                         | 第一反应动作                                                                  | 最容易走的弯路                                                           | 对应章节                                                                                       |
| ------------- | ------------------------------------------------ | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| **扫不到**    | App 列表没有设备 / 时有时无 / 只有部分手机能扫到 | 双手机对照（不同品牌+系统）扫一遍；nRF Connect 看「是否广播、广播内容是什么」 | 只用一台手机下结论；反复重烧固件碰运气；忽略 iOS 与 Android 扫描策略差异 | [[ble-debug-ch04-advertising-packets\|第四章]]                                                 |
| **连不上**    | 点连接转圈失败 / 偶发成功 / 卡在服务发现         | 分阶段取证：广播在吗→连接请求发了吗→连接建立了吗→加密过了吗→服务发现完了吗    | 上来就恢复出厂/重配对，破坏复现条件；把 App 超时当成协议失败             | [[ble-debug-ch05-connection-parameters\|第五章]]                                               |
| **掉线/不稳** | 用着断、口袋里断、特定距离断                     | 拉断连事件时间线（手机日志/固件日志），找 supervision timeout 还是主动断开    | 调大重连重试把症状藏起来；只看一端日志就定责                             | [[ble-debug-ch07-disconnect-cases\|第七章]]                                                    |
| **慢/延迟大** | 数据刷新慢、响应迟钝、大批量传输卡顿             | 把 conn interval/latency、MTU、PHY 模式一个个记账，先算理论上限再谈实测       | 用「感觉」代替测量；直接怪手机性能                                       | [[ble-debug-ch09-throughput-latency\|第九章]]                                                  |
| **功耗/认证** | 续航与规格差一个量级；过不了认证预测试           | 功耗仪挂电流曲线对账；预测试逐条读 fail 项与限值口径                          | 用万用表找微安级平均电流；盲目改 RF 参数硬压 fail                        | [[ble-debug-ch10-ble-power-debug\|第十章]]、[[ble-debug-ch11-qualification-pretest\|第十一章]] |

三条读表说明。其一，**分类依据是用户可感知的现象，不是根因**——同一个根因（比如广播包结构错误）可以同时呈现为「扫不到」「连不上」「连接慢」三类症状；分类只是入口，下钻才是路。其二，每类的第一反应动作都在 1.3 的 L1/L3 层，成本几乎为零——先花十分钟，再谈动手。其三，弯路里有一条 BLE 特有的：**手机端既是你的测试仪，又是最大的变量**——同一固件在不同品牌、不同系统版本的手机上表现可以完全不同，1.5 的纪律一就是为此而设。

五分类的分诊顺序画成一条流程，前两步永远免费：

```text
「蓝牙不行」
   │
   ├─ 换一台不同品牌的手机再扫一遍 ──结果不同──▶ 分类收敛为「扫不到」
   │                                            且第一嫌疑人是手机扫描策略
   │
   ├─ nRF Connect 关掉过滤器，看目标出不出来 ──不出来──▶ 「扫不到」（固件/空口侧）
   │                                            出来了 ──▶ 试连接，看卡在哪一步
   │                                                        │
   │                          ┌──────────────────────────────┼─────────────────┐
   │                          ▼                              ▼                 ▼
   │                     连接失败/超时                  连上但服务异常      用着用着断
   │                     「连不上」                        GATT 问题        「掉线/不稳」
   │
   └─ 上述全正常，只是「慢」或「费电」 ──▶ 量化（conn 参数账 / 电流曲线）
                                          「慢/延迟大」「功耗/认证」
```

> [!tip] 先分类，再下钻
> 拿到问题先问一句：这属于五类里的哪一类？答不上来就回 L1 把现象钉死（1.3.1）——「iPhone 上有、Android 上没有」和「所有手机都没有」是两个不同的案子，别让口头的「蓝牙不行」把它们混在一起。

## 1.3 分层取证框架：L1 到 L4

五分类解决「从哪类入手」，分层解决「证据到哪找」。框架从 [[wifi-hw-debug-ch01-debug-methodology-toolbox|WiFi 调试（一）]] 原样移植，只是每一层的「管子」换成蓝牙的：从信息最便宜的一层开始，每层回答一个问题，回答不了才往下走。

```text
L1 观测层     —— 手机 App 看到的：广播名/RSSI/服务列表/断连频次
L2 空口层     —— 嗅探器看到的：广播包/连接建立/数据包/断连原因
L3 主机栈层   —— btmon/hcidump/NimBLE 日志：HCI 命令与事件流
L4 控制器射频层 —— 物理层健康吗：功率/灵敏度/频偏/晶体/共存
```

总表先行，逐层展开在后：

| 层              | 回答的问题     | 主力工具                                                                    | 取证成本                    | 输出证据                    | 证据可信度与边界                                   |
| --------------- | -------------- | --------------------------------------------------------------------------- | --------------------------- | --------------------------- | -------------------------------------------------- |
| L1 观测层       | 现象是什么样   | nRF Connect（Android/iOS）、LightBlue、系统蓝牙设置                         | 极低（分钟级，¥0）          | 带机型标注的现象基线        | 指示器不是根因；App 过滤策略会伪造「扫不到」       |
| L2 空口层       | 空口发生了什么 | nRF Sniffer for BLE + Wireshark、Ellisys/Frontline（专业档）                | 低~高（几十元板子到专业仪） | 帧级 pcap                   | 时间因果最可信；嗅探器只守一个信道，有视野盲区     |
| L3 主机栈层     | 主机栈怎么说   | `btmon`/`hcidump`（Linux）、NimBLE/Bluedroid 日志（ESP-IDF）、手机 HCI 日志 | 低（¥0，需设备访问权）      | HCI 命令/事件流、协议错误码 | 栈只报告它知道的；HCI 错误码一旦出现即是决定性线索 |
| L4 控制器射频层 | 物理层健康吗   | 频谱仪、示波器 + 电流探头、RF 测试盒/综合测试仪                             | 高（仪器/租借/送测）        | 可与限值对比的测量数值      | 最权威，但测量口径错误会造成「权威的错误」         |

### 1.3.1 L1 观测层：先把现象钉死

十分钟、零成本，把「不行」变成带机型标注的数据。主力是两台手机 App：

| 动作                               | 看什么                                                | 注意                                          |
| ---------------------------------- | ----------------------------------------------------- | --------------------------------------------- |
| nRF Connect「Scanner」页           | 目标设备出不出来、广播名/RSSI/广播类型完整与否        | 注意 App 自带名称/格式过滤器，先全部关掉      |
| LightBlue（iOS）对照               | iPhone 视角下同一目标的表现                           | iOS 扫描行为与 Android 不同，结果不同不是故障 |
| nRF Connect 设备详情展开           | 广播原始字节（Advertisment raw data）、服务 UUID 列表 | 对照固件代码里写的广播结构逐字节核对          |
| 连接后「Service/Characteristic」树 | GATT 结构可见性、可读/可写/notify 标志                | 为第五、六章的 GATT 问题提供第一手现象        |

L1 的产出同样是一条**基线**：什么手机、什么系统版本、距离多远、什么环境（办公室/家里/产线），现象精确到「哪台设备、哪个时刻、什么表现」。它是 1.5 纪律二的前提，也是后面每层验证「改动是否有效」的对照组。

L1 的可信度边界要背下来：**App 列表是「扫描策略 + 过滤器 + 栈行为」的合成结果，不是空口的实况转播**——iOS 后台扫描不发扫描请求、看不到 Scan Response，Android 各厂商对后台扫描的节流策略各不相同；RSSI 值不同手机没有可比性（校准差异 + 天线方向），只看趋势不看绝对值；「信号格数/连接质量」类 UI 指示是用户体验刻度，不是工程数据。

> [!warning] L1 的最大陷阱
> 现象没钉死就开始改：重烧一版固件「好像能扫到了」、换个位置「似乎稳了」——全部作废。没有「哪台手机、什么版本、什么距离」的基线，你只是在掷硬币，而 BLE 的手机端变量恰好特别多。

### 1.3.2 L2 空口层：旁听电磁波上的真话

BLE 的每个动作——广播包、扫描请求/响应、连接建立、数据交互、断连——都写在空口上。一块 nRF52 级开发板刷上 nRF Sniffer for BLE 固件，配上 Wireshark，就能旁听全部过程（完整操作在第四章展开）：

| 能回答的问题                                 | 在包里看什么                                   |
| -------------------------------------------- | ---------------------------------------------- |
| 设备到底有没有在广播？在哪些信道？间隔多少？ | ADV_IND 出现的信道（37/38/39）与时间间隔       |
| 手机有没有发扫描请求？设备响应了吗？         | SCAN_REQ / SCAN_RSP 对                         |
| 连接是谁发起的？连接参数是多少？             | CONNECT_IND 里的 conn interval/latency/timeout |
| 数据交互/加密在哪一步停住？                  | LL 层与 ATT/PDU 序列的最后成功帧               |
| 断连是谁发起的？原因码是什么？               | LL_TERMINATE_IND 或 supervision timeout 的缺席 |

成本与可信度：几十元级板子（nRF52 DK / dongle / 部分国产开发板）+ 免费的 Wireshark，外加半天到一天学会 BLE 帧解析与过滤；输出是帧级 pcap，**时间戳精度与因果可信度全场最高**。三条边界：嗅探器**一次只守一个广播/数据信道**，连接建立后要跟随跳频（nRF Sniffer 会自动跟随，但跟随失败会整段丢包），「pcap 里没有」不等于「空口没发生」；加密链路的数据内容看不到（拿到密钥后部分工具可解密，第四章给方法与边界）；抓包点离被测设备越远，看到的越是双方视角的并集。

工具选型一句话：嗅探硬件（能跑嗅探固件的 nRF52 级板/dongle，手头的开发板刷固件即可）+ 解析软件（Wireshark 加 nRF Sniffer 插件脚本，均免费）——部分厂商 IDE 自带等价抓包能力，格式多为专有，跨工具分享时转 pcap。选购与刷机的完整步骤在第四章给（含加密链路的解密方法与边界）。

### 1.3.3 L3 主机栈层：协议栈的自述

主机栈自己也有一份说法——HCI 命令与事件流、协议层错误码：

| 环境         | 工具与入口                                                 | 能看什么                                   |
| ------------ | ---------------------------------------------------------- | ------------------------------------------ |
| Linux        | `btmon`（HCI 流监控）、`bluetoothctl`、`btmgmt`、`hcidump` | 控制器上报的事件、主机下发的命令、错误码   |
| ESP-IDF      | NimBLE（`bt` 日志模块）或 Bluedroid 的日志与回调事件       | 协议栈状态机、GATT 事件、断连原因码        |
| Android 手机 | 开发者选项「蓝牙 HCI 信息收集日志」，导出 btsnoop_hci.log  | 手机侧完整 HCI 流，可用 Wireshark 直接打开 |
| iOS          | sysdiagnose 里附带蓝牙相关日志（概念级，深入受限）         | 有限：连接事件与错误，远不如 Android 透明  |

成本与可信度：Linux 侧 ¥0；输出是 HCI 命令/事件流——**HCI 错误码（如 Connection Failed to be Established、Command Disallowed）一旦出现，基本就是决定性线索**（错误码速查在第二章 2.6）。边界同样要背：主机栈只报告它知道的事，控制器内部（LL 重传、物理层重试）对主机基本不可见，L3「一切正常」不等于链路健康；btsnoop 的 HCI 日志记录的是**主机与控制器的对话**，不是空口——它看不到对端设备的广播包；iOS 的透明度刻意受限，把 iOS 当「只能看现象」的 L1 仪器更符合实际。

### 1.3.4 L4 控制器射频层：物理层的体检报告

L1~L3 的证据都指向物理层时，才轮到这一层。能看的：实际发射功率、频偏/调制质量、接收灵敏度、邻道与杂散、发射电流毛刺、2.4G 共存表现（与 WiFi 的 AFH/共存机制见 [[ch14-interference-coexistence|射频入门（十四）]]）。工具与口径：频谱仪（功率/杂散）、蓝牙 RF 综合测试仪（灵敏度/调制参数，按 Bluetooth RF Test Specification 口径）、示波器 + 电流探头（电源毛刺）；板级排查先做传导测量（U.FL 转 SMA 工装），晶振频偏问题见 [[ch11-crystal-clock|射频入门（十一）]] 的 dB/频率语言。

成本与可信度：全场最高；输出是可与 datasheet 与 Bluetooth Core Spec RF 测试限值逐条对比的数值。但**测量口径错误会造成「权威的错误」**：传导还是辐射、测试模式进对了没有、限值适用哪条规范——口径错了结论全错（第十一、八章反复强调）。同样适用「测」与「改」的区分：拿仪器测一次是取证，看到频偏超标就直接改晶振布局，是在证据链没闭合时烧钱。

### 1.3.5 症状 → 起始层判定表

| 症状                       | 建议起始层 | 理由                                               | 典型升级路径                |
| -------------------------- | ---------- | -------------------------------------------------- | --------------------------- |
| 扫不到（所有手机都扫不到） | L2         | 先确认空口上有没有广播包，再谈固件逻辑             | L2 → L4（功率/天线）        |
| 扫不到（仅部分手机）       | L1         | 手机扫描策略差异本身就是第一嫌疑人                 | L1 → L2（广播结构）         |
| 点连接失败                 | L2         | CONNECT_IND 发出去没有、对端响应没有，帧级看最直接 | L2 → L3 → L4（频偏/灵敏度） |
| 连接上了但服务发现失败     | L3         | GATT 交互错误码在主机栈最清楚                      | L3 → L2                     |
| 频繁掉线                   | L3 + L2    | 断连原因码与空口时间线互为证人，先对时再定责       | L3 → L2 → L4                |
| 慢/延迟大                  | L1 + L3    | 先记 conn 参数账，再实测吞吐                       | L3 → L2 → L9 章实测         |
| 续航与规格差太远           | L3         | 先看广播/连接参数实际配置，再上功耗仪              | L3 → L4（电流曲线）         |
| 配对/加密失败              | L3         | SM 层错误码在 HCI 流里                             | L3 → L2（配对包）           |
| 特定位置/时段才发生        | L1         | 位置/时间相关性本身就是证据                        | L1 → L2（占用观测）→ L4     |
| 预测试 fail                | L4         | 这一类起点就在物理层（传导测量）                   | L4 → 送正式资质实验室       |

> [!tip] 分层是「默认成本序」，不是死序
> 手头已有日志权限时，先扫一眼 L3 自述再上抓包完全合理；两层的证据本来就要对时互证。原则始终只有一条：**先便宜后贵，别跳着花**。

## 1.5 调试纪律五条

五条纪律从 [[wifi-hw-debug-ch01-debug-methodology-toolbox|WiFi 调试（一）]] 移植，并按 BLE 的特性改写。每个「查了两周不收敛」的案子，事后复盘几乎都栽在其中一条上：

| #   | 纪律               | BLE 特化的反面案例（教学复盘口径）                                                                | 落地做法                                                                                   |
| --- | ------------------ | ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| 一  | 每份证据标注测试机 | 「用户说连不上」——哪台手机、什么系统、App 什么版本？iOS 与 Android 行为不同，混在一起等于没有证据 | 每条记录写清：机型/系统版本/App 版本/距离/环境；多机型矩阵是千元档第一投入的理由           |
| 二  | 一次只改一个变量   | 同时换了手机、刷了固件、挪了距离——「变好了」，复发时不知道该回滚哪一个                            | 每轮实验只动一个旋钮；手机端变量最多，优先钉死它（固定同一台测试机做全部对照）             |
| 三  | 先记录基线         | 「之前好像也没多差吧」——没有基线，改动效果永远无法判定                                            | 动手前先跑一轮标准取证（双手机扫描截图 + 广播包 dump + btmon 片段），输出存档              |
| 四  | 对照实验           | 手上只有坏机，看什么都觉得异常                                                                    | 好机 vs 坏机同场对比；同一固件 iOS vs Android 对比；同一手机前台 vs 后台扫描对比           |
| 五  | 证据链可复现       | 案子破了，三个月后复发，没人记得当时的抓包过滤式、手机版本与固件 commit                           | 每个案子留「取证记录 + 环境清单」（固件版本、手机列表、嗅探器固件版本、pcap 文件与过滤式） |

五条共同服务一个目标：**证据链闭合**——从现象到根因的每一步都有记录、可重放、可反驳。蓝牙比 WiFi 多一条隐性纪律藏在第一条里：**手机厂商的栈行为是你无法控制也不透明的黑盒**，所以「换一台手机试」在 BLE 调试里的地位，相当于 WiFi 调试里「换一张网卡试」——便宜、快速、信息量大。

## 本章小结

- **症状五分类**：扫不到、连不上、掉线/不稳、慢/延迟大、功耗/认证——分类依据是可感知现象而非根因；每类的第一反应动作都在 L1/L3 层，成本近零（1.2 总表）。
- **分层取证 L1→L4**：手机观测钉现象（标测试机）、空口嗅探看帧（因果）、主机栈听自述（HCI 错误码）、控制器射频做体检（与限值对比）——取证成本从低到高，各层可信度边界（1.3 总表）比各层工具更重要。
- **改板子永远放最后**：与 WiFi 系列同一条成本曲线；L4 里「测」是取证、「改」是决策，证据链没闭合不动烙铁。
- **装备四档 = 能破案到哪一层**：¥0 档双手机 + btmon 覆盖 L1+L3、百元档嗅探板打通 L2、千元档钉死手机变量并摸到功耗的门口、专业档空口分析仪按需租借（1.4）。
- **五条纪律**：标注测试机、单变量、先基线、对照实验、可复现——BLE 特有的是「手机机型与系统版本是最大变量」（1.5）。
