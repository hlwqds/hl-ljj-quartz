## 3.1 全景图：两大块 + 一条缝合线

BLE 协议栈可以一刀切成两大块，中间用一条缝合线（HCI）连起来。这张图是全系列的名词表，后面每一章都在图里定位：

```text
┌──────────────────────────────────────────────────────────────┐
│ 应用（App / 嵌入式业务逻辑）                                   │  你写的代码
├──────────────────────────── HOST ─────────────────────────────┤
│ GAP     通用访问规范：角色、广播行为、连接策略、安全入口        │  「怎么被发现/怎么连」
│ GATT    通用属性规范：服务/特征/描述符的数据组织               │  「连上后传什么」
│ ATT     属性协议：GATT 的承载——读/写/notify 的报文与错误码      │
│ SM      安全管理：配对/绑定/加密的协商与密钥分发                │
│ L2CAP   逻辑链路控制：多路复用、MTU、信道（ATT/信令走这里）     │
├──────────────────── HCI（Host Controller Interface）───────────┤
│         命令(→) / 事件(←) / ACL 数据(↔)，btsnoop/btmon 看这里   │
├─────────────────────── CONTROLLER ────────────────────────────┤
│ LL 链路层  广播状态机、扫描、连接维护、跳频、重传、加密执行      │  时序最紧的一层
│ PHY 物理层  GFSK 调制、1M/2M/Coded PHY、频道与功率              │  电磁波出发
└──────────────────────────────────────────────────────────────┘
```

两个术语先钉死：**Host（主机）** = 上半块，通常跑在 CPU 上的软件；**Controller（控制器）** = 下半块，对时序敏感，跑在蓝牙芯片的固件/硬件里。HCI 就是两者的标准化接口——注意它是「接口规范」，不强制是物理总线。

**单芯 SoC vs 双芯（host + controller）**，对调试取证的差异一张表看清：

| 维度         | 单芯 SoC（nRF52/ESP32 等）                                          | 双芯方案（主机 CPU + 蓝牙 dongle/芯片）                    |
| ------------ | ------------------------------------------------------------------- | ---------------------------------------------------------- |
| HCI 走哪里   | 芯片内部的函数调用/队列，**默认看不见**                             | UART/USB 物理线路，**天然可旁听**                          |
| L3 取证手段  | 栈内日志（NimBLE/Bluedroid）、厂商 RTT/trace、部分栈支持导出 HCI 流 | `btmon`/`hcidump` 直接看；UART 上甚至可以接第二个 MCU 抓流 |
| 空口取证     | 不变：嗅探器照样能看（第四章）                                      | 不变                                                       |
| 典型调试难点 | 「栈内发生的事要靠日志还原」，日志开关要提前埋                      | 两个芯片的固件/驱动版本组合是额外变量                      |

一句话结论：**空口（L2）对两种方案一视同仁，差异在 L3**——单芯方案的 HCI 流默认不可见，所以嵌入式项目的日志埋点要「趁早」；双芯方案的 HCI 流免费送，但版本组合管理要「趁严」。ESP32 系虽然单芯，NimBLE 的 HCI 层是独立源码目录，部分项目利用 HCI UART 模式把它跑成「纯控制器」给外部主机用——这正是「同一颗芯片、两种角色、两种取证位置」的活例子。

## 3.2 每层一句话职责 + 调试插管位置

| 层           | 一句话职责                                      | 调试时在哪层插管子                            | 对应工具/章节                        |
| ------------ | ----------------------------------------------- | --------------------------------------------- | ------------------------------------ |
| 应用         | 决定业务行为：什么时候广播/连接/读写            | App 端日志、嵌入式业务回调                    | nRF Connect 操作、自家代码日志       |
| GAP          | 定义设备角色与发现/连接策略                     | 广播参数、角色配置审查；配对入口              | 第四章（广播）、第五章（连接）       |
| GATT         | 把数据组织成服务/特征树                         | 特征权限、CCCD、服务发现结果                  | 第六章全文                           |
| ATT          | 属性读/写/notify 的报文与错误码                 | ATT PDU 逐条看、错误码查表                    | btmon ACL 段、Wireshark `btatt` 过滤 |
| SM           | 配对/绑定/加密协商                              | 配对包逐条看、错误码（SMP 层）                | 第五、六章的安全段落                 |
| L2CAP        | 多路复用与 MTU 协商                             | MTU 交换、固定信道（ATT/信令）                | btmon/Wireshark 的 l2cap 段          |
| HCI          | 主机与控制器的标准对话                          | 命令/事件流全文                               | btmon/btsnoop（第二章）              |
| LL（链路层） | 广播状态机、扫描、连接维护、跳频、LL 重传、断连 | 空口抓包看 LL PDU；supervision timeout 在这层 | 第四章、第五章、第七章               |
| PHY          | 调制、PHY 选择、功率与频偏                      | RF 参数传导测量                               | 第八章、第十一章                     |

把「问题类型 → 该看哪层」再压成一张速查：

| 问题类型                   | 第一嫌疑层 | 为什么                                               |
| -------------------------- | ---------- | ---------------------------------------------------- |
| 扫不到 / 广播内容不对      | GAP → LL   | 广播策略与广播状态机的事，空口帧最直接               |
| 连不上（连接请求没被接受） | LL → HCI   | LL 层建链失败，`LE Connection Complete` 状态码给答案 |
| 读不到 / 写不进 / 数据不对 | GATT → ATT | 权限位与错误码的事                                   |
| 配对失败 / 换手机连不上    | SM         | 密钥与分发策略的事                                   |
| 大数据传输慢 / MTU 争议    | L2CAP → LL | MTU 协商与事件调度的事                               |
| 神秘掉线（无双方主动断开） | LL         | supervision timeout 是 LL 层机制，空口时间线才能定责 |
| 距离一远就断 / 特定角度断  | PHY        | 灵敏度/链路预算/天线的事                             |

> [!tip] 自下而上问一句「这个症状最底能赖到哪」
> 分层地图的最大用处是**给症状画下界**：「读不到」最底只能赖到 ATT（错误码）或 GATT（权限位），赖不到 PHY——除非空口抓包显示包根本没到对方。先画下界，再决定取证预算花在哪。

把一次「扫描→连接→读数据」的完整历程叠在分层图上，每一步各有各的「翻车点」，这张图是第四至七章案例的公共底稿：

```text
应用      选设备 ──────────────── 发起读写/订阅 ─────────▶ 收到数据
            │                                        │              ▲
GAP       发现策略、过滤规则                         │              │
            │                                        │              │
GATT/ATT  ──────────────────── 服务发现 ──▶ 读/写/订阅(带错误码) ─┘
            │                            │
SM        配对/绑定请求（若需加密）       │
            │                            │
L2CAP     ─────── MTU 协商 ─────────────▶
            │
HCI       ── 扫描命令 ── 建链命令+事件 ── ACL 数据上下行
            │
LL        广播包/扫描响应 → CONNECT_IND → 连接事件(跳频+重传) → supervision
            │
PHY       每一包都过射频：功率/频偏/灵敏度决定上面每一层能不能活着说话
```

翻车点速记：**广播没人回** → GAP/LL（第四章）；**CONNECT_IND 之后没有 Connection Complete** → LL/PHY（第五章）；**服务发现不完整或读写报错** → GATT/ATT（第六章）；**用着用着 supervision 判死** → LL + 链路质量（第七章）；**上面全部正常但慢/费电** → 参数与占空比账（第九、十章）。

## 3.3 GAP 角色：广播与连接行为的总开关

GAP 定义四种角色，角色的组合决定了设备「会被谁看到、能和谁连接」：

| 角色        | 干什么               | 发广播？ | 可连接？   | 典型设备                       |
| ----------- | -------------------- | -------- | ---------- | ------------------------------ |
| Broadcaster | 只广播，不收不连     | 是       | 否         | 信标（beacon）、温度贴片       |
| Observer    | 只听广播，不回不连   | —        | —          | 网关的「只听」模式、信标接收端 |
| Peripheral  | 广播自己，等别人来连 | 是       | 可连接广播 | 手环、传感器、遥控器           |
| Central     | 扫描，主动发起连接   | 否（可） | 发起方     | 手机、网关、调试主机           |

对调试的含义有三条。其一，**「扫不到」先查角色与广播类型**：设备如果是 Broadcaster（非可连接广播），那它本来就不接受连接，「点连接失败」是预期行为不是故障——nRF Connect 里广播类型字段（ADV_IND 与 ADV_NONCONN_IND 等，第四章逐个拆）直接区分。其二，**Peripheral 的广播参数（间隔、类型、内容）是第四章的主场**，Central 的扫描参数（窗口/间隔、Active/Passive）决定「你能不能看到完整广播」——第二章 btmon 骨架里 `Scan type: Active` 那一行的伏笔在此兑现。其三，**角色可以切换且可以共存**（如手机既是 Central 连手环、又作为 Peripheral 给电脑传数据）；调试时先用 btmon/抓包确认「当前实际角色与广播状态」，再谈上层逻辑。

## 3.4 ATT/GATT：数据模型一页（为第六章铺路）

GATT 把设备的全部数据组织成一棵树，ATT 是搬运这棵树的报文协议：

```text
GATT Server（设备侧，如传感器）             GATT Client（手机/网关）
├─ Service: Battery Service (0x180F)        ← 通过「服务发现」拿到这棵树
│   └─ Characteristic: Battery Level        ← 权限位决定能读/写/订阅吗
│       └─ Descriptor: CCCD                 ← notify 开关（订阅前必须写它）
├─ Service: 自定义服务 (128-bit UUID)
│   ├─ Characteristic: 配置（可写）
│   └─ Characteristic: 测量值（notify）
```

四个名词的分工，现在只需要记住：

| 名词              | 是什么                                   | 调试关键词                                       |
| ----------------- | ---------------------------------------- | ------------------------------------------------ |
| Attribute（属性） | ATT 世界里的最小单元：句柄 + 类型 + 值   | 一切 GATT 东西底层都是属性；句柄是地址           |
| ATT               | 报文协议：Read/Write/Notify/Error…       | 错误码体系（第二章 2.6 的 ATT 段）；`btatt` 过滤 |
| GATT              | 用属性拼出来的数据模型：服务/特征/描述符 | 服务发现、权限位、CCCD                           |
| MTU               | 一次 ATT 报文的最大长度                  | 连接后先协商 MTU 再谈大块数据；L2CAP 层管        |

调试时最常见的三个坑在这里先埋种子：**权限位**（特征定义了 write 权限才能写，ATT `Write Not Permitted` 就是它的错）、**CCCD**（想收 notify 必须先写 CCCD，「notify on 了却没数据」的第一嫌疑）、**MTU**（默认 ATT MTU 23 字节，头占了 3 字节，有效载荷 20 字节——「一次只能传 20 字节」类问题的第一嫌疑）。三个坑都在第六章逐个引爆，本章只要求能在 btmon 输出里认出它们对应的 PDU 名字。

高频 ATT PDU 先混个脸熟（Wireshark 里 `btatt` 过滤后看到的 OpCode 名）：

| PDU（OpCode 名）              | 方向          | 干什么                           | 调试线索                                |
| ----------------------------- | ------------- | -------------------------------- | --------------------------------------- |
| Exchange MTU Request/Response | 双向          | 协商更大的 ATT MTU               | 没协商就谈大块传输 = 白搭               |
| Read By Group Type Request    | Client→Server | 服务发现第一步（按服务 UUID 找） | 发现「卡在第一步」= 连接刚建立就断了    |
| Read By Type Request          | Client→Server | 发现特征                         | 服务发现走多远，这里看得见              |
| Read Request / Response       | 双向          | 读属性值                         | Response 换成 Error → 查错误码          |
| Write Request / Response      | 双向          | 写属性值（要应答）               | 权限位/加密不足的错误多在这             |
| Write Command                 | 单向          | 写但不等应答                     | 「发了却没生效」——它本来就不回执        |
| Handle Value Notification     | Server→Client | notify 数据推送                  | 出现前必须有 CCCD 写入                  |
| Error Response                | Server→Client | 拒绝并给错误码                   | L3 层最值钱的证据之一（第二章错误码表） |

## 3.5 SM 安全：配对/绑定/加密三概念辨析（为第五、六章铺路）

日常口语把这三件事混成一团「配对」，协议上它们是三步：

| 概念               | 是什么                                            | 生命周期 | 调试关键词                                      |
| ------------------ | ------------------------------------------------- | -------- | ----------------------------------------------- |
| 配对（Pairing）    | 交换能力、协商算法、生成并分发密钥的过程          | 一次会话 | 配对包逐条看；SM 层错误码                       |
| 绑定（Bonding）    | 配对产生的密钥**存下来**，下次直接用              | 持久化   | `bluetoothctl` 的 `Bonded` 字段；「删绑定重试」 |
| 加密（Encryption） | 用密钥把链路数据加密，配对/绑定是手段，加密是目的 | 连接期间 | 加密失败事件；「读加密特征被拒」                |

三条对调试最要紧的关系。其一，**配对 ≠ 绑定**：只配对不绑定，断开后下次要重新走完整配对——「每次重连都要点确认」的现场十有八九是某一方没存密钥。其二，**绑定 ≠ 加密恢复**：绑定存了密钥，但重连后要显式发起加密请求才会加密；加密没起来时访问加密特征会得到 `Insufficient Authentication` 类 ATT 错误（第二章错误码表的伏笔）。其三，**换手机连不上「旧设备」的经典剧情**：旧手机的密钥还在设备里，新手机来配对，设备端密钥槽满或策略拒绝——症状在 SM，解法常是「设备端删掉旧绑定」。IRK/身份地址、配对方法分类（Just Works / Passkey / OOB）留到第五、六章的安全段落展开。

配对在协议上长什么样，先看骨架（每一步都能在 btmon 或空口抓包里认出来）：

```text
手机(Central)                          设备(Peripheral)
     │  Pairing Request（能力清单：IO 能力/算法偏好）  │
     │ ◀────────────────────────────────────────────▶ │ Pairing Response
     │                                                │
     │  按 IO 能力选定方法：Just Works / Passkey / OOB │  ←「弹出六位数字」就是这里
     │                                                │
     │  密钥生成与分发（LTK 等；IRK/身份地址可选分发） │
     │                                                │
     │  Bonding：双方把 LTK 存进各自数据库             │
     │                                                │
     ▼  之后任意一方发起 Encryption Request，链路加密  ▼
```

调试取证的对应关系：配对卡在哪一步，btmon 里的 SMP PDU 序列与配对失败错误码说得最清楚（如 Pairing Failed 带的原因值）；「配对成功但重连后没加密」则看连接建立后有没有 SM Encryption Request——这两个观测点在第五、六章各引爆一次。

## 3.6 BR/EDR 边界页：经典蓝牙与 BLE 是同名不同栈

「蓝牙」这个词下其实住着两套协议栈：**BR/EDR**（经典蓝牙，Basic Rate / Enhanced Data Rate）与 **BLE**（Low Energy）。它们由同一家组织（Bluetooth SIG）用同一部 Core Spec 定义、常在同一颗双模芯片上共存，但**从物理层到应用层几乎完全不同**：

| 维度       | BR/EDR（经典蓝牙）                     | BLE（本系列主角）                    |
| ---------- | -------------------------------------- | ------------------------------------ |
| 诞生目标   | 持续音视频/数据流，替代线缆            | 低功耗、小数据、间歇通信             |
| 发现机制   | inquiry/页面扫描（非广播包模型）       | 三个广播信道上的广播包               |
| 数据模型   | RFCOMM 串口、各种 Profile（A2DP/HFP…） | GATT 服务/特征树                     |
| 连接建立   | 先寻呼建链再协商                       | 广播包里就带连接请求（CONNECT_IND）  |
| 功耗量级   | 持续连接为主，mW 级持续                | 可深度睡眠，µA 级平均                |
| 主机栈实现 | BlueZ 同栈共存 / ESP-IDF 用 Bluedroid  | BlueZ 同栈共存 / ESP-IDF 推荐 NimBLE |

两条调试相关的边界结论。**其一，本系列范围声明：只讲 BLE**。A2DP 音频断连、HFP 通话问题、SPP 串口问题不在本系列——它们的取证工具链（SCO 链路、avdtp 等）与 BLE 几乎无交集，混在一起只会稀释方法论。**其二，双模共存一句话**：双模芯片上 BR/EDR 与 BLE 共享射频与天线，共享的部分（RF 前端、天线、2.4G 共存与 AFH）是唯一可能「BLE 的问题赖到经典蓝牙头上」的地方——第八章共存段落会处理这一条；除此之外，两套栈的症状、工具、错误码互不相认，排查时先确认「出问题的到底在哪套栈」，这一步能砍掉一半误诊。

| Broadcaster                   | 只广播不可连接的 GAP 角色                                   | 3.3               |

## 本章小结

- **两大块一条缝**：Host（GAP/GATT/ATT/SM/L2CAP）+ Controller（LL/PHY），HCI 缝合；单芯方案 HCI 流默认不可见（靠栈内日志），双芯方案 HCI 流天然可旁听——差异全在 L3，空口取证一视同仁（3.1）。
- **每层一句话 + 插管位置**：问题类型 → 第一嫌疑层有速查表；「这个症状最底能赖到哪」是分配取证预算的第一问（3.2）。
- **GAP 角色定行为**：Broadcaster 本来就不可连接；「扫不到/连不上」先对照角色与广播类型，再谈故障（3.3）。
- **数据与安全两棵树**：ATT/GATT 的权限位、CCCD、MTU 三坑与 SM 的配对/绑定/加密三概念，是第五、六章的种子（3.4、3.5）。
- **边界划清**：BR/EDR 与 BLE 同名不同栈，本系列只讲 BLE；双模共存只在共享射频处可能有交集（3.6）。
