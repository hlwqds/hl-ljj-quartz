## 本章证据口径

> [!note] 先立规矩
> 本章广播机制数值（信道频率、间隔上下限、随机延迟范围）引 **Bluetooth Core Spec** 口径（以 Core Spec v5.x/v6.x 的 GAP/LL 层定义为准，正文逐处标注）；手机端扫描行为差异引各平台官方开发文档口径（Apple Accessory Design Guidelines / Android 开发者文档），查不到确切出处标「待核对」。Wireshark/nRF Sniffer 命令与过滤器为工具官方文档语法。**帧解析样例均为「格式示意」**；案例为**教学复盘案例，取材自常见故障模式综述**，非某产品事故报告。不虚构任何实测读数。

## 4.1 现场引入：三类「扫不到」

「App 扫不到设备」是 BLE 现场出镜率第一的报障。同一句汇报，通常是三种不同的问题域：

| 类型                                 | 典型描述                           | 问题域直觉                                      | 常见重灾区                        |
| ------------------------------------ | ---------------------------------- | ----------------------------------------------- | --------------------------------- |
| A：新设备从未被扫到                  | 「新板子上电，App 列表里根本没它」 | 设备根本没在广播 / 广播参数违规 / 包内容非法    | 新固件、广播间隔配错、AD 结构越界 |
| B：只有部分手机扫得到                | 「iPhone 扫不到，Android 能扫到」  | 平台扫描策略差异 / 广播类型兼容性 / 名称分片    | 扫描缓存、TxPower 字段、名称超长  |
| C：时有时无 / 要么很快要么永远扫不到 | 「多扫几次偶尔能蹦出来」           | 广播间隔过大 + 随机延迟 / 三信道遗漏 / 信道被挤 | 广播间隔配 1s+、扫描窗口太窄      |

分类的检查顺序不同：A 类先确认设备真的在发（4.4 抓包一步定案）；B 类是本章 4.5 的案例主角；C 类十有八九落在 4.2 的广播间隔账上。三类共享同一个取证原则：**别在 App 里猜，上嗅探器看空气里到底有没有那串包**。手机 App（nRF Connect/LightBlue）的扫描列表本身就是「被平台策略过滤过的二手证据」（第一章 L1 层），广播抓包才是 L2 层的原始真相。

## 4.2 广播机制：信道、事件与间隔

### 4.2.1 三个广播信道与扫频时序

BLE 把 2.4 GHz 频段切成 40 个 2 MHz 信道，其中**三个专门留给广播**（引 Bluetooth Core Spec 链路层定义口径）：

| 广播信道 | 中心频率 | 索引 | 选址考量（标准设计意图）             |
| -------- | -------- | ---- | ------------------------------------ |
| 37       | 2402 MHz | 0x00 | 频段最低端，避开 802.11 信道 1 中心  |
| 38       | 2426 MHz | 0x01 | 挑在 WiFi 信道 1 与 6 之间的缝隙附近 |
| 39       | 2480 MHz | 0x02 | 频段最高端，避开 802.11 信道 11 中心 |

三个信道刻意**在频率上彼此拉开**，就是为了不与最常用的 WiFi 信道（1/6/11）中心重叠——但只是「避开中心」，边带重叠躲不掉，所以 WiFi 繁忙环境下广播丢包是常态而非异常（共存话题第八章展开）。设备在**每个广播事件里依次在 37→38→39 三个信道各发一次**同一广播包：

```text
广播事件（advertising event），格式示意：
  t0 ──> 信道37 发 ADV_IND ──> 信道38 发 ADV_IND ──> 信道39 发 ADV_IND ──> 事件结束
                  │                    │                    │
            扫描方恰好在 37        恰好在 38            恰好在 39
            （每个扫描方只驻留一个信道，所以三个包缺一不可）
```

扫描方（手机）也有自己的节奏：按 scan interval/scan window 驻留切换信道。两边都是独立的自由振荡器，相遇是概率事件——这就是为什么「扫描时间过短 + 广播间隔过大」的组合必然表现为「时有时无」。

### 4.2.2 广播间隔与随机延迟：扫不到的第一嫌疑

传统广播（legacy advertising）的定时账（引 Bluetooth Core Spec 口径）：

| 参数                                        | 取值范围（Core Spec 口径）     | 说明                                                  |
| ------------------------------------------- | ------------------------------ | ----------------------------------------------------- |
| advInterval（可连接/可扫描非定向）          | 20 ms – 10.24 s，步进 0.625 ms | GAP 推荐下限另受互操作要求约束（见下）                |
| advInterval（不可连接非定向，BLE 4.x 口径） | 100 ms – 10.24 s               | Core 5.0 起放宽（待核对具体版本措辞）                 |
| 随机延迟 advDelay                           | 0 – 10 ms，每次广播事件随机    | 加在每次事件之后：T_advEvent = advInterval + advDelay |

```text
时间轴（格式示意），advInterval = 100 ms：
  事件1(37/38/39) …advDelay… 事件2(37/38/39) …advDelay… 事件3 …
  |←──────────── T_advEvent（不小于 advInterval，最多多 10 ms）────→|
```

**随机延迟设计的动机是防碰撞**：如果两台设备都用精确 100 ms 周期广播，一旦相位重合就永远在空中相撞（捕获效应下弱者永远输）。随机抖动让相位持续漂移，碰撞概率被时间平均掉。但代价是：调试时的账要按「间隔 + 最多 10 ms」算，且**单次扫描窗口恰好全部错过三个信道的情形真实存在**。

现场排查口诀：

- 广播间隔设 1 s 以上 → 手机一次扫描（通常 10 s 量级）也可能撞运气失败 → **「时有时无」第一嫌疑**；
- 信标类产品常见取 100 ms–1 s 之间平衡可见性与功耗（功耗账第十章细算）；
- GAP 规范层面对可连接广播的间隔下限另有互操作性建议（20 ms；Apple 平台对 accessories 的建议间隔见其官方文档口径，Android 无强制），把「Core Spec 允许」和「GAP/平台建议」分开记。

### 4.2.3 广播包类型家族

传统（legacy）广播 PDU 四型 + 扫描响应，是绝大多数现场问题的全部：

| PDU 类型        | 可连接     | 可扫描 | 典型用途                          | 备注                                             |
| --------------- | ---------- | ------ | --------------------------------- | ------------------------------------------------ |
| ADV_IND         | ✅         | ✅     | 通用可连接广播，日常默认          | 扫描方可回 SCAN_REQ，主机可回 CONNECT_IND        |
| ADV_DIRECT_IND  | ✅（定向） | ❌     | 已绑定设备快速重连（带目标 AdvA） | 高占空比定向广播有专门时序规则（Core Spec 口径） |
| ADV_NONCONN_IND | ❌         | ❌     | 纯信标 beacon                     | 一发完事，无人可应答                             |
| ADV_SCAN_IND    | ❌         | ✅     | 可扫描非连接信标                  | 允许被扫，拿 SCAN_RSP 补充信息                   |
| SCAN_RSP        | —          | —      | 对 SCAN_REQ 的应答，携带补充 AD   | **与 ADV_IND 分属两个包**，见 4.3.2              |

BLE 5.0 起新增两套机制（引 Core Spec 5.0 口径）：

| 机制                             | 关键变化                                                                                             | 调试注意                                                                                                       |
| -------------------------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 扩展广播（extended advertising） | 主广播信道只发 AUX_ADV_IND 指针，净负载挪到次信道（AUX 广播链）；PDU 类型 ADV_EXT_IND/AUX_ADV_IND 等 | 老 App/老嗅探器常不认；Wireshark 需按扩展广播解析；很多「BLE5 设备 iPhone 扫不到」落在平台对扩展广播的过滤策略 |
| 周期广播（periodic advertising） | 广播以固定间隔+AOA 准同步发送，接收方可锁定                                                          | CTE/定位类应用；调它先确认双方周期广播同步参数                                                                 |

> [!tip] 版本对照原则
> 现场先问一句：设备广播走的是 legacy 还是 extended？很多「扫不到」是「一套 API 默认切到了 extended，而对面手机/库只认 legacy」。判别方法见 4.4 的抓包：Wireshark 里 PDU 类型一目了然。

## 4.3 广播包字段解读

### 4.3.1 一个 ADV_IND 的完整解剖

传统 ADV_IND 的净负载结构（字段结构引 Core Spec 口径，具体值为**格式示意**）：

```text
ADV_IND PDU（格式示意）
┌─────────┬──────────┬────────────────────────────────────┐
│ AdvA    │ AdvData  │（净负载 ≤ 31 字节）                 │
│ 6字节   │          │                                    │
└─────────┴──────────┴────────────────────────────────────┘
AdvData 内部是 AD 结构的串联，每段：
┌──────────┬───────────┬──────────────────┐
│ Length   │ AD Type   │ AD Data          │
│ 1 字节   │ 1 字节    │ Length-1 字节    │
└──────────┴───────────┴──────────────────┘
例：02 01 06      → Length=2, Type=0x01(Flags), Data=0x06
    0B 09 'N' 'R' 'F' '-' 'D' 'e' 'm' 'o'   → Length=11, Type=0x09(完整名称)
    03 03 'D' '0'  → Length=3, Type=0x03(16-bit UUID 完整列表)
    07 FF 'C' '0' ... → Type=0xFF(厂商自定义)
```

高频字段速查（AD Type 取值引 Core Spec「Assigned Numbers」口径）：

| AD Type     | 名称                          | 现场意义                                                                   |
| ----------- | ----------------------------- | -------------------------------------------------------------------------- |
| 0x01        | Flags                         | 设备能力声明位段；BLE only/BR-EDR not supported 等位组合，**几乎每包必带** |
| 0x03 / 0x02 | 完整/不完整 16-bit UUID 列表  | 宣告 GATT 服务 UUID（SIG 分配的短 UUID）                                   |
| 0x07 / 0x06 | 完整/不完整 128-bit UUID 列表 | 自定义服务 UUID；**16 字节，很占空间**                                     |
| 0x09 / 0x08 | 完整/不完整设备名             | 超长触发分片，见 4.3.2                                                     |
| 0x0A        | TxPower Level                 | 设备自报发射功率（有符号 8 位，dBm）                                       |
| 0xFF        | Manufacturer Specific Data    | 厂商自定义；头两字节为公司 ID（SIG 分配）                                  |

### 4.3.2 ADV_IND 与 SCAN_RSP 的「双包结构」

净负载 31 字节放不下全部内容（名称 + 128-bit UUID + 厂商数据是标配组合，轻松超限），业界通行做法是拆两包：

```text
扫描方                          设备
  │ ── ADV_IND（广播信道，31B 内）────► │
  │ ◄── 若感兴趣，发 SCAN_REQ ────────  │   （仅在收到 ADV_IND 的同一信道）
  │ ── SCAN_RSP ──────────────────────► │   （再给最多 31 字节补充 AD）
```

关键点：**SCAN_RSP 只在扫描方主动请求时才发**。这派生两条现场规则：

| 规则                                                                      | 推论                                                             |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 广播包里放的应是「让扫描器决定要不要理你」的最小集（Flags+名称短版+UUID） | 把名称全名、厂商数据放 SCAN_RSP 是常见布局                       |
| 只监听广播包的日志工具**看不到 SCAN_RSP 内容**                            | App 显示的设备名来自广播包或扫描响应，两者不一致完全正常         |
| iOS/Android 对 SCAN_RSP 的主动扫描策略不同                                | 「某平台显示长名称、另一平台显示短名」多源于此（平台口径待核对） |

### 4.3.3 UUID 的坑：16-bit 与 128-bit 与 App 过滤器

App 按 UUID 过滤扫描结果时，最容易踩三条坑：

1. **广播里放的是 16-bit UUID，App 按 128-bit 过滤**（或反之）：设备明明在发，App 过滤器永远空。服务到底用 16-bit 还是 128-bit UUID 宣告，要与 App 端约定一致；
2. **服务在广播里没宣告，只在 GATT 里存在**：很多 App 的扫描过滤器只看广播 AD 里的 UUID 列表——GATT 表里有而广播里没有，照样过滤为空。对策：把服务 UUID 加进广播包或 SCAN_RSP；
3. **TxPower 字段作为平台过滤因子**：部分平台对广播包解析有额外校验行为（具体策略随版本变化，待核对），现场遇到「字段一改就过/不过」的玄学，先做**二分删除法**：逐段删 AD 结构，定位是哪一段触发平台拒绝。这是 B 类问题的万能起手式。

## 4.4 nRF Sniffer for BLE + Wireshark 实战

### 4.4.1 环境搭建

nRF Sniffer for BLE 是 Nordic 提供的免费嗅探方案：一块 nRF52 级开发板（或 nRF52 dongle）烧录嗅探固件，通过串口桥接进 Wireshark。

| 步骤 | 动作                                                        | 要点                                                                                                                                      |
| ---- | ----------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | 从 Nordic 官网下载 nRF Sniffer for BLE 软件包               | 包含固件 hex、Wireshark 插件与 Python 抓包脚本                                                                                            |
| 2    | 用 nrfutil 烧录嗅探固件到板子/dongle                        | 例（dongle 口径）：`nrfutil dfu usb-serial -p <COM口> -pkg sniffer_nrf52dongle_nrf52840_x.y.z.zip`；开发板用 J-Link/`nrfjprog` 烧对应 hex |
| 3    | 安装 Wireshark 插件                                         | 把软件包内 `extcap/` 下脚本放入 Wireshark 的 extcap 目录，装 Python 3 与 requirements                                                     |
| 4    | Wireshark 捕获接口列表应出现 `nRF Sniffer for Bluetooth LE` | 没出现：查 Python 路径与插件版本匹配                                                                                                      |

验证嗅探器活着：Wireshark 开始捕获后，能在接口下拉里看到设备列表、且附近有广播设备时抓到包，即部署成功。完整安装步骤以 Nordic 官方文档（nRF Sniffer for BLE user guide）为准，版本迭代较快，此处只列骨架。

### 4.4.2 跟踪目标设备：按 BD_ADDR 锁定

开放环境里空气中有几十台设备在广播，第一步永远是锁定目标：

| 操作                                            | 位置                                 | 用途                         |
| ----------------------------------------------- | ------------------------------------ | ---------------------------- |
| Device 下拉选目标 BD_ADDR                       | Wireshark 工具栏（插件提供的工具栏） | 嗅探器固件按地址过滤上报     |
| 过滤器 `ble.addr == aa:bb:cc:dd:ee:ff`          | 显示过滤器                           | 离线 pcap 里聚焦目标全部流量 |
| 抓不到目标 → 取消地址过滤抓全量，先找到目标再锁 | —                                    | 目标地址抄错时的自救动作     |

### 4.4.3 常用过滤器清单

Wireshark BLE 显示过滤器（官方文档语法）：

| 过滤表达式                                  | 语义                                                               | 什么时候用                     |
| ------------------------------------------- | ------------------------------------------------------------------ | ------------------------------ |
| `ble.flag` 族 / 抓包接口的 Advertising 选项 | 只看广播包                                                         | 现场先看「设备到底发不发广播」 |
| `ble.advertising_header.pdu_type == 0x02`   | 只看 ADV_IND（按 PDU 类型值过滤，值口径以 Wireshark BLE 解码为准） | 确认可连接广播存在             |
| `ble.advertising_header.pdu_type == 0x04`   | 只看 SCAN_RSP                                                      | 核对扫描响应内容               |
| `ble.addr == <BD_ADDR>`                     | 聚焦某地址                                                         | 目标流量全量                   |
| `btcommon.eir_ad.entry.device_name`         | 广播中的设备名                                                     | 名称相关问题的快速筛           |
| `btcommon.eir_ad.entry.company_id`          | 厂商自定义数据                                                     | 0xFF 段解析核对                |
| `ble.connection_request`                    | 连接请求（CONNECT_IND）                                            | 第五章的入口判据               |

> [!tip] 没有嗅探器的最低配替代
> 两个手机装 nRF Connect（Android）+ LightBlue（iOS）交叉扫描，配合 Linux 端 `bluetoothctl scan on`、`btmon` 抓 HCI 层广播上报（第二章工具链），可以回答「设备在不在广播、广播内容是什么」这两问——只是看不到「设备发了但扫描方没收到」的空口丢失。嗅探器是在这一步之后才必要。

## 4.5 案例：「iPhone 扫不到、Android 能扫到」

**教学复盘案例，取材自常见故障模式综述。**现象：设备（名称 20+ 字符，带 128-bit 自定义服务 UUID）在 Android nRF Connect 里稳定出现；iPhone 上 LightBlue/nRF Connect 时有时无，甚至完全不出现。设备固件近期改过：广播内容加了名称全名。

### 4.5.1 取证链

```text
步骤1  抓包确认设备在广播吗？
       → nRF Sniffer 全量抓：37/38/39 三信道都有 ADV_IND，间隔 ~100ms
       → 结论：设备端广播本身健康，问题在「扫描方为什么不认」
步骤2  对比广播内容与扫描响应内容
       → ADV_IND 净负载已满 31 字节（名称全名 + 128-bit UUID + 厂商段）
       → SCAN_RSP 里是名称的另一半
步骤3  逐段二分 AD 结构（4.3.3 的万能起手式）
       → 删掉名称全名后，iPhone 稳定扫到
       → 恢复名称、删 128-bit UUID 段，iPhone 也扫到
       → 两个段同时存在时必现
步骤4  调整布局：广播包只放 Flags + 短名 + 128-bit UUID
       → 名称全名挪进 SCAN_RSP
       → iPhone 与 Android 稳定一致
```

### 4.5.2 根因剖析与三条通用教训

| 层             | 教训                                                                                                                                                                                                   |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 广播类型兼容性 | iOS 对净负载放满 31 字节 + 名称跨包分片（广播包与 SCAN_RSP 各持名称的一半）的组合解析行为与 Android 不同，超出其容忍度的包直接不出现在扫描结果（平台行为口径待核对，但「跨包分片名称」是社区高频嫌疑） |
| 扫描缓存       | iOS 扫描结果有缓存：**同一设备改名/改广播内容后，App 列表可能仍显示旧值**；系统级开关蓝牙再开、或等缓存过期才刷新（平台口径待核对）。调试期纪律：每次改广播内容，iPhone 侧完整重启蓝牙                 |
| 布局纪律       | 「扫描器第一眼要看的信息放广播包，第二眼才需要的信息放 SCAN_RSP」——不要把 31 字节塞满                                                                                                                  |

> [!warning] 归因纪律
> B 类问题（部分平台扫不到）最容易错误归因为「iPhone 灵敏度差」或「设备信号弱」。平台策略差异属于协议之上的**行为差异**，抓包里设备明明在发、内容肉眼可见时，答案几乎总在「平台怎么过滤」而不是「射频多差」。射频归因要等抓包显示设备**真的没在发**或信号边缘场景时才登场（那是第八章的地盘）。

## 4.6 根因速查表

| 症状                     | 判据（App 层）                        | 判据（抓包层）             | 根因                                | 对策                               |
| ------------------------ | ------------------------------------- | -------------------------- | ----------------------------------- | ---------------------------------- |
| 全平台扫不到             | nRF Connect 也无                      | 三信道无任何 ADV_IND       | 设备没在广播/固件未起               | 查固件广播使能与状态机             |
| 全平台扫不到             | App 有其他设备                        | 有其他设备的广播，无目标   | 广播间隔过大撞不上扫描窗口          | 缩短 advInterval；延长扫描时间     |
| 时有时无                 | 多扫几次出现                          | ADV_IND 间隔 >1s           | 同上（大间隔 + advDelay 抖动）      | 间隔调 ≤100ms 验证                 |
| 新设备扫不到             | 首次上电                              | ADV_IND 只在部分信道       | 三信道发射缺一（信道 39 常见）      | 抓包逐信道核对；查射频配置         |
| iPhone 扫不到 Android 能 | LightBlue 无、nRF Connect(Android) 有 | ADV_IND 正常，净负载满载   | 广播内容/分片触平台过滤（4.5 案例） | 二分 AD 结构；名称挪 SCAN_RSP      |
| 改名后显示旧名           | App 列表旧名                          | 新广播包已是新名           | 平台扫描缓存                        | 重启蓝牙清缓存（iOS 常见，待核对） |
| App 按 UUID 过滤为空     | 不过滤能看到设备                      | 广播无该 UUID 段           | 服务 UUID 未在广播宣告              | UUID 加入广播/SCAN_RSP             |
| App 扫到但信息缺         | 无名称/无厂商数据                     | SCAN_RSP 未被请求或内容缺  | 布局在 SCAN_RSP 而 App 不主动扫     | 名称挪回广播包或换扫描器           |
| 靠近能扫到远处不能       | 距离敏感                              | ADV_IND RSSI 边缘          | 信号边缘 + 广播包无重传             | 改善链路；缩短间隔提高命中         |
| 干扰时段扫不到           | WiFi 繁忙时段集中出现                 | 广播丢包率随 WiFi 活动波动 | 2.4G 共存挤压广播信道               | 第八章共存话题；换广播时机         |

> [!summary] 本章收束
> 「扫不到」的解法同样是流程而非背表：先抓包确认设备在不在发（4.4）→ 在发则核对广播内容与布局（4.3）→ 内容没问题再对照平台策略差异（4.5）→ 时有时无回到间隔账（4.2）。扫描这关过了，下一关是连接——设备出现了、点「Connect」转圈失败，就是第五章的主战场：连接建立的三参数与逐阶段取证。
