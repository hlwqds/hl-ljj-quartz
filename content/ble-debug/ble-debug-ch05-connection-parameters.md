## 本章证据口径

> [!note] 先立规矩
> 本章连接参数数值（interval/latency/supervision timeout 范围与约束式）、LL 控制过程名称引 **Bluetooth Core Spec** 链路层定义口径；手机端参数偏好引各平台官方文档口径（Apple Accessory Design Guidelines / Android 开发者文档，随版本演进，正文标注「官方文档口径」或「待核对」）。`bluetoothctl`/`btmon`/nRF Connect 操作为真实可执行命令；**帧序列与 HCI 流样例均为「格式示意」**；案例为**教学复盘案例，取材自常见故障模式综述**。不虚构实测读数。

## 5.1 现场引入：三类「连不上」

广播能扫到之后，「点连接转圈失败」接棒成为新热点。同样是「连不上」，先按可观测特征分三类：

| 类型              | 典型描述                                | 问题域直觉                                  | 首查位置                    |
| ----------------- | --------------------------------------- | ------------------------------------------- | --------------------------- |
| A：点了永远连不上 | 「列表里有设备，点 Connect 转圈到超时」 | 连接请求发出后无响应 / 设备拒绝 / 请求丢失  | 5.4 分阶段：卡在哪一步      |
| B：连上秒断       | 「连上一两秒就掉，循环往复」            | 加密/参数审查失败、设备端异常断开           | 5.5 配对加密坑 + 断连原因码 |
| C：换手机结果不同 | 「A 牌手机连得上，B 牌连不上」          | 平台参数策略 / 地址类型 / 扫描-连接衔接差异 | 5.3.3 平台参数偏好表        |

与第四章的分类表对照：A 类是「广播 OK 之后链路层建不起来」，B 类是「链路建起来了但安全层踢人」，C 类是**互操作性**问题。三类的取证都遵循同一条纪律：**先定位断在哪个阶段，再谈根因**——这正是本章 5.4 的分阶段取证法。

## 5.2 连接建立流程：从 CONNECT_IND 到第一个 connection event

传统广播路径下的建链全图（PDU 名称引 Core Spec 口径；时序为格式示意）：

```text
  发起方（Initiator，通常手机）              广播方（Advertiser，设备）
        │                                          │
  ① 扫描态：收 ADV_IND（37/38/39 任一信道） ◄──────│ 周期广播
        │                                          │
  ② 发 CONNECT_IND（同信道，含双方地址、      ────►│
     conn interval/latency/timeout、          │
     channel map、hop、CRCInit 等）           │
        │                                          │
  ③ 双方各自约定：transmitWindowOffset 之后       │
     的第一个 anchor point 开始收发            │
        │        ◄──── 第一个数据信道 PDU ──────── │
        │   （连接正式建立；此后离开广播信道，   │
        │     按信道图在数据信道间跳频）         │
        ▼                                          ▼
  connection event N：master 在 t 发，slave 在 t+150µs 内应答
```

三个调试要点：

1. **CONNECT_IND 带着连接的全部基因**：channel map、hop increment、sleep clock accuracy、窗口参数一次定案。抓到 CONNECT_IND 就等于拿到了「双方各自认为的连接配置」，第五章以后所有参数纠纷都拿它对账；
2. **第一个 connection event 之前有窗口协商**：若广播方没在窗口内听到发起方的首个 PDU，连接**从未真正建立**——表现为「CONNECT_IND 发了，但设备侧无连接回调」，是 A 类「转圈失败」的经典形态；
3. **BLE 5 扩展广播路径不同**：对应 PDU 是 AUX_CONNECT_REQ/AUX_CONNECT_RSP（经次信道），抓包过滤器与解析路径不同（第四章 4.2.3 的扩展广播链条）。

Wireshark 侧：过滤器 `ble.connection_request` 直达 CONNECT_IND；`btcommon.advertising.address` / `ble.addr` 聚焦目标地址。

### 5.2.1 CONNECT_IND 字段速查

对账用字段清单（字段名与语义引 Core Spec 口径）：

| 字段                             | 语义                                            | 对账用途                                            |
| -------------------------------- | ----------------------------------------------- | --------------------------------------------------- |
| InitA / AdvA                     | 发起方/广播方地址（各带地址类型 public/random） | **地址类型不一致是 C 类连不上的高发点**（5.6 案例） |
| LLData: AA                       | 连接后数据 PDU 的访问地址（随机生成）           | 抓包里识别「这是该连接的数据包」的依据              |
| LLData: CRCInit                  | 该连接的 CRC 种子                               | 同上，解码数据信道的钥匙                            |
| LLData: WinSize/WinOffset        | 首个连接事件的接收窗口                          | 窗口内设备没听到首包 = 连接未真正建立               |
| LLData: Interval/Latency/Timeout | 三参数初值（5.3.1）                             | 参数纠纷的第一份证据                                |
| LLData: ChannelMap               | 使用的数据信道位图                              | 某信道被 map 掉属正常（AFH）；全 0 非法             |
| LLData: Hop                      | 跳频增量（5–16）                                | 两端各执一份，理论上一致                            |

### 5.2.2 跳频与 connection event：数据信道的节奏

连接建立后，双方在每个 connection event 上按既定规则跳频收发（机制引 Core Spec 口径）：

```text
connection event N（格式示意）：
  anchor point ──> master 发 PDU ──> 150µs 后 slave 应答 ──> 可继续更多包
                                                      （直到事件预算耗尽）
  下一个 event：信道 = (上次信道 + hop) mod 37，被 channel map
  排除的信道按重映射表顺延
```

| 概念               | 现场意义                                                                               |
| ------------------ | -------------------------------------------------------------------------------------- |
| anchor point       | 每个事件的时间基准；「数据延迟抖动大」先看事件有没有按 interval 出现                   |
| 150µs 应答间隔     | BLE 固定时序；抓包里 master→slave 包间距异常即协商/时钟问题线索                        |
| channel map 重映射 | 设备与手机各自维护 map，认知不一致时双方在不同的信道上互相找不到——秒断的协商类根因之一 |
| slave latency 跳过 | latency>0 时从机可连续跳过事件；「设备不应答」先查是不是在合法跳过（第七章展开）       |

## 5.3 三参数深入：interval、latency、supervision timeout

### 5.3.1 数值范围与约束（Core Spec 口径）

CONNECT_IND 与后续参数更新携带的三参数，全部以「约定单位」编码：

| 参数                   | 单位       | 允许范围（Core Spec 口径）        | 现场换算                            |
| ---------------------- | ---------- | --------------------------------- | ----------------------------------- |
| connInterval           | 1.25 ms    | 6 – 3200（即 **7.5 ms – 4 s**）   | 6=7.5ms，16=20ms，32=40ms，80=100ms |
| connSlaveLatency       | 连接事件数 | 0 – 499（且受约束式限制）         | latency=4 表示从机可跳过 4 个事件   |
| connSupervisionTimeout | 10 ms      | 10 – 3200（即 **100 ms – 32 s**） | 400=4s，600=6s                      |

硬性约束式（Core Spec 口径，违反即非法参数）：

```text
connSupervisionTimeout > (1 + connSlaveLatency) × connInterval × 2
```

> [!warning] 最常撞的一条约束
> 想要「低功耗」把 latency 开大、又想「快速检测断线」把 timeout 收小，两者相乘就撞墙。例：interval=7.5ms、latency=100、则 timeout 必须 > (1+100)×7.5×2 = 1515 ms。约束式报错的直接表现是：设备端拒绝参数更新、或手机侧 LL_CONNECTION_UPDATE_IND 后链路立即掉——「连上秒断」的参数形态之一（B 类）。

### 5.3.2 参数更新请求：双路径

连接建立后，从机通常想把手机给的缺省参数换成自己的业务参数。Core Spec 有两条路径，**取证时必须分清是哪条**（引 Core Spec 口径）：

| 路径       | 层级   | PDU/信令                                                                                        | 方向                         | 特点                                                                                          |
| ---------- | ------ | ----------------------------------------------------------------------------------------------- | ---------------------------- | --------------------------------------------------------------------------------------------- |
| LL 路径    | 链路层 | `LL_CONNECTION_UPDATE_IND`                                                                      | 双向（任何一方的 LL 均可发） | 即时生效带 instant 字段（生效时刻）；对端无法「拒绝」只能执行                                 |
| L2CAP 路径 | 主机层 | L2CAP Connection Parameter Update Request（信令通道 CID 0x0005，指令码见 Core Spec L2CAP 章节） | **仅从机→主机**              | 主机（手机）收到后**决定**是否发 LL_CONNECTION_UPDATE_IND——本质上是一个「请求」，审批权在手机 |

取证含义：设备发了 L2CAP 更新请求但参数始终没变，**不是设备没发，是手机没批**——这是 A/B/C 三类问题的共同交叉点。btmon 里对应能看到 L2CAP 信令帧（`btmon` 输出中 L2CAP Signaling: Connection Parameter Update Request 字样，格式示意）：

```text
< ACL Data TX: Handle 64 flags ... (格式示意)
    L2CAP: Signaling Channel (0x0005)
      Code: Connection Parameter Update Request
      Interval Min: 24   (30 ms)
      Interval Max: 40   (50 ms)
      Slave Latency: 0
      Timeout Multiplier: 400  (4000 ms)
```

### 5.3.3 手机端参数偏好

两平台对连接参数都有各自的审查逻辑（引各平台官方文档口径；**具体数值随系统版本演进，以下为广为引用的典型约束，实际以文档现行版本为准，待核对**）：

| 平台                                          | 典型约束（官方文档口径）                                                                                                       | 不满足时的表现                                            |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| iOS（Apple Accessory Design Guidelines 口径） | interval 建议 ≥ 15 ms 且为 15 ms 的倍数；latency ≤ 4（建议范围）；supervision timeout 建议 ≤ 6 s；不满足时系统可能改用自定参数 | 设备请求被「改判」为平台自选参数，业务延迟与设计不符      |
| Android（官方文档/栈行为口径）                | 栈接受设备请求的尺度较宽，部分请求可被直接执行；后台连接有自身的参数策略                                                       | 前台/后台参数不同；「同一设备不同手机上行为不同」多源于此 |

> [!tip] 参数纠纷的对账方法
> 争议时永远拿三份证据对账：①CONNECT_IND 里的初始参数；②设备发起的更新请求参数；③实际生效参数（btmon 的 LL_CONNECTION_UPDATE_IND / HCI LE Connection Update Complete 事件，或设备端协议栈日志）。三份证据一摆，「谁改了参数、改成了什么、谁拒绝的」一目了然。

## 5.4 分阶段取证法：每一阶段失败的帧特征

连接建立是**链式过程**，任何一环断掉，现象都是「转圈失败」，但帧特征完全不同。这是本章的主地图：

| 阶段                    | 成功的帧特征（抓包）                                     | 失败时的帧特征                   | 最可能根因                                                            |
| ----------------------- | -------------------------------------------------------- | -------------------------------- | --------------------------------------------------------------------- |
| ①广播可见               | ADV_IND 三信道稳定                                       | 无 ADV_IND / 间隔过大            | 回第四章；此处假设已过                                                |
| ②连接请求发出           | CONNECT_IND 出现（`ble.connection_request`）             | 手机从未发 CONNECT_IND           | App 层连接失败（地址类型错、平台策略）——**空口没动作说明问题在手机**  |
| ③CONNECT_IND 被设备收到 | CONNECT_IND 后 6 个 interval 内首个数据信道 PDU 往返出现 | CONNECT_IND 有，之后寂静         | 设备没收到（信道图/时序窗口错过）或设备协议栈未处理（设备端日志定案） |
| ④GATT 发现              | ATT 层 Exchange MTU / Read By Group Type Request 出现    | 数据 PDU 往返正常但 ATT 层无后续 | 主机层问题（App 侧超时/设备 GATT 表注册失败）——转第六章               |
| ⑤加密（若需要）         | LL Encryption Start（0x03）控制过程完成                  | Start Enc Request 后断链         | 5.5 配对/密钥问题                                                     |

现场执行顺序（配合第四章的嗅探环境）：

```bash
# 1. Linux 端同时留 HCI 层证据（设备是 Linux 主机时；手机无 HCI 抓包条件则靠空口）
sudo btmon -w hci.pcap &
# 2. Wireshark/nRF Sniffer 抓空口，锁定目标地址
#    过滤器：ble.addr == <设备BD_ADDR>
# 3. 触发一次连接，按 5.4 表格逐阶段对帧
# 4. 两份 pcap（空口 + HCI）用同一 UTC 时钟对齐（同机同钟，跨机先对表）
```

各阶段的免费替代证据（无嗅探器时）：手机 nRF Connect 的连接进度条只反映 App 层；Android 开发者选项的「蓝牙 HCI 信息收集日志」可导出 btsnoop 格式 HCI 日志（平台功能口径），配合 Wireshark 直接读——**手机侧 HCI 日志 + 设备端日志**两端对齐，通常足以定位到阶段，只是看不到空口丢失。

## 5.5 加密阶段：配对/绑定失败的常见坑

链路加密由 SM（Security Manager）层完成：配对（pairing，交换/协商密钥，一次性）→ 密钥分发 → 绑定（bonding，密钥落盘供重连复用）。常见故障坑（引 Core Spec SM 层口径）：

| 坑                  | 机理                                                                                                                                   | 典型表现                                                         | 判别                                                   |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------------ |
| **IO 能力不匹配**   | 配对算法按双方 IO 能力（DisplayYesNo/KeyboardOnly/NoInputNoOutput 等）选配对方法；一侧声明与实际不符时流程卡死或回退到 Just Works 失败 | 配对弹窗不出现 / 直接 Pairing Failed                             | 抓 SM 层 Pairing Request/Response 对照双方 IO 能力字段 |
| 密钥分发失败        | 分发阶段（IRK/LTK/CSRK 等）任一包丢失或一侧不支持                                                                                      | 配对到一半断                                                     | 空口看 SMP 层 Distribution of keys 各 PDU 是否齐       |
| 绑定密钥过期/不一致 | 设备端擦了绑定信息（恢复出厂/NVS 重写），手机还持旧密钥                                                                                | 重连时加密协商失败、**反复配对失败**，删掉手机端配对记录立即恢复 | 设备端查 NVS；抓包看加密请求被拒                       |
| OOB/Passkey 输错    | 带外方式或 passkey 验证失败次数超限                                                                                                    | 提示配对错误、设备可能临时锁定                                   | 按 SM 层错误码读（Pairing Failed 原因字段）            |
| 安全等级门槛        | GATT 特征要求加密/认证级保护（第六章 6.5），手机在未配对状态下访问触发 Insufficient Authentication                                     | 「能连上但一读就断/弹配对」                                      | ATT 错误码 + btmon 的 SMP 流水线                       |

> [!warning] B 类「连上秒断」的半数在此
> 设备端 NVS 绑定信息与手机端记录不同步（一边清了另一边没清）是「秒断」的头号惯犯。取证顺序：先在手机端**删除配对记录**重连一次——这一步零成本，能立刻区分「密钥问题」和「链路问题」。

配对失败时 SM 层会给出 Pairing Failed 的原因码（引 Core Spec SM 层标准定义，常用项）：

| Pairing Failed 原因 | 名称                                       | 现场对应                                  |
| ------------------- | ------------------------------------------ | ----------------------------------------- |
| 0x03                | Confirm Value Failed                       | passkey 比对错（输错/双方算法输入不一致） |
| 0x05                | Pairing Not Supported                      | 一侧根本不支持配对                        |
| 0x06                | Encrypt Key Size                           | 密钥长度协商不匹配（实现差异高发）        |
| 0x07/0x08           | Command Not Supported / Unspecified Reason | 泛化失败，配合双方日志看                  |
| 0x0A                | Invalid Parameters                         | 配对请求参数非法（OOB/IO 能力字段越界）   |

抓包判读：过滤器锁定 SM 层 Pairing Request/Response 与 Pairing Failed，把双方 IO 能力字段并排对——「声明的 IO 能力」与「设备真实硬件」不符是本层最常见的乌龙（比如声明 KeyboardOnly 但没有键盘输入通路）。

### 5.5.1 常用 LL 控制过程速查

连接生命周期里双方 LL 层还有一批控制过程，抓包排障时按需对号（过程名与操作码引 Core Spec LL 控制过程口径）：

| 控制过程                 | 用途                            | 排障意义                             |
| ------------------------ | ------------------------------- | ------------------------------------ |
| LL_CONNECTION_UPDATE_IND | 参数更新（5.3.2 的 LL 路径）    | 参数纠纷的对账单                     |
| LL_CHANNEL_MAP_IND       | 信道图更新                      | 「双方 map 认知不一致」的对账单      |
| LL_LENGTH_REQ/RSP        | 数据长度协商（DLE，第九章展开） | 吞吐问题先看协商结果                 |
| LL_PHY_REQ/RSP           | PHY 更新（2M/Coded，第九章）    | 速率/功耗异常先看 PHY 现状           |
| LL_PING_REQ/RSP          | 链路活性探测                    | 区分「协议栈活着但应用卡死」         |
| LL_TERMINATE_IND         | 正常断链（带原因码）            | **掉线归因的第一现场**（第七章主角） |

## 5.6 教学案例：「连不上」完整取证时间线

**教学复盘案例，取材自常见故障模式综述。**现象：设备在 Android 能连，另一台 Android 机型点连接转圈到超时（C 类）。设备固件近期把广播间隔从 200 ms 调到 1 s（功耗优化）。

```text
取证时间线（格式示意；两路证据：空口 pcap + 设备端日志，UTC 对齐）

T+0.0s  手机A点连接：空口立即出现 CONNECT_IND → 首个连接事件往返正常
T+0.2s  ATT 层 Exchange MTU → 服务发现开始 → 连接稳定建立
T+5.0s  手机B点连接：空口出现 CONNECT_IND
T+5.0s  ……之后数据信道一片寂静
T+5.2s  设备端日志：无「连接建立」回调，但 RF 层有接收到包的计数
T+5.3s  复查 CONNECT_IND 内容：channel map 覆盖 37 个数据信道，hop 正常
T+5.4s  对比手机A的 CONNECT_IND：参数完全一致，差异只在设备地址类型字段
T+5.5s  设备广播的 AdvA 类型为 public，手机B发出的 CONNECT_IND
        中 InitiatorA/AdvA 使用了不同地址类型解析
T+6.0s  归因：手机B对地址类型解析与设备不匹配 → 建链窗口内
        设备未确认连接 → 手机侧转圈超时
```

三条复盘教训：

| #   | 教训                                                                                                                                                         |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1   | **CONNECT_IND 内容对账是 C 类问题的第一现场**：地址类型（public/static random/RPA）两边认知不一致是高频坑，尤其设备用可解析随机地址（RPA）+ 地址解析边界场景 |
| 2   | 「转圈超时」不等于「手机没发请求」：先抓空口确认 CONNECT_IND 是否发出（阶段②），再确认设备是否确认（阶段③），**别把两个阶段混为一谈**                        |
| 3   | 设备端「RF 收到包但协议栈无回调」的日志形态，指向的是**连接参数/地址/信道图**这类建链协商问题，而不是射频灵敏度——后者通常表现为所有手机都时好时坏            |

## 5.7 根因速查表

| 症状                | 阶段 | 抓包特征                            | 根因                                         | 对策                                      |
| ------------------- | ---- | ----------------------------------- | -------------------------------------------- | ----------------------------------------- |
| 点连接转圈失败      | ②    | 无 CONNECT_IND                      | App 层连接失败（地址类型/平台策略/后台限制） | 换官方 App/系统蓝牙设置页验证；查地址类型 |
| 点连接转圈失败      | ③    | CONNECT_IND 有，之后无数据 PDU      | 设备未在窗口内确认（时序/信道图/地址解析）   | 对账 CONNECT_IND 各字段；设备端查建链回调 |
| 点连接转圈失败      | ①    | 广播间隔过大                        | 扫描到设备与连接衔接时设备恰好不在广播       | 广播间隔回调（第四章口诀）                |
| 连上秒断（循环）    | ⑤    | Encryption Start 后断链             | 绑定密钥不一致（设备端清了/手机没清）        | 手机删配对记录重连；设备端查 NVS          |
| 连上秒断（循环）    | 参数 | LL_CONNECTION_UPDATE_IND 后即断     | 三参数违反约束式（5.3.1）                    | 按约束式重算 latency/timeout              |
| 连上秒断（循环）    | ⑤    | SMP Pairing Failed 反复             | IO 能力声明与实际不符 / passkey 流程错       | 抓 Pairing Request 对照双方 IO 能力       |
| A 手机连得上 B 不行 | ②③   | 两台 CONNECT_IND 字段差异           | 地址类型/参数偏好平台差异                    | 逐字段 diff 两台手机的 CONNECT_IND        |
| 数据延迟与设计不符  | 参数 | 实际 interval 与请求不符            | 手机改判参数（5.3.3 平台偏好）               | 对账三份参数证据；按平台口径调整请求      |
| 近能连远不能        | ②③   | CONNECT_IND/首个 PDU 丢失率随距离升 | 链路预算边缘（射频）                         | 第八章链路预算；先改善天线/位置           |
| 时连时不连          | ①③   | 广播丢失与建链失败混合              | 弱信号 + 大广播间隔叠加                      | 先解广播（第四章），再回本表              |

> [!summary] 本章收束
> 「连不上」的解法仍然是流程：CONNECT_IND 什么时候发出（阶段②）→ 设备有没有确认（阶段③）→ 加密协商走到哪一步（阶段⑤）——每一步的帧特征都有固定判据，参数纠纷永远拿三份证据对账。链路建起来之后，下一个关卡是「连上了但读不到数据」：GATT 数据模型、ATT 错误码与 MTU，就是第六章的主战场。
