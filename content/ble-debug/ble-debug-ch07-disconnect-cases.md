## 7.1 现场引入：四类「掉线」不是一种病

第五章解决「连不上」；本章往后挪一步：**连接建立之后，链路意外终止**。用户口中的「掉线」至少是四种不同的病，混着查必然绕路：

| #   | 用户描述                       | 现象特征                             | 高频真因                                      | 首选取证                             |
| --- | ------------------------------ | ------------------------------------ | --------------------------------------------- | ------------------------------------ |
| 1   | 「放进口袋/手包就断」          | 贴身携带必断，拿出来又自己连上       | 人体遮挡吃掉链路余量（→第八章链路预算）       | RSSI 曲线 + 断连方向与错误码         |
| 2   | 「走远一点/隔堵墙就断」        | 特定房间、门外必断，位置强相关       | 链路预算到边：距离 × 穿透 × 天线              | 定距 RSSI 梯度（第八章 8.6）+ 错误码 |
| 3   | 「用着用着随机断」             | 与位置、动作无稳定关联，偶发         | 2.4G 干扰时段/事件；偶发参数协商问题          | 断连时刻直方图 + 三源对齐（7.3）     |
| 4   | 「熄屏就断」「App 在前台才稳」 | 屏幕一灭几分钟内必断，亮屏回来又恢复 | 手机省电策略杀后台——「软件伪装硬件」（7.4.3） | 判别法四步；看链路是否真断           |

排查前先答最便宜的问题——**断的是蓝牙链路，还是 App 的会话**。BLE 设备一旦处于连接态就不再广播，这个协议特性送了一条免费的判别法：

```text
「掉线了」
 ├─ 复现时刻，用第二台手机 nRF Connect 扫描：
 │    ├─ 扫不到该设备 → 它多半还连着（连接态不广播），链路活着
 │    │               → 「断」的是 App 的会话/上报，去 7.4.3 软件伪装硬件
 │    └─ 能扫到（设备恢复广播） → 链路真断了 → 按 7.3「谁先断」下钻
 └─ 三源对齐（App 日志 / 主机栈 HCI / 空口抓包）定方向与原因 → 7.4 根因家族
```

总索引的分层取证顺序照用：掉线的主战场在 L2 空口层与 L3 主机栈层，L4 射频层是「错误码 0x08 + 位置/时段相关性」坐实之后的下钻（第八章）。工具盲区回 [[ble-debug-ch02-host-stack-toolkit|第二章：主机栈工具链]] 补课。

## 7.2 断连的协议机制：静默死亡与主动告别

BLE 链路层只有两条路走到「断连」，取证价值截然不同（Core Spec 链路层口径）：

```text
断连的两条路
 A 静默死亡：supervision timeout 到期
    连续 connSupervisionTimeout 时间内收不到任何有效包
    → 双方各自判定链路死亡；空口上没有告别帧——包就是「戛然而止」
    → 两端 HCI 事件均报 0x08 Connection Timeout
 B 主动告别：LL_TERMINATE_IND
    断开方（通常由主机栈的 HCI Disconnect 命令触发）
    发 LL_TERMINATE_IND（LL Control PDU，携带错误码）→ 对端回 LL_TERMINATE_IND 确认
    → 空口上看得见「有来有回」的告别
    → 发起侧 HCI 报 0x16 Connection Terminated By Local Host，对端报 0x13
```

记住一句话就够定方向：**有告别帧 = 有人主动断；没告别帧 = 超时或设备死了**。断前的重传密度、事件完整性是判断「为什么超时」的关键辅证——这些证据都在 7.3 的取证动作里收割。

两条路在三份证据源里的成像不同，取证前先背下这张对照：

| 机制                    | 空口抓包看到                       | 发起侧 HCI 事件         | 对端 HCI 事件 | 第一嫌疑                 |
| ----------------------- | ---------------------------------- | ----------------------- | ------------- | ------------------------ |
| A：supervision timeout  | 包戛然而止，无告别帧               | 0x08 Connection Timeout | 0x08（同码）  | 射频失联/干扰/设备重启   |
| B：主动告别（手机发起） | LL_TERMINATE_IND 手机→设备有来有回 | 0x16                    | 0x13          | App/系统行为（软件家族） |
| B：主动告别（设备发起） | LL_TERMINATE_IND 设备→手机有来有回 | 0x16                    | 0x13          | 设备固件策略或设备侧故障 |
| B：参数更新后即断       | LL_CONNECTION_UPDATE_IND 后告别    | 0x28/0x3B 常伴生        | 同左          | 参数过激（7.5）          |

### 高频 HCI 错误码表（Core Spec『Controller Error Codes』表口径，v6.2；编号域多年稳定）

| 码        | 官方名称                                      | 大白话                | 现场含义                                                                                 |
| --------- | --------------------------------------------- | --------------------- | ---------------------------------------------------------------------------------------- |
| 0x08      | Connection Timeout                            | 链路监督超时          | 射频失联的第一嫌疑：弱信号/干扰/设备重启；两端 HCI 事件同报此码                          |
| 0x13      | Remote User Terminated Connection             | 对端用户/主机主动断   | 「断」的对端是手机时的常见形态：App 调 disconnect、系统回收连接                          |
| 0x14      | Remote Device Terminated due to Low Resources | 对端资源不足          | 手机资源紧张时的体面告别，常与省电策略伴生                                               |
| 0x15      | Remote Device Terminated due to Power Off     | 对端要下电            | 手机关蓝牙/关机、对端设备断电                                                            |
| 0x16      | Connection Terminated By Local Host           | 本地主机主动断        | **谁的 HCI 日志里出现它，谁就是发起方**（7.3 的定侧证据）                                |
| 0x1E/0x20 | Invalid/Unsupported LL Parameter              | LL 参数不合法/不支持  | 参数更新协商失败（7.5；协商过程回 [[ble-debug-ch05-connection-parameters\|第五章]] 5.3） |
| 0x22      | LL Response Timeout                           | LL 控制事务失步       | 控制器级异常（丢包把 LL 事务卡死），少见但真实，多为芯片/栈问题                          |
| 0x23      | LL Procedure Collision                        | LL 过程冲突           | 两个控制过程撞车，多为协议栈实现问题                                                     |
| 0x28      | Instant Passed                                | 参数更新 instant 错过 | 参数切换时刻没赶上（丢包/调度太晚），「一更新就断」的常见解释                            |
| 0x3B      | Unacceptable Connection Parameters            | 参数不可接受          | 对端拒绝参数请求（7.5）                                                                  |
| 0x3E      | Connection Failed to be Established           | 连接没能建立          | 建链阶段失败，归 [[ble-debug-ch05-connection-parameters\|第五章：连接建立与参数]]        |

> [!warning] 口径提醒：两处容易张冠李戴
> 其一，0x08 与 0x16 别混：0x08 是**超时**（没人主动），0x16 是**本地主机主动**（有人主动且就是本端）。其二，空口 LL_TERMINATE_IND 里携带的错误码与 HCI 事件里的 Reason 同属一张表（Core Spec 口径），但常见实现里主机发起断开时 LL 层填 0x13——同一件事在发起侧 HCI 记 0x16、对端 HCI 记 0x13、空口告别帧里常是 0x13，**三个位置读数不同不是矛盾**，是视角不同。

## 7.3 取证：谁先断——三源对齐一条时间线

### 7.3.1 三种证据源各自能回答什么

| 证据源     | 能回答                                         | 不能回答                          | 工具                                                                           |
| ---------- | ---------------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------ |
| App 日志   | 用户视角的断连时刻与报错文案                   | 谁先断、哪层断（App 报错≠链路断） | App 自身日志                                                                   |
| 主机栈 HCI | Disconnect Complete 的 Reason 与发起侧         | 空口上包是怎么没的                | `btmon` / 手机 HCI snoop / 设备端协议栈日志                                    |
| 空口抓包   | LL_TERMINATE 方向、断前事件健康度（重传/缺包） | 端内状态机为什么走                | nRF Sniffer + Wireshark（[[ble-debug-ch04-advertising-packets\|第四章]] 部署） |

Linux 侧全程录制 HCI 流（btsnoop 格式，Wireshark 可直接打开）：

```bash
sudo btmon -w ble_drop.log &                    # 全程录 HCI 命令与事件
bluetoothctl connect AA:BB:CC:DD:EE:FF
bluetoothctl info AA:BB:CC:DD:EE:FF             # Connected: yes/no，快速对账
bluetoothctl disconnect AA:BB:CC:DD:EE:FF       # 最便宜的「打点」实验：制造一次已知发起方
```

Wireshark 里筛断连事件（过滤器为真实语法）：

```text
bthci_evt.code == 0x05        # HCI Event: Disconnect Complete，展开读 Reason
```

手机侧取证操作（免费，且常是唯一能拿到手机视角 HCI 的路径）：

| 平台    | 动作                                                                       | 产物与用法                                          |
| ------- | -------------------------------------------------------------------------- | --------------------------------------------------- |
| Android | 开发者选项开「启用蓝牙 HCI 信息收集日志」→ 复现 → 生成 bugreport           | `btsnoop_hci.log`，Wireshark 直接读（平台功能口径） |
| Android | 复现前后各抓一次 `adb shell dumpsys bluetooth_manager`（启用 adb 时）      | 连接状态与断连记录快照（实现口径）                  |
| iOS     | 无用户级 HCI 导出；用 Sysdiagnose 里的蓝牙日志（系统诊断包口径，解析繁琐） | 仅在必要时用；通常以设备侧 + 空口替代               |
| 通用    | 断连瞬间用第二台手机 nRF Connect 扫描并截屏                                | 「链路是否真断」的最快证词（7.1 判别法）            |

btmon 文本流里的断连长这样（**格式示意**）：

```text
> HCI Event: Disconnect Complete (0x05) plen 4        #26582 12:03:41.882310
      Handle: 64
      Reason: Remote User Terminated Connection (0x13)
```

### 7.3.2 谁先断：一棵决策树

```text
拿到一次断连的三份证据
 ├─ 空口有 LL_TERMINATE_IND（在 Wireshark 解码树里展开 LL Data PDU：LLID=11 的
 │   Control PDU，OpCode=LL_TERMINATE_IND；字段名随版本，按 OpCode 名检索）
 │    ├─ 方向 手机→设备：手机侧发起（手机 HCI 0x16 / 设备侧 0x13）
 │    │    ├─ 断点对齐熄屏/切后台/App 被杀    → 软件伪装硬件（7.4.3）
 │    │    └─ 断点对齐用户操作（点断开/解绑）  → 正常业务，不是故障
 │    └─ 方向 设备→手机：设备侧发起（设备 0x16 / 手机 0x13）
 │         ├─ 设备日志有 assert/复位记录       → 固件塌了（7.4.4）
 │         └─ 设备日志干净、断前 RSSI 恶化     → 设备主动止损，查固件策略
 ├─ 空口无告别帧、包戛然而止 → supervision timeout（两端 0x08）
 │    ├─ 断前重传增多/连接事件缺失             → 干扰或弱信号（7.4.1/7.4.2 → 第八章）
 │    └─ 断后设备立即恢复广播 + 有复位记录     → 设备重启伪装成断线（7.4.4）
 └─ 三源都查无断连记录 → 「断」在 App 会话层 → 7.4.3
```

### 7.3.3 三源对时：让三份日志共用一块表

App 日志、手机 HCI snoop、设备端日志、空口 pcap 分属四个时钟域，不对时一切「同时发生」都是巧合（WiFi 系列的同款纪律见 [[wifi-hw-debug-ch05-disconnect-roaming|WiFi 调试（五）]] 5.4）。BLE 的对时锚点更便宜：**主动断一次**——`bluetoothctl disconnect`（或 App 里点断开）制造一次发起方已知的告别帧，三路证据里找同一个 LL_TERMINATE_IND/Disconnect Complete，把各钟偏移一次性钉住。Android 侧的免费证据：开发者选项「启用蓝牙 HCI 信息收集日志」，从 bugreport 里取 `btsnoop_hci.log`（平台功能口径），Wireshark 直接读。

对齐后的拼图（**格式示意**，时间为示意值）：

```text
UTC(换算后)     App 日志                            手机 HCI(snoop)               空口(Sniffer)
12:03:41.608    ——                                  （无本地断开命令）            最后一段 LL Data PDU，重传密集
12:03:41.612    onConnectionStateChange(status=8)   Disconnect Complete 0x08      包戛然而止（无告别帧）
12:03:42.050    开始重连扫描                                                        设备 400 ms 后恢复广播
判读：无告别帧 + 两端 0x08 → supervision timeout；断前重传密集 → 干扰/弱信号家族（7.4.2）
```

## 7.4 根因家族逐个过

### 7.4.1 距离与遮挡：链路预算到边（真·射频）

特征指纹：错误码 0x08；断连与位置强相关（口袋、门外、电梯）；断前 RSSI 已滑到 -85~-90 dBm 一带（**经验口径**，随芯片灵敏度差异大）。人体是 2.4 GHz 的大号衰减器，贴身遮挡吃掉 10~20 dB 链路余量是工程常见量级（**经验口径**），「放进口袋就断」多半就是这一族——产品形态决定人体遮挡不可避免，对策在链路预算与天线设计（第八章 8.4/8.6），而不是把 supervision timeout 调小（那只会更快发现断线，治不了病）。

这一族内部再用「位置标签」细分，取证时让用户/测试带位置描述报障，价值极大：

| 位置子模式         | 典型衰减来源                          | 复测要点                                 |
| ------------------ | ------------------------------------- | ---------------------------------------- |
| 口袋/背包/手腕内侧 | 人体遮挡（10~20 dB，经验口径）        | 同一姿势定距复测 RSSI；注意佩戴松紧差异  |
| 隔一堵墙/门外      | 建筑穿透（每堵墙 10~15 dB，经验口径） | 换材料对照（砖/混凝土/玻璃差异大）       |
| 电梯/金属柜内      | 法拉第笼式屏蔽，几乎无解              | 测「出梯即恢复」的时延，验证自动重连策略 |
| 仅某一房间断       | 局部干扰源 + 遮挡叠加                 | 该房间时段复测，与 7.4.2 干扰家族交叉    |

### 7.4.2 干扰：2.4G 的邻居们

特征指纹：0x08 成簇出现在特定时段/地点（微波炉工作的厨房、WiFi 高峰的客厅）；断前连接事件重传飙升；空口抓包见 CRC 错帧或成片噪声（嗅探器口径）。WiFi 与微波炉的机理与现场指纹在 [[ch14-interference-coexistence|射频入门（十四）]] 讲透，本章不重复；BLE 侧的自救手段是 AFH 自适应跳频——机制与取证（抓 LL_CHANNEL_MAP_IND 看信道地图变化）在第八章 8.5 展开。判别捷径：**同一位置换时段复测**，断连率随时段波动 → 干扰家族。

### 7.4.3 手机省电杀后台：「软件伪装硬件」

掉线投诉里最冤的一族：设备射频好好的，锅却先扣到固件头上。两种假象要分清：

| 假象                             | 机制                                                                      | 空口/HCI 指纹                                        |
| -------------------------------- | ------------------------------------------------------------------------- | ---------------------------------------------------- |
| 链路活着，App 会话死了           | 省电策略冻结 App 进程，App 与云端的会话断/上报停，用户感知为「设备掉了」  | 三源均无断连记录；第二台手机扫不到设备（仍处连接态） |
| App 进程被杀，框架回收 GATT 连接 | 持有 BluetoothGatt 的进程死亡，系统侧拆链（**行为随 OS 版本与实现差异**） | 空口手机→设备 LL_TERMINATE_IND；手机 0x16/设备 0x13  |

「App 进程被杀≠蓝牙断连」——被杀只保证 **App 层**的连接对象消失；链路是否被系统回收取决于平台与场景（iOS 的 state restoration 可由系统维持连接，Android 不同版本行为亦有差异，**官方文档口径，随版本演进**）。所以判别不能靠背结论，要靠四步：

```text
判别法四步（复现现场照做一遍）
 ① 立刻用第二台手机 nRF Connect 扫描：扫不到 → 链路还连着（假象一坐实）
 ② 看设备侧心跳/上报计数是否连续：连续 → 链路从未断，断的是 App 会话
 ③ 手机 btsnoop 里搜 Disconnect Complete(0x05)：有 0x16 → 系统侧真拆链（假象二）
    其时刻对照熄屏/切后台/省电策略触发点，对上即定案
 ④ 开关对照：把 App 加入电池优化白名单（或保持前台服务）复测——消失即归因
```

对策落在两侧：手机侧按平台规范用前台服务/白名单（写进 App 交付文档）；设备侧容忍手机侧的主动断开，做好自动重连。责任判定一句话：**这一族不是射频的锅，别去改发射功率**。

### 7.4.4 固件 assert：设备重启伪装成断线

指纹最硬的一族：固件跑飞/assert/看门狗复位后，链路随控制器一起消失——两端 HCI 各报 0x08（超时语义），空口表现是「戛然而止」，与弱信号超时难以区分。三个区分点：

| 观察点         | 弱信号/干扰超时                    | 固件重启                                                                                |
| -------------- | ---------------------------------- | --------------------------------------------------------------------------------------- |
| 广播恢复时延   | 固件重连策略决定，通常数秒或不广播 | 复位后数百 ms 内即以「全新身份」恢复广播                                                |
| 设备端复位记录 | 无                                 | 有：复位原因寄存器/panic backtrace（实现口径，nRF RESETREAS、ESP32 panic 各查各家文档） |
| 断前设备日志   | RSSI 曲线、重传统计异常            | assert/看门狗打印在前，断连是结果不是原因                                               |

判别口诀沿用 WiFi 系列的：**掉线前有固件报错 = 塌栈**（修固件、查看门狗与复位路径——机制见 [[ch13-timers-watchdogs|FreeRTOS（十三）]]）；供电劣化也会以重启形式出现，查电源完整性（[[ch12-power-supply|射频入门（十二）]]）；**掉线前无本地异常 = 链路问题**，回 7.4.1/7.4.2。

## 7.5 参数过激导致的断连：一条检查式兜底

第五章 5.3.1 讲过三参数的合法范围与硬性约束式，这里把它变成断连排障的**检查式**——凡「连上秒断」「一更新参数就断」「换手机后偶发断」，先跑一遍再谈射频：

```text
检查式（对断连前实际生效的参数逐条跑，Core Spec 口径）
 ① T_out > 2 × (1 + latency) × interval      # 硬性约束，违反即非法参数
 ② latency × interval ≤ 产品允许的最大响应延迟 # 业务口径（第九章 9.4 再算一遍）
 ③ 参数更新时机合法                            # 平台口径：设备发起更新过早会被拒（Android
                                               #   平台对更新时机的窗口要求，具体数值待核对）
踩线翻车的经典组合（教学计算示意）：
 interval = 7.5 ms，latency = 99 → 要求 T_out > 2 × 100 × 7.5 ms = 1500 ms
 固件配 T_out = 1000 ms → 违反 ①：更新被拒（0x20/0x3B）或链路刚切参数即断
```

另一类「伪掉线」也要在这一节拆掉：**latency > 0 时的合法缺席**。从机可以在没有数据时连续跳过 latency 个连接事件，「看起来很久不应答」是协议允许的正常行为（Core Spec 口径）——抓包里事件以 interval×(latency+1) 的节奏出现、LL 流健康，就不是掉线。判定动作：把抓包里相邻连接事件的间隔与 interval×(latency+1) 对一遍，对上了就是合法跳过（第五章预告过的展开，此处兑现）。

参数过激的三种断连形态，错误码与处理各不相同：

| 形态                   | 空口/HCI 表现                           | 错误码常客 | 处理                                                     |
| ---------------------- | --------------------------------------- | ---------- | -------------------------------------------------------- |
| 更新请求被拒           | L2CAP/LL 层收到拒绝，链路继续但参数没变 | 0x20/0x3B  | 按检查式重算后重新请求；对账三份参数证据（第五章 5.3.3） |
| 参数切换即断           | LL_CONNECTION_UPDATE_IND 后立刻告别     | 0x28 伴生  | instant 调度留足时间；排查切换期间的丢包                 |
| 更新成功但业务超时误判 | 链路活着，App 层超时重连风暴            | 无断连记录 | App 超时 ≥ interval×(latency+1) + 余量                   |

## 7.6 教学案例完整复盘：口袋断的两轮真相

**教学复盘案例，取材自常见故障模式综述**（非真实事故报告）：一款 BLE 手环进入小批量试产，售后渠道两周内收到 37 起「放进口袋/背包装一会儿就断，拿出来又自己连上」的投诉；同时测试部报告「熄屏放桌上一夜，早上 App 显示已断」。完整取证链走一遍：

**第一步：判层 + 直方图。** 汇总所有断连的 App 侧时刻与位置标签：61% 与「贴身/入包」强相关，39% 集中在「熄屏后 30~60 秒」。两类时刻分布截然不同——先怀疑是两种病。

**第二步：三源对齐「熄屏断」。** 按 7.3.3 打点对时，复现「熄屏断」（**格式示意**）：熄屏后 42 秒，空口出现手机→设备的 LL_TERMINATE_IND，手机 HCI 记 0x16、设备记 0x13；设备侧心跳计数在断连前后**连续无缺口**；把 App 加入电池白名单后该类断连消失。定案：省电策略杀后台导致系统回收连接——软件伪装硬件，锅不在射频（7.4.3 假象二）。

**第三步：三源对齐「口袋断」。** 剩余样本空口无告别帧、两端 0x08；断前最后一段连接事件重传密集；设备侧 RSSI 日志显示入包瞬间 RSSI 从 -78 dBm 滑到 -91 dBm（**示意值**）。第二次复现时嗅探器同时盯广播信道：断连后 600 ms 设备恢复广播，**无复位记录**——排除固件重启（7.4.4 的区分点用上）。定案：人体遮挡把链路压到灵敏度边缘，supervision timeout 到期，静默死亡（7.4.1）。

**第四步：双头修复 + 闭环。** App 侧上白名单引导与自动重连（治熄屏断）；硬件侧复查天线净空——发现量产外壳的天线净空区贴了导电泡棉，撕掉后同位置入包 RSSI 抬回 6 dB，断连率降一个量级（**示意值**，天线与净空的展开在 [[ble-debug-ch08-ble-rf-phy|第八章]]）；固件侧按第八章重算链路预算留 10 dB 余量。复测两周，两类投诉均归零——闭环。

复盘模板：**分类别 → 对时 → 三源定方向 → 错误码定家族 → 找触发器 → 双侧修复 → 复测归零**。与 [[wifi-hw-debug-ch05-disconnect-roaming|WiFi 调试（五）]] 的掉线复盘同构，只是「定方向」的空口证据从 deauth 方向换成了 LL_TERMINATE 方向与告别帧有无。
