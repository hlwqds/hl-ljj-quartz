## 9.1 现场引入：三类「慢」，两根轴

BLE 的「慢」投诉集中在三个开场白，但它们落在两根**互相独立**的轴上——吞吐（单位时间搬多少数据）与延迟（一次交互等多久）。混轴排查是这一类问题最大的弯路：

| #   | 现场陈述                     | 表面读数             | 直觉归因（多数是错的） | 本章归宿       |
| --- | ---------------------------- | -------------------- | ---------------------- | -------------- |
| A   | 「传感器数据刷新慢」         | 界面数字几秒才跳一次 | 「传感器采样慢」       | 9.4 延迟轴     |
| B   | 「OTA 固件升级要等十几分钟」 | 进度条龟速           | 「服务器/手机卡」      | 9.2/9.3 吞吐轴 |
| C   | 「按键到灯亮半秒延迟」       | 体感迟钝             | 「芯片性能不行」       | 9.4 延迟轴     |

先分轴再下钻：

```text
「慢」的两根轴
 吞吐轴：单位时间内搬运的数据量不够
   → 主嫌疑：conn interval 太大、MTU/DLE 没开、PHY 是 1M   → 9.2/9.3
 延迟轴：单次交互的等待时间太长
   → 主嫌疑：interval×(latency+1) 太大、read 轮询式交互     → 9.4
 两轴共享的背景板：链路质量（重传吃掉有效带宽）与共存挤压   → 第八/七章
```

与 [[wifi-hw-debug-ch06-throughput-debugging|WiFi 调试（六）]] 的「物理速率≠有效吞吐」是同款问题、同款算法：先算理论上限，再对实测，差值逐项归因——只是 BLE 的开销科目换了一套（9.2 的账单）。同时记住第七章的教训：**先确认链路不断**（重连风暴会让一切吞吐测量作废），再谈快慢。

## 9.2 吞吐模型：connection event 的带宽账单

### 9.2.1 调度模型：每 interval 一个窗口，窗口内拼命装

连接建立后，两端以 conn interval 为节拍约定「连接事件」（connection event）：每到锚点，双方醒来、跳到约定信道、互相发包；**窗口内可以连发多对包**（数据 PDU → 150 µs IFS → 空口确认 PDU → 150 µs IFS → 下一对），直到没数据或窗口结束（调度在 central，Core Spec 口径）。latency > 0 时从机可整段跳过窗口（功耗账在 [[ble-debug-ch10-ble-power-debug|第十章]]）。

```text
一个连接事件（教学示意）
 锚点 ─┬─ M→S 数据PDU(≤251B) ─IFS 150µs─ S→M 确认PDU ─IFS 150µs─ M→S 数据PDU ─…
       └─ 窗口结束 → 双方睡眠 interval × (1+latency) 后再醒
 吞吐上限 ≈ 事件内装下的应用字节数 ÷ conn interval
```

由此得出 BLE 吞吐的第一公式：**interval 越大，分母越大，吞吐越低**——interval 从 15 ms 放大到 500 ms，同样的「事件内装包能力」吞吐直接掉 33 倍。这就是「OTA 慢」最常见的单一病因。

### 9.2.2 理论上限的算式（教学估算口径）

单位周期由链路层开销钉死：LL Data PDU 固定开销 10 B（前导 1 + 接入地址 4 + 报头 2 + CRC 3，未编码 PHY 口径），应答间隔 IFS 固定 150 µs。按「数据 PDU → IFS → 空 PDU 确认 → IFS」循环估算链路层天花板：

| 配置                    | 单周期算式                                        | 应用层吞吐上限（教学估算）         |
| ----------------------- | ------------------------------------------------- | ---------------------------------- |
| 1M PHY + DLE 27（默认） | (27+10)×8 µs + 150 + 80 + 150 ≈ 676 µs 装 20 B    | ≈ 237 kb/s（MTU 23 时每包仅 20 B） |
| 1M PHY + DLE 251        | (251+10)×8 µs + 150 + 80 + 150 ≈ 2.47 ms 装 244 B | ≈ 790 kb/s                         |
| 2M PHY + DLE 251        | ≈ 1.38 ms 装 244 B                                | ≈ 1.4 Mb/s                         |
| Coded S=2/S=8           | 时间 ×2/×8（第八章口径）                          | ≈ 400/100 kb/s 量级                |

> [!warning] 三层折扣，账要逐层对
> ①链路层上限（上表）②interval 折扣：每事件装 6 对包、interval 30 ms → 6×244 B ÷ 30 ms ≈ 390 kb/s；③实际达成：手机侧调度余量、协议栈缓冲、应用流控会再打七折上下（**量级综述口径**，NUS 类应用实测常见数百 kb/s）。实测远低于三层折扣后的预期，才谈「有病」，按 9.5 取证。

把 interval 折扣单独拉成网格（1M PHY + DLE 251，每事件按 6 对包估，**教学估算口径**）——排障时拿实测值对格入座：

| conn interval   | 每事件装载（6×244 B） | 吞吐量级（教学估算）   | 典型用途        |
| --------------- | --------------------- | ---------------------- | --------------- |
| 7.5 ms          | 1464 B                | ≈ 190 kb/s（上限附近） | 音频类/高速回传 |
| 15 ms           | 1464 B                | ≈ 97 kb/s              | OTA/批量传输    |
| 30 ms           | 1464 B                | ≈ 49 kb/s              | 活跃传感器      |
| 100 ms          | 1464 B                | ≈ 15 kb/s              | 常规上报        |
| 500 ms          | 1464 B                | ≈ 2.9 kb/s             | 低功耗常态      |
| 4 s（规格上限） | 1464 B                | ≈ 0.37 kb/s            | 信标式温湿度    |

读法：**同一套链路层能力，interval 一项就把吞吐拉开三个数量级**——所以吞吐排障第一问永远是「现在实际生效的 interval 是多少」（9.3.1 的对账法），而不是「芯片快不快」。

还有一个常被忽略的调度细节：**窗口装不满的三种姿势**（Core Spec 调度口径 + 实现综述）。其一，central 提前收工——没数据可发时 central 可以随时结束事件，从机即使有数据也得等下一个窗口（所以 peripheral 侧的供数策略要「攒批」：事件前排好队，别一事一包）；其二，从机漏窗——latency 跳过合法但撞上供数时刻就是白等一个窗口；其三，流控反压——协议栈发送缓冲满时应用层的 write 会阻塞，抓包表现为「事件空转」（9.5.2 的第三行判读）。三种姿势的取证都落在「填充率」这一个读数上，这也是 9.5.2 把它立为头号指标的原因。

## 9.3 加速三件套：interval、DLE/MTU、PHY

### 9.3.1 第一件：conn interval 收紧（分母游戏）

interval 合法范围 7.5 ms~4 s（Core Spec 口径），但**下限实际由手机说了算**：iOS 建议按 15 ms 倍数申请，Android 由栈按前台/后台策略改判——完整口径表在 [[ble-debug-ch05-connection-parameters|第五章：连接建立与参数]] 5.3.3。工程要点两条：其一，**参数是手机批的**——设备发起 L2CAP 连接参数更新请求后，以 btmon/抓包里实际生效值为准，别信固件里写的数（第五章的「三份证据对账法」直接复用）；其二，**更新时机有讲究**——连接刚建立就发起更新请求，可能撞上平台对更新时机的要求（Android 平台对请求时机的窗口要求，具体数值**待核对**），被静默拒绝后协议栈若不重试，参数就永远停在初始慢档（9.6 案例的元凶之一）。

btmon 里一次成功的参数更新长这样（**格式示意**，请求值→批准值的落差一目了然）：

```text
> ACL Data RX: Handle 64 (L2CAP: Connection Parameter Update Request)
      Interval Min: 12 (15 ms)   Interval Max: 12 (15 ms)
      Slave Latency: 0           Supervision Timeout: 400 (4 s)
< ACL Data TX: Handle 64 (L2CAP: Connection Parameter Update Response)
      Result: Accepted
> HCI Event: LE Connection Update Complete (0x3e) plen 4
      Status: Success   Conn_Interval: 24 (30 ms)   ← 手机改判：15 ms 没批，批了 30 ms
      Conn_Latency: 0   Supv_Timeout: 480 (4.8 s)
判读：请求被接受 ≠ 请求值生效；吞吐估算永远用 Update Complete 里的生效值
```

### 9.3.2 第二件：DLE 与 MTU——两层独立的账

这是被误解最多的一件，先把两层拆清（Core Spec 口径）：

| 层            | 参数        | 默认 | 上限           | 谁来扩                         | 不扩的后果                      |
| ------------- | ----------- | ---- | -------------- | ------------------------------ | ------------------------------- |
| 链路层（LL）  | Data Length | 27 B | 251 B          | 任一端发起 LL_LENGTH_REQ/RSP   | 每包只装 ≤27 B，事件窗口装不满  |
| 主机层（ATT） | MTU         | 23 B | 517（LE 上限） | **手机 App 发起 Exchange MTU** | ATT 每包净荷只有 20 B，DLE 白扩 |

关键交互：**MTU 23 时 DLE 扩了也白扩**——ATT 通知的净荷被 MTU 钉死在 20 B，链路层包再大也只装 20 B 应用数据（上表第一行的 237 kb/s 上限就是这么来的）。而 MTU 扩到 247 后，配合 DLE 251 恰好一包装下一个完整 ATT PDU（251 − 4 L2CAP 头 − 3 ATT 头 = 244 B 净荷）。工程动作清单：固件端使能 DLE 与 MTU 上限声明；**App 端连接后立即请求 requestMtu**（iOS 由系统按协商结果处理，Android 显式调）；扩完用 9.5 的抓包读数验证，不靠「代码里写了」。

### 9.3.3 第三件：2M PHY，以及 Coded PHY 的反向用法

2M PHY 让同一包的空口时间减半，吞吐上限翻倍（9.2.2 表），还顺带缩短 radio-on 时间（功耗双赢，[[ble-debug-ch10-ble-power-debug|第十章]] 的账）。但它是协商制：任一端不使能就静默留在 1M——确认方法在 [[ble-debug-ch08-ble-rf-phy|第八章]] 8.2.3，不重复。反向地，**Coded PHY 是用速率买距离**：S=8 时吞吐上限掉到百 kb/s 量级，「为了远距选了 Coded 又抱怨 OTA 慢」是设计矛盾不是故障——距离与速率的取舍要先在产品定义里做完。

三件套叠加的收益梯度（教学估算，1M→2M、DLE27→251、interval 500 ms→15 ms 全链打通时的量级）：

```text
初始（默认全家桶）：MTU 23 + DLE 27 + interval 500 ms ≈ 20 B × 2 events/s = 40 B/s
只修 MTU+DLE：      244 B/包 × 2 events/s              ≈ 0.5 kB/s
再修 interval：     ~6 包/事件 × 244 B ÷ 15 ms          ≈ 97 kb/s（链路层上限内）
再上 2M PHY：       ≈ 1.4 Mb/s 上限（实际数十~百 kb/s 视调度）
读法：第一步百倍、第二步百倍、第三步翻倍——顺序错 Step 一步，全盘慢一个量级
```

## 9.4 延迟优化：推送、轮询与 latency 的三角

吞吐之外，交互类应用（按键、控制、报警）卡的是**单次往返的等待**。三笔账：

| 设计选择                  | 延迟构成                                                       | 适用场景                             |
| ------------------------- | -------------------------------------------------------------- | ------------------------------------ |
| notify 推送（设备主动发） | 事件排队：0 ~ interval×(latency+1)                             | 传感器上报、按键事件（默认选它）     |
| read 轮询（手机定期读）   | 排队 + 完整请求/响应往返 + App 轮询周期                        | 仅限低频状态查询；高频轮询既慢又费电 |
| slave latency > 0         | 最坏多等 latency×interval（合法跳过，第七章 7.5 的伪掉线同源） | 无数据时段省电（第十章）             |

顺带钉死 notify 与 indicate 的取舍（ATT 机制口径，第六章的 PDU 家族在此应用）：notify 不需对端确认，一发即忘，延迟与吞吐都最优；indicate 要求对端回确认后才算送达，可靠性高一级，代价是每个 PDU 多一个往返——批量数据流里 indicate 会把有效吞吐腰斩量级。所以 **OTA/流数据用 notify，配置写入回执用 indicate 或写响应**，混用错位也是「莫名变慢」的常见小病（核对 CCCD 订阅的 0x0001/0x0002 位即可，第六章口径）。

权衡的核心式：**响应延迟上限 ≈ (latency + 1) × interval**（Core Spec 调度口径）。HID 类（键盘/遥控器）的经典配方是 interval 7.5~15 ms + latency 4——没按键时省电，按键时因 interval 本身极小，最坏延迟仍可接受；数据推送类（仪表刷新）则应 interval 适中 + latency 0~1，把最坏延迟压到亚秒级（以上为常见配方量级，**经验口径**，按产品延迟预算反推）。

把一次「按键→手机收到 notify」的等待拆成四段（教学示意），延迟病灶当场现形：

```text
t0        按键事件发生（设备侧）
t0→t1     设备内部处理：采样/去抖/协议栈入队          ms 级（正常可忽略）
t1→t2     等下一个连接事件：0 ~ interval × (latency+1)   ← 大头在这里
t2→t3     事件内发送 + 重传（链路差时 +1~n 个 interval） ← 射频背景板（第七/八章）
t3→t4     手机协议栈→App 分发                            ms 级
延迟病灶自查：t2 段长 → 查 interval/latency；t3 段抖 → 查重传与链路质量；
             t4 段长 → 查 App 线程与省电（第七章 7.4.3 的软件家族）
```

反模式清单：用 read 轮询冒充推送（App 定时器 1 s 一读，刷新慢的锅在 App 设计）；给推送类应用配大 latency 省电（省出半秒延迟，售后背锅）；把「延迟大」当吞吐问题去缩 MTU（方向反了，回 9.1 分轴）。

## 9.5 实测方法：回环、工具与填充率

### 9.5.1 NUS 风格回环测试（无仪器基线法）

Nordic UART Service（NUS）是事实上的吞吐基准载荷：服务 `6E400001-B5A3-F393-E0A9-E50E24DCCA9E`，写特征（手机→设备）`…0002…`，通知特征（设备→手机）`…0003…`（Nordic 官方定义口径）。回环法三步：固件把收到的写数据原样 notify 回去；手机按固定块长连续写入并计数；按「收到字节数 ÷ 时间窗」算双向吞吐。

| 步骤 | 动作                                                | 要点                                       |
| ---- | --------------------------------------------------- | ------------------------------------------ |
| 1    | nRF Connect 连接设备，连接详情记下 interval/MTU/PHY | 参数层底账，先写进测试记录                 |
| 2    | 开启通知特征的 Notify（CCCD 订阅，第六章口径）      | 忘开 CCCD → 一个包都收不到，别误判为「慢」 |
| 3    | 对写特征按固定块长循环写入，记录写入字节/时间       | 块长 = MTU 净荷的整数倍最有意义            |
| 4    | 统计回环收到的通知字节与时间窗                      | 双向吞吐分别记录；注意方向不对称           |
| 5    | 同配置复测 3 次取均值；改一个变量重测               | 对照纪律与 WiFi 章相同                     |

成规模测量建议直接跑芯片厂商的官方吞吐测试例程（Nordic/Espressif 均有，实现口径），手机侧用其配套 App 或脚本计数。

### 9.5.2 空口抓包：看事件填充率与真实包长

nRF Sniffer 抓连接期流量（部署见 [[ble-debug-ch04-advertising-packets|第四章]]），过滤器与统计为真实语法：

```bash
# 只看 ATT 通知（设备→手机的数据流）
btatt.opcode == 0x1b
# 写命令（手机→设备方向）
btatt.opcode == 0x52
# 离线统计通知字节数（配合时间窗换算吞吐）
tshark -r nus.pcap -Y "btatt.opcode == 0x1b" -T fields -e frame.len | awk '{s+=$1} END {print s}'
```

事件填充率的肉眼判读（**格式示意**，时间戳为示意值）：

```text
事件号   时刻(s)   interval   事件内 PDU 序列                        填充率判读
#412     6.180     30 ms      M→S 251B ×6 + S→M 空PDU ×6             满：链路层在吃满窗口
#413     6.210     30 ms      M→S 27B ×1 + S→M 空 ×1                 1/6：包小（DLE/MTU 没开）
#414     6.240     30 ms      M→S 无，S→M 空 ×1                       空转：应用层供数不足
判读：填充率低 → 先分清「包太小」（9.3.2）还是「供数不足」（应用层）；填充满还慢 → 查 interval 与 PHY
```

三路读数交叉：回环吞吐（应用层）× 填充率（链路层）× nRF Connect 显示的 interval/MTU/PHY（参数层）——哪一层先断档，瓶颈就在哪一层。

### 9.5.3 没有嗅探器时的降级测量

手头没有第二块板子当嗅探器时，参数层与应用层两路读数仍能定案多数问题：

```text
① 参数层：nRF Connect 连接详情的 interval/MTU/PHY —— 9.3 三件套逐项对
② 应用层：回环吞吐对照 9.2.2 的表格 —— 差距 > 一个量级即有病
③ 时序层：设备端在 notify 回调里打印时间戳与序号（格式自定），
   与手机端接收时间戳对差值 —— 差值大 = 排队/漏窗，差值稳定小 = 链路健康
缺的一路只有「事件填充率」，它决定 9.7 表里「包长正常还慢」分支的走向——
判定不了时按「先修三件套、再复测」推进，多数现场到这一步已经闭环。
```

## 9.6 教学案例复盘：OTA 慢的三层病

**教学复盘案例，取材自常见故障模式综述**（非真实事故报告）：一款 BLE 设备的固件 OTA 功能，升级一个 200 KB 的包要等十分钟级（**教学估算场景**），用户投诉集中在 Android 机型。复盘走一遍：

**第一步：分轴 + 留证。** OTA 慢是吞吐轴问题，按 9.2 先算账再抓包。空口抓包 + 手机 nRF Connect 截图 + 设备端协议栈日志三路留证。

**第二步：参数层读数。** 连接详情显示：MTU 23、interval 50 ms、latency 0、1M PHY。抓包确认每个事件只装 1 对 27 B 的 LL 包——ATT 净荷 20 B/包，即 20 B ÷ 50 ms = **400 B/s**（教学估算），200 KB 要 8 分钟级：账对上了，慢在参数层，不在射频。

**第三步：查「为什么参数没扩」。** 固件日志显示：设备在连接建立后立刻发了 L2CAP 连接参数更新请求（要求 15 ms/latency 0）——按平台口径，连接伊始就发更新可能撞上 Android 对更新时机的窗口要求（**待核对**），请求被拒且固件**没有重试**，interval 停在 50 ms；MTU 则因 App 从未调用 requestMtu 而停在 23；DLE 双端都没发起。三层病一次全中：**没协商的参数 + 没发起的 MTU + 没使能的 DLE**。

**第四步：修复与验证。** 固件：连接 5 秒后发起参数更新（规避时机窗口）并对拒绝做有限重试；App：连接成功后 requestMtu(247)；两端使能 DLE，PHY 更新到 2M。OTA 包照常打包（nrfutil 6.x 口径）：

```bash
nrfutil pkg generate --hw-version 52 --sd-req 0x0100 \
  --application app.bin --key-file key.pem app_dfu_package.zip
```

修复前后抓包对比（**格式示意**）：修复前事件内 27 B×1 对、interval 50 ms；修复后 251 B×6 对、interval 15 ms、2M PHY——链路层吞吐从 0.4 kB/s 量级抬到数十 kB/s 量级（教学估算口径；实际达成受 DFU 流控与手机调度打折），200 KB 的升级从「分钟级」压进「十秒级」。复测三台不同品牌 Android 机型一致——闭环。

```text
修复前（三病并发，格式示意）              修复后（三件套全开，格式示意）
interval 50 ms（请求被拒未重试）          interval 15 ms（5 s 后请求获批）
MTU 23 → ATT 净荷 20 B/包                 MTU 247 → ATT 净荷 244 B/包
DLE 未使能 → LL 包 27 B                   DLE 251 → LL 包 251 B
1M PHY                                    2M PHY（协商成功）
事件填充率 1/6，ATT 包 27 B               事件填充率 6/6，ATT 包 251 B
→ 0.4 kB/s 量级，分钟级                   → 数十 kB/s 量级，十秒级（教学估算）
```

复盘要点三条：**先算账再抓包**（9.2 的账单直接指认参数层）；**三层参数独立协商、缺一塌一截**（MTU 归 App 发起、DLE 归协议栈、interval 归平台审批）；**被拒绝的请求必须有重试**（静默失败是 BLE 参数协商的第一隐形坑）。同一模板可平移到 9.1 的 A/C 类现场：分轴 → 参数层读数 → 填充率定层 → 三方协作修复。

## 9.7 收尾：吞吐/延迟根因速查表

| 症灶（证据）                            | 层       | 下一步取证                           | 对策                                              |
| --------------------------------------- | -------- | ------------------------------------ | ------------------------------------------------- |
| ATT 净荷 20 B/包（MTU 23）              | 主机层   | 连接详情读 MTU；抓 Exchange MTU      | App requestMtu；上限 517（Core 口径）             |
| 事件内包长 ≤27 B（DLE 未开）            | 链路层   | 抓包看 LL 包长；LL_LENGTH 过程       | 双端使能 DLE，251 生效                            |
| interval 50~500 ms 且固件「明明请求过」 | 参数层   | 三份证据对账（第五章 5.3.3）         | 时机合规后重试；按平台口径调请求值                |
| 事件填充率低但包长正常                  | 应用层   | 供数侧时序日志                       | 应用缓冲/流控优化，别动射频                       |
| 填充率满仍慢                            | 参数层   | interval 与 PHY 读数（第八章 8.2.3） | 缩 interval（手机约束内）；协商 2M                |
| 距离换来的慢（Coded S=8）               | 设计口径 | 确认 PHY 协商结果                    | 回产品定义：距离 vs 速率取舍                      |
| 刷新慢但吞吐正常                        | 延迟轴   | (latency+1)×interval 算最坏延迟      | read 轮询改 notify；latency 降档                  |
| 按键类偶发半秒延迟                      | 调度口径 | 抓包看跳过的事件段                   | interval 压小或 latency 减小，重算功耗（→第十章） |
| 时段性变慢伴随断连                      | 共存背景 | 第七章 7.4.2 + 第八章 8.5            | AFH/信道规划，回干扰家族                          |

> [!summary] 收束
> 吞吐排障的肌肉记忆三句话：**先分轴（吞吐还是延迟），先算账（interval 分母 × 事件内包数 × 包长三层），再分层对读数（参数层 → 链路层填充率 → 应用层吞吐）**。BLE 的「慢」绝大多数死在没协商的参数上——MTU/DLE/interval 各自独立协商，任何一层缺席都是量级损失；参数全对还慢，才轮到射频与共存背景板。省下来的 radio-on 时间怎么变成电池寿命，是下一章功耗调试的账。
