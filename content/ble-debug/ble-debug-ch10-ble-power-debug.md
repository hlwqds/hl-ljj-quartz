## 10.1 现场引入：BLE 功耗的三类病

第九章的 [[ble-debug-ch09-throughput-latency|吞吐与延迟]] 讲的是「跑得快不快」；本章讲的是「电池撑不撑得住」。BLE 产品天生长在电池上——手环、门锁、传感器标签、遥控器——功耗问题在这里出现的频率比 WiFi 产品高一个量级，而且呈现高度模式化：

| 类型                      | 典型描述                                                     | 第一直觉                                     | 常见重灾区                                                                |
| ------------------------- | ------------------------------------------------------------ | -------------------------------------------- | ------------------------------------------------------------------------- |
| A：规格 µA 级、实测 mA 级 | 「datasheet 说 system ON 几 µA，整机躺着也有 mA」            | 睡的是**错的模式**，或睡眠基电流被外设抬高   | 产品该睡 deep sleep 却维持着连接；广播开着没人连；LED/传感器/调试串口漏电 |
| B：续航比预算差 5 倍      | 「按平均电流算能用一年，实测两个月就没电」                   | 平均电流**算错了**：占空比或唤醒频次估计乐观 | 广播间隔配太密；conn interval 太小；latency 没用上；重连风暴              |
| C：电流忽大忽小           | 「同一批板子睡眠电流离散大」「功耗仪上时不时冒出一串大尖峰」 | 状态机**没睡稳**：某事件周期性把它拽醒       | 应用定时器打断；手机侧反复触发服务发现；链路不稳反复断连重连              |

BLE 的功耗病灶比 WiFi 更「薄」：BLE 的 RF 活动窗本来就是毫秒级的短脉冲，整机省电好与坏几乎完全由**协议节拍**决定。所以 BLE 功耗调试的第一性问题不是「电花在哪」，而是「**协议让设备醒了多少次**」——先做占空比的账（10.2），再看曲线对不对账（10.4、10.5）。

## 10.2 功耗模型：两套占空比账

### 10.2.1 一条公式打天下

与 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]] 同一套模型：`I_avg = D × I_active + (1 − D) × I_base`。BLE 的特殊性在于：**I_active 是 mA 级的短脉冲，I_base 可以做到 µA 甚至 nA 级**（芯片在 system OFF/deep sleep 保留 RAM 的典型值，以所用 datasheet 为准），于是平均电流几乎完全被占空比 D 支配。拿教学数字感受量级（**教学计算示意，非实测**）：设活动峰值 8 mA 量级、基电流 2 µA：

| 场景（教学计算示意）            | 唤醒周期 | 活动时长 | 占空比 | 平均电流    | 一节 200 mAh 纽扣电池理论寿命 |
| ------------------------------- | -------- | -------- | ------ | ----------- | ----------------------------- |
| 广播 20 ms 间隔，永不连         | 20 ms    | ~3 ms/窗 | ~15%   | ≈ 1.2 mA    | 约一周                        |
| 同上，广播 1 s 间隔             | 1 s      | ~3 ms/窗 | ~0.3%  | ≈ 26 µA     | 约一年                        |
| 同上，广播 10 s 间隔            | 10 s     | ~3 ms/窗 | ~0.03% | ≈ 4.2 µA    | 五年以上（基电流开始做主）    |
| 连接态 interval 7.5 ms          | 7.5 ms   | ~2 ms/窗 | ~27%   | ≈ 2.2 mA    | 几天                          |
| 连接态 interval 1 s + latency 4 | 4 s      | ~2 ms/窗 | ~0.05% | ≈ 6 µA 量级 | 年级                          |

这张表的结论同样值得抄在便签上：**降平均 = 降峰值 × 降占空比**。BLE 的活动峰值被 RF 物理层钉死（TX/RX 突发电流是芯片属性，抠不动几个 mA）；所以 BLE 功耗优化几乎全是**占空比游戏**——控制「多久醒一次、一次醒多久」。这与 WiFi 章的「换地板」（modem sleep → light sleep → deep sleep）不同：BLE 协议天生为占空比设计，地板本来就低，**账算错了比硬件选错了更常见**。

### 10.2.2 广播期的账：interval × 事件时长

广播态的模型最简单：每过一个广播间隔（advertising interval），在三个广播信道（37/38/39）上各发一个广播 PDU（Core Spec 口径，广播事件 = 三个信道上的发送 + 每个信道上短暂等听 scan response）：

```text
        （示意，非实测记录；一个广播事件 ≈ 三个信道的短突发）

电流
  │   ▂█▂ ▂█▂ ▂█▂                          ▂█▂ ▂█▂ ▂█▂
  │─────────────────────────────────────────────────  ← µA 级睡眠地板
  └────┬──────────────────────────────────────┬────► 时间
       ◄──────── 广播间隔 advertising interval ────►
       每 interval 一次广播事件：三个信道的 TX + 短暂 RX 等待
```

账目三要素：

| 要素     | 是谁决定的                                              | 调试要点                                                                              |
| -------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| 广播间隔 | 固件（Host 配置，Core Spec 规定合法范围与随机抖动规则） | 越大越省、越省越「难被发现」；上限与下限以所用 Core Spec 版本为准（待核对具体 ms 值） |
| 事件时长 | 广播 PDU 长度（含扩展广播时更长）+ 等 SR 时间           | 广播数据塞满（31 字节用尽、或扩展广播多 bunch）事件就变宽                             |
| 有没有RX | 广播类型：可连接/可扫描广播要开 RX 等扫描请求           | ADV_NONCONN 类广播省掉等待窗，是纯 beacon 产品的常用选择                              |

### 10.2.3 连接期的账：interval 与 latency 双杠杆

连接态是 BLE 省电的精髓：主从约定「每 conn interval 见一面」；从机还可以用 **slave latency**（从机延迟）声明「连续 N 个 interval 没我的事我可以不到场」——对表时钟是**主机的锚点**，从机每隔 (interval × (latency + 1)) 才需要实际收发一次：

```text
        （示意，非实测记录；latency=3，即每 4 个 interval 出席一次）

conn interval:  |--I--|--I--|--I--|--I--|--I--|--I--|--I--|--I--|
从机出席:              ▲                  ▲                  ▲
电流(从机侧):  ────────▄█▄────────────────▄█▄────────────────▄█▄──
                        ↑ 醒来收包/发包     ↑ 跳过 3 次不醒（省掉）
```

| 杠杆          | 作用                                       | 代价                                                                           |
| ------------- | ------------------------------------------ | ------------------------------------------------------------------------------ |
| conn interval | 每 interval 一次收发机会，决定「醒多密」   | interval 越大，单包数据延迟越大、吞吐越低（第九章的账）；范围以 Core Spec 为准 |
| slave latency | 从机连续缺席 N 个 interval，决定「醒多少」 | 对延迟敏感的应用（按键、告警）不能太大；主从任一方可发起参数更新协商           |
| 连接事件本身  | 事件内可以连发多包，决定「一次醒多久」     | DLE/大 MTU 让单事件更饱满（吞吐换效率，第九章）                                |

两套账的关系：广播态是「单方决定」（自己定 interval），连接态是「**双方合同**」（参数由主机/从机协商，任一方可发起 update）——这解释了为什么连接态功耗问题常有「对手戏」：你的固件配得再省，手机 App 一条参数更新请求就能把它改掉。10.5 的病灶会反复用到这一点。

## 10.3 机制盘点：BLE 是怎么省的

概念基础在第五章（连接参数）与第十章前的各章已建立，这里按**调试视角**盘点：每个机制在电流曲线上长什么样、由谁控制、坏了会怎么坏。

### 10.3.1 广播间隔：省电与可发现性的跷跷板

| 广播间隔量级   | 广播功耗（方向性） | 手机扫描发现速度                  | 典型用途                     |
| -------------- | ------------------ | --------------------------------- | ---------------------------- |
| 快（~20 ms）   | 高，占空比可观     | 秒级被发现                        | 配网页面打开时的「冲刺广播」 |
| 中（~100 ms+） | 折中               | 数秒内被发现                      | 通用外设的常态广播           |
| 慢（秒级）     | 极低，µA 级平均    | 扫描窗口/间隔不巧时**很久扫不到** | 门锁、标签等「不必秒连」产品 |

两个容易踩的坑：一是**许多手机 App 的扫描本身就是占空比的**（scan interval 大于 scan window，窗口之间不扫），你的广播事件可能恰好落进扫描空档——「扫不到」未必是广播太慢，见第四章；二是广播间隔有 Core Spec 规定的**随机抖动**要求（避免多设备广播事件永久碰撞），所以电流曲线上的广播尖峰间距天然有轻微不均匀，别把抖动当病灶。

### 10.3.2 slave latency：深睡的正确姿势

latency 是从机省电的主杠杆，但生效有前提：**没有数据要发、也没有要收**。从机缺席的 interval 里若有主机发来的数据，从机必须照常出席——所以「配了 latency 却不省」的排查方向是：谁在源源不断地给从机发东西（手机 App 的轮询、notify 确认、链路层保活类行为）。另一个前提是**参数真的谈下来了**：latency 在 CONNECT_IND 与后续 LL 连接参数更新里声明，固件里配的值要和空口实际协商值核对（第五章方法、btmon 看 LL_UPDATE 事件，第二章工具）。

### 10.3.3 连接事件提前唤醒的代价

从机不是掐着点才醒：因为**睡眠时钟有误差**，从机要提前一点醒来把时钟对齐、把接收窗开好——时钟越糙，提前量越大，每次「出席」的真实时长越长。这就是 sleep clock accuracy（睡眠时钟精度）参数存在的意义：它写进连接建立时的协商里，精度越差（比如用便宜的内部 RC 振荡器），从机每场约会要多醒一段「候场时间」（具体量级随芯片与漂移而定，以芯片手册为准，**待核对**）。调试含义：电池产品的晶振/时钟方案是功耗参数，不只是 BOM 成本参数（时钟概念的延伸见 [[ch11-crystal-clock|射频入门（十一）]]）。

### 10.3.4 广播与连接的切换期：重连是功耗黑洞

广播态 µA 级、连接态看参数，但两者之间的**切换瞬间**很贵：

| 动作                         | 电流特征（示意）                                                 | 为什么贵                                              |
| ---------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------- |
| 手机发 CONNECT_IND 建链      | 尖峰略高于普通广播事件                                           | 三个信道上的扫描/收发集中                             |
| 链路建立后手机立刻做服务发现 | 出现**一串密集尖峰簇**（GATT 发现要几十上百次 ATT 事务，第六章） | 每次 ATT 事务都要占连接事件，连续多个 interval 高活动 |
| 加密配对（若每次重连都重做） | 更高的活动窗                                                     | SM 流程计算与多轮包交互（第六章）                     |
| 掉线 → 重新广播 → 被重新连接 | 回到广播态 + 又一次尖峰簇                                        | **一次重连的能量抵得上几百上千个安静连接间隔**        |

这最后一行是本章最重要的直觉：**链路稳定性就是功耗**。一个「每十分钟悄悄掉线重连一次」的产品，续航看起来像是「广播参数没调好」——其实是第七章的连接稳定性问题穿着功耗的外衣（10.5.3 病灶三专讲读图）。

## 10.4 实测方法：直接复用 WiFi 的阶梯

方法阶梯（采样电阻/万用表陷阱/专用功耗仪/长跑记录）在 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]] 已完整建立，**全部直接复用，本章不重复**。只把 BLE 的特有差异列出来：

| 差异点       | WiFi 章口径            | BLE 侧的调整                                                                                                  |
| ------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------- |
| 电流动态范围 | mA 尖峰 + mA 级地板    | BLE 地板常在 µA~nA 级，动态范围更大：功耗仪（PPK2/Joulescope 级）从「标配」变成「几乎必需」，万用表陷阱更致命 |
| 事件宽度     | 毫秒~十毫秒级活动窗    | BLE 活动窗更窄（亚毫秒~几毫秒），示波器单发抓窗需要更快的触发与采样设置                                       |
| 平均电流     | mA 级为主              | µA 级为主：**积分平均**是唯一可信口径，读「瞬时电流」毫无意义                                                 |
| 对时手段     | beacon/DTIM 对空口抓包 | 空口抓包（第四章的 nRF Sniffer）与功耗仪**对时**，把每个电流尖峰对到具体广播/连接事件                         |

### 10.4.1 BLE 特有观察点：connection event 对表法

这是 BLE 功耗读图最实用的一招：**规整的连接态电流曲线上，相邻两个尖峰的间距就是实测 conn interval**。拿它与固件里配置的值、与手机 App 声明的值三方对表：

```text
        （示意，非实测记录）

电流
  │    ▄█▄        ▄█▄        ▄█▄        ▄█▄        ▄█▄
  │────┘  └──────┘  └──────┘  └──────┘  └──────┘  └────  ← µA 地板
  └────┬──────────┬──────────┬──────────┬──────────┬────► 时间
       ◄── T ──►
       T = 实测 conn interval；与固件配置值对表，对不上 = 参数被对手改了
```

| 对表结果                      | 结论                                                | 下一步                                                       |
| ----------------------------- | --------------------------------------------------- | ------------------------------------------------------------ |
| 间距 = 固件配置的 interval    | 参数生效，节拍正常                                  | 问题去别处找（看地板、看窗宽）                               |
| 间距 ≠ 固件配置值             | **参数被更新过**：手机 App/系统发起 LL 连接参数更新 | btmon 抓 LL_UPDATE，看是谁发起、改成了什么（第二章、第五章） |
| 间距是配置值的 (latency+1) 倍 | latency 生效了                                      | 正常，且是好消息——核对延迟是否影响应用体验                   |
| 尖峰时有时无、间距漂移        | 链路不稳或广播/连接态在反复切换                     | 转第七章掉线取证                                             |

广播态同理：广播尖峰的间距（去掉抖动）就是实测广播间隔，可对表固件配置。**对表法的价值在于便宜**：一张功耗曲线 + 一份固件配置，就能定案「参数有没有被对手改掉」，不用上嗅探器。

### 10.5.2 病灶一：睡不深

```text
        （示意，非实测记录）
电流
  │  ▂█▂▂█▂▂█▂ ▂▂▂▂▂▂▂  ▂█▂▂█▂▂█▂ ▂▂▂▂▂▂
```

图特征：地板不平——整体抬高，或被与应用行为无关的小毛刺切碎。先查清单（便宜到贵）：

| 先查项         | 手段                                                                  | 常见根因                                                         |
| -------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 睡眠模式对不对 | 固件里低功耗模式的实际调用（该 deep sleep 的产品是否维持着连接/广播） | 产品语义：要「随时可连」就不能真睡透（对照 WiFi 章案例同款矛盾） |
| 广播间隔       | 对表法：实测广播尖峰间距 vs 固件配置                                  | 误配了最快的广播间隔；或冲刺广播忘了回调                         |
| 应用层定时器   | 应用日志时间戳与毛刺对表                                              | 秒级传感器轮询、心跳、日志打印把芯片反复拽醒                     |
| 外设地板       | 逐个关外设看地板变化                                                  | 常开传感器、LED、调试串口、电平转换器漏电                        |
| 睡眠时钟方案   | 查时钟树与提前唤醒量（10.3.3）                                        | 用了高漂移时钟源，每次唤醒的「候场」变长                         |

### 10.5.3 病灶二：周期尖峰异常（对表对不上的那一类）

```text
        （示意，非实测记录）
电流
  │  ▂█▂▂█▂▂█▂      ▂▂▂█▂▂█▂▂█▂▂█▂▂█▂▂█▂
  │──────────────────────────────────────────────────
  └────┬────────────┬─────────────────────────────► 时间
        正常广播      ← 一段异常密集的尖峰：间隔突然变小
```

图特征：正常节拍之外出现**间距或宽度异常的尖峰段**，且往往有周期性或与某个手机侧动作相关。按嫌疑对表：

| 尖峰模式                       | 嫌疑对象                                        | 验证手段                                            |
| ------------------------------ | ----------------------------------------------- | --------------------------------------------------- |
| 密集尖峰簇，随机时刻           | 手机侧服务发现/重新连接后的 GATT 浏览（10.3.4） | btmon/空口抓包看 ATT 事务；复现时手动触发手机读服务 |
| conn interval 周期性变小又变大 | **参数更新风暴**：App/系统反复发起 LL 参数更新  | btmon 看 LL 连接参数更新请求的发起方与频率          |
| 固定周期的大尖峰（分钟~小时）  | 应用上报、NTP、OTA 检查、传感器校准             | 与应用日志对表；预期行为则纳入预算不再追            |
| 广播尖峰突然变宽               | 广播数据变更/扩展广播启用/scan response 频繁    | 空口抓包对比广播 PDU 内容（第四章）                 |

其中「参数更新风暴」值得单独记一笔：部分手机系统与 App 会按自己的策略频繁请求连接参数（省电策略、调度需求），你的固件可以拒绝或二次协商——**连接态的节拍从来不是你单方面说了算**。取证时务必区分「谁发起的更新」，btmon 的 HCI 事件里带发起方信息（以所用协议栈文档为准）。

### 10.5.4 病灶三：掉线重连尖峰簇——穿着功耗外衣的稳定性问题

```text
        （示意，非实测记录）
电流
  │  ▂█▂▂█▂▂█▂        ▂▂█▂▂█▂▂█▂▂█▂▂█▂▂█▂▂█▂▂█▂▂█▂
  │──────────────────────────────────────────────────
  └────┬────────────┬─────────────────────────────► 时间
        正常广播      ← 密集尖峰簇：重连 + 服务发现 + 可能的配对
```

图特征：每隔一段不短的时间，出现一整串**远高于平时节拍的密集尖峰**，之后回到安静。这是 BLE 功耗曲线上**单价最高**的动作：一次重连（含链路建立、服务发现、可能的加密）的能量可达安静期成百上千个连接间隔（示意量级）。误判路径极常见：团队看到「平均电流高、续航差」就去调广播参数，实际根因是链路在环境干扰/RSSI 边缘下反复断连（第七章的完整取证路径）。判别口诀：**先数尖峰簇的频次**——重连簇的周期与断连事件的周期对上了，功耗问题立刻转案为连接稳定性问题，去第七章，别再纠结广播参数。

## 10.6 优化路径与权衡

按 10.2 的框架（降占空比为主、峰值基本抠不动）组织。**下表为方向性预期，非承诺数值**，每项改完必须回 10.4 重新量平均：

| 优化项                            | 走哪条路   | 预期收益                                 | 代价与风险                                                 |
| --------------------------------- | ---------- | ---------------------------------------- | ---------------------------------------------------------- |
| 增大广播间隔（如 100 ms → 1 s）   | 降占空比   | 广播态平均电流约按比例下降               | 发现变慢；配合「配网时冲刺广播」两段式策略缓解             |
| 不可连接产品改 ADV_NONCONN 类广播 | 降窗宽     | 省掉等待扫描请求的 RX 窗                 | 失去可连接/可扫描能力，仅适用纯 beacon                     |
| 增大 conn interval                | 降占空比   | 连接态尖峰变稀                           | 单包延迟增大、吞吐下降（第九章的账）；手机可能拒绝过激参数 |
| 用足 slave latency                | 降占空比   | 从机连续缺席，尖峰密度再降               | 数据下行延迟增大；有数据时自动失效（10.3.2）               |
| 冲刺广播两段式（配网快/常态慢）   | 降占空比   | 常态 µA 级，体验不受损                   | 需要产品侧定义「何时冲刺、何时收兵」的状态机               |
| 改善睡眠时钟精度                  | 降窗宽     | 每次唤醒的提前量与候场时间缩短（10.3.3） | BOM 成本（外部晶振）；以芯片手册核对收益                   |
| 合并应用心跳/传感器轮询           | 降占空比   | 图外小毛刺变稀（10.5.2）                 | 状态更新延迟；与云端/网关的超时语义要同步改                |
| 广播数据瘦身                      | 降窗宽     | 广播事件变短                             | 少放了数据（厂商自定义段空间紧张时另想招）                 |
| 治理重连（第七章的稳定性对策）    | 消灭贵动作 | 收益常常是所有项里最大的                 | 属于连接稳定性工程，不是功耗参数旋钮                       |

排序建议与 WiFi 章同款：先做**无感知**的（NONCONN、数据瘦身、合并轮询、治重连），再谈判判**延迟预算**的（interval/latency/广播间隔），最后才是**产品语义**级的重设计（连接维持策略、两段式广播状态机）。

## 10.7 教学案例复盘

**教学复盘案例，取材自常见故障模式综述。** 以下为量级叙述与教学推演，不对应任何真实项目的实测读数。

- **背景**：电池供电的 BLE 门磁传感器，产品目标「一节纽扣电池用一年」。固件默认广播间隔较快、连接参数写死为一组「响应快」的值。上市前整机实测续航只有目标的五分之一左右（10.1 的 B 类病）。
- **第一步：形状先行**。上功耗仪看形状：连接态下尖峰规整但**间距明显小于固件配置的 interval**（10.4.1 对表法，教学推演层面读取）。第一结论：连接参数在空口上**不是固件里配的那组**——被对手改了。
- **第二步：抓发起方**。btmon 抓 HCI 流（第二章），看到手机系统在链路建立后反复发起连接参数更新请求，把 interval 改小（量级示意：改到接近最小合法值）。这是**参数更新风暴**（10.5.3）：手机为了自身调度效率偏好小 interval，代价全在从机的电池上。
- **第三步：固件侧谈判**。在固件的参数更新回调里按产品策略**拒绝过激请求或二次协商**到折中值（方向示意，具体机制以所用协议栈 API 为准），连接态尖峰间距回到设计值，平均电流显著下降（教学推演，不引具体数）。
- **第四步：广播侧收尾**。把常态广播间隔调慢、配网窗口期才冲刺（10.6 两段式）；再对表清掉应用层一个秒级轮询定时器的多余唤醒。续航账回到目标量级。
- **复盘三句话**：①BLE 连接参数是**双边合同**，固件配置只是报价单，空口实际协商值才是成交价——对表法定案；②功耗优化的大头常在**治住对手侧行为**（参数更新、服务发现），不在抠自己的广播间隔；③改完每项都回功耗仪重新积分，**收益以自己的曲线为准**。

## 10.8 收尾：功耗调试 checklist

| #   | 检查项                                             | 工具/手段                   | 合格判据（口径）                         | 对应小节 |
| --- | -------------------------------------------------- | --------------------------- | ---------------------------------------- | -------- |
| 1   | 先明确产品语义：要「随时可连」还是「睡到天荒地老」 | 产品需求评审                | 两种语义的功耗预算完全不同，先定再测     | 10.1     |
| 2   | 睡眠模式核对：该睡透的产品是否维持着连接/广播      | 固件代码审查 + 电流曲线形状 | 曲线形状与产品语义匹配                   | 10.5.2   |
| 3   | 广播间隔对表：实测广播尖峰间距 vs 固件配置         | 功耗仪 + 对表法             | 一致（含 Core Spec 规定的随机抖动）      | 10.4.1   |
| 4   | conn interval 对表：实测尖峰间距 vs 固件配置       | 功耗仪 + 对表法             | 一致；不一致则查参数更新（第 5 项）      | 10.4.1   |
| 5   | 连接参数更新发起方确认：是否被手机侧改小 interval  | btmon HCI/LL 事件           | 更新行为可控、有策略地接受/拒绝          | 10.5.3   |
| 6   | slave latency 实际生效核对                         | 曲线尖峰密度 + btmon        | 尖峰间距呈 (latency+1) 倍关系            | 10.3.2   |
| 7   | 睡眠基电流地板核对                                 | 功耗仪/万用表（仅量级）     | 与芯片模式口径同量级；外设逐个排除       | 10.5.2   |
| 8   | 应用定时器与毛刺对表                               | 应用日志时间戳              | 每个图外毛刺都能对上一个已知定时器       | 10.5.2   |
| 9   | 重连尖峰簇频次统计                                 | 功耗曲线分段计数            | 簇频次 ≈ 0；与断连事件周期对上则转第七章 | 10.5.4   |
| 10  | 服务发现/配对开销计量                              | 尖峰簇宽度 + 空口抓包       | 重连开销已知并纳入续航预算               | 10.3.4   |
| 11  | 睡眠时钟方案与提前唤醒量核对                       | 芯片手册 + 曲线窗宽         | 时钟精度与提前量在预期内                 | 10.3.3   |

本章把 BLE 功耗问题的分析框架收成一句话：**先算账（占空比）、再对表（协议参数）、最后治贵动作（重连与服务发现）**。下一章换一条赛道：产品要出货，还得过认证——[[ble-debug-ch11-qualification-pretest|第十一章：认证与预测试]]讲送测之前能自己排掉哪些 fail。
