# 手写 VPN（四）：从 XOR 到 ChaCha20——流加密与 nonce 纪律

第二章的隧道在裸奔，这一章开始穿衣服——第一件是**流加密**。路线由浅入深正好三步：先看 XOR 为什么是最诚实也最脆的加密（4.1），再理解流密码的本质不过是"把 XOR 的密钥换成一条无限长的伪随机流"（4.2），然后手写一条这样的流：ChaCha20（4.3），最后立下比算法本身更重要的 nonce 纪律（4.4）。WireGuard 的对称加密正是 ChaCha20（[[vpn-deep-dive|姊妹篇]]第二十章拆它的密码学全家桶），我们手写它等于提前拆到了 WireGuard 的心脏。

---

## 4.1 XOR：一个比特的加密术，两种死法

XOR（异或）拥有完美的密码学性质：`P ⊕ K = C`，`C ⊕ K = P`，加密解密同一行代码。**如果密钥与明文等长且完全随机且只用一次**（一次性密码本），它在数学上不可破解——但工程上没人付得起这个代价，于是所有人都"复用密钥"，然后死法整齐地分两类：

**死法一：密钥复用，两条密文互消。** 同一条密钥流 K 加密两条明文 P₁、P₂：

```text
C₁ = P₁ ⊕ K      C₂ = P₂ ⊕ K
C₁ ⊕ C₂ = (P₁ ⊕ K) ⊕ (P₂ ⊕ K) = P₁ ⊕ P₂      ← 密钥消掉了！
```

攻击者拿到两条密文，异或出两条明文的异或。而已知一门语言/协议的冗余度极高（HTTP 头、IP 头都是已知模式），从此逐步恢复两段明文。二战后的 VENONA 计划破苏联一次性密码本，靠的就是密钥页复用——这条死法有历史正文。

**死法二：已知明文，密钥流直接还魂。** 隧道场景尤其致命：我们封装的是 IP 包，**头 20 字节高度可预测**（版本 4、头长 5、协议号、地址……）。攻击者拿到 `C = P ⊕ K`，猜出一段 P（比如 `0x45 0x00 …`），就得到一段 K；流密码的输出是确定序列——**拿到一段密钥流，同密钥/nonce 下后续密钥流全部可推**。

配套工程 `vpn-labs/ch04-chacha20` 的 `xor_demo.c` 把两种死法做成可运行实验：同密钥加密两条消息，演示 `C₁ ⊕ C₂` 里赫然浮出两段明文的差异；再用已知 IP 头还原密钥流前 20 字节。**结论不是 XOR 弱，是"密钥流重复"致命**——于是问题变成：如何用短密钥生成一条永不重复的伪随机流。

## 4.2 流密码：把 XOR 的钥匙换成一条流

流密码 = **密钥流生成器 + XOR**。生成器吃进（密钥 K，nonce N，块计数器 c）吐出确定的伪随机字节流；同一个 (K, N) 永远生成同一条流，**换一个 N 就是全新的一条**。加密就是把它与明文异或：

```text
keystream = F(K, N, 0), F(K, N, 1), F(K, N, 2)…   （64B 一块）
C = P ⊕ keystream
```

由此流密码的全部安全问题收敛为两条：其一，生成器要像随机（这是 ChaCha20 的本职）；其二，**(K, N) 组合绝不能重复**（4.4 的纪律）。RC4 之死（WEP 里 nonce 短到几小时必撞）死在第二条，不是第一条。

## 4.3 ChaCha20：一台打乱机的手写笔记

ChaCha20（RFC 8439，WireGuard/TLS 1.3 同门）是纯整数运算的流密码——没有 S 盒、没有查表、常数时间，特别适合手写与旁路免疫。状态是 16 个 32 位字（512 bit），排成 4×4：

```text
┌────────────┬────────────┬────────────┬────────────┐
│  const     │  const     │  const     │  const     │  4 个常量 "expa" "nd 3" "2-by" "te k"
├────────────┼────────────┼────────────┼────────────┤
│  key[0]    │  key[1]    │  key[2]    │  key[3]    │  256-bit 密钥
│  key[4]    │  key[5]    │  key[6]    │  key[7]    │
├────────────┼────────────┼────────────┼────────────┤
│  counter   │  nonce[0]  │  nonce[1]  │  nonce[2]  │  块计数器 + 96-bit nonce
└────────────┴────────────┴────────────┴────────────┘
```

然后是 **20 轮混合**：每轮对这 16 个字做 8 次 **quarter round**（ARX：模加 Add、循环移位 Rotate、异或 eXclusive-or，三种运算各两次）：

```c
/* quarter round：一列/一对角线上四个字互相搅拌 —— ChaCha20 的全部秘密就这 4 行 */
static uint32_t rotl(uint32_t v, int n) { return (v << n) | (v >> (32 - n)); }
static void qround(uint32_t *s, int a, int b, int c, int d)
{
    s[a] += s[b];  s[d] ^= s[a];  s[d] = rotl(s[d], 16);   /* 对角线打乱 */
    s[c] += s[d];  s[b] ^= s[c];  s[b] = rotl(s[b], 12);
    s[a] += s[b];  s[d] ^= s[a];  s[d] = rotl(s[d], 8);
    s[c] += s[d];  s[b] ^= s[c];  s[b] = rotl(s[b], 7);
}
/* 一轮 = 4 次按列 qround + 4 次按对角线 qround；20 轮后：
   keystream 块 = 混合后状态 + 初始状态（加法喂回去，防可逆） */
```

手写时三个易错点（配套工程的 chachatest.c 全都盯死了）：**块结尾要加上初始状态**（`state[i] += init[i]`，漏掉它密钥流是错的）；**counter 从 0 还是 1 起**（RFC 8439 的原版从 0，TLS 变体从 1——我们按 RFC 从 0，并用官方测试向量钉死）；**nonce 小端序**。字节序按小端（little-endian）装填字——x86 天然契合，也是选 ChaCha 而非 Salsa 的工程理由之一。

验证用 RFC 8439 的 block function 测试向量：key=`00..1f`，nonce=`000000090000004a00000000`，counter=1，输出必须逐字节等于规范给出的 64 字节——手写密码学的第一纪律：**永远对着官方向量验收，不靠"看起来随机"**。

## 4.4 nonce 纪律：比算法更重要的规矩

ChaCha20 本身不坏在任何攻击下，坏全坏在 (K, N) 重复——回到 4.1 的死法。给隧道发帧分配 nonce 的两种正路：

1. **计数器**：发方维护 64 位计数器，每帧 +1，收方同序跟踪。简单、有序（防重放白送，ch05），但**双方必须约定谁的主机序、从几开始、重启后怎么办**（重启回零 = 密钥流重放 = 全线崩溃；工程解法：新会话新密钥，或把计数器持久化）。
2. **随机 nonce**：每帧 96 位随机，撞车概率低到天文数字级忽视；缺点是帧头多带 12 字节、且无序——防重放要另想辙（ch05 的窗口）。

WireGuard 的选择是混合体：**握手时随机生成、会话期内计数器递增**（每方向 64 位计数器，ch09 展开）。我们的 mini-VPN 取最简：每方向一个 64 位计数器从 1 起，重启换密钥。

## 4.5 小结

- XOR 是完美的一比特加密术，死于密钥流复用：两条密文互消、已知明文还魂密钥流——隧道里 IP 头就是现成的已知明文。
- 流密码 = 伪随机密钥流生成器 + XOR；全部安全性收敛为两条：生成器像随机（ChaCha20 的 20 轮 ARX 搅拌），(K, nonce) 永不重复（工程纪律问题）。
- ChaCha20：4×4 状态（常量+密钥+计数器+nonce）、quarter round 四行 ARX、20 轮、末尾加回初始状态；手写三坑——末态加法、counter 起点、小端序，全部用 RFC 官方向量钉死。
- nonce 分配两条正路：计数器（有序、防重放白送、怕重启回零）与随机（无序、多 12 字节）；WireGuard 用混合体，mini-VPN 用每方向计数器+重启换钥。

密文现在遮住了内容，但攻击者的字典里还有"改"：翻转一个密文比特、重放旧帧、调包乱序。下一章给隧道装第二个零件——完整性校验（HMAC）与防重放滑动窗口，也就是 AEAD 的 E 之外那两个字母。[[ch05-mac-replay|第五章：完整性与防重放]]。
