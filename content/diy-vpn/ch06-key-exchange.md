# 手写 VPN（六）：密钥交换——DH、前向保密与中间人

加密要同一把钥匙，可两边隔着一条**攻击者能看能改**的网线——怎么在不安全信道上约定密钥？这就是 1976 年 Diffie-Hellman 论文的标题问题，也是本章主角。路线：DH 的数学直觉（6.1）、手写一遍完整协商（6.2）、密钥派生（6.3）、前向保密（6.4）、然后是最重要的一课——**中间人当场攻陷我们的 DH**（6.5），最后看 WireGuard 怎么用 Noise 握手把这些教训一次付清（6.6）。

---

## 6.1 直觉：混色问题

DH 的经典比喻：双方各持一份秘密颜色，公开混入同一底色互换——**"混合容易、分离难"**。数论版本：在一个大素数 p 的模乘群里，`g^x mod p` 好算（快速幂），但从 `g^x mod p` 反解 x（离散对数）在 p 足够大时无有效算法。于是：

```text
公开信道（攻击者全程可见）：p, g, A = g^a mod p, B = g^b mod p
A 私下算：s = B^a mod p = (g^b)^a = g^(ab)
B 私下算：s = A^b mod p = (g^a)^b = g^(ab)      ← 同一个 s，攻击者只有 g^a、g^b，凑不出 g^(ab)
```

攻击者要 s，等价于解离散对数——**数学单向门**替代了"安全信道"。手写时要处理的工程件只有两个：找一对 (p, g)（p 得是大素数、g 是它的原根，配套工程用 p = 2⁶¹−1 这个梅森素数并在运行时验证 g 的原根性——比背常数更可信）和**快速模幂**（平方-乘，61 位素数下中间积用 128 位整型即可承载）。

## 6.2 手写协商：十二行核心

```c
/* dh.c 核心（配套工程 vpn-labs/ch06-dh-exchange） */
uint64_t powmod(uint64_t base, uint64_t exp, uint64_t p)   /* 平方-乘快速幂 */
{
    unsigned __int128 r = 1, b = base;                     /* 61bit×61bit 需要 128 位 */
    while (exp) {
        if (exp & 1) r = r * b % p;
        b = b * b % p;
        exp >>= 1;
    }
    return (uint64_t)r;
}
/* A：私钥 a 随机，公钥 A = g^a mod p      ——> 明文发给 B
   B：私钥 b 随机，公钥 B = g^b mod p      ——> 明文发回 A
   双方各自 s = powmod(对方公钥, 自己私钥, p)   —— 必须相等 */
```

跑起来你会看到两侧算出**同一个 61 位数**——隔着攻击者的网线，密钥无声地握手成功。这个实验值得多跑几遍换不同 a、b：结果每次都变、每次都相等，"每次会话新密钥"的直觉从这里长出来。

## 6.3 密钥派生：s 不能直接当密钥

协商出的 s 是个群元素，**不是均匀的对称密钥**（它的数学结构可能泄露信息）。正规做法是过一层 KDF：`session_key = SHA-256(s ∥ 会话标识 ∥ 方向标记)`——哈希打散结构，把"协商素材"蒸馏成"密钥字节"。工程细节：**两个方向用不同标记派生两把钥**（发/收各一），避免自发自收的 nonce 混淆；WireGuard 的 HKDF 链是同一思想的工业化版本（[[vpn-deep-dive|姊妹篇]]第二十章）。

## 6.4 前向保密：为什么密钥要"用完即弃"

如果双方用**静态长期密钥**加密所有会话（我们的 mini-VPN ch07 就这样，先坦白），攻击者今天录下全部密文、明年偷走你的私钥——**回放历史全部解密**。前向保密（Forward Secrecy）的对策：会话密钥由**每次临时生成的 DH 结果**派生，用完即弃；长期身份只用来**认证**握手（签名/静态公钥比对），不直接加密内容。这样偷走长期密钥也只能冒充你，解不开昨天录的流量。WireGuard 每两分钟重握手一轮新临时密钥（REKEY_AFTER_TIME），就是拿 ch06 的零件持续运转。

## 6.5 中间人：DH 的一文不值时刻

DH 有个天真的假设：**A 收到的 g^b 真的来自 B**。攻击者 M 只要坐在中间各做一次 DH，就把一条隧道劈成两条：

```text
A ──g^a──▶ M（冒充 B）           M（冒充 A）──g^m2──▶ B
A ◀─g^m1── M                     M ◀──g^b── B
A 与 M 共享 s1；M 与 B 共享 s2 —— 两头各自加密，M 两头全解，明文中转
```

配套工程的 `--mitm` 模式完整演出这一幕：A、B 各自"协商成功"（各自算出与 M 的共享密钥），打印出的两侧密钥**并不相等**——如果它们相等该多好，那说明没人插队；不等，就是中间有人的铁证。可惜运行中的两端永远看不到对方的密钥，**这个差异只有上帝视角（实验日志）能看见**。真实世界的对策是把"公钥属于谁"绑定起来：

1. **PSK（预共享密钥）**：见面/安全信道先对一句暗号，握手时互相 HMAC 挑战——简单，但每对关系都要人工配；
2. **公钥签名/证书**：对方公钥由 CA 背书（IPsec/TLS 路线）——信任锚换成证书体系；
3. **公钥指纹**（TOFU / 手工核对）：第一次拿到对方公钥时记下指纹（SSH 的 yes 那一下）， WireGuard 干脆把"公钥即身份"写进配置——**两边配置文件里互相贴对方公钥，就是手工完成的认证**。

mini-VPN（ch07）取最简：静态对称密钥 + 配置文件手工分发，把 ch06 的 DH 留给"生产化"清单（ch10）。

## 6.6 WireGuard 的答案：Noise 握手鸟瞰

把我们三个零件（DH、认证、前向保密）装进一个协议要处理远不止数学：防重放的握手、身份隐藏（被动抓包者连"谁在跟谁握手"都看不到）、DoS 时的 cookie 机制、密钥轮换定时器——WireGuard 用 Noise 协议框架的四个报文（Initiation/Response 两次 DH + 两个 MAC）一次付清，总代码量四千行（OpenSSL 路线的十分之一）。第九章逐字段对照我们的轮子与它的差距；密码学细节在姊妹篇第二十章展开。

> [!tip] 🧪 配套实验：vpn-labs/ch06-dh-exchange
> 完整 DH 协商（运行时验证梅森素数 2⁶¹−1 与原根、128 位快速模幂、两侧共享密钥相等）+ 密钥派生（SHA-256 蒸馏成双向会话密钥）+ `--mitm` 中间人全流程演示（两侧"协商成功"但密钥不等——上帝视角铁证）。源码直达：[dh.c（代码浏览）](/static/code/#/vpn-labs/ch06-dh-exchange/dh.c)、[完整工程](/static/code/#/vpn-labs/ch06-dh-exchange/README.md)、[GitHub 源](https://github.com/hlwqds/hl-ljj-quartz/tree/v4/practice/vpn-labs/ch06-dh-exchange)。

## 6.7 小结

- DH 用"离散对数难"在公开信道上约定共享密钥；工程件是大素数+原根与快速模幂，核心十二行。
- 协商结果必须过 KDF 才能当密钥（哈希蒸馏 + 双向分钥）。
- 前向保密 = 临时密钥用完即弃 + 长期身份只做认证；静态密钥则历史流量可被事后解密。
- DH 不防中间人：MITM 各做一次 DH 劈成两条隧道，两端毫无感觉；三条出路 PSK/签名/公钥指纹，WireGuard 用"配置里互贴公钥"的手工认证。
- WireGuard 的 Noise 握手 = DH + 认证 + 防重放 + 身份隐藏 + DoS 防护的总装，第九章对照。

三个加密零件到齐，第七章回到总装台：把 ch02 的隧道、ch04/05 的安全信封、ch03 的 TUN 拼成双端可跑的 mini-VPN——你的笔记本和服务器之间，一条自己造的加密链路。[[ch07-minivpn|第七章：组装 mini-VPN]]。
