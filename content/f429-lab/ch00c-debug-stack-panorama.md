## 1. 敲门之后，CPU 在干嘛

答案分两类，界限清晰：

**大多数敲门（读读写写）——CPU 什么都不干，甚至不知道有人来过。**
`mdw` 读 RCC、读 RAM 走的是 TAP→调试端口→MEM-AP→**直接对总线发起事务**——
总线仲裁器看有空档就插进去（和 DMA 抢总线一个待遇）。CPU 不"服务"请求、没有
任何代码参与。这是「零侵入」的根源，也是能读到活着的 `xTickCount` 的原因。

**少数敲门（叫停级）——调试单元对 CPU 有硬件特权通道：**

| 指令     | CPU 身上发生什么                             |
| -------- | -------------------------------------------- |
| `halt`   | 冻在**当前指令边界**——PC、寄存器现场原样冻住 |
| 单步     | 执行一条再冻住                               |
| 断点命中 | FPB 地址比较器发现 PC 走到埋伏点，自动冻住   |
| `resume` | 解冻，若无其事继续                           |

关键细节：**CPU 冻住期间外面的世界照常**——外设跑、DMA 搬、串口进字节；只有
这颗核心停了，中断变挂起，resume 后补处理。系统侧最贴切的类比是 **ptrace**：
进程不知道 tracer 存在、被停在指令边界、寄存器被外部读写——嵌入式版是同一
剧本的硬件演出（下一节会看到这不是巧合）。

## 2. 三层翻译链：gdb 怎么摸到芯片（含实测）

gdb 不认识 TAP 也不认识 SWD——它是链条最上层的租户，只说 **RSP**（Remote
Serial Protocol，TCP :3333）：

```text
gdb（说意图："给我看 xTickCount"）
   │  RSP 协议（TCP :3333）            ← 应用层
   ▼
openocd（gdb server + 总翻译官）
   │  CMSIS-DAP 协议（USB）            ← 传输层
   ▼
野火 DAP 固件（命令打成物理位流）
   │  JTAG：走 TAP 状态机 ／ SWD：走帧格式   ← 物理层敲门
   ▼
芯片调试单元（DP→AP→总线/CPU）
```

类比：gdb≈psql 客户端、openocd≈数据库服务端、RSP≈SQL 方言、USB≈TCP、
TAP/SWD≈网卡 PHY。**底层脚手架对上层全透明**——所以 JTAG↔SWD 切换，gdb
命令一字不改。

**实测（2026-08-30，Fedora 原生 gdb 17.1 经 RSP 连 openocd/SWD）**：

```text
$1 = 898                                          ← p xTickCount（调度器活着）
$3 = 0x20000c24 <ucHeap+2840> "IDLE"              ← p (char*)pxCurrentTCB->pcTaskName
                                                     gdb 带源码符号爬进 TCB，抓拍到空闲任务
```

顺带挖出的两个工程坑（已修/已记）：

1. Fedora **没有 `arm-none-eabi-gdb` 包**——原生 `gdb` 是全目标编译（含 ARM），
   Makefile 的 `make gdb` 已改用它；
2. `monitor halt` 之后 gdb 的**寄存器缓存不刷新**（`$pc` 显 0）——停/走/单步
   要用 gdb 原生指令（`interrupt`/`step`），不要经 `monitor` 绕路。

## 3. 本机对照：gdb 调本机进程走哪套

**ptrace + CPU 自带调试设施**——和嵌入式那套**架构同源**，逐项对译：

| 嵌入式侧（你已通）       | 本机侧（你的主场）              | 本质         |
| ------------------------ | ------------------------------- | ------------ |
| openocd（总翻译官）      | ptrace（内核的调试服务）        | 中间执行者   |
| DHCSR 写 C_HALT          | ptrace attach + SIGSTOP         | "停下"       |
| FPB 硬件断点（6 个）     | **DR0–DR3 调试寄存器**（4 个）  | 硬件断点单元 |
| DWT 观察点（4 个）       | DR4–DR7 的 watchpoint 用法      | 硬件观察点   |
| DHCSR 单步位             | EFLAGS 的 TF 陷阱标志           | 单步         |
| BKPT 指令（软件断点）    | int3（0xCC 一字节替换）         | 软件断点     |
| `mdw` 读内存             | PTRACE_PEEKDATA / /proc/pid/mem | 零侵入读     |
| 故障恢复前提"死了也能调" | 硬件层调试不依赖被调者配合      | 同一设计哲学 |

RSP 在哪？本机不需要——它本来就是"把意图搬过网线"的协议，同机时退化消失；
用 `gdbserver` 跨机时它才重新出现（角色同 :3333 的 openocd）。

两家"家底"也同款：`make probe` 报的 6 breakpoints/4 watchpoints 是 M4 的
FPB/DWT；x86 是 4+4 的 DR 寄存器——**两边硬件断点都稀缺**，所以 gdb 的 `break`
默认走软件断点（改指令），硬件位留给只读段和数据观察。

## 4. 两扇门：self-hosted 与 external

在 ARM 上这两套不是"碰巧像"，是**官方设计**——同一套断点/观察点/单步硬件，
开两扇门：

|          | 朝里的门（self-hosted） | 朝外的门（external）          |
| -------- | ----------------------- | ----------------------------- |
| 谁走     | 内核（本机 gdb+ptrace） | 仿真器（openocd+DAP）         |
| 怎么进   | CPU 指令访问调试寄存器  | 经 JTAG TAP / SWD / CoreSight |
| 底层硬件 | **同一套**              | **同一套**                    |

| 内核家族                | 断点  | 观察点 | 外部门入口               |
| ----------------------- | ----- | ------ | ------------------------ |
| Cortex-M（挑战者 F429） | FPB   | DWT    | SWJ-DP（SWD/JTAG）       |
| Cortex-A（树莓派 A72）  | BRP   | WRP    | CoreSight（经 DAP）      |
| x86（笔记本）           | DR0-3 | DR4-7  | 无标准（Intel DCI 专有） |

x86 只开里门；ARM 两扇都标准化——芯片厂要能换仿真器、OS 厂要能自调试，
"IP 授权给所有人"的架构必然如此。

**三台设备=三种形态**：笔记本（只有里门，二十年老体验）；F429（外门是主角——
裸机无 OS 当中间人）；树莓派（**两扇门都开着**——SSH 进去 gdb 是里门，GPIO 可
复用出 JTAG 是外门）。

> 🎁 **彩蛋实验（留给 RPi 系列）**：同一块树莓派、同一个进程——先用里门（板上
> gdb）halt 它，再用外门（JTAG）看它——两次看到同一个现场。「两扇门通向同一套
> 硬件」从推论变成亲眼所见。

## 5. 证据链的位置学：为什么时钟配置故障复盘立功的是二号 TAP

时钟配置故障复盘两个 TAP 都应了门，但含金量天差地别：

|            | 一号 TAP（`0x4ba00477`）        | 二号 TAP（`0x06419041`）         |
| ---------- | ------------------------------- | -------------------------------- |
| 厂商字段   | **ARM Ltd**（通用 IP 模块）     | **ST**（芯片本体）               |
| 含义       | "ARM 卖给全世界的前门活着"      | "ST 造的 F429 本体还在"          |
| 那晚能给的 | 门活着（门后的路 CPUID=0 全断） | 身份自含在 IDCODE 里，无需往里走 |

诊断当时要的是"人在、芯好、链没断"——二号恰好是**唯一不依赖灾区（CPU 域）
任何功能的证据来源**。系统侧的你早就懂这条：判断机器活着不看它跑的服务，
看带外口的灯——**证据链的可靠性取决于采样点离故障域有多远**。二号立功不是
因为它强，因为它站的位置好。

## 6. IDCODE 考古：值从哪来、名字从哪来

**值（硬件侧）**：制造时物理固化（掩膜/熔丝），CPU 和固件都改不了。厂商号向
JEDEC 申请（全球唯一），part 号厂商自定义。读出=你学过的码本：上电默认 IDCODE
指令→走状态机到 Shift-DR→32 个 TCK 从 TDO 逐位移出。

**切分（IEEE 1149.1 固定格式）**：

```text
位：   31…28      27…12        11…1      0
       ┌──────┬────────────┬──────────┬───┐
       │ ver  │    part    │   mfg    │ 1 │
       └──────┴────────────┴──────────┴───┘

0x4ba00477 → ver=4, part=0xba00(ARM DAP), mfg=0x23b(ARM)
0x06419041 → ver=0, part=0x6419(F42x/43x), mfg=0x020(ST)
```

**名字（主机侧）**：芯片只交数字，人类可读的名字全在 openocd 源码的对照表里
——厂商表源头是 JEDEC JEP106 出版物（全球厂商号段总册）；part 对应来自芯片
文档与 target 配置。这就是 **MAC OUI 的同款模式**：网卡固化 24 位数字，
wireshark 显示厂商名靠本地 IEEE 表——**硬件交数字，软件配字典**。

**bit0 哨兵**：永远=1 不是凑数——链上没焊芯片的位置走 BYPASS，移出恒 0。
openocd 扫链看到全 0 就知道"这里没人"，看到 bit0=1 才认"真 TAP 在此，后 31
位是身份证"。一个比特完成"**有人才谈身份**"的存在性检测。
