## 目标（先说结论）

- 三个实验一决：①把 ch10 的 DMA 缓冲用 `__attribute__((section(".ccm")))`（GCC 编译器注记：
  把变量放进名叫 `.ccm` 的链接段——链接段=最终镜像里一块命名的内存区间，落哪个地址由链接
  脚本决定，见「工程改动」术语卡）搬进 CCM
  （0x10000000）→ 观察故障形态；②同一份代码只删一个 attribute（缓冲落回 SRAM）→ 一切正常；
  ③openocd 三连读：CPU 对 CCM 可读写（D-bus 通——CPU 直连 CCM 的那条专用总线）vs DMA 的
  NDTR（DMA 的剩余搬运笔数倒计数寄存器）/TE（Transfer Error，传输错误）标志（矩阵不通）。
- 最阴的预期先立起来：**CPU 一切正常、程序不崩**——CPU 访问 CCM 走 D-bus 畅通无阻，死的
  只是 DMA 的搬运单。这是「静默劣化」型 bug 的标本：不崩、不吵、数据悄悄没了。
- 主资产：把 ch05 的总线图**用实测箭头重新标注**（CPU→CCM ✓、DMA→CCM ✗）——理论图升格为
  证据图。ch05 结尾那句「届时图上的虚线处会补上总线错误的实证读数」，本章来还愿。

> 📖 **术语卡：CCM**
> **是什么**：Core Coupled Memory（内核耦合内存），F429 上 64KB、地址 0x10000000 的 SRAM，只挂 CPU 私有的 D-bus——其他任何主设备（DMA、以太网、USB）在总线矩阵里没有通往它的端口。其他芯片上的近亲叫 TCM（Tightly-Coupled Memory，紧耦合内存）。
> **为什么存在**：给 CPU 留一块零争用、零等待的私有 RAM：没人抢端口，访问永不排队。
> **类比**：你办公桌的抽屉 vs 公共仓库：抽屉只有你能开（快、私密）；快递员（DMA）根本进不了你的办公室。
> ⚠️ 类比边界：抽屉挡的是「人」（权限），CCM 卡的是「硬件端口」——不是权限配置问题，改任何寄存器都救不了，物理上就没接线。

> 📖 **术语卡：DMA**
> **是什么**：Direct Memory Access（直接内存访问）控制器：独立于 CPU 的搬运工硬件，编程好「源地址、目的地址、几笔数据」后自己搬，完成/出错才插一脚中断。F429 有 DMA1/DMA2 两个控制器，各 8 条 stream（流），每条 stream 再从 8 个 channel（通道）里选一个对应具体外设请求。
> **为什么存在**：串口每收一字节就让 CPU 亲赴一次太浪费；DMA 让 CPU 下完单就去干别的。
> **类比**：你的主场：网卡 DMA/异步拷贝引擎——CPU 下单、硬件履约、完成中断回执。
> ⚠️ 类比边界：DMA 是独立主设备，有**自己的可达范围**——CPU 够得着 ≠ DMA 够得着，本章主题正是这句话。

## 系统侧类比：NUMA 的权限版

| CCM 侧                    | 系统侧对应                                       |
| ------------------------- | ------------------------------------------------ |
| CPU 可读写、DMA 不可达    | NUMA 远端内存的**权限版**：不是慢，是根本不通    |
| 同一地址空间、不同可达性  | /proc/self/maps 里 rwx 差异：地址对，权限不对    |
| `.ccm` 段落位由链接器管   | `numactl --membind`：数据放哪是显式拓扑决策      |
| 缓冲进 CCM → DMA 静默失败 | 远端 DMA 映射缺失：网卡 DMA 到不可映射页直接掉包 |
| CPU 自检通过掩盖 DMA 失败 | 本地读写全对、异步路径全错——同步测试掩盖异步 bug |

ch05 用过「NUMA 本地内存」类比；本章补上它残酷的下半句：NUMA 远端访问是**慢**，CCM 对 DMA
是**拒收**。前者调 `numastat` 能看到命中率劣化，后者连错误都未必有人看——取决于 TEIE 开没开。
（NUMA/`numactl --membind`/`numastat` 都是你的主场，一句话版：多路机器上各 CPU 有本地/远端
内存之分，`--membind` 显式指定数据落在哪个节点——不再展开。）

## 原理下钻

### 拓扑回顾：一张图里只有一条路

ch05 的总线图结论浓缩成两行：**192KB SRAM 挂 BusMatrix 从端口（所有主设备可达）；64KB CCM
只挂 CPU 的 D-bus（其余主设备在矩阵里根本没有通往它的从端口）**。DMA2 的搬运要走「外设口/
内存口 → BusMatrix → 从端口」——对 0x10000000 这个地址，矩阵里不存在出口。RM0090 的原文
（ch05 引用过）：CCM「only accessible by the CPU」；至于 DMA 撞墙时总线给什么响应（错误
响应回给 DMA 控制器 → 置 TEIF？还是写事务被丢弃？），手册没写——候选症状见表，实跑定夺。

（RM0090=ST 官方《STM32F4 参考手册》的文档编号，F429 寄存器与总线拓扑的权威出处。）

> 📖 **术语卡：总线矩阵（BusMatrix）**
> **是什么**：芯片内部的交叉开关阵列：一侧接主设备（CPU 的几条访存总线、DMA1/DMA2、以太网、USB OTG 等），另一侧接从设备（FLASH、SRAM1/2/3、各外设寄存器区）。哪个主设备能到哪个从设备由物理接线决定；多条互不冲突的通路还能并行跑。
> **为什么存在**：多个主设备并发访存，需要硬件仲裁+并行通路，而不是所有人挤一条独木桥。
> **类比**：地铁换乘大厅：不是任意两线都互通，图上没画的换乘通道就是走不通——CCM 就是那个没画通道的站台。
> ⚠️ 类比边界：矩阵不能「申请开通」新通路——接线在芯片流片那刻焊死，软件无解，只能换地址。

> 📖 **术语卡：D-bus / S-bus（CPU 的几条出口）**
> **是什么**：Cortex-M4 给 CPU 配的访存总线：I-bus 取指令；D-bus（D-code）管装载/存储，覆盖代码区与 0xE0000000 起的核心私有寄存器区等；S-bus（system bus）走总线矩阵，覆盖 0x20000000 起的 SRAM 与外设。CCM 挂在 D-bus 上，所以 CPU 够得着；DMA 只能走矩阵，而矩阵里没有 CCM 的口。
> **为什么存在**：给 CPU 常用的区域（代码、核心私有外设）留直连快车道，其余流量统一过矩阵仲裁。
> **类比**：CEO 专属直达电梯（D-bus）vs 公共换乘走廊（S-bus→矩阵，大家排队仲裁）。
> ⚠️ 类比边界：走哪条总线由**地址段**决定，不是特权级——任何代码访问 0x10000000 都自动走 D-bus。

### 工程改动：链接脚本 + 一个 attribute

ch05 解读过的 `STM32F429IG.ld` 里 `CCM (rwx) : ORIGIN = 0x10000000, LENGTH = 64K` 声明着
但一个 section 都没放。本章补上搬运通道（SECTIONS 追加）：

```text
.ccm (NOLOAD) :
{
    . = ALIGN(4);
    __ccm_start = .;
    KEEP(*(.ccm))
    . = ALIGN(4);
    __ccm_end = .;
} > CCM
```

**链接脚本走读**（逐行拆上块与声明行）：

| 行                                              | 作用                                                                                     |
| ----------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `CCM (rwx) : ORIGIN = 0x10000000, LENGTH = 64K` | 在 MEMORY 区登记一块名叫 CCM 的区域：起点/大小/读写执行属性——登记≠使用，ch05 前一直空着  |
| `.ccm (NOLOAD) :`                               | 开一个输出段叫 `.ccm`；NOLOAD=该段不生成固件镜像内容（RAM 区上电内容无意义，不占 flash） |
| `. = ALIGN(4);`                                 | 把当前位置指针 `. `调到 4 字节边界（对齐）                                               |
| `__ccm_start = .;` / `__ccm_end = .;`           | 把段起止地址存成符号，代码里可用它做运行期自检/清零                                      |
| `KEEP(*(.ccm))`                                 | 把所有输入段里名叫 `.ccm` 的内容收进来；KEEP 防止链接器「无人引用即丢弃」的优化把段删掉  |
| `> CCM`                                         | 关键落位指令：本段内容放进上文 MEMORY 登记的 CCM 区域（0x10000000 起）                   |

固件侧只动缓冲的声明——ch10 的 DMA 代码一字不改：

```c
#define EXP_CCM 1
#if EXP_CCM
static uint8_t g_dma_rx[RX_BUF_SIZE] __attribute__((section(".ccm"), aligned(4)));
#else                       /* 对照组：删掉 section 属性即落 .bss→SRAM@0x2000xxxx */
static uint8_t g_dma_rx[RX_BUF_SIZE] __attribute__((aligned(4)));
#endif
```

> 📖 **术语卡：`__attribute__((section(".ccm")))`（链接段属性）**
> **是什么**：GCC 的变量注记：把该变量放进名叫 `.ccm` 的**链接段**（section，最终镜像里的一块命名区间），配合链接脚本 `.ccm … > CCM` 的落位规则，变量地址就落在 0x10000000 段。
> **为什么存在**：C 默认只分 .data（有初值）/ .bss（无初值）等段；要把特定数据钉到特定内存区（CCM、DMA 可达区、备份域），就得走「变量→自定义段→链接脚本→物理地址」这条传送带。
> **类比**：你的主场：内核把 per-cpu 数据钉进 `.data..percpu` 段再由 ld 脚本落位，同一套手法。
> ⚠️ 类比边界：属性只管「进哪段」；段落哪还取决于链接脚本——两边名字对不上时变量会**悄悄落回默认位置且不报错**，这是该机制的经典静默坑。

开机先做 CPU 侧自检，把「CPU 通、DMA 不通」拆成两个独立观察点：

```c
static void ccm_selftest(void)      /* uart_puthex：工程里的小助手，按 8 位十六进制打印 */
{
    volatile uint32_t *p = (volatile uint32_t *)(void *)g_dma_rx;
    *p = 0xC0FFEE11u;               /* CPU 写 */
    uart_puts("[CCM] cpu-rdbk=");
    uart_puthex(*p);                /* 预期 0xC0FFEE11：D-bus 通 */
    uart_puts(" buf=");
    uart_puthex((uint32_t)p);       /* 实验组 0x1000xxxx / 对照组 0x2000xxxx：落位证明 */
    uart_puts("\r\n");
}
```

**C 代码走读**（缓冲声明 + 自检函数逐行拆）：

| 行                                                    | 作用                                                  | 值得注意                                                 |
| ----------------------------------------------------- | ----------------------------------------------------- | -------------------------------------------------------- |
| `#define EXP_CCM 1`                                   | 实验/对照组总开关：1=翻车组，0=对照组                 | 一键切换、其余代码零改动——实验说服力的来源               |
| `section(".ccm"), aligned(4)`                         | 双注记：进 .ccm 段 + 4 字节对齐                       | DMA 对源/目的地址对齐有硬要求（ch10 踩过）               |
| 对照组（只删 section 属性）                           | 变量落回默认段 .bss（未显式初始化的静态变量住的段）   | .bss 在 SRAM@0x2000xxxx——两组唯一差异就是选址            |
| `volatile uint32_t *p = (volatile …)(void *)g_dma_rx` | volatile=禁止编译器优化/缓存掉这些读写                | 自检必须真的写、真的读                                   |
| `*p = 0xC0FFEE11u;`                                   | CPU 往缓冲头写魔数（COFFEE 的十六进制玩笑，便于认读） | CPU 写得进 ≠ DMA 也够得着——本章拆的两个观察点            |
| `uart_puthex(*p)`                                     | 读回并打印：预期原样 0xC0FFEE11                       | 读回一致=D-bus 通（症状#6 的取证点）                     |
| `uart_puthex((uint32_t)p)`                            | 打印缓冲地址                                          | 落位证明：从串口打印即可确认变量住 0x1000 还是 0x2000 段 |

### 候选症状表（真实形态待实测）

| #   | 候选症状                   | 观察点                          | 推理                                                     |
| --- | -------------------------- | ------------------------------- | -------------------------------------------------------- |
| 1   | TEIF2 置位                 | `mdw 0x40026400` 的 bit19       | 矩阵回错误响应，DMA 置 TE（开 TEIE 则进 ISR，ch10 已开） |
| 2   | 数据不落（回显缺失/全 00） | host 侧收不到回显或缓冲保持初值 | 写事务被丢，RX 缓冲没人写                                |
| 3   | TX 方向线上出 0xFF/垃圾    | host 侧收到的字节               | 读事务读不到源，DMA 把默认值塞给 USART                   |
| 4   | NDTR 原地不动              | `mdw 0x40026444` 恒 64          | 第一笔就失败，计数不递减（或停在中途）                   |
| 5   | HardFault                  | （低概率）                      | 错误响应止于 DMA 主口，一般不升级 CPU 异常               |
| 6   | **CPU 侧一切正常**         | 自检打印、程序继续跑            | D-bus 通——最阴的一条，几乎是必然命中                     |

> 📖 **术语卡：TEIF / TEIE（DMA 传输错误一对儿）**
> **是什么**：TE=Transfer Error（传输错误）：DMA 的一笔总线事务被从设备拒收/无响应时置起的标志。TEIF2=DMA2 Stream2 的 TE 标志位（住在 LISR——低中断状态寄存器——的 bit19）；TEIE=该标志对应的中断使能位：开了它，标志一置就进中断；不开，就只有主动轮询标志才能发现。标志要用「向 LIFCR 对应位写 1」清除。
> **为什么存在**：DMA 独自跑没人盯，错误必须留痕；要不要打断 CPU 则由 TEIE 交给开发者权衡（ch10 开了，所以本章能靠 te 计数报警）。
> **类比**：你的主场：errno+信号开关的硬件版——错误先落标志，发不发通知是另一个开关。
> ⚠️ 类比边界：TE 置位后 stream 会停（手册口径是自动清 EN 摘机），**不会重试到成功**；具体停成「只挂标志/停流/摘机」哪种形态，正是待核对清单#3 要实测的。

对照实验②的预期只有一行：**te=0、回显逐字节一致**——与 ch10 完全相同的行为。两组的唯一
差异是缓冲落在哪个地址段，这正是实验的说服力所在：变量选址改变行为，程序逻辑零改动。

## 实验：翻车、对照、活体取证

三步各自独立可观察，证据链沿用系列惯例（串口字节 + `mdw` 寄存器读数）：

1. **翻车组（EXP_CCM=1）**：烧录后先看自检行（CPU 通），再跑 ch10 的 64B 定长块回显——host
   （接在串口另一头的电脑；回显 echo=板子把收到的字节原样发回）侧记录回显形态，板侧记录 te
   计数；RX（DMA 写 CCM）与 TX（DMA 读 CCM）两个方向各观察一次。
2. **对照组（EXP_CCM=0）**：同代码重编译烧录，其余步骤原样重演。
3. **openocd 三连读**（翻车组运行中，序章方法论：`mdw` 活体读不用 halt）：

```bash
mdw 0x10000000     # 自检值 0xC0FFEE11：CPU/D-bus 路径的读回（见待核对#2 的双结果设计）
mdw 0x40026444     # DMA2_S2 NDTR：恒 0x40（一笔未搬）还是中途停滞
mdw 0x40026400     # DMA2 LISR：bit19（TEIF2）是否挂起=0x00080000
```

**命令拆解：** openocd 三连读 `mdw 0x10000000` / `mdw 0x40026444` / `mdw 0x40026400`

| 命令与地址   | 读的是什么                                                                             |
| ------------ | -------------------------------------------------------------------------------------- |
| `mdw`        | openocd 的按 32 位字读内存命令（memory display word）                                  |
| `0x10000000` | CCM 首地址：看自检魔数 0xC0FFEE11 在不在——同时探「调试器自己能不能到 CCM」             |
| `0x40026444` | DMA2 Stream2 的 NDTR（Number of Data to Transfer）：剩余搬运笔数倒计数，0x40=64 笔没动 |
| `0x40026400` | DMA2 的 LISR（低中断状态寄存器）：bit19=TEIF2，读数 0x00080000 即传输错误挂起          |

**你会看到**：见下节「openocd 三连读」三行——任一形态都是证据（双结果设计）。
**失败了先查**：地址拼写（十六进制）；翻车组须在**运行中**读（序章方法论：活体读、不 halt——halt 会改变 DMA 运行状态）。

名词补注：调试器的 `mdw` 走的是 AHB-AP（AHB Access Port，调试访问端口 DAP 伸进芯片内部总线的口子）——「AHB-AP 到 CCM 走不走 D-bus」本身就是待核对#2 的双结果设计要回答的问题。

## 主资产：总线图的实测箭头版

ch05 的理论图加上本章证据后（✓/✗=实测结论，?处=实跑回填）：

```text
                          ┌─────────────── 实测标注（ch13）───────────────┐
CPU ──D-bus 直挂─────────► CCM 64K @0x10000000   ✓ 0xC0FFEE11 写读自检通过
DMA2 ─S-bus→BusMatrix──✗──► CCM                  ✗ 矩阵无此从端口：TE/不落（形态？）
DMA2 ───────────────────► SRAM 192K @0x20000000  ✓ ch10/ch11 全部实验的地基
CPU ──S-bus→BusMatrix───► SRAM                    ✓ 同一块内存两条路——单边可达
```

这张图此后是系列的地基资产：**「谁要访问这块数据」决定「数据能放哪」**。CCM 的正确用法
（ch05 预告过）：调度器私有结构、热点查找表、只有 CPU 碰的 ISR 工作区——收益是零等待、
不受 DMA 带宽挤兑；雷区就是本章踩过的：任何一天有人把这块缓冲交给 DMA。

## 与 FreeRTOS / 系列对照

- **ESP32 的同款课**：[[ch21-stack-and-memory-layout|FreeRTOS（廿一）：栈与内存布局]]
  里 IDF 把内存分成 DRAM/IRAM/RTC 等 capability 域、按能力分配——`MALLOC_CAP_DMA` 的存在
  正是因为 ESP32 也有「DMA 可达/不可达」的地址之分。F429 没有这套 allocator，全靠链接脚本
  和人肉纪律：**平台是否替你管「DMA 可达性」，决定了你要不要自己背这份心智负担**。
- **lwIP 侧的伏笔**：ch05 说过 heap_4 的 64KB 不放 CCM，因为 pbuf 终将交给以太网 DMA——
  本章的翻车就是那个决策的反面演示。阶段 5（ch20/21）的 pbuf 选址问题，答案已在本章。
- **排障方法论**：`mdw` 读数对位序验（TEIF2 是 LISR 的 bit19=0x00080000）、双结果设计
  （mdw 对 CCM 可达与否都是证据）——序章方法论 3/5 条的又一次应用。
- 顺带核销 ch05 待核对#4 的一角：DMA 打 SRAM1 的同时 CPU 读 SRAM3 的真并发收益，可用
  ch10 空转计数器变体在本章对照组上量——列为待核对，不展开。

**名词补注（本节里的对面世界）**：lwIP=嵌入式轻量级 TCP/IP 协议栈；pbuf=lwIP 的收发包缓冲
结构（协议栈内外传递数据的载体）；heap_4=FreeRTOS 官方四套堆方案之一（heap_1~4，heap_4 支持
空闲块合并与 free）；MALLOC_CAP_DMA=ESP-IDF「按能力分内存域」的分配标志——申请内存时声明
「这块要能被 DMA 到」，分配器保证落对地址域。F429 裸机没有这层保护，全靠链接脚本+人肉纪律，
本章踩的就是缺这层保护的坑。
