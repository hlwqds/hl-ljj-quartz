# lwIP 深度解析（二十四）：性能调优与故障注入实战

这一章是全系列的收官，回答最后三个问题：**这套系统在这个环境里到底能跑多快——上限由谁决定**（SLIRP？lwIP 配置？CPU 账单？24.3 用三口径配对实测拆账）；**要提性能该先拧哪个旋钮**（24.4 用一张逐点重建烧写的实测矩阵回答，并给出本章最有价值的发现：TCP 接收窗口与 openeth RX 描述符环深必须配对放大，单拧必翻车）；**前 23 章教过的注入手法怎么变成一张可检索的总表**（24.5 总集 + 弱网×堆紧张组合拳新实验）。源码参照：ESP-IDF v6.0.2（`~/esp/esp-idf`），捆绑 lwIP 2.2.0-dev。所有数字均出自本章实验工程 `practice/lwip-ch24-performance-tuning-pitfalls/` 的真实运行，方法与轮次在正文写明。

## 24.1 调优的三问与决策树

### 1. 上限由谁决定：先把"锅"分对

一次吞吐测试跑出来 80 Mbit/s，谁该负责？这条链路上站着四个嫌疑人：

```text
主机应用 ── SLIRP 用户态转发 ── QEMU/openeth 假网卡 ── 驱动任务 emac_rx
                                                            │ 邮箱
                                              tcpip_thread ─┘ ── netconn/socket ── 应用任务
```

各嫌疑人的"前科"在本系列已分别定罪过：

| 层              | 已知天花板                             | 出处     |
| --------------- | -------------------------------------- | -------- |
| SLIRP 外环      | 默认 SND_BUF 与调大后都到顶 ≈120 Mbit  | 第六章   |
| openeth DMA 环  | TX=1/RX=4 个描述符，过载窗坍缩到 33fps | 第十七章 |
| lwIP 单线程邮箱 | socket 吞吐 38.9 vs raw 67.7 Mbit      | 第十六章 |
| 任务优先级      | 高优自旋钉核占空比 ≥85% 全灭           | 第十九章 |

本章的贡献是把四者的**相对占比**在同一负载下量出来，做成三层账。

### 2. 先拧哪个旋钮：一棵决策树

按"确诊哪个层是瓶颈 → 只拧那一层的旋钮"组织，别跨层乱试：

```text
现象是什么？
│
├─ 吞吐低，RTT 正常，重传计数不涨
│    ├─ 发送方向：先查发送泵是否注册了 tcp_sent()（ACK 驱动，第六章）
│    ├─ 再看 SND_BUF ≥ 2×MSS（否则被窗口掐死）
│    └─ 最后检查对端通告窗口（TCP_WND / 窗口缩放）
│
├─ 吞吐低且网卡层丢帧告警 / RTO 重传暴涨
│    ├─ RX 方向：描述符环深度 ≥ 在途帧数 = WND/MSS（本章 24.4 的交叉验证！）
│    └─ TX 方向：TX 环满走 INT_BUSY（第十七章）
│
├─ RTT 抖动而吞吐尚可 → 单线程邮箱排队：
│    └─ tcpip 任务有没有被高优自旋/长回调霸占（第十三、十九章）
│
├─ 内存水位持续下滑 → 全堆化世界的碎片化三联征（第五、二十二章）
│
└─ 连接莫名死/RST → 故障注入总表 24.5
```

### 3. 本章实验的统一纪律

- **同时段配对**：QEMU 吞吐受宿主机负载影响可达 ±50%（第三章教训），所有对比轮次背靠背连跑。
- **固定负载**：外环灌流 host→guest/guest→host 各 4 MB；回环 ping-pong 512 B × 200；回环批量 4 MB。
- **重建制矩阵**：`snd_buf/wnd/mss/mbox` 都是编译期 Kconfig，每个矩阵点独立构建 + 手工 `esptool merge-bin` 合并 flash 镜像（绕开 `idf.py qemu monitor` 在重复构建后静默不更新镜像的坑——本章开头两小时就被它坑掉一批数据）。
- **判废门限**：某点若外环 <40 Mbit 或回环批量 <50 Mbit 判为环境污染，立即重测。

拿一个具体场景演示决策树的用法，它正是本章矩阵里真实出现过的 p2 格：某天发现设备下行灌流只有 4 Mbit。第一步查重传与 memerr——重传暴涨而 `tcp.memerr=0`，锁掉内存假设；第二步跑回环对照——批量 94 Mbit 飞快、RTT 582 µs 健康，栈无罪；第三步只剩接收侧资源一算：窗口 11520 / MSS 1440 = 8 帧在途，openeth RX 环深 4。十分钟定位，一次旋钮修复（环抬到 16）。反过来说，如果没有这套分层观测位，这个故事通常会以"QEMU 不稳定、换个姿势再试试"收场——那才是嵌入式网络调试真正的深渊。

## 24.2 实验工程一览

`practice/lwip-ch24-performance-tuning-pitfalls/`：一个固件覆盖三个实验，全部参数经 TCP 控制通道（hostfwd 8029→:9999）注入，避免反复烧写；bulk 数据口 :8888（8028）、HTTP 服务 :80（8030）、内部 loopback 测试对 :7777。

启动后的真实档案（串口原文摘录）：

```text
$$$ DATAREADY port=8888 mode=rx
$$$ HTTPREADY port=80
$$$ CTRLREADY port=9999
$$$ MEM boot free=210996 largest=110592 min_ever=208964
$$$ BUILD sndbuf=5760 wnd=5760 mss=1440 tcpip_mbox=32 pbuf_pool=16
```

固件自带三类观测位：任务表快照（`uxTaskGetSystemState`）、内存账本（free/largest/min-ever）、lwIP 统计（link/tcp 计数）。控制平面钉核 1、优先级 22——**活在受害者带宽之外**（第十九章的血泪教训）。

### 1. 复现全流程的可复制命令

环境与构建侧（每个矩阵点一轮，`tools/` 里已固化成脚本）：

```bash
# 激活 IDF v6.0.2 后，在工程目录内
idf.py set-target esp32        # 仅首次

# 用指定预设构建并手工合并 flash 镜像（tools/build_point.sh 的内核动作）
cp configs/base.sdkdef sdkconfig.defaults && rm -f sdkconfig   # 改默认值必须重生 sdkconfig
idf.py build
( cd build && python -m esptool --chip esp32 merge-bin \
    -o qemu_flash.bin --pad-to-size 4MB @flash_args )          # 关键兜底！见 24.7

# 启动实例（tools/run_qemu.sh），hostfwd 端口约定见脚本头注释
LOG=logs/m_p0base.log tools/run_qemu.sh >/dev/null 2>&1 &
for i in $(seq 1 30); do grep -q CTRLREADY logs/m_p0base.log && break; sleep 1; done
```

主机侧驱动（`tools/bench_host.py`，所有指标从这里产生）：

```bash
# 外环吞吐：host→guest 灌 4MB，等 guest 的 EOF 应答位
python3 tools/bench_host.py --mb 4 --timeout 8 thrx
# RESULT kind=thrx mb=4 ack=b'K' secs=0.440 mbit=72.68

# 外环反方向：guest 泵模式（先经控制口切换），host 读到 EOF 计数
python3 tools/bench_host.py ctrl --cmd "sinkmode tx"
python3 tools/bench_host.py --mb 4 thtx
# RESULT kind=thtx want=4000000 got=4000000 secs=0.327 mbit=97.76 clean_eof=n

# 回环 RTT / 回环批量（结果从串口 log 收割）
python3 tools/bench_host.py ctrl --cmd "rtt 200 512"
grep LBRTT logs/m_p0base.log | tail -1
# $$$ LBRTT ok=200/200 size=512 avg_rtt_us=580 min=433 max=1056
python3 tools/bench_host.py ctrl --cmd "th 4000000"
grep 'LBTH ' logs/m_p0base.log | tail -1
# $$$ LBTH ack_r=0 bytes=4000000 elapsed_us=356991 mbit=89.64

# HTTP 时延画像（实验 C 与调优对照组共用）
python3 tools/bench_host.py http --n 12 --timeout 5
```

故障注入命令一览（控制口下发，幂等）：`loss <pct>`（TX 帧按概率吞）、`heap <kb|off>`（malloc 到只剩 kb KB）、`sinkmode <rx|tx>`、`mem/tasks`（观测位快照）。整个点的自动化串在 `tools/run_matrix_point.sh` 与带判废重测的 `tools/run_stable_point.sh` 里。

> [!warning] 本轮实测踩出的三个工程坑，全部写进了脚本注释
>
> 1. **QEMU flash 镜像静默过期**：重复构建后 `idf.py qemu monitor` 可能不再更新 `qemu_flash.bin`。本轮因此烧着旧镜像测了约一小时废数据；根治手段是每次构建后强制执行上面的手动 merge-bin，并在固件启动时打印 `__TIME__` 作为镜像身份指纹核对。
> 2. **PCB 上限 16 的黑洞式串联**：多轮连接后新连接全体无响应而老连接健康（详见 24.5 的 note），全程测量必须抬高 `CONFIG_LWIP_MAX_ACTIVE_TCP`。
> 3. **并行作者的端口互踩**：QEMU 必须 kill 自己那组 hostfwd 特征的精确 PID（`pgrep -f` 匹配 QEMU 二进制路径而非宽泛关键字，否则会误杀自己的 shell 或别人的实验）。

## 24.3 实验 A：天花板校准——三层分解账

### 1. 口径定义与原始数据

同一 4 MB 批量负载，三种口径各 3 轮配对（基线配置，构建戳 `BUILD sndbuf=5760 wnd=5760 mss=1440`）：

| 口径                      | 路径含义                          | r1    | r2    | r3         |
| ------------------------- | --------------------------------- | ----- | ----- | ---------- |
| A1 SLIRP 外环 host→guest  | 含 SLIRP + 假网卡 + 栈            | 72.68 | 93.16 | 77.51 Mbit |
| A1' SLIRP 外环 guest→host | 泵模式，方向不对称参照组\*        | 97.76 | 90.44 | 71.07 Mbit |
| A2 loopback 批量 4 MB     | 纯协议栈 + 两端应用，无 NIC/SLIRP | 89.64 | 74.71 | 86.80 Mbit |

\* 泵方向数据取自紧邻的上一版镜像同序列实测；泵模式对发送节奏敏感，在后文 24.4 的反模式中还会见到它。

回环 RTT（512 B × 200，同批轮次）：**580 / 635 / 615 µs**（min 433–470 µs），对照基线 boot 时内存 free≈206 KB。

方向不对称值得单独一提：同是 4 MB、同配置，guest→host 的泵模式三轮均值 86.4 Mbit 略高于 host→guest 的 81.1 Mbit。两条路径的栈部分完全对称，差异只能来自 SLIRP 对两个方向的转发实现细节（socket 缓冲水位、宿主机调度时机）。这正符合本章开头定下的纪律：跨方向的绝对值比较没有意义，配对的意义只在于同窗互证稳定性。

下一节的调优矩阵要逐个扫描这些旋钮，先把它们各自物理上作用在哪里登记造册（对照 Kconfig 名）：

| 旋钮                                             | 作用位置                                 | 本章验证结果                               |
| ------------------------------------------------ | ---------------------------------------- | ------------------------------------------ |
| `LWIP_TCP_SND_BUF_DEFAULT`                       | 发送缓冲字节预算，阻塞 send() 的水库容量 | 小幅收益；拉满有涓流反模式                 |
| `LWIP_TCP_WND_DEFAULT`                           | 接收窗口字节数 = 允许对端的在途量        | 必须与接收侧深度联动（见下）               |
| `LWIP_TCP_MSS`                                   | 单段上限，决定包粒度与开销比             | 1440→1460 安全小赚；536 让批量掉到 38 Mbit |
| `ETH_OPENETH_DMA_RX_BUFFER_NUM`                  | 仿真网卡 RX 描述符环深（默认 4）         | 隐藏的第三人：决定上面两行谁说了算         |
| `LWIP_TCPIP_RECVMBOX_SIZE` / `TCP_RECVMBOX_SIZE` | tcpip/netconn 邮箱深度                   | 本负载档内不敏感（8→64 噪声级）            |

### 2. 三层分解账

把三口径放回一条时间线，就能读出每层的"抽成"。先看最底层的账本——一次回环批量在固件侧的完整痕迹（`results/p0base.log` 原文）：

```text
--- round 1 ---
RESULT kind=thrx mb=4 ack=b'K' secs=0.440 mbit=72.68
RESULT kind=thtx want=4000000 got=4000000 secs=0.327 mbit=97.76 clean_eof=n
[fw] $$$ LBTH ack_r=0 bytes=4000000 elapsed_us=356991 mbit=89.64
[fw] $$$ LBRTT ok=200/200 size=512 avg_rtt_us=580 min=433 max=1056
[fw] $$$ MEM on-cmd free=205924 largest=110592 min_ever=181680
[fw] $$$ LWSTATS on-cmd link.recv=16244 link.xmit=16244 link.drop=0 tcp.memerr=0 tcp.err=0 tcp.drop=0
```

指标读法：`thrx/thtx` 的计时覆盖 connect→最后字节确认（含 TCP 流控全程）；`LBTH/LBRTT` 是 guest 内 127.0.0.1 的纯栈路径；`LWSTATS` 行里 `link.drop=0 tcp.memerr=0` 是本轮数据有效的健康证词——凡出现非零即作废重测。

三层结论表：

| 层                        | 结论                                                                                                           | 证据                                                            |
| ------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **环境天花板（SLIRP）**   | ≈70–95 Mbit 为常态带宽段，上下摆动主要来自宿主机负载而非配置                                                   | 同一镜像同配置三轮就摆动 ±15%                                   |
| **配置上限**              | 小步旋钮（如 MSS→1460）可在此段内抬升约 5–10%；但"拉满型"旋钮组合会把数据面拖入涓流档（见 24.4 反模式）        | mss1460 点实测见 24.4 矩阵 p5                                   |
| **协议开销（lwIP 本体）** | 回环 83.7 Mbit 均值 ≈ 外环均值，瓶颈由「SLIRP≈驱动≈栈」三家分摊、无一家独大；socket 的时延代价则完全记在栈头上 | 64 B RTT 各层单价见第十五、十六章（raw 162 µs / socket 439 µs） |

这张账的用法是**反查式定位**：如果外环掉到 30 Mbit 而回环还能 85 Mbit，锅在 SLIRP/网卡一层；如果连回环一起塌，才轮到怀疑 lwIP 配置或 CPU。一次测量同时覆盖两条口径，正是为了拿到这个分辨力。而无论 base 还是极限配置，回环 RTT 都稳定在 520–730 µs——时延类指标对编译期缓冲旋钮几乎不敏感，想压延迟去找调度和 API 层。

### 3. 纵向对齐：这些数字和前几章矛盾吗

把本章数字放回全系列的账本里，有三处看似冲突、实则自洽：

1. 第六章说 SLIRP 天花板 ≈120 Mbit，本章外环只有 70–95 Mbit——负载不同：第六章是 guest 单向泵、主机只收；本章 thrx 是 guest 收，多了 SLIRP→guest 方向的整条接收链。天花板从来不是标量，而是"哪条路径"的属性。
2. 第十六章说 socket TCP 吞吐只有 38.9 Mbit，本章同为 socket 路径却有 80+ Mbit——差异来自数据口用 16 KB 大缓冲整块拷贝、热路径零日志，而第十六章测的是逐消息语义。API 层代价（RTT 的 2.7×）与吞吐潜力是两个变量。
3. 第十九章每包 CPU 账单 601 µs，本章独立重测的回环 RTT ≈600 µs 同量级——两次不同构建的相互印证，也是 RTT 指标稳定性的直接证据。

这种"每个绝对值都带着自己的实验条件"的记账方式，就是全系列反复强调的方法论本体：**数字没有上下文就只是噪音，条件钉死了它才叫结论。**

### 4. 可选加分项的结果记录：iperf 例程放弃原因

官方例程族中确有 `examples/ethernet/iperf`，但其依赖的 `protocol_examples_common` 组件**没有 openeth 的 Kconfig 入口**（v6 里只剩 `sdkconfig.rename` 里一条指向不存在的 `CONFIG_ETHERNET_OPENETH_SUPPORT` 的改名残迹；`ETH_USE_OPENETH` 只存在于 esp_eth 组件自身菜单里）。把例程接上 openeth 需要改它的连接管理代码，与本实验"复用已验证 bring-up 模板"的原则相悖，故如实放弃，沿用自研 bench 对齐口径。

## 24.4 实验 B：调优矩阵——旋钮 × 档位 × 三指标

### 1. 矩阵总表

固定负载（外环 RX 4 MB + 回环 RTT 512 B×200 + 回环批量 4 MB），每次只动一个旋钮、其余回到 IDF 默认，每点两轮同窗实测。DMA 行即 `CONFIG_ETH_OPENETH_DMA_RX_BUFFER_NUM`（openeth RX 描述符个数，默认 4）。

| 点  | 改动旋钮                 | 外环 RX吞吐 (Mbit)      | 回环 RTT avg (µs) | 回环批量 (Mbit) | 堆 free/min-ever (KB) |
| --- | ------------------------ | ----------------------- | ----------------- | --------------- | --------------------- |
| p0  | 基线（IDF 默认值）       | 72.7 / 93.2             | 580 / 635         | 89.6 / 74.7     | 206 / 182             |
| p1  | SND_BUF 28800            | 91.1 / 76.7             | 584 / 563         | 87.2 / 84.8     | 207 / 160             |
| p2  | WND 11520（RX 环=4）     | **3.4–6.7（三测皆崩）** | 535–585           | **94 档正常**   | 206 / 176             |
| p2b | WND 11520 + **RX 环=16** | 57.4 / 69.0             | 560 / 535         | 84.4 / 94.2     | —                     |
| p3  | WND 28800（RX 环=4）     | 无有效轮（黑洞性劣化）  | ~597              | —               | —                     |
| p3b | WND 28800 + RX 环=16     | 10.0                    | 514–633           | 101.3 / 101.2   | 187 / 139             |
| p3c | WND 28800 + RX 环=32     | 54.6 / 72.2             | —                 | 79.4 / 101.8    | —                     |
| p4  | MSS 536（RX 环=4）       | 无有效轮                | 537 / 770         | **38.7 / 37.9** | 197 / 145             |
| p5  | MSS 1460                 | 74.3                    | 681 / 566         | 85.9 / 84.2     | 206 / 182             |
| p6  | TCPIP_RECVMBOX 64        | 89.3                    | 575 / 589         | 83.9 / 76.5     | 206 / 184             |
| p7  | TCPIP_RECVMBOX 8         | 86.1                    | 590 / 567         | 75.3 / 76.7     | 207 / 184             |
| p8  | TCP_RECVMBOX 32          | 72.9                    | 584 / 567         | 85.9 / 84.2     | 206 / 183             |
| p9  | 基线 + RX 环=16          | 73.1 / 82.5             | 637 / 628         | 81.4 / 83.2     | 187 / 163             |

三个"打脸"观察比任何结论都重要：

1. **PBUF_POOL_SIZE 是死旋钮**。它在 IDF v6 的 Kconfig 里根本不存在（grep 整个组件只有上游 `opt.h` 的默认值 16）；在全堆化下它连名义计数闸都不覆盖。`BUILD` 打印里的 `pbuf_pool=16` 从头到尾没变过。
2. **邮箱深度在这套负载下不敏感**。TCPIP 邮箱从 8 到 64、TCP recv 邮箱到 32，三指标位移都在噪声内——因为单条 bulk 流的邮箱压力远小于突发多连接场景，别指望用邮箱换吞吐。
3. **窗口不是白给的**，往下看。

### 2. 本章核心发现：接收窗口必须与 RX 环深配对

p2/p3/p3b/p3c 四个格子拼出一条单调规律：

```text
在途帧数 ≈ 接收窗口 / MSS          openeth RX 环槽位数
   WND 5760  =  4 帧      ⟶  环 4 刚好装下  ⟶ 92 Mbit ✅
   WND 11520 =  8 帧      ⟶  环 4 装不下    ⟶ 3–7 Mbit 💥
   WND 11520 =  8 帧      ⟶  环 16 装得下   ⟶ 57–69 Mbit ✅
   WND 28800 = 20 帧      ⟶  环 16 不够     ⟶ 10 Mbit 💥
   WND 28800 = 20 帧      ⟶  环 32 够       ⟶ 55–72 Mbit ✅
```

机理链：更宽的接收窗口允许 SLIRP 把更多帧背靠背推进 guest → 超出描述符环容量的帧在**驱动层被直接丢弃**（第十七章：洪峰第一瓶颈是 RX 环，先于任何 lwIP memerr）→ TCP 等一个永远不会到达的序号 → 大量时间耗在等超时+选择性重传的死循环上。带宽不但没有涨，反而跌到百分之一；loopback 路径不经 NIC 所以照常起飞（94→101 Mbit），这是区分"环满"与"栈病"的关键对照组。

> [!tip] 迁移到真机怎么读这张表
> openeth 的环是仿真的，ESP32 真机以太网 DMA 描述符数量不同、WiFi 更是没有环的概念。但"**接收侧资源深度 ≥ 对端允许的在途量**"这个不等式在任何栈上都成立：真机上它变成「PBUF 储备量 ≥ 对端窗口/MSS」「WiFi AMPDU 密度 vs 驱动队列」。调优的第一步永远是把这个不等式两边算出来，而不是先动旋钮。

### 3. 发现过程：从灵异现象到单调规律

矩阵不是一次设计出来的，而是被一个"灵异现象"逼出来的。给接收窗口调到 11520 之后：

```text
RESULT kind=thrx mb=4 ack=b'K' secs=9.098 mbit=3.52                 ← 外环崩了
[fw] $$$ LBTH ack_r=0 bytes=4000000 elapsed_us=16395106 mbit=1.95   ← 回环批量也崩!
[fw] $$$ LBRTT ok=200/200 size=512 avg_rtt_us=582 min=464 max=2192  ← RTT 却精准健康?!
```

排查走的是经典排除法。第一反应是宿主机负载漂移（第三章教训），同点连测三次皆崩——排除环境；换回基线配置同窗重跑立刻回到 80+ Mbit——锁定配置相关；再看症状组合：大报文路径死、小报文 RTT 精准健康、控制面无恙，这是典型的**丢帧型重传死锁**而非 CPU 或内存问题。顺着第十七章那句「openeth RX 描述符环是洪峰第一瓶颈」一算账：WND/MSS = 11520/1440 = 8 帧在途 vs 环深 4，正好装不下。抬环到 16 重跑同一配置，外环立刻回到 57–69 Mbit——因果闭环。p3/p3b/p3c 三格再用 28800 窗口复刻一遍这个台阶（16 不够、32 才够），规律就此坐实。

方法论彩蛋：这条规律的发现成本几乎为零，因为它只需要一张"把窗口与环深当二维变量"的网格——但若当初按单变量思维只扫窗口档位，结论就会停在"大窗口在这套环境里会崩"这种错误归因上。**跨层配对扫描应该成为嵌入式网络调优的默认姿势**。

### 4. 反模式实录：「拉满」组合的数据面涓流

实验 A 的第三口径——SND_BUF=65535、WND=65535、MSS=1460（无窗口缩放时的全部上限）——收获了本年度最意外的一条曲线：回环批量单轮跌入 **0.31 Mbit**（4 MB 跑了 103 秒），而同一实例的回环 RTT 依旧 604–723 µs 健康如初；外环方向同期也出现秒级~分钟级吞吐坍缩，关掉之后恢复正常。也就是说：**控制面健康、小报文健康、唯独长队列 bulk 进入涓流档**，且复现存在非确定性（同配置冷启动有时又是百兆档）。

给出可复现的形状描述与当时串口摘录（完整日志存档于工程 `results/ext_dma16.log`）：

```text
$$$ BUILD 07:03:16 sndbuf=65535 wnd=65535 mss=1460 tcpip_mbox=32 pbuf_pool=16
$$$ LBTH ack_r=0 bytes=4000000 elapsed_us=103782935 mbit=0.31
$$$ LBRTT ok=200/200 size=512 avg_rtt_us=723 min=424 max=3183     ← RTT 同时正常
```

这与第二十二章留下的两条未闭合悬案同属一类诚实记录：现象真实、条件敏感、机理尚未完全定位（疑点集中于超大 unsent 队列与 Nagle/ACK 钟摆及 SLIRP 内部缓冲的相互作用）。工程结论反而很干脆：**在没有窗口缩放的平台上把 SND_BUF/WND 一口气拉满是反模式**——65535 这个"看起来最大的整数"正是雷区边缘，生产建议以 4×MSS 到 20×MSS 区间结合实测选择，并永远搭配接收侧资源复核。

### 5. 内存指标怎么读

矩阵最后一列的 min-ever 是周期采样的堆低水位。两个信号值得留意：把 SND_BUF 抬到 28800 后 min-ever 从 182 KB 掉到 160 KB（发送缓冲预留更大的绝对内存账单）；数字本身有毛刺，因为全堆化世界里"最低点"取决于采样时机撞上哪次突发（第五、二十二章的双指标纪律：阶段差分 + 低水位只做哨兵不做预算）。

### 6. 矩阵的使用方法：三步定位法

把这张表变成工程动作，按顺序走三步：

1. **先复算不等式**。写出 `在途帧数 = WND/MSS`，再查接收侧资源的实际深度（仿真是环深，真机是 PBUF 储备与驱动队列）。等式右大于左立即危险。
2. **二分口径**。跑一对「外环 vs 回环」的对照测量：只有外环塌 → 接收/转发层；两条一起塌 → 栈或 CPU；RTT 单独健康 → 大报文路径专属问题。这一步的分辨力远高于任何单点压测。
3. **只动确认过的那一层**，并且一次一个旋钮、留好回退档位。矩阵里 p6/p7/p8 三行的好消息是：邮箱深度这类旋钮在负载不满时拧了也白拧——省下来的调试时间就是收益。

最后提醒一句排障顺序：任何调优之前先把 PCB/fd 这类"数资源上限"的死闸门核对一遍（本章的 MAX_ACTIVE_TCP=16 之坑），否则测出来的所有曲线都可能是伪影。

## 24.5 实验 C：故障注入总集与组合拳

### 1. 全系列手法总表（可检索版）

十类注入，前三列告诉你怎么打，后两列教你把它翻译成人间事故：

值得强调两条横向规律。其一，**观测位永远成对出现**：每个注入点旁边都站着一个"预期会动的计数器"和几个"预期必须纹丝不动的计数器"（比如 TX 丢帧时 tcp.memerr 必须保持 0——它动了就说明丢错层了）。单计数器观测是误诊之源。其二，**恢复路径比故障路径更值得设计**：本次实验里每个阶段后都插一个 recovery 段，就是为了让"系统还能不能自愈"成为被测对象，而不是想当然。

### 2. 组合拳：弱网上行 × 堆紧张下的 HTTP 服务行为画像

被测服务是一个刻意的最小 HTTP responder：accept 之后读到 `\r\n\r\n`，回一段固定 200 应答再收尾关闭——每请求一线程、无常驻连接池，正是大多数嵌入式 Web 服务的原型形态。故障源两个：`loss 15` 在 netif->linkoutput 上按 15% 概率吞掉 guest 出站帧（等效于"上行残废"的物联网节点），`heap 40` 把堆 malloc 到只剩 ~40 KB（largest block 仅剩 30 KB）。测试设计原则来自第十九章的教训：控制通道固定走另一条链路位置，注入的元命令永远不受被注流量的拥塞影响。

被测服务的完整五阶段时间线（`results/expc.log` 原文摘录，顺序 GET，12~15 发/阶段，超时 5 s，每次注入后必跟恢复段证明因果）：

驱动命令序列（`tools/run_expc.sh` 的主干，可复制执行）：

```bash
B="python3 tools/bench_host.py"
$B http --n 12 --timeout 5          # p1 基线
$B ctrl --cmd "loss 15"             # p2 弱网上行
$B http --n 12 --timeout 5
$B ctrl --cmd "loss 0"; $B http --n 6 --timeout 5    # p2b 恢复对照
$B ctrl --cmd "heap 40"             # p3 堆紧张（malloc 到只剩 ~40KB）
$B http --n 8 --timeout 5
$B ctrl --cmd "heap off"; $B http --n 5 --timeout 5  # p3b 恢复对照
$B ctrl --cmd "loss 15"; $B ctrl --cmd "heap 40"     # p4 组合拳
$B http --n 15 --timeout 6
$B ctrl --cmd "loss 0"; $B ctrl --cmd "heap off"     # p5 全恢复
grep -c '### DROP' logs/m_expc.log  # 注入量对账
```

五个阶段的实测结果：

```text
p1 基线            12/12 成功   avg 6.8 ms   max 12 ms
p2 loss 15%（TX）  12/12 成功   avg 1093 ms  p90 4185 ms  ← 百分百成功、秒级尾延!
p2b 摘除丢帧        6/6 成功     avg 4.5 ms                        （瞬间痊愈）
p3 heap→≤40 KB     8/8 成功     avg 5.1 ms                        （单请求太小，饿不死）
p4 loss15+heap40   15/15 成功   avg 1301 ms  p50 1494 ms max 4500 ms
p5 双摘除           10/10 成功   avg 6.8 ms                        （全愈）
```

这份画像的结论比"服务挂没挂"深刻得多：

1. **可靠性机制在替你掩盖事故**。15% 上行丢帧没有产生任何一个失败请求——TCP 重传把丢失全部兜住——代价是 p90 从 11 ms 飙到 4185 ms。如果你只监控成功率，事故已经发生而你毫无感知；如果监控 P99，它藏不住。
2. **堆紧张不是均匀变慢，而是沉默等待**。heap 压到 40 KB（largest block 仅剩 30720 B）期间 HTTP 还能全绿——单个 GET 的 pbuf 需求恰好落在残余余量内；但 mem 快照显示 min-ever 被永久砸穿：stress 前后 203 KB→30 KB 且释放后不再回升到原高度，这就是全堆化的碎屑留在池底。
3. **叠加的度量学**：两者叠加时失败率依然为零，慢却从"少数请求的长尾"变成"一半以上请求的常态"（p50 1494 ms）。容量评估必须做组合注入，单元格全绿不代表乘积成立。

支撑第三条的内存账本原始记录（注入期间的 `mem` 快照与串口 DROP 计数）：

```text
dropped_frames_total_serial_lines=25          ← p2/p4 阶段共吞掉 25 个出站帧
[fw] $$$ MEM under-stress free=39896 largest=30720 min_ever=39896
[fw] $$$ MEM after-off    free=197776 largest=110592 min_ever=30448
[fw] $$$ MEM under-stress free=40104 largest=30720 min_ever=30448
[fw] $$$ MEM after-off    free=193320 largest=110592 min_ever=25828
```

注意 `min_ever` 的行为：第一轮 stress/release 之后它停在 30.4 KB，第二轮跌到 25.8 KB 再也不回头——这就是第五章讲的"低水位哨兵"真实工作起来的样子：free 看起来回到了 190 KB+，但系统的历史最低点已经证明过它曾经离悬崖只剩 25 KB。任何"释放了就安全了"的判断在全堆化世界里都要过这道哨兵的复核。

### 3. 把总表变成日常资产

这张总表的正确打开方式不是事故后翻阅，而是三个前移：

- **设计期**：新服务上线前过一遍表格右列（真实事故对应），每找到一条适用行就补一个对应的观测位与恢复预案；
- **CI 冒烟**：把「loss 10% 下跑通一组请求」「heap 压到阈值 X 后核心功能仍可用」做成两分钟的回归用例——它们抓住的是"谁又偷偷往关键路径上加了分配"这类最难人工排查的回归；
- **值班手册**：观测位列就是告警指标的候选清单，恢复路径列就是 runbook 的第一稿。

### 2. 三条贯穿暗线的总结陈词

**暗线 A｜单线程邮箱模型的边界即性能预算地图。** 第一章埋下的 tcpip_thread，在第十三章成为解释一切的钥匙，到本章彻底显形：它既是单位（37 µs/api 往返）、也是瓶颈（一次 busy-wait 拖垮全连接）、还是诊断仪（rt 计数差分）。判定任何优化前先问：这活儿本来应该睡在哪个邮箱上？

**暗线 B｜Vanilla 与 IDF 的每一处分叉都是一章素材。** 从 `LWIP_NETIF_TX_SINGLE_PBUF` 硬编码到 `LWIP_MQTT=0`，从 ESP_LWIP 补丁族的按需定时器到本期补刀的「PBUF_POOL_SIZE 无 Kconfig」，idf fork 的改造清单已经在 24.8 汇总成大表——读懂它你迁移 upstream 版本指南时就不用重走这些弯路。

**暗线 C｜全堆化改变了内存问题的问法。** 问"池子多大"已经没有意义，问"这一秒谁在跟堆借内存"才有意义：PBUF_POOL_SIZE 死旋钮（本章）、计数闸只护 PCB（第五章）、mbedtls alloc 直呼（第二十二章）、min-ever 池底碎屑（本章组合拳）。这是 Vanilla 文档完全帮不上忙的地界。

### 3. 如果只带走五句话

1. 邮箱是 lwIP 世界的呼吸机——所有慢问题的第一嫌疑人是"谁占了 tcpip 线程的呼吸周期"，而不是哪个协议参数。
2. 全堆化之后，"池子"变成"账本"；计数器还在，钱包没了。
3. 吞吐问题先写不等式：接收侧深度 ≥ 在途帧数 ≥ BDP/MSS，再动手拧旋钮。
4. 故障注入要打组合拳、留恢复段；监控要看分位数，成功率会在最要命的事故面前装睡。
5. QEMU 教给你的方法论全部可以带去真机，绝对数字一概不能——每张表都标清楚哪一列属于哪边。

## 24.7 性能预算方法论：五本账定容量

给一台设备做容量规划，就列这五张表；每张表的栏目都在前文有自己的章节出处：

1. **CPU 账**（ch19）：每包 601 µs 全链路账单分解；进出双向 × 目标包速率 = 期望占用率，对照优先级地图找抖动源头。
2. **内存账**（ch5/22）：稳态集合（TLS 会话 +27 KB 这类）+ 峰值差额（握手 +33 KB）+ 最坏并发的 fd/pcb 数；哨兵用 min-ever，预算用手动清单。
3. **带宽×时延积**（ch12）：BDP 决定窗口需求下限，本章补上接收侧：**环深/储料 ≥ WND/MSS ≥ BDP/MSS** 左右两端都要满足才谈得上提速。做个算术示范：100 Mbit 链路 × 10 ms 往返 → BDP = 100e6 bit/s × 0.01 s / 8 = 125 KB；MSS 1460 时在途帧数 ≈ 86 帧。把这个数字写在白板上，再去看自己接收侧的 PBUF 储备和驱动队列深度——很多"玄学丢包"在这一步就现形了，根本轮不到动协议栈参数。
4. **仿真天花板换算表**（本章产物）：SLIRP 外环 70–95 Mbit 段、±50% 负载漂移、ping 会话毛刺、ICMP 单向通——凡在这几条下面做的测量标注"仅限相对比较"。绝对值不可迁移清单一览：

| 测得的绝对值                  | 能否带去真机           | 替代物                         |
| ----------------------------- | ---------------------- | ------------------------------ |
| SLIRP 外环吞吐（~80 Mbit 段） | ✗                      | 真机 PHY 实测 + 主机侧抓包计时 |
| openeth RX 环 = 4             | ✗（真机另有 DMA 配置） | 「深度 ≥ 在途」不等式          |
| socket/raw 单价比 2.7×        | △ 量级近似保留         | 真机上快速重标定               |
| RTT 600 µs 回环单价           | ✗（QEMU CPU 模型差异） | 板上同法重测                   |
| memerr/RTO/退避行为序列       | ✓ 逻辑层面可迁移       | 相同注入手段即可复现           |
| 故障注入→观测位映射表         | ✓ 方法论整体迁移       | —                              |

5. **故障预算**（ch20/21/24）：允许丢失多少、允许慢多久（P50/P90/P99 分别为几毫秒），然后以此反推哪些注入必须纳入 CI 冒烟。

## 24.9 结语：一条路，三个坐标系

二十四章走完，三条主线在这里交汇：

- 和 [[freertos-deep-dive|FreeRTOS 深度解析系列]]的关系：lwIP 每一处"为什么阻塞在这里、被谁唤醒"，最终都会落到 FreeRTOS 的队列、信号量和 tick——两个系列互为对方的运行时注脚。lwIP 第十九、二十二章的任务账单，就是 FreeRTOS 第二十四章调试方法论的实习报告。
- 和 [[linux-driver-deep-dive|Linux 设备驱动开发详解系列]]的关系：同一个 netdev/API 分层心智模型的两极呈现。学完 lwIP 再看 Linux 驱动会得到一份"同一问题域在不同资源假设下的两种答案"的对照笔记——比如 NAPI 轮询恰是 openeth RX 环问题的重量级解法。
- 和读者你的关系：这个系列从未想把 lwIP 当成需要背诵的 API 集——它是一条完整的证据链，每一章都在练习同一种能力：**对着一个黑盒系统，提出可证伪的问题，找到合适的观测位，再用可复现的实验收束答案**。终点站的送别礼物只有一句：下次设备"跑不快"或"莫名其妙死"的时候，愿你随手就能画出那棵决策树。

下一站没有本系列的章节了。如果想继续沿着这套方法往前走，三个方向都在同一条延长线上：把本章矩阵搬上真机以太网 PHY 重测一遍（检验 24.7 的换算表）；给 ch20 的 HTTP 服务接上 TLS 看第四种口径的长尾；或者干脆挑一个还不熟悉的协议栈（Zephyr / LwIP upstream 2.2 正式版）用这二十四章练出来的手艺从头拆一遍。工具已经全部在你手里：[[ch3-qemu-network-lab|第三章]]的实验室、[[ch12-tcp-reliability-flow-control|第十二章]]的注入手法、[[ch23-debugging-toolbox|第二十三章]]的工具箱和本章的预算清单。

## 24.10 小结

- 天花板三层账：环境（SLIRP 70–95 Mbit 段）、配置（安全区间的小步旋钮）、协议开销（loopback RTT ≈600 µs 恒定、吞吐与外环持平说明瓶颈三家共担）。
- 本章头号发现：**接收窗口 × RX 环深**不等式。WND 11520 用环 4 必然黑洞化（3–7 Mbit），配环 16 恢复 57–69 Mbit；WND 28800 要环 32 才救回来。任何加速窗口的动作必须同步复核接收侧储料深度。
- 反模式与悬案如实入库：无缩放平台 SND_BUF/WND 拉满会诱发间歇性涓流档（LBTH 0.31 Mbit 而 RTT 同期正常）；`PBUF_POOL_SIZE` 是没有 Kconfig 的死旋钮；TCPIP 邮箱 8→64 三指标均在噪声内。
- PCB 上限 16 的黑洞式串联（SYN 静默丢弃）再次上榜——本轮所有连续测量都建立在把它抬到 64 之后。
- 组合拳结论：HTTP 在弱网+堆紧张下"从不失败、只会长尾"（成功率 100%，p90 4185 ms），故障预算必须写成 P99/时延分位数，成功率监控会在这种事故面前集体失明。
- 系列完结：知识地图见 24.6，预算方法论与不可迁移清单见 24.7，IDF 改造点大表见 24.8。
