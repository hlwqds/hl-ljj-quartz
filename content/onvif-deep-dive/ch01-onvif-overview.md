# ONVIF 深度解析（一）：ONVIF 是什么——三件套技术栈与 Profile 体系

这一章回答三个问题：**ONVIF 解决什么问题**（互操作荒漠——2008 年前每个厂商一套 SDK 的世界）、**它技术上是什么**（一句话：发现用组播、控制用 SOAP、取流用 RTSP 的三件套）、**Profile 体系怎么读**（S/G/C/T/M/D/A 各圈一块能力域）。读完它，任何一台 ONVIF 设备的说明书你都能一眼定位它「会什么、不会什么」。

---

## 1.1 互操作荒漠：ONVIF 之前的世界

网络摄像机诞生之初的十年（1996 年 Axis 造出第一台起），行业被一个朴素问题卡死：**A 厂的 NVR 连不上 B 厂的摄像头**。每家都私有协议 + 私有 SDK，集成商每接一个新品牌就要重写一遍对接代码，项目越大供应商锁定越深。2008 年，Axis、Bosch、Sony 三家发起成立 ONVIF（Open Network Video Interface Forum）——注意它**先是论坛、后是标准**：标准文本由成员共同维护，符合性靠认证流程背书。十几年后它成了事实上的行业底座：主流安防厂商几乎全数在册，「支持 ONVIF」成了 IP 摄像机/NVR 的出厂默认词。

理解 ONVIF 的正确姿势：**它不是发明了新技术，而是把三样现成的 Web 服务技术钉在了一起**（1.2），再用 Profile 体系（1.3）解决「标准太全反而没人全实现」的老问题。

## 1.2 技术栈一张图：三件套与控制/媒体分离

```text
┌────────────────────────────────────────────────────────────────┐
│  发现层  WS-Discovery（SOAP over UDP 组播 239.255.255.250:3702）│
│          设备自报家门：我是谁、我在哪、我能干什么（ch02）        │
├────────────────────────────────────────────────────────────────┤
│  控制面  SOAP/WSDL over HTTP（通常 80 端口，XML 一切）          │
│          设备管理/媒体配置/PTZ/事件/录像——全是「带 XML 的 POST」 │
│          （ch03–ch05、ch07、ch08）                              │
├────────────────────────────────────────────────────────────────┤
│  媒体面  RTSP/RTP（通常 554 端口）                              │
│          GetStreamUri 从控制面领到 rtsp:// 地址后，             │
│          媒体数据走 RTSP 信令 + RTP 传输（ch06）                │
└────────────────────────────────────────────────────────────────┘
```

这个**控制/媒体分离**的架构是 ONVIF 最值得品味的一笔：控制面全是低频的 XML 请求-应答（配个编码器、转一下云台），媒体面全是高频的二进制流（H.264/H.265 帧数据）——两者对延迟、可靠性、传输协议的要求完全不同，硬塞进一条通道必然两头不讨好。分离之后，控制面复用了整个 Web 服务生态（WSDL 代码生成、XML 工具链），媒体面复用了流媒体生态（RTSP/RTP、播放器、ffmpeg）。代价也明确：**两套协议栈、两个端口、两条鉴权体系**（ch04 会看到口令怎么在两条体系里各算一遍）。

一句话记住三个组件的分工：**发现告诉你它在哪，控制告诉你怎么配，媒体把画面给你**。

## 1.3 Profile 体系：给标准做减法的艺术

ONVIF 规范卷帙浩繁（几十个服务、上千个操作），没有厂商做得到全实现——于是 ONVIF 用 **Profile** 把能力切成「保证互相兼容的最小集合」，设备按实现的 Profile 打标：

| Profile | 圈定的能力域                        | 关键词                    |
| ------- | ----------------------------------- | ------------------------- |
| **S**   | IP 摄像机 → 客户端的实时取流        | 本系列的主体（ch05/ch06） |
| **G**   | 录像、存储、回放、搜索              | NVR/存储侧（ch08）        |
| **C**   | 门禁（出入口控制）                  | 与视频并行的另一条产品线  |
| **T**   | S 的现代化：H.265、双向音频、元数据 | 取流能力升级包            |
| **M**   | 元数据与边缘智能（为机器学习供数）  | 分析结果标准化            |
| **D/A** | 显示设备 / 门禁新代（凭据管理等）   | 生态外延                  |

读法要点：Profile 是**能力声明而非版本号**——一台标着 S+T 的摄像机意味着两套保证同时生效；标着 S 却缺 S 必选特性的「伪装者」是互通坑王（ch09 专门审判）。Profile 之间的演进关系也有讲究：T 不是 S 的替代而是超集方向，新项目选型时「S 起步、T 增强」是常见组合。

## 1.4 与近亲们的边界辨析

- **RTSP**：只是媒体面的传输协议（ONVIF 三件套之一）。设备「支持 RTSP」不等于「支持 ONVIF」——前者只保证你能拉到流（还常常要靠文档猜 URL），后者保证发现、配置、控制、取流全链可编程；
- **厂商私有 SDK**：ONVIF 出现前的世界秩序，至今仍以「私有协议跑全量功能、ONVIF 跑基础功能」的形态共存——很多设备的 ONVIF 面只是私有能力的子集投影（ch09 的兼容性坑一半来自这里）；
- **GB28181**：国内视频监控联网的标准，走 SIP 信令路线，与 ONVIF 的 SOAP 路线是两套体系；国内项目常见「双栈」设备。深入它属于另一个系列的活，本系列只在对照处提及。

## 1.6 小结

- ONVIF = 论坛 + 标准：把 WS-Discovery、SOAP/WSDL、RTSP/RTP 三件现成技术钉在一起，解决 IP 视频设备的互操作问题。
- 架构核心是控制/媒体分离：低频 XML 走 HTTP、高频码流走 RTSP——代价是两套协议栈与两套鉴权。
- Profile 是「保证互通的最小能力集合」而非版本号：S 取流、G 录像、T 现代化、M 边缘智能；标 S 不等于全套 S（ch09 审判伪装者）。
- RTSP ≠ ONVIF；私有 SDK 以「超集」形态共存；GB28181 是另一条 SIP 路线。
