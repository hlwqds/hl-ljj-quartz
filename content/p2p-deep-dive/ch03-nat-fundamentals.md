# P2P 网络深度解析（三）：NAT——P2P 的头号敌人（原理、分类与观察）

上一章末尾，我们的对等程序死在一个现象上：**出站能通，入站被拦**。这一章拆开那个盒子：NAT 的映射表长什么样（3.1）、为什么 NAT 的"类型"不是玄学而是两个正交行为的组合（3.2–3.4）、如何亲手测出你家 NAT 的类型（3.5）、以及为什么这决定了你的 P2P 程序能否被直连（3.6）。读完它，"你的 NAT 是对称的"这句话对你应该是完全具体、可验证的命题，而不是运维黑话。

---

## 3.1 NAT 的本体：一张五元组改写表

### 1. 它解决的问题：IPv4 不够分

IPv4 地址 32 位，约 43 亿个，1990 年代就见了顶。RFC 1918 划出三段私网地址（`10/8`、`172.16/12`、`192.168/16`）供内网自由使用，代价是它们**在公网不可路由**。NAT（Network Address Translation）就是那道翻译关卡：整个内网共用一个（或一小池）公网地址出网，路由器在边界上改写每个包的地址端口。

```text
内网主机A 192.168.1.20:54321 ──┐          ┌── 公网服务器 47.x.x.x:443
内网主机B 192.168.1.30:54322 ──┤   NAT    ├── 公网服务器 8.8.8.8:53
内网主机C 192.168.1.40:54321 ──┘          └── ...
                                ▲
                    出站包：源 192.168.1.20:54321 → 源 203.0.113.7:40001
                    入站包：目的 203.0.113.7:40001 → 还原成 192.168.1.20:54321
```

改写的依据就是映射表（Linux 内核里即 conntrack，见 [[kernel-protocol-stack-deep-dive|内核网络协议栈系列]]）：

| 内部端点 (ip:port) | 外部端点 (ip:port) | 对端 (ip:port) | 状态        |
| ------------------ | ------------------ | -------------- | ----------- |
| 192.168.1.20:54321 | 203.0.113.7:40001  | 47.x.x.x:443   | ESTABLISHED |
| 192.168.1.30:54322 | 203.0.113.7:40002  | 8.8.8.8:53     | ESTABLISHED |
| 192.168.1.40:54321 | 203.0.113.7:40003  | 任意           | ...         |

### 2. 关键观察：外部端口是"借"出来的

注意第三列"对端"——这正是后面一切分化的源头。**NAT 给你的外部端口，可能是专属于某个对端的（用过就锁），也可能是一张通用门牌（谁都能凭它找到你）**。这个差异无法从外部一眼看穿，却是"你家能不能被打洞"的全部秘密。

另一个关键观察：映射是**由出站流量创建的**。内网主机主动发包，NAT 才建立映射；没发过包的内网主机在公网上没有地址——这就是上一章"入站被拦"的机制本体：不是 NAT 恶意拦你，是**查无此映射**。

> [!note] NAT 不是防火墙，但顺手当了防火墙
> 严格说 NAT 只做地址改写，"丢弃不匹配映射的入站包"是它的副作用——无映射可还原的包只能丢弃。家宽路由器把这个副作用与状态防火墙合体后，NAT 在大众认知里就成了"安全设备"。这个混淆有实际后果：IPv6 时代地址充足、NAT 退场，很多人突然发现设备直接暴露公网——因为安全从来靠的是状态过滤，不是地址改写。

## 3.2 经典四型：RFC 3489 的分类法

2003 年的 RFC 3489（STUN v1）按行为把 NAT 分成四型，这套词汇至今仍是行业通用语。理解四型的钥匙只有一个问题：**同一个内部端口，向不同对端发包，NAT 给它分配的外部端口变不变？过滤规则跟着对端走多严？**

### 1. Full Cone（全锥）

最宽松：内部端点 `192.168.1.20:54321` 第一次出站时，NAT 分配 `203.0.113.7:40001`，并在表里记下"**任何**外部主机发往 `40001` 都转给它"。门牌一旦挂出，全网可见：

```text
              ┌────────────┐   ①A:54321→X 首包，NAT 分配 40001
   A ─────────│    NAT     │──────────▶ X（建立映射）
              │ 40001→A    │
   X ─────────│            │◀── 任意主机 → 40001 都能进（无需 A 先联系过）
   Y ─────────│            │◀── ✅ 通
   Z ─────────│            │◀── ✅ 通
              └────────────┘
```

### 2. Restricted Cone（地址受限锥）

映射照样按内部端点分配，但入站放开一个条件：**只有 A 主动发过包的那个 IP**（不管端口）可以回入。X 主机的任意端口能进，Y、Z 不行——除非 A 先给 Y 发过包。

### 3. Port-Restricted Cone（端口受限锥）

再加一档严格：**只有 A 主动联系过的精确端点** `X:x` 的回包能进。X 的其他端口也不行。家用路由器大多是这一型（或其与对称的混合）。

### 4. Symmetric（对称）

最严：**换一个对端，就换一个外部端口**。A:54321 → X 走 `40001`，A:54321 → Y 走 `40002`。外部观察者从 X 看到的是 `40001`，从 Y 看到的是 `40002`——**同一个内部端点在不同对端眼里是两副面孔**，这直接击碎打洞的前提（3.6 节推导）。

### 5. 四型对照表

| 类型             | 外部端口分配       | 入站过滤条件          | 打洞友好度 |
| ---------------- | ------------------ | --------------------- | ---------- |
| Full Cone        | 每内部端点固定一个 | 无（任意源可入）      | 🟢 随便打  |
| Restricted Cone  | 每内部端点固定一个 | 源 IP 须被主动联系过  | 🟢 可打    |
| Port-Restr. Cone | 每内部端点固定一个 | 源 ip:port 须被联系过 | 🟢 可打    |
| Symmetric        | 随对端变化         | 精确端点匹配          | 🔴 难打    |

前三型的共同点：**映射与对端无关**（外部端点对全网一致）；对称型映射与对端绑定。这个二分比四分更重要——下一节的现代分类法就是把它扶正。

## 3.3 现代视角：RFC 4787 的二维正交分类

RFC 3489 的四型把两件独立的事搅在一起了：**映射怎么建**（出站方向）和**包怎么过滤**（入站方向）。2007 年的 RFC 4787（NAT 的 UDP 行为要求）把它们拆成正交两轴，从此描述一个 NAT 只需两个词：

**映射行为（Mapping Behavior）**——问：同一内部端点 `i1:i2` 先后向不同对端发包，外部映射端点变不变？

| 行为                         | 含义                     | 对应旧称       |
| ---------------------------- | ------------------------ | -------------- |
| Endpoint-Independent (EIM)   | 不变：一次映射，全网复用 | 前三锥的共同点 |
| Address-Dependent (ADM)      | 换目标 IP 就换映射       | 对称的子集     |
| Address-and-Port-Dep. (APDM) | 换目标 ip:port 就换映射  | 对称           |

**过滤行为（Filtering Behavior）**——问：已有映射的前提下，哪些源的入站包被放行？

| 行为                         | 放行条件                  | 对应旧称         |
| ---------------------------- | ------------------------- | ---------------- |
| Endpoint-Independent (EIF)   | 任意源（凭映射即可入）    | Full Cone 的过滤 |
| Address-Dependent (ADF)      | 源 IP 须匹配映射的对端 IP | Restricted Cone  |
| Address-and-Port-Dep. (APDF) | 源 ip:port 须完全匹配     | Port-Restr. Cone |

加上第三个独立属性 **hairpinning（打环）**：两台同在内网的主机，各自通过 NAT 的公网侧地址互访，NAT 能否"绕回来"转给对方？大量家宽路由器不支持打环——这意味着**两台同一 NAT 后的设备互相打洞也会失败**，只能靠局域网内直连兜底（WebRTC 的 ICE 把"同网段 host candidate"排在最高优先级，就是给这个留的后门）。

> [!tip] 为什么这个二维化重要
> 因为打洞的成败**只由映射行为决定**：打洞的前提是"对端从服务器 X 学到的我的公网端点，恰好就是它直连我时能用的端点"。EIM 满足此前提，APDM（对称）不满足。过滤行为反而好办——它只决定"洞"要多准：EIF 的洞谁都能钻，APDF 就要求双方出站包精确互指（ch04 的打洞时序干的就是这件事）。把变量拆开后，策略设计第一次变得可以推理。

## 3.4 对称 NAT 为什么是 P2P 的天敌

把打洞的前提逐字代入对称 NAT，看它在哪一步断裂。设想 A、B 各自在家，S 是公网引路服务器：

```text
①  A:9999 ──"我要连B"──▶ S     S 看到 A 的映射是 203.0.113.7:40001
②  B:9999 ──"我要连A"──▶ S     S 看到 B 的映射是 198.51.100.9:50001
③  S 告诉 A："B 在 198.51.100.9:50001"；告诉 B："A 在 203.0.113.7:40001"
④  A 直接向 198.51.100.9:50001 发包 ──▶ B 的 NAT 收到……
```

第 ④ 步，B 的 NAT 查表：B 的映射 `50001` 是**专门为对端 S 建的**。A 的包源地址不是 S → APDF 过滤丢弃。更糟的是 A 侧：A 向 B 发包这个动作，又触发 A 的 NAT 为"对端 B"新建了一条**不同的**映射（比如 `40088`）——B 按引路服务器给的信息回打 `40001`，那个门牌此刻只对 S 有效。**双方各自说的地址，在对方眼里都是错的**，洞越打越歪。

EIM 世界里这一切不存在：A 在第 ① 步挂出的门牌 `40001` 对全网有效，第 ③ 步交换的信息天然准确，第 ④ 步双方互指即穿透。一句话总结：**打洞交换的是地址情报，EIM 的情报是全局真的，对称 NAT 的情报是按对端分裂的假面**。

## 3.5 实验：测出你家 NAT 的类型

### 1. 用 STUN 客户端看映射

Linux 上装 `stun-client`（`apt install stun` / `pacman -S stun`）：

```bash
$ stun stun.stunprotocol.org
MappedAddress = 203.0.113.7:40001      # 这就是你 NAT 给你的公侧面孔
```

换个 STUN 服务器再测一次，比较两次的**端口**：相同 → 大概率 EIM（前三锥）；不同 → 对称。这一条是最要紧的判据（这就是 RFC 3489 的经典测试法，RFC 5389 之前 STUN 的本职工作之一）。

### 2. 双客户端交叉验证

更严谨的测法需要两个不同 IP 的观察点。用两台手机（各自流量）+ 一台电脑做观察者太奢侈，实践中可用现成工具：Wireshark 官方维护的 `stun` 版本、或 `pystun3`、或直接跑 ch04 将要写的迷你引路服务器——它顺手就把"两次映射到不同服务器"的对比做了。

### 3. 观察打环

在家用两台设备测同一个公网映射互访，或在路由器管理界面看 conntrack 表（OpenWrt：`cat /proc/net/nf_conntrack | grep udp`），能看到映射的创建与老化——**UDP 映射的典型寿命只有几十秒到几分钟**（RFC 4787 建议 TCP 2 小时、UDP 至少 2 分钟，但家用设备实现五花八门），这就是为什么需要保活（keepalive）：P2P 程序定期发包，防止 NAT 把洞的记录当垃圾回收。

> [!warning] 一个 NAT 一个脾气，甚至一个固件一个脾气
> 运营商级 NAT（CGNAT，你和你楼上共用一个公网地址的那层）叠加家庭路由器，意味着你的包可能穿过**两台行为不同的 NAT**——整体行为取交集，通常更糟。所以工程实践（如 WebRTC）从不假设类型，而是把所有候选路径排成表挨个试——这正是 ch04 ICE 的存在意义。别相信"我家是全锥"的静态判断，NAT 行为还会随固件更新、负载、时段变化。

> [!tip] 🧪 配套实验：p2p-labs/ch03-stun-probe
> 本节判型实验的完整工程：手搓 RFC 5389 STUN 客户端（20 字节头、magic cookie、XOR-MAPPED-ADDRESS 解异或）+ 可离线运行的 mock 服务器（`--offset` 模拟对称 NAT 的映射漂移）。实测：两台同 offset 服务器 → 端口一致判 EIM；异 offset → 漂移 100 判对称。源码直达：[stun.c（代码浏览）](/static/code/#/p2p-labs/ch03-stun-probe/stun.c)、[完整工程](/static/code/#/p2p-labs/ch03-stun-probe/README.md)、[GitHub 源](https://github.com/hlwqds/hl-ljj-quartz/tree/v4/practice/p2p-labs/ch03-stun-probe)。

## 3.6 小结

- NAT 的本体是一张由**出站流量创建**的五元组改写表；入站被拦不是防火墙逻辑而是**查无映射**。
- RFC 3489 四型（全锥/受限锥/端口受限锥/对称）应升级为 RFC 4787 二维模型理解：**映射行为**（EIM/ADM/APDM）× **过滤行为**（EIF/ADF/APDF）+ 打环支持，三个正交属性。
- 对 P2P 最要命的二分：**映射是否与对端相关**。EIM（前三锥）映射全网一致，引路服务器分发的地址情报真实有效；对称 NAT 按对端分裂面孔，情报天然失真——打洞成功率的天花板由它决定。
- 过滤行为决定洞的精度要求而非可行性：EIF 全开，APDF 要求双方出站包精确互指。
- 可观测性：换 STUN 服务器比对端口可判对称与否；conntrack 表可见映射生死；UDP 映射寿命短，需要应用层保活。
- 下一章的 ICE 哲学在本章已经写好：**不要静态判断 NAT 类型，要在运行时把所有路径排出来逐一尝试**。

类型学已经备齐，武器库里还缺三样东西：一个告诉我们"你的公网面孔"的协议（STUN）、一个打洞失败后兜底转发的中继（TURN）、一个把所有候选路径编排起来逐一尝试的框架（ICE）。[[ch04-nat-traversal|第四章：NAT 穿透——打洞、STUN/TURN 与 ICE]]把它们一次配齐——这也是 Tailscale 和 WebRTC 每天在全球跑几十亿次的那套流程。
