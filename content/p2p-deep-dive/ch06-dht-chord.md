# P2P 网络深度解析（六）：分布式哈希表——一致性哈希与 Chord

第五章的结论是要"人为耦合"：**用哈希同时决定数据住哪和拓扑怎么长**。这一章把这个思想做成算法：一致性哈希解决"节点增减时的搬家风暴"（6.1），Chord 环解决"怎么在环上导航"（6.2–6.3），稳定化协议解决"拓扑永动手术"（6.4）。Chord（Stoica 等人，2001）是 DHT 的教学范本——下一章的 Kademlia 会修正它的每个工程缺陷，但不先懂 Chord，就不知道 Kademlia 在优化什么。

---

## 6.1 一致性哈希：把"搬家风暴"压到 K/N

### 1. 朴素方案的雪崩

把字典直接搬上集群，最直觉的设计是 `节点 = hash(key) mod N`。问题出在 **N 会变**：

```text
N=100 时：hash("foo") mod 100 = 37  → 存到 37 号节点
扩容到 N=101：hash("foo") mod 101 = 91  → 搬家！
```

每加一台机器，约 **K×(1 − 100/101) ≈ 99%** 的键全部重定位——扩容一次，全集群洗牌，缓存全失效。对 P2P 这是个死刑判决：节点每秒都在上线离线（churn），意味着数据每一秒都在全网络搬家。

### 2. 哈希环：位置稳定，只搬邻居的货

一致性哈希（Karger 等人，1997，Akamai 的地基）把哈希输出围成一个环，节点和键都撒在环上，规则一句话：**键住进"顺时针方向第一个 ≥ 它的节点"**：

```text
            0
      N56 ╱     ╲ N8          节点：hash(IP) 撒环上
        │         │           键：  hash(key) 撒环上
      N42         N14 ◀─ K10  ← K10 住进顺时针第一个节点 N14
        │         │
      N32 ╲     ╱ N21          键的宿主 = successor(key)
            └─ K30 ──▶ N32
```

节点增减时，只有**紧邻它的那一段弧**上的键需要搬家：新节点 N38 插入，只有 (32, 38] 弧上的键从旧宿主 N42 迁来——平均 **K/N 个键**动窝，其余纹丝不动。从 99% 到 1/N，这就是"一致性"的含义。

> [!note] 虚拟节点：修补哈希的不均匀
> 节点按 IP 哈希落环，位置是随机的——环上会出现贫富不均的弧段（某节点管辖 40% 的键空间）。解法是每个物理节点在环上撒 v 个**虚拟节点**（hash(IP#1)、hash(IP#2)…），大数定律把键空间摊平；顺带收获异构支持（强机器多撒几个）与退出匀速化（一台机器的负载匀给所有人而非砸给一个邻居）。这个 1997 年的补丁今天活在 Redis Cluster 的 16384 槽位、Dynamo/Cassandra 的 token ring 里——一致性哈希早已溢出 P2P，成为分布式存储的标准零件。

## 6.2 Chord 环：路由信息的极简主义

Chord 把一致性哈希环变成可导航网络，全部状态就一个概念：**successor（后继）**——顺时针方向的下一个节点。

- 节点 ID = `hash(IP)`，键 ID = `hash(键)`（同一哈希空间，m 位，典型 160 位）
- 键 K 由 **successor(K)** 负责：环上第一个 ID ≥ K 的节点
- 每个节点至少知道自己的 successor——**朴素查找**就是沿环问过去：

```text
N8 查 K54：问 N14"你管 54 吗？" → "不管，问我后继" → 问 N21 → N32 → N38 → N42 → N48 → N51 → N56"我管！"
                                                                                     8 跳，O(N)
```

线性表能查但太慢。Chord 的全部加速机制是给每个节点加一张 **m 项的 finger table**：

```text
finger[i] = successor( n + 2^(i-1) )     i = 1..m

N8 的 finger table（m=6，环共 64 个位置）：
┌───┬──────────────┬────────────┐
│ i │ 起点 n+2^(i-1) │ finger[i]  │
├───┼──────────────┼────────────┤
│ 1 │ 8+1  = 9     │ N14        │
│ 2 │ 8+2  = 10    │ N14        │
│ 3 │ 8+4  = 12    │ N14        │
│ 4 │ 8+8  = 16    │ N21        │
│ 5 │ 8+16 = 24    │ N32        │
│ 6 │ 8+32 = 40    │ N42        │   ← 越远的条目跨度越大：1,2,4,8,16,32
└───┴──────────────┴────────────┘
```

注意 finger table 的形状：**指数间距**。前几项盯着隔壁（管近处的事），后几项跨半个环（管长途跳跃）——像高速公路匝道体系：近程走辅路，远程直接上环线。

## 6.3 路由算例：每跳至少减半剩余距离

**查找算法**：要找键 K，把请求转发给 finger table 里 **ID 不超过 K 的最远节点**（" closest preceding finger"）；若自身 successor 已 ≥ K，则自己就是宿主，直接应答。

完整走一遍 `N8 查 K54`（沿用上图节点集 {N8, N14, N21, N32, N38, N42, N48, N51, N56}）：

```text
① N8：查 finger，不超过 54 的最远者是 finger[6]=N42（起点 40）
        N8 ──"帮我找 54"──▶ N42          剩余距离 54-40 = 14
② N42：finger[4]=N51（起点 50，不超过 54 的最远者）
        N42 ─────────────▶ N51          剩余距离 54-50 = 4
③ N51：自己的 successor 是 N56 ≥ 54 → 我知道答案：K54 归 N56
        N51 ──"在 N56"──▶ N8            3 跳完成（朴素查找要 8 跳）
```

为什么是 O(log N)？关键在指数间距：设当前节点距 K 还有 D，选择的最远 finger 起点 ≤ K 意味着**下一跳离 K 的距离 < D/2**（跨度 2^i 的条目能跳过 [n, n+2^i) 的整段）。每跳距离减半，m 位环上最多 log₂(2^m) = m 次内收敛；N 个节点的环里平均只需 **O(log N) 跳**。一百万节点的网络，log₂(10⁶) ≈ 20 跳——第五章的"问遍所有人"变成了"二十次定向跳跃"。

> [!tip] 路由核心长什么样（C 版摘录）
>
> ```c
> /* chord.c —— 查找主循环：closest_preceding_finger 逐跳转发并计数 */
> for (;;) {
>     if (key == cur->id)
>         return cur->id;                 /* 哈希恰好砸在节点 ID 上：宿主是我 */
>     if (between(cur->id, key, succ0))
>         return succ0;                   /* 目标落在我的后继弧段：它就是宿主 */
>     /* 从最远 finger 往回找不超过 key 的活节点 */
>     int next = -1;
>     for (int i = M - 1; i >= 0; i--) {
>         if (between(cur->id, cur->finger[i], key)) {
>             next = cur->finger[i];
>             break;
>         }
>     }
>     (*hops)++;
>     cur = by_id(next);                  /* 每跳至少把剩余距离减半 */
> }
> ```
>
> 这正是上面 N8→N42→N51 三跳的代码形态。churn、稳定化、容错它都没有——那正是 6.4 的内容，也是从教科书到工程的全部距离。配套实验把这段核心补成了完整模拟器（含后继链容错与杀节点实验）：
>

> > m=8 位环、16 节点单文件模拟器：200 次查找实测平均 1.78 跳/零错判；随机杀 37% 节点 + 3 轮 stabilize 后 200/200 全部成功、23 次超时回退如实呈现。源码直达：[chord.c（代码浏览）](/static/code/#/p2p-labs/ch06-mini-chord/chord.c)、[完整工程](/static/code/#/p2p-labs/ch06-mini-chord/README.md)、[GitHub 源](https://github.com/hlwqds/hl-ljj-quartz/tree/v4/practice/p2p-labs/ch06-mini-chord)。

## 6.4 动态世界：加入、离开与稳定化

静态环只是幻觉，P2P 网络的常态是 churn。Chord 用三个后台协议维持环的正确性，全部是**周期性自愈**而非事件驱动——因为在一个你永远不知道谁刚掉线的网络里，"事件"本身不可观测，只能靠周期体检：

- **stabilize**：节点定期问 successor"你的 predecessor 是谁？"，若答案是别人则修正自己的 successor 指针，并通知 successor"我才是你新的 predecessor"。新节点加入后就是靠这个协议被前后邻居逐渐接纳。
- **notify**：被通知的节点更新自己的 predecessor 指针（身份确认的握手）。
- **fix_fingers**：定期随机挑一个 finger 重查 successor( n+2^(i-1) )，让指距表跟上拓扑变化。
- **后继链（successor list）**：每个节点维护 r 个后继而不只 1 个——宿主节点瞬间死亡时，第二个后继无缝接管它管辖的弧段。没有这层冗余，环上任何一次断链都可能把查找引向黑洞。

新节点 N38 加入的完整流程：找到任一在线节点（bootstrap，ch02 广播发现的互联网版），查 successor(38) 得 N42 → N38 插入环中，接管 (32, 38] 弧段的键（前任 N32 把这段键迁移过来）→ 后台 stabilize/fix_fingers 慢慢把它织进所有邻居的 finger table。**注意"慢慢"**：在稳定化周期之间，finger table 是过时的——Chord 的路由正确性并不依赖 finger table 全对，只要 successor 链是对的，最坏退化为线性查找也能到达。这是分布式设计的成熟品味：**快速路径允许脏，正确性挂在慢速路径上**。

> [!warning] Chord 的工程短板（Kademlia 的入场券）
> Chord 在论文实验里优雅，落地时暴露三个问题：其一，**路由状态与路由跳数的权衡不灵活**（finger table 固定 m 项，维护成本随 ID 空间线性增长，160 位空间就是 160 项指针要 fix）；其二，**拓扑感知缺失**——finger 选的是 ID 上的近，不是网络上的近，一次查找可能绕地球三跳；其三，**对恶性 churn 的稳定化开销大**，环状结构的单点 successor 链是软肋（后续 EpiChord 等用并发查询修补）。下一章的 Kademlia 逐条对症下药。

## 6.5 小结

- `hash mod N` 在节点增减时重映射约 100% 键；一致性哈希环把它压到 **K/N**——键住进顺时针第一个节点，节点增减只动邻弧。
- 虚拟节点修补分布不均，并顺带支持异构与匀速退出；该技术活在 Redis Cluster 槽位与 Dynamo/Cassandra token ring 里。
- Chord 状态极简：successor + 指数间距的 finger table；查找每跳至少把剩余距离减半，N 节点网络 O(log N) 跳——一百万节点约 20 跳。
- 路由正确性挂在 successor 链上而非 finger table 上：快速路径允许脏数据，慢速周期协议（stabilize/notify/fix_fingers）负责自愈，后继链负责宿主死亡时的接管。
- Chord 的三个工程短板——指针维护成本、无拓扑感知、恶性 churn 下的稳定化开销——正是 Kademlia 的优化清单。
