# 无线共存调试实战（一）：同板三射频解剖

> [!info] 无线共存调试实战系列 0. [[radio-coexist|系列索引]]
> 系列开篇（本章为第一章）
> **第一章：同板三射频解剖**（当前章）

## 1.1 三个现场：单协议都好，同板就乱

先看三个现场（**教学复盘案例，取材自常见故障模式综述**——产品与团队均属合成，把多起常见故障折进同一条叙述线，便于提炼方法）。它们的共同背景：WiFi、BLE、Thread 三种 2.4G 射频，或同一颗芯片，或同一块板子。

**现场 A：配 Matter 设备时，WiFi 视频卡顿**。智能家居中枢（多协议 SoC 一块）平时一切正常。家人用手机给新买的 Matter 灯配网（BLE 广播+连接，走手机 App），同一时刻客厅电视的 2.4G WiFi 视频开始卡顿；配网一结束，视频立刻恢复。事后查路由器后台：无掉线记录；重测网速：满速。「偶发、时段相关、自愈」——软件侧排查一轮没有结果。

**现场 B：Matter 网关 OTA 时，BLE 配网超时**。反向场景：网关正在走 WiFi 下载固件（大流量持续数分钟），用户恰好在给新设备做 BLE 配网，App 反复转圈超时；OTA 一下载完，配网一次成功。固件工程师怀疑 BLE 协议栈，抓包看到的全是重传——「协议栈在干活，但干不成」。

**现场 C：路由器开 Thread 后，2.4G 吞吐下滑**。路由器固件升级后启用了 Thread（做 Matter 边缘网关），用户发现 2.4G 无线的吞吐比升级前低了；把 Thread 功能关掉，吞吐回升；5G 无线全程无感。单看 Thread 网络本身：设备都在线，延迟也正常——Thread 侧「没有故障」。

三个现场的共同点：**每个单协议单独看都健康，凑在同一块板子上互相拖累**。用三部曲的取证框架各自排一轮（现象分类、分层下钻）都不会收敛——因为根因不在「某一个协议」里，而在「共享」里。先把三案按共存视角拆开：

| 现场 | 表面症状                   | 单协议视角的解释（都不成立）                 | 共存视角的嫌疑                                    | 初判归层   |
| ---- | -------------------------- | -------------------------------------------- | ------------------------------------------------- | ---------- |
| A    | 配网时段 WiFi 视频卡顿     | 路由器问题——但后台无异常、配网结束自愈       | BLE 配网活动与 WiFi 业务在同一射频/同一频段上撞车 | 频谱或片上 |
| B    | OTA 时段 BLE 配网超时      | BLE 协议栈问题——但重传正常发出，OTA 结束秒过 | WiFi 大流量挤占了 BLE 的连接事件/广播窗口         | 频谱或片上 |
| C    | 开 Thread 后 2.4G 吞吐下滑 | Thread 网络问题——但 Thread 侧一切正常        | Thread 射频活动分走了同芯片/同频段的资源          | 频谱或片上 |

注意「初判归层」一列全写着「频谱或片上」——这正是共存调试的第一课：**先归层，再取证**。三案到底是什么层，后面的章节会用隔离实验和联合观测给出答案；本章先把归层的方法论立起来（1.3），并把「数芯片」这一步做扎实（1.2）。

与三部曲的分工，一张表钉死边界：

| 维度       | [[wifi-hw-debug\|WiFi 硬件调试实战]] / [[ble-debug\|蓝牙调试实战]] / [[thread-debug\|Thread 调试实战]] | 本系列                                       |
| ---------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------- |
| 回答的问题 | 一种射频怎么查（单协议排障）                                                                           | 三种射频挤在一块板子上怎么查（互拖互踩）     |
| 隐含假设   | 射频之间互不相干                                                                                       | 射频之间共享芯片/频段/天线/网络角色          |
| 取证单位   | 单协议的事件时间线                                                                                     | 多协议时间线对齐 + 隔离实验                  |
| 单协议概念 | 各自成体系                                                                                             | 一律回链三部曲，只讲共存增量，发现重复教即删 |

## 1.2 芯片形态学：先数清几颗射频

共存调试的第一步不是抓包，是**数芯片**。板子上到底有几颗射频、它们之间有没有协调线路，决定了共存问题的形态与全套工具选择——这是灵魂拷问 Q1（1.4）的答案，也是本章标题里「解剖」二字的含义。工程上多射频产品归成三类形态：

| 形态              | 典型例子                                                                                                          | 射频间关系                           | 共存靠什么                                            | 调试工具面                                         | 最典型的一个坑                     |
| ----------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------ | ----------------------------------------------------- | -------------------------------------------------- | ---------------------------------- |
| **单 SoC 多协议** | ESP32-C6（WiFi 6 + BLE + 802.15.4）、ESP32-H2（BLE + 802.15.4，无 WiFi）、nRF5340/nRF54L15（BLE + 802.15.4）      | 同一颗收发器按时间片轮流服务多协议   | 片上调度：软件时间片 + 优先级仲裁（厂商口径见 1.2.1） | 协议栈日志 + 厂商共存统计/计数器；抓包只能看到结果 | 共存调度配置没开或用默认优先级     |
| **多芯片组合**    | Linux 网关板载 WiFi + USB 802.15.4 dongle（树莓派 OTBR 组合，见 [[rpi-lab\|树莓派实验室]]）；路由器 + 外接 dongle | 各自独立的射频芯片，芯片间无协调线路 | **没有仲裁**——只剩频谱避让与应用层自律                | 两套独立工具链并行 + 总线级观测（`lsusb`/`dmesg`） | 信道撞车无人调停；两套日志两套时钟 |
| **RF 前端共享**   | 两颗射频芯片经射频开关/双工器共享一根天线（部分网关/模组方案）                                                    | 前端共享，时间上必须互斥             | 硬件开关 + PTA 类仲裁信号分时                         | 双工具链 + 示波器看共存 GPIO/开关控制时序          | 仲裁线时序冲突：两边同时发射       |

三类的共存机制位置完全不同，先看一张剖面图（**格式示意**）：

```text
单 SoC 多协议 : WiFi 栈 / BLE 栈 / 15.4 栈 → 片上调度器 → 一颗收发器 → 天线
                调度器把「时间冲突」挡在前面；抓包只看得到结果，调度内心靠日志与计数
多芯片组合    : WiFi SoC ──（无协调线路）── 802.15.4 dongle → 各自天线
                没有仲裁；只剩频谱避让（第二章）与应用层自律（第五章）
RF 前端共享   : WiFi SoC ──┐
                802.15.4 ──┴→ 射频开关 ←─ 仲裁信号 → 共享一根天线
                时间必须互斥；示波器是第三只眼（第六章对齐法）
────────────────────────────────────────────────────────────────
共性：三种形态的频谱层互扰都存在——差别只在有没有调度器兜底
```

三类的共性也要看清：**不管哪种形态，频谱层的互扰都存在**——只是单 SoC 形态里调度器把「时间冲突」挡在了前面，多芯片形态里连这层保护都没有。下面逐类展开。

### 1.2.1 单 SoC 多协议：一颗芯片里的时间战争

一颗收发器，多个协议栈排队用。谁来排？厂商方案不同，但都是「片上调度器」这一族（机制细节第三章、第四章展开，此处只立概念）：

| 厂商方案                    | 口径出处                                                | 一句话机制                                              |
| --------------------------- | ------------------------------------------------------- | ------------------------------------------------------- |
| Espressif 共存调度          | ESP-IDF 官方文档《Wi-Fi and Bluetooth coexistence》口径 | WiFi 与 BT/BLE 按优先级+时间片共享射频，软件调度为主    |
| Nordic MPSL（多协议服务层） | Nordic 官方文档（nRF Connect SDK）口径                  | 对 BLE 与 802.15.4 的射频占用做时分仲裁，事件级抢占协调 |

工具面重点是：**抓包看到的是结果，调度器的内心要靠日志与计数器**。BLE 突然丢了一个连接事件，空口抓包只显示「没发包」；为什么没发——是调度器把时间让给了 WiFi——只有厂商共存统计和栈日志能回答。所以单 SoC 形态的取证阵型是「空口抓包 ×2（两个协议各一路）+ 协议栈日志 + 厂商共存计数」。

典型坑对照表：

| 坑                    | 现象                                       | 一手验证                                                                       |
| --------------------- | ------------------------------------------ | ------------------------------------------------------------------------------ |
| 共存调度没启用        | 双栈同开就崩/一栈饿死，单栈各自都好        | 核对 SDK 配置项（如 ESP-IDF 的 coexist 配置族，menuconfig 口径以到手版本为准） |
| 优先级用默认值        | 业务场景变了（比如新增 OTA），互拖方向变了 | 查厂商文档优先级语义，对照实际业务列优先级表                                   |
| 把双栈当双射频        | 「我明明关了 WiFi，怎么还乱」              | 数芯片：一颗收发器就只有一个时间轴，不存在真正的并行                           |
| 配网/OTA 时段独占设计 | 两个业务在固件里各排各的时段，撞在高峰     | 固件业务时段表与射频占用记录对时                                               |

### 1.2.2 多芯片组合：没有仲裁的世界

板载 WiFi + USB dongle 是最常见的多芯片组合（OTBR 网关的标准长相）。芯片之间互不相识，没有 REQUEST/GRANT，没有时间片——**唯一的「共存机制」是设计者在频谱层替它们规划好信道（第二章），在应用层替它们排好业务时段（第五章）**。这既是自由也是风险：没有调度器兜底，规划错了就是硬撞。

工具面：三部曲各自的工具链并行开动（WiFi 一路 sniffer、802.15.4 一路 sniffer，第二章给联合观测实操）；外加总线级观测——`lsusb -t` 确认 dongle 挂载与速率、`dmesg -T` 盯 dongle 掉线重连（dongle 被 USB 供电/枚举问题折腾时，症状会伪装成共存问题）。

典型坑对照表：

| 坑                       | 现象                                        | 一手验证                                                   |
| ------------------------ | ------------------------------------------- | ---------------------------------------------------------- |
| 信道撞车                 | Thread 信道正落在 WiFi 主信道上，且两侧都忙 | 查 dataset 的 Channel 字段 + WiFi 侧信道占用（第二章方法） |
| USB 口引入射频噪声       | dongle 灵敏度莫名差，换位置/换口就变        | 换 USB 口（避开 USB3.0 口）、加延长线远离主板对照          |
| 两套日志两套时钟         | 「WiFi 日志说 14:03，Thread 日志说 14:07」  | 双侧 NTP 对时；无外网时人为触发共同事件对齐（第六章）      |
| dongle 供电/枚举问题伪装 | 「共存问题」实为 dongle 掉线重连            | `dmesg -T` 里的 USB 事件时间线与无线症状对时               |

### 1.2.3 RF 前端共享：一根天线两头抢

第三种形态介于两者之间：两颗独立射频芯片，但物理上共享一根天线（经射频开关或双工器）。共享是省成本省空间的手段，代价是**时间上必须互斥**——两颗芯片同时往一根天线上打，前端互相顶牛，灵敏度一起完蛋。谁来保证互斥？硬件仲裁信号：业界通行的 PTA（Packet Traffic Arbitration）家族——REQUEST/GRANT（±PRIORITY）握手线，具体线序与时序随方案而定（厂商文档口径，细节第三章展开）。

工具面因此多一路：**示波器看仲裁线与开关控制时序**——「两边有没有同时发射」「切换窗口够不够」这类问题，抓包和日志都答不了，只有波形能（对齐方法第六章）。布局与隔离度的设计侧问题留给第七章。

典型坑对照表：

| 坑                    | 现象                           | 一手验证                                                                           |
| --------------------- | ------------------------------ | ---------------------------------------------------------------------------------- |
| 仲裁线未接/接反       | 双发互怼：两协议灵敏度同时骤降 | 示波器看 REQUEST/GRANT 波形与发射时刻对齐                                          |
| 开关切换时序窗口不足  | 协议切换瞬间丢包成簇           | 波形上量切换窗口宽度，对照方案文档口径（查不到标待核对）                           |
| 控制线毛刺/长走线耦合 | 偶发、与某些业务相关的怪病     | 波形抓毛刺；布局审查回链 [[wifi-hw-debug-ch08-antenna-structure\|WiFi 调试（八）]] |
| 共享后隔离度不足      | 发射时对端接收阻塞             | 隔离度概念与设计口径见第七章                                                       |

三类形态怎么快速辨认，收成一张判定表：

| 观察到的证据                      | 形态判定      | 立刻该做的事                           |
| --------------------------------- | ------------- | -------------------------------------- |
| 原理图/BOM 里只有一颗多协议芯片   | 单 SoC 多协议 | 研读该芯片的共存文档与 SDK 配置        |
| 板上/箱内有多颗射频芯片且无线直连 | 多芯片组合    | 信道规划 + 业务时段协调 + 双工具链取证 |
| 天线口只有一根，芯片有两颗        | RF 前端共享   | 找到仲裁信号，确认其在工作（示波器）   |

## 1.3 共存三层次：先把问题归对层

[[radio-coexist|系列索引]] 给过三层次的定义表，本章把它升级成**可操作的归层工具**：每层补上「归层判定问句」——拿到一个共存疑案，先逐层问句过一遍，层归错了，后面每一步取证都在白费。

### 1.3.1 三层次的本质、症状与判定问句

| 层次         | 本质                                       | 典型症状                                               | 归层判定问句                                                                                     | 对应章节                                                                                                                    |
| ------------ | ------------------------------------------ | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| **频谱共存** | 空口互扰：同/邻频占用互抢 airtime 与信噪比 | 距离变近、重传升高、特定信道劣化、换信道就好           | 「把嫌疑协议挪到不重叠的信道（或关掉），症状消失吗？两颗互不相干的芯片放同一房间也会发生吗？」   | 第二章                                                                                                                      |
| **片上共存** | 收发器时间被调度互抢                       | 单协议正常、双协议同开就抖；症状随另一协议活动节拍起伏 | 「症状是否与另一协议的活动（配网/OTA/大流量）在时间上强相关？只在同一颗射频/共享前端上发生吗？」 | 第三、四、五章                                                                                                              |
| **网络协作** | 角色分工与数据通路设计不当                 | 配网失败、BR 失联、App 远程失效但本地互通正常          | 「两侧射频都健康吗？是不是流程/角色把健康链路用错了（谁供网、谁配网、配网顺序）？」              | 第五章；[[thread-debug-ch06-border-router\|Thread 调试（六）]]、[[thread-debug-ch10-matter-over-thread\|Thread 调试（十）]] |

三层叠成一张剖面（**格式示意**），取证顺序自下而上：频谱层最便宜（换信道对照实验），片上层次之（暂停另一协议对照），网络协作层最需要流程梳理：

```text
网络协作层 —— 谁供网 / 谁配网 / 谁是 BR（流程把链路用错）
              → 配网失败、BR 失联、App 远程失效但本地互通正常
片上共存层 —— 调度器 / 开关把时间分给谁（资源互抢）
              → 单协议都好、双协议同开就抖、症状随另一协议节拍起伏
频谱共存层 —— 空气里谁占用 / 谁撞谁（信道与 airtime）
              → 重传升高、特定信道劣化、距离变近
归层问句：换信道会好吗？（频谱）→ 暂停另一协议会好吗？（片上）→ 都不会？（网络协作）
```

两条使用须知。其一，**归层不等于终判**：层次之间会连锁——频谱层重传拉高，会反过来加大片上层的时间压力；片上调度失衡，也可能在网络协作层表现为配网超时。归层是给取证定起点，不是给结论盖章。其二，1.1 三个现场的初判都是「频谱或片上」，因为它们的症状同时满足两层的部分特征——这正是下一小节互拖矩阵要解决的模糊性。

### 1.3.2 互拖矩阵：行是被害，列是嫌疑

全系列反复使用的思维工具：拿一张 3×3 表，**行是被害协议（谁在疼），列是嫌疑协议（谁开着）**，逐格填一句话——「它开着的时候，我什么时候会疼」。填表的过程本身就是归层：疼在频谱上的格子写信道，疼在片上的格子写时段，写不出来的格子标「未观测」。

以 1.1 现场 A 的中枢为例（一块 ESP32-C6 级多协议板，跑 WiFi STA + BLE 配网 + Thread 终端，**教学复盘案例口径**），第一张示例矩阵：

| 被害 ↓ · 嫌疑 → | WiFi                                                           | BLE                                                            | Thread                                                       |
| --------------- | -------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------ |
| **WiFi**        | —                                                              | 配网时段广播/连接事件挤占片上调度 → 视频卡顿（现场 A，片上层） | Thread 父子交互低占空，通常不疼；密集 MLE 时段轻微（未观测） |
| **BLE**         | OTA/大流量挤掉连接事件 → 配网超时（现场 B，片上/频谱待隔离）   | —                                                              | 信道重叠时广播包偶丢 → 扫得慢（未观测）                      |
| **Thread**      | 同频大流量 → 重传↑、延迟↑，SED 可能掉线（现场 C 嫌疑，频谱层） | 配网广播撞在 Thread 信道邻格时偶发丢包（未观测）               | —                                                            |

三个使用要点：

| 要点                 | 说明                                                                                                         |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| 先填「未观测」再动手 | 矩阵不是知识竞赛，是**取证计划**——「未观测」的格子就是后面隔离实验与联合观测的工作清单（1.4 路线图的第④⑤步） |
| 每格都要归层         | 格子里写清「疼在什么条件下」并标注归层判断；一张矩阵画完，问题清单自动按层分组                               |
| 随实验更新           | 每完成一组 A/B 对照就回填结论；最终矩阵是结案报告的骨架                                                      |

> [!tip] 矩阵的另一半用法：向非无线同事解释
> 「为什么测 BLE 要先停 OTA」——指着矩阵格子讲，比讲十分钟 PTA 原理有效。它也是跨团队排期谈判的工具：哪些格子的冲突值得排期修，哪些格子的风险可以靠信道规划白嫖掉（第二章），一目了然。

## 1.4 三个灵魂拷问与取证路线图

[[radio-coexist|系列索引]] 里的三个灵魂拷问，是共存问题的一切入口。每个拷问配「怎么答」与「证据从哪来」：

| 拷问                      | 怎么答                                                                                           | 证据来源                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| **Q1 物理上几颗射频？**   | 看原理图/BOM/芯片丝印；软件侧 `lsusb -t`/`lspci` 确认 dongle 与 PCIe 设备；查模组 datasheet 框图 | 归入 1.2 三类形态之一；形态决定后面所有工具选择                                                       |
| **Q2 时间上怎么互相让？** | 先读厂商文档口径（Espressif 共存文档、Nordic MPSL 文档），再实测验证行为                         | 调度窗口/优先级语义（第三、四章）+ 实际行为对齐（第六章三通道法）                                     |
| **Q3 网络上怎么分工？**   | 画数据通路图：谁给谁供网、配网走哪条路、BR 在哪、各协议的角色                                    | 流程图 + 各协议栈日志（[[thread-debug-ch10-matter-over-thread\|Thread 调试（十）]] 的配网分解是样板） |

拷问的顺序有讲究：Q1 是物理事实，五分钟内可钉死，**永远第一个答**；Q2 决定性能互拖的边界，是多数「慢/抖」类案件的战场；Q3 决定故障会不会跨协议传播（配网挂在 BLE 上、业务断在 WiFi 上），是多数「失败」类案件的战场。三个都答了，互拖矩阵的每个格子都有了填法。

把 1.2、1.3 串成一条可执行的取证路线图（**格式示意**）：

```text
① 归层     —— 1.3.1 判定问句逐层过，得「频谱/片上/网络协作」起点
② 数射频   —— Q1：单 SoC / 多芯片 / 前端共享，选定工具阵型（1.2）
③ 画矩阵   —— 行=被害列=嫌疑，逐格写「何时疼」，「未观测」格即工作清单
④ 隔离实验 —— 逐个关/暂停射频与业务：A/B 对照把矩阵格子逐个收敛（单变量纪律！）
⑤ 联合观测 —— 并行空口抓包 + 电流实测 + 各栈日志（第二章给抓包实操，第六章给对齐法）
⑥ 时间线对齐 —— 多路证据同一时间轴，看谁先动的手
⑦ 定责与决策 —— 信道规划（第二章）/调度配置（三、四章）/布局（第七章）落地
```

| 步骤       | 产出                         | 成本   | 一句话纪律                                                                                 |
| ---------- | ---------------------------- | ------ | ------------------------------------------------------------------------------------------ |
| ① 归层     | 层次判断 + 判定依据          | ¥0     | 层错了方向就全错，值得多花十分钟                                                           |
| ② 数射频   | 形态判定                     | ¥0     | 打开原理图之前不要猜                                                                       |
| ③ 画矩阵   | 带归层标注的 3×3 工作清单    | ¥0     | 「未观测」是计划，不是空白                                                                 |
| ④ 隔离实验 | 格子逐个收敛为「实锤/排除」  | ¥0~低  | [[wifi-hw-debug-ch01-debug-methodology-toolbox\|WiFi 调试（一）]] 纪律一：一次只改一个变量 |
| ⑤ 联合观测 | 多通道原始证据               | 百元级 | 观测时段必须覆盖冲突场景（配网/OTA/大流量）                                                |
| ⑥ 对齐     | 同一时间轴的因果链           | ¥0     | 没有对时，多路证据只是多堆噪音                                                             |
| ⑦ 定责决策 | 结论 + 落地措施 + 更新后矩阵 | —      | 结论必须能被④⑤⑥的证据反驳                                                                  |

## 本章小结

- **三个现场一个规律**：单协议各自健康、同板互拖互踩——症状在 A 协议上，根因常在 B 协议的时序里（1.1）。
- **先数芯片再取证**：单 SoC 多协议（片上调度兜底）、多芯片组合（没有仲裁只剩规划）、RF 前端共享（硬件开关分时）三类形态，各有各的工具面与头号坑（1.2 总表与三类判定表）。
- **共存三层次配判定问句**：频谱（换信道会好吗）、片上（暂停另一协议会好吗）、网络协作（流程用错了吗）——归层给取证定起点，层间会连锁，归层不是终判（1.3.1）。
- **互拖矩阵是全系列的通用语**：行=被害、列=嫌疑，逐格写「何时疼」并归层；「未观测」格子就是取证计划（1.3.2）。
- **三个灵魂拷问定顺序**：Q1 数射频（物理事实，先答）→ Q2 时间怎么让（性能互拖）→ Q3 网络怎么分工（故障传播）；配套七步取证路线图（1.4）。
