## 3.1 现场引入：各自都好，同开就翻车

先看三个现场（**教学复盘案例，取材自常见故障模式综述**——团队与产品均属合成，把 WiFi+BLE 同板产品的多起常见故障折进同一条叙述线）。

**现场 A：BLE 遥控失灵**。一台带投屏功能的平板网关外接 BLE 遥控器：WiFi 空闲时按键响应干脆；一旦开启投屏或跑大文件下载，按键延迟肉眼可见地变大、偶发完全失灵，停掉流量立刻恢复。遥控器固件没动过，配对参数反复重配过三遍，无果。

**现场 B：BLE 连接间隔「名不副实」**。传感器板走 BLE 上报：连接时协商的 conn interval 是明确写进合同的（连接参数的账见 [[ble-debug-ch05-connection-parameters|蓝牙调试（五）]]）。但同板 WiFi 跑 iperf 压测时，数据到达节拍忽快忽慢，偶发 supervision timeout 掉线；**单独跑 BLE 一整天不出事**。

**现场 C：WiFi 延迟毛刺**。整机测试视角反过来：`ping` 网关延迟曲线整体平缓，但每隔固定节拍冒出尖刺，吞吐在 BLE 活跃时段整体掉一截。把尖刺时刻与 BLE 业务（连接事件、广播）的调度节拍摆在一起对时——对得上。

三个现场的共同点，用一张表钉住：

| 现场     | 用户可感知症状       | 被害协议 | 嫌疑协议 | 关键反常点                 |
| -------- | -------------------- | -------- | -------- | -------------------------- |
| A 遥控   | 按键延迟/失灵        | BLE      | WiFi     | 症状与 WiFi 流量强相关     |
| B 传感器 | 数据节拍抖、偶发掉线 | BLE      | WiFi     | 协商参数没变，实测节拍变了 |
| C 网关   | 延迟尖刺、吞吐下滑   | WiFi     | BLE      | 尖刺节拍与 BLE 调度对齐    |

反常点指向同一件事：**单协议工作时一切正常，同板同开就互拖**。这正是 [[radio-coexist-ch01-same-board-anatomy|第一章]] 共存三层次里「片上共存」层的定义性症状——归层先归对，方向才不会错。频谱层（空口互扰，见 [[radio-coexist-ch02-24ghz-spectrum-map|第二章]]）的症状是「距离变近、重传升高」，而本章三个现场在**关掉另一方射频发射**后症状立刻消失——锅不在空口环境，在板子内部的射频时间分配。

> [!note] 本章证据口径
> 命令（`iperf3`/`btmon`/`iw`）全部真实可执行，输出格式以工具版本为准；共存机制行为（时间片分配、保护窗口、PTA 时序参数）以 Espressif/Nordic 官方文档为口径并逐处注明，公开文档未给数值的一律标「待核对」；时序图与日志样例均为「格式示意」；不出现任何虚构实测读数，实验给设计与判据。

## 3.2 单 SoC 的共存本质：一套收发器，两个协议栈

先回到硬件事实（芯片形态学的完整分类见 [[radio-coexist-ch01-same-board-anatomy|第一章]]，此处只取与分时相关的增量）。ESP32-C6/H2、nRF5340 这类多协议 SoC，WiFi 和 BLE 共享的是**同一颗半双工收发器**：同一时刻，它只能按一种调制的参数收或发一种分组。两个协议栈（`esp_wifi` 与蓝牙控制器、或 Wi-Fi 驱动与 SoftDevice Controller）在软件里各自独立，往下走到射频这一层，被压进同一条时间轴：

| 共享层次 | 单 SoC 多协议方案                    | 双芯片方案                |
| -------- | ------------------------------------ | ------------------------- |
| 天线     | 共享（或分天线）                     | 通常分天线                |
| 射频前端 | 共享                                 | 各自独立                  |
| 收发器   | **共享（一颗，分时）**               | 各自独立                  |
| 时间分配 | 芯片内部仲裁器（软件共存层，见 3.4） | 芯片间握手（PTA，见 3.3） |
| 调试视角 | 看不到仲裁过程，只能看结果           | 仲裁信号可引到 GPIO 观测  |

所以「WiFi+BLE 共存」的本质不是无线技术问题，是**实时调度问题**：两个都自认为「我很急」的协议栈，轮流使用一颗不能并行的收发器。分时示意图（格式示意）：

```text
（格式示意）单颗射频上的 WiFi/BLE 分时——时间从左到右
radio: |WiFi TX|WiFi RX|—idle—|BLE conn ev|—idle—|WiFi TX|BLE adv|WiFi RX|
WiFi 视角:  |←—————— 大流量窗口（A-MPDU 连发）——————→|
BLE 视角:                    ↑ 连接事件想上线，正撞上 WiFi 的聚合突发
代价一:     BLE 连接事件被推迟 → 数据顺延到下一个事件（事件调度模型见蓝牙调试（九））
代价二:     WiFi 长聚合被打断 → 整块重传 → 有效吞吐进一步下降
```

两类代价在三个现场各有映射：现场 A/B 是 BLE 侧代价（连接事件错位、超时逼近），现场 C 是 WiFi 侧代价（节拍性让出、聚合被打断）。**两边都是受害者，仲裁器两边都不是**——这是共存调试最容易犯的归因错误：盯着被拖慢的一方调参数，调到天荒地老。

天平向任何一端倾斜过度，都有各自的指纹（格式示意，倾斜程度由 preference/保护窗/业务量共同决定）：

```text
（格式示意）倾斜的两端
WiFi 拿满（偏 WiFi 或 BLE 业务突然加重）:
radio: |WiFi|WiFi|WiFi|WiFi|WiFi|WiFi|BLE(挤成一瞬)|WiFi|
BLE 视角: 锚点漂移成常态 → 事件连续顺延 → supervision 倒计时逼近
BLE 拿满（偏 BT）:
radio: |BLE|BLE|—|BLE|BLE|—|WiFi(碎片化)|—|
WiFi 视角: 聚合窗口凑不齐 → 有效速率档位下探 → 吞吐断崖式下滑
```

| 倾斜指纹（观测面）    | 偏 WiFi 的形态                   | 偏 BT 的形态                |
| --------------------- | -------------------------------- | --------------------------- |
| BLE 锚点间隔          | 呈 WiFi 业务周期的倍数关系       | 几乎不动                    |
| WiFi 吞吐曲线         | 平稳（代价转嫁给 BLE）           | 锯齿状、断崖                |
| 双方都疼还是一方疼    | BLE 单方疼                       | WiFi 单方疼                 |
| preference 改动的反应 | 改回 BALANCE 后 BLE 症状立刻缓解 | 改回 BALANCE 后吞吐立刻回升 |

指纹表的价值在排查早期：先看「一方疼还是双方疼」，再决定往哪个旋钮下手——双方都疼且无规律（翻烧饼形态）通常是优先级语义冲突，交给 3.6 速查表最后一行。

BLE 侧还有一条特有约束要记住：conn interval 是协商值，但**连接事件的实际起拍点由控制器调度**。共存挤压不改变协商参数（所以 `bluetoothctl info` 看一切正常），只改变事件的实际落点——「合同没变，执行变了」，这解释了现场 B 的全部反常。

## 3.3 硬件共存接口 PTA：两颗芯片的握手

单 SoC 内部的仲裁你摸不着，双芯片方案（WiFi 模组 + 独立 BT SoC，或 nRF7002 这类 WiFi 伴生芯片与同板 BLE 射频的共址设计）把仲裁搬到了板级走线上——这就是 **PTA（Packet Traffic Arbitration，包流量仲裁）**。行业通用的 3 线接口：

| 信号       | 方向      | 含义                                  | 缺了它会怎样                    |
| ---------- | --------- | ------------------------------------- | ------------------------------- |
| BT_REQ     | BT → WiFi | BT 侧申请空口窗口                     | WiFi 不知道 BT 要用，永不主动让 |
| BT_PRI     | BT → WiFi | 本次申请的优先级（高/低两档）         | WiFi 无法区分语音级与杂务级申请 |
| GRANT      | WiFi → BT | WiFi 授出窗口（BT 独占期间）          | BT 只能盲等，窗口边界不齐       |
| （4 线制） | BT → WiFi | 频点/发送确认等附加信息（各厂商不同） | 优先级判决精度下降（待核对）    |

握手时序（**格式示意**，电平极性与具体时序参数依芯片 datasheet，公开材料未给统一数值——待核对）：

```text
（格式示意）3 线 PTA 典型握手
BT_REQ:  _______/▔▔▔▔▔▔▔\____________________/▔▔▔▔\_______
BT_PRI:  _______/▔▔▔▔▔▔▔\____________________/▔▔▔▔\_______   高=本次业务优先级高
GRANT :  ___________/▔▔▔▔▔▔▔▔▔▔▔\__________/▔▔▔▔▔▔▔\_____
             ↑ 申请先于业务窗口拉起     ↑ BT 得窗使用
规则:    申请提前量内 WiFi 让出 → 授予期间 BT 独占 → 撤申请归还
         低优先级申请可被 WiFi 忽略；高优先级申请强制让出
```

双芯片方案的接线与配置要点：

| 检查项     | 正确姿势                                                                                                                                                                                               | 常见翻法                       |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------ |
| 三线齐全   | REQ/PRI/GRANT 全接                                                                                                                                                                                     | 只接 REQ+GRANT：退化成先到先得 |
| 极性与电平 | 按双方 datasheet，必要时上下拉定缺省态                                                                                                                                                                 | 极性反：永远申请/永远让出      |
| GPIO 映射  | ESP-IDF 侧经 GPIO matrix 映射 coex 引脚（`CONFIG_ESP_COEX_EXTERNAL_COEXIST_ENABLE` 一类配置项，名称随版本，以所用 IDF 版本 menuconfig 为准）；Nordic nRF7002 的 COEX 引脚组以 nRF Connect SDK 文档为准 | 引脚号抄别家文档               |
| 优先级映射 | BT_PRI 的高/低两档对应什么业务要显式设计                                                                                                                                                               | 全部拉高：等于没有优先级       |
| grant 超时 | GRANT 失效时的 BT 侧行为要确认                                                                                                                                                                         | 没配超时：BT 死等 → 链路超时   |

Nordic 口径注明：nRF7002 官方文档提供与共址 BLE 射频的共存接口（COEX 引脚组），引脚功能与时序参数以 nRF Connect SDK 文档为准，具体数值本系列不引（待核对）。Espressif 口径：ESP32 系列对外部共存的配置项与引脚映射见 ESP-IDF 文档，同样以版本为准。

> [!tip] PTA 调试的独特优势
> 双芯片方案仲裁信号是**可见的**：示波器/逻辑分析仪抓 REQ/PRI/GRANT 三线，谁在什么时候申请、谁让谁不让，一眼定案——单 SoC 方案最缺的就是这份「仲裁器行车记录仪」。所以双芯片产品的共存问题，取证第一动作就是上逻辑分析仪，别急着翻软件日志。

三线波形的最小抓取配置：三个数字通道（REQ/PRI/GRANT），触发条件设在 REQ 上升沿，采样窗口覆盖一轮完整业务（至少一次 BT 业务申请全程）。抓到波形后按指纹表判读：

| 波形指纹                       | 判读                                      | 处置方向                 |
| ------------------------------ | ----------------------------------------- | ------------------------ |
| REQ 常高、GRANT 恒低           | WiFi 侧未使能 PTA / GRANT 极性接反        | 查使能与极性             |
| REQ 拉起紧贴业务窗口、无提前量 | 提前量参数过小，WiFi 来不及让出           | 调提前量（依 datasheet） |
| GRANT 有窗但窄于业务实际需要   | 优先级映射低，WiFi 按「可拒绝」处理       | 重排 PRI 映射            |
| GRANT 中途被拉低               | WiFi 侧抢占高优先级业务（可能是正常行为） | 与 WiFi 侧业务表核对     |
| 三线全静默但 BT 明明在丢包     | 业务没走 PTA（固件没配共存模式）          | 查固件共存使能           |

## 3.4 软件共存层：时间片、优先级与保护窗口

### 3.4.1 时间片与优先级：仲裁器怎么想

单 SoC 没有板级握手可抓，仲裁发生在驱动内部的**软件共存层**。以 Espressif 为口径（ESP-IDF 官方文档与 ESP-FAQ 共存章节）：WiFi 与蓝牙共用射频时，由共存（coexist）模块按「**优先级 + 时间片**」仲裁双方请求——每个射频事件带优先级与期望时长，仲裁器在冲突时决定让谁先上；机制概念公开，具体窗口数值未公开（待核对）。蓝牙侧若配了经典蓝牙音频等业务，同样进这套仲裁。Nordic 单芯片 BLE+802.15.4 的对应物是 MPSL 时隙机制（思想同源：请求-授予+优先级，细节在 [[radio-coexist-ch04-multiprotocol-802154|第四章]] 展开，此处不重复）。

ESP-IDF 侧两个直接可用的抓手：

```c
#include "esp_coexist.h"
/* 共存偏好：三选一（API 细节随 IDF 版本，以 esp_coex.h 为准） */
esp_coex_preference_set(ESP_COEX_PREFER_BALANCE); /* 或 ESP_COEX_PREFER_WIFI / ESP_COEX_PREFER_BT */
```

| 偏好值                    | 仲裁倾斜  | 适合场景                        | 症状面                                   |
| ------------------------- | --------- | ------------------------------- | ---------------------------------------- |
| `ESP_COEX_PREFER_BALANCE` | 折中      | 通用默认起点                    | 两边都有抖动，幅度均衡                   |
| `ESP_COEX_PREFER_WIFI`    | WiFi 优先 | 视频流/大吞吐为主，BLE 低频上报 | BLE 节拍抖、偶发超时（现场 B 的形态）    |
| `ESP_COEX_PREFER_BT`      | 蓝牙优先  | 遥控/语音类 BLE 强实时业务      | WiFi 吞吐下滑、毛刺变密（现场 C 的形态） |

配合 Kconfig：`CONFIG_ESP_COEX_SW_COEXIST_ENABLE` 一类开关控制软件共存是否启用（名称与菜单位置随 IDF 版本，以所用版本 menuconfig 为准）。**排查第一步永远是确认它开着**——3.6 速查表第一行就是它。

### 3.4.2 共存保护窗口：三难旋钮

「**共存保护窗口**」（保护带/guard time，各厂商叫法不一，机制为共证）：仲裁器为每个已排定的射频事件预留的缓冲时间。BLE 连接事件前后各留一小段，WiFi 就不会把帧掐在事件门口；WiFi beacon/DTIM 唤醒点同理（DTIM 与 modem sleep 的账见 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]]）。保护窗是个三难旋钮：

| 保护窗取值 | BLE 侧         | WiFi 侧        | 总体                                 |
| ---------- | -------------- | -------------- | ------------------------------------ |
| 偏大       | 连接事件稳定   | 空口时间被切碎 | 吞吐下降、延迟升                     |
| 偏小       | 事件边界被挤压 | 聚合效率高     | BLE 偶发错位                         |
| 适中       | 均可接受       | 均可接受       | 待核对（厂商未公开默认值，实验标定） |

**保护窗对 BLE 连接事件的具体影响**：连接事件的「合同」是 conn interval（协商层），执行层是锚点（anchor point）——每个事件的实际起拍时刻。共存挤压不改合同、只挪锚点：锚点后挪 = 该事件内排的数据全部顺延；连续多个事件被挤 = 有效间隔变成 `k × conn interval`，逼近 supervision timeout 就掉线。所以查现场 B 类问题，**别只看协商参数，要看事件的实际落点**（3.5 的观测方法就是为此设计的）。

共存层能拧的把手汇总（数值口径：厂商未公开默认值的项均标待核对，调法走 3.5 的标定实验）：

| 把手                  | 所在层     | 拧向 BLE 稳          | 拧向 WiFi 快         | 风险                   |
| --------------------- | ---------- | -------------------- | -------------------- | ---------------------- |
| preference 三档       | 软件共存层 | `PREFER_BT`          | `PREFER_WIFI`        | 另一方进入倾斜指纹形态 |
| 共存开关（Kconfig）   | 编译配置   | 必须开启（前提项）   | —                    | 关掉等于裸奔           |
| conn interval/latency | BLE 业务   | 缩短间隔、降 latency | 拉长间隔、升 latency | BLE 实时性换 WiFi 空口 |
| BLE 业务形态          | 应用层     | 保持连接、高频事件   | 改广播、降频         | 交互手感               |
| 保护窗/仲裁参数       | 驱动层     | 偏大                 | 偏小                 | 三难表；无公开默认值   |
| WiFi 聚合/重试参数    | WiFi 驱动  | 收敛突发长度         | 放开聚合             | 吞吐换突发长度         |

## 3.5 验证与取证：怎么确认共存机制在工作

核心思路只有一个：**把「共存开」与「共存关」做成对照实验**，看两组差异是否与仲裁机制的预测一致。先定实验矩阵：

| 组  | WiFi 侧    | BLE 侧           | 机制在工作的预期         |
| --- | ---------- | ---------------- | ------------------------ |
| A   | iperf 压测 | 完全断开         | WiFi 吞吐 = 空板基线     |
| B   | iperf 压测 | 已连接但静默     | 吞吐略降（保护窗开销）   |
| C   | iperf 压测 | 高速 notify 业务 | 吞吐进一步降，BLE 节拍抖 |

WiFi 侧命令（方法体系见 [[wifi-hw-debug-ch06-throughput-debugging|WiFi 调试（六）]]，此处只给三组跑法）：

```bash
iperf3 -c 192.168.1.100 -t 30 -R | tee runA-wifi-idle.log      # A：BLE 断开
iperf3 -c 192.168.1.100 -t 30 -R | tee runB-ble-idle.log       # B：BLE 静默连接
iperf3 -c 192.168.1.100 -t 30 -R | tee runC-ble-busy.log       # C：BLE 高速业务
```

BLE 侧两条取证线。其一，**连接事件落点观测**（空口真话）：BLE 嗅探器 + Wireshark 抓锚点时间戳统计（抓包搭建见 [[ble-debug-ch04-advertising-packets|蓝牙调试（四）]]，事件调度读法见 [[ble-debug-ch09-throughput-latency|蓝牙调试（九）]]，不重抄），对比 WiFi 空闲/压测两轮的锚点间隔分布。其二，**HCI 流旁证**（BlueZ 主机栈工具全景见 [[ble-debug-ch02-host-stack-toolkit|蓝牙调试（二）]]）：

```bash
btmon -w ble-during-wifi.log        # HCI 流存档，与 WiFi 压测时段对时
```

日志对时沿用 [[wifi-hw-debug-ch01-debug-methodology-toolbox|WiFi 调试（一）]] 纪律四：各设备先对钟，或用共同事件对齐（人为触发一次 BLE 断连，三方日志同标记）。WiFi 侧配合链路质量快照：

```bash
iw dev wlan0 link                   # RSSI 与协商速率（STA 视角）
iw dev wlan0 station dump           # 站点级重传统计（AP/网关视角）
cat /proc/net/wireless              # 内核视角，脚本友好
```

判读表——观测到什么，下什么结论：

| 观测                                  | 结论                                  | 动作方向               |
| ------------------------------------- | ------------------------------------- | ---------------------- |
| A/B/C 吞吐单调递减、BLE 仅 C 组节拍抖 | 机制在工作，倾斜度按需求调 preference | 调偏好/业务错峰        |
| A=B=C，BLE 断开与否毫无差别           | 共存未生效或 BLE 根本没占射频         | 查共存开关/接线（3.6） |
| B 组就大幅降吞吐、BLE 静默还抖        | 保护窗/仲裁异常                       | 查固件配置与版本       |
| C 组 BLE 锚点间隔呈规律性倍增         | WiFi 长业务周期性挤压（可错峰）       | 错峰或限速             |

ESP32 侧加一路旁证：串口日志记录 `esp_coex_preference_set` 切换前后的行为差异，preference 改动若对两组数据毫无影响，优先怀疑共存模块未参与（配置没编进去或版本不支持），而不是参数不对。

第三条取证线是**电流曲线**：radio 在「让出」与「占用」之间的切换在电流上留痕（实测方法复用 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]] 与 [[ble-debug-ch10-ble-power-debug|蓝牙调试（十）]] 的采样法，不重抄）。它的共存增量价值：把「BLE 事件被推迟」从日志推断升级为物理事实——被挤压事件在电流上表现为「该出现的尖峰没出现，出现在了更晚的位置」。

实验记录模板（每个共存案子建档，字段不全省略）：

| 字段         | 记什么                                                               |
| ------------ | -------------------------------------------------------------------- |
| 环境快照     | 板型/芯片、固件与驱动版本、preference 与 Kconfig 现值                |
| 拓扑         | 谁连谁、信道、对端设备型号；双芯片方案附 PTA 接线图                  |
| 对时方式     | NTP 还是共同事件；各路日志的时钟偏移记录                             |
| 组别与重复数 | A/B/C 各跑几轮；每轮原始日志文件名（可复现纪律，见 WiFi 调试（一）） |

## 3.6 根因速查表

| 症状形态                    | 根因候选         | 一手证据                                  | 处置                                       |
| --------------------------- | ---------------- | ----------------------------------------- | ------------------------------------------ |
| 双方同开毫无互扰也毫无协同  | 共存未启用       | menuconfig/Kconfig 现场核对；A=B=C 数据   | 打开 `CONFIG_ESP_COEX_SW_COEXIST_*` 一类项 |
| 双芯片方案 BT 永远抢不到窗  | PTA 接线错       | 逻辑分析仪三线波形：REQ 拉起无 GRANT 响应 | 核极性/电平/引脚映射                       |
| BT 抢窗但业务仍被砍         | 优先级配置错     | PRI 恒低或恒高；grant 窗口时长与业务不符  | 按业务重排优先级映射                       |
| WiFi 吞吐长期掉三成以上量级 | 保护窗过大/偏 BT | B 组（静默连接）就显著降吞吐              | 回 BALANCE，重标保护窗（标定实验）         |
| BLE 锚点间隔规律性倍增      | 周期性业务同相   | 锚点直方图双峰；尖刺节拍与 WiFi 业务对齐  | 业务错峰（第五章方法论）                   |
| 双方都抖且无规律            | 优先级来回翻烧饼 | 长时段 btmon+iperf 曲线同颤               | 固定 preference，再逐项加业务              |

## 本章小结

- **本质**：WiFi+BLE 同板共存是调度问题——一颗半双工收发器被两个协议栈分时；症状在被拖的一方，根因在仲裁的时间分配里（3.2）。
- **双芯片走 PTA**：REQ/PRI/GRANT 三线握手，接线极性、优先级映射、grant 超时是三大翻车点；仲裁信号可观测是双芯片方案的取证红利（3.3）。
- **单 SoC 走软件共存层**：Espressif 口径的「优先级+时间片」仲裁、`esp_coex_preference_set` 三档偏好、`CONFIG_ESP_COEX_SW_COEXIST_*` 开关（版本相关，以所用 IDF 为准）；「共存保护窗口」是 BLE 稳定性与 WiFi 吞吐的三难旋钮（3.4）。
- **共存挤压不改协商参数、只挪锚点**：查「conn interval 名不副实」类问题，看事件实际落点，不看合同文本（3.4）。
- **验证靠对照实验**：A/B/C 三组矩阵 + 锚点分布 + btmon/iw 对时，判读表定结论（3.5）；速查表先把六个高频根因排一遍再深挖（3.6）。
