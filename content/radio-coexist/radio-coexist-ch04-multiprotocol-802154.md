## 4.1 现场引入：配网几分钟，掉线一大片

两个现场（**教学复盘案例，取材自常见故障模式综述**——把 BLE+Thread 同板产品的常见故障折成一条叙述线）。

**现场 A：Matter 网关的配网窗口**。一块 Matter 边缘网关：BLE 配网 + Thread 边界路由，同板同 SoC。每逢给新设备配网——BLE 大流量传证书的那几十秒——家里已入网的 Thread 子设备（SED 门磁、温湿度）集中出现数据断流，个别触发 child 重连；配网一结束全部自愈。反复测，次次如此。

**现场 B：广播拉快，SED 变慢**。网关固件迭代后把 BLE 外设广播从低频改成了高频连发（为了配网时好被 App 扫到）。回归测试发现：SED 子节点的上报延迟整体变大，偶发 child 老化告警；把广播改回去，延迟回落。改动前后 Thread 侧任何配置都没动。

两个现场的归层动作与第三章同款——先证明不是频谱层（把 BLE 射频关掉，Thread 症状立刻消失，排除邻居干扰与环境因素），再落「片上共存」层：

| 现场     | 症状                     | 被害协议 | 嫌疑协议 | 与第三章的差异                   |
| -------- | ------------------------ | -------- | -------- | -------------------------------- |
| A 配网窗 | Thread 子设备断流/重连   | 802.15.4 | BLE      | 被害方从 WiFi 换成 Thread        |
| B 广播频 | SED 上报延迟大、偶发老化 | 802.15.4 | BLE      | 嫌疑从「大流量」变「低占空高频」 |

现场 B 特别有教学价值：BLE 广播是**低占空**业务，按频谱层的思路（第二章的占用率视角）它几乎可以忽略——但它照样把 SED 拖慢了。原因藏在被动态：Thread 的 SED 不像 WiFi 可以「等等再说」，它每个采听窗错过就是错过，**一个窗口的缺席以整个周期为代价**。占空比账算不出互拖程度，时序对齐账才算得出——这是本章的核心认知增量。

这类问题最常见的跑偏是被误诊为频谱层（空口干扰），因为症状读起来很像「信号不好」：

| 误诊信号                 | 为什么像频谱层         | 一票否决的鉴别动作             |
| ------------------------ | ---------------------- | ------------------------------ |
| 症状随 BLE 业务出现/消失 | 像某种周期性外来干扰   | 关掉本板 BLE 发射，症状即消失  |
| 换信道似乎缓解           | 更像邻居干扰了         | 换信道只是挪了撞点，撞点跟着走 |
| RSSI 良好但延迟/重传恶化 | 「满格却烂」的经典迷惑 | 频谱层恶化不会与 BLE 节拍同相  |

鉴别原则一句话：**频谱层的锅在空口环境（换环境换信道有效），片上共存的锅在板内调度（关对方射频有效）**——先把这条鉴别做掉，再决定走本章路线还是回 [[radio-coexist-ch02-24ghz-spectrum-map|第二章]]。

> [!note] 本章证据口径
> 命令（OpenThread CLI 等）真实可执行；多协议调度机制（MPSL 时隙/切换策略）以 Nordic nRF Connect SDK 与 Espressif ESP-IDF 官方文档为口径并注明，未公开的时隙数值标「待核对」；时序图为「格式示意」；不虚构实测读数，实验给设计与判据。SED 节拍与 CSL 机制本体回链 [[thread-debug-ch07-sleepy-end-device|Thread 调试（七）]]，本章只讲共存挤压增量。

## 4.2 一颗 radio 上的两个协议：分时调度器

### 4.2.1 共享的物理前提

**能共享的前提**一句话带过：BLE（GFSK，1/2 Mbps）与 802.15.4（O-QPSK，250 kbps）同处 2.4 GHz 窄带、同为短突发分组，收发链路与信道滤波设计高度相似，所以一颗多模 radio 换调制参数即可切换——调制细节回链 [[ble-debug-ch08-ble-rf-phy|蓝牙调试（八）]] 与 [[thread-debug-ch09-802154-rf-phy|Thread 调试（九）]]，不展开。信道间隔的相邻关系（谁压谁的边）回链 [[radio-coexist-ch02-24ghz-spectrum-map|第二章]] 的频谱地图，本章只管时间轴。

### 4.2.2 Nordic MPSL：时隙请求与授予

**谁来分时**，两大阵营的机制概念：

| 阵营      | 调度器                              | 机制要点（厂商文档口径）                                                                                                                                 |
| --------- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Nordic    | MPSL（Multiprotocol Service Layer） | BLE 控制器（SoftDevice Controller）持有 radio；其他协议（如 OpenThread）按时隙申请，MPSL 按「最早/最晚」窗口仲裁，BLE 事件通常优先（时隙参数细节待核对） |
| Espressif | 驱动层切换（ESP32-H2 等）           | BLE 与 802.15.4 共用 radio，由驱动在两者事件间切换；并发能力边界随 IDF 版本演进（待核对）                                                                |

MPSL 的时隙思想画成图（**格式示意**；机制为 Nordic nRF Connect SDK / SoftDevice Controller 文档口径，图中数值不对应任何真实参数）：

```text
（格式示意）MPSL 时隙仲裁——BLE 持有 radio，外部协议按时隙申请
BLE 事件 : |conn ev#1|-----空闲-----|conn ev#2|----------|conn ev#3|
OT 申请  :        ↑申请 100 ms 窗                ↑申请与 conn ev#2 撞车
radio 实际: |conn ev#1|OT TX/RX 窗|conn ev#2|OT 剩余窗续用|conn ev#3|
                            ↑撞车段 OT 让路，窗口剩余部分视剩余时长续用
```

「最早/最晚」窗口语义值得多说一句（概念口径同上）：时隙申请不是「给我从 T 开始的 100 ms」，而是「最早不早于 T、最晚不晚于 T+δ，需要 100 ms」——调度器拿到的是一段**可挪动的弹性**，BLE 事件插进来时可以压缩或推迟 OT 的窗口而不撕毁申请。这正是多协议共享的调度艺术：**不是消灭冲突，是把冲突变成可挪动的延迟**。调试视角的推论：看 MPSL 日志（Nordic 平台的 timeslot 事件追踪，开关与工具以 nRF Connect SDK 文档为准，待核对）时，重点看窗口被「压」到什么程度、被推迟的次数分布——被推迟是设计内行为，被推迟到窗口塞不下才丢业务。

### 4.2.3 与 WiFi+BLE 分时的两点关键差异

| 维度       | WiFi+BLE（第三章）          | BLE+802.15.4（本章）                             |
| ---------- | --------------------------- | ------------------------------------------------ |
| 双方节拍   | WiFi 连续突发，BLE 周期事件 | **双方都是周期事件**（conn interval × CSL/poll） |
| 撞车形态   | 随机挤压为主                | **周期性同相共振**为主（最危险）                 |
| 被害面     | 吞吐/延迟（可感知为「慢」） | 丢窗/老化（可感知为「掉」）                      |
| 调度器归属 | 协议栈内部仲裁（不可见）    | 独立调度层（MPSL 可观测 timeslot 事件）          |

「双方都是周期事件」意味着本章问题的主力形态不是随机挤压，是**同相共振**：两个周期性事件如果频率接近或成整数比关系，会反复在同一时刻撞车，且一旦同相就持续同相——现场 B 的广播频率改动恰好把共振点挪了出来，就是这类形态。

## 4.3 冲突点解剖：连接事件 × CSL 窗 × 接收窗口

把三个请求方的「合同」与「代价」摆在一张表里：

| 请求方                  | 节拍来源      | 错过一次的代价                                                   | 代价的可恢复性       |
| ----------------------- | ------------- | ---------------------------------------------------------------- | -------------------- |
| BLE 连接事件            | conn interval | 事件内数据全部顺延到下一事件                                     | 中（持续错过→超时）  |
| BLE 广播事件            | adv interval  | 该轮广播缺席，App 扫到时间变长                                   | 高（下一轮就回来）   |
| Thread CSL 采听窗       | CSL 周期      | **SED 整个周期盲区**：父节点在该窗投递的数据作废，上行要等下一窗 | 低（周期级代价）     |
| Thread legacy poll      | poll period   | 该轮 data request 缺席，下行缓存延迟                             | 中（同上量级）       |
| 802.15.4 常开 RX（FTD） | 连续监听      | 被挤掉的帧直接丢，依赖 MAC 重传                                  | 中（重传吃空口时间） |

CSL 机制本体（协调采样监听、调度参数怎么算）见 [[thread-debug-ch07-sleepy-end-device|Thread 调试（七）]]；这里只补共存视角的一条：**CSL 窗口是三方里「错过代价/占用时长」比最悬殊的**——它占空可能只有千分位量级，但缺席一次等于让 SED 瞎一个周期。调度器把 CSL 窗口当「不可推迟事件」对待正是为此。

共振撞车的时序（**格式示意**）：

```text
（格式示意）BLE 广播事件与 SED 的 CSL 采听窗同相共振
BLE 广播: |ADV|·····|ADV|·····|ADV|·····|ADV|·····|ADV|
CSL 窗  : ···|CSL|·····|CSL|·····|CSL|·····|CSL|···
                     ↑第 2 次撞车      ↑第 4 次撞车（周期接近 → 撞点缓慢漂移，反复命中）
后果    : 父节点投递窗被 BLE 广播挤占 → SED 该窗白醒 → 上行顺延一个 CSL 周期
```

共振的「疼法」由两个周期的比值决定，画出来一目了然（格式示意）：

```text
（格式示意）周期比值决定撞点的确定性与可复现性
非整数比（adv 100 ms × CSL 周期 320 ms）——撞点漂移:
  |ADV|·····|ADV|·····|ADV|·····|ADV|
  ···|CSL|·····|CSL|·····|CSL|·····|CSL|
  撞点每次挪一点 → 「偶尔疼」，测试难复现，现场偶发难定位
整数比且同相（1:1）——撞点固定:
  |ADV|·····|ADV|·····|ADV|
  |CSL|·····|CSL|·····|CSL|     每轮都撞 → 「稳定地疼」反而好抓
整数比且错相——永不撞:
  |ADV|·····|ADV|·····|ADV|
     |CSL|·····|CSL|·····|CSL|  设计目标：把撞点钉死在空隙里
```

这个视角解释了共存问题的「薛定谔复现」：实验室测不出来的偶发，是撞点在漂移；量产后稳定复现的，是撞点被固定。**4.5 的错峰设计本质上就是第三种形态——把周期关系设计成可控的，而不是祈祷它漂走**。

症状到根因的映射表（现场复盘时从左往右查）：

| 可感知症状               | 调度层解释                                       | 对应排查入口              |
| ------------------------ | ------------------------------------------------ | ------------------------- |
| SED 上报延迟呈周期性恶化 | CSL 窗与 BLE 事件反复同相                        | 4.4 实验矩阵              |
| 配网期间子设备集中断流   | BLE 大流量 + attach 洪峰叠加（第五章风暴的前奏） | 4.4 双通道抓包            |
| child 老化偶发           | 连续多窗缺席逼近 child timeout                   | 计数器趋势（4.4）         |
| BLE 侧自己掉线           | 反向挤压：conn event 连续被挤                    | 锚点分布（第三章方法）    |
| 网关自身 802.15.4 丢帧   | 常开 RX 被逐帧挤压                               | `counters mac` retry 趋势 |

最后一行单独说明：FTD/Router 角色的 802.15.4 是**常开接收**（除非休眠调度介入），它的被挤压形态与 SED 不同——不是「整窗盲掉」而是「逐帧丢失」，MAC 层重传兜底，症状是吞吐与重传率的慢性恶化而非断流。同一个 BLE 嫌疑，压 SED 呈「断」，压 Router 呈「慢」——被压角色不同，症状光谱不同，归因时别拿 SED 的判据去套 Router。

## 4.4 验证与取证：把共振抓出来

### 4.4.1 实验矩阵：广播间隔 × SED 节拍

设计一个两因素对照：BLE 广播间隔取「慢/快」两档，SED 节拍取「poll 模式/CSL 模式」两档，测 SED 上行延迟与 BLE 扫描可见性。观测点直接复用前系列：广播抓包与间隔测量见 [[ble-debug-ch04-advertising-packets|蓝牙调试（四）]]；SED 节拍、父子交互与延迟观测见 [[thread-debug-ch07-sleepy-end-device|Thread 调试（七）]]——这里只列**调参用的 CLI**（OpenThread CLI，单位与取值范围以官方文档为准）：

```bash
pollperiod 3000            # legacy SED 轮询周期（ms）
csl period 320             # CSL 周期（单位/范围以 OpenThread 文档为准）
counters mac               # MAC 计数器：Tx retry/Rx err 趋势；counters mac reset 清零
state                      # 角色确认（child/router），防止拿错节点做实验
```

判据：若「广播快档」下 SED 延迟分布显著右移且 `counters mac` 的 retry 上升、广播慢档回落，则共振挤压成立；若两档毫无差异而延迟照旧，回去查电源与频谱层——**实验的意义不只是抓共振，还包括排除它**。

### 4.4.2 双通道并行抓包：单通道看不见的撞车

单通道的盲区：BLE 嗅探器看不到 802.15.4 在干嘛，反之亦然。共振的「同时性」必须双通道并行取证：

```text
（格式示意）双通道取证与时间对齐
BLE 嗅探器 ──┐
             ├── 同一主机 Wireshark ×2 实例；用共同事件打标对时（人为触发一次 BLE 连接/断开）
802.15.4 ────┘
三射频板型（BLE+Thread+WiFi 同板）再并联 WiFi sniffer（方法见 [[wifi-hw-debug-ch03-ota-sniffing|WiFi 调试（三）]]）
```

抓包环境搭建本体不重抄：BLE 侧见蓝牙调试（四），802.15.4 侧（信道选择、密钥解密、MLE 解读）见 [[thread-debug-ch03-802154-sniffing|Thread 调试（三）]]。两个通道各有一个共存特有的注意点：BLE 嗅探器跟的是广播信道（三选一或轮扫，连接后跳数据信道要看嗅探器能力）；802.15.4 嗅探器**锁死单信道**——先确认本板 Thread 网络的工作信道（`ot-cli` 里 `channel` 一查即得），锁错信道抓一整天都是空的。本章增量只有两条判读规则：

| 双通道证据组合                                    | 结论                         |
| ------------------------------------------------- | ---------------------------- |
| BLE 广播帧的时间戳反复命中 CSL 窗口边界内         | 同相共振实锤                 |
| 802.15.4 侧 MLE 数据帧缺失 + BLE 侧大流量突发对齐 | 挤压型（非共振型），错峰有效 |
| 双通道各自都干净但症状仍在                        | 回归频谱层/电源层排查        |

设备侧旁证组合：`counters mac`（Thread 侧）+ btmon（BLE 侧）+ 电流曲线（方法复用 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]]）三路对时，radio 被挤的时段电流上「该醒没醒」的 SED 与「被推迟」的 BLE 事件会同时现形。MPSL 时隙视角可再观测：Nordic 平台下 MPSL 的 timeslot 事件日志（以 nRF Connect SDK 文档口径为准，具体开关待核对）能直接显示「谁的窗口被挪了」。

实验记录沿用第三章模板（环境/对时/组别/判读四要素），另加本章特有两行：

| 追加字段   | 记什么                                                                      |
| ---------- | --------------------------------------------------------------------------- |
| 周期关系表 | 本板全部周期性业务的周期清单（adv/conn/CSL/poll），标出整数比关系与相位假设 |
| 撞点预测   | 按周期关系推算的预期撞点位置，供双通道抓包定点验证                          |

最后一条纪律：**无差异的实验结果必须留档**。「广播快慢两档毫无差异」这一阴性结果，是把嫌疑从片上共存层排除的关键证据——下一站是频谱层或电源层。案子只许用证据结，不许用「测了好像没问题」结。

## 4.5 设计侧缓解：错峰、分工、优先级

### 4.5.1 错峰：把周期调开

周期性事件相亲和的根因是共振，解法是把周期错开。三条经验规则（均为设计期规划工具，非运行时参数）：

| 规则       | 做法                                       | 防的是什么                             |
| ---------- | ------------------------------------------ | -------------------------------------- |
| 整数倍原则 | CSL 周期取 BLE 广播间隔的整数倍（或反之）  | 撞点漂移（偶尔疼、复现不了、验收无解） |
| 相位错开   | 配网/重连后显式错开两者的相位              | 固定同相（每轮都撞同一点）             |
| 避开危险比 | 避免 1:1、1:2 这类小整数比裸奔（不配相位） | 高频反复命中                           |

三条规则合起来就是 4.3 第三种形态的落地：**整数倍管「撞点可预测」，相位错开管「预测出的撞点不撞」**——只做前者是把灾难定时，只做后者是每次开机重新赌。广播间隔的设计账本（占空比与功耗视角）见 [[ble-debug-ch10-ble-power-debug|蓝牙调试（十）]]；CSL 周期的选择约束见 Thread 调试（七）。本章增量是**把两个账本合起来算**：单看 BLE 广播 5% 占空没问题、单看 CSL 千分位占空没问题，合起来撞窗照样疼。

### 4.5.2 角色分工：让冲突消失而不是解决冲突

| 分工策略          | 适用                                  | 代价                                                                             |
| ----------------- | ------------------------------------- | -------------------------------------------------------------------------------- | ---------- |
| 专板专协议        | 网关的 802.15.4 与 BLE 用独立芯片     | BOM/体积/天线数量上升（布局联动见 [[radio-coexist-ch07-antenna-rf-coexist-design | 第七章]]） |
| BLE 按窗口开关    | 配网/维护窗口才开广播，平时关         | 现场维护流程要配合                                                               |
| 低占空化 BLE 业务 | 广播/连接参数按「最小必要实时性」配置 | 交互手感下降                                                                     |

现场 A 的根治走的就是第二、三条组合：配网窗口外 BLE 完全静默，配网窗口内接受 Thread 子设备的瞬时抖动（并可提前给用户预期——「配网时家里传感器会卡几十秒」不是 bug 是调度事实）。

### 4.5.3 优先级语义：按代价不对称排座次

调度器优先级不该按「哪个协议贵」排，该按「**错过代价的不对称性**」排：CSL 窗错过 = 周期级代价 > BLE 连接事件错过 = 事件级代价 > BLE 广播错过 = 一轮间隔。给不可推迟的事件高优先级，可推迟的让路——MPSL 的默认倾向（BLE 事件优先，文档口径）与这条原则一致，但**应用层仍有把手**：把 BLE 业务往可推迟的形态做（广播而非保持连接、拉长 conn interval），等于主动给 Thread 让出高优先级席位。连接参数的调整空间见 [[ble-debug-ch05-connection-parameters|蓝牙调试（五）]]。

## 本章小结

- **共享前提**：BLE 与 802.15.4 物理层亲缘使多模 radio 可行；调度器（Nordic MPSL 时隙 / Espressif 驱动切换）在两条周期性时间轴之间做仲裁——文档口径已注明，时隙数值待核对（4.2）。
- **主力形态是共振**：双方都是周期事件，撞车不是随机挤压而是同相反复命中；「占空比账算不出互拖，时序对齐账才算得出」（4.3）。
- **CSL 窗口最娇贵**：占用最小、代价最大（周期级盲区），按代价不对称性排优先级（4.3、4.5.3）。
- **取证靠双通道**：BLE + 802.15.4 嗅探并行、共同事件对时，单通道永远看不见「同时性」；实验矩阵（广播档位 × SED 节拍）负责抓共振也负责排除共振（4.4）。
- **设计侧三招**：错峰（整数倍/相位/避危险比）、角色分工（专板/窗口化/低占空化）、优先级语义（代价不对称排座次）（4.5）。
