## 5.1 机理开场：峰值同相叠加

「单测都好，一起跑就崩」不是玄学，是算术。每个协议单独验收时都有一份漂亮的占空比账：WiFi 业务 30%、BLE 业务 5%、802.15.4 养护流量 3%——单看任何一个都远不到 100%（以下数字为示意口径，实测以各板为准）。问题在于**占空比是平均值，radio 是瞬时资源**：平均值都低不等于峰值错得开。当几个协议的突发窗口恰好叠进同一段时间轴里，瞬时需求就超过 100%，仲裁器只能让一部分请求排队：

```text
（格式示意）占空比账 vs 峰值叠加账
单协议视角（全部合格）:
  WiFi 业务: 占空 30%（突发成片）   BLE: 占空 5%（分散）   802.15.4: 占空 3%（分散）
同相叠加（瞬时需求 > 100%）:
  radio: |——WiFi 大帧聚合突发——|——WiFi 重传——|——WiFi 突发——|
   BLE:        ↑conn ev 错过    ↑conn ev 顺延   ↑adv 缺席
   Thread:              ↑CSL 窗被挤=SED 盲一个周期
  排队 → 错窗 → 重传 → 更多排队（正反馈，风暴成形）
```

风暴有三个加重项，缺一个都成不了气候：

| 加重项       | 机制                                                | 对应前系列概念                                                           |
| ------------ | --------------------------------------------------- | ------------------------------------------------------------------------ |
| 重传放大     | 错窗→丢包→MAC/应用层重传，新增流量挤占更多窗口      | 重传三角（[[wifi-hw-debug-ch06-throughput-debugging\|WiFi 调试（六）]]） |
| 超时误判     | 应用层把「变慢」判成「失败」，重试/重连再放一股流量 | 掉线分类（蓝牙调试（七）思路）                                           |
| 优先级翻烧饼 | 仲裁优先级来回倾斜，双方都抖且无规律                | 第三章 preference 语义                                                   |

先立一条鉴别纪律，免得风暴被当成干扰白查三天：

> [!warning] 风暴不是干扰：灶的位置不同
> **干扰的灶在环境**：多台设备同时坏、换信道/换位置有效、与自家业务节拍无关。**风暴的灶在设备内部**：只坏叠加窗口（业务时段相关）、关掉某路射频立刻痊愈、换环境无效。三个鉴别动作都是零成本动作——复用第一章的对照实验纪律即可。拿不准时先做「关一路射频」的 A/B，再决定走本章还是回频谱层。

设计期还有一招「把风暴算出来」：给整板做一张**叠加预算表**，把每路周期性/突发性业务的时长、周期、可推迟性、错过代价列出来，人工推演最坏同相窗口——很多风暴在评审会上就能预见，根本不用等量产出事：

| 列        | 填什么                                     | 用途                       |
| --------- | ------------------------------------------ | -------------------------- |
| 业务名    | OTA/配网/上报/视频流/养护流量…             | 盘点谁会抢 radio           |
| 时长×周期 | 单次多久、多久一次（突发类标「事件驱动」） | 算同相概率                 |
| 可推迟性  | 能否限速/挪窗/串行化                       | 缓解手段的抓手             |
| 错过代价  | 丢一轮 vs 断链 vs 超时误判                 | 排优先级座次（第四章原则） |

预算表填完，凡「事件驱动大流量」多于一路的板子，本章就是必读——剩下的就是把哪类风暴对号入座。

本章把三类高频风暴按固定四件套拆解——**症状 → 归层 → 取证动作 → 缓解**。归层统一用 [[radio-coexist-ch01-same-board-anatomy|第一章]] 的三层次表；取证工具全部复用前几章已搭好的环境（第三章 A/B/C 矩阵、第四章双通道抓包），不重复搭台。

## 5.2 场景一：配网风暴

### 5.2.1 现场还原

Matter 设备配网是三射频叠加的天然风暴源：BLE 阶段传证书与 CSR（大流量写/notify，流程分解见 [[thread-debug-ch10-matter-over-thread|Thread 调试（十）]]），Thread attach 需要扫描与 MLE 建链（过程见 [[thread-debug-ch04-network-formation-commissioning|Thread 调试（四）]]），入网完成后 App 端立刻触发云端上报（TLS 握手走 WiFi）。时间轴还原（**格式示意**）：

```text
（格式示意）Matter 配网窗口的三射频叠加
BLE    : |广播|连接|MTU/配对|==证书+CSR 大流量==|断开|
Thread : ......|扫描 discover|attach+MLE 建链（重试×N）|入网完成|
WiFi   : ..............|连 AP|TLS 握手|遥测上报（重试）|
叠加区 : BLE 洪峰 × attach 洪峰 × 上报洪峰 —— 每方都慢、都重试、都再挤
```

### 5.2.2 四件套

| 项   | 内容                                                                                                                                          |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 症状 | 三方同时报错：BLE 写超时、Thread attach 反复重试、WiFi 云连接慢——跨协议甩锅的经典现场                                                         |
| 归层 | 片上共存（峰值同相）+ 网络协作（配网流程把三路流量钉在了同一时间窗）                                                                          |
| 取证 | BLE 侧 btmon 看写交互停滞段；Thread 侧 ot-cli 看 attach 重试与 `counters mac`；WiFi 侧 `iw dev wlan0 link` + 上报耗时日志；三路按共同事件对时 |
| 缓解 | 见下表                                                                                                                                        |

缓解策略与适用性：

| 缓解手段 | 做法                                               | 适用性                       |
| -------- | -------------------------------------------------- | ---------------------------- |
| 错峰     | 入网完成后再触发云上报；证书传输与 attach 分段推进 | 流程可改时首选，零硬件代价   |
| 限速     | BLE 阶段控制 notify 速率，给 attach 留窗口余量     | 流程不可改时的次选           |
| 分板     | 配网网关与 Thread BR 用独立芯片                    | 产品形态可接受时的根治       |
| 用户预期 | 「配网时家里传感器会卡几十秒」写进产品文案         | 永远适用（调度事实不是 bug） |

### 5.2.3 取证命令与判据

配网窗口的三路取证命令（各栈工具全景回链对应系列，不重抄）：

```bash
# Thread 侧（ot-cli）：attach 状态与链路计数
state                        # 角色与 attach 状态确认
counters mac                 # Tx retry/Rx err 趋势；counters mac reset 清零
# BLE 侧（BlueZ 主机栈）：配网写交互流
btmon -w commissioning.log
# WiFi 侧：链路快照，配合应用层上报耗时日志（上报耗时无标准命令，打点自留）
iw dev wlan0 link
```

三路按共同事件对时后（对时纪律见 [[wifi-hw-debug-ch01-debug-methodology-toolbox|WiFi 调试（一）]] 纪律四），判据表对号：

| 证据组合                                    | 结论                           |
| ------------------------------------------- | ------------------------------ |
| BLE 写交互停滞段与 Thread attach 重试段重叠 | 洪峰叠加实锤                   |
| 上报握手耗时显著超过空板基线且时段吻合      | WiFi 侧被挤（第三路洪峰在场）  |
| 三路都慢但无一失败                          | 风暴在可容忍区，做错峰即可安心 |
| 只有一路慢、其余两路正常                    | 不是风暴，回单协议路线排查     |

## 5.3 场景二：OTA 风暴

### 5.3.1 现场还原

同板双 OTA：WiFi 侧下载固件包（esp_ota 一类机制）与 BLE 侧 DFU（nrfutil 驱动的分包传输，工具链见 [[ble-debug-ch02-host-stack-toolkit|蓝牙调试（二）]]）同时进行。两路都吃带宽、都写 flash、都有应用层超时——互抢的尽头是**看门狗误判**：

```text
（格式示意）双 OTA 互抢与看门狗误判的正反馈
WiFi OTA : |下载分块|—写 flash—|下载分块|—写 flash—|
BLE DFU  :    |分包传输|等 flash/带宽（被 OTA 占）|分包|...
应用层   :  ↑进度停滞 → 判「下载失败」→ 重试 → 风暴加剧
任务层   :  射频/闪存高优先级任务 + 中断负载 → 应用任务饿死 → task WDT 误报
```

看门狗误判的机理要说清：task WDT（ESP-IDF 任务看门狗一类机制）报的「任务没喂狗」多数时候不是共存直接杀死了任务，而是**高优先级射频/驱动任务与中断负载把低优先级应用任务挤出了调度**——共存只是提高了任务负载密度。取证第一问：超时的是哪一层？应用层超时（业务判失败）还是任务层饿死（WDT 复位）？两层处置完全不同。

「限速+断点续传」值得展开一句，因为它是双 OTA 场景里性价比最高的缓解：限速把「两路洪峰」降级成「一路洪峰+一路细流」，radio 的瞬时超载直接消失；断点续传把「失败重下」从风暴放大器变成无害等待——重下的成本从「重新抢带宽」降到「从断点继续」，正反馈链在第二环就被剪断。实现上并无玄学：下载侧分块拉取+本地进度表，DFU 侧本来就是分包协议（分包号即天然断点），要补的只是「失败后从断点续」而不是「从头再来」的产品逻辑。

### 5.3.2 四件套

| 项   | 内容                                                                                                            |
| ---- | --------------------------------------------------------------------------------------------------------------- |
| 症状 | 双 OTA 都慢且都「间歇性失败」；日志里进度条走停相间；偶发 WDT 复位把现场直接炸掉                                |
| 归层 | 片上共存（带宽互抢）+ 应用层容错设计（超时阈值没有按共存降速的真实口径设置）                                    |
| 取证 | 双侧进度日志对时（OTA 分块号 vs DFU 分包号）；WiFi 侧 iperf 基线对比（第三章 A/B/C 法）；WDT 日志定位饿死任务名 |
| 缓解 | 见下表                                                                                                          |

| 缓解手段       | 做法                                               | 针对                         |
| -------------- | -------------------------------------------------- | ---------------------------- |
| 串行化         | 先 WiFi OTA 后 BLE DFU（或反之），调度上互斥       | 根治互抢                     |
| 限速+断点续传  | 下载限速并支持断点，把「失败重下」变「慢慢下完」   | 超时误判                     |
| 超时与退避改配 | 应用层超时按共存工况放大，重试加指数退避           | 正反馈放大                   |
| 看门狗预算     | 高负载窗口临时放宽 WDT 阈值/挪喂狗到高优先级上下文 | WDT 误判（误报不是真饿死时） |

### 5.3.3 两层超时的鉴别：先分清「谁在喊疼」

双 OTA 现场的超时有完全不同的两层，处置互斥，喊错就开错药：

| 维度     | 应用层超时（业务判失败）               | 任务层饿死（WDT 报警/复位）                                                                         |
| -------- | -------------------------------------- | --------------------------------------------------------------------------------------------------- |
| 现象     | OTA/DFU 进度判「失败」，触发重试       | 设备复位或 panic；进程被杀                                                                          |
| 日志指纹 | 自定义业务日志（分块号停滞→失败→重试） | task WDT panic + 任务名（ESP-IDF 串口输出）；Linux 网关 `journalctl -k \| grep -iE "wdt\|watchdog"` |
| 因果位置 | 风暴的直接结果（慢→误判）              | 负载密度的次生灾害（饿死→报警）                                                                     |
| 正确处置 | 超时放大/退避/限速/串行化              | 喂狗路径与任务优先级整改                                                                            |
| 错误处置 | 无脑缩超时（越缩越误判）               | 直接关看门狗（把报警器拆了当修好）                                                                  |

一条实操经验：**先看复位/报警发生在哪层，再看要不要动超时**——两层问题同时在场时（常见），先止血任务层（保证活着），再治风暴（保证不慢），顺序反了会陷入「复位毁现场、现场毁了复不了盘」的死循环。

## 5.4 场景三：持续流量风暴

### 5.4.1 现场还原

视频流（WiFi 高持续占空，modem sleep 名存实亡，DTIM 账见 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]]）与 Thread 网络养护（MLE 链路统计、keepalive、子节点管理，见 [[thread-debug-ch05-routing-topology|Thread 调试（五）]]）长期共存。这不是几分钟的洪峰，是**小时级的慢性互拖**：

```text
（格式示意）长期互拖的两条曲线
WiFi  : |====视频流持续占用====|====|====|====|====|   （长期高位，让出窗口固定化）
Thread: 养护帧被挤 → 邻居质量衰减 → 重试变多 → 养护流量上升 → 被挤更狠
症状漂移: 第一天只是延迟大 → 一周后 child 频繁老化 → 月度复盘发现「Thread 不如从前稳」
```

### 5.4.2 四件套

| 项   | 内容                                                                                                                                                   |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 症状 | Thread 子设备慢性丢包、延迟基线整体抬升；WiFi 延迟毛刺长期化；单看任何一天的日志都「不算严重」                                                         |
| 归层 | 片上共存长期倾斜（preference 固定偏 WiFi）+ 信道规划缺位（养护流量挤在 WiFi 邻道重传带里，见 [[radio-coexist-ch02-24ghz-spectrum-map\|第二章]]）       |
| 取证 | 计数器长期趋势（`counters mac` 日导出、`iw` 统计）；双通道抓包做「时段采样对比」而非盯瞬时；电流曲线佐证让出节拍                                       |
| 缓解 | preference 回 BALANCE 并验证（第三章方法）；Thread 信道与 WiFi 错开（信道策略见 [[thread-debug-ch09-802154-rf-phy\|Thread 调试（九）]]）；重度场景分板 |

慢性风暴的取证心法与急性不同：**不要找「那一刻发生了什么」，要找「趋势何时拐头」**——计数器周报对比、延迟基线周对比。瞬时抓包在慢性风暴里几乎必然「看起来正常」，因为风暴散布在每一天里。

### 5.4.3 取证节奏：把「慢性」当疾病监测做

| 节奏 | 动作                                               | 看什么                           |
| ---- | -------------------------------------------------- | -------------------------------- |
| 日   | `counters mac` 抽样 + 上报延迟抽样（自动留档）     | retry 与延迟的单日突变           |
| 周   | 延迟基线周对比（本周分布 vs 上周分布）             | **拐头点**——风暴确诊的核心证据   |
| 月   | 双通道抓包采样 + 电流采样（复用第三章/第六章方法） | 结构性恶化（窗口被挤的固定形态） |

拐头点还有一个隐藏价值：**它通常与某次变更对齐**——固件发布、新业务上线、preference 改动。5.5 的案例正是靠「拐头与 OTA 版本发布同周」这条线索破的案。变更台账与性能基线放在一起看，是慢性风暴最便宜的破案手段。

## 5.5 教学案例：网关 OTA 期间 BLE 配网超时率飙升

**教学复盘案例，取材自常见故障模式综述**——把三类团队在多射频网关产品上高频踩中的坑折成一条时间线，人物与产品均属合成。

**背景**：某多协议网关（WiFi+BLE+Thread 同板）量产三个月，云端报表显示近一周 BLE 配网失败率从个位数百分比量级显著抬升；同期无固件发布，无线环境无大改。BLE 团队与 WiFi 团队各自排查一周无果。

| 阶段 | 动作                                                                                              | 结论/证据                                |
| ---- | ------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| D0   | 云端报表告警；两团队各查各的：BLE 查配对流程，WiFi 查关联质量                                     | 双方各自「单协议测试全过」，僵局         |
| D1   | 复用第三章 A/B/C 思路做共存对照：仅当 OTA 推送窗口与用户配网时段重叠时失败率跳升                  | **时间相关性浮出**：锅在叠加，不在单协议 |
| D2   | 对时取证：OTA 分块日志 × btmon 配网写交互 × `counters mac`；发现 OTA 期间共存偏好为 `PREFER_WIFI` | BLE 连接事件被系统性挤压，配对写超时     |
| D3   | 复盘配置：OTA 版本发布时顺手把 preference 从 BALANCE 改成 WIFI（为下载速度），未评估 BLE 配网业务 | **根因锁定**：配置变更 × 业务叠加        |
| 处置 | OTA 窗口与配网错峰 + preference 回 BALANCE + 配对写超时按共存工况放大                             | 失败率回落；加监控指标后无复发           |

复盘教训表：

| 教训                 | 具体化                                                         |
| -------------------- | -------------------------------------------------------------- |
| 监控缺共存指标       | 报表只有单协议成功率，无「叠加时段」维度——风暴在报表上是隐形的 |
| 配置变更无共存评审   | 改 preference 前问一句：此刻板子上还跑着谁、谁的实时性更娇贵   |
| OTA 无窗口/限速      | 大流量业务必须有节流阀与时间窗，见 5.3 缓解表                  |
| 阈值没按共存工况标定 | 所有应用层超时都要有「共存工况」一档，不能只按空板口径设定     |

这个案例的用法不是「看故事」，是**迁移**：把它套到自家产品上走三步——①我家的 OTA/配网/上报有没有时间上的重叠可能？②preference/优先级这类配置最近一次变更是谁、为什么？③监控里能不能按叠加时段切出失败率？三问里只要有一问答不上来，5.6 的清单就先过一遍再上线。

## 5.6 收尾：风暴预防设计清单

设计评审时逐行过（可并入 [[radio-coexist-ch08-casebook-checklist|第八章]] 的全系列清单）：

| #   | 检查项                   | 合格线                                                |
| --- | ------------------------ | ----------------------------------------------------- |
| 1   | 大流量业务有节流阀       | OTA/上报/流媒体均限速且可配置                         |
| 2   | 大流量业务有时间窗       | OTA 错开配网/业务高峰；窗口可运维调整                 |
| 3   | 共存偏好有默认值且有评审 | 默认 BALANCE；改动走共存评审                          |
| 4   | 应用层超时含共存工况档   | 每个超时值都能回答「空板口径还是共存口径」            |
| 5   | 重试有退避               | 指数退避 + 抖动，禁止固定间隔硬重试                   |
| 6   | 周期性业务错峰规划       | 广播/CSL/上报周期做过整数倍与相位检查（第四章规则）   |
| 7   | 监控有叠加维度           | 报表能按「多业务并发时段」切分失败率                  |
| 8   | 看门狗预算分级           | 高负载窗口的 WDT 阈值与喂狗路径有预案                 |
| 9   | 分板决策有依据           | 单板 vs 专板的取舍记录过量化理由（BOM/体积/故障隔离） |
| 10  | 配网等关键流程有预期管理 | 用户文档写明配网窗口内其他设备可能瞬时卡顿            |

清单的用法与三条纪律配套：**每行都要能指出证据**（设计文档、实验数据或监控截图，三者其一）；**证据带日期**（半年前的基线不算数，业务变了基线就变）；**过清单的人不当运动员**（做业务的自己给自己打勾，等于没查——这也是 5.5 案例里 preference 变更无人评审的教训）。清单不是一次性的，每次新增大流量业务或改共存配置都重新过一遍。

## 本章小结

- **风暴=峰值同相叠加**：占空比账算不出互拖，瞬时叠加账才算得出；重传放大、超时误判、优先级翻烧饼是三个加重项（5.1）。
- **配网风暴**：三路洪峰被流程钉在同一窗口；缓解首选流程错峰，写明用户预期（5.2）。
- **OTA 风暴**：互抢加超时误判构成正反馈，WDT 报警先分「真饿死还是误报」；串行化+限速+退避是标准组合（5.3）。
- **持续流量风暴**：慢性互拖取证靠趋势拐头不靠瞬时抓包；信道规划与 preference 回调是主药（5.4）。
- **复盘案例**：配置变更 × 业务叠加是最高频根因组合；监控必须带叠加维度（5.5）。
- **预防清单十条**：设计评审逐行过（5.6）。

三张风暴现场图都指向同一个取证短板：**时间轴对不齐，风暴就破不了案**。怎么把电流、空口、日志三路证据拉到同一条时间轴上，怎么设计逐个关射频的 A/B 隔离实验、给共存性能定量化判据——下一章把全系列的取证方法收拢成体系：见 [[radio-coexist-ch06-coexist-forensics|第六章：共存取证方法与工具]]。
