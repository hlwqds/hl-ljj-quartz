## 6.1 共存取证与单协议取证差在哪

第二、三、四、五章把共存的机制讲完了：频谱层谁占谁的时间（第二章）、片上射频怎么互相让（第三、四章）、什么场景会让「让路」机制过载（第五章）。本章解决下一层问题：**机制上知道会互拖之后，怎么在证据层证明它**——把「我觉得是共存问题」变成一条可交付的证据链。

先承认一件事：三个前系列教你的一切取证动作，在共存现场都**依然有效但不够用**。单协议取证有一条隐含假设——被测设备上只有一颗射频在工作，所有观测到的异常默认都归它。这个假设一旦不成立，同样的动作会得出同样的错误结论。两个视野的差别摊开成表：

| 维度     | 单协议取证                              | 共存取证                                                                 |
| -------- | --------------------------------------- | ------------------------------------------------------------------------ |
| 证据面   | 一条空口信道 + 站端日志，一个视角看到底 | 每个协议一条空口信道，外加电流与多栈日志，多视角拼图                     |
| 假设空间 | 根因在本协议的栈/射频/环境里            | 根因可能在**任何一颗射频的时序里**，包括「受害者自己没病、是别人踩了它」 |
| 时间基准 | 一套日志一个时钟                        | 三套栈三个时钟加两台抓包机，时钟偏移本身就是第一号陷阱                   |
| 对照变量 | 信号、信道、配置                        | **每颗射频的开关与负载**都是变量，且互相耦合                             |
| 误判模式 | 把环境干扰误判为固件问题                | 症状在 A、根因在 B——在 A 的栈里反复试错，方向从第一步就错了              |

「症状在 A、根因在 B」是共存取证的第一定律，它有几种固定形态，提前认识可以少走很多弯路：

| 形态           | 表现                                                       | 单协议视野下的误判                             | 正确动作                                                                           |
| -------------- | ---------------------------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------- |
| 频谱被占       | Thread/BLE 丢包升高，但本协议栈一切正常                    | 怀疑本协议射频灵敏度、怀疑环境、反复调重传参数 | 看邻居信道占用（第二章地图 + [[ch14-interference-coexistence\|射频入门（十四）]]） |
| 片上被抢       | 本协议单测全好，同开才坏；坏的时刻与另一协议的流量峰值对齐 | 怀疑本协议调度参数、固件 bug，逐个配置试错     | 三通道对齐，看时间相关性（6.2）                                                    |
| 网络跨协议传播 | A 协议负责供网/供时，B 协议依赖它，A 抖 B 跟着抖           | 在 B 的协议栈里找根因，越查越深                | 先画角色分工图（第一章的 Q3），再归层                                              |

```text
单协议视野的误判闭环（不先归层的代价）：
Thread 掉线 → 查 Thread 栈 → 邻居表/父子关系正常 → 调 SED 参数 → 无效
            → 换父节点 → 无效 → 刷固件 → 无效 → 「玄学」结案
                    ↑ 实际上每一轮 Thread 侧取证都是「正常」，
                      正常本身就是线索：受害者没病，去找施害者
```

值得强调的是右下角那半句：**受害者侧取证全部正常，本身就是指向施害者的证据**。共存取证与单协议取证不是替换关系——前系列的分层取证（[[wifi-hw-debug-ch01-debug-methodology-toolbox|WiFi 调试（一）]] 的 L1-L4）依然是每条协议内部下钻的骨架，共存层做的是把多套骨架**对齐到一个时间轴上**。

> [!note] 本章证据口径
> 本章命令均为真实可执行命令（`tcpdump`/`iw`/`btmon`/`journalctl`/`iperf3`/ot-cli，参数写明，输出格式以各工具官方文档为准）；电流实测方法复用 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]] 已注明的口径；涉及厂商共存机制行为（PTA/分时窗口）以 Espressif、Nordic 官方文档口径为准（第三章已梳理，本章不重复）；6.5 案例为教学复盘案例，取材自常见故障模式综述；本章不出现虚构实测读数，经验判据标「经验口径/待核对」。

## 6.2 三通道对齐法：电流 + 空口 + 日志

这是全系列的核心方法论。互拖的本质是**时间资源的冲突**，所以取证的核心动作是**把三路独立证据放到同一条时间轴上**，看坏事件与谁的时间行为对齐：

| 通道     | 看什么                                                        | 主力工具                                                       | 证据形态                | 盲区                                     | 方法出处                                                                                                             |
| -------- | ------------------------------------------------------------- | -------------------------------------------------------------- | ----------------------- | ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 电流通道 | 射频收发的电流台阶：谁在发、发多久、是否此起彼伏              | 功耗分析仪（PPK2/Joulescope 一类）或采样电阻 + 示波器/记录仪   | 电流波形 + 时间戳       | 分不清电流属于哪颗射频（靠对齐来归属）   | [[wifi-hw-debug-ch10-power-consumption\|WiFi 调试（十）]]                                                            |
| 空口通道 | 每个协议的空口真相：谁在占用、重传、丢帧、beacon/事件是否缺失 | WiFi sniffer + 802.15.4 sniffer 并行（BLE 嗅探按需第三路）     | 帧级 pcap（各协议一份） | 单 sniffer 单信道；抓包点视角 ≠ 设备视角 | [[wifi-hw-debug-ch03-ota-sniffing\|WiFi 调试（三）]]、[[thread-debug-ch03-802154-sniffing\|Thread 调试（三）]]       |
| 日志通道 | 三套协议栈的自述：事件、状态机、错误码、计数器                | `esp_wifi` 事件流、`btmon`/HCI 日志、ot-cli 与 otbr-agent 日志 | 三份带时间戳的日志      | 各栈只报告自己知道的；三套时钟各自为政   | [[ble-debug-ch02-host-stack-toolkit\|蓝牙调试（二）]]、[[thread-debug-ch02-openthread-toolchain\|Thread 调试（二）]] |

```text
三通道全景（同板三射频的一路并发取证）：
电流仪 ──────── 整机电流波形（数字通道同时录 GPIO 打点）
   │
   ├─ WiFi sniffer ─── 停在 WiFi 工作信道 ── wifi.pcap
   ├─ 15.4 sniffer ─── 停在 Thread 信道 ──── thread.pcap
   ├─ (BLE sniffer ─── 按需第三路 ────────── ble.pcap)
   │
   └─ 三栈日志：esp_wifi 事件 │ btmon -t │ ot-cli / otbr-agent
                        ↓ 全部归并到统一时间轴 ↓
        坏事件时刻 ←→ 谁的电流台阶 / 谁的空口突发 / 谁的日志状态变化
```

### 6.2.1 电流通道：共存的叠加波形怎么读

单协议功耗取证的方法、装备、口径全部照搬 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]]——平均电流、活动窗口、采样率选择都在那一章。共存增量只有一个：同板多射频的电流是**叠加波形**，读法从「找自己协议的活动」变成「分辨活动属于谁、以及多颗射频的时间关系」：

| 电流形态                 | 单协议读法         | 共存读法                                                                       |
| ------------------------ | ------------------ | ------------------------------------------------------------------------------ |
| 独立的发射台阶           | 本协议 TX 活动     | 记录每个台阶的起止时刻，事后与空口 pcap 对齐归属——**电流只出时间，归属靠对齐** |
| 两个台阶严丝合缝地错开   | （罕见，视为异常） | 共存仲裁在工作的签名：射频被时间互斥地调度（PTA/分时，口径见第三章）           |
| 台阶重叠、幅度比单射频高 | （不可能出现）     | 多芯片方案各自独立发波，互不知晓——片上共存缺位的直接证据                       |
| 长平台段（持续发射）     | 大流量传输         | 嫌疑负载：哪颗射频在长平台？它对应什么业务？——6.5 案例的关键证据               |
| 掉线时刻附近无任何活动   | 本协议静默         | 受害者「想发发不出」或父端无响应——结合空口通道分辨                             |

实操要点两条。其一，**打点**：在固件里留一个 GPIO 翻转位，在关键事件（配网开始、OTA 开始、每秒心跳）翻转一次——功耗分析仪的数字输入通道（PPK2 一类设备具备）能把它录进电流文件，日志里同时打印一行带毫秒时间戳的标记。这一个动作把电流文件和日志文件缝在一条轴上，是三源合并最便宜的手段。其二，**采样率与窗口**：共存事件的窗口常在秒级（一次配网、一次 OTA 分块），比单协议功耗账的窗口大，先用低采样率长窗口圈出事件区间，再对嫌疑区间高采样细看。

### 6.2.2 空口通道：双 sniffer 并行

单协议抓包方法分别来自 [[wifi-hw-debug-ch03-ota-sniffing|WiFi 调试（三）]] 与 [[thread-debug-ch03-802154-sniffing|Thread 调试（三）]]，共存增量是**并行**：WiFi sniffer 守在 WiFi 工作信道，802.15.4 sniffer 守在 Thread 信道，两路同时开录——互拖的证据往往藏在「两份 pcap 的同一时刻」里。BLE 是否需要第三路看场景：配网类问题必开（广播/连接都在 BLE 侧），纯 WiFi+Thread 互拖可不开。

```bash
# WiFi 路：监听网卡守在目标信道（网卡选购与验证见 WiFi 调试（三））
iw dev wlan0 interface add mon0 type monitor && ip link set mon0 up
iw dev mon0 set freq 2437                       # 例：6 号信道
tcpdump -i mon0 -y IEEE802_11_RADIO -w wifi.pcap

# 802.15.4 路：刷好 sniffer 固件的板子守在 Thread 信道（配置见 Thread 调试（三））
#   信道设置在 sniffer 固件/Wireshark 配置中指定，例：Thread channel 25（2475 MHz）
# Wireshark 侧：两份 pcap 分开录、分开存，文件名带信道与起止时间
#   Thread 流量解密需网络密钥，配置方法见 Thread 调试（三）
```

并行抓包三条纪律：**两台抓包机先对时**（同一 NTP 源，见 6.2.4；无外网用共同事件对齐）；**录制窗口覆盖完整事件区间**（配网从按下按钮到成功、OTA 从通知到完成），半截 pcap 定不了因果；**各自加注环境**（信道、位置、天线），两份 pcap 的元数据混在一起就废了。

### 6.2.3 日志通道：三栈日志与对时

| 栈     | 日志来源                               | 打开方式（真实命令）                                                                                | 常看内容                              |
| ------ | -------------------------------------- | --------------------------------------------------------------------------------------------------- | ------------------------------------- |
| WiFi   | `esp_wifi` 事件流 / Linux 无线日志     | `idf.py monitor`（ESP32 侧）；`dmesg -T -w`、`journalctl -u NetworkManager`（Linux 侧）             | 断连事件、扫描/关联状态、RSSI 上报    |
| BLE    | HCI 层抓包（控制器与主机之间全部流量） | `btmon -t`（-t 给每条记录加时间戳）                                                                 | 连接建立/断开原因、广播参数、HCI 错误 |
| Thread | ot-cli 状态 / OTBR 服务日志            | ot-cli 的 `state`/`router table`/`child table`；`journalctl -u otbr-agent --since "30 minutes ago"` | attach/分离、邻居变化、MLE 事件       |

日志通道的头号工程是**对时**。三套栈各有一个时钟，两台抓包机还有两个，五个时钟不同源，时间轴合并就是空谈。按成本从低到高：

```bash
# 有外网：全部设备指向同一 NTP 源，然后核对偏移
timedatectl status          # 每台设备/主机各执行一次，记录 NTP 同步状态
chronyc tracking            # 装了 chrony 的设备，看与源的偏差
# 无外网（隔离实验台）：打点对齐——
#   1) 所有日志进程启动前先执行：date +%s.%N   # 记录各自时钟的绝对读数
#   2) 人工触发一次全系统可观测的共同事件（GPIO 打点 + 各栈日志打印 MARKER 行）
#   3) 以该共同事件为原点回推各时钟偏移
```

### 6.2.4 三源时间轴合并的实操步骤

1. **开工前建记录卡**：问题一句话、涉及射频、当前配置（信道/参数/固件版本）——沿用第一章纪律五的模板。
2. **冻结环境**：信道、天线、位置、对端、负载源全部固定并记录；这一步没做，后面所有相关性都不可信。
3. **对时**：按 6.2.3 把五个时钟对到一条轴上，记录各源偏移。
4. **打点布置**：GPIO 打点位 + 各栈 MARKER 日志行 + 负载源的起停日志（iperf3/BLE 广播/OTA 任务的开始结束各打一行）。
5. **单开基线**：各协议单独跑一轮标准负载（下一节定负载），录下电流、pcap、日志——**没有单开基线，同开的证据无从比对**。
6. **同开复现**：叠加负载复现问题，三通道同步录制，反复录到至少三段完整的坏事件窗口。
7. **合并归一**：把坏事件时刻作为锚点，回看锚点前后各一秒内三通道各自有什么——对齐工作在 Wireshark（pcap 时间轴）+ 电流文件标记 + 日志时间戳三处进行，合并成一张表。

打点对齐的常用技巧汇总：

| 技巧               | 做法                                             | 适用场景               | 成本 |
| ------------------ | ------------------------------------------------ | ---------------------- | ---- |
| GPIO 数字打点      | 固件在关键事件翻转 GPIO，功耗仪数字通道录入      | 电流文件与日志缝合     | 低   |
| 共同事件原点       | 人工触发一次全系统可观测事件，各源以此为时间原点 | 无 NTP 的隔离实验台    | 低   |
| 负载起停打日志     | iperf3/BLE 广播/OTA 任务起停各打印一行           | 把负载变成时间轴上的块 | 极低 |
| Wireshark IO Graph | 对 pcap 按秒聚合流量曲线，肉眼找突发窗口         | 两路 pcap 快速对齐     | 极低 |
| 心跳周期校准       | 用已知周期（如 1 s 心跳）核对各时钟速率偏差      | 长时间录制防时钟漂移   | 低   |

> [!tip] 三通道的分工口诀
> 电流出**时间**（谁在什么时候活动）、空口出**因果**（空口上到底发生了什么帧）、日志出**语义**（协议栈怎么解释这件事）。只有一条通道时最多形成嫌疑，三条对齐才算定案——6.5 的案例会完整走一遍。

## 6.3 A/B 隔离实验设计：逐个关射频

三通道对齐回答「坏事件与谁相关」，相关性还不是因果。把因果钉死的是矩阵实验：**每颗射频都是一个可开关的变量，逐个组合，看性能跟谁走**。

### 6.3.1 开关矩阵实验

三射频（WiFi/BLE/Thread）× 两状态 = 8 组合。每行跑同一套标准负载、记同一组指标：

| 组  | WiFi | BLE | Thread | 想回答的问题                                    |
| --- | ---- | --- | ------ | ----------------------------------------------- |
| 1   | 关   | 关  | 关     | （无意义，空跑校准记录流程）                    |
| 2   | 开   | 关  | 关     | WiFi 单开基线                                   |
| 3   | 关   | 开  | 关     | BLE 单开基线                                    |
| 4   | 关   | 关  | 开     | Thread 单开基线                                 |
| 5   | 开   | 开  | 关     | WiFi↔BLE 互拖？（片上共存，第三章机制）         |
| 6   | 开   | 关  | 开     | WiFi↔Thread 互拖？（频谱+片上，第二、三章机制） |
| 7   | 关   | 开  | 开     | BLE↔Thread 互拖？（多协议射频共享，第四章机制） |
| 8   | 开   | 开  | 开     | 全开：产品真实形态，问题是否复现                |

判读规则三条。**只关心与单开基线的差值**——同开组合掉多少、掉了跟哪颗射频的加入同步；**双开组合定位配对**——组 6 坏而组 5、7 好，嫌疑收窄到 WiFi↔Thread 这一对，再按第二章（频谱层）与第三章（片上层）的证据特征归层；**全开才坏而双开都好，先怀疑组合效应**（三颗射频的调度余量叠加耗尽，第五章的调度风暴形态），回组 5/6/7 逐对加压复测。

### 6.3.2 负载注入可控化

矩阵实验要能复现、能比较，前提是**负载可控**——「手机随便用用」不是负载，「iperf3 定速 10 Mbps 跑 60 秒」才是。三类负载的可控化：

| 负载源      | 可控参数          | 控制方式（真实命令/API）                                                                                                                             | 验证手段                                                           |
| ----------- | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| WiFi 流量   | 速率/时长/方向    | `iperf3 -c <对端IP> -t 60 -b 10M`（TCP 定速）；`iperf3 -c <对端IP> -u -b 10M -t 60`（UDP）                                                           | iperf3 报告 + WiFi sniffer                                         |
| BLE 活动    | 广播间隔/连接参数 | 固件定值：NimBLE `ble_gap_adv_params` 的 `itvl_min`/`itvl_max` 固定为同一值（BLE 单位 0.625 ms）                                                     | `btmon -t` 看 LE Set Advertising Parameters + BLE 嗅探核验实际间隔 |
| Thread 活动 | SED 轮询/CSL 节拍 | ot-cli：`pollperiod 3000`（SED 数据轮询周期，ms）；`csl period <us>`（CSL 周期，按 [[thread-debug-ch07-sleepy-end-device\|Thread 调试（七）]] 口径） | 802.15.4 sniffer 看轮询/CSL 节拍                                   |

可控化的意义在 6.5 案例里会显形：**「打印机在打印」不是可复现的负载，「按打印机任务的包长与间隔注入定速流量」才是**——前者只能碰运气复现，后者可以随时重放、可以逐档加压（10M→20M→40M），把「什么时候开始疼」的边界画出来。

### 6.3.3 单一变量的纪律

共存实验比单协议实验更容易自我欺骗，因为变量天然成对出现。纪律照搬 [[wifi-hw-debug-ch01-debug-methodology-toolbox|WiFi 调试（一）]] 的五条，共存侧再加三条：

- **冻结清单**：每轮实验前过一遍——各射频信道、天线/位置、负载参数、固件版本、环境（邻居 AP 有没有新增）。清单外任何东西变动，本轮作废。
- **开关也是变量**：验证「关掉 BLE 就好了」之后，必须**再开回来复现一次**（A→B→A 三点），否则你分不清是「BLE 的存在导致」还是「期间环境变了」。
- **顺序随机化防惯性**：矩阵 8 组按固定顺序跑时，环境本身在漂（邻居占用、温漂）。可疑时打乱顺序重跑关键组，两次结果一致才算数。

## 6.4 共存性能的量化判据：互拖比

「变卡了」「感觉慢了」没法进 checklist。共存性能要变成数，单位是**互拖比**——同开性能相对单开基线的衰减倍数：

```text
吞吐/成功率类（越大越好）：  互拖比 R = 指标(单开基线) / 指标(同开)
时延/掉线类（越小越好）：    互拖比 R = 指标(同开)     / 指标(单开)

R ≈ 1.0  无实质互拖
R >  1.0 有互拖，幅度即比值
判读永远对照单开基线，没有基线的互拖比是编出来的
```

按指标分列的判据表（**均为经验口径，供排障时划红线用；不同产品按业务定义，公开文献无统一阈值，待核对**）：

| 指标            | 单开基线怎么取                     | 同开判读（经验口径）                                       | 出自 |
| --------------- | ---------------------------------- | ---------------------------------------------------------- | ---- |
| WiFi 吞吐互拖比 | 组 2 基线（iperf3 定时长三取中位） | ≤ 1.3 良好；1.3~2 需评估；> 2 不可接受                     | 本章 |
| Thread PDR 衰减 | 组 4 基线（定窗口统计投递率）      | 同开后 PDR 相对下降 ≤ 5% 良好；> 10% 必须归因              | 本章 |
| BLE 连接稳定性  | 组 3 基线（断连次数/小时）         | 同开后无新增断连；supervision timeout 触发即为红灯         | 本章 |
| BLE 配网成功率  | 组 3 基线（≥ 20 次统计）           | 同开成功率下降 ≤ 5%（如 95%→90% 以上量级）可接受           | 本章 |
| 时延类（p95）   | 单开 ping/往返统计                 | 增幅 ≤ 2× 良好；与另一射频流量峰值强相关即归共存           | 本章 |
| SED/child 掉线  | 组 4 基线（child table 稳定态）    | 同开后出现新增周期性掉线即红灯（对应片上挤压，第四章口径） | 本章 |

三条使用注意。其一，**相对判据优先于绝对判据**：绝对吞吐受环境摆布，互拖比是同场同条件下的自比，抗环境漂移。其二，判据分层的意义是**止损**：互拖比 > 2 的组合不值得继续调参——按第三、四、五章的机制，参数只能在机制允许的余量里挪，余量被设计锁死时要回 6.3 的矩阵重新归层，或转第七章的设计侧方案。其三，**所有判据表里的数字必须能追溯到一次带记录卡的测量**，否则它只是传言。

## 6.5 教学取证演示：Thread 掉线其实是 WiFi 打印机传输

> 教学复盘案例，取材自常见故障模式综述。现象、根因类型与取证路径在业界具有普遍性，具体数值不对应任何真实项目，全文不给虚构读数。

| 环节         | 内容                                                                                                                                                                                                                                                                                                      |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **场景**     | 智能中枢：WiFi STA（供网）+ Thread 边界路由同板。用户报障：全屋 Thread 灯具/传感器**每天不定时卡顿**，部分设备短暂显示离线后自愈，偶发场景联动失效                                                                                                                                                        |
| **弯路一**   | 按 [[thread-debug-ch08-mesh-reliability\|Thread 调试（八）]] 查网内可靠性：拓扑稳定、router 数正常、无分区记录——全部正常。**正常本身就是线索**，但当时被当成「没查出来」，而不是「受害者没病」                                                                                                            |
| **弯路二**   | 怀疑 SED 节奏问题，按 [[thread-debug-ch07-sleepy-end-device\|Thread 调试（七）]] 调大 child timeout、调 pollperiod——无效。在受害者侧反复下钻，方向从第一天就偏了                                                                                                                                          |
| **转折点**   | 按本章方法布三通道，长窗口录电流 + 双 sniffer 并行 + 三栈日志对时。对齐后发现：**每次 Thread 卡顿窗口都对应电流上一个持续数十秒的发射平台，且该平台与 otbr-agent 日志里 WiFi 大流量时段逐一对齐**——追查该时段业务，是同一台网络打印机在向中枢回传扫描件。「随机」变成了「与 WiFi 大流量强相关」，方向反转 |
| **空口证据** | WiFi sniffer 证实平台时段为本机持续发包；802.15.4 侧同一时段出现成片重传与 MLE 保活帧缺失——Thread 的空口时间被挤压，CSL/轮询交互错过窗口（机制口径见第二、四章）                                                                                                                                          |
| **根因**     | 频谱层与片上层叠加：WiFi 持续大流量占满 2.4G 空口时间（与 Thread 信道重叠，第二章），叠加片上共存仲裁窗口不足以给 802.15.4 让出节拍（第三章口径），SED 保活/轮询错过导致报「离线」，流量回落后自愈                                                                                                        |
| **对策**     | ① Thread 信道错开 WiFi 主信道（第二章的信道地图）；② 打印机类大流量业务做调度/限速，避开低功耗设备的保活窗口；③ 复核共存仲裁配置与固件版本（以 Espressif 官方文档与 changelog 口径为准，待核对）；④ 天线隔离按第七章评估                                                                                  |
| **预防**     | 新品测试矩阵加入「同板大流量 + 网内业务并发」用例（第五章的调度风暴场景清单）；低功耗设备保活窗口与大流量业务的时序冲突列入设计评审项                                                                                                                                                                     |

**证据链复盘**：受害者侧两轮取证全正常（Thread 栈无病）→ **转折点：电流平台与 WiFi 大流量时段、Thread 卡顿窗口三者在时间轴上逐一对齐**（把随机变相关）→ 双 sniffer 提供空口因果（WiFi 占用 + Thread 重传）→ 对照实验锁因果（限速重放打印流量可复现、停掉即消失）→ 机制解释 → 分层对策。三通道各自的贡献：

| 通道 | 本案贡献                                        | 缺了它会怎样                           |
| ---- | ----------------------------------------------- | -------------------------------------- |
| 电流 | 揭示「持续发射平台」这一嫌疑负载的存在          | 不会想到去查同一时刻还有什么业务在跑   |
| 空口 | 证明 Thread 侧是重传/保活缺失，而非自身故障     | 分不清「没发」还是「发了没应」         |
| 日志 | 把平台时段钉到具体业务（otbr-agent + 业务日志） | 只知道「有流量」，不知道「是谁的流量」 |

## 本章小结

- **共存取证第一定律**：症状在 A、根因在 B——受害者侧取证「全部正常」本身就是指向施害者的证据，先归层再下钻（6.1）。
- **三通道对齐法**：电流出时间、空口出因果、日志出语义；GPIO 打点与共同事件原点把五个时钟缝到一条轴上，三源合并七步走（6.2）。
- **矩阵实验锁因果**：8 组合开关矩阵定位嫌疑配对，负载可控化让问题可重放可加压，A→B→A 回开验证排除环境漂移（6.3）。
- **互拖比量化**：一切判读对照单开基线；红线判据均为经验口径，数字必须能追溯到带记录卡的测量（6.4）。
- **方法论演示**：Thread 掉线案里，转折点是电流平台、WiFi 大流量、Thread 卡顿窗口的三源对齐——单协议视野在受害者侧永远查不到施害者（6.5）。
