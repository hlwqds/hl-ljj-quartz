## 8.1 四系列方法总纲

十一章……不对，是七章结束时，武器已经全部发完；本章把它们串成一条完整的破案路径，然后收队。如果只允许用一句话概括四个系列的全部方法，那就是：

> **单协议分层取证缩小范围，共存三层次归层定方向，三通道对齐锁根因。**

| 关键词         | 含义                                                                             | 出处                                                                                                                                                                                             |
| -------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 单协议分层取证 | 每个协议内部按信息成本从低到高下钻（WiFi 的 L1-L4、BLE 的四层、Thread 的三世界） | [[wifi-hw-debug-ch01-debug-methodology-toolbox\|WiFi 调试（一）]]、[[ble-debug-ch01-debug-methodology-toolbox\|蓝牙调试（一）]]、[[thread-debug-ch01-architecture-debug-map\|Thread 调试（一）]] |
| 共存三层次归层 | 症状先归频谱/片上/网络协作三层，层错了方向就全错；互拖矩阵圈定嫌疑配对           | [[radio-coexist-ch01-same-board-anatomy\|第一章]]、[[radio-coexist-ch02-24ghz-spectrum-map\|第二章]]                                                                                             |
| 三通道对齐     | 电流出时间、空口出因果、日志出语义，五时钟一条轴；矩阵实验与互拖比把嫌疑钉成因果 | [[radio-coexist-ch06-coexist-forensics\|第六章]]                                                                                                                                                 |

三个案例就是这三句话的完整走法。每个案例诚实列出**弯路**与**转折点证据**——转折点不是运气，是「哪一步证据本可以更早拿到」的教材；弯路也不白走，每条都兑换成了一条 checklist（8.3）。

把四系列方法收成一张流程图（每一步标注武器出处）：

```text
接到问题「多射频设备某个协议不行」
   │
   ├─ ① 受害协议先走一遍单协议分层取证（wifi/ble/thread 各自系列）
   │      └─ 全正常？——记录在案：受害者无罪，转共存线
   │
   ├─ ② 三层次归层 + 互拖矩阵（第一、二章）
   │      └─ 频谱层 → 空口占用证据（第二章 + 双 sniffer）
   │         片上层 → 调度证据（第三、四、五章 + 电流/日志）
   │         网络协作层 → 角色分工与跨协议传播（第一章 Q3）
   │
   ├─ ③ 三通道对齐锁根因（第六章）
   │      └─ 电流出时间、空口出因果、日志出语义
   │         + 矩阵实验定因果 + 互拖比定严重度
   │
   └─ ④ 对策分侧（第三~五、七章）
          调参/配置/策略 → 软件侧立即落地
          隔离/布局/信道规划 → 设计侧进下一版（第七章）
```

> [!note] 证据口径
> 本章三个案例均为**教学复盘案例，取材自常见故障模式综述**：现象、根因类型与取证路径在业界具有普遍性，团队与产品均属合成，具体数值（吞吐百分比、电流、时间戳）不对应任何真实项目，不给虚构读数；涉及的共存机制行为（PTA/分时/多协议调度）以 Espressif、Nordic 官方文档口径为准（第三、四章已梳理）；判据标「经验口径」处按产品定义，待核对。

## 8.2 三个端到端教学复盘案例

三个案例分别落在频谱层单层叠加（案例一）、频谱+片上双层（案例二）、片上层单层（案例三）——正好把三层次模型的三个象限各走一遍，也把第一至七章的武器按需取用。

### 案例一：中枢配网期间全屋 Thread 卡顿（频谱层：信道重叠 + 调度风暴叠加）

> 教学复盘案例，取材自常见故障模式综述。

| 环节                   | 内容                                                                                                                                                                                                                                                                                                              |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**               | 新装智能中枢（WiFi STA 供网 + Thread 边界路由 + BLE 配网）。每次用手机 App 给新设备配网，全屋已入网的 Thread 灯具/传感器集体卡顿：开关响应慢到秒级，部分设备短暂显示离线后自愈；配网一结束全部恢复。平时从不出问题，**每次配网必现**                                                                              |
| **弯路一**             | 按 [[thread-debug-ch08-mesh-reliability\|Thread 调试（八）]] 查网内可靠性：拓扑稳定、路由表正常、无分区记录——全正常。受害者侧无罪，但当时只当成「没查出来」                                                                                                                                                       |
| **弯路二**             | 怀疑边界路由转发：otbr-agent 的 CPU 占用不高，关闭 NAT64 无改善。在「Thread 世界」里打转，因为症状全部长在 Thread 设备上                                                                                                                                                                                          |
| **关键证据（转折点）** | 按第六章布三通道：**配网窗口与卡顿窗口在时间轴上严格对齐**——三栈日志打点证实每次配网开始/结束与卡顿起止逐次对应；双 sniffer 并行显示配网期间 WiFi 信道扫描跳跃 + BLE 广播/连接密集（广播信道与 Thread 工作频段重叠），802.15.4 侧同期成片重传。**「每次配网必现」从用户抱怨变成时间轴上的硬相关**，这是全案转折点 |
| **根因**               | 频谱层为主、片上层叠加：配网三路流量（WiFi 扫描/关联 + BLE 广播连接 + 配网数据）在 2.4G 空口与 Thread 工作信道重叠冲突（第二章地图）；叠加同板射频时间被配网任务挤占、Thread 让路窗口不足（第五章的配网类调度风暴）；板上天线隔离有限放大了互扰（第七章）                                                         |
| **对策**               | ① Thread 信道错开 WiFi 主信道（按第二章信道地图）；② 配网流程分阶段限速，错开低功耗设备保活窗口；③ 复核共存仲裁配置（以厂商文档口径为准，待核对）；④ 按 7.5 决策表重审「空间×频谱」落位                                                                                                                           |
| **预防**               | 测试矩阵加入「配网期间网内业务并发」用例（第五章场景清单）；新品评审过 7.5 决策表，不让产品落进右下角象限                                                                                                                                                                                                         |

**证据链复盘**：症状全部长在 Thread 侧 → 两轮 Thread 世界取证全正常（受害者无罪）→ **转折点：配网窗口与卡顿窗口三源对齐**（把「必现」变成可定位的相关性）→ 双 sniffer 给出空口因果（三路流量重叠 + 15.4 重传）→ 信道错开后窗口内卡顿消失（对照实验锁因果）→ 三层对策收口。跨章索引：频谱层判读（第二章）、调度风暴形态（第五章）、设计侧预防（第七章）。

### 案例二：路由器开 Thread 后 2.4G 吞吐下滑三成（频谱 + 片上双层）

> 教学复盘案例，取材自常见故障模式综述。

| 环节                   | 内容                                                                                                                                                                                                                                                                                                                                                  |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**               | 家用路由器（WiFi SoC + 802.15.4 射频双芯片）固件升级后启用 Thread。用户反馈 2.4G 网速「慢了一截」，iperf3 对比启用前后下滑约三成（用户口径的量级）；5G 频段无感知。Thread 网络本身工作正常                                                                                                                                                            |
| **弯路一**             | 怀疑 CPU：otbr-agent 与相关进程占用很低，排除转发路径算力问题。**教训：「新功能拖慢了网」的第一直觉是软件开销，共存问题的第一动作却是画互拖矩阵**                                                                                                                                                                                                     |
| **弯路二**             | 怀疑 NAT64/DNS 路径：关闭 NAT64 复测无改善。在协议栈层打转，没有先做「单开 vs 同开」的对照                                                                                                                                                                                                                                                            |
| **关键证据（转折点）** | 第六章 6.3.1 的开关矩阵：**WiFi 单开基线正常；WiFi + 802.15.4 空口活动（Thread 网络在网但几乎无业务流量）即出现与用户反馈同量级的下滑**——说明拖累不是 Thread 业务流量，而是 802.15.4 的空口活动本身。双 sniffer 证实 Thread 的 beacon/MLE/路由维护周期帧持续占用，WiFi 侧重传率同步上升。**矩阵实验的差值把「软件开销」假设当场击穿**，这是全案转折点 |
| **根因**               | 双层叠加：频谱层——Thread 信道与 2.4G WiFi 工作信道重叠，15.4 周期帧与 WiFi 抢 airtime（第二章）；片上层——两颗射频间共存仲裁未正确启用，WiFi 发射窗口被反复打断（第三章口径，配置项以厂商文档为准，待核对）                                                                                                                                            |
| **对策**               | ① Thread 信道错开；② 启用并核对双芯片共存握手配置（三线 PTA 类机制，厂商文档口径）；③ 按 6.4 公式复测互拖比回落到良好区间再发版                                                                                                                                                                                                                       |
| **预防**               | 「单开 vs 同开」基线进发版流程：任何新启用一枚射频，发布前必须过开关矩阵与互拖比验收                                                                                                                                                                                                                                                                  |

**证据链复盘**：软件开销假设（两轮弯路都在协议栈层）→ **转折点：矩阵实验里「无线流量的 15.4 空口活动」单独复现下滑**（差值把嫌疑从软件钉到空口）→ 双 sniffer 给出占用与重传证据 → 启用共存 + 错开信道后互拖比回落（双向对照锁因果）→ 发版流程收口。跨章索引：频谱占用特征（第二章）、片上共存配置（第三章）、矩阵方法（第六章）。

### 案例三：Matter 网关 OTA 期间 BLE 配网超时（片上层调度风暴）

> 教学复盘案例，取材自常见故障模式综述。

| 环节                   | 内容                                                                                                                                                                                                                                                                                                                         |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **现象**               | Matter 边缘网关（单 SoC：WiFi+BLE+802.15.4，形态见 [[radio-coexist-ch01-same-board-anatomy\|第一章]]）。后台给网关推送 OTA 下载期间，现场用 App 给新设备做 BLE 配网频繁超时；OTA 结束后配网一切正常。两条时间线平日互不相扰，一重叠就出事                                                                                    |
| **弯路一**             | 怀疑 Matter 配网流程与证书：按 [[thread-debug-ch10-matter-over-thread\|Thread 调试（十）]] 的三阶段分解单独复测配网——全通过。单测都好，恰是调度风暴（[[radio-coexist-ch05-scheduling-storms\|第五章]]）的签名，当时没认出来                                                                                                  |
| **弯路二**             | 怀疑手机端：换手机、换系统版本复测仍超时。在「配网侧」反复加测，因为超时报错长在配网日志里                                                                                                                                                                                                                                   |
| **关键证据（转折点）** | 第六章三通道：日志通道里**每次 BLE 配网超时时刻都与 OTA 分块下载的突发对齐**；电流通道显示 OTA 期间 WiFi 发射占空比极高、BLE 事件被挤压在缝隙里；BLE 空口侧连接事件间隔漂移、丢包（连接参数账见 [[ble-debug-ch05-connection-parameters\|蓝牙调试（五）]]）。**「配网超时」与「OTA 突发」的双时间线逐点对齐**，这是全案转折点 |
| **根因**               | 片上层调度风暴：WiFi 持续大流量吃满射频时间，BLE 连接事件被反复推迟，GATT 传输窗口错过导致上层超时；单协议单测时余量充足，同开即穿底（第五章 OTA 场景的教科书形态）                                                                                                                                                          |
| **对策**               | ① OTA 下载限速（iperf3 定速同款思路，把突发削成平台）；② 产品策略：配网期间暂停/延后 OTA；③ BLE 连接参数按 [[ble-debug-ch05-connection-parameters\|蓝牙调试（五）]] 协商更稳的组合；④ 共存仲裁配置复核（厂商文档口径，待核对）                                                                                               |
| **预防**               | 高负载任务（OTA/大流量）与配网/低功耗业务的**时序互斥规则**写进产品策略；测试矩阵加入「OTA 期间配网」并发用例（第五章场景清单）                                                                                                                                                                                              |

**证据链复盘**：配网侧两轮单测全通过（「单测都好，一起跑就崩」）→ **转折点：超时时刻与 OTA 突发的双时间线对齐**（把偶发超时钉到片上调度挤压）→ 电流通道给出占空比证据 → 限速后配网恢复（对照实验锁因果）→ 产品策略收口。跨章索引：调度风暴机制（第五章）、BLE 参数账（蓝牙调试（五））、限速工具（第六章）。

### 三个转折点的公共形态

| 形态         | 案例                                | 本质                           | 复用动作                         |
| ------------ | ----------------------------------- | ------------------------------ | -------------------------------- |
| 窗口相关性   | 案例一：配网窗口与卡顿窗口逐次对应  | 把「必现」变成时间轴上的硬相关 | 三通道布好后先对窗口，再谈机制   |
| 矩阵差值     | 案例二：15.4 空口活动单独复现下滑   | 把「软件开销」类假设当场击穿   | 单开基线先行，差值只认矩阵实验   |
| 双时间线对齐 | 案例三：超时时刻与 OTA 突发逐点对齐 | 两条独立来源证据互相指认       | 单条证据只定嫌疑，交叉指认才定案 |

三种形态分别出自第六章的「三源合并」「矩阵实验」「时间轴对齐」——方法论不是章节能改编的口号，是案例里真实扣动扳机的那一发。

### 三案的公共结构与弯路兑换

三案按三层次模型摊平对比——注意症状层与根因层的错位，正是第六章说的「症状在 A、根因在 B」：

| 维度       | 案例一                                 | 案例二                                  | 案例三                             |
| ---------- | -------------------------------------- | --------------------------------------- | ---------------------------------- |
| 症状长在哪 | 全屋 Thread 设备卡顿/离线              | WiFi 吞吐                               | BLE 配网超时                       |
| 根因在哪   | 频谱层（信道重叠）+ 片上层（配网挤占） | 频谱层（15.4 占用）+ 片上层（仲裁缺位） | 片上层（WiFi 大流量挤压 BLE 事件） |
| 弯路共性   | 在受害协议栈里反复下钻                 | 先入为主怀疑软件开销                    | 单测都好就换测试对象               |
| 转折点形态 | 窗口相关性                             | 矩阵差值                                | 双时间线对齐                       |
| 对照实验   | 信道错开后窗口内卡顿消失               | 启用共存 + 错开信道后互拖比回落         | 限速后配网恢复                     |
| 最终收口   | 信道规划 + 并发用例进矩阵              | 「单开 vs 同开」进发版流程              | 高负载与配网时序互斥进产品策略     |

每条弯路都兑换成了一行 checklist——这是弯路唯一正确的变现方式：

| 弯路（当时的样子）                   | 兑换出的防线                 | 兑换后防线在 checklist 的位置 |
| ------------------------------------ | ---------------------------- | ----------------------------- |
| Thread 世界两轮取证全正常仍不转向    | 「受害者无罪」转共存线的纪律 | 行 29（跨协议相关性）         |
| 「新功能拖慢网」先查软件开销         | 单开 vs 同开基线进发版流程   | 行 16、17（单开基线/矩阵）    |
| 单测通过就换手机复测                 | 并发用例进测试矩阵           | 行 26、10（并发/环境矩阵）    |
| 辐射口径对比读数跳（第七章案例同款） | 传导口径验收进方案变更流程   | 行 3、4（隔离/净空审查）      |

### 共存版证据记录卡（现场模板）

排障现场最贵的是「事后想不起来」。开工先建一页记录卡，共存版在单协议版上加三栏：

```text
== 共存证据记录卡 ==
问题一句话：______________（症状协议 + 触发条件）
症状协议：WiFi / BLE / Thread          症状分类：该协议五分类之一
三层次归层：频谱 / 片上 / 网络协作      嫌疑配对：____ ↔ ____

时钟对齐记录：
  对时方式：NTP / 共同事件原点          各源偏移：wifi.__s  ble.__s  15.4.__s  pcap.__s
  打点位：GPIO __（事件：____）  MARKER 行格式：____

单开基线（矩阵组 2/3/4）：
  WiFi 单开：吞吐__ PDR__ 断连__ 配网__     （存档文件名：____）
  BLE 单开：……                Thread 单开：……

开关矩阵记录（组 5/6/7/8 与基线的差值）：
  组 5（WiFi+BLE）：__   组 6（WiFi+15.4）：__   组 7（BLE+15.4）：__   组 8：__

嫌疑排序与证据：
  1. ____  支持证据：____  反对证据：____
转折点：______________（哪条证据改变了方向）
结论三要素自检：症状吻合 □  独立证据 □  可复现 □
```

「时钟对齐记录」与「单开基线」是共存版新增的两栏，也是第六章全部手法的前置条件——它们缺席，后面的每条证据都不可信。

## 8.5 结语：无线调试 tracks 收官

从 [[wifi-rf-hw|射频硬件入门]] 的一颗 PA 一根天线，到 [[wifi-hw-debug|WiFi 硬件调试实战]] 的逐帧空口、[[ble-debug|蓝牙调试实战]] 的广播与连接、[[thread-debug|Thread 调试实战]] 的 mesh 与边界，再到本系列的三射频同板——四个系列走完，无线调试这条 track 的拼图就齐了。

最后送三句话上路。

**先归层，再取证。** 共存时代最贵的浪费，是在受害协议的栈里反复下钻——方向错了，努力只会把弯路走得更扎实。互拖矩阵先画，三层次先归，这一步只花十分钟，却决定后面两周的方向。

**相关性不是根因，对齐才是证据。** 「它们同时发生」只值一个嫌疑；电流、空口、日志三条独立时间轴在同一时刻互相指认，才配写进结案报告。第六章的方法在一切「互拖」类疑难上通用，远不止无线。

**工具会过时，纪律不会。** `iw` 会改版、sniffer 固件会停更、芯片会换代，但「先基线、单变量、对照实验、对时、可复现」这五条纪律（[[wifi-hw-debug-ch01-debug-methodology-toolbox|WiFi 调试（一）]] 第一章定下、四个系列共用）在任何一代工具上都成立。带走的应该是纪律，不是命令行。

祝调试顺利，证据常在，互拖早防。四个系列，全系列完——江湖再见。
