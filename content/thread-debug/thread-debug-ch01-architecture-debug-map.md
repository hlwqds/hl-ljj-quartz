## 1.1 Thread 一页定位：802.15.4 上的自组网 IPv6 mesh

调试任何协议前先钉死它的本质，否则排障时会拿着错误的地图走路。Thread 的本质用一句话说：

**Thread = IEEE 802.15.4（2.4 GHz PHY/MAC）+ 6LoWPAN 头压缩 + 自组网 IPv6 mesh 路由，无单点故障，Matter 生态的首选底层。**

拆开看这三层：

| 组成               | 干什么                                                                                                       | 调试时意味着什么                                               |
| ------------------ | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| IEEE 802.15.4 底座 | 2.4 GHz O-QPSK/DSSS 物理层，信道 11~26；MAC 层带 CSMA/CA 与短地址机制（协议版本：IEEE 802.15.4-2006 及后继） | 射频问题（灵敏度/干扰/信道占用）与 WiFi 共享同一套 2.4G 世界观 |
| 6LoWPAN 头压缩     | 把 40 字节的 IPv6 头压缩成几个字节塞进 802.15.4 的 127 字节帧（IPHC 编码）                                   | 抓包时看到的第一层是压缩头——第三章教你怎么读                   |
| 自组网 IPv6 mesh   | 设备自选举 Leader、自建路由，节点挂了网络自愈；全部寻址是 IPv6（Link-Local / Mesh-Local）                    | 排障语言是「地址、路由、前缀」，不是「AP、关联、漫游」         |

与近邻协议的边界，一张表钉死（口径：各协议官方规范；Thread 以 Thread Specification 1.3 口径，Matter 关系以 CSA 公开口径）：

| 维度       | Thread                        | WiFi（802.11）           | BLE                                       | Zigbee                         |
| ---------- | ----------------------------- | ------------------------ | ----------------------------------------- | ------------------------------ |
| 底层 PHY   | 802.15.4，2.4 GHz，信道 11~26 | 802.11 家族，2.4/5/6 GHz | 2.4 GHz 专用信道                          | 802.15.4，2.4 GHz（也有 SubG） |
| 组网模型   | 自组网 IPv6 mesh，自愈        | 星型（AP 为中心）        | 星型 piconet（连接为中心）                | 自组网 mesh（Zigbee 3.0）      |
| 网络层     | IPv6 + 6LoWPAN                | IPv4/IPv6                | GATT/属性模型为主                         | Zigbee 网络层（自有协议）      |
| 功耗定位   | 原生支持休眠终端（SED/CSL）   | 高功耗，非电池场景       | 低功耗连接，但无 mesh（除 Mesh 桥接扩展） | 低功耗 mesh                    |
| IP 直达    | 是——每个设备有 IPv6 地址      | 是                       | 否（需网关翻译）                          | 否（需网关翻译）               |
| 单点故障   | 无（Leader/Router 可再选举）  | AP 即单点                | 中心设备即单点                            | 协调器角色接近单点             |
| 生态归属   | Matter 首选底层               | 全品类                   | 配网信道 + 近距交互                       | 智能家居遗留生态               |
| 调试工具面 | ot-cli + 802.15.4 抓包        | iw/wpa_cli + 802.11 抓包 | bluetoothctl/btmon                        | 专用厂商工具为主               |

协议栈的叠层关系用一张图钉死（与 WiFi 的对照帮助你复用既有直觉）：

```text
        Thread                    WiFi（对照）
      ┌───────────┐             ┌───────────┐
应用  │ Matter/CoAP │            │ HTTP 等    │
      ├───────────┤             ├───────────┤
传输  │ UDP/DTLS   │             │ TCP/UDP    │
      ├───────────┤             ├───────────┤
网络  │ IPv6 + 6LoWPAN(压缩) │   │ IPv4/IPv6  │
      ├───────────┤             ├───────────┤
链路  │ 802.15.4 MAC(含mesh路由)│ │ 802.11 MAC │
      ├───────────┤             ├───────────┤
物理  │ O-QPSK 2.4G │            │ 802.11 PHY │
      └───────────┘             └───────────┘
```

两条对本系列最重要的读表结论。其一，**Thread 设备是 IP 节点**：ping、UDP、地址、路由这些 IP 世界的直觉全部适用——`ot-cli` 里能直接 `ping` 一个 v6 地址，这是 BLE/Zigbee 都给不了的调试便利。其二，**Matter 首选底层的关系是单向依赖**：Matter over Thread 时，Matter 的消息跑在 Thread 的 IPv6 之上、经 Border Router 出入家庭 IP 网——Thread 网不通，Matter 层一切免谈（第十章逐层分解）。频段与干扰的物理层背景在 [[ch02-radio-and-spectrum|射频入门（二）]] 已打底，第九章换成 802.15.4 的口径再讲一遍共存。

## 1.2 角色家族：谁管什么

Thread 网络里的每个节点都带着两个标签：**设备能力标签**（FTD/MTD，固件决定）与**网络角色标签**（Router/End Device/Leader，网络动态分配）。调试时这两个标签要分开问。

```text
                        ┌────────────────────────┐
                        │   Border Router (OTBR)  │ ← 家庭 IP 网的出入口
                        │  前缀分发 / NAT64 / mDNS │
                        └───────────┬────────────┘
                                    │
              ┌─────────────────────┼─────────────────────┐
              │              Leader（Router 中选出）        │
              │         管理 Router ID / 地址分配 / 网络数据  │
              │        ┌────────┴────────┐                  │
              │   Router A            Router B             │
              │   ┌───┴───┐          ┌───┴───┐              │
              │   │       │          │       │              │
              │  End     End       REED    End             │
              │  Device  Device  (可升Router) Device        │
              │   │                 │                      │
              │  SED (MTD, 休眠)    SED                     │
              └─────────────────────────────────────────────┘
                        同一 Thread 网络（同一 dataset）
```

两类标签的完整职责表：

| 标签体系   | 角色                  | 全称/含义                     | 谁决定它                      | 它管什么（调试关注点）                                   |
| ---------- | --------------------- | ----------------------------- | ----------------------------- | -------------------------------------------------------- |
| 能力标签   | FTD                   | Full Thread Device            | 固件编译选项                  | 能当 Router/Leader；常驻收听                             |
| 能力标签   | MTD                   | Minimal Thread Device         | 固件编译选项                  | 只当终端设备；可休眠（SED 是 MTD 的低功耗用法）          |
| 网络角色   | Router                | 路由节点                      | Leader 动态分配 Router ID     | 为子设备转发；维持 mesh 链路；最多 32 个                 |
| 网络角色   | REED                  | Router-Eligible End Device    | 网络按需晋升（Router 不足时） | 平时是终端，需要时升级成 Router——拓扑变化的嫌疑人之一    |
| 网络角色   | End Device / SED      | 终端/休眠终端                 | 自身能力 + 父节点分配         | 挂在某个 Router 名下；SED 靠 poll/CSL 收包（第七章）     |
| 网络角色   | Leader                | Router 中的一个               | 选举产生（Router 挂了重选）   | 分配 Router ID、维护网络数据（Network Data）、地址查询   |
| 网络外角色 | Border Router（OTBR） | Thread ↔ 家庭 IP 网的边界网关 | 独立部署（树莓派 + Linux）    | 前缀分发/路由发布/NAT64/mDNS——「出不了网」类问题的主战场 |

「谁管什么」速查表——拿到症状先对号入座（各行的取证细节在对应章节展开）：

| 你怀疑的事                 | 先问哪个角色           | 第一条取证命令（口径：OpenThread CLI 文档）  |
| -------------------------- | ---------------------- | -------------------------------------------- |
| 节点忽隐忽现、拓扑频繁变动 | REED/Router 晋升与老化 | `ot-cli` 的 `router table`、`neighbor table` |
| 整网地址/网络数据异常      | Leader                 | `leader data`、`state`                       |
| 单个设备连不上网           | 该设备的父节点         | 设备侧 `state`、父侧 `child table`           |
| 网内通、外网不通           | Border Router          | OTBR 日志 + `netdata show`                   |
| 电池设备延迟大/掉线        | SED 的父节点           | 父侧 `child table` 的超时计数（第七章）      |

> [!tip] 角色是动态的，取证要带时间戳
> 「Router B 挂了」「Leader 换人了」在 Thread 里是**正常事件**——自愈就是靠它们。调试时看到角色变化先别定罪，把变化时刻与故障时刻对时（对时纪律见 1.5 与第三章），变化发生在故障之前才有资格当嫌疑人。

角色的一生（生命周期视角，帮助理解「什么变化是正常的」）：

| 角色          | 怎么成为它                      | 怎么失去它               | 正常频率         | 异常信号（值得取证）             |
| ------------- | ------------------------------- | ------------------------ | ---------------- | -------------------------------- |
| End Device    | attach 成功即成为               | 换父、被老化、掉线       | 低频             | 频繁换父（乒乓）                 |
| REED          | FTD 入网且 Router 满员时        | Router 空位出现被征召    | 低频             | 长期 REED 却频繁参与竞争         |
| Router        | Leader 分配 Router ID 晋升      | 主动让位、老化退出、掉线 | 拓扑稳定后接近零 | 反复晋升/退出循环                |
| Leader        | Router 间选举（权重与 ID 竞争） | 掉线，剩余 Router 重选   | 故障换防时       | 高频换 Leader、分区双 Leader     |
| Border Router | 人工部署（不参与选举）          | 服务停了/主机挂了        | 低频             | 反复重启、前缀忽有忽无（第六章） |

## 1.3 三世界取证框架

与 [[wifi-hw-debug-ch01-debug-methodology-toolbox|WiFi 调试（一）]] 的 L1~L4 分层同构，Thread 的故障横跨三个世界，每个世界一套工具、一种证据形态。三世界不是先后顺序，而是**三个并行的观测口**——复杂案子要同时开窗、互相作证：

```text
┌────────────────────────────────────────────────────────────────┐
│ 设备世界 —— 节点自己的状态机与自述                              │
│   工具：ot-cli（state/neighbor/router table/计数器）、串口日志   │
│   证据：attach 状态、邻居表、MAC/MLE 计数器、日志模块标签        │
├────────────────────────────────────────────────────────────────┤
│ 网络世界 —— 空口上实际发生的每一帧                              │
│   工具：sniffer 板 + Wireshark（802.15.4 TAP + Thread 解密）     │
│   证据：MLE 消息序列、6LoWPAN 帧、重传、CoAP 交互、时间线        │
├────────────────────────────────────────────────────────────────┤
│ 边界世界 —— Thread 网与家庭 IP 网的接缝                          │
│   工具：OTBR 日志（otbr-agent）、Linux 网络栈（ip -6 route 等）  │
│   证据：前缀分发记录、NAT64/mDNS 行为、路由表、外网连通性        │
└────────────────────────────────────────────────────────────────┘
```

三世界的对比总表：

| 世界     | 回答的问题              | 主力工具                                                       | 取证成本            | 证据可信度边界                                          |
| -------- | ----------------------- | -------------------------------------------------------------- | ------------------- | ------------------------------------------------------- |
| 设备世界 | 节点自己认为状态如何    | `ot-cli` 全套、OpenThread 日志                                 | 极低（串口 + 免费） | 节点只报告它知道的；它认为 connected ≠ 空口真通         |
| 网络世界 | 空口上实际发生了什么    | sniffer 板（nRF52840 dongle 等）+ Wireshark + dataset 网络密钥 | 低（一块板）        | 单板单信道，有视野盲区；解密需拿到正确 dataset          |
| 边界世界 | 出网/服务发现为什么不通 | OTBR（otbr-agent 日志）、Linux `ip -6`/`rdisc6` 等             | 低（树莓派上）      | 涉及家宽上游时，OTBR 之外还有家庭路由器一层，要分层排除 |

三世界的联动规则与 WiFi 系列的「日志与事件对时」同源：**任何结论都要至少两个世界互证**。设备侧日志说「已 attach」，网络侧抓包里却看不到它的 Parent Response——这种矛盾本身就是证据（第四章的入网失败案例就是这么破的）。

### 1.3.1 设备世界速写

ot-cli 的取证入口（第二章速成），设备世界的三板斧：

```bash
> state              # 我是谁（角色）与卡在哪一态
> neighbor table     # 我看见的邻居与链路质量
> counters mac       # MAC 层计数器：发了几帧、重传几次、收不到几个 ACK
```

`counters mac` 是最被低估的一条：TxTotal 与 TxAckFailed 的差值走势就是链路层健康度，配 RSSI 一屏分清「信号差」还是「对面忙」。

### 1.3.2 网络世界速写

sniffer + Wireshark（第三章完整教学），网络世界的三个视角：

| 视角     | 看什么                          | 回答什么                         |
| -------- | ------------------------------- | -------------------------------- |
| 帧列表   | 时间线上谁说了什么              | 交互停在哪一步、谁先沉默         |
| 协议分层 | 802.15.4 → 6LoWPAN → IPv6 → UDP | 消息面（MLE/CoAP）与载荷         |
| 统计视图 | 按源地址/消息类型聚合计数       | 谁话最多、谁在重传、比例是否异常 |

### 1.3.3 边界世界速写

OTBR 侧（第六章主场），边界世界的取证入口：

```bash
sudo ot-ctl state                 # OTBR 眼中的网络状态
sudo ot-ctl netdata show          # 网络数据：对外发布的前缀/路由
ip -6 route show                  # Linux 侧路由：Thread 前缀挂上去了吗
journalctl -u otbr-agent -n 100   # otbr-agent 的自述
```

边界世界最容易产生的误判是「Thread 网坏了」——先做一条分界测试：**网内 ping OTBR 通不通**。通，则问题在边界世界（前缀/路由/NAT64）；不通，问题其实在网内（回设备/网络世界）。一条命令切开两个世界的责任线。

## 1.4 症状五分类总表

用户说「Thread 不行」同样没有排查价值，第一步翻译成五类（与 [[thread-debug|系列索引]] 的地图一致）：

| 症状分类       | 典型表现                                            | 第一反应动作（成本近零）                                          | 最容易走的弯路                            | 对应章节       |
| -------------- | --------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------- | -------------- |
| **入不了网**   | 扫不到网络 / attach 反复失败 / commissioning 不完成 | 设备侧 `state` 看卡在哪一态；抓包看 MLE 交互停在哪条消息          | 反复 reset 重试破坏现场；盲目改功率与位置 | 第四章         |
| **网内不稳**   | 忽隐忽现、拓扑频繁变化、整网分区                    | `router table`/`neighbor table` 记录变化；MLE/路由日志对时间线    | 把正常晋升/老化当故障；只看单点不看整网   | 第五章、第八章 |
| **出不了网**   | 网内互通但访问不了外网 / App 远程失效               | OTBR 日志 + `netdata show` 核前缀；网内 ping 通 OTBR 再看出网     | 直接重启 OTBR；先怪家宽运营商             | 第六章         |
| **低功耗异常** | SED 掉线、数据延迟大、电池缩水                      | 父侧 `child table` 看超时计数；设备侧 poll/CSL 参数与电流曲线对时 | 先怀疑电池硬件；把数据延迟当吞吐问题调    | 第七章         |
| **配网/认证**  | Matter 配网失败；预测试 fail                        | 把流程拆成 BLE→Thread→Matter 三段，逐段定位断点；RF 预测试逐项过  | 三段混在一起排；直接送正式实验室烧钱      | 十、十一章     |

三条读表说明。其一，分类依据是可感知现象而非根因——同一个根因（比如信道被 WiFi 挤占）可以呈现为入不了网、网内不稳、低功耗异常三类症状。其二，每类的第一反应动作都在设备世界或网络世界，成本近零。其三，五类里有四类的第一步都会路过同一道门——**dataset 核对**，这就是下一节。

拿到模糊症状时的分流路线（先问两个问题，再进五分类）：

```text
「Thread 不行」
   ├─ 问题出现在配网/重配网过程中？ ──→ 配网/认证类（十、十一章）
   ├─ 只有一类设备（电池供电）异常？ ──→ 低功耗异常类（第七章）
   ├─ 网内互通、只有外网不通？      ──→ 出不了网类（第六章）
   ├─ 时好时坏、忽隐忽现？          ──→ 网内不稳类（五、八章）
   └─ 从头就 attach 不上？          ──→ 入不了网类（第四章）
                                        └─ 无论哪类：先 dataset active -x
```

## 1.5 Thread 特有纪律：先核对 dataset

Thread 网络的一切身份都在 **dataset**（运营数据集）里：PAN ID、扩展 PAN ID、网络名称、**信道**、**网络密钥**、PSKc 等。两个节点 dataset 不一致，就是两个网络——物理上同处一室、空口互相听得见，逻辑上老死不相往来。

由此得到全系列第一条纪律，优先级高于一切下钻：

> [!warning] 先核对 dataset，再谈排查
> 任何「连不上」「看不到对方」「忽隐忽现」，第一步永远是：在涉事节点上跑 `dataset active -x`（十六进制汇总输出，**格式示意**），比对 Ext PAN ID / PAN ID / Channel / Network Key / Mesh-Local 前缀五大字段。实际案例中，一大半「玄学连不上」只是两边 dataset 不一致——比如反复组网后新旧密钥混用、channel 改了但只有一半节点收到了 pending dataset 更新。
>
> 顺手的好处：核对 dataset 时拿到的 **network key** 正是第三章解密 Thread 抓包的钥匙。dataset 家族（active/pending）与 commissioning 流程在第四章完整展开，本章只需记住口诀：**先 dataset，后玄学**。

## 本章小结

- **一页定位**：Thread = 802.15.4 底座 + 6LoWPAN 头压缩 + 自组网 IPv6 mesh；设备是 IP 节点，ping/地址/路由的 IP 直觉全部适用；与 Zigbee 同底层不同网络层，与 BLE 同频段不同组网模型（1.1 对照表）。
- **角色家族两套标签**：FTD/MTD 是固件决定的能力，Router/REED/End Device/Leader 是网络动态分配的角色，Border Router 在网外——调试先问「问题在哪个角色头上」，且角色变化本身要带时间戳看（1.2）。
- **三世界取证**：设备世界（ot-cli 自述）、网络世界（空口抓包）、边界世界（OTBR）三个并行观测口，任何结论至少两个世界互证（1.3）。
- **症状五分类**：入不了网/网内不稳/出不了网/低功耗异常/配网认证——分类入口，下钻才是路（1.4）。
- **Thread 特有纪律**：先核对 dataset 再谈排查——五个字段五个嫌疑人，一条命令定一半案子（1.5）。

**本章自查清单**（全部打勾再进第二章）：
