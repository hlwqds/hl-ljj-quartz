## 7.1 现场引入：电池设备的三副面孔

第六章解决了「出不了网」，本章回到网内最容易被误判的群体：**电池供电的终端**。现场症状高度模式化：

| 症状             | 现场原话                              | 第一直觉                  | 实际方向                          |
| ---------------- | ------------------------------------- | ------------------------- | --------------------------------- |
| 隔天掉线         | 「昨天还好好的，今天 App 里就是离线」 | 设备坏了 / 信号差         | 父子关系或 poll 节拍问题          |
| 下发命令延迟大   | 「开个灯要等十几秒」                  | 网络拥塞 / 信号差         | poll period × 重传的延迟账        |
| 换电池后「死」了 | 「换上新电池反而连不上了」            | 电池仓接触不良 / 固件 bug | 父表残留 + 重新 attach 的时序问题 |

三副面孔共享同一个底层事实：**这类设备大部分时间在睡觉，醒来的时刻由它自己和父节点的一份「合同」决定**。合同上的三个条款——多久醒一次（poll period）、多久不联系就算违约（child timeout）、违约后怎么处理（父表老化与重新 attach）——就是本章全部病灶的来源。调试这类设备的第一纪律：**别把它当常供电设备查**。`ot-cli` 里它可能显示一切正常，唯独「父节点那边不认识它了」——证据必须从父子两侧分别取。

## 7.2 SED 机制盘点

### 7.2.1 角色家族：FTD / MTD / SED

Thread 规范把设备按能力分两类（Thread Specification 1.1 口径）：

| 角色 | 全称                  | 能力                                                                              | 典型设备             |
| ---- | --------------------- | --------------------------------------------------------------------------------- | -------------------- |
| FTD  | Full Thread Device    | 常开收发、可当 Router/REED、转发他人流量                                          | 插电灯、网关、插座   |
| MTD  | Minimal Thread Device | 无路由能力、依赖父节点、可深度睡眠                                                | 电池传感器、门磁、锁 |
| SED  | Sleepy End Device     | **行为描述**而非独立角色：MTD（或 Rx-off-when-idle 的 FTD）长期关收发机，定期唤醒 | ——                   |

调试视角的要点：SED 是 **Rx-off-when-idle** 的设备——空闲时接收机关闭，**父节点不能随时找到它**。于是所有下行数据（App 下发的命令、UDP 响应）都只能攒在父节点那里，等 SED 自己醒来「问一句有没有我的快递」。这一问，就是 802.15.4 MAC 的 **Data Request** 命令帧。

### 7.2.2 poll 节拍：data request 与 poll period

SED 的基本呼吸节拍（Thread 1.1 经典机制，IEEE 802.15.4 MAC 层的间接传输）：

```text
        （格式示意：SED 与父节点的轮询交互）

 SED        ●睡        ●睡        ●醒→发Data Request→父有货→收数据→●睡
  │──────────┤──────────┤───────────▲──────────────────────────┤───►
  │          │          │           │                          │
  ◄────── poll period ────►        父节点：此前一直替它缓存下行帧
```

- SED 每隔 **poll period** 醒一次，向父节点发 802.15.4 Data Request 命令帧。
- 父节点若有缓存数据，紧跟着回传；没有，回一个空确认，SED 继续睡。
- **下行延迟的下限就是 poll period**：命令到达父节点后，最坏要等 SED 下一次醒来才被取走。poll period 定 10 s，用户侧就可能出现「十几秒才执行」——这不是网络慢，是时刻表如此。

ot-cli 侧（MTD 设备，命令以所用 OpenThread 版本 CLI 文档为准）：

```console
## 查/设 poll period（单位 ms，仅轮询类 MTD 有意义）
> pollperiod
10000
Done
> pollperiod 5000
Done
```

### 7.2.3 child timeout 与父表老化

反向的合同条款是 **child timeout**：SED 每次与父节点交互（poll 本身带 MLE 保活语义），都会刷新父节点里的一个倒计时；如果 **child timeout 时长内父节点没有收到该子的任何消息**，就判定它「违约」，把它从子表（child table）里移除，回收分配给它的地址资源（Thread Specification 1.1 的 child id/parent-child 关系维护机制）。

| 参数           | 在谁身上  | ot-cli 命令                    | 调试意义                                                     |
| -------------- | --------- | ------------------------------ | ------------------------------------------------------------ |
| child timeout  | SED 侧    | `timeout`（查询/设置，单位秒） | SED 告诉父节点「我最多这么久不出现」；须显著大于 poll period |
| poll period    | SED 侧    | `pollperiod`（单位 ms）        | 唤醒节拍；延迟与功耗的直接旋钮                               |
| 子表条目老化   | 父侧      | `child table`（可见 age 计数） | 倒计时可视化：age 持续涨到超时 → 子被移除                    |
| 路由器自身超时 | Router 侧 | `router` 相关命令族            | 与本章无关，第五章的老化机制                                 |

经验配比（**教学建议，非规范数值**）：poll period 取秒级时，child timeout 取 poll period 的数十倍以上，给丢包与重连留出充分余量。两者配置失衡——比如 poll period 大于 child timeout——等于合同自相矛盾：设备按节拍睡觉，父节点却等不到它，**稳定地周期性掉线**。这是低功耗调试里性价比最高的第一查。

### 7.2.4 CSL：Thread 1.2 的第二套时刻表

Thread 1.2 引入 **CSL**（Coordinated Sampled Listening，协调采样侦听，Thread Specification 1.2 口径），机制上与 poll 是两条路线：

```text
        （概念对比，格式示意）

poll（Thread 1.1）：
 SED   ●─────────●─────────●────   每次醒来主动发帧问父节点（RX 长开一小段）
 父    攒着等它来取，被动等

CSL（Thread 1.2）：
 SED   ˄    ˄    ˄    ˄    ˄     按 CSL 通道（channel）周期性短暂开 RX（微秒~ms 级）
 父    算好时刻，在 SED 醒来的窗口精准发下行帧
```

| 维度         | poll（1.1）            | CSL（1.2）                               |
| ------------ | ---------------------- | ---------------------------------------- |
| 谁决定时刻   | SED 自己醒、主动问     | 双方协商 CSL 周期与相位，父侧按表投递    |
| 每次唤醒成本 | 发一帧问询（TX，较贵） | 短暂开 RX 听一瞬（通常更省，待实测核对） |
| 下行延迟     | 下限 = poll period     | 下限 = CSL 周期，且父侧可按需触发        |
| 上行时机     | 任意（醒时顺路发）     | 醒时顺路发                               |
| 调试抓手     | `pollperiod`           | CSL 相关属性/数据集字段，以版本为准      |

对调试者的实操含义：**先分清手里的设备跑的是哪套机制**。抓包里看到周期性 Data Request 命令帧 → poll 型；看到 IEEE 802.15.4 头部带 CSL IE（Information Element）→ CSL 型（第三章的抓包方法，解密后看 MAC 头）。病灶分析框架一致——都是「时刻表没对上」——但取证对象不同。

## 7.3 父子关系取证

### 7.3.1 子侧：我在谁家、合同条款是什么

```console
> parent        ## 当前父节点与最近一次交互信息
Ext Addr: 9e3f...（示意）
Rloc: 0x3400
Link Quality In: 3, Out: 3
...

> timeout       ## 自己申报的 child timeout（秒）
240
Done
> state
child
```

看点三件套：父节点的 **RLOC**、双向链路质量、以及 `timeout` 与 `pollperiod` 的配比是否合理。注意 SED 挂在 Router 还是 REED 化的子设备下，行为可能有差异（第八章展开）。

### 7.3.2 父侧：子表与老化倒计时

```console
> child table   ## （示意格式）
| ID  | RLOC16 | Timeout | Age | LQ In | C_VN |R|S|D|N| Extended MAC |
|   1 | 0x3401 |     240 |  37 |     3 |  131 |1|1|1|1| a6e1...      |
|   2 | 0x3402 |     240 | 191 |     2 |  131 |1|1|0|0| 8a2c...      |
Done
```

**Age 就是倒计时的镜像**：距上次交互过去了多少秒。age 稳定在小值附近波动 → 子设备呼吸正常；age 一路涨到逼近 Timeout → 这台子设备快「失联违约」了。这就是父侧看「隔天掉线」最直观的一格证据。Router 侧配合 `router table` 确认自己在拓扑里的角色（第五章口径）。

### 7.3.3 「换电池后死了」的机制解释

换电池断电几秒钟，设备重启后发生的事（教学推演链）：

1. **断电瞬间**：父节点那边它还是「在册子表条目」，倒计时照走。
2. **重启后**：固件若恢复/重取了 dataset，会尝试直接向原父节点重新 attach；但期间它自己的 MLE 状态、安全上下文可能已与父侧记录错位。
3. **错位期间**：父节点可能因该子长期无交互而先把它老化移除；或子设备 attach 到了**另一个**父节点，而应用层/App 云端仍缓存旧的 RLOC/服务注册——路由到了旧地址，没人应答。
4. **表象**：设备自检一切正常（本地 `state` 是 child），App 里却「死」了。

所以「换电池后死了」**极少是电池仓物理问题**（先排除接触不良只需一步：重启后本地 `state` 是否回到 `child`/`router`），多数是**子表残留 + 地址/注册不一致**的时序病。对策方向：子侧 attach 成功后**立即刷新应用层注册**（重新做 service/地址发布，第六章与第八章的 network data 机制）；父侧等待老化自然完成或子侧显式 detach-reattach。

## 7.4 三类病灶与先查清单

### 7.4.1 病灶一：唤不醒

现象：设备彻底离线，本地看却像活着，或重启后能回但过阵子又掉。

```text
        （格式示意：poll 型 SED 的「唤不醒」）
 SED  ●──问──●──问──●──问──✗(父不认识我了)──✗──✗
 父   在册    在册    在册    →老化移除→ 后续 data request 被当陌生帧丢弃
```

| 先查什么                     | 手段                                                 | 常见根因                                       |
| ---------------------------- | ---------------------------------------------------- | ---------------------------------------------- |
| poll period vs child timeout | 两侧 `pollperiod`/`timeout` 配比（7.2.3）            | 配比失衡，稳定周期性掉线                       |
| 父节点是否重启过             | 父侧日志/`router table` 的 uptime 线索               | 父重启后子表重建，旧关系丢失，子还在按旧节拍问 |
| 双向链路质量                 | 子侧 `parent` 的 LQ In/Out；父侧 `child table` 的 LQ | 链路边缘化 → 交互时续时断 → 间歇触发老化       |
| 空口证据                     | 抓包看 data request 是否有应答（第三章方法）         | 请求发出但父不应答 → 父侧关系已丢失的实锤      |

### 7.4.2 病灶二：命令延迟大

现象：网内通信「通」，但下发一条命令十几秒才执行。这笔账是**乘法**：

```text
        （教学计算示意，非实测）
最坏下行延迟 ≈ poll period + 每跳重传叠加

例：poll period = 10 s
  命令到父节点：0 ~ 10 s（等它醒来）
  取走时遇链路差：data request/数据帧 MAC 重传，每轮叠加 ms~s 级
  应用层若再兜一层重试：再乘一个系数
  用户感知：10 s + 重传账 ≈ 「十几秒才执行」
```

| 先查什么       | 手段                                              | 判读                                      |
| -------------- | ------------------------------------------------- | ----------------------------------------- |
| poll period 值 | 子侧 `pollperiod`                                 | 延迟下限就是它；产品要秒级响应就别配 10 s |
| 重传占比       | 抓包统计 retry 帧（第三章过滤器）；`counters mac` | 占比高 → 先治链路，延迟会跟着降           |
| 父子链路质量   | 两侧 LQ                                           | LQ 1~2 → 边缘链路，重传常态化             |
| 端到端再兜底   | 应用层超时/重试参数                               | 应用重试与 poll 周期同频共振会放大延迟    |

### 7.4.3 病灶三：掉线

现象：App 里设备离线，过一会儿自己回来，或要人工干预。

掉线判据就一句话：**child timeout 内父节点没等到任何交互**（7.2.3）。三个来源：链路恶化（交互失败累积）、节拍失衡（7.4.1）、设备侧省电策略过激（固件私自拉长 poll 周期/进入更深的睡眠档）。父侧 `child table` 的 age 曲线是分辨利器：**age 缓慢爬升后归零再爬升** → 设备时连时断（链路病）；**age 单调爬到超时** → 设备彻底没呼吸（节拍或电源病）。

## 7.5 与功耗联查：电流曲线对表法

SED 的功耗问题最终要在电流曲线上定案，方法与 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]] 的实测方法阶梯完全同构（采样电阻+示波器看形状，功耗分析仪看形状+平均），这里只讲 Thread 特有的**对表对象**：

```text
        （格式示意：poll 型 SED 的理想电流曲线）
电流
  │  ▄█▄       ▄█▄       ▄█▄       ▄█▄      ← poll 醒来：TX data request + 短 RX
  │──┘ └──────┘ └──────┘ └──────┘ └────   ← 睡眠地板（µA 级，具体值查芯片 datasheet）
  └──┬────────┬────────┬────────┬────► 时间
     ◄─ poll period ─►
```

| 曲线特征（示意）            | 对表的已知行为               | 结论方向                          |
| --------------------------- | ---------------------------- | --------------------------------- |
| 规整尖峰，周期 = pollperiod | data request 节拍            | 健康；平均电流高就调大周期        |
| 尖峰之外多出杂毛            | 传感器采样/日志/看门狗喂狗等 | 与应用日志对时，区分合法与失控    |
| 尖峰簇（密集高窗）          | attach/重新入网全过程        | 掉线重连的能量代价，回到 7.4 查因 |
| 尖峰变矮变空                | 只醒不发（或链路差发不出）   | 请求未达父侧，配合抓包定案        |

功耗与掉线在这里合流：**每一次「唤不醒→老化→重连」都对应曲线上一个尖峰簇**，重连能耗往往远超几百个安静周期——续航异常偏低时先数尖峰簇的密度，比抠平均数更快找到方向（方法论同 [[wifi-hw-debug-ch10-power-consumption|WiFi 调试（十）]] 10.5 的读图三步）。

## 7.6 教学案例复盘：电池锁「死机」实为父表老化

**教学复盘案例，取材自常见故障模式综述。** 以下数值为量级叙述与教学推演，非某次真实测试读数。

- **背景**：电池供电智能门锁，MTD/poll 型，poll period 配 30 s，child timeout 沿用工程模板默认值。现场反馈：装上后偶发「死机」——App 下发开锁无响应，重启（机械钥匙开门后换电池）恢复，几天后复发。
- **第一步：先问合同**。登录网关侧，`child table` 里该锁的条目 age 曾长时间贴近 Timeout 值——说明它**多次濒临违约**。回到固件配置：poll period 30 s 而 child timeout 只给了 60 s，配比仅 2 倍，链路稍差丢几轮交互就直接老化（7.4.3 的单调爬升形态）。
- **第二步：空口定案**。按第三章方法在锁的位置抓包：掉线时段内 data request 照发、但父节点应答丢失的比例明显抬升——锁在「违约边缘」反复试探，最终一个超时窗口内交互为零，父侧移除子表条目。
- **第三步：解释「换电池后死」**。老化移除后，App 云端仍向锁的旧服务注册地址下发命令；锁换电池重启后 attach 到了新父节点，应用层未重新注册，命令持续打到旧地址——「死」的是**注册不一致**，不是锁本身。
- **对策与验证**：①child timeout 提到数十倍 poll period（教学建议配比见 7.2.3）；②固件改为 attach 成功后立即重做应用层注册；③复测：父侧 age 曲线稳定低位波动，尖峰簇消失，连续观察期内无复发。
- **复盘三句话**：①「死机」先查**父子合同配比**，别急着拆电池仓；②poll period 与 child timeout 是同一份合同的正反面，改一个必须看另一个；③任何 attach 成功之后都必须紧跟**应用层重注册**，否则路由通了业务仍是断的。

## 7.7 根因速查表

| 症状              | 高概率根因                       | 一击命中的取证                                                                     | 章节锚点 |
| ----------------- | -------------------------------- | ---------------------------------------------------------------------------------- | -------- |
| 稳定周期性掉线    | poll period ≥ child timeout 量级 | 两侧 `pollperiod`/`timeout` 配比                                                   | 7.2.3    |
| 隔天/数小时后掉线 | 交互失败累积触发父表老化         | 父侧 `child table` age 单调爬升                                                    | 7.3.2    |
| 父节点重启后掉线  | 旧父子关系丢失，子仍按旧节拍发   | 父侧 uptime 与掉线时刻对时；抓包请求无应答                                         | 7.4.1    |
| 命令延迟十几秒    | 下行等 poll + 重传叠加           | `pollperiod` 值 + retry 帧占比统计                                                 | 7.4.2    |
| 换电池后「死」    | 子表残留/地址与注册不一致        | 本地 `state` 正常但云端命令打旧地址                                                | 7.3.3    |
| 时连时断          | 边缘链路                         | 双侧 LQ In/Out；age 锯齿形波动                                                     | 7.4.3    |
| 续航远低于预算    | 频繁重连的尖峰簇 + 过密 poll     | 电流曲线数尖峰簇（[[wifi-hw-debug-ch10-power-consumption\|WiFi 调试（十）]] 方法） | 7.5      |
