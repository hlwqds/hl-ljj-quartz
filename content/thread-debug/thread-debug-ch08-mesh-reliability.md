## 本章证据口径

> [!note] 先立规矩
> ot-cli 命令（`state`、`netdata`、`router table`、`neighbor table`、`counters` 等）以 **OpenThread CLI 官方文档**为准，输出字段名随版本略有差异。规范数值：链路质量三档与 LQI 引 **IEEE 802.15.4**，Router 数量上限引 **Thread Specification**（正文标注版本）；link margin 属通用射频概念，定义参见 [[ch03-decibel-family|射频入门（三）]]。日志与拓扑图均为**格式示意**，不虚构实测读数；案例为**教学复盘案例，取材自常见故障模式综述**。

## 8.1 现场引入：可靠性问题的三种长相

第七章管的是「一台 SED 与它父亲的合同」，本章把镜头拉远到整张网。可靠性问题的现场呈现通常落在三类：

| 类型             | 典型描述                               | 第一直觉       | 实际方向                                    |
| ---------------- | -------------------------------------- | -------------- | ------------------------------------------- |
| 边角设备丢包     | 「大平层最远那间房的传感器时好时坏」   | 换更大功率设备 | 多跳链路质量 + 拓扑结构问题                 |
| 全网偶发卡顿     | 「所有设备一起迟钝几秒，又自己恢复」   | 网关死机       | Leader 选举/Router 变动/network data 重收敛 |
| 新装设备拖慢整网 | 「装了十几个设备后，原来好好的也变卡」 | 新设备有 bug   | Router 容量、路由更新风暴、多播放大         |

三类的共同点：**单看任何一台设备都「没病」**——每台 `state` 正常、LQ 尚可，但把证据拼成整网视角（拓扑、重传占比、network data 一致性），病灶才浮出来。这章的方法论核心就一句话：**mesh 的可靠性是系统属性，取证也必须成系统**。

## 8.2 链路质量体系

### 8.2.1 LQI、RSSI 与三档链路质量

Thread/802.15.4 体系里三个容易混淆的量：

| 量                   | 是什么                                 | 范围（口径）                                            | 调试用途                           |
| -------------------- | -------------------------------------- | ------------------------------------------------------- | ---------------------------------- |
| RSSI                 | 接收信号功率，dBm                      | 芯片实测，典型 -100~0 dBm 量级（以芯片 datasheet 为准） | 有多强；链路预算核算               |
| LQI                  | 链路质量指示，基于信号特征（误码率等） | 0~255（IEEE 802.15.4 定义）                             | 有多「干净」；强信号也可能 LQI 差  |
| Link Quality（三档） | 协议内部的链路质量等级                 | 0~3，3 最好（IEEE 802.15.4 定义 LQ 值 0~3）             | ot-cli 输出里的 `LQ In/Out` 就是它 |

三者关系（教学口径）：RSSI 管「音量」，LQI 管「清晰度」，三档 Link Quality 是协议内部把观测值映射出的**档位结论**。调试时三档是最快的手感指标——`ot-cli` 里 Link Quality 3 = 链路好，2 = 可用，1 = 边缘，0 = 基本不可用。

### 8.2.2 link margin：链路预算的「余额」

link margin（链路余量）= 接收信号强度 − 接收灵敏度，即**距离「听不清」还有多少 dB 的余钱**。概念与计算框架见 [[ch03-decibel-family|射频入门（三）]]，此处只给调试换算直觉：margin 越小，重传率对环境波动（人走动、门开关、同频干扰）越敏感——**边角设备「平时能通、偶发丢包」几乎总是 margin 见底**，而不是「坏了」。多跳链路的总可靠性是各跳连乘：两跳各 90% 单帧成功率，端到端只剩 81%；这就是为什么边角病灶要先看**每一跳**的 LQ 而不是只看端点（每跳取证的通道就是 8.6 的邻居表）。

### 8.2.3 邻居老化与链路质量的观测纪律

链路质量不是一个静态快照，而是一条**会漂移的时间线**：`neighbor table` 里每条邻居除了 LQ，还带着最近交互时间（age 类字段，字段名以所用 OpenThread 版本为准）。调试「偶发」病灶时的采样纪律：

| 纪律                           | 为什么                                         | 做法示意                                   |
| ------------------------------ | ---------------------------------------------- | ------------------------------------------ |
| 多轮采样再下结论               | 单次 LQ 1 可能只是一次瞬时干扰                 | 固定间隔连采 6~12 轮，看 LQ 分布而非单值   |
| 双向都看                       | LQ In 好 Out 差 = 非对称链路（常见于天线朝向） | 邻居两端各跑一次 `neighbor table` 交叉比对 |
| 与事件时间戳对齐               | 卡顿发生时刻的 LQ 才有诊断价值                 | 症状时刻前后加采，与日志对时               |
| 区分「邻居降级」与「邻居消失」 | 降级是链路病，消失是拓扑病（老化/角色变动）    | age 缓慢变大 vs 条目直接不见               |

非对称链路值得单独点名：LQ In 3 / Out 1 的组合在现场相当常见——设备能「听清」父节点，父节点却听不清它（上行更弱）。这类链路上 MAC 重传集中在上行方向，抓包里 retry 帧的方向分布就是判据（8.6.2），而单看任何一侧的表都会得出「链路还行」的误判。

## 8.3 消息可靠性：谁管重传

Thread 跑在 UDP 之上——**UDP 无连接，没人天生管可靠**。可靠性被拆成了两层，各自独立运作：

```text
        （格式示意：两层重传体系）

 端到端层：CoAP 确认消息重传 / MLE 消息重传（应用与路由维护自己负责）
             │  作用域：源节点 ⇄ 目的节点（可跨多跳）
             ▼
 MAC 层：  802.15.4 帧级重传 + CSMA/CA 退避（逐跳）
             │  作用域：相邻两跳之间
             ▼
          空口
```

| 层       | 机制                                                | 谁配置                     | 取证手段                                      |
| -------- | --------------------------------------------------- | -------------------------- | --------------------------------------------- |
| MAC 层   | 帧级 ACK + 有限次重传，CSMA/CA 先退避后发送         | 栈内常量（以所用实现为准） | 抓包看 retry 帧；`counters mac` 的 TxRetry 等 |
| 端到端层 | CoAP CON 消息确认与超时重传；MLE 消息自身的重传逻辑 | 应用/栈参数                | 抓包看相同 message id 重复出现                |

一条命令的最坏延迟账，把两层叠起来看（**教学计算示意，非实测**）：

```text
        （格式示意：两层重传的延迟叠乘）
 t0   应用发出 CoAP CON
      └─ 每跳 MAC：CSMA 退避若干次 + 帧重传最多 N 次（N 为栈内常量）
 t1   三跳链路：单帧送达概率 = 各跳连乘；一跳丢 → 整条重走
 t2   端到端：ACK 超时未回 → CoAP 整条重传（指数退避）
 t3   应用层若还有自己的超时重试 → 再乘一层
 用户感知 = 「网络很卡」，实际是三层账本叠出来的
```

排查这类「卡」的分层判据：

| 判据                                     | 指向                         | 下一步                       |
| ---------------------------------------- | ---------------------------- | ---------------------------- |
| MAC retry 占比高（8.6.2 口径）           | 跳间链路差/干扰              | 按 8.2/8.7 治链路            |
| retry 帧不多但抓包见相同 message id 重复 | 端到端 ACK 丢失（不对称）    | 查回程方向链路与目的节点状态 |
| 三层都不重，但延迟仍大                   | 应用层账本（心跳/队列/轮询） | 与应用日志对账               |

配置权衡一句提醒：调大 MAC 重传次数能救弱链路，但会**放大全网信道占用**（每一帧更赖在空口上），在密集网络里反而恶化别人的 CSMA 体验——可靠性与容量是一对拔河绳，参数必须整网视角评估。

关键调试直觉：**两层重传会叠乘放大延迟**——MAC 层每跳重传几轮 × 中间跳数 × 端到端再兜底，一条命令的「最坏延迟账」就这么滚出来的（与第七章 7.4.2 的延迟账同一条乘法链）。排障时先分清「丢在跳间（MAC retry 占比高）」还是「丢在端到端（retry 帧不多但应用超时）」，方向完全不同。另有**消息优先级**概念：Thread 规范支持为消息标注优先级（如 MLE 高于普通数据，规范细节以 Thread Specification 为准），栈在排队时会让路——「重要消息反被普通流量淹没」类病灶要查优先级设置是否被应用侧覆盖（待核对具体 API 口径）。

## 8.4 network data：为什么 BR 挂了网还「半通」

### 8.4.1 机制：Leader 保管的「全网公告板」

network data 是由 **Leader 集中维护、向全网分发**的数据集：外网前缀（BR 注册的）、路由信息、以及**服务注册**（service——「某设备在网、提供某种能力」的声明，供 mDNS/发现类功能用，第六章口径）。设备通过 CoAP 向 Leader 注册/注销（OpenThread 的 `netdata register` 触发重注册，注册细节以 Thread Specification 与 OT 文档为准）。

### 8.4.2 「半通」的机制解释

BR 掉线后的时间线（教学推演）：

```text
        （格式示意）
 t0  BR 掉线
 t1  网内互访：仍然全通 —— network data 里的网内路由没受影响
 t2  外网访问：已有会话/缓存的 DNS 陆续失效 —— 「网坏了」的观感开始
 t3  有人发起新连接：DNS64/NAT64/前缀没了 → 失败
 t4  若触发 Leader 选举/角色迁移：全网短暂抖动（8.5）
```

所以「BR 挂了网还半通」不是玄学：**网内 mesh 与边界服务是 network data 里两类独立条目**，前者不受 BR 影响，后者随 BR 注册一起失效。取证顺序：`netdata show` 对比故障前后前缀/服务条目差异；OTBR 侧日志（第六章）确认注册何时撤下。

### 8.4.3 多 BR 场景的一致性

规模部署常放两台以上 BR 互备，此时 network data 里**同时存在多个前缀/服务条目**，一致性问题变成新的病灶来源：

| 症状                         | 机制                                 | 取证                                          |
| ---------------------------- | ------------------------------------ | --------------------------------------------- |
| 时通时断，两台 BR 都「活着」 | 设备在两个前缀间漂移，会话随地址失效 | `netdata show` 看多前缀并存；对照设备实际选用 |
| 一台 BR 维护后全网外网抖动   | 注册条目回切/覆盖                    | 两台 OTBR 日志的注册/撤销时刻对时             |
| 部分设备走 A BR、部分走 B    | 各自注册时序不同，属正常但需可预期   | 拓扑 + netdata 快照定期对比                   |

多 BR 的选举与回切细节以 Thread Specification 版本口径为准（待核对）。调试纪律与本章总原则一致：**公告板上的每个条目都要能对上一个已知注册者**，对不上的条目就是幽灵前缀/幽灵服务，优先清理。

## 8.5 大规模网络问题

### 8.5.1 Router 容量上限与 downgrade 抖动

Thread 网络的骨干是 Router。**规范口径：网络中活跃 Router 数量上限为 32 个（Router ID 资源 0~62 中任选，活跃上限 32，Thread Specification 口径）**。Router 数量不是越多越好——Router 之间要两两维护路由与保活，数量膨胀本身消耗空口。网内还有 REED（有 Router 能力但暂以 End Device 身份运行的 FTD）动态升级/降级来平衡：

- 设备密集部署时，多个 REED 同时满足升级条件 → **Router 数量震荡**（升上去又因策略降下来），每次变动伴随路由重算与 network data 更新 → 全网偶发卡顿。这就是「新装设备拖慢整网」的常见机制之一。
- OpenThread 侧有 router 升降级阈值类配置（`router selection jitter` 等，参数名以所用版本 CLI/配置文档为准），密集部署时应拉大抖动抑制。

| 现象                  | 机制                    | 取证                                         |
| --------------------- | ----------------------- | -------------------------------------------- |
| 全网周期性卡几秒      | Router 升降级风暴       | `router table` 的成员列表多次快照对比        |
| 拓扑图频繁变化        | REED 升降 + Leader 事件 | Leader 日志 / MLE Router ID 分配帧（第三章） |
| Router 数逼近 32 上限 | 密集部署无节制升级      | `router table` 行数；`state` 里角色分布      |

### 8.5.2 多播对全网的拖累

多播帧在 mesh 里是**全网洪泛/复制的**（Thread 的多播转发机制，含父→子复制与 Router 间转发，规范细节以 Thread Specification 为准）。一个 mDNS 查询发出去，空口上可能是几十帧的连锁。多播监听（类似 IPv6 的 MLD 监听注册语义，Thread 用自己的多播注册机制把监听者名单注册进 network data，细节待核对版本口径）没配好时，设备会被塞进不该进的多播组，全网流量被无谓放大。**先查什么**：抓包统计多播帧占比（目的地址多播位的帧，第三章过滤器思路）；对照各设备的应用需求——不监听多播的设备不该出现在监听名单里。

### 8.5.3 规模增长的分层体检

把 8.5 的两类问题放进一张「规模增长体检表」，网络扩容前/后各过一遍：

| 体检项                | 健康量级（经验口径，非规范）   | 超标后的动作                            |
| --------------------- | ------------------------------ | --------------------------------------- |
| 活跃 Router 数        | 稠密小型网 5~10 个量级足够     | 调整升级策略，抑制无谓 REED 升级        |
| Router 间最小链路质量 | 骨干互链 LQ ≥ 2                | Router 化设备挪位，别让骨干靠边缘链互撑 |
| 每节点子表占用        | 各父节点子数均衡               | 拆散过载父节点（搬家或补节点）          |
| 多播帧占比            | 稳态流量下占比小（8.5.2 口径） | 治理监听注册与应用层发现频率            |
| 全网 retry 占比       | 8.6.2 分档                     | 按 8.6.2 空间分布下钻                   |

扩容型病灶的典型时间线（教学推演）：装机日一切正常 → 设备陆续上线触发多轮 REED 升级 → Router 表频繁变动 → 路由与 network data 反复重分发 → 「越用越卡」。这类病灶**在装机当天测不出来**，交付验收应包含「稳定 72 小时」观察项。

## 8.6 取证实操：网络体检与重传占比

### 8.6.1 ot-cli 网络体检脚本

在任意节点把整网状态一次看全（命令以 OpenThread CLI 文档为准）：

```console
> state                    ## 我是谁：leader/router/child + 分区信息
> netdata show             ## 公告板上有什么：前缀、路由、服务
> router table             ## Router 名单与各 Router 的链路质量
> neighbor table           ## 我的邻居与双向 LQ/最近交互
> counters mac             ## MAC 收发与重传计数
> counters ip              ## IP 层收发计数
> child table              ## （若带子）子表老化状态（第七章口径）
```

| 命令             | 体检回答的问题                 | 异常指纹                      |
| ---------------- | ------------------------------ | ----------------------------- |
| `state`          | 分区是否正常、我是骨干还是叶子 | `detached`/分区 ID 频繁变化   |
| `router table`   | 骨干成员与质量                 | 行数逼近 32；LQ 1~2 的 Router |
| `neighbor table` | 每一跳的链路余额               | LQ 1、age 长期大              |
| `netdata show`   | 公告板一致性                   | 前缀/服务缺失或与预期不符     |
| `counters mac`   | 空口健康度                     | TxRetry/TxFail 占比随时间抬升 |

**采样纪律**：上述快照按固定间隔（如 5 分钟）多轮采集、横向对比，单次快照几乎诊断不了「偶发卡顿」类病灶——体检的是**趋势**不是截面。

### 8.6.2 空口侧：重传占比

方法就是 [[thread-debug-ch03-802154-sniffing|第三章]] 的抓包，重点看 retry 位的帧（Wireshark 过滤字段以所用版本为准，示意过滤器：`wlan.flags.retry == 1`）：

```text
        （教学计算示意）
重传占比 = retry 帧数 / 总数据帧数
  < 5%   ：健康量级
  5~15%  ：链路余量紧张，先查边角
  > 15%  ：系统性问题（干扰/拓扑/容量），分层下钻
（分档为经验口径，随网络规模与流量类型调整，非规范数值）
```

占比高时的下钻次序：按**发送方**分组 → 定位重传集中在哪条链路；再对照该链路两端的 `neighbor table` LQ——重传热区与 LQ 低档重合 → 链路问题（8.2）；重传全网均匀 → 干扰或信道占用问题（第九章）。

## 8.7 教学案例复盘：边角丢包，加一台 Router 化设备改善

**教学复盘案例，取材自常见故障模式综述。** 数值为量级叙述与教学推演，非实测读数。

- **背景**：大平层项目，一台 OTBR + 若干插电 FTD + 边角电池传感器。反馈：最远卧室传感器频繁离线/丢报，靠近走廊就恢复。
- **第一步：拓扑取证**。传感器 `parent` 显示其父节点是远端一台 FTD，双向 LQ 均为 1——它挂在了一条**两跳串联的弱链路末端**。`router table` 显示全网仅 2 个 Router：OTBR 与一台早期设备。结构问题浮出水面：**骨干太稀，边角全靠端到端多跳硬撑**，任何一跳波动都直接变成丢包（8.2.2 连乘效应）。
- **第二步：空口交叉验证**。第三章方法抓包：重传帧高度集中于该传感器与其中间父节点之间的链路，全网其他链路重传占比正常——不是干扰，是**局部链路余量见底**。
- **第三步：机制性对策**。在走廊中部加一台**保持 Router 角色的常供电设备**（策略上抑制其 downgrade——原因见 8.5.1：设备密集时 REED 角色震荡会让改善不稳定）。效果机制：传感器到骨干的最弱跳被替换为两跳各 LQ 3 的短链路，端到端成功率从「两跳 0.7×0.7 量级」提升到「两跳各 0.9+ 量级」（教学示意乘法），且路由收敛后中间父节点的转发负担下降。
- **验证**：加节点后连续观察，`neighbor table` 中该传感器新父链路 LQ 3，重传占比回落到健康量级，离线事件消失。
- **复盘三句话**：①mesh 的边角病灶先看**拓扑结构**（每跳 LQ + 跳数），再谈换硬件；②骨干 Router 的**密度与稳定性**直接决定边角体验，Router 数量与角色稳定是工程参数不是随机结果；③抓包重传的**空间分布**（集中 vs 均匀）是区分「局部链路」与「全网干扰」的分水岭。

## 8.8 根因速查表

| 症状                | 高概率根因                       | 一击命中的取证                          | 章节锚点 |
| ------------------- | -------------------------------- | --------------------------------------- | -------- |
| 边角设备时好时坏    | 多跳弱链路，link margin 见底     | 逐跳 `neighbor table` LQ + 重传热区定位 | 8.2/8.7  |
| 全网偶发卡顿数秒    | Leader 事件/Router 升降级风暴    | `router table` 多轮快照对比；MLE 帧     | 8.5.1    |
| 新装设备后整网变卡  | Router 容量与角色震荡/多播放大   | `router table` 行数趋势；多播帧占比     | 8.5      |
| BR 挂了「网还半通」 | 网内路由与边界服务独立失效       | 故障前后 `netdata show` 对比            | 8.4      |
| 强信号设备仍丢包    | LQI/干扰类链路劣化（非功率问题） | RSSI 正常但 LQ 低 → 看空口误码与干扰    | 8.2.1    |
| 命令最坏延迟巨大    | 两层重传叠乘                     | MAC retry 占比 + 应用重试参数对账       | 8.3      |
| 多播类功能拖累全网  | 多播洪泛 + 监听注册失控          | 多播帧占比统计；监听名单核对            | 8.5.2    |
| 分区/detached 闪断  | 骨干不稳或 Router ID 资源紧张    | `state` 与分区 ID 时间线                | 8.5.1    |
