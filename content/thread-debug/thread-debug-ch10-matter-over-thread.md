## 10.1 现场引入：配网失败的「三种死法」

前九章的 Thread 世界里，设备入网靠 `ot-cli` 手动下发 dataset——干净、可控、想怎么连就怎么连。但量产产品不走这条路：用户拿出手机，打开生态 App（Google Home / Apple 家庭 / Amazon Alexa），扫码，等转圈。**这个转圈过程横跨三个协议栈**——BLE、Thread、Matter——任何一个环节出问题，用户看到的都是同一句话：「设备添加失败，请重试」。

工程师拿到的故障报告也永远只有这一句话。没有日志文件、没有抓包、只有一段手机录屏（有时候连录屏都没有）。于是排障的第一件事不是抓包，而是**把笼统的「配不上」分解成可分辨的死法**。现场最常见的三种：

| 死法                           | 用户视角                                                          | 转圈发生的位置                          | 本质              |
| ------------------------------ | ----------------------------------------------------------------- | --------------------------------------- | ----------------- |
| 死法一：BLE 阶段断             | 扫到设备、点添加，转一下就报错，甚至压根扫不到设备                | App 与设备还没建立 Matter 会话          | 蓝牙连接层问题    |
| 死法二：Thread 入网失败        | BLE 阶段走完了，App 提示「正在连接网络」卡住或报错                | 凭证已下发，设备 attach Thread 网络失败 | Thread 网络侧问题 |
| 死法三：Matter onboarding 卡住 | 设备已连上网（OTBR 的 mesh 里能看到它上线了），但添加最后一步超时 | PASE/CASE 会话建立或证书校验阶段        | Matter 应用层问题 |

三种死法的价值在于：**它们发生的先后顺序就是排查的顺序**。BLE 阶段没走完就不用看 dataset；设备已经在 mesh 里上线了，就别再纠结入网问题；配对完成但控制不稳，那多半不是配网问题而是出网问题。本章的任务就是给每个阶段配上「成功标志」与「失败特征」，让你看一眼现象就能说出「死在哪个阶段」。

> [!note] 证据口径
> 本章流程依据 Matter Specification（CSA 发布）与 Bluetooth Core Spec 的 commissioning 相关章节概念整理，OpenThread 侧命令以官方文档为准；chip-tool 日志行为格式示意，非逐字实录；不虚构任何实测读数。本章案例均标教学复盘。

## 10.2 配网流程分解：一张图看懂三阶段

Matter over Thread 的标准配网路径（commissioning over BLE）可以画成这样：

```text
 手机 App                        设备（未入网）                Thread 网络 / OTBR
    │                                 │                             │
    │  ① BLE: 扫描 commissionable 广播 │                             │
    │<────(BLE adv, 含 Discriminator)──│                             │
    │  ② BLE 连接建立                  │                             │
    │<════════ BLE 连接 ══════════════>│                             │
    │  ③ PASE 会话（配网期安全会话，    │                             │
    │     用 onboarding payload 派生） │                             │
    │<────── Matter over BLE ────────>│                             │
    │  ④ 下发网络凭证                  │                             │
    │     (Thread: dataset 关键字段)   │                             │
    │  ──────────────────────────────>│── ⑤ Thread attach ────────>│
    │                                 │   （MLE join、上线、         │
    │                                 │     获取 RLOC/ML-EID）       │
    │  ⑥ App 与设备建 CASE 会话        │      │                      │
    │  （经 OTBR，运行证书认证）        │<─────┴── Thread mesh ───────│
    │<═══════ CASE over Thread ═══════>│                             │
    │  ⑦ 证书链校验、ACL 配置          │                             │
    │  ⑧ Commissioning complete       │                             │
```

几个关键概念，排查时必须分清：

| 概念                | 是什么                                                                                                      | 排查意义                                                           |
| ------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| Commissionable 广播 | 设备在 BLE 侧发出的可配网广播，携带 Discriminator 等标识                                                    | 扫不到它 = 死法一，根本轮不到 Thread                               |
| Onboarding payload  | 二维码/手动配对码里的信息：Discriminator、PASSCODE（配对码，Matter 语境下对应 BLE 阶段的认证凭据）、VID/PID | 输错或扫错码，PASE 会建不起来                                      |
| PASE                | Passcode-Authenticated Session Establishment，配网期用 PASSCODE 认证的临时安全会话，跑在 BLE 上             | PASE 起不来 = BLE 通了但 Matter 会话层死了，容易误判成「蓝牙问题」 |
| CASE                | Certificate-Authenticated Session Establishment，用运营证书（NOC）建立的正式安全会话，跑在 Thread 上        | CASE 超时 = 死法三的典型，此时设备其实已经入网                     |
| Dataset 下发        | App 把 Thread 网络的 PAN ID/信道/主密钥等经 BLE 写给设备                                                    | 字段错一个，attach 必失败——死法二的头号根因                        |
| Discriminator       | 区分同一空间多台可配网设备的标识                                                                            | 两台设备同时配网时扫错对象，是最冤枉的一种失败                     |

onboarding payload 里的字段，排障时逐项核对（以 Matter 规范当期定义为准）：

| 字段               | 作用                                  | 错了会怎样                        |
| ------------------ | ------------------------------------- | --------------------------------- |
| Discriminator      | BLE 阶段定位目标设备                  | 扫错设备/扫不到                   |
| PASSCODE（配对码） | PASE 会话的认证凭据                   | PASE 认证失败——BLE 连上了也过不了 |
| VID/PID            | 厂商/产品标识                         | App 校验宣称不符时报错            |
| Discovery 能力位   | 声明支持 BLE/WiFi/Thread 哪些配网通道 | 走错配网通道（如走成 WiFi 配网）  |

注意一个容易搞反的点：**给 Thread 设备下发的是 dataset 而不是「WiFi 密码」**——那是 WiFi 型 Matter 设备的事。Thread 设备拿到的是整个 active dataset（第四章讲过的那个东西），所以死法二的排查最终一定落回 dataset 核对——这正是第四章 dataset 纪律在配网场景的直接应用。

## 10.3 三阶段取证法：每个阶段的成功标志与失败特征

### 阶段一：BLE 连接（commissionable 广播 → BLE 连接 → PASE）

| 取证点       | 成功标志                                       | 失败特征                                              | 工具/方法                                                                                                          |
| ------------ | ---------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| 广播可见     | 扫描工具看到设备广播，Discriminator 与包装一致 | 扫不到广播；或广播在但连不上                          | nRF Connect for Mobile 扫描（看设备名/Discriminator）                                                              |
| 广播参数     | 广播间隔稳定、类型符合可连接要求               | 广播间隔过长（省电固件配置激进）导致 App 扫描窗口错过 | nRF Connect 看广播间隔；对照固件广播配置                                                                           |
| BLE 连接稳定 | 连接建立后 GATT 会话不掉                       | 连上几秒即断；反复连接-断开循环                       | Android 开发者选项开 HCI snoop log，方法同 [[ble-debug-ch05-connection-parameters\|蓝牙调试（五）]] 的连接参数分析 |
| 连接参数协商 | 手机侧参数请求被接受，间隔合理                 | 参数更新被拒后掉线；或间隔被拉大到事务超时            | HCI log 看连接参数更新过程（蓝牙调试（五）口径）                                                                   |
| PASE 建立    | App 日志显示 secure session/PASE established   | BLE 明明连着，Matter 会话起不来                       | 核对 PASSCODE/Discriminator 是否用错（扫了旧码、包装码与固件不一致）                                               |

这一段的取证手法全部复用蓝牙系列：连接间隔是否被手机侧省电拉大、RSSI 是否临界、广播类型与间隔——不重抄，遇到 BLE 层问题直接按 [[ble-debug-ch05-connection-parameters|蓝牙调试（五）]] 的清单走。

### 阶段二：Thread 入网（凭证下发 → attach）

| 取证点       | 成功标志                                                       | 失败特征                                            | 工具/方法                                             |
| ------------ | -------------------------------------------------------------- | --------------------------------------------------- | ----------------------------------------------------- |
| 凭证写入     | 设备侧日志显示收到网络凭证并开始 attach                        | 写入阶段就报错（注意区分 BLE 断在写之前还是写之后） | 设备串口日志 / ot-cli 日志等级调高（第二章方法）      |
| attach 完成  | 设备侧 state 从 detached → child/router；RLOC 与 ML-EID 已分配 | 卡在 detached；反复 scan-join-fail 循环             | 设备侧 `state`、`dataset active` 逐项核对             |
| dataset 一致 | 与 OTBR 侧 `dataset active -x` 输出的关键字段逐项相同          | PAN ID/信道/主密钥/扩展 PAN ID 任一不一致           | 两侧各跑一次导出，逐字段 diff——第四章的 dataset 纪律  |
| mesh 可达    | OTBR 侧能 ping 通设备 ML-EID；mesh 路由正常                    | 设备 state 正常但 ping 不通                         | OTBR 侧 ot-ctl 命令 + 第三章空口抓包看 MLE 交互       |
| 入网后稳定   | attach 后 state 持续稳定，不反复掉线                           | 上线几秒又掉回 detached                             | 抓包看是 MLE 拒绝（配置问题）还是链路丢帧（射频问题） |

死法二的标准动作：**设备侧 dataset 与 OTBR 侧 dataset 各导出一份做 diff**。App 下发的 dataset 来自 OTBR（生态 App 通常从 Border Router 拉取），任何一侧配置被手动动过（换信道、重建网络），旧 dataset 就成了毒药。

### 阶段三：Matter onboarding（CASE 会话 → 证书校验 → 完成）

| 取证点    | 成功标志                                    | 失败特征                                           | 工具/方法                                                                               |
| --------- | ------------------------------------------- | -------------------------------------------------- | --------------------------------------------------------------------------------------- |
| CASE 建立 | App/控制器日志显示 CASE session established | 设备已入网但 CASE 反复超时                         | chip-tool 配对日志（见下）                                                              |
| 发现路径  | 控制器能发现设备的操作地址（经 OTBR/mDNS）  | 发现不到设备——控制器与设备不在可达路径上           | 第六章的 mDNS/发现路径取证                                                              |
| 证书校验  | Device Attestation 通过                     | 证书链/DAC 校验失败报错                            | 日志关键行定位；概念级排查（换正式 DAC/核对 certification declaration），不展开证书工程 |
| ACL 配置  | 配对完成提示；控制指令可达                  | 配对完成但控制时灵时不灵——那是出网问题，先别混进来 | 第六章取证                                                                              |

chip-tool 侧排查时把日志等级拉高，关注关键行（**格式示意，非逐字实录**）：

```text
# chip-tool 配对，日志等级调到 detail（格式示意）
$ chip-tool pairing code <nodeid> MT:-24J0AFN00KA0648G00
  [CLI] Discovering commissionable node          ← BLE 阶段开始
  [BLE] Remote device found, discriminator match ← 广播命中
  [BLE] Connection established                   ← BLE 连接成功
  [SC] Secure Session Established ... PASE       ← 阶段一通过
  [BLE] Sending network credentials              ← 下发 dataset
  [DIS] Waiting for device to join network ...   ← 等待设备入网（阶段二窗口）
  [SC] CASE establishing with ...                ← 阶段二通过后才到这里
  [SC] Secure Session Established ... CASE       ← 阶段三核心节点
  [ZCL] Commissioning complete                   ← 全流程通过
```

这张示意日志的价值在于**把「卡在哪一行」翻译成「死在哪个阶段」**：卡在 PASE 前是 BLE 问题；PASE 过了、CASE 起不来，是 Thread 入网或 mesh 可达问题；CASE 过了还在报错，是证书/ACL 层问题。排查顺序从此有了坐标轴。

把三阶段与三世界、与本书各章对上，就是这张坐标表：

| 配网阶段           | 死法         | 所属世界             | 深查章节                                                 |
| ------------------ | ------------ | -------------------- | -------------------------------------------------------- |
| BLE 广播/连接/PASE | 死法一       | 蓝牙世界（跨界）     | [[ble-debug-ch05-connection-parameters\|蓝牙调试（五）]] |
| 凭证下发 + attach  | 死法二       | 网络/设备世界        | 第四章                                                   |
| CASE + 证书 + ACL  | 死法三       | 边界世界             | 第六章、第十章 10.4                                      |
| 配对完成后的控制   | 不算配网失败 | 边界世界（出网路径） | 第六章                                                   |

## 10.4 常见失败 TOP：三种死法的头号根因

### TOP 1：BLE 阶段断连（手机省电 / 信号）

| 环节     | 内容                                                                                                                                                                                                                                   |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 失败机理 | 手机侧为省电对 BLE 连接参数有激进要求（[[ble-debug-ch05-connection-parameters\|蓝牙调试（五）]] 讲过连接间隔协商）；设备若不支持手机的参数请求，或现场 2.4G 拥挤导致丢包，长事务（下发 dataset + 等待 attach，可能持续数十秒）中途断链 |
| 典型特征 | 断点总在「下发凭证」前后；Android 的 HCI snoop log 里可见连接参数更新请求或断连原因；靠近设备/关 WiFi 后成功率波动性提高                                                                                                               |
| 对策     | 设备固件接受合理的连接参数更新请求；缩短 BLE 阶段的事务时长；配网指引让用户靠近设备；App 侧重试逻辑覆盖断链重连                                                                                                                        |

### TOP 2：dataset 下发后 attach 失败

| 环节     | 内容                                                                                                                                                                                                                                                                                                      |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 失败机理 | 三类：① dataset 本身不一致——OTBR 重建过网络/手动改过信道，App 缓存或拉取到的 dataset 与实际网络不符；② OTBR 侧网络没问题但设备射频临界（第九章的灵敏度/共存问题——WiFi 强干扰下 2.4G 的 802.15.4 信道丢 MLE 帧）；③ OTBR 虽然活着但 mesh 侧异常（Leader 选举震荡，第八章），设备 attach 上去了网络却不收敛 |
| 典型特征 | 设备 state 卡 detached、或 router/child 后马上又掉；空口抓包能看到 MLE 帧但拿不到应答（射频临界）或根本看不到目标网络的 MLE 交互（信道/密钥不对）                                                                                                                                                         |
| 对策     | 先做两侧 dataset diff（免费）；再让设备靠近 OTBR 排除射频临界；最后按第四、五章查 OTBR 侧 mesh 状态                                                                                                                                                                                                       |

### TOP 3：CASE 会话超时

| 环节     | 内容                                                                                                                                                                                                                                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 失败机理 | 设备已入网，App 要经 OTBR 与设备建 CASE。超时的常见方向：① 路径不通——手机在另一网段/路由器隔离了 mDNS 发现（第六章的 mDNS 内容），控制器找不到设备的操作地址；② 时钟问题——证书有效期校验依赖时间，设备时钟异常会导致证书校验失败（概念级，以 Matter 规范口径为准）；③ 证书宣称问题——DAC/certification declaration 配置与产品宣称不符（量产前的工程样机常见） |
| 典型特征 | 设备在 mesh 里在线、可 ping 通 ML-EID，但配对最后一步超时；chip-tool 卡在 CASE establishing 一行                                                                                                                                                                                                                                                             |
| 对策     | 先证 mesh 可达（ping ML-EID）；再查控制器与设备是否真的经 OTBR 互通（第六章的出网/发现路径）；证书类问题对照产品认证资料核对，不在现场硬啃                                                                                                                                                                                                                   |

### 三种死法的分界判据一句话

| 死法   | 一句话判据                                          |
| ------ | --------------------------------------------------- |
| 死法一 | BLE 会话没建立或中途断——App 日志无 PASE established |
| 死法二 | PASE 建立了，设备 state 没到 child/router           |
| 死法三 | 设备 state 正常且 mesh 可达，CASE 起不来或校验失败  |

每个 TOP 的最小取证动作清单（按成本从低到高）：

| TOP   | 第一动作（¥0）                | 第二动作                     | 第三动作                   |
| ----- | ----------------------------- | ---------------------------- | -------------------------- |
| TOP 1 | 换手机/靠近设备对照           | nRF Connect 看广播与连接参数 | HCI snoop log 分析         |
| TOP 2 | 两侧 `dataset active -x` diff | 设备靠近 OTBR 复测           | 空口抓包看 MLE 交互        |
| TOP 3 | ping 设备 ML-EID 证 mesh 可达 | 对照「网内直控 vs 外网回程」 | chip-tool 日志 CASE 段定位 |

## 10.5 互操作视角：不同生态 App 的排查差异

同一台设备，三个生态的配网体验与排查要点并不相同：

| 生态         | 配网路径特点                                                       | 排查注意                                                                                                                                           |
| ------------ | ------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Google Home  | App 内引导扫码，Thread 凭证经手机从 OTBR/生态侧获取                | 确认手机与 OTBR 在同一局域网且 mDNS 未被隔离；Google 侧 Thread 边界路由角色（如 Google Hub 兼当 BR）与自建 OTBR 的关系要理清——**谁在提供 dataset** |
| Apple 家庭   | 依赖苹果家庭控制器架构；HomePod/Apple TV 可兼 Thread Border Router | 设备若被 Apple 生态的 BR 吸走，你自建 OTBR 的网络可能不是它入的那个网——先确认设备到底在哪个 Thread 网络（两侧 dataset diff）                       |
| Amazon Alexa | Echo 设备兼 Border Router 的场景常见                               | 同上：多 BR 环境下「设备在哪个网」是第一问；Echo 的 Thread 网络与你自建网络的 dataset 不同则永远配不上                                             |

多 BR 环境的一条铁律：**配网失败第一问不是「为什么失败」，而是「这个网络里有几个 BR、设备想加入哪个」**。家里同时有 Google Hub 和自建 OTBR 时，两个 Thread 网络（两套 dataset）并存是完全可能的，设备被拉进其中一个，你的取证就要换到那个网络的视角。

第二个要问的问题是「dataset 是谁提供的」：生态 App 拉取 dataset 的来源（自建 OTBR、生态 BR、还是手机缓存的旧数据）决定了「网络侧改了配置，App 什么时候才知道」——凡是「网络侧明明改好了、App 还是配不上」的现象，先怀疑 dataset 供给链路（第六章的 BR 职责），而不是设备。

互操作排查的通用注意：

| 注意点       | 说明                                                                       |
| ------------ | -------------------------------------------------------------------------- |
| App 版本     | 生态 App 更新频繁，行为可能随版本变化；复测前记录 App 版本号               |
| 手机系统版本 | 同一 App 在不同系统版本上的 BLE 栈行为可能不同（尤其 Android 厂商定制）    |
| 权限         | 定位/蓝牙权限未授予时 App 可能静默扫不到设备——先查权限再查协议             |
| 复现记录     | 每次失败记录「App+系统+手机型号+失败卡点」四元组，互操作问题的对照表就靠它 |

## 10.6 教学案例：三阶段分解定位到 Thread 阶段

> 教学复盘案例，取材自常见故障模式综述。

| 环节       | 内容                                                                                                                                                                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象       | 工程样机用生态 App 配网，反复失败；同批次另一台用同样流程一次成功                                                                                                                                                                                                                      |
| 弯路一     | 先怀疑 BLE：换手机、贴近设备、关 WiFi——部分尝试成功率提高但从不稳定。**教训**：「有时能过」说明 BLE 链路不是主瓶颈，却花了两轮在换手机上                                                                                                                                               |
| 弯路二     | 怀疑设备固件 Matter 栈：重刷固件、核对 VID/PID 与二维码——无效。**教训**：没先做阶段分解，在第三阶段的问题上折腾第一阶段的假设                                                                                                                                                          |
| 转折点证据 | 按三阶段取证：chip-tool 日志（格式示意）显示 PASE 稳定建立、网络凭证发送后卡死在 CASE 阶段——**死法二**；设备侧 `state` 反复在 detached；两侧 dataset diff 发现**主密钥不一致**——坏板曾手动加入过另一个测试网络，App 下发的 dataset 与设备残留的 active dataset 冲突，attach 每次都被拒 |
| 根因       | 设备残留旧测试网络的 active dataset，与生态 App 下发的 OTBR dataset 不一致；attach 阶段按 MLE 拒绝，App 只报「添加失败」                                                                                                                                                               |
| 对策       | 工程阶段：复测前统一执行 `factoryreset` 清掉残留 dataset；产线侧：配网测试前增加 dataset 状态检查步骤                                                                                                                                                                                  |
| 预防       | 「换网复测必 factoryreset」写进团队 checklist；两块板复用做实验时，谁最后碰过 dataset 要有记录——这正是第四章 dataset 纪律在 Matter 配网场景的直接延伸                                                                                                                                  |

复盘一句话：**三阶段分解的价值不是理论好看，而是把「App 说失败」翻译成「日志卡在第几行」**——卡点定位了，根因自然浮出来。

> [!tip] 转折点形态小结
> 第十章的转折点证据与第十二章三个案例一样，都是「换一种观测方式后信号才从噪声里出来」：本章是「按日志卡点分层」，案例手册里还有「抓包按层切开」「多点同时取证」「双时间线对齐」——形态不同，本质相同：**单一视角看随机，换视角看条件**。

## 10.7 收尾：配网失败分诊速查表

| 现象/卡点              | 首判断定  | 第一个动作                                   | 深查去向                                                      |
| ---------------------- | --------- | -------------------------------------------- | ------------------------------------------------------------- |
| App 扫不到设备         | 死法一    | nRF Connect 看广播与 Discriminator           | [[ble-debug-ch05-connection-parameters\|蓝牙调试（五）]]      |
| 广播在、连上就断       | 死法一    | HCI snoop log 看断连原因与连接参数           | 蓝牙调试（五）                                                |
| BLE 稳定但 PASE 起不来 | 一/三交界 | 核对二维码 payload（Discriminator/PASSCODE） | Matter 规范 onboarding 章节                                   |
| 凭证下发后卡 detached  | 死法二    | 两侧 `dataset active -x` diff                | [[thread-debug-ch04-network-formation-commissioning\|第四章]] |
| attach 成功又掉        | 死法二    | 空口抓包看 MLE 交互；设备远离干扰源复测      | 第三章、第九章                                                |
| 设备在线但 CASE 超时   | 死法三    | OTBR 侧 ping 设备 ML-EID 证可达              | [[thread-debug-ch06-border-router\|第六章]]                   |
| CASE 过但控制不稳      | 出网问题  | 别按配网查——按第六章出网路径查               | 第六章                                                        |
| 多 BR 家庭配不上       | 环境问题  | 先问「设备被拉进了哪个 Thread 网络」         | 10.5                                                          |

> [!tip] 一句话带走
> 配网排查的全部秘密就一条：**别信 App 的报错文案，信每个阶段自己的成功标志**——PASE established、state 到 child/router、CASE established，三个里程碑逐个验，死在哪一格一目了然。
