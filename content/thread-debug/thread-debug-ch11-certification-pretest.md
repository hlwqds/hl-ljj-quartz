## 11.1 认证体系：两条线，别混着排期

做一个 Thread/Matter 产品，出厂前要过的认证其实是**两条独立的线**，很多团队第一次排期时把它们搅在一起，预算和周期全算错：

```text
线一：协议/生态认证（技术联盟线）
  Thread Certified Component ──► Thread Certified Product（产品级）
  Matter 认证（CSA）─────────► 生态准入（Apple/Google/Amazon 可信接入）
  谁管：Thread Group / CSA Connectivity Standards Alliance
  测什么：协议一致性 + 互操作性 + 少量 RF 性能项

线二：国别射频法规（政府监管线）
  FCC（美国）/ CE-RED（欧盟）/ SRRC（中国大陆）……
  谁管：各国监管机构
  测什么：发射功率、杂散、带宽、频谱模板——与协议无关，只看射频物理层
```

两条线的关系一句话：**法规线不管你会不会说 Thread，联盟线不管你吵不吵到邻居**。协议认证通过了不代表射频合规，射频合规了不代表设备真的会跑 Thread 协议——两套测试互不替代，都要做。

两条线的交付物也不同：法规线交付的是**各国监管的证书/报告**（市场准入的门票），联盟线交付的是**认证标识与生态准入资格**（产品能挂 Thread/Matter logo、进生态配网体系的前提）。混了线的最典型事故：以为「过了认证」就能上市，结果只有联盟证书没有目标市场法规证书（或反之）——排期与预算双双爆雷。概念框架（FCC/CE/SRRC 各管什么、限值逻辑、模组认证复用边界）[[ch17-certification-regulations|射频入门（十七）]] 与 [[wifi-hw-debug-ch11-precompliance|WiFi 调试（十一）]] 已经完整建立过——方法论完全同构，本章不重复，只讲 Thread 特有的部分。

Thread 与 Matter 认证的顺序关系：

| 认证                       | 说明                                     | 顺序意义                                                      |
| -------------------------- | ---------------------------------------- | ------------------------------------------------------------- |
| Thread Certified Component | 芯片/模组/栈通过 Thread Group 的组件认证 | 通常由芯片厂商完成，产品团队**复用**其结果                    |
| Thread Certified Product   | 整机产品级认证                           | 基于 Component 的成果做产品级测试                             |
| Matter 认证（CSA）         | 设备成为 Matter 可信节点                 | Thread 连接层就绪后才有意义；量产固件 + 正式 DAC 证书链是前提 |

一条实务上的依赖链值得记住：**芯片/模组厂商的 Component 认证是你产品认证的地基**。选型期就要确认：目标芯片的 Component 认证状态、覆盖的 Thread 规范版本、以及厂商 Matter SDK 版本与认证的对应关系——这三件事任何一个有缺口，你的送测范围都会膨胀（从「复用成果」退化成「从栈开始测」），费用和周期完全不是一个量级。

典型产品的认证时间线（概念示意，各项周期以当期政策为准）：

```text
选型期 ──► 确认芯片 Component 认证状态 / Matter SDK 版本对应关系
  │
工程期 ──► 固件开发 + 本地一致性预跑（THCI）
  │        + 三厂商互操作冒烟（11.4）+ RF 传导预测试（11.3）
  ▼
送测期 ──► 法规线：目标市场逐个送（FCC/CE/SRRC 排期可并行）
  │        联盟线：Thread Product 认证 → Matter 认证
  ▼
量产 ────► 固件/天线/结构任何变更 → 重新评估两条线的认证有效性
```

实务口径：认证政策与流程细节**必须向 Thread Group / CSA 当期文件与芯片厂商索取书面说明**——你的产品认证建立在哪些已认证成果之上、有没有时效限制，直接决定送测范围与费用。政策更新频繁，本节不展开流程细节（避免过期口径）。

## 11.2 Thread 认证测什么

Thread 认证的测试内容大致三类，预测试策略各不相同：

| 类别       | 测什么                                                                                                      | 怎么测（概念）                                                                         | 预测试可行性                                                           |
| ---------- | ----------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 协议一致性 | 协议行为是否符合 Thread Specification（MLE、CoAP/网络数据、地址分配、SED 行为……按设备角色 FTD/MTD/BR 分项） | Test Harness（认证测试台）+ THCI（Test Harness Control Interface）驱动被测设备执行用例 | **高**——THCI 固件 + 开源测试框架可在本地预跑多数用例                   |
| 互操作性   | 与其他厂商设备组网是否正常：多厂商组网测试床，混搭不同厂商的 Router/SED/BR                                  | 测试床按场景脚本执行（组网、路由收敛、SED 调度、跨厂商控制）                           | **中**——无法完全复刻官方测试床，但可用多厂商真实设备做冒烟预演（11.4） |
| RF 性能项  | 灵敏度、抗邻道干扰、CSMA 行为等（以 Thread Group 当期测试计划为准，项数与限值「待核对」）                   | 传导环境下的标准化测量                                                                 | **高**——与第九章的射频方法直接衔接                                     |

对工程团队的实际意义：三类里**一致性是可以提前大规模自测的**（这也是 Thread 认证工具链开源化的红利），互操作性靠多厂商设备预演兜底，RF 项靠传导预测试兜底。三者都排过了，送测的意外就只剩「测试床环境差异」这一类。

一致性预跑的最小环境：

| 组件                | 作用                             | 说明                                                      |
| ------------------- | -------------------------------- | --------------------------------------------------------- |
| THCI 固件           | 让被测设备接受测试框架的指令驱动 | OpenThread 固件带 THCI 支持；版本与测试框架匹配           |
| 测试框架/自动化环境 | 逐条执行一致性用例、收集结果     | OpenThread 侧有开源自动化测试资产可参考（以官方仓库为准） |
| 参考设备            | 与被测设备组网的对端             | 用另一块开发板即可起步                                    |
| 结果记录            | 用例通过/失败清单                | fail 的用例按第一章的五分类归位，再决定是否可修           |

预跑的价值排序：**先跑被测角色核心路径的用例**（FTD 的组网/路由、MTD 的 SED 行为、BR 的前缀分发），再铺长尾——系统性 fail（如某类消息格式错误）会在核心路径就暴露，没必要等全量跑完才知道。

按产品角色的测试侧重：

| 角色               | 一致性侧重            | 互操作侧重              | RF 侧重             |
| ------------------ | --------------------- | ----------------------- | ------------------- |
| FTD（Router 能力） | 组网/路由/MLE 行为    | Router 间互通、选举接管 | 发射功率/灵敏度全项 |
| MTD（SED）         | poll/CSL/child 行为   | 混网中的 SED 调度       | 峰值发射 + 低功耗态 |
| BR（OTBR 类产品）  | 前缀分发/NAT64/多链路 | 与多厂商网络的边界行为  | 同 FTD + 长期稳定   |

## 11.3 RF 预测试：802.15.4 项目的测法与常见 fail

### 预测试项目与方法

方法论的完整版在两处：物理层概念与灵敏度/邻道在 [[thread-debug-ch09-802154-rf-phy|第九章]]，传导测试的仪器操作路线在 [[wifi-hw-debug-ch07-phy-measurements|WiFi 调试（七）]]——同样的频谱仪、同样的传导口径，只是把被测对象换成 802.15.4 信道 11-26。这里只给 Thread 特有的速查表：

| 预测试项       | 测什么                             | 方法要点                                                                                                              | 判据口径                                                                  |
| -------------- | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| 各信道发射功率 | 信道 11-26 逐信道传导功率          | 测试模式固件锁定信道 + 连续发射；频谱仪信道功率测量；**注意天线增益要算进 EIRP 预算**（WiFi 十一章 TOP 4 的同款错误） | 法规限值（以对应法规文件为准，待核对）                                    |
| 占用带宽       | O-QPSK 信号的 2 MHz 标称带宽是否超 | 频谱仪 OBW 功能                                                                                                       | 授权带宽内                                                                |
| 频谱模板/带外  | 主瓣滚降与邻道泄漏                 | 频谱模板比对                                                                                                          | 以法规/标准模板为准                                                       |
| 传导杂散       | 谐波与寄生分量宽扫                 | 几十 MHz 到谐波可及范围；重点看晶振谐波族                                                                             | 对照限值线                                                                |
| 频率容限       | 载波频偏                           | 频谱仪测中心频率偏差                                                                                                  | 802.15.4 规范容差 ±40 ppm（IEEE 802.15.4 口径，量级核对以标准原文为准）   |
| 灵敏度         | PER=1% 时的最小输入电平            | 信号源 + 衰减器打标定包（第九章方法）                                                                                 | -85 dBm @ 250 kbps O-QPSK 2.4G（规范最低要求；实测余量以 datasheet 为准） |

传导预测试的执行顺序（每台样机走一遍，逐信道记录）：

```text
测试模式固件（连续发射/锁信道）
   │
   ├─ ① 信道 11 → 频谱仪：信道功率 ──► EIRP 预算表
   ├─ ② 同信道：OBW ────────────► 带宽判据
   ├─ ③ 同信道：频谱模板 ────────► 模板框内
   ├─ ④ 宽扫：传导杂散 ─────────► 限值线；找时钟谐波族
   ├─ ⑤ 测中心频率偏差 ─────────► ±40 ppm 口径
   ├─ ⑥ 信道 12 … 26 重复 ①-⑤
   └─ ⑦ 换样机（装配态/裸板各一轮）──► 对比记录
```

### 常见 fail 与对策

按 WiFi 十一章的同款框架，802.15.4 侧的高频 fail：

| Fail 项              | 失败机理                                                                               | 第一动作（免费）                                                      | 第二动作（花小钱）                                                                               |
| -------------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 杂散超标（时钟谐波） | MCU/晶振谐波经天线馈线辐射——机理与 WiFi 完全同构                                       | 布局审查（时钟线远离馈线）、屏蔽罩接地、晶振包地                      | 频谱仪宽扫复测；对策表直接复用 [[wifi-hw-debug-ch11-precompliance\|WiFi 调试（十一）]] 11.4      |
| 频偏超差             | 802.15.4 对频偏更敏感（窄带 2 MHz 信道 + ±40 ppm 容差），晶振选型/负载电容失配直接超差 | 核对晶振规格与负载电容配置                                            | 温箱验证（[[ch11-crystal-clock\|射频入门（十一）]]）；注意温漂——常温合格、高低温超差是经典翻车点 |
| 频谱模板/邻道泄漏    | 发射功率推满导致频谱再生；EVM 劣化扩散频谱                                             | 回调功率、查供电跌落                                                  | 频谱仪实测模板                                                                                   |
| 天线失谐连锁         | 装配态天线失谐 → 辐射效率掉 + 带外能量抬升，杂散与灵敏度双双劣化                       | 净空审查（[[wifi-hw-debug-ch08-antenna-structure\|WiFi 调试（八）]]） | 装配态复测而非裸板测；VSWR/降级装配态对比法                                                      |

一句话记忆：**802.15.4 的 RF 预测试是 WiFi 预测试的窄带版**——项更少、带宽更窄，但频偏容差更苛刻、装配态敏感性不减。做过 WiFi 预测试的团队上手很快，容易翻车的是「以为一样就照抄限值」。同构的是方法，不同的是数字：

| 维度       | WiFi（2.4G）            | 802.15.4（2.4G）              | 排查含义                   |
| ---------- | ----------------------- | ----------------------------- | -------------------------- |
| 信号带宽   | 20/40 MHz 起            | 2 MHz                         | 模板刻度完全不同，别套用   |
| 频偏容差   | 数十 ppm 量级（按标准） | ±40 ppm（规范口径）           | 窄带下频偏余量更紧         |
| 信道数     | 1-13（按地区）          | 11-26                         | 逐信道测的工作量更小但别漏 |
| 灵敏度要求 | 按速率分档              | -85 dBm 最低线（规范）        | 判据更单一，但余量更重要   |
| 共存对象   | 邻居 WiFi/微波炉        | 同频段的 WiFi/BLE/Zigbee 全家 | 信道策略更拥挤（第九章）   |

还有一点隐性差异值得记一笔：802.15.4 设备多为电池供电产品，预测试时别只测「满电满功率」态——低电量态下的发射性能（功放供电余量）也是量产一致性的常见薄弱点，虽然多数认证只要求标称供电态，工程侧仍建议自测覆盖（按项目定义，待核对）。

## 11.4 送测准备

| 准备项       | 要点                                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 样机         | 按认证机构/测试计划要求准备数量与状态（含 RF 测试口引出版本）；数量与形态「待核对」——以当期 Thread Group / CSA 流程文件为准 |
| 测试模式固件 | THCI 固件（一致性用）+ 连续发射/锁信道工程固件（RF 用）；确认认证机构认可你们的固件入口                                     |
| 文档清单     | 产品规格、Thread/Matter 版本宣称、所用芯片/模组的 Component 认证编号、DAC 证书资料（Matter）、天线增益说明、用户手册        |
| 环境自建     | 一致性预跑：测试框架 + THCI；互操作预演：见下方冒烟清单                                                                     |
| 排期沟通     | 与实验室对齐：目标市场（法规线）、认证级别（联盟线）、SDK 版本、被测角色（FTD/MTD/BR 分开算）                               |

文档清单展开成一张勾选表（送测包逐项核对）：

| 文档                     | 用途                   | 备注                                                                  |
| ------------------------ | ---------------------- | --------------------------------------------------------------------- |
| 产品规格书               | 被测功能与宣称范围     | 与固件实际行为一致（WiFi 十一章的经验：机构测的是「说明书里的产品」） |
| Thread/Matter 版本宣称   | 确定适用规范版本       | 与芯片厂商 SDK release 对应                                           |
| Component 认证编号与副本 | 复用厂商成果的凭证     | 向芯片/模组厂商索取                                                   |
| DAC 证书与宣称资料       | Matter 设备证明        | 工程样机与量产证书要分清                                              |
| 天线规格与增益说明       | EIRP 预算依据          | 换过天线必须更新                                                      |
| 用户手册                 | 机构按手册确定测试模式 | 文档没写的模式不会被测                                                |

### 低成本互操作预测试：三厂商冒烟清单

没有官方测试床，也能用真机做方向性预演——目标是「和不同厂商的设备组过网、跑过基本场景」，把互操作性层面的低级问题（如对某厂商 BR 的网络数据处理不兼容）在送测前暴露。

冒烟环境的最低配置（比想象中便宜）：

| 设备                        | 角色                              | 来源                    |
| --------------------------- | --------------------------------- | ----------------------- |
| 开发板 ×2（不同厂商芯片）   | 被测 + 对端（Leader/Router 互换） | 团队常备                |
| 市售成品 Thread 设备 1-2 台 | 第三厂商真机                      | 智能灯/插座类，零售可购 |
| 树莓派 + OTBR               | BR 与抓包/取证中枢                | 第二、六章环境复用      |
| sniffer 板 + Wireshark      | 空口取证                          | 第三章环境复用          |

| #   | 冒烟项                                           | 判据                                              |
| --- | ------------------------------------------------ | ------------------------------------------------- |
| 1   | 厂商 A 芯片做 Leader + 厂商 B 板做 Router attach | state 正常收敛，无反复分区                        |
| 2   | 加入厂商 C 的成品设备（市售智能灯/插座类）       | 设备上线且网络数据同步正常                        |
| 3   | A 控制经 mesh 控制跨厂商设备                     | 端到端指令可达、延迟可解释                        |
| 4   | 混入 1 台 SED（厂商 B 固件跑 MTD/sed 角色）      | SED 正常 poll/CSL 调度，不掉线（第七章判据）      |
| 5   | OTBR（树莓派）作为 BR 加入多厂商网络             | 前缀分发正常，mesh 内设备可出网（第六章判据）     |
| 6   | 断电 Leader 后 Router 接管                       | 选举在秒级完成、拓扑收敛（第五章判据）            |
| 7   | 全程开 2.4G WiFi 干扰源                          | 无大规模掉线；CSMA 退避行为正常（第九章共存判据） |

七项全绿，互操作性层面的大坑基本排掉；剩下的差异属于官方测试床的脚本细节，交给认证机构处理。

冒烟时的记录纪律（和第十二章的证据记录卡同一套逻辑）：

| 记录项       | 内容                                       |
| ------------ | ------------------------------------------ |
| 组网阵容     | 哪家芯片当 Leader/Router/SED/BR，固件版本  |
| 现象与时间线 | 每个异常的时间点、复现步骤                 |
| 证据文件     | 抓包文件名、日志文件名、ot-cli 导出        |
| 整改结论     | 修了什么、复测是否通过——失败过的项也要留档 |

### 预测试能排掉 vs 排不掉的问题

诚实划界，避免「我自查过了为什么还挂」的错觉：

| 能排掉（预测试覆盖）                        | 排不掉（必须实验室/认证机构）    |
| ------------------------------------------- | -------------------------------- |
| 一致性用例的系统性 fail（本地预跑直接暴露） | 官方测试床环境差异导致的偶发问题 |
| 多厂商组网的低级不兼容（冒烟清单覆盖）      | 官方互操作测试的完整场景矩阵     |
| RF 传导项：功率/OBW/模板/杂散/频偏/灵敏度   | 辐射杂散的准确判定（需暗室）     |
| 设计侧低级错误（净空、接地、滤波缺失）      | 正式证书与报告本身               |

如果仍然 fail：按 WiFi 十一章 11.1 的代价账处理——先定位是哪条线挂（法规线 fail 走整改-复测流程；联盟线 fail 按认证机构的整改意见走），评估「修」与「降宣称」（比如缩减支持的信道/角色重新申报）两条路径的成本，再决定。fail 不可怕，可怕的是 fail 了没有预案、在排期表上裸奔。

这张 checklist 的使用口径与 WiFi 十一章同源：前几行在立项期完成，中段在工程期持续维护，最后几行是送测前的最后一道闸。任何一项「暂时做不了」都要写明原因与补做时点——空白项不是跳过的理由，是风险的延期支付。

第 1-3 行是立项期的事，第 4-5 行是工程期就能做的免费预演，第 6-10 行是 RF 预测试闸门，第 11-13 行是送测动作本身。**十三项全绿再送测**——不是仪式感，是把「认证 fail = 排期与预算的双重损失」这笔账，在送测前一笔一笔关掉。

> [!tip] 一条提醒
> 认证不是一个「项目结束时的事件」，而是贯穿选型期（Component 复用确认）→ 工程期（预跑/冒烟/RF 预测试）→ 送测期（材料与环境）的持续状态。等到项目尾声才想起认证，能提前排掉的问题已经全部变成送测风险。
