## 12.1 一句话收回全系列的方法

十一章把产品送进了实验室；本章把你自己送出门——带着一套不依赖任何人的排障方法。

如果只允许用一句话概括全部十二章：

> **三世界取证缩小范围，dataset 优先核对，证据链锁定根因。**

拆开三层：

| 关键词       | 含义                                                                                                                    | 出自                                                          |
| ------------ | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 三世界取证   | 先判断问题在设备世界（OpenThread 栈）、网络世界（mesh 路由/拓扑）还是边界世界（OTBR/外网/配网），各世界配专属工具再下钻 | [[thread-debug-ch01-architecture-debug-map\|第一章]]          |
| dataset 优先 | 任何「连不上」，第一动作是两侧 `dataset active -x` 做 diff——一大半玄学只是两个 dataset 不一致                           | [[thread-debug-ch04-network-formation-commissioning\|第四章]] |
| 证据链       | 根因结论必须「症状吻合 + 独立证据 + 可复现」三要素齐全；抓包（第三章）与时间线对齐是最硬的两类证据                      | [[thread-debug-ch03-802154-sniffing\|第三章]]起所有案例章     |

取证成本的顺序也藏在三世界里：设备世界最便宜（`ot-cli` 一条命令的事），网络世界次之（要抓包、要对时），边界世界最贵（要动 OTBR 配置、要看家宽环境）。**从便宜的世界开始排除，证据随时允许你跳到贵的世界**——这是第一章「取证成本从低到高」的全系列落地版。

下面三个案例就是这套方法的完整走法，每个案例都诚实列出走过的**弯路**——弯路不是失败记录，是「哪条证据本可以更早拿到」的教材。

> [!note] 证据口径
> 三个案例均为**教学复盘案例，取材自常见故障模式综述**：现象、根因类型与取证路径在业界具有普遍性，具体数值（时间戳、RSSI、电流读数）不对应任何真实项目，一律不给虚构读数；命令与日志为格式示意。

## 12.2 三个端到端教学复盘案例

三个案例分别横跨组网（第四章）、边界（第六章）、低功耗（第七章）——正好是三世界各自最典型的纵深线。

### 案例一：新家居设备 joiner 失败（PSKd 输错 + dataset 不一致）

> 教学复盘案例，取材自常见故障模式综述。

| 环节       | 内容                                                                                                                                                                                                                                                                                                                                               |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象       | 用 OT Commissioner 给一块新板子入网，commissioner 端始终报 joiner 失败；换板子、换 USB 线、重刷固件都一样                                                                                                                                                                                                                                          |
| 弯路一     | 怀疑射频：把 joiner 板搬到 OTBR 旁边一米内重试——失败依旧。**教训**：距离改动无效本身就是证据（射频临界被排除），当时没记录                                                                                                                                                                                                                         |
| 弯路二     | 重刷 joiner 固件、核对固件版本——无效。在设备世界打转，因为「新板子连不上」看起来像板子的问题                                                                                                                                                                                                                                                       |
| 转折点证据 | 按第三章方法在空口抓包（解密用网络密钥）：**能看到 joiner 的扫描请求帧，但 commissioning 的 UDP 交互完全没有建立**——说明 joiner 至少「听得见」网络，问题不在物理层而在 commissioning 会话层。进一步核对：commissioner 侧 PSKd 与 joiner 固件里烧录的 PSKd **大小写不一致**；同时两侧 dataset diff 发现扩展 PAN ID 也不一致——测试同事中途重建过网络 |
| 根因       | 双重：① PSKd 输错导致 commissioning 握手认证失败；② joiner 残留旧 dataset，即使 PSKd 对了 attach 也会被拒。两个问题互相掩护——修正其一症状不变，制造了「改了没用」的假象                                                                                                                                                                            |
| 对策       | 统一 PSKd 为团队共享的配置文件单一来源；重建网络后同步分发新 dataset；复测前 joiner 一律 `factoryreset`                                                                                                                                                                                                                                            |
| 预防       | 「dataset diff + 凭证字符串 diff」作为入网失败的第一动作写进 checklist（第四章纪律）；跨网络复用的实验板建立 factoryreset 习惯                                                                                                                                                                                                                     |

**证据链复盘**：距离对照排除射频 → 抓包证明物理层可达、会话层未建立（把问题从「板子坏」变成「握手不成」）→ 两侧 diff 同时抓出 PSKd 与 dataset 两个独立根因。转折点是**抓包把问题按层切开**——没有这一步，两个叠加根因永远猜不出来。

### 案例二：App 远程控制时灵时不灵（OTBR 前缀/NAT64 链路不稳）

> 教学复盘案例，取材自常见故障模式综述。

| 环节       | 内容                                                                                                                                                                                                                                                                         |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 现象       | 设备入网正常、家里局域网内控制正常；但出门在外用 App 远程控制，时灵时不灵，失败时设备在 App 里显示离线，回家又「自己好了」                                                                                                                                                   |
| 弯路一     | 怀疑 Thread mesh 不稳：开了拓扑日志盯着看一周——mesh 内拓扑纹丝不动，设备 RLOC/ML-EID 稳定。**教训**：mesh 稳定这一证据早就可以把矛头推向边界世界，可惜先入为主盯着网内                                                                                                       |
| 弯路二     | 怀疑云服务：查生态 App 的服务状态页、重装 App——无效，且失败时刻服务状态正常                                                                                                                                                                                                  |
| 转折点证据 | 在失败窗口于家庭内网同时抓三处：手机与 OTBR 的连通、OTBR 的 NAT64/路由状态、设备在 mesh 内的可达性。发现失败时**手机到 OTBR 的链路正常、OTBR 的 NAT64 前缀状态异常（前缀周期性变化，旧地址未及时更新）**——设备的同步会话目标是基于旧前缀的地址，手机经外网回来的路径找不到它 |
| 根因       | OTBR 侧前缀分发配置与家宽环境的 RA 行为叠加，导致 NAT64 前缀/地址映射周期性失稳；局域网内走本地路径感知不到，只有外网回程路径暴露问题（第六章的出网/回程路径问题）                                                                                                           |
| 对策       | 固化 OTBR 前缀配置、核对路由通告参数与家宽环境兼容性；升级 OTBR 版本（该类前缀稳定性问题常见于版本修复清单，以 OpenThread release note 为准）；对时延敏感的控制路径优先考虑局域网内直达而非外网回环                                                                          |
| 预防       | 边界类问题的验收必须包含「外网回程路径」用例——局域网全绿不等于可用；OTBR 版本升级纳入变更管理，升级前后各跑一轮第六章的出网检查                                                                                                                                              |

**证据链复盘**：mesh 稳定（排除网络世界）→ 云服务正常（排除外部）→ **三处同时取证、只有 NAT64 前缀态异常**（唯一变化点即最大嫌疑）→ 机理与「在家正常出门失效」的现象完全吻合。这是三世界方法论的标准胜利：问题最终不修设备、不修 App，修在边界世界的配置上。

### 案例三：电池传感器隔周离线（child timeout 与 poll 周期配置）

> 教学复盘案例，取材自常见故障模式综述。

| 环节       | 内容                                                                                                                                                                                                                                                                                                         |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 现象       | 电池供电的温湿度传感器入网后正常，但大约每隔一两周从 App 里消失一次，需手动唤醒/复位才恢复；电池电量显示正常                                                                                                                                                                                                 |
| 弯路一     | 怀疑电池：换新电池、查电量曲线——电量充足，排除。**教训**：排除是对的，但「电量正常还掉线」已经暗示问题在通信节拍而不是能量                                                                                                                                                                                   |
| 弯路二     | 怀疑射频临界：安装点 RSSI 尚可（L1 口径），且掉线周期性出现而非随机——周期性现象与射频随机的衰落模型不符，此路不通                                                                                                                                                                                            |
| 转折点证据 | 在父节点（Router）侧开父子交互日志，对齐掉线时间线：**每次离线前，传感器的 data request 间隔都出现过一次明显拉长**，拉长后超过父节点配置的 child timeout 窗口，父节点把它从 child 表移除；设备侧核对发现固件的 poll 周期在某些低功耗状态下会超过 child timeout——第七章讲过的「两边节拍必须互相知道」被违反了 |
| 根因       | 设备侧 poll/CSL 周期与父节点 child timeout 配置失配：设备进入某个节能档后响应窗口超出父节点的容忍度，被父节点老化掉线；设备自身不知情，直到下次主动上报才被发现「失踪」                                                                                                                                      |
| 对策       | 统一配置：child timeout 与设备各节能档的 poll 周期满足「timeout > 数个 poll 周期」的余量关系（第七章口径）；设备侧增加离线检测与重新 attach 上报                                                                                                                                                             |
| 预防       | 电池产品的功耗调优（第七章）与网络侧超时配置必须**联调验收**：把「最深节能档跑满一个 child timeout 周期不掉线」列为出厂测试用例；配置参数写入产品规格，不留给固件工程师现场拍脑袋                                                                                                                            |

**证据链复盘**：电量排除 → 周期性（排除随机衰落）→ **父节点日志里 data request 间隔拉长与掉线时间对齐**（双时间线指认）→ 配置失配机理与现象周期吻合。周期性故障的通用打法再次生效：**先找周期，再问周期是谁的配置**。

### 转折点证据的三种形态

三个案例的转折点恰好是三种形态的取证武器，值得单独记一笔：

| 形态         | 案例                                        | 本质                             | 学到的动作                       |
| ------------ | ------------------------------------------- | -------------------------------- | -------------------------------- |
| 按层切开     | 案例一：抓包证明物理层可达、会话层未建立    | 把「一坨症状」切成「哪层坏了」   | 任何连不上，先抓包定层再动手     |
| 唯一异常点   | 案例二：三处同时观测，只有 NAT64 态异常     | 多点取证后，唯一变化点即最大嫌疑 | 拿不准就多点同时观测做差         |
| 双时间线对齐 | 案例三：data request 间隔拉长与掉线时刻对齐 | 两条独立来源的证据互相指认       | 单条证据定性嫌疑，交叉指认才定案 |

### 一页证据记录卡（现场模板）

排障时最贵的是「事后想不起来当时看到什么」。每个现场问题开工时先建一页记录卡：

```text
== 证据记录卡（Thread 版） ==
问题一句话：______________（现象 + 触发条件）
症状五分类：入不了网 / 网内不稳 / 出不了网 / 低功耗异常 / 配网认证（第一章）
当前世界：设备 / 网络 / 边界

时间线（每条复现必记）：
  [时间] [复现步骤] [观察到的现象] [同时采集的证据文件名]
  ...

dataset 记录（凡涉入网/配网必填）：
  设备侧 dataset active -x 导出：______
  对端（OTBR/父节点）侧导出：______
  diff 结果：一致 □ / 差异字段：______

已排除（对照实验记录）：
  变量：______ 改动：______ 结果：变好/变差/不变   ← 不变的也要记
  ...

嫌疑根因（按证据强度排序）：
  1. ____  支持证据：____  反对证据：____
  2. ...

转折点：______________（哪一条证据改变了排查方向）
结论三要素自检：症状吻合 □  独立证据 □  可复现 □
```

「已排除」栏最容易被省略，但它恰恰是弯路变教材的地方——案例一的搬距离、案例三的换电池，如果当时被记成对照实验结论，都能提前一步改写排查方向。

### 三个案例的公共结构

| 维度       | 案例一                           | 案例二                   | 案例三                  |
| ---------- | -------------------------------- | ------------------------ | ----------------------- |
| 世界       | 设备+网络（组网）                | 边界（OTBR/NAT64）       | 设备+网络（低功耗节拍） |
| 弯路共性   | 在错误的层反复重刷               | 盯着网内不看边界         | 把配置问题当能量问题    |

| 最终收口   | 配置单一来源 + factoryreset 纪律 | OTBR 配置固化 + 版本管理 | 超时与节拍联调验收      |

## 12.3 全系列调试 checklist（三世界 × 症状）

用法：先按症状选行，再按「三世界」顺序排除——设备世界最便宜（ot-cli 一条命令），网络世界次之（要抓包），边界世界最后（要动 OTBR/家宽）。判据中无公开出处的一律标「待核对/按项目定义」。

### 设备世界（OpenThread 栈）

| #   | 症状/检查点                       | 工具/命令                                 | 判据                                       | 章节            |
| --- | --------------------------------- | ----------------------------------------- | ------------------------------------------ | --------------- |
| 1   | 入不了网：attach 卡 detached      | `state`、`dataset active`、`factoryreset` | dataset 与对端逐字段一致；否则先 reset     | 四、12.2 案例一 |
| 2   | dataset 一致性（凡入网/配网问题） | 两侧 `dataset active -x`                  | PAN ID/信道/主密钥/扩展 PAN ID 逐项相同    | 四、十          |
| 3   | 角色与地址异常                    | `state`、`rloc16`、`extaddr`、`ipaddr`    | state 符合设计角色；ML-EID 已分配          | 五              |
| 4   | 邻居质量差                        | `neighbor table`、链路质量三档            | 无持续恶化的链路质量                       | 八              |
| 5   | 发送失败计数增长                  | `counters`（mac/CoAP 族）                 | 错误计数不持续增长                         | 二、八          |
| 6   | SED 节拍配置                      | `pollperiod`、CSL 参数                    | poll 周期与父节点 child timeout 有余量关系 | 七、12.2 案例三 |
| 7   | 日志等级与复位原因                | OpenThread 日志宏、复位原因寄存器         | 日志可读、复位原因可解释                   | 二              |
| 8   | 固件/SDK 版本                     | 版本查询命令                              | 与已知问题清单（release note）核对         | 二、十一        |
| 9   | 组网能力开关/角色配置             | `mode`、路由角色相关命令                  | 配置与产品宣称角色一致                     | 五、十一        |

### 网络世界（mesh 与空口）

| #   | 症状/检查点             | 工具/命令                               | 判据                                           | 章节            |
| --- | ----------------------- | --------------------------------------- | ---------------------------------------------- | --------------- |

| 13  | Router 选举异常         | `router table`、REED 状态               | 选举秒级完成；Router 数量在规范范围内          | 五              |

| 16  | 2.4G 共存干扰           | 抓包 + WiFi 环境对照（第九章信道策略）  | 信道避开 WiFi 主占用；CSMA 退避行为正常        | 九              |
| 17  | 射频临界                | 距离对照 + 抓包丢帧观察                 | 靠近 OTBR 后症状消失 → 链路预算问题            | 九、12.2 案例一 |
| 18  | 频偏/灵敏度（硬件怀疑） | 传导测试（第九/十一章方法）             | 频偏在 ±40 ppm 口径内；灵敏度余量正常          | 九、十一        |

### 边界世界（OTBR 与外网）

| #   | 症状/检查点        | 工具/命令                             | 判据                                   | 章节                |
| --- | ------------------ | ------------------------------------- | -------------------------------------- | ------------------- |
| 19  | OTBR 健康度        | `ot-ctl status`、服务日志             | BR 服务在跑；`br` 状态正常             | 六                  |

| 22  | 外网回程路径       | 外网侧访问 + OTBR 抓包（第六章路径）  | 回程可达；「在家正常出门失效」必查此项 | 六、12.2 案例二     |

**Thread 1.4 新特性跟踪**：Thread 规范在持续演进，1.4 一代重点关注的是更大规模的设备类型支持与网络侧增强（以 Thread Group 官方发布为准，具体特性清单此不展开避免过期口径）。实战建议是：把本系列学的 dataset、拓扑、SED 节拍三条主线当作「不随版本大变的底盘」，新版本发布后对照 release note 只看「哪些命令新增了、哪些默认值变了」——默认值变化（尤其 child timeout、CSL 相关）是升级后行为差异的第一嫌疑，老经验在升级翻车时照旧适用。

**Zigbee 对照阅读**：Zigbee 与 Thread 同住 802.15.4 物理层，但组网模型（Zigbee 的协调器/Cluster 树 vs Thread 的 IPv6 mesh）、应用层（ZCL vs 应用无关的 IP 化）差异很大。对照阅读的价值不在迁移知识，而在**理解「为什么 Matter 选了 IP 化的 Thread」**：地址体系（IPv6 vs 短地址）、与现有互联网设施的互通（无需应用层网关翻译）、以及生态边界（Thread 只管连接层，应用交给 Matter）。做过 Zigbee 的团队上手 Thread，最大的思维转换是「没有 coordinator 这个神，只有可替换的 Leader 和 BR」。

**射频工程师路线**：如果本系列让你对物理层产生了兴趣，路线与 WiFi 十二章 12.4 给出的一致：吃透 [[wifi-rf-hw|射频硬件入门]] 概念层 → 本系列第九、十一章的 802.15.4 实测层 → 系统学射频电路（S 参数、匹配、滤波器）→ 天线仿真与认证实验室实践。802.15.4 侧的差异化机会在**多协议共存设计**：2.4G 频段里 WiFi/BLE/802.15.4 同板共存的天线隔离与时分调度，是智能家居硬件绕不开的工程题，也恰好横跨本系列与两个姊妹系列的全部知识。

## 12.5 结语：回到第一章的三个世界

第一章开场画过那个三层世界的图。现在带着十二章的武器重走一遍——每界给一条最短复查路径：

**设备世界里，「设备连不上网」。** 当年你只会重刷固件。现在的路径：`dataset active` 与对端 diff（第四章纪律，12.2 案例一的转折点就藏在这里）→ `state` 看卡在哪个状态 → 邻居表看链路质量 → 都干净才怀疑固件与射频。重刷固件从第一反应降级为最后手段。

**网络世界里，「网内时通时断」。** 当年你只能换设备碰运气。现在的路径：抓包解密（第三章）确认 MLE 交互是否完整 → 拓扑日志看有没有分区与选举震荡（第五章）→ 计数器看重传与丢包趋势（第八章）→ 周期性现象先找周期（12.2 案例三的教训）。玄学从「随机」变成了「有条件触发」。

**边界世界里，「App 里设备时隐时现」。** 当年你怀疑过云服务、怀疑过 App、甚至怀疑过宽带运营商。现在的路径：mesh 内直控对照（第 26 行闸门，区分网内/边界）→ OTBR 前缀/NAT64/mDNS 三件套逐项查（第六章）→ 多 BR 环境先确认设备在哪个网络（第十章 10.5）。12.2 案例二里那台「在家正常出门失效」的设备，就是这条路径的标准毕业生。

三个世界，三次升级：从「换个东西试试」到「拿得出证据、下得了结论、防得住复发」。Thread 的调试没有魔法——**dataset 先 diff，三世界先定位，证据链再定案**。祝调试顺利，证据常在。系列完结，复习路线见 [[wifi-hw-debug|WiFi 硬件调试实战]] 与 [[ble-debug|蓝牙调试实战]]。
