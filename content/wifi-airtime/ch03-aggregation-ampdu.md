# WiFi 空口调度实战（三）：一次接入搬更多字节——聚合与 Block ACK

两台机器在同一个 AP 下互传图像、空口争抢严重——[[ch01-dcf-contention-basics|第一章]]的账本解释过为什么：每个包都要单独买门票（DIFS＋退避＋碰撞风险），发完再单独结账（SIFS＋ACK），固定税按包征收。[[ch02-measuring-airtime|第二章]]给了把空口看清楚的仪器。这一章回答下一个问题：**不改竞争规则、不动优先级，怎样把「赢一次能搬的字节」放大 N 倍**——机制是什么（3.1/3.2 的两种打包）、批量确认怎么做（3.3 的 Block ACK 会话）、收益到底多大（3.4 用 E3 的真实数字算账）、工程上拧哪里（3.5），以及这根杠杆的边界（3.6：它不解决优先级，也不解决速率）。

---

## 3.1 杠杆直觉：一张门票，搬 N 件货

先复习 [[ch01-dcf-contention-basics|第一章]]的三种时隙账。一次成功的单帧发送，在空口上的完整成本是：

```text
[ DIFS | 退避空闲时隙×m | 前导码+帧体 | SIFS | ACK ]
  ←───────── 竞争税 ─────────→ ←有效载荷→ ←── 确认税 ──→
```

前后两段是每个包必缴的「固定税」，中间才是真正搬的字节。互传图像的流量形态把这税放大了：TCP 把图像切成 MSS 量级（约 1.4KB）的段，落到空口就是一长串小帧——帧越短，固定税占比越高。E1 里 N=2 的两站场景读数（摘自 `practice/wifi-airtime-labs/ch01-dcf-sim/run.log`）：吞吐 0.1780、空闲时隙占 81.03%、碰撞占 1.17%——**每 100 个时隙只有约 18 个在传有效载荷，其余 82 个都是税**。

聚合的杠杆就压在这里：竞争胜出的门票只买一次，进场后连续发 N 个子帧，结尾一次总账确认：

```text
无聚合（k=1）：每个包各买一次门票，各结一次账
  [DIFS+退避][ D1 ][SIFS][ACK] [DIFS+退避][ D2 ][SIFS][ACK] ...
  ←─ 固定税 ─→ ←有效载荷→      ←─ 固定税 ─→

A-MPDU（k=3）：一张门票搬三件，批尾一次总账
  [DIFS+退避][ D1 | D2 | D3 ][SIFS][BlockACK]
  ←─ 固定税 ─→ ←── 有效载荷 ──→        ←税→
```

关键认知只有一句：**聚合不改变「谁赢」**——退避规则、碰撞概率、站间公平全都原样；它只放大「赢一次搬多少」。所以这是一根效率杠杆，不是调度杠杆。这句话先记住，3.6 会回来收尾。

## 3.2 两种打包：A-MSDU 与 A-MPDU

批量确认的 Block ACK 机制其实更早铺路（802.11e，2005），聚合则由 802.11n（2009）补上，两者配合成名。打包有两种，聚合的层不同：

- **A-MSDU（MAC 级）**：多个完整的 MSDU 拼进一个 MPDU，共享同一个 MAC 头和**同一个 FCS**，子帧之间靠长度字段切分。整条只有一个校验和——任何一个比特错，整条作废重传。
- **A-MPDU（PHY 装配级）**：多个完整的 MPDU（**各有** MAC 头与 FCS）背靠背装进一个 PPDU；每个子帧前有 MPDU delimiter（定界＋长度），子帧间按协商好的最小间隔垫 padding；同一 PPDU 共用一份前导码、一个速率一发到底。

```text
一个 PPDU（一次信道占用）
├── PLCP 前导码 ──────────── 门票里「只付一次」的部分
├── [delimiter] MPDU#1 ──── MAC头 + 载荷 + FCS#1（可内含一个 A-MSDU）
├── [delimiter] MPDU#2 ──── MAC头 + 载荷 + FCS#2
├── …（子帧数上限 11n 64 / 11ac 256，量级以规范版本为准）
└── [EOF delimiter + padding]
```

两者还能嵌套：A-MPDU 的某个子帧本身可以是一个 A-MSDU——两级打包，现代 Wi-Fi 的常态。一张表认清分工：

| 维度     | A-MSDU                             | A-MPDU                                         |
| -------- | ---------------------------------- | ---------------------------------------------- |
| 聚合的层 | MAC：多个 MSDU 共用一个帧头/FCS    | PHY 装配：多个完整 MPDU 同车一个 PPDU          |
| 校验粒度 | 整条一个 FCS，一比特错整条作废     | 每子帧独立 FCS，可部分成功                     |
| 重传单位 | 整条                               | 只重传失败的子帧                               |
| 长度上限 | 3839 或 7935 字节（HT 能力位决定） | 按能力位分档（3839/8191/16383/65535 字节量级） |
| 确认方式 | 本身是单个 MPDU，普通 ACK 即可收货 | 必须有 Block ACK 会话配合                      |

具体档位数值以所用规范版本与设备能力宣告为准——工程上记住量级即可：聚合上限以「几十个子帧、几 KB 到 64KB 量级」为典型区间。

## 3.3 Block ACK：让批量确认成为可能

A-MPDU 的子帧是背靠背的，中间插不进 SIFS＋ACK——若每发一个子帧就停下来等确认，聚合就名存实亡。Block ACK 把「逐帧应答」改成「批尾一次总账」：一批子帧连续发完，接收方回一个 BlockAck 帧，位图里逐帧汇报收没收到。

总账不是凭空开的，要先握手建立会话（monitor 模式抓包能看到）：

- **ADDBA Request / Response**（一对 Action 帧）：协商 TID（挂在哪个优先级队列上）、缓冲尺寸（位图窗口，11n 典型 64 帧、11ac 256 帧量级）、起始序号 SSN、确认策略（Immediate 或 Delayed）、会话超时；
- **DELBA**：任一侧拆除会话（超时、缓冲压力等）。

位图的工作方式：

```text
序号：   SSN   SSN+1   SSN+2   SSN+3  …  SSN+w-1    （窗口 w 帧量级，序号空间 4096）
位图：    1      1       0       1    …     1
                        └─ 只补位图为 0 的子帧，补完窗口前滑
```

三个工程要点：

1. **重传与聚合解耦**：单子帧失败只重传该子帧——A-MPDU 每子帧独立 FCS 的功劳；A-MSDU 则一坏整条重来，差信道下代价放大。这正是 A-MPDU 成为主角的原因。
2. **Immediate 是常态**：收完立刻在 SIFS 后回总账；Delayed（稍后另发）实战中极少遇到。
3. **接收方要付重排序的成本**：位图窗口内乱序补齐、按序上交，缓冲或超时处理不当时表现为吞吐周期性塌陷——「BA 会话不稳」是聚合吞吐问题的常见病灶。

还有一条伏笔：**会话按 TID 建立**——不同优先级的流量各有各的 Block ACK 会话。TID 是什么、怎么用，是 [[ch04-wmm-edca-qos|下一章]]的主角。

## 3.4 账本：E3 的真实数字

直觉要用数字验收。E3 实验设置（摘自 `practice/wifi-airtime-labs/ch01-dcf-sim/run.log`）：N=8 个饱和站，CWmin=15、CWmax=1023，竞争胜出者每次连发 k 包（占 k 时隙），碰撞的聚合整条报废（双方同样烧掉 k 时隙）；固定随机种子、每配置仿真 100 万时隙。

```text
   k      thr       wins        att       coll         pkts    ovh/win    ovh/pkt
   1   0.2431     243101     368982     125881       243101       3.11      3.114
   4   0.5103     127583     193647      66064       510332       3.84      0.960
  16   0.7035      43971      66767      22796       703536       6.74      0.421
  64   0.7780      12157      18406       6249       778048      18.26      0.285
```

（thr=有效吞吐；wins=成功接入次数；att=发射尝试次数；coll=碰撞发射次数；pkts=成功包总数；ovh/win=每次成功接入摊到的竞争开销时隙（(idle+coll)/wins）；ovh/pkt=摊到每包。）

账本式解读，五笔账：

1. **吞吐 3.2 倍**：0.2431 → 0.7780，且增益递减——k 从 1→4→16→64，每步涨幅 0.267/0.193/0.075，越往后越平。
2. **接入次数 ÷20**：wins 从 243101 降到 12157。100 万时隙里少打了约 23 万次擂台，省下的正是 E1 里占 69.79% 的空闲退避时隙（同配置读数）。
3. **每包竞争税 ÷11**：ovh/pkt 从 3.114 降到 0.285 时隙/包——聚合省钱的本质就是把这笔税摊薄。
4. **但每次接入的税在涨**：ovh/win 从 3.11 涨到 18.26。原因：竞争的节拍变成了「整条聚合」——一次碰撞烧 k 时隙；碰撞概率本身几乎没变（尝试碰撞率 k=1 时 125881/368982≈34.1%，k=64 时 6249/18406≈33.9%，与 E1 同配置的 34.12% 同源），变的是单次的代价。
5. **总税负降约七成**：以 ovh/win×wins 推算，竞争开销从约 75.6 万时隙降到约 22.2 万——绝对量大幅下降，只是摊法从「每包 3.1」变成了「每次 18.3、每包 0.29」。

为什么涨不到 1：碰撞整条报废，k 越大单次碰撞烧得越狠。站点更多、碰撞概率更高的场景里，盲目加大聚合上限，收益边际递减。还要记住模型的边界（工程 README 明示的简化）：时隙归一化（1 包=1 时隙），thr 读数是**时隙利用率**不是 Mbps，绝对值与真机不可比；但「接入次数 ÷20、每包税 ÷11」这类结构性结论是稳的。

## 3.5 工程侧：把聚合拧到位

**AP/宿主侧（hostapd + mac80211）**。聚合不是独立开关，而是挂在 HT 能力协商上：关联时双方交换 HT Capabilities，之后驱动自动建 ADDBA 会话，用户态通常无感。hostapd.conf 里常见的配置位：

```text
ieee80211n=1        # HT 入口：聚合与 Block ACK 的前提（11ac 再加 ieee80211ac=1）
wmm_enabled=1       # 聚合与 BA 会话都跑在 WMM 的 TID 框架上
ht_capab=[MAX-AMSDU-7935]   # 能力括号位：宣告 A-MSDU 用大档上限
```

另两个聚合参数位——Max A-MPDU Length Exponent（长度上限档位）与 Min MPDU Start Spacing（子帧间最小间隔，¼µs 步进的档位）——住在 HT Capabilities IE 里，宿主上通常由 mac80211/驱动决定后透传，hostapd 不总暴露独立的配置项；可用位以所用 hostapd 版本的示例配置为准。观察命令（真实形态，控制帧要在 monitor 模式接口上抓）：

```bash
# 每站协商速率/重传/失败计数——聚合效果的侧写
iw dev wlan0 station dump
# 按站读 BA 会话状态：哪些 TID 挂着 active 的聚合会话
cat /sys/kernel/debug/ieee80211/phy0/netdev:wlan0/stations/<对端MAC>/agg_status
# 抓 BlockAck（子类型 25；BlockAckReq 是 24）与 Action 帧（ADDBA/DELBA 住在里面）
tshark -i mon0 -Y 'wlan.fc.type_subtype == 25'
tshark -i mon0 -Y 'wlan.fc.type_subtype == 13'
```

看点清单：关联后几秒内应有一对 ADDBA Req/Resp；数据期子帧背靠背＋周期性 BlockAck；agg_status 里对应 TID 挂上会话。若始终没有 ADDBA——聚合根本没开，吞吐先塌一半再谈别的。

**ESP32 侧（ESP-IDF）**。机制同上，配置位在 Kconfig（`idf.py menuconfig` → Component config → Wi-Fi）：

- **总闸**：`CONFIG_ESP_WIFI_AMPDU_TX_ENABLED` / `CONFIG_ESP_WIFI_AMPDU_RX_ENABLED`（部分版本以 `ESP32_WIFI_AMPDU_*` 前缀提供等价项）。拿它做对照实验最有体感：关掉 TX 侧重测吞吐，聚合的贡献一目了然——默认值以所用 IDF 版本为准。
- **收发缓冲**：`CONFIG_ESP_WIFI_TX_BUFFER_TYPE`（TX 缓冲放内部还是外部 RAM）、`CONFIG_ESP_WIFI_STATIC_RX_BUFFER_NUM` / `CONFIG_ESP_WIFI_DYNAMIC_RX_BUFFER_NUM`（收方向的静态/动态缓冲数）。聚合需要缓冲把子帧攒起来，缓冲不足的现象是吞吐上不去＋RX 丢帧；具体项名与档位以所用 IDF 版本为准。

最后是**供数节奏**：聚合要「凑得起」子帧——发送前有个短暂的攒包窗，上层供数太碎、太慢，聚合自然小、收益打折。TCP 场景下窗口与发送缓冲是供数的上游（[[lwip-deep-dive|lwIP 深度解析系列]]），应用层该以什么节奏喂它，是 [[ch07-pacing-and-structure|第七章]]的主题；ESP32 侧收发链路的硬件约束见 [[esp32-s3-box-3|ESP32-S3-BOX-3 工程实战]]。

## 3.6 小结

- 聚合是**效率杠杆**：一张竞争门票搬 N 件货，把每包必缴的固定税（DIFS＋退避＋碰撞风险＋确认）摊薄；它不改变谁赢，只改变赢一次搬多少。
- 两种打包：A-MSDU（MAC 级、单 FCS、一坏整条重传）与 A-MPDU（PHY 装配、子帧独立 FCS、单帧级重传）；后者靠 Block ACK 会话（ADDBA 握手、按 TID、位图窗口）完成批量确认，是现代 Wi-Fi 的主角。
- E3 真实账本：k 从 1 到 64，吞吐 0.2431→0.7780（3.2 倍）、接入次数 ÷20、每包竞争税 3.11→0.285 时隙；增益递减的根因是碰撞整条报废、单次碰撞代价随 k 放大。
- 工程位：hostapd 的 `ieee80211n`/`wmm_enabled`/`ht_capab`；mac80211 的 `agg_status` 与 tshark 子类型 25/24/13 观察会话；IDF 的 AMPDU TX/RX 开关与 TX/RX 缓冲项。
- 边界：聚合只提升「单位接入的效率」。它不给流量分优先级——图像流与控制流照样同场竞争，见 [[ch04-wmm-edca-qos|下一章]]；它也不解决速率问题——弱信号端该降速还得降速，那是 [[ch05-rate-and-channel-width|第五章]]的另一根杠杆。

回到开头的痛点现场：两台机器互传图像，把聚合拧开、供数喂饱之后，「每次接入搬的字节」已经到位——但这只解决了搬得多，没解决**谁先搬**。图像流与 VoIP、控制流同场竞争时谁让路、谁插队，聚合一个字都没说。下一章把 802.11 的四条队列摆上桌：WMM/EDCA 的 AC 分类、AIFS/CW/TXOP 三件套怎么给流量定规矩，以及图像流该进哪条队、要付什么代价——[[ch04-wmm-edca-qos|下一章]]：WMM 与 EDCA，给流量分优先级。
