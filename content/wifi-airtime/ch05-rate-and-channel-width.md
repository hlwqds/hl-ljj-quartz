# WiFi 空口调度实战（五）：每个字节的空口成本——速率、带宽与重传

局域网里两台机器互传图像，空口争抢严重时的第一直觉往往是「换路由器」「加带宽」。但 [[ch01-dcf-contention-basics|第一章]]的结论在先：DCF 只保证发送机会大致均等，不保证发送时长均等——**一个字节值多少信道时间（airtime），由发送方此刻选用的速率档决定**，与路由器标称的千兆无关。本章回答四个问题：同一张图在不同档位下到底占多少空口（5.1）；为什么一台弱信号机器能把强信号一方拖慢一个数量级（5.2）；自适应速率什么时候值得手动锁死（5.3）；信道开 40 MHz 还是守住 20 MHz（5.4）；最后把这些落到铁件与摆位上——一分钟检查清单（5.5）。

---

## 5.1 每字节的空口账：MCS、保护间隔与信道宽度

一帧的信道时间由两部分组成，固定成本与可变成本：

```text
一帧信道时间 ≈ 前导/训练序列 + 数据本体 + SIFS + ACK + 竞争退避
                └── 固定成本 ──┘  └ 字节数÷速率 ┘└── 固定成本 ──┘
数据本体 = 字节数 × 8 ÷ PHY 速率     ← 唯一随「发了多少货」变化的部分
```

PHY 速率则是四个旋钮的乘除法：调制阶数与码率（打包成 MCS 编号）× 子载波数（由信道宽度决定）÷ 符号周期（由保护间隔决定）。11n 单空间流的标准速率表（IEEE 标准值，每格可用公式复算；完整推导见 [[wifi-rf-hw|WiFi 射频硬件入门]]的速率协商章，那里逐格核对过标准表与芯片头文件注释）：

| MCS | 调制  | 码率 | HT20 长 GI | HT20 短 GI | HT40 长 GI | HT40 短 GI |
| --- | ----- | ---- | ---------- | ---------- | ---------- | ---------- |
| 0   | BPSK  | 1/2  | 6.5        | 7.2        | 13.5       | 15         |
| 1   | QPSK  | 1/2  | 13         | 14.4       | 27         | 30         |
| 2   | QPSK  | 3/4  | 19.5       | 21.7       | 40.5       | 45         |
| 3   | 16QAM | 1/2  | 26         | 28.9       | 54         | 60         |
| 4   | 16QAM | 3/4  | 39         | 43.3       | 81         | 90         |
| 5   | 64QAM | 2/3  | 52         | 57.8       | 108        | 120        |
| 6   | 64QAM | 3/4  | 58.5       | 65         | 121.5      | 135        |
| 7   | 64QAM | 5/6  | 65         | 72.2       | 135        | 150        |

三个变量对「每字节成本」的贡献量级：MCS 阶梯 6.5 → 65 Mbps 贡献**十倍**；信道宽度 20 → 40 MHz（数据子载波 52 → 108 条）贡献**约两倍**；短 GI（符号周期 4 → 3.6 µs）只贡献**约 11%**。主次分明：先保住 MCS，再谈宽度。

拿一张 1.5 MB 的图复算一版量级账（口径：按上表标准速率计算数据时间，每帧按 1500 字节切分，每帧固定开销取几十到百余微秒的量级示意，未计聚合与重传；这是复算不是实测）：

| 发送档位            | PHY 速率 | 1.5 MB 图的数据本体 | 加上每帧固定开销后 |
| ------------------- | -------- | ------------------- | ------------------ |
| MCS7 / HT40 / 短 GI | 150 Mbps | ≈ 80 ms             | ≈ 0.2 s 量级       |
| MCS7 / HT20 / 长 GI | 65 Mbps  | ≈ 185 ms            | ≈ 0.3 s 量级       |
| MCS3 / HT20 / 长 GI | 26 Mbps  | ≈ 460 ms            | ≈ 0.6 s 量级       |
| MCS0 / HT20 / 长 GI | 6.5 Mbps | ≈ 1.85 s            | ≈ 2 s 量级         |

同一张图，最贵与最便宜的档位差一个数量级。重传再往上乘：链路 PER 高到每帧平均发两遍，账本直接翻倍——**速率与重传在账本上是乘法关系**。[[ch03-aggregation-ampdu|第三章]]的聚合改写的是「每帧固定开销」那一栏（一次仲裁摊薄前导与 ACK），不改变「数据本体 = 字节 ÷ 速率」这条主轴——链路差到只剩低档时，聚合救不了账本。

## 5.2 慢速率异常：一个低速率站点拖死全小区

DCF 每次竞争成功换来的是**一次发送机会**，机会近似等概率；但机会的**时长**由发送方自己的速率决定。慢站点一次机会占两毫秒，快站点一次机会占零点一毫秒——时间份额于是严重倾斜：

```text
DCF 眼里：人人机会均等          信道时间轴眼里（同一批数据）：
强站 A：帧 ▏0.1 ms            t → AA BBBB AA BBBB BBBB AA ...
弱站 B：帧 ████████ 2 ms          B 的慢帧把共享时钟整段吃掉
```

这就是 802.11 的**性能异常**（rate anomaly / performance anomaly）：小区里出现一个低速率站点后，高速率站点的吞吐会被拉低到与低速站点可比的量级——不是谁抢了谁的优先级，而是慢帧把共享的时间轴占走了。该现象由 Heusse 等人 2003 年的论文首次系统刻画（结论方向如此，具体数值以原文为准）。注意 [[ch04-wmm-edca-qos|第四章]]的 EDCA 在这里帮不上忙：它改的是「谁能更早抢到机会」，抢到之后一帧占多久仍由速率决定。

两机互传的经典形态：机器 A 近而信号好，机器 B 隔墙信号差。B 的帧以低 MCS 发送、每帧时间长数倍，且链路质量差导致重传再把时间翻倍——结果 A 的 iperf 掉到单机测试的一小部分，但 AP 面板上 A 自己的信号与速率档都「正常」。排查思路是**找出那台拖后腿的**，而不是给 A 加配置：

```bash
# AP/Linux 网桥侧逐站点看三件事：信号、当前速率档、重传率
iw dev wlan0 station dump
#   signal avg:         对端信号（弱站通常显著更低）
#   tx bitrate:         当前发送档（低 MCS 即长帧来源）
#   tx retries / tx packets: 重传率（ch02 的判定阈值：>30% 偏高）
```

[[ch02-measuring-airtime|第二章]]的探针工具（`practice/wifi-airtime-labs/ch02-airtime-probe`）解析的正是这两类 `iw` 文本：`survey dump` 看信道 busy 是否饱和（阈值 70%），`station dump` 算每站点重传率（阈值 30%，均为工具源码内的判定阈值，输出样例为构造自检值而非真机数据）。**结论先行：改善弱站的信号（5.5），或把弱站的大流量挪走/限速，收益远大于给强站开 40 MHz。**

## 5.3 自动速率 vs 固定速率：什么时候亲手拧

自动速率（rate adaptation）逐帧选档：主流实现以重传统计为主反馈——ACK 没来就降档、连续成功就试探爬档，加性增、乘性减（Linux mac80211 的代表实现是 Minstrel；AP 与手机多用厂商私有算法）。链路平稳时它工作得不错；麻烦出在**饱和加多机**的环境：

- **碰撞被误读为信道差**。多机竞争下重传可能来自碰撞而非解调失败，速率算法分不清两者，把碰撞当噪声降档——帧变长、占空口更久、更容易撞，形成下探的正反馈；
- **试探有代价**。饱和期爬档试探会发出注定失败的帧，每个失败帧都按当前档的时长白占空口，还触发重传链。

（以上是机制层面的定性描述；饱和到底把档位压低几档，用 ch02 的 busy/retries 序列在自己的环境里量。）

什么时候值得锁死速率：**链路是静态的、且两端都归你管**——固定部署的近距图传、替代网线的点对点回传、演示台上的双机互联。这类场景 RSSI 稳定、无漫游、SNR 余量可提前实测，锁定高 MCS 换来两样东西：每帧信道时间可预测（给发送侧的整形与队列预算一个稳定的分母，[[ch07-pacing-and-structure|第七章]]要用），以及消灭试探震荡。代价同样明确：**你关掉的是链路的自保反射**——遮挡一变，没有降档兜底，PER 直接起飞。所以锁速两条纪律：先逐档实测选「吞吐最高且重传不涨」的档，而不是无脑 MCS7；锁速必须配重传率监控。

```bash
# Linux/mac80211 侧（STA 上行方向）：
iw dev wlan0 link                       # 先看当前 txbitrate/rxbitrate 与 signal
iperf3 -c <对端IP> -t 30                 # 逐档实测吞吐与重传，再决定锁哪档
iw dev wlan0 set bitrates ht-mcs-2.4 7  # 锁 HT MCS7（2.4G；形态照此，档位自选）
iw dev wlan0 set bitrates               # 不带参数 = 清除锁定，恢复自适应
```

ESP32 目标机侧，TX 定速有现成 API：`esp_wifi_config_80211_tx_rate(WIFI_IF_STA, WIFI_PHY_RATE_MCS7_LGI)`（要求在 `esp_wifi_init()` 之后、`esp_wifi_start()` 之前调用；头文件事实在 [[wifi-rf-hw|WiFi 射频硬件入门]]的速率协商章已逐行核对，跑板现场见 [[esp32-s3-box-3|ESP32-S3-BOX-3 工程实战]]）。锁速只对「你自己的发送方向」有效——这就是为什么它适合自建双机网络，而不适合去「优化」别人家 STA 的公共环境。

## 5.4 信道宽度：20 与 40 MHz 的三角

40 MHz 用子载波翻倍（52 → 108）换 PHY 速率约 ×2.07，但代价是**干扰暴露**：占掉两个 20 MHz 信道。2.4G 全频段只有 83.5 MHz，一个 40 MHz 信道吃掉三分之二，几乎必然压到邻居。规范为此内置了 20/40 共存规则：AP 探测到重叠 BSS 就应退回 20 MHz——所以城市住宅的 2.4G 里 40 MHz 常常开不起来、或开了也被顶回去。三股力量的三角：

| 力量     | 40 MHz 的收益/代价                                     |
| -------- | ------------------------------------------------------ |
| 吞吐     | PHY 速率约 ×2.07（数据子载波 52→108）                  |
| 干扰暴露 | 占两个 20 MHz 信道；2.4G 仅容一个 40，且副信道必须干净 |
| 邻道容忍 | 共存规则强制退回 20；强行保持会压邻居                  |

两机图传自建网络的决策线：

| 环境                            | 选择                  | 理由                                |
| ------------------------------- | --------------------- | ----------------------------------- |
| 自建且可用 5G（现场/产线/演示） | 5G 40 MHz 起步        | 频段干净，宽度直接换吞吐            |
| 自建但只有 2.4G                 | 可试 40，用数据验证   | 先看副信道忙闲，收益存疑就退回      |
| 共存环境（办公室/住宅）         | 2.4G 守 20，选 1/6/11 | 40 会被共存机制顶回，且把干扰面翻倍 |

AP 侧（hostapd）与 ESP32 AP 侧的真实配置方向：

```ini
# hostapd.conf（自建 AP）
ieee80211n=1
ht_capab=[HT40+]        # 副信道在上侧（HT40- 为下侧），按主信道位置选
# noscan=1              # 跳过 20/40 共存探测、强行保持 40 —— 会压到邻居，
                        # 只在确知周围无人的自建网络里用
```

```c
// ESP32 AP 侧（仅 11n 生效，头文件已核；SDK 形态）
esp_wifi_set_bandwidth(WIFI_IF_AP, WIFI_BW40);
```

开 40 之前先用 ch02 的工具验一眼副信道：`iw dev wlan0 survey dump` 里的 `extended channel busy time` 正是 HT40 副信道的忙时（探针已解析该字段）。副信道忙则 40 的收益会被 CCA 静默期吃掉，老老实实退 20。最后一个清醒剂：**40 MHz 不治 5.2 的病**——带宽是全小区共享的，速率是每条链路自己的；瓶颈在弱站的低 MCS 时，加倍带宽只是把每个慢帧的时间减半，异常还在，只是没那么难看。

## 5.5 信号工程速写：悬崖效应与一分钟检查清单

「信号还能用」与「信号够快」之间隔着一道悬崖。标准灵敏度底线（HT20、PER≤10% 口径，出自 IEEE 802.11-2012 的最小输入灵敏度表，以规范版本为准；实际芯片普遍比底线灵敏，具体以 datasheet 为准）：

| 档位 | HT20 速率 | 标准灵敏度底线 |
| ---- | --------- | -------------- |
| MCS0 | 6.5 Mbps  | 约 -82 dBm     |
| MCS3 | 26 Mbps   | 约 -74 dBm     |
| MCS7 | 65 Mbps   | 约 -64 dBm     |

整条 MCS 阶梯只铺在约 18 dB 的窗口里。走过一个人、关一扇门、天线偏几厘米，都能带来几个 dB 的起伏——足够跨掉两三个档位，每字节成本立刻乘上 1.5 到 2。所以图传链路的预算要按**最差时刻的 RSSI**留余量，而不是按均值。另有两个口径提醒：RSSI 各厂标定不同，真正的定档依据是 SNR（信号减底噪，底噪就看 `survey dump` 的 noise 字段）；以及信号满格不等于能跑高 MCS——满格只说明分子大，分母（底噪）被干扰抬高时菜单照样只能点便宜的档。这些 dB 账、天线摆位与多径的原理性推导，在 [[wifi-rf-hw|WiFi 射频硬件入门]]的对应章节有完整版，这里只给结论性的一分钟清单：

```bash
# 两机互传现场，先跑三条命令建立基线（Linux/树莓派侧均可，见 [[rpi-lab|树莓派实验室]]）
iw dev wlan0 link           # 本机视角：signal / txbitrate / rxbitrate
iw dev wlan0 station dump   # 对端视角：signal avg / tx bitrate / retries
iw dev wlan0 survey dump    # 底噪 noise 与 busy / extbusy（ch02 工具直接吃这些文本）
```

1. **极化与朝向一致**：两台机器的天线要么都竖直、要么都水平，一横一竖先吃几分贝；
2. **挪 30 cm 复测**：信号跳动好几个 dB，说明正站在多径零点上——换个位置比换天线便宜；
3. **拉高、离金属**：离开机箱面、金属桌、线缆捆；2.4G 穿墙不如绕墙；
4. **算 SNR 余量**：signal 减 noise 不足 20 dB 量级，就别指望高 MCS 档位；
5. **一次只改一处**：每改一次摆位就复测一遍 station dump，三处一起改等于没改。

## 5.6 小结

- **一张账本**：一帧信道时间 = 固定开销 + 字节 ÷ 速率；MCS 阶梯贡献十倍、信道宽度约两倍、短 GI 约 11%——同一张图在 MCS7/HT40 与 MCS0/HT20 下的空口成本差一个数量级以上（按标准速率表复算的量级账）。
- **一个异常**：DCF 等概率发机会、不等长发时间，一个低 MCS 站点就能把全小区拖到自己的量级（性能异常，Heusse 2003）；两机互传先查弱站——`station dump` 里 signal 低、重传率高的那台才是账本大头。
- **一个取舍**：自动速率在饱和多机下会把碰撞误读为信道差而震荡下探；链路静态、两端归你时值得锁速（`iw set bitrates` / `esp_wifi_config_80211_tx_rate`），前提是逐档实测加重传监控。
- **一条决策线**：自建 5G 用 40 MHz；2.4G 共存环境守 20 选 1/6/11；开 40 前看 `extended channel busy time` 验副信道，强行 `noscan` 只限无人自建网。带宽治不了慢速率异常。
- **一道悬崖**：MCS 阶梯只有约 18 dB 宽，按最差时刻的信号留余量；天线极化对齐、躲多径零点、算 SNR 而不是只看满格。

到这里，「每个字节多少钱」的账本有了：速率定单价，重传是乘数，带宽是整条街的宽度。但账本再清楚，DCF 的「机会等概率」依然没变——弱站还是每次竞争都赢得和强站一样多的机会。下一章换一个问题：怎么把「等概率」改成「等时间」——airtime 公平性的原理、AP 侧队列调度在哪里下手，以及两机图传怎么借它把强站的吞吐救回来。[[ch06-airtime-fairness|下一章]]。
