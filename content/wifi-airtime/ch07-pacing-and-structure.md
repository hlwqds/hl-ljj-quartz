# WiFi 空口调度实战（七）：釜底抽薪——应用层 pacing 与结构性解法

前六章都在「怎么把蛋糕分好」里打转：DCF 的账本、测量、聚合、WMM、速率、公平——全是供给侧调参。这一章换到需求侧，回答两个问题：**为什么把发送速率压到「可持续吞吐之下」这一步，往往比前面所有 MAC 参数加起来都值钱**（7.1 的根因账、7.2 的令牌桶整流、7.3 的回环实验证据）；以及**当压速率也救不了时，还有哪些结构性出路**（7.4 TCP 的反向代价与传输协议决策线，7.5 四条结构性解法清单）。

## 7.1 争抢的根因账：饱和排队与突发

争抢有一个比 MAC 参数更上游的开关：**要不要来这么多人抢**。两个机制把小争抢放大成大争抢。

**饱和排队**。应用产包速率超过链路可持续吞吐时，驱动队列只进不出，站点**永远有包可发**——这正是 [[ch01-dcf-contention-basics|第一章]] 仿真里「饱和站点」假设的现实来源。后果是一条链：每个空闲时隙都有人守着竞争 → 退避水位抬升 → 碰撞与空闲时隙双双上涨（第一章 E1 的账）；同时队列本身是时延蓄水池——排在前面的每一包都在给后面的包加时延，这部分时延与空口质量无关，纯属性能浪费，也是图传「画面到了却晚了」的主要来源。

**突发是放大器**。即使平均速率不饱和，突发也会制造**瞬时**饱和：编码器吐出一帧图像，几十个 UDP 包瞬间塞满队列，信道被连续占用一整块，其他站的包只能在队列与退避里干等。[[ch03-aggregation-ampdu|第三章]]的聚合还会把突发打包成更长的占用块——A-MPDU 整条传输期间信道锁死，突发越长、锁得越久。突发也让 MAC 层的「平均占用」统计失去意义：70% 的平均占用率若是 30% 与 100% 交替的方波，排队照样在 100% 的相位里堆起来。

第一章 E4 的仿真（`ch01-dcf-sim` 真实输出，run.log 第 49–51 行）正是「退一步海阔天空」的证据：

```text
scenario            thr_A    thr_B  thr_all    coll%    tryc%     jain
both-saturated     0.0889   0.0891   0.1780     1.17    11.63   1.0000
A-sat+B-lim50      0.1190   0.0150   0.1340     0.22     3.24   0.6241
```

B 从饱和退成限速（每 50 时隙尝试一次），碰撞时隙占比降到不足 1/5（1.17%→0.22%），留下的 A 吞吐 +34%（0.0889→0.1190）。E4 的另一半教训——限速站份额崩到对方的 1/8、Jain 掉到 0.6241——是 [[ch06-airtime-fairness|第六章]]公平性的话题，那里的解法是 AP 侧 airtime 调度；本章的解法更朴素：**B 的应用本来就不该以饱和速率发**。

于是本节的结论可以一句话说死：MAC 参数（CW、AIFS、TXOP、聚合深度）改变的是「抢的时候多有礼貌」，压速率改变的是「要不要抢」。前者收益有天花板——第一章 E2 里 CWmin 从 7 拉到 63，碰撞率降到 1/6 的代价是吞吐掉一半；后者直接把一个竞争者请下牌桌。**把发送速率压到可持续吞吐之下，往往是你能做的最大一笔交易。**

## 7.2 令牌桶 pacing：把发送节奏钉在预算上

压速率靠什么落地？答案是**应用层整流（pacing）**：发送端不把包一股脑交给协议栈，而是按一个恒定节奏放行。最常用的零件是令牌桶：

```text
              ┌────────────────── 令牌桶 ──────────────────┐
 速率 r pps ──▶│ ○ ○ ○ …   桶深 b ＝ 允许攒下的信用上限      │──有令牌──▶ sendto()
              │                                            │
 应用产帧 ───▶│ 没令牌就等（不发也不堆积成突发）            │
              └────────────────────────────────────────────┘
  b＝1   最严格：攒够 1 个令牌才发，不蓄任何突发信用
  b＞1   允许小突发：平滑度让位于起播延迟、I 帧大块等需求
```

两个参数各自管一件事：**rate 定长期均值**（对齐预算），**depth 定允许的突发额度**（对齐时延要求）。对图传，I 帧远大于 P 帧是天然的周期性脉冲——桶深按「一个帧间隔内摊平一帧」设计通常就够，不需要为 I 帧单独放大信用。

**整流到什么速率？**分两步，顺序不能反：

1. **先测可持续吞吐**：[[ch02-measuring-airtime|第二章]]的 survey busy% 告诉你现在占了多少，iperf3 打满告诉你这条链路的真实上限（无线环境波动大，多测几轮看稳定段）；
2. **再定预算并整流**：编码码率预算 = 可持续吞吐 × 安全系数。系数的工程经验量级是 0.7–0.8（留 20–30% 给重传、信标、邻居流量）——这不是规范值，现场以测量为准；令牌桶 rate 再按码率折算的 pps 设定，钉住节奏。

**为什么整流同时降碰撞与降时延抖动**——一份投入两份回报：

- **降碰撞**：队列常空 → 站点大多数时隙根本不在竞争 → 信道上的有效竞争者变少，正是 E4 里 B 退成限速后碰撞降到 1/5 的机制；
- **降抖动**：发送间隔稳定 → 排队深度稳定 → 排队时延方差小，接收端的抖动缓冲可以收窄；同时恒定供给让每次接入攒出的 A-MPDU 尺寸稳定，避免「饿一顿饱一顿」的极端聚合块。

图传的码率-帧率-分辨率预算怎么跟空口预算对齐——先认每个旋钮动的是哪本账：

| 旋钮           | 对空口占用的影响 | 代价/备注                                      |
| -------------- | ---------------- | ---------------------------------------------- |
| 编码码率       | 线性             | 每秒比特数直接变成空口秒数，主旋钮             |
| 帧率           | 近似线性         | 每帧自带编码开销；pps 随之变，影响聚合与开销   |
| 分辨率         | 经码率起作用     | 同码率升分辨率＝压缩更狠，占用几乎不变画质让步 |
| GOP/关键帧间隔 | 周期性脉冲       | I 帧是突发源，pacing 桶深要按它设计            |

```text
算例（假设数字仅作演算，实测以你的链路为准）：
  码率 8 Mbps ÷ 30 fps   ≈ 33 KB/帧
  33 KB ÷ 1316 B/包      ≈ 26 包/帧 → 图传 pacing 的实际含义：
                          把「每帧一次性 26 包」摊成「33ms 帧间隔内匀速发」
  对预算：8 Mbps ÷ 实测可持续吞吐 40 Mbps  ＝ 20% 占用，有裕度
          32 Mbps ÷ 40 Mbps              ＝ 80%，顶着饱和线 —— 该动码率，不是动 MAC
```

## 7.3 实验：ch07-pacing-harness——整流前后的 gap 分布

配套工程 `ch07-pacing-harness`（C11 零依赖单文件）把 7.2 的论断做成可运行的测量：**同一个 UDP 发送端，burst（连续尽快发）与 paced（令牌桶限速）各跑一遍，接收端对每个到达包打单调时钟时间戳**，统计到达间隔 gap 的 min/avg/p99/max、标准差 σ、RFC3550 抖动 J 与直方图，最后打印对比表。

默认参数（2000 包 × 1316 B → 127.0.0.1:13201，paced 目标 500 pps）的真实回环输出（run.log 第 46–51 行）：

```text
==== 对比表: burst vs paced (接收端到达 gap, 单位 us) ====
mode        rx/loss     rx_pps      min      avg      p99        max    sigma    J3550  <100us
burst     2000/0.0%      76598     1.10     13.1     73.6      349.9     17.9     4.10   99.5%
paced     2000/0.0%      437.5     23.9    2286     6286      64736     2630     24.0    0.1%
[结论] burst: 99.5% 的到达 gap < 100us —— 微秒级聚簇, 即突发形态在回环上的证据
       paced: 平均 gap 2286 us vs 目标 2000 us (偏差 +14.29%) —— 令牌桶把节奏钉在目标附近
```

读法：burst 的到达 gap **99.5% 小于 100µs**、直方图聚在 5–20µs 两桶——这就是突发形态本身：包挤成一坨，中间没有呼吸。paced（目标间隔 2000µs）的 gap 有 79.2% 落在 1900–2100µs（run.log 第 39–40 行直方图两桶 44.2%+35.0% 相加），均值偏差 +14.29%——节奏被钉住了，但尾部有 10–65ms 的毛刺（max 64736µs），来自宿主调度把等待线程饿了一拍。两组补充运行：`--pps 250` 时均值 4265µs vs 目标 4000µs（偏差 +6.62%，run.log §2），桶随参数收紧/放宽生效；双进程形态下发送端 TX avg 2070µs 与接收端 RX avg 2070µs 逐位一致（run.log §3）——回环不引入节奏失真，统计链路自证清白。

用法（编译与参数均摘自工程 README）：

```bash
~/zig/zig cc -O2 -o pacing pacing.c -lws2_32   # Windows；POSIX 去掉 -lws2_32
./pacing                          # 默认：2000 包 × 1316B，burst 与 paced(500pps) 各一遍
./pacing --count 600 --pps 250    # 令牌桶随 argv 收紧/放宽（--depth 桶深、--payload 包长可调）
```

真机 WiFi 上的同款测量（工程 README 标注「待真机」的命令形态）：

```bash
./pacing --ip <PC地址> --pps 500 --count 5000   # 设备侧：发往接收端
./pacing --rx-only 30 --count 5000              # PC 侧：只收不发（树莓派即可当此角色）
```

**诚实边界**（与工程 README 同口径）：回环验证的是**整流工具链与 gap 统计本身**——令牌桶→定时器→时间戳→统计的整条链路，以及 p99/σ/J/直方图能不能分辨两种节奏形态；回环上没有 MAC 排队、CSMA/CA 退避、重传与信标打断，**这些数字不能当作空口画像引用**，空口对整流的「还原度」要靠上面的真机命令现场量。跨机测量另有两个注意：J3550 依赖对端时钟，跨机晶振 ppm 级频偏会带来少量偏差；接收打点在用户态 `recvfrom` 返回处，含唤醒延迟。

回环还暴露了**用户态整流的天花板**：均值可控、尾延迟靠 OS 调度赏饭（那 10–65ms 的毛刺）。真要微秒级尾延迟得下沉到内核——Linux 的 `fq` qdisc 自带按发车时刻 pacing，`etf` qdisc 配合 `SO_TXTIME` 把发送时刻精确交给内核（真实命令形态，参数与适用条件以内核文档为准）：

```bash
tc qdisc replace dev wlan0 root fq                          # fq 自带 pacing
tc qdisc replace dev eth0 root etf delta 300000 clockid CLOCK_TAI   # ETF：SO_TXTIME 精确发车
```

## 7.4 TCP 的反向代价：ACK 也在抢空口

传输协议的选择本身就是一条 pacing 决策线。先看 TCP 在这个场景里多付的三笔钱：

```text
机器 A ──图像数据（大包，正向）───▶ 机器 B
机器 A ◀──TCP ACK（约 40B，反向）─ 机器 B    ← 反向也要走一次完整信道接入：
                                              DIFS→退避→前导→数据→SIFS→链路层 ACK
```

- **ACK 的空口账**：两台机器互传是双向大流量，每个方向的数据都拖着反方向的 ACK。TCP ACK 无应用载荷（IPv4+TCP 头约 40 字节），但 802.11 发它的固定成本一分不少——前导码、信道接入、SIFS 后的链路层 ACK 全照收。小包的空口效率极差，这笔账与 [[ch03-aggregation-ampdu|第三章]]算过的「每包固定开销」同源，只是方向反过来。延迟 ACK（典型实现每两个数据段回一个）只是缓解，不改变反向有流量的事实。
- **窗口爬坡与自发突发**：TCP 慢启动爬坡、稳态窗口锯齿（丢包型拥塞控制如 CUBIC，回退再冲）——每一轮冲高就是一次应用管不住的突发，正好撞上 7.1 说的突发放大器。
- **bufferbloat**：TCP 拼命填满驱动与网络栈队列，队列一满，空口时延跟着涨——这是 7.1「饱和排队」最典型的成因，而应用层几乎看不见它，只觉得「带宽没跑满，时延却炸了」。

决策线一张表：

| 场景                          | 建议            | 一句话理由                                              |
| ----------------------------- | --------------- | ------------------------------------------------------- |
| 实时预览/图传（可容忍丢帧）   | UDP＋应用层控制 | 节奏自己定（pacing/FEC/关键帧按需重传），时延不跟队列走 |
| 文件/录像回放（不可丢，不急） | TCP             | 可靠性交给协议栈，突发代价可接受                        |
| 双机互传（双向都是大流量）    | 优先 UDP        | 双向 ACK 挤占＋两边窗口锯齿互相激励，最差组合           |
| 跨互联网/未知路径             | TCP/QUIC        | 路径拥塞必须有人管——QUIC 的拥塞控制章正是为此           |

跨网那一行的展开：[[quic-deep-dive|QUIC 深度探索系列]]对拥塞控制的拆解（窗口、 pacing、丢包推断）值得单独一章去读——本章只取它的直觉。

拥塞控制的直觉一句话：AIMD——撞了（丢包/时延涨）就把速率砍半，再慢慢加回来；本质上是 TCP 在替你做 7.2 的事，只是它优化的是「路径吞吐」，不是「你这块空口的预算」。值得一提的是，现代拥塞控制（如 BBR）本身就内置 pacing 发送——协议演进从侧面印证了本章立场：**整流优于猛发**。取流场景里「RTP over UDP 还是 RTSP interleaved over TCP」的选择与这张决策线同构（[[onvif-deep-dive|ONVIF 协议深度解析]]的取流章节）；设备侧若在嵌入式协议栈上自建发送循环，令牌桶门放在 `sendto` 之前的思路完全一致（[[lwip-deep-dive|lwIP 深度解析系列]]的发送路径）。

## 7.5 结构性解法清单：不改速率，改棋盘

压速率解决的是「一条信道内怎么少抢」，还有一类问题只能改棋盘——让争抢根本不发生。四条出路与各自的适用条件：

| 解法          | 做法                                                            | 一句适用条件                         |
| ------------- | --------------------------------------------------------------- | ------------------------------------ |
| 信道规划      | 2.4G 只用 1/6/11 三个非重叠信道；能上 5G 就优先 5G              | 现场有邻网/多 BSS 且你能控制 AP 信道 |
| 双流拆信道    | 两路图传各占一个信道（双 AP 或 2.4G/5G 各一路），互不争抢       | 有双 AP/双频资源，接收端能分别接入   |
| 降频传输      | 图传帧率减半，空口占用近似减半                                  | 带宽预算紧、流畅度可让               |
| 有线回程/旁路 | 图传走网线/网桥，WiFi 只留控制面；或收发两端单独组 BSS 避开主网 | 能布线或能加一台交换机/AP            |

三条使用备注：

- **信道规划**：2.4G 的 1/6/11 才真正互不重叠，选 1 和 3 等于没拆；5G 信道多、常见家用干扰源少，但注意 DFS 信道有雷达避让的可用性问题。频段与信道宽度的物理细节见 [[wifi-rf-hw|WiFi 射频硬件入门]]的频段地图。
- **双流拆信道**：把 [[ch01-dcf-contention-basics|第一章]]里 N=2 的竞争直接拆成两个 N=1——每个信道里只剩一个发送者，退避与碰撞账几乎清零，是「多路图传」场景最彻底的一招。
- **降频传输**：占用≈码率线性（7.2 的表），30fps 降到 15fps 占用近似减半——纯算术关系，不用测；配合 [[ch05-rate-and-channel-width|第五章]]的速率与信道宽度调优一起做。有线回程则是唯一「不占」而非「少占」的选项——其余三条都在省，这一条是清零。

## 7.6 小结

- 争抢的根因在需求侧：**饱和排队**让站点永远在场竞争（时延还随队列堆积），**突发**制造瞬时饱和并被聚合放大成长占用块；ch01 E4 仿真证据——一站退成限速，碰撞时隙占比 1.17%→0.22%、对方吞吐 +34%。
- **压速率比调 MAC 参数值钱**：MAC 参数只改「抢的姿势」（CWmin 拉大 9 倍的代价是吞吐掉一半），压速率把竞争者请下牌桌。
- **令牌桶 pacing**：rate 定均值（对齐「实测可持续吞吐 × 0.7–0.8 量级」的预算，系数是工程经验非规范值），depth 定突发额度（按一帧摊平设计）；整流同时降碰撞（竞争者变少）与降抖动（队列与聚合块尺寸稳定）；码率-帧率-分辨率各旋钮对空口账的影响不同——码率线性、I 帧是脉冲源。
- **回环证据**（ch07-pacing-harness run.log）：burst 99.5% 到达 gap <100µs 微秒级聚簇 vs paced 79.2% 落在目标 ±5%——回环验证整流工具链与统计口径，空口画像要靠 `--ip`/`--rx-only` 真机同款命令现场量；用户态整流尾延迟靠 OS 调度，更严的要下沉 fq/ETF。
- **TCP 的反向代价**：ACK 挤占反向空口（小包固定成本照收）、窗口锯齿是自发突发、bufferbloat 喂饱饱和排队；实时图传选 UDP＋应用层控制，可靠不急选 TCP，跨互联网交给 TCP/QUIC 的拥塞控制（BBR 内置 pacing 是「整流优于猛发」的侧证）。
- **结构性解法四条**：信道规划（1/6/11、5G 优先、注意 DFS）、双流拆信道（N=2 拆成两个 N=1）、降频传输（占用≈码率线性）、有线回程/旁路（唯一清零项）——每条都有适用条件，先看手里有什么资源再选。
