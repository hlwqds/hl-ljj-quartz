# WiFi 空口调度实战（八）：排错手册——决策树与杠杆清单

前七章是把空口一层层拆开看：竞争怎么发生（[[ch01-dcf-contention-basics|第一章]]）、怎么测量（[[ch02-measuring-airtime|第二章]]）、聚合/EDCA/速率/公平性/pacing 各自怎么调（第三到七章）。这一章反过来：现场已经出了问题——两台机器互传图像，互相拖死、掉帧、卡顿——从症状出发往回找杠杆。回答三个问题：**症状落到哪条分支**（8.1 决策树）、**按什么顺序查**（8.2/8.3 十步流程）、**手里六根杠杆先动哪根**（8.4 总排序）。最后把本系列放回整个仓库的坐标系：空口的上面和下面，各有哪些姊妹系列接手（8.5）。

## 8.1 从症状到杠杆：一棵决策树

先立两条纪律，它们比树本身更重要：

- **先测量后动手**——[[ch02-measuring-airtime|第二章]]的三件套把「感觉很卡」换成读数：`survey dump`（信道占用率）、`station dump`（链路质量：信号/速率/重传）、monitor 模式抓包（帧级证据）。决策树的每个分支口都立着其中一件；
- **症状会叠加，按最痛的先来**——改一处，复测一次三件套，再动下一处。同时拧三个旋钮的排错等于没排。

四个症状入口，各自的「先查什么」与落点：

```text
症状入口（挑当前最痛的一个起手；改一处，复测一处）
│
├─ 互相拖死：两台单独传都正常，同时传双双变慢
│    先查：survey dump 占用率（三件套之一）
│    ├─ busy/active 偏高（经验量级，非规范阈值）→ 空口总量不足
│    │    → 杠杆① 应用层 pacing 与图传参数（ch07）
│    │      仍不够 → 杠杆② 分信道（ch05/ch06）
│    └─ busy/active 不高 → 争抢开销（重传/碎片帧）占大头
│         → 进 8.2 第 4 步「重传归因」
│
├─ 单边慢：一头接近满速，另一头始终上不去
│    先查：station dump 两侧 signal + tx/rx bitrate
│    ├─ 慢的一头信号也弱 → 链路预算不足（距离/遮挡/天线）
│    │    → 杠杆④ 速率与带宽选择，配合挪位/换天线
│    └─ 信号不差但 bitrate 钉在低档 → 协商没谈好或聚合未生效
│         → 杠杆③ 聚合核查、④ 锁定高速率档
│
├─ 时延抖：吞吐尚可，ping 毛刺、交互卡顿
│    先查：get power_save + 重传率 + 谁在长时间占空口
│    ├─ 省电 on → 缓冲转发引入的抖动 → 关掉复测
│    ├─ 对端长帧突发独占发送机会 → 杠杆⑤ WMM 标记 + ① pacing
│    └─ 重传毛刺 → 同「重传归因」分支
│
└─ 掉帧：图像缺帧/马赛克（应用层可见）
     先查：应用层帧计数 vs station dump 的 tx failed
     ├─ tx failed 同步增长 → 链路在丢 → 信号/速率杠杆（④）
     └─ 链路没丢、应用在丢 → 发送侧队列溢出，帧没来得及上线
          → 杠杆① 降帧率/码率 + pacing 摊平 I 帧突发
```

读树的两点说明：其一，「互相拖死」与「掉帧」经常是同一个病——总量不足时应用层先表现为丢帧、链路层表现为排队，所以两条分支最终都汇回占用率与重传这两个读数；其二，「单边慢」要先分清是**哪一侧**慢——WiFi 半双工，发送与接收共享同一份信道时间，一头快一头慢常常不是公平性问题而是两侧链路质量不对称。

## 8.2 十步流程（上）：测量与归因

十步的总纲：**便宜的先做**。测量（1–3）几乎零成本，归因（4–5）只需要读数与抓包，核查（6–8）是配置检查，动手（9–10）才改网络形态。前五步先把命令底账立起来——三件套加两个补充项，都在任一台机器上执行（`wlan0` 换成实际接口名）：

```bash
iw dev wlan0 link           # 当前 BSS/信道/宽度/信号
iw dev wlan0 survey dump    # 信道占用率：两次采样相减再除以间隔才是速率
iw dev wlan0 station dump   # 对端：signal / tx bitrate / tx retries / tx failed
iw dev wlan0 get power_save # 省电状态（时延抖的常客）
iw dev wlan0 scan dump      # 邻居 BSS 与信号（竞争环境底账）

# monitor 模式：帧级证据（按发送方聚合的重传分布）
iw dev wlan0 interface add mon0 type monitor
ip link set mon0 up
tshark -i mon0 -Y 'wlan.fc.retry == 1' -T fields -e wlan.ta \
  | sort | uniq -c | sort -rn
```

`survey dump` 的读数字段形态如下（数值以现场采样为准，差值才是占用率）：

```text
frequency:              5180 MHz
channel active time:    <ms>    ← 采样窗口内信道活跃时长（分母）
busy time:              <ms>    ← 其中被占用时长（分子）
receive time:           <ms>
transmit time:          <ms>    ← 本机发送占用的部分
noise:                  <-dBm>  ← 噪声底
```

前五步的查什么/判读/分支：

| 步  | 查什么   | 手段                                            | 判读 → 分支                                                                    |
| --- | -------- | ----------------------------------------------- | ------------------------------------------------------------------------------ |
| 1   | 占用率   | `survey dump` 两次采样取差值                    | busy/active 高（>70%，ch02 判定线）→ 空口不足，直奔第 9/10 步；不高 → 走 3     |
| 2   | 邻居环境 | `scan dump` 看同信道 BSS 数量与信号             | 同信道 BSS 多、噪声底高 → 竞争/干扰环境，第 10 步权重↑；干净 → 走 3            |
| 3   | 信号底账 | `station dump` 两侧 `signal` 与 `tx/rx bitrate` | 慢的一头信号也弱（量级参考 -70 dBm 以下开始紧张）→ 覆盖问题，走 5；不差 → 走 4 |
| 4   | 重传归因 | `tx retries`/`tx failed` + retry 位抓包分布     | 信号好+重传高 → 碰撞/干扰；信号差+重传高 → 覆盖/速率不匹配，走 5               |
| 5   | 速率带宽 | `iw dev wlan0 link` 的宽度字段与协商 MCS        | 钉低档或宽度退化（80→20 MHz）→ ch05 杠杆；速率正常仍慢 → 走 6                  |

第 4 步是全流程的岔路口，展开说。**信号与重传的组合是归因的两把尺子**：信号读数好、重传却高，说明帧在半路被打——同信道碰撞或非 WiFi 干扰（微波炉、蓝牙），前者第 2 步的邻居底账有线索，后者要靠频谱视角，交给 [[wifi-rf-hw|WiFi 射频硬件入门]]的干扰共存与测量两章；信号读数差、重传也高，则是链路预算问题——距离、遮挡或天线，先挪位置再谈参数。retry 位抓包的按发送方聚合输出，还能回答「重传是谁贡献的」：如果集中在某一台慢设备上，问题多半在那台的链路质量，而不是信道总量。

## 8.3 十步流程（下）：核查与落地

后五步从读数转向配置。核查三件事（6–8），动手两件事（9–10）：

| 步  | 查什么      | 手段                                                                            | 判读 → 分支                                                 |
| --- | ----------- | ------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| 6   | 聚合核查    | `iw list` 的 A-MPDU 能力；mac80211 调试文件系统有逐站聚合状态（路径随内核版本） | 高 MCS 却吞吐低、发送碎片化 → 聚合被关闭或被省电打断 → ch03 |
| 7   | 省电状态    | `iw dev wlan0 get power_save`                                                   | on → 图传/低时延场景先关掉复测（时延抖的常见来源）          |
| 8   | 优先级落点  | 抓包看 QoS Data 的 TID 分布；应用是否给控制流打标                               | 控制小包与图传大包同挤 BE → WMM 杠杆（ch04）+ DSCP 标记     |
| 9   | pacing 落地 | `tc` 整形 + 应用层定速 + 图传参数（帧率/码率/GOP）                              | 摊平 I 帧突发，反向小包时延立降 → 复测三件套确认            |
| 10  | 分信道      | 换 AP 信道/双频分流/第二个 AP；自组场景 `iw dev wlan0 set channel 36 HT20`      | 前九步做完仍顶到占用率天花板 → 把介质从共享变独占，量级收益 |

第 9 步的具体形态，[[ch07-pacing-and-structure|第七章]]有完整论证，这里给可复现的最小命令：

```bash
# 发送侧 pacing：fq 整形 + 上限速率（数值用第 1 步实测占用率回填）
tc qdisc replace dev wlan0 root fq maxrate 40mbit
# 多队列无线网卡上 root fq 可能报错，改挂 mq 各子队列（形态见 ch07）

# 控制流打上 EF，交给 AP 的 DSCP→WMM 映射（方向示例）
iptables -t mangle -A OUTPUT -p udp --dport 5000 -j DSCP --set-dscp-class EF
```

AP 侧的 WMM 配置方向（hostapd 字段名真实存在；典型默认值以规范版本与设备实现为准）：

```text
wmm_enabled=1
wmm_ac_vi_aifs=2
wmm_ac_vi_cwmin=3
wmm_ac_vi_cwmax=4
wmm_ac_vi_txop_limit=94       # 3/4 为指数（CW=7/15）；94×32µs=3008µs，AC_VO 为 47×32µs=1504µs
```

第 10 步的「分信道」在双机图传场景有三种形态，按控制权从大到小：**换 AP 信道**（对 AP 有管理权时，挑 `scan dump` 里最干净的信道）；**双频分流**（两台机器或两路流量分别落在 2.4/5 GHz，同一台双频 AP 就能做到）；**第二 BSS/自组点对点**（AP 不可控时的 workaround）。注意 managed 模式接口的信道跟随 AP，`set channel` 只适用于自组/监视场景。

## 8.4 杠杆清单总排序：投入产出视角

把前七章的杠杆摊开，按「单位投入换来的确定性收益」排序：

| 序  | 杠杆                     | 一句话理由                                         | 成本/前置               | 详见      |
| --- | ------------------------ | -------------------------------------------------- | ----------------------- | --------- |
| ①   | 应用层 pacing 与图传参数 | 需求侧减量：发得少、发得匀，不动网络就有收益       | 改几行代码/几个编码参数 | ch07      |
| ②   | 信道规划/分信道          | 供给侧扩容：介质从共享变独占，网络侧量级最大的收益 | 需要对 AP/频谱有控制权  | ch05/ch06 |
| ③   | 聚合确认                 | 拿回本该有的效率，多数场景只是确认它没被关掉       | 低                      | ch03      |
| ④   | 速率与带宽               | 收益场景化，锁错档位反而伤鲁棒性                   | 中，需实测回填          | ch05      |
| ⑤   | WMM 标记                 | 只重排队不增产：救时延，不救吞吐                   | 低                      | ch04      |
| ⑥   | ATF/信道时间调度         | 多客户端与低速受害者场景才显效，固件支持参差       | 高                      | ch06      |

这个默认排序不是教条，四种典型场景要重排：

- **网络不可控**（现场用的是别人的 AP）→ ② 沦为「给业主的建议」，能动只剩终端侧：①③⑤ 前移；
- **多客户端且混有低速率设备**（[[ch06-airtime-fairness|第六章]]的经典问题：一个慢客户端拖住整个信道）→ ⑥ 与 ② 前移，先隔离慢设备或启用信道时间调度；
- **时延敏感控制流与图传并存** → ⑤ 提到 ① 之后——先把小包从大帧队尾救出来，再谈减量；
- **频段环境脏**（微波炉/蓝牙/邻道拥挤）→ ② 回到最前——先离开噪声源，其余杠杆的收益才有意义。

排序的本质是决策树的倒影：决策树从症状找到杠杆，排序回答「多个杠杆同时可用时先拉哪根」。共同底线仍是 8.1 的两条纪律——先测量，改一处复测一处。

## 8.6 小结

- **决策树**：互相拖死先查占用率，单边慢先查两侧信号与速率，时延抖先查省电与重传，掉帧先分清链路丢还是发送侧丢——四个入口最终都汇回占用率与重传两个读数。
- **十步流程**：survey dump 起手、分信道收官；顺序本身就是投入产出排序——测量与归因（1–5）先于核查（6–8），先于动手（9–10）。
- **杠杆总排序**：应用层 pacing 与图传参数 > 信道规划/分信道 > 聚合确认 > 速率与带宽 > WMM 标记 > ATF；按「网络是否可控、是否多客户端混低速、是否时延敏感、频段是否脏」四个维度重排。
- **衔接地图**：空口只是栈中的一层——往下是射频物理，往上是设备协议栈、传输层与取流应用；排错的线头常常要拉到层外，才知道去哪个系列找答案。

空口是共享介质，半双工、全队可见——这是本系列第一句话的前提，也是最后一句的结论：「调度」并不住在某一个旋钮里，它分布在讲过的每一层：DCF 的退避时钟（ch01）、聚合的批次（ch03）、EDCA 的队列（ch04）、速率档位（ch05）、AP 的信道时间分配（ch06）、应用层的发送节奏（ch07），全都在对同一份稀缺资源排队。双机图传的健康终态，因此可以用三件套的三行读数来定义：**占用率可控、重传低、时延平稳**——三者同时成立，速率与画质只是这三行的推论。

本章与全系列给出的阈值（占用率的经验量级、信号的分界、TXOP 典型值）都是待校准的先验，不是规范条文。真机落地时，请用自己现场的三件套读数回填各章——把排错过程沉淀成 run.log 里的实测数字，决策树才会长在你自己的数据上。这也是这本手册期待的后续：不是下一章，而是下一次测量。
