# F429 × Korvo-1（五）：控制通道——TLV 命令与异步事件

帧层（ch03）给了我们"可靠的信封"，现在定义信里写什么。控制通道负责一切**低频、请求-应答式**的交互：查状态、扫网、入网、解析域名——它是 F429 的远程驾驶舱。这一章定四件事：命令的线格式（5.1 TLV）、最小命令集（5.2）、请求-应答的会话规则（5.3）、以及大载荷与异步事件两个边角（5.4）。编解码全部本机实测。

---

## 5.1 线格式：TLV 的纪律

控制帧的载荷用 **TLV（Type-Length-Value）**组织——每个字段自描述长度，增删字段不破坏兼容：

```text
请求帧载荷：
┌─────────┬─────────┬─────────┬──────────────┐
│ cmd(2B) │ req_id(2B) │ 参数 TLV 序列 ……      │
└─────────┴─────────┴─────────┴──────────────┘
应答帧载荷：
┌─────────┬─────────┬─────────┬──────────────┐
│ cmd(2B) │ req_id(2B) │ status(1B) │ 结果 TLV │
└─────────┴─────────┴─────────┴──────────────┘
每个 TLV：[type(1B)][len(2B)][value(lenB)]，参数顺序无关、未知 type 跳过不报错
```

三条纪律值得写死在两侧代码的注释里：**所有多字节字段网络序（大端）**——两侧 CPU 都是小编，但协议序是协议序，别给未来埋雷；**len 是 value 的字节数不含自己**——对不上就是线协议 bug，直接断言；**status 用枚举留一段用户区**——0x40 起给"应用层错误"（如 DNS 查询失败、无凭证），0x00–0x0F 保留给链路/协议层。

## 5.2 最小命令集：每条命令的"为什么"

命令不在多，在每条都物有所值：

| cmd  | 名称   | 请求参数         | 应答结果                    | 为什么需要它                                  |
| ---- | ------ | ---------------- | --------------------------- | --------------------------------------------- |
| 0x01 | PING   | 任意 4B          | 原样回                      | 链路 RTT 与存活探测（联调第一课 + 看门狗）    |
| 0x02 | STATUS | —                | 状态机态/RSSI/SSID/BSSID/IP | F429 的仪表盘；重连后对齐世界                 |
| 0x03 | SCAN   | 通道/SSID 过滤   | AP 列表（分片，见 5.4）     | 入网前的选择；也是"协处理器真的在干活"的证据  |
| 0x04 | JOIN   | SSID/密码（TLV） | 受理/最终结果               | 凭证下发：换网不刷机（ch04 的承诺兑现）       |
| 0x05 | DNS    | 域名             | IPv4                        | S3 的解析器借给 F429（socket 代理的前置）     |
| 0x40 | EVENT  | （S3→F429 专用） | —                           | 事件帧：LINK_UP/DOWN/SCAN_DONE 的通知编号空间 |

设计口味说明：**REQ/RSP 同 cmd 复用**（应答靠 type=控制应答帧 + req_id 关联），而不是为每条命令发明两个号——编号空间是协议的稀缺资源，省着花。

## 5.3 会话规则：req_id 表 + 超时

请求-应答跨一条不可靠链路，需要一张"未决请求表"：

```text
F429 发起方：
  req_id 自增；登记 [req_id → 命令、发出时间、回调/信号量]
  200ms 无应答 → 重发（ch03 可靠帧的重传兜底；应用层再兜一层）
  三次无应答   → 返回 LINK_TIMEOUT，交上层决策（重启 S3？切 UART 兜底？）
S3 应答方：
  收到即解析执行；应答帧原样带回 req_id——无状态、可乱序应答
  （耗时命令如 SCAN 先回"受理"，结果用事件帧送——见 5.4）
```

req_id 用 2 字节回绕即可（65536 个未决请求早已超过队列容量）；两侧对称的编码器/解码器放在同一个 `control.c` 里、两侧共用一份源文件——**联调省命法则**第二次出场（ch03 的 crc32.c 同理）。

## 5.4 两个边角：大载荷与异步事件

**扫描列表分片**：一次扫描十几个 AP，SSID 都是 32 字节上限，TLV 总长轻松破 480B 帧上限（ch03）。解法是"受理-分片-汇总"三步：SCAN 请求先得一个 `ACCEPTED` 应答带总片数，结果以 `SCAN_RESULT` 事件帧逐片推送（片号 + 单个 AP 的 TLV），F429 攒齐触发回调。**长应答一律事件化**，是嵌入式命令协议的通用手法。

**事件编号空间**：EVENT 帧（cmd=0x40）的载荷是 `[event_id(1B)][TLV…]`，独立于请求-应答：LINK_UP（带 IP）、LINK_DOWN（带原因）、SCAN_DONE、SOCK_DATA（ch06 的数据通知）。事件是 S3 的主动话语权——**协处理器不是只应答的哑终端，它会主动汇报世界的变化**。

## 5.5 小结

- 控制载荷 TLV 化：字段自描述、增删兼容、未知 type 跳过；网络序、len 语义、状态码分区三条纪律焊死。
- 最小命令集六条（PING/STATUS/SCAN/JOIN/DNS/EVENT），每条都为后续章节供能；REQ/RSP 同 cmd 复用，编号空间省着花。
- 会话规则：req_id 未决表 + 双层超时重试；应答方无状态。
- 长应答一律事件化分片（受理→逐片推送→汇聚）；事件帧是 S3 的主动话语权。
- 两侧共用同一份 control.c——协议零件同源，联调省命。
