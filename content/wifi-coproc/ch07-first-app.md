# F429 × Korvo-1（七）：总装——NTP 校时与 HTTP 下载

六个零件（链路/帧/状态机/控制/事件/代理）全部就位，这一章点火整机：两个经典应用，各自验收链路的一组能力。**NTP 校时**走 UDP 一问一答，考的是"控制通道 + UDP 代理 + 超时重试"；**HTTP 下载**走 TCP 流式拉取，考的是"连接保持 + 分帧重组 + 背压消费 + 完整性对账"。前者 3 秒能通，后者通了才有资格谈性能（ch08）。

---

## 7.0 启动时序：整机点火序列

两个应用共同的前置是把整机按正确顺序拉起来——这张时序图就是系统的"总装图"：

```text
F429                          S3(Korvo-1)
 │ 上电 → 外设/DMA/EXTI 初始化    │ 上电 → 任务拓扑启动，SPI 从机挂队列
 │ ───── PING（重试直至应答）────▶ │   ← 链路心跳 + 双方就绪判定
 │ ◀──────────── PONG ──────────┤
 │ ───── STATUS ────────────────▶ │   版本协商（帧协议 ver）+ WiFi 当前态
 │ ◀── CONNECTED(IP=…) 或 IDLE ──┤
 │ （若 IDLE：SCAN → 选择 → JOIN）  │   状态机走 ch04 的迁移图
 │ ◀────── LINK_UP(IP) 事件 ──────┤
 │ === 链路层与网络层双双就绪 ===   │
 │ ───── DNS("pool.ntp.org") ────▶ │
 │ ◀──────── IPv4 ───────────────┤
 │ ws_socket(UDP)/connect/send…   │   应用自由区
```

版本协商藏在 STATUS 里（TLV 带 `proto_ver`）：**两侧帧协议版本不一致要当场报错**，而不是跑起来出一堆诡异坏帧——"启动时对表"是跨芯片协议的第一课。

## 7.1 应用一：NTP 校时

NTP 的协议本体只有 48 字节请求/应答（LI/VN/Mode + 时间戳），选它因为**一次交互覆盖全链路五层**：

```c
/* F429 侧，ws_* API 视角——除名字外与你熟悉的 socket 无异 */
uint8_t ip[4];
ws_dns("pool.ntp.org", ip);                 /* ① 控制通道：DNS 借力          */
int s = ws_socket(SOCK_DGRAM);              /* ② 代理：UDP socket           */
ws_connect(s, ip, 123);
build_ntp_request(pkt);                     /* LI=0 VN=4 Mode=3，全是 0 就行 */
ws_send(s, pkt, 48);                        /* ③ 数据通道出                  */
int n = ws_recv(s, buf, sizeof buf);        /* ④ 数据通道回（事件驱动唤醒）   */
/* ⑤ 从应答的 Transmit Timestamp(40..47B) 换算 Unix 秒 → 写 F429 RTC      */
```

工程要点两个：**超时与重试**（UDP 天然会丢，2 秒无应答重发、三次换服务器——DNS 再解析一次即可）；**时区与 RTC**（NTP 给的是 UTC 秒，F429 的 RTC 寄存器按本地时区换算写入，秒进位抖动 ±1s 属正常——校时精度不是本系列目标，链路验收才是）。

## 7.2 应用二：HTTP 下载

比 NTP 难一个量级：**长流、多帧、要背压、要校验**。流程与关注点：

```text
ws_dns + ws_socket(TCP) + ws_connect(:80)
  → 发 "GET /bigfile.bin HTTP/1.0\r\nHost:…\r\n\r\n"（一次性小 send）
  → 循环 ws_recv：
      状态机先过响应头（找 200 与 Content-Length，\r\n\r\n 定界）
      之后全是体——按收到即消费（写 TF 卡 / 喂 SHA-1）
  → recv 返回 0（EOF）→ 下载完成
  → SHA-1(本地结果) 对比服务端公布/预存的摘要（p2p-labs 的老规矩，跨工程复用）
```

三个验收指标同时记录：**总字节与 Content-Length 对账**（分帧重组正确性）、**SHA-1 一致**（数据完整性过 CRC 之上的第二重保险）、**总耗时与均速**（ch08 的基线数据第一次落袋）。背压在这里是"隐形考题"：F429 写 TF 卡慢于 WiFi 收包时，三闸门应自动让链路降速、S3 内存平稳——**压测时盯一眼 S3 侧的水位计数器，它不动就说明背压没工作**。

## 7.3 基线对照：三条路的吞吐

F429 实验室已经跑过两条联网路（[[f429-lab|F429 实验室]]ch20/21 板载以太网、ch22 与 ESP 直连对照），加上本系列的第三条，基线表如下（量级示意，具体以各章实测为准）：

| 路               | 链路             | 协议栈位置                  | 吞吐量级                          |
| ---------------- | ---------------- | --------------------------- | --------------------------------- |
| 板载以太网       | RMII + PHY       | F429 本地 lwIP              | 10 Mbps 档（ch21 基线）           |
| ESP 直连（ch22） | 应用与 WiFi 同芯 | ESP 本地 lwIP               | ESP32 射频上限档                  |
| **本系列**       | **SPI 代理**     | **S3 本地 lwIP + 跨河 RPC** | **SPI 与代理开销决定，ch08 实测** |

第三条路注定不是最快，但它是**唯一可移植的**：换掉 F429、换掉 SPI，协议栈照跑——这份通用性是 ch09 树莓派延伸的伏笔。

## 7.4 小结

- 启动时序先对表再干活：PING 判链路、STATUS 带版本协商、按需 SCAN/JOIN；帧协议版本不符要当场报错。
- NTP 一问一答覆盖全链路五层，重点练超时重试与 DNS 借力；校时精度让位于链路验收。
- HTTP 下载考长流：响应头解析、按收即消费、EOF 语义、SHA-1 对账；背压是否工作看 S3 水位计数器是否"不动如山"。
- 三条联网路各有站位：以太网最快、同芯直连最省、SPI 代理最可移植——吞吐让位给通用性。

链路通了、应用跑了，下一章把这口锅烧到最热：SPI 时钟从 0.33 MHz 逐档爬坡找实物极限、DMA 双缓冲的乒乓间隙怎么压到最小、吞吐-延迟曲线怎么画、断电拔线重启 S3 的稳定性剧本怎么写——性能与稳定，是玩具与工具的分界线。[[ch08-performance|第八章：性能]]。
