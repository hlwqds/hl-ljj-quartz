## 1.1 三个现场：软件栈排到底之后

先看三个现场（**教学复盘案例，取材自常见故障模式综述**——团队与产品均属合成，把多起常见故障折进同一条叙述线，便于提炼方法）。

**现场 A：满格却频繁掉线的新品**。某团队新品内测，手机信号满格，用着用着就断。软件侧把该查的全查了：驱动版本回滚对比、wpa_supplicant 配置逐行审、漫游参数一组组试，两周不收敛。最后在结构装配环节找到答案：天线馈线的 IPEX 端子在整机组装时被结构件压伤，接触状态随装配应力漂移——天线链路上的机械性病灶（第八章的案例类型）。

**现场 B：客户家实测正常，他家拉胯**。同一款产品、同一套固件：A 客户家信号强、视频流畅；B 客户家信号弱一截、视频卡顿。固件背了两周的锅，最后用手机 WiFi 分析仪站在 B 客户家里看了一眼：2.4 GHz 频段上挤着成片的邻居 AP——环境侧的同频占用，与固件无关（干扰概念见 [[ch14-interference-coexistence|射频入门（十四）]]，取证手法见第六章）。

**现场 C：量产前过不了预测试**。认证实验室的报告发回来：杂散超标。团队第一反应是降功率硬压——功率压下去了，调制质量又被拖到限值边缘。回头复盘，问题在设计期就埋下了：滤波与布局余量不足，只是到预测试这一关才被迫现形（第七、十一章的案例类型）。

三个现场的共同点：团队最先动用的都是软件侧排查——而且都不算白干，是**排完软件侧之后**剩下的硬骨头。把三类症状的两侧排查对照成表（本系列对 [[wifi-rf-hw|射频硬件入门]] 第一章同主题表的实战版改写——那章教你「认识部件」，本章起假设你已认识，重点是「怎么查」）：

| 症状             | 软件侧你排到底时查过的       | 硬件侧剩下的真相                     | 本系列哪章   |
| ---------------- | ---------------------------- | ------------------------------------ | ------------ |
| 满格却频繁掉线   | 驱动版本、漫游参数、保活配置 | 天线馈线压伤、净空区被结构遮挡       | 第八、五章   |
| 他家正常你家拉胯 | 固件升级、重置配置、复测多台 | 邻居信道占用、金属结构、覆盖盲区     | 第六、八章   |
| 量产前预测试不过 | （软件侧基本无从下手）       | 杂散、功率、带宽余量——设计期埋下的雷 | 第七、十一章 |
| 一发射就整机复位 | 看门狗、任务栈、电源管理策略 | 发射瞬态电流拉低电压触发 brownout    | 第九章       |

## 1.2 症状五分类：把「WiFi 不行」翻译成排查路径

用户说「WiFi 不行」没有任何排查价值，第一步是翻译。可感知的症状归成五类（与 [[wifi-hw-debug|系列索引]] 的章节地图一致），每类给「第一反应动作」与「最容易走的弯路」：

| 症状分类        | 典型表现                              | 第一反应动作                                                                            | 最容易走的弯路                                               | 对应章节                                                                                         |
| --------------- | ------------------------------------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ |
| **连不上**      | 扫不到 SSID、认证/关联失败、卡在 DHCP | `wpa_cli -i wlan0 status` 看 `wpa_state` 卡在哪一态；`iw dev wlan0 scan` 确认 SSID 可见 | 上来就恢复出厂/改密码——现场被破坏，复现条件先没了            | [[wifi-hw-debug-ch04-cannot-associate\|第四章]]                                                  |
| **掉线/漫游差** | 用着用着断、跨房间断、漫游乒乓        | `dmesg -T` 与 `journalctl` 拉断连事件与原因码时间线                                     | 调大保活/重试参数把症状藏起来；只看站端日志不看空口          | [[wifi-hw-debug-ch05-disconnect-roaming\|第五章]]                                                |
| **慢**          | 连上了但吞吐低、延迟大                | `iw dev wlan0 link` 记 RSSI 与协商速率，`iperf3` 建吞吐基线                             | 反复刷测速网页取最好成绩；直接怪运营商带宽                   | [[wifi-hw-debug-ch06-throughput-debugging\|第六章]]                                              |
| **功耗/电源类** | 发射瞬间复位、续航与规格差一个量级    | 把复位时刻与 WiFi 事件对时（`dmesg -T` 时间戳）                                         | 用万用表找毫秒级电流毛刺（带宽根本看不见）；先怀疑电池与算法 | [[wifi-hw-debug-ch09-power-integrity\|第九章]]、[[wifi-hw-debug-ch10-power-consumption\|第十章]] |
| **认证不过**    | 预测试 fail：功率/杂散/带宽           | 逐条读 fail 项对应的限值线与测量口径，先分设计余量问题还是测法问题                      | 盲目降功率硬压杂散；直接送正式实验室烧钱试错                 | [[wifi-hw-debug-ch11-precompliance\|第十一章]]                                                   |

三条读表说明。其一，**分类依据是用户可感知的现象，不是根因**——同一个根因（比如天线馈线压伤）在不同现场可以呈现为三类症状：轻则慢、重则掉线、再重则连不上。分类只是入口，下钻才是路。其二，每类的「第一反应动作」都是下一节 L1/L3 级的取证，成本几乎为零——先花十分钟，再谈动手。其三，「最容易走的弯路」有一半是同一类错误：**在证据链闭合之前先动了手**，把现场改掉了。

> [!tip] 先分类，再下钻
> 拿到问题先问一句：这属于五类里的哪一类？答不上来就回 L1 把现象钉死（1.3.1）——分类都定不了的问题，谈不上定位。

## 1.3 分层取证框架：L1 到 L4

五分类解决「从哪类入手」，分层解决「证据到哪找」。入门系列的「四问下钻」是认知框架（为理解设计而设），这里是**取证顺序**（为定位故障而设）：从信息最便宜的一层开始，每层回答一个问题，回答不了才往下走。

```text
L1 观测层     —— 用户看得到什么？RSSI、速率、断连频次、时间点
L2 协议层     —— 空口发生了什么？beacon/认证/关联/4-way/deauth 逐帧看
L3 驱动固件层 —— 站端怎么说？事件、错误码、重试计数、固件断言
L4 射频电路层 —— 物理层健康吗？功率、EVM、频偏、VSWR、电源毛刺
```

总表先行，逐层展开在后：

| 层            | 回答的问题     | 主力工具                                          | 取证成本                 | 输出证据                   | 证据可信度与边界                               |
| ------------- | -------------- | ------------------------------------------------- | ------------------------ | -------------------------- | ---------------------------------------------- |
| L1 观测层     | 现象是什么样   | 手机 App、路由器后台、`iw`/`ping`                 | 极低（分钟级，¥0）       | 带时间戳的基线             | 指示器不是根因；RSSI ≠ 信噪比                  |
| L2 协议层     | 空口发生了什么 | 监听网卡 + Wireshark/`tcpdump`                    | 低（几十元 + 半天学习）  | 帧级 pcap                  | 时间因果最可信；单网卡单信道，有视野盲区       |
| L3 驱动固件层 | 设备自己怎么说 | `dmesg`/`journalctl`/`wpa_cli` 事件/debugfs/串口  | 低（¥0，但需设备访问权） | 事件时间线、错误码、计数器 | 驱动只报告它知道的；固件断言一旦出现即是决定性 |
| L4 射频电路层 | 物理层健康吗   | 频谱仪、矢网、示波器 + 电流探头、U.FL 转 SMA 工装 | 高（仪器/租借/送测）     | 可与限值逐条对比的测量数值 | 最权威，但测量口径错误会造成「权威的错误」     |

### 1.3.1 L1 观测层：先把现象钉死

十分钟、零成本，把「不行」变成带时间戳的数据：

```bash
# 站端：连接质量一屏看清（信号、协商速率、信道）
iw dev wlan0 link
cat /proc/net/wireless                 # 内核视角的信号质量，脚本友好
# 丢包/延迟随时间曲线，-D 给每行打时间戳，tee 存档作基线
ping -i 0.2 -D 192.168.1.1 | tee baseline-ping.log
```

再加两路旁证：手机 WiFi 分析仪 App 看当前信道挤不挤；路由器管理后台看已连接站点列表与信号粗值。L1 的产出是一条**基线**——它是 1.5 纪律二的前提，也是后面每一层验证「改动是否有效」的对照组。

被测设备是嵌入式站端（ESP32 一类、没有 shell）时，L1 的手法换形不换义：`esp_wifi_sta_get_ap_info()` 返回当前 AP 的 RSSI 等链路信息，事件流里的连接状态变化自带时间戳，路由器后台的站点列表就是它的外部观测口。L1 的定义是「把现象钉死」，不是「非 Linux 不可」。

L1 的可信度边界要背下来：RSSI 只是接收强度，**高 RSSI 不等于好链路**——同信道邻居拥挤时，满格照样烂（信噪比与速率协商的关系见 [[ch03-decibel-family|射频入门（三）]] 的 dB 语言，第六章实操）；手机 App 的信道占用是采样型粗测，能看「挤不挤」，看不了「谁在重传」；图形界面的「信号格数」是厂商的用户体验刻度，不是工程数据。

> [!warning] L1 的最大陷阱
> 现象没钉死就开始改：换了信道「好像好点」、挪了位置「似乎稳了」——全部作废。没有基线，后面每一层都无法判定改动有没有效果，你只是在掷硬币。

### 1.3.2 L2 协议层：空口的逐帧真话

802.11 的每个动作——beacon、认证、关联、4-way 握手、deauth——都写在空口上。一块支持监听模式的网卡 + Wireshark，就能旁听全部过程：

```bash
# 用支持监听模式的接口创建 mon0（网卡选购与验证见第三章）
iw dev wlan0 interface add mon0 type monitor
ip link set mon0 up
iw dev mon0 set freq 2437              # 停在 6 号信道（2437 MHz）
# 只抓管理帧里的 deauth（第四章起按状态机阶段细化过滤）
tcpdump -i mon0 -y IEEE802_11_RADIO 'type mgt subtype deauth' -w deauth.pcap
```

L2 能回答 L1 答不了的问题：AP 还在不在发 beacon？认证/关联交互停在哪一帧？4-way 握手有没有走完？deauth 帧的原因码是什么（第五章全解读）？空口重传比例多少？「谁先动的手」——是 AP 主动踢人，还是站端先消失——在帧级时间线里一目了然。

成本与可信度：一块监听 USB 网卡几十元级（第三章给选购与验证方法），外加半天到一天学会 Wireshark 的 802.11 解析与 WPA 解密；输出是帧级 pcap，**时间戳精度与因果可信度全场最高**。三条边界：加密帧看不到数据内容（持有密钥才能解密，第三章给方法）；单网卡单信道——跨信道漫游、双频切换的瞬间你只守得着一个信道，「pcap 里没有」不等于「空口没发生」；抓包点离被测设备越远，看到的越是双方视角的并集，而非任一方的真实视角。

实战里最常见的 L2 配置是**双网卡双角色**：一块保持正常连接当 STA（被观测对象），另一块专职监听（sniffer）——这样取证过程中业务不断，且观测者与被观测者解耦。1.4 的百元档「一块监听网卡 + 对端」配的就是这套阵型；只带一块卡时，监听期间本机断网，别忘了这也是一种变量。

### 1.3.3 L3 驱动固件层：设备的自述

设备自己也有一份说法——事件流、错误码、计数器：

```bash
# 内核无线子系统的事件流，-T 给出可读时间戳
dmesg -T -w | grep -iE 'wlan|deauth|disconnect'
# NetworkManager 的会话日志（无 NM 的系统看 wpa_supplicant 单元）
journalctl -u NetworkManager --since "2 hours ago" | grep -iE 'reason|deauth'
# mac80211 统计计数器目录：每个文件是一个计数（重传、失败帧），需 root
sudo ls /sys/kernel/debug/ieee80211/phy0/statistics/
```

ESP32 侧同理：`idf.py monitor` 里的 `esp_wifi` 事件流（`WIFI_EVENT_STA_DISCONNECTED` 等）就是站端的 L3 自述，事件模型 [[ch16-wifi-events|BOX-3（十六）]] 已拆过一遍，第五章会把这份自述与空口帧逐条对时。驱动边界（协议栈与 WiFi 驱动的接缝）见 [[ch18-esp32-wifi-lwip-integration|lwIP（十八）]]。

成本与可信度：¥0，但需要设备访问权——串口控制台、SSH 或 root；输出是事件时间线、原因码、重试/失败计数，以及**固件断言（firmware assert）——它一旦出现基本就是决定性证据**。边界同样要背：驱动只报告它知道的事，「日志里没有错」不等于「没有错」；不同驱动对同一事件的措辞与粒度差异很大；单独看 L3 常常「有事件、无因果」——必须与 L2 对时，才能确认日志里那条 deauth 和空口上那帧是不是同一件事。

### 1.3.4 L4 射频电路层：物理层的体检报告

L1~L3 的证据都指向物理层时，才轮到这一层出场。能看的：实际发射功率、EVM（调制质量）、频偏、频谱模板、天线 VSWR、发射瞬间的电源电压跌落。工具：频谱仪（功率/杂散/模板）、矢量网络分析仪（天线匹配）、示波器 + 电流探头（电源毛刺），外加让整机能做传导测量的 U.FL 转 SMA 工装。电源余量不是玄学——入门系列已核对过 ESP-FAQ 的数字：ESP8266 模拟电源峰值 350 mA、数字电源峰值 200 mA、模拟极限 500 mA（出处见文末清单），发射瞬间的电流台阶是毫秒级的，第九章用示波器把它拍下来；频偏与晶振的关系见 [[ch11-crystal-clock|射频入门（十一）]]。

成本与可信度：全场最高——仪器、工装、校准，以及最贵的「时间」（每改一次硬件的反馈回路以天计）；输出是可与 datasheet、法规限值逐条对比的数值（第七章给判据），数值本身最权威。但**测量口径错误会造成「权威的错误」**：传导还是辐射、有没有校准、限值适用哪条法规条款——口径错了结论全错（第七、十一章反复强调，法规背景见 [[ch17-certification-regulations|射频入门（十七）]]）。

最后把「取证成本从低到高，改板子永远放最后」说完整：改板的成本曲线（一次流板以周计、牵动结构产能）、置信曲线（L1~L3 没收敛就动硬件，等于抛硬币）、可回退性（软件回退是 `git revert`，硬件回退是再流一次板）三条曲线叠加，决定了 L4 里「测」与「改」是两件事——拿频谱仪测一次传导功率是取证，值得做；看到频偏超标就直接改晶振布局，是在证据链没闭合时烧钱。

> [!tip] 分层是「默认成本序」，不是死序
> 1.3.5 的判定表里，「频繁掉线」「发射时复位」的起始层写着 L3 在前——手头已有日志权限时，先扫一眼自述再上抓包完全合理，两层的证据本来就要对时互证。原则始终只有一条：**先便宜后贵，别跳着花**。

### 1.3.5 症状 → 起始层判定表

| 症状                | 建议起始层 | 理由                                        | 典型升级路径                    |
| ------------------- | ---------- | ------------------------------------------- | ------------------------------- |
| 扫不到目标 SSID     | L2         | 先确认空口上有没有 beacon，再谈站端配置     | L2 → L3                         |
| 认证/关联失败       | L2         | 交互停在哪一帧，原因码直接缩小范围          | L2 → L3 → L4（频偏/灵敏度）     |
| 卡在 DHCP           | L1 + L2    | 先分清「连上了拿不到 IP」还是「根本没连上」 | L1 → L2                         |
| 频繁掉线            | L3 + L2    | 站端事件与空口帧互为证人，先对时再定责      | L3 → L2 → L4                    |
| 漫游乒乓            | L2         | 跨 AP 的 beacon 强度与切换帧逐一看          | L2 → L4（覆盖/结构）            |
| 吞吐低              | L1         | RSSI/MCS/重传三角，先量三角的三个角         | L1 → L2 → L4                    |
| 延迟抖动            | L1         | 先量基线，再区分链路慢还是 airtime 被抢     | L1 → L2                         |
| 发射时复位          | L3 + L4    | 日志对齐复位时刻，示波器抓电压跌落          | L3 → L4                         |
| 续航与规格差太远    | L3         | 先看睡没睡、睡多深，再上功耗仪              | L3 → L4                         |
| 特定位置/时段才发生 | L1         | 位置/时间相关性本身就是证据，先画出相关性   | L1 → L2（占用观测）→ L4（覆盖） |
| 预测试 fail         | L4         | 这一类的起点就在物理层（传导测量）          | L4 → 送正式实验室               |

## 1.5 调试纪律五条

方法论最后收束成五条纪律。它们不起眼，但每个「查了两周不收敛」的案子，事后复盘几乎都栽在其中一条上：

| #   | 纪律             | 反面案例（教学复盘口径）                                                       | 落地做法                                                                                |
| --- | ---------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 一  | 一次只改一个变量 | 同时换了信道、刷了固件、挪了设备位置——「变好了」，但复发时你不知道该回滚哪一个 | 每轮实验只动一个旋钮，其余全部冻结并记录                                                |
| 二  | 先记录基线       | 「之前好像也没多差吧」——没有基线数据，改动效果永远无法判定                     | 动手前先跑一轮标准取证（`iw dev wlan0 link` + `iperf3 -c <对端IP> -t 30`），输出存档    |
| 三  | 对照实验         | 手上只有坏机，看什么都觉得异常                                                 | 好机 vs 坏机同场对比；同机好位置 vs 坏位置对比；有壳 vs 无壳对比                        |
| 四  | 日志与事件对时   | 站端日志说 14:03 掉线，AP 日志说 14:05，pcap 时间戳又是一套——三个时钟各说各话  | 各设备先 NTP 对时；无外网时用共同事件对齐（人为触发一次断连），并记录每份日志的时钟偏移 |
| 五  | 证据链可复现     | 案子破了，三个月后复发，没人记得当时的命令、版本与配置                         | 每个案子留「取证脚本 + 环境记录」（内核/驱动/固件版本、拓扑草图）；能脚本化的全部脚本化 |

五条共同服务一个目标：**证据链闭合**——从现象到根因的每一步都有记录、可重放、可反驳。第二章起的每一章，都会把这五条变成具体命令与操作步骤。

## 本章小结

- **症状五分类**：连不上、掉线/漫游差、慢、功耗/电源类、认证不过——分类依据是可感知现象而非根因；每类的第一反应动作都在 L1/L3 层，成本近零（1.2 总表）。
- **分层取证 L1→L4**：观测层钉现象（基线）、协议层看帧（因果）、驱动层听自述（错误码）、射频层做体检（与限值对比）——取证成本从低到高，各层可信度边界（1.3 总表与各小节）比各层工具更重要。
- **改板子永远放最后**：成本、置信、可回退性三条曲线共同决定；L4 里「测」是取证、「改」是决策，证据链没闭合不动烙铁。
- **装备四档 = 能破案到哪一层**：¥0 档覆盖 L1+L3、百元档打通 L2、千元档摸到 L4 门口、专业档按需租借——升档判据是「假设收敛到只剩一个而当前档无法验证」（1.4）。
- **五条纪律**：单变量、先基线、对照实验、对时、可复现——目标只有一个：证据链闭合（1.5）。
