## 6.1 现场引入：三类「慢」，三种病

「慢」是 WiFi 投诉里最大的一筐，筐里的病因却极少相同。三个典型开场白：

| #   | 现场陈述                                 | 表面读数                | 直觉归因（多数是错的） | 本章归宿 |
| --- | ---------------------------------------- | ----------------------- | ---------------------- | -------- |
| A   | 「协商 866 Mbps，实测 200 都不到」       | 链接详情显示 866.7 Mbps | 「路由器虚标」         | 6.2、6.3 |
| B   | 「离路由器越近反而越慢，挪远两米就正常」 | 近处 RSSI 满格          | 「玄学」               | 6.3、6.5 |
| C   | 「白天还行，一到晚上就卡」               | 白天复测一切正常        | 「运营商的问题」       | 6.5      |

共性：用户手里唯一的读数（协商速率或信号格）被当成了「网络健康的全部」。而「慢」有三个互相独立的坐标轴，先把轴立起来，取证才知道往哪走：

```text
「慢」的三个独立坐标轴——先别急着怪「WiFi 不行」：
  轴 1 链路质量：RSSI / MCS / 重传 —— 电波到没到、听清了没        → 6.3
  轴 2 信道环境：同频邻居 / 非 WiFi 干扰 / 带宽降档 —— 路被谁占着  → 6.5、6.6
  轴 3 主机与背板：CPU 软中断 / 省电模式 / AP 有线背板 —— 谁在搬包  → 6.4
三轴分别取证、交叉读数，多数「慢」能在一小时内定案；6.7 的判断树就是这三根轴的走法。
```

## 6.2 先立预期：物理速率 ≠ 有效吞吐

### 1. 协商速率是什么、不是什么

站表和手机链接详情里的 866.7 Mbps，是 802.11ac 80 MHz、2 空间流、MCS9（256QAM 5/6）、短保护间隔下的**物理层瞬时名义速率**——它回答「此刻发射一帧，物理层打包用多快」，不回答「一秒能搬多少应用数据」。机理背景见 [[ch16-rate-negotiation|射频入门（十六）：速率协商]]。名义速率到有效吞吐之间隔着一张开销账单：

| 开销项                             | 谁在付           | 量级（示意口径）                       |
| ---------------------------------- | ---------------- | -------------------------------------- |
| 帧结构开销（前导/帧间隔/随机退避） | 每帧             | 数十 µs 起，信道越忙退避越长           |
| SIFS + ACK                         | 每帧（正常确认） | 数十 µs 量级                           |
| beacon/管理帧/广播帧               | 全 BSS 轮流承担  | 常驻低速 airtime（6.6 单独算账）       |
| 加密头尾 + TCP/IP 头部             | 每帧每包         | CCMP +16 B 级、TCP/IP 约 40~78 B/包    |
| 单流 TCP 窗口/RTT 限制             | 主机协议栈       | 长肥管道下明显——本征问题，不是 WiFi 锅 |
| 主机栈（中断/拷贝/软中断）         | 端与 AP 两边     | 嵌入式端经常才是真瓶颈                 |

### 2. 一笔示意账：聚合前后的差距

同样名义速率，「一帧一发」和「聚合发射」的空口效率差一个数量级：

```text
单帧逐发（无聚合，1500 B/帧，名义 866.7 Mbps，示意估算，忽略重传与竞争恶化）：
  数据时间 ≈ 12 000 bit ÷ 866.7 Mbps ≈ 14 µs
  开销   ≈ 前导 40 + DIFS 34 + 退避约 40 + SIFS 16 + ACK 约 40 ≈ 170 µs
  → 空口有效占比 ≈ 14 / (14 + 170) ≈ 7%，折算约 60~70 Mbps
64 帧聚合 A-MPDU（约 96 KB，示意）：数据时间 ≈ 886 µs，固定开销摊薄到 20% 以下
  → 空口效率升至约 80%，再扣 TCP 与主机侧，落到经验区间 400~600 Mbps
```

推论：**驱动和 AP 有没有把聚合用起来，本身就是「866 协商、200 实测」的一级嫌疑**（抓包验证见 6.4.3）。

### 3. MCS→有效吞吐参考表（经验估算口径）

名义速率引自 IEEE 802.11 速率表（802.11ac 为短 GI 口径，802.11ax 仅有长 GI 口径）；「经验有效吞吐」为干净信道、单客户端、TCP 长流下的**经验估算区间，随驱动、聚合能力、环境浮动很大，仅作预期校准，不是实测承诺**：

| 模式（带宽/NSS/档位）              | 名义物理速率   | 经验有效吞吐（TCP） |
| ---------------------------------- | -------------- | ------------------- |
| 802.11n 2.4G 20 MHz 2SS MCS7       | 144.4 Mbps     | 60~90 Mbps          |
| 802.11n 40 MHz 2SS MCS7            | 300 Mbps       | 120~180 Mbps        |
| 802.11ac 80 MHz 1SS MCS9           | 433.3 Mbps     | 200~300 Mbps        |
| **802.11ac 80 MHz 2SS MCS9**       | **866.7 Mbps** | **400~600 Mbps**    |
| 802.11ac 20 MHz 2SS MCS9（降宽后） | 200 Mbps       | 90~140 Mbps         |
| 802.11ax 80 MHz 1SS MCS11          | 600.5 Mbps     | 350~500 Mbps        |
| 802.11ax 80 MHz 2SS MCS11          | 1201 Mbps      | 700~950 Mbps        |
| 802.11ax 2.4G 20 MHz 1SS MCS11     | 143.4 Mbps     | 70~110 Mbps         |

现场用法：实测落在区间内 → 链路没大毛病，转轴 3 或接受现状；实测显著低于区间下限 → 按三轴往下取证。

## 6.3 RSSI-MCS-重传三角：读懂 `iw dev wlan0 station dump`

### 1. 采样命令与输出样例

站端（连着 AP 的 Linux 设备）与 AP 端（OpenWrt 上看客户端）都能采，两边对照能看到链路的不对称：

```bash
sudo iw dev wlan0 link        # 快速版：信号 + 当前收发码率
sudo iw dev wlan0 station dump
```

输出样例（**格式示意**，字段集合随内核版本与驱动差异，airtime 类字段需驱动支持）：

```text
Station 3c:5a:b4:xx:xx:xx (on wlan0)
	rx packets:		631204
	tx packets:		9031
	tx retries:		5123
	tx failed:		147
	rx bitrate:		722.2 MBit/s HE-MCS 10 80MHz HE-NSS 2
	tx bitrate:		360.3 MBit/s HE-MCS 7 80MHz HE-NSS 2
	signal:			-49 [-53, -46] dBm
	signal avg:		-50 [-54, -47] dBm
```

### 2. 关键字段逐个读

| 字段             | 读什么                                          | 经验判读                                            |
| ---------------- | ----------------------------------------------- | --------------------------------------------------- |
| `signal`         | 当前 RSSI，方括号内为各接收链路分值             | 看区间（下表）；链路间差值大提示天线/遮挡方向性问题 |
| `signal avg`     | 滑动平均 RSSI                                   | 与 `signal` 差得多 → 信号在抖（间歇干扰或位置变动） |
| `tx bitrate`     | 本站→AP **最近实际发射档位**（MCS/带宽/NSS/GI） | 不是能力上限；忽高忽低 = 速率自适应在挣扎           |
| `rx bitrate`     | AP→本站档位                                     | 与 `tx bitrate` 严重不对称 → 查 AP 发射侧或其负载   |
| `tx retries`     | 累计重传帧数；`tx failed` 为重传耗尽被丢弃的帧  | **看斜率不看绝对值**：failed 持续增长 = 链路在恶化  |
| `rx/tx duration` | 空口占用时间（新内核 + 驱动支持时）             | 直接的 airtime 读数，有就是宝藏                     |

重传斜率的两点采样法（间隔 30 秒取增量即够）：`sudo iw dev wlan0 station dump | grep -E 'tx retries|tx failed'` 跑两次，中间 `sleep 30`。

### 3. 三角失衡组合诊断表

RSSI（听多清）、MCS（跑多快）、重传（错多少）三者组合，比任何单值都更能定罪：

| 组合（三角读数）                       | 站表指纹（示意）                   | 诊断方向                  | 下一步                    |
| -------------------------------------- | ---------------------------------- | ------------------------- | ------------------------- |
| 高 RSSI + 满档 MCS + 重传低 + 吞吐仍低 | signal ≈ -45，866.7 档，retries 平 | 主机/背板瓶颈             | 6.4 主机侧清单            |
| 高 RSSI + 重传高/failed 增长           | MCS 忽高忽低，retries 斜率大       | **干扰/同频拥挤**         | 6.5 三档测法              |
| 低 RSSI + 低 MCS + 重传高              | signal < -70，掉到 MCS2~4 档       | 距离/穿透/天线            | 挪点位、查天线（第八章）  |
| 高 RSSI + 低 MCS + 重传低              | signal ≈ -45 却只有 60~90 Mbps 档  | 兼容性降档/省电/带宽降宽  | 查 20/40 coex、power_save |
| tx 与 rx bitrate 严重不对称            | tx 866 档 / rx 195 档              | AP 发射侧或 AP 正被别人占 | AP 端 station dump 对照   |
| `avg` 显著低于 `signal`                | -45 对 -63                         | 间歇干扰/位置抖动         | 分时段采样对比            |

RSSI 经验区间（**经验综述口径，非标准规定**；RSSI 是芯片自定义相对量，跨机型不可比、同机前后比才有意义；dBm 换算见 [[ch03-decibel-family|射频入门（三）]]，SNR 与灵敏度视角见 [[ch05-rx-chain-sensitivity|射频入门（五）]]）：

| RSSI        | 区间判读                                    |
| ----------- | ------------------------------------------- |
| ≥ -55 dBm   | 好，高吞吐档位可用                          |
| -55~-67 dBm | 可用；高吞吐开始受影响，办公/视频的常用下限 |
| -67~-75 dBm | 差；高 MCS 档位保不住，体验明显下降         |
| ≤ -75 dBm   | 基本跑不了高吞吐，掉线风险区                |

## 6.4 iperf3 方法论：把「慢」量化成一条曲线

### 1. 六种打法

服务端跑在有线侧（台式机/服务器），客户端跑在被测 WiFi 站上。`iperf3` 一次进程只测一个方向，其余维度用参数切换：

| 打法       | 命令                                   | 回答什么问题                    |
| ---------- | -------------------------------------- | ------------------------------- |
| 基线       | `iperf3 -c 192.168.1.2 -t 30`          | 当前方向能搬多少                |
| 反向       | 加 `-R`                                | 上下行是否不对称                |
| 多流       | 加 `-P 4`                              | 是单流窗口卡住，还是链路真的窄  |
| UDP        | 加 `-u -b 300M`（服务端侧读丢包/抖动） | 链路质量直接读数，绕开 TCP 遮罩 |
| 长跑       | `-t 300 -i 5 -O 3`（丢弃前 3 秒热身）  | 周期性劣化：省电周期/时段性干扰 |
| 服务端视角 | 加 `--get-server-output`               | 把对端读数一并留档，取证归档用  |

判读经验线（经验口径）：多流能抬吞吐 → 先查 TCP 单流问题；UDP 丢包轻载下仍 >1~2% → 链路质量问题，转 6.3/6.5；TCP 很差但 UDP 正常 → 主机或配置问题居多。

### 2. 链路问题还是主机问题

TCP 吞吐低时，先在主机上做四个便宜的检查，再谈空口：

| 检查              | 命令                                                                                             | 判读                                            |
| ----------------- | ------------------------------------------------------------------------------------------------ | ----------------------------------------------- | ------------------------------------------- |
| 软中断            | `top`（看 `%si`）；或 `mpstat -P ALL 1 5`（sysstat）；或 `grep NET_RX /proc/softirqs` 两次取增量 | 单核 `%si` 打满 → 主机收包瓶颈                  |
| 省电模式          | `iw dev wlan0 get power_save`；`sudo iw dev wlan0 set power_save off` 后复测                     | 关掉后吞吐上台阶 → 元凶即它（功耗代价见第十章） |
| AP 有线背板       | 登录 AP/OpenWrt：`cat /sys/class/net/eth0/speed`                                                 | 显示 100 → 全链路封顶约 94 Mbps，别在无线里找了 |
| iperf3 服务器本身 | 服务端 `top` 观察同刻负载                                                                        | 嵌入式/MCU 端做服务器时常见（[[wifi-coproc      | F429 × WiFi 协处理器]]里 MCU 端尤其要怀疑） |

### 3. 空口侧同步取证：重传帧占比

iperf3 跑长流的同时，用监听网卡抓同信道（监听模式配置详见 [[wifi-hw-debug-ch03-ota-sniffing|第三章]]）；省电模式的站端行为也会以事件形式反映在驱动/固件日志里，与 [[ch16-wifi-events|BOX-3（十六）]] 的事件模型对得上：

```bash
sudo iw dev wlan0 interface add mon0 type monitor && sudo ip link set mon0 up
sudo iw dev mon0 set channel 36              # 对准站当前所在信道
sudo tcpdump -i mon0 -e -s 256 -w air.pcap   # 与 iperf3 同步运行
```

统计重传占比（过滤器与字段均为 Wireshark 真实语法；第二条追加 `&& wlan.sa == 3c:5a:b4:xx:xx:xx` 可只看目标站发射方向）：

```bash
tshark -r air.pcap -Y "wlan.fc.type == 2" -T fields -e frame.number | wc -l   # 数据帧总数
tshark -r air.pcap -Y "wlan.fc.type == 2 && wlan.fc.retry == 1" -T fields -e frame.number | wc -l   # 重传帧
tshark -r air.pcap -Y "wlan.fc.type == 2" -T fields -e frame.len | sort -n | uniq -c   # 长度分布：大量大帧 = A-MPDU 在工作
```

GUI 对应 Wireshark 的 Statistics → WLAN Traffic 与过滤器 `wlan.fc.retry == 1`。判读经验线（经验综述口径）：干净链路重传占比 <5%；>15% 明显异常；>30% 用户必然可感。占比高 → 转 6.5 查干扰；占比低但吞吐低 → 回轴 3。

## 6.5 干扰定位：信道占用与「晚上变卡」

### 1. 信道占用率三档测法

| 档   | 工具                       | 能看什么                                  | 局限                               |
| ---- | -------------------------- | ----------------------------------------- | ---------------------------------- |
| 一档 | 手机 WiFi 分析仪 App       | 各信道 AP 数量/强度图表，占用粗测         | 粗，App 的「占用率」算法不透明     |
| 二档 | `iw scan`                  | 邻居 AP 的频点/信号/带宽/能力快照         | 一次性快照，无时间维度             |
| 三档 | 空口抓包统计               | 帧密度、每 BSS 帧量、重传、非 WiFi 源痕迹 | 最重：需监听网卡 + 分析时间        |
| 奖励 | `iw dev wlan0 survey dump` | 信道 active/busy 时间（驱动支持时）       | 输出以驱动实际支持为准，待实测口径 |

二档实用命令（扫描会短暂打断本机连接，取证时注意），及三档的两个统计（近似口径：帧数/字节数只是 airtime 的粗代理，未按速率折算；CRC 错帧需网卡报告 FCS 状态，部分驱动不给）：

```bash
sudo iw dev wlan0 scan | awk '/freq:/{f=$2} /signal:/{print f, $2}' | sort | uniq -c
tshark -r air.pcap -Y "wlan.fc.type == 2" -T fields -e wlan.bssid | sort | uniq -c | sort -rn   # 每 BSS 帧量排行
tshark -r air.pcap -Y "wlan.fcs_good == 0" -T fields -e frame.number | wc -l   # CRC 错误帧数
```

### 2. 同频 vs 邻频：机制不同，处方不同

| 干扰类型           | 机制                                                      | 现场指纹                   | 处方                      |
| ------------------ | --------------------------------------------------------- | -------------------------- | ------------------------- |
| 同频（co-channel） | 邻居听得懂彼此，按 CSMA/CA 规矩**轮流让出 airtime**       | 重传不高，吞吐按占用比摊薄 | 换更空信道，或接受分蛋糕  |
| 部分重叠（邻频）   | 互相听不全 → 对方成了**听不懂的噪声**，退避失灵、碰撞重传 | 重传飙升，双方吞吐一起烂   | 2.4G 回 1/6/11 三信道规划 |
| 次信道占用         | 主信道干净但 40/80 MHz 的次信道上有邻居                   | 链路健康，带宽却降档       | 6.6 的降宽主题            |

### 3. 非 WiFi 干扰源特征

干扰与共存机理的完整展开在 [[ch14-interference-coexistence|射频入门（十四）]]，本节只给现场指纹：

| 干扰源         | 特征（定性综述口径）                                                          | 抓包痕迹                         |
| -------------- | ----------------------------------------------------------------------------- | -------------------------------- |
| 微波炉         | 2.4G 中段约 20~30 MHz 宽、突发式、占空比高，信道 7~12 一带最重                | 大片 CRC 错帧 + 无法解码的噪声帧 |
| USB3 接口/线缆 | 宽带噪声铺满 2.4~2.5 GHz（Intel 2012 白皮书口径），模组靠近 USB3 口时噪底抬升 | 全信道「RSSI 好、SNR 差」的怪象  |
| 蓝牙音频       | 2.4G 前段突发占用，AFH 跳频可缓解                                             | 信道前段周期性劣化               |

现场 B 类故障（「离得近反而慢」）的常见解释正是 USB3 一行：近了 RSSI 高，但 USB3 噪声把噪底抬得更高，SNR 反而崩——三角读数表现为高 RSSI + 高重传（6.3 组合表第二行）。

### 4. 「晚上变卡」的典型解释

头号解释：**邻居晚间回家，同频信道流量高峰**——白天邻居路由器空转（只有 beacon），晚上视频/下载把同频 airtime 吃满，你的 BSS 被迫分蛋糕。取证动作就一件事：**去坏时段采样**，好坏时段各跑一轮 `iperf3 -c 192.168.1.2 -t 300 -i 5 -O 3 --get-server-output`，并对照 `station dump` 与 `survey dump`。判据（示意口径）：坏时段 retries 斜率与同信道邻居帧量同涨、`tx bitrate` 整体掉档 → 同频拥挤实锤。次要解释按出现频率排：微波炉（晚饭时段高度吻合）、ISP 侧拥塞（LAN 内 iperf3 正常而外网慢，则与本主题无关）。

## 6.6 带宽与保护机制：被吃掉的后半程

### 1. 「连上只有 20 MHz」真相

40/80 MHz 不是配置了就一定生效——**次信道必须空闲，且双方协商允许**。2.4G 有 20/40 共存机制（BSS 载荷带 40MHz intolerant 位，邻居 AP 主信道压着你的次信道时 AP 会主动降宽保稳）；5G 的次信道同样受 OBSS 占用与 DFS 雷达事件约束（DFS 与法规背景见 [[ch17-certification-regulations|射频入门（十七）]]）。拥挤居民楼里 2.4G 几乎必然落在 20 MHz，这是**机制在正确工作**，不是故障：

```bash
iw dev wlan0 info   # 看 width: 20 MHz 还是 80 MHz
iw dev wlan0 link   # bitrate 行里的带宽字样
```

AP 侧（OpenWrt）看 hostapd 日志的降宽记录更直接。降宽的吞吐代价先按带宽比预估：866.7 → 20 MHz 档约 200 Mbps（6.2 表第五行），先核对期望再定「这是问题还是现实」。

### 2. legacy 终端拖慢整个 BSS

一个 802.11b/g 老设备在场，全 BSS 一起买单，机制有三层：

| 机制                 | 怎么拖                                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------------------------- |
| 保护机制             | 混合模式下为让老设备听得懂，其余站点的帧前要附加 CTS-to-self/RTS 保护开销，人人交税                             |
| airtime 被低速帧吃掉 | airtime 与速率成反比：同样 1500 B，11 Mbps 老帧占用的发射时间约为 866 Mbps 帧的数十倍——老设备每发一帧，全场等它 |
| 兼容性降档           | 部分实现为照顾最弱成员整体收敛保守，速率自适应上限被拉低                                                        |

经验综述口径：一个老 11b 设备持续跑流量，可把 g/n 混合 BSS 的吞吐砍掉一半以上。定位靠 6.5 抓包统计里看低速档帧的来源站；对策是老设备单独 SSID/单独 AP，或迁到 5G。

### 3. 组播与广播低速帧

组播/广播帧没有 ACK，为让最弱成员收到，**按 basic rate（2.4G 旧配置常为 1 Mbps）发射**；beacon 也走 basic rate。示意账：约 500 B 的 beacon 以 1 Mbps 发射需约 5 ms，每 102.4 ms 一次，**仅 beacon 就吃掉约 5% 信道时间**（示意估算口径）；basic rate 抬到 6 Mbps 后降到 1% 以下。定量用广播帧计数，对策：抬升 basic rate（牺牲最老设备）、砍掉无谓广播应用、IoT 隔离到独立 BSS：

```bash
tshark -r air.pcap -Y "wlan.da == ff:ff:ff:ff:ff:ff" -T fields -e frame.number | wc -l
```

## 6.7 瓶颈甄别流程图

把 6.3~6.6 收成一张判断树——从 iperf3 基线开始，每步只问一个「空口满不满」：

```text
iperf3 实测 < 预期带下限（6.2 表）
 │
 ├─ ① 空口 airtime 满（帧密度高 / survey busy 高 / 邻居帧量大）
 │     ├─ 重传占比 > 15%（wlan.fc.retry==1 统计）
 │     │      → 干扰/失配：同频拥挤、邻频重叠、微波炉、USB3（6.5）
 │     │        辅证：站表高 RSSI + 高 retries；抓包 CRC 错帧成片
 │     └─ 重传低但帧多 → 同频负载/legacy 拖累：邻居分蛋糕、低速帧占道（6.6）
 │
 ├─ ② 空口不满、链路质量差（低 RSSI / 低 MCS + 高重传）
 │      → 距离/穿透/天线：挪点位、组网补盲、查馈线与净空（第八章）
 │
 └─ ③ 空口不满、链路质量好（高 MCS、低重传、RSSI 达标）
        → 主机/AP 背板：CPU 软中断、power_save、有线背板 100M、
          iperf3 服务器本身慢（6.4.2 清单逐项过）
```

执行纪律：**一次只改一个变量**（信道/带宽/省电/点位），每改一次重跑同一组命令，证据链才闭合。

## 6.8 教学案例复盘：866 → 200 的两段式破案

> [!warning] 教学复盘案例——本节为**教学复盘案例，取材自常见故障模式综述**：场景为常见故障模式的组合复现，帧计数与读数均为示意数值，用于演示取证路径，非真实事故记录。

**背景**：一台 2 空间流 802.11ac 模组的 Linux 嵌入式设备（类 NAS 用途），投诉：协商 866 Mbps，白天实测 400+，晚间掉到 200 以下；销售口径是「WiFi 千兆」。

| 步骤 | 动作                                                | 读数（示意）                                                                    | 结论推进                         |
| ---- | --------------------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------- |
| 1    | 建 iperf3 基线：`-t 300 -i 5 -O 3`，白天/晚间各一轮 | 白天 430 Mbps 平稳；晚间 160 Mbps 且锯齿明显                                    | 时段相关 → 轴 2 优先             |
| 2    | 两个时段各采 `station dump`                         | 白天 MCS9 满档、retries 平；晚间掉到 MCS3~5、retries 斜率约白天 5 倍            | 高 RSSI + 高重传 → 干扰族谱      |
| 3    | 晚间抓包 5 分钟：重传占比 + 每 BSS 帧量排行         | 重传占比约 1/3；同信道邻居 AP 帧量居榜首（白天仅零星 beacon）                   | 同频拥挤实锤                     |
| 4    | 复查次要嫌疑并处理                                  | `power_save` 为 on、AP 有线口 100 → 迁 5G ch149 验证 80 MHz、关省电、换千兆背板 | 复测晚间稳定 450 Mbps 级（示意） |

复盘要点：**协商速率只是门票**，866 是 6.2 表的名义值，不该出现在验收标准里；**坏时段取证是胜负手**，白天复测一切正常，差点以「无法复现」结案；**根因常常是组合拳**，同频拥挤是主犯、省电与百兆背板是从犯——只修主犯，用户还会回来第二次。同类完整案例将在 [[wifi-hw-debug-ch12-casebook-checklist|第十二章]] 汇总成册。

## 6.9 根因速查总表

| 症状指纹                   | 第一嫌疑             | 一锤定音的取证                        | 对策方向                      |
| -------------------------- | -------------------- | ------------------------------------- | ----------------------------- |
| 协商满档、重传低、吞吐仍低 | 主机/背板            | `%si`、power_save、`eth0/speed`       | 6.4.2 主机侧清单              |
| 高 RSSI + 高重传           | 干扰/同频拥挤        | 抓包 retry 占比 + 每 BSS 帧量排行     | 换信道、除源（6.5）           |
| 低 RSSI + 低 MCS + 高重传  | 距离/穿透/天线       | station dump 三角 + 分点位采样        | 挪 AP、组网、查天线（第八章） |
| 高 RSSI + 低 MCS、无重传   | 降宽/兼容降档/省电   | `iw dev wlan0 info` 宽度 + power_save | 配置侧（6.6）                 |
| 只在特定时段慢             | 同频高峰/微波炉      | 分时段对照 + CRC 噪声帧统计           | 频段/信道规划（6.5）          |
| tx/rx bitrate 严重不对称   | AP 发射侧或 AP 正忙  | AP 端 station dump 对照               | AP 侧排查                     |
| TCP 很差、UDP 正常         | 单流窗口/主机问题    | `-P 4` 对比、服务端负载               | 主机侧                        |
| 广播/低速帧占比高          | legacy 拖累/组播配置 | 广播帧计数 + basic rate 核对          | basic rate/设备隔离（6.6）    |

**本章小结**：协商速率是物理层瞬时名义值，验收要用 6.2 的经验区间校准预期；`station dump` 的 RSSI-MCS-重传三角给出第一张定性画像；iperf3 六种打法把「慢」变成曲线，主机侧四项便宜检查排掉一半假案；信道占用三档测法把干扰从感觉变成排行；20 MHz 降宽与 legacy 拖累是「机制正确地工作」而非故障。下一章离开软件视角，用仪器直接量发射功率、EVM 与频偏，见 [[wifi-hw-debug-ch07-phy-measurements|第七章：物理层实测]]。
