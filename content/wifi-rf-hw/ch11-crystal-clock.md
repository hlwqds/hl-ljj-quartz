# WiFi 射频硬件入门（十一）：晶振与时钟

> [!info] WiFi 射频硬件入门系列 0. [[wifi-rf-hw|系列索引]]
> 上一章：[[ch10-rf-front-end-fem|第十章：射频前端 FEM]]
> **第十一章：晶振与时钟**（当前章）
> 下一章：[[ch12-power-supply|第十二章：WiFi 的电源性格]]

第八章末尾留过一个作业：在 esp-box 原理图上找 40 MHz 主晶振和它两端的负载电容，并预告「负载电容公式与温漂是第十一章的开场」。这一章兑现它。全章只解决一个问题：**时钟从哪来、差多少会死**。

核心类比先立起来：**频偏 = 时钟漂移**。你一定见过两块板子各用内部时钟生成波特率、差 2% 就开始出乱码的场面——异步串口没有时钟线，接收方全靠自己本地采样，双方节拍不一致，采样窗逐位漂移，帧就废了。WiFi 是同一个故事的射频版：你和 AP 各用自己的晶振生成 2.4 GHz 载波，**载波频率就是射频世界的波特率基准**，晶振偏差几十 ppm，正交子载波就互相踩踏、解调崩盘。串口的病根是「各玩各的钟」，WiFi 一模一样，只是差度单位从百分之二换算成了百万分之四十。

## 11.1 时钟的硬件源头：晶振是石英压电节拍器

### 1. 石英为什么会「打拍子」

晶振的核心是一片切好的石英晶体。石英有压电效应：给它加电压它会形变，形变了它又会反过来产生电压。把这片石英切到特定尺寸（常见的 AT 切型），它有一个由物理尺寸决定的固有机械共振频率——像音叉认得自己的音高。振荡电路做的事情只有一件：放大器不断给它补充能量，石英片则用自己的固有频率约束整个环路。所以晶振不是「产生」时间，而是**把电路里杂乱的振荡锁死在一个非常稳定的频率上**——它是节拍器，不是作曲家。

软件类比：晶振是整个系统的**硬件单调时钟源**。CPU 主频、esp_timer 的微秒、Wi-Fi 的 2.4 GHz 载波、蓝牙的跳频节拍，全是从这一根源**倍频/分频派生**出来的。就像全机时间统一从一个 NTP 源派生——源歪了，下游全部一起歪，而且谁也发现不了（对下游来说源就是真理）。

### 2. 板上的时钟源点名

| 时钟源                      | 频率                   | 精度口径           | 职责                       |
| --------------------------- | ---------------------- | ------------------ | -------------------------- |
| 40 MHz 主晶振（必装）       | 40 MHz                 | ±10 ppm 以内       | 时钟树的根，CPU 与射频共用 |
| 32.768 kHz RTC 晶振（可选） | 32.768 kHz             | 高稳定但慢         | 深睡计时，不供射频         |
| 芯片内部 RC 振荡器          | 150 kHz / 8.5 MHz 派生 | 温漂远大于晶振     | 非高精度场景的应急时钟     |
| ESP8266 主晶振（对照）      | 26 MHz                 | ±10 PPM（ESP-FAQ） | 老平台同款 ppm 纪律        |

四行出处：40 MHz 唯一性——ESP32 Datasheet v5.3 特性原文「External 2 MHz ~60 MHz crystal oscillator (40 MHz only for Wi-Fi/Bluetooth functionality)」；ESP32-S3 设计指南更干脆：「The ESP32-S3 firmware only supports 40 MHz crystal」。RTC 晶振与内部 RC 的对比——ESP-FAQ 记载 ESP32 内部有 150 kHz RC 振荡器和 8.5 MHz 振荡器分频时钟可当 RTC 时钟源，但「频率稳定性受温度影响较大」，只适合非高精度场景。ESP8266 行——ESP-FAQ 原文「选用的晶振自身精度需在 ±10 PPM」。注意最后一列的分工：**32 kHz 晶振再准也不管载波**，载波精度只由 40 MHz 主晶振负责——这个区分在 11.7 误区表里还要回来。

用模组的人（本系列读者的大多数）其实拿不到「选晶振」这个坑：模组厂替你踩完了。ESP32-S3-WROOM-1 模组内置 40 MHz 晶振，模组 datasheet v1.8 参考原理图上那颗 Y1 的标注就是 **40MHz(±10ppm)**。坑留给裸片自制板的人——也正是他们贡献了 11.5 的故障案例。

### 3. 负载电容为什么成对出现：给晶振「配重」

第八章讲过电容在 RF 里的三份工作（去耦/隔直/匹配），这里补第四份：**给晶振定工况**。石英晶体的 datasheet 里有个关键参数 CL（负载电容，load capacitance）：厂家的频率标称值是在「晶体两端各挂指定电容」的标准电路下调准的。你的板子给晶体呈现的等效电容不等于 CL，谐振频率就偏离标称——**负载电容选错，能把一颗 ±10 ppm 的晶振用出几十 ppm 的频偏**，这比晶振自身精度差是更常见的翻车原因。

两个电容为什么成对？晶振电路（皮尔斯振荡器）的结构决定了晶体两端各挂一颗对地电容，从晶体看过去这两颗是串联关系。公式直接抄设计指南原文：

```text
CL = (C1 × C4) / (C1 + C4) + C_stray

C1、C4：晶体两侧的对地负载电容（通常取相等）
C_stray：PCB 走线与芯片引脚带来的杂散电容
```

三条工程含义：

1. **两颗通常相等**，特殊工况（比如补偿不对称的走线）才故意取不等——设计指南明说初始值按公式定，量产前实测微调；
2. **C_stray 是隐式参数**：同一份原理图，换一块 layout、换一家板厂，杂散电容就变，照抄上一版的电容值不保证还准。软件类比：CL 是晶振的接口契约，你的调用环境（PCB）是没写进签名的隐式依赖——换环境不传新参，契约就破了；
3. 调电容就是在调频偏：设计指南原文「Adjust the frequency offset to be within ±10 ppm (recommended) by adjusting the external load capacitance」，方向是**频偏为正（偏快）说明等效负载电容偏小，要加大电容；偏负则减**。

顺带一条原理图上容易忽略的小件：设计指南建议在 XTAL_P 走线上**串联 24 nH 电感**，原话是「reduce the impact of high-frequency crystal harmonics on RF performance」。为什么晶振的谐波会打扰射频？算一笔账：40 MHz 的第 60 次谐波恰好是 2400 MHz——正砸在 2.4 GHz 频段下沿。节拍器的主音很纯，但泛音串进了隔壁录音棚。

## 11.2 ppm：时钟界的百分比

### 1. 定义与换算

ppm = parts per million，百万分之一。1 ppm = 0.0001%，±40 ppm = ±0.004%。你其实早就在跟 ppm 打交道：「五个九」可用性（99.999%）= 每年停机 10 ppm 量级；单精度浮点的机器精度 2^-23 ≈ 1.2e-7 ≈ 0.12 ppm——软件工程师天天写的 float，其相对分辨率就是亚 ppm 级的。

晶振精度的行业口径就是 ppm：乐鑫要求主晶振 ±10 ppm 以内（设计指南），本章算账用更宽的 ±40 ppm——这是「选型失误或负载电容错配后」的现实偏差量级。

### 2. 同一个误差，两本账

40 ppm 换算到不同消费者头上：

| 基准频率                | ±10 ppm   | ±40 ppm   | 谁在消费这个频率 |
| ----------------------- | --------- | --------- | ---------------- |
| 40 MHz（晶振本体）      | ±400 Hz   | ±1.6 kHz  | CPU、外设        |
| 240 MHz（PLL 倍频后）   | ±2.4 kHz  | ±9.6 kHz  | CPU 时钟         |
| 2412 MHz（信道 1 载波） | ±24.1 kHz | ±96.5 kHz | OFDM 解调器      |

关键规律：**PLL 倍频忠实复制相对误差**。40 MHz 偏 40 ppm，倍频到 2.4 GHz 后还是偏 40 ppm——相对误差不变，绝对值被放大 60 倍。这就是「40ppm @2.4GHz = ±96kHz」的来历（按标称 2.4 GHz 算正好 96 kHz，信道 1 中心 2412 MHz 上是 96.5 kHz）。类比：单位换算消不掉百分比错误——把毫秒算错 0.004%，换成纳秒还是错 0.004%，但绝对值跟着涨一千倍。

### 3. CPU 差这点无所谓，载波差这点致命

| 消费者           | 40 ppm 换算成什么        | 实际后果                       |
| ---------------- | ------------------------ | ------------------------------ |
| CPU 时钟域       | 每秒慢 40 µs，一天 3.5 s | 调度、tick、日志时间戳全无感   |
| 串口波特率域     | 115200 波特偏约 4.6 波特 | 远在 ±2% 乱码线内，无感        |
| 载波域（信道 1） | 载波偏 ±96.5 kHz         | 吃掉子载波间隔的 31%，解调恶化 |

三行逐个说。**CPU 域**：240 MHz 偏 ±9.6 kHz，esp_timer 每秒慢 40 µs，一天累计 3.5 秒——除了长时间不校时的时钟会漂，任务调度、tick、性能计数全无感。[[ch16-portmacro-port-contract|FreeRTOS（十六）]]讲过 tick 的契约（谁提供、能不能停），本章只补一个维度：**那个 tick 的源准不准**——契约管交付，ppm 管成色。

**串口域**：115200 波特偏 4.6 波特，相对偏差还是 0.004%，离 2% 的乱码线差三个数量级，毫无感觉。这也是为什么波特率容忍度是百分之几、而射规用 ppm：串口一帧才 10 个比特，采样窗只在帧内漂；载波是「每秒 24 亿拍」的持续正交采样，误差按符号累积。

**载波域**是致命的那行，单独立账：

| 账目                            | 数值      | 含义                         |
| ------------------------------- | --------- | ---------------------------- |
| OFDM 子载波间隔                 | 312.5 kHz | 「车道宽度」，正交性所在     |
| 40 ppm 在信道 1 上的频偏        | 96.5 kHz  | 吃掉车道间隔的 31%           |
| OFDM 符号时长（无保护间隔）     | 3.2 µs    | 与子载波间隔互为倒数         |
| 96.5 kHz 在 3.2 µs 内的相位旋转 | 约 111°   | 星座整体旋转，64QAM 无法解调 |

[[ch04-tx-chain|第四章]]讲过 OFDM 的「并行车道」：20 MHz 信道切成 64 个子载波槽位，相邻车道间隔 312.5 kHz，正交性靠的是「一个子载波的谱零点正好落在邻居的谱峰上」。频偏 96.5 kHz 相当于**所有车道整体平移了三分之一个车道宽**——接收端 FFT 的采样窗对不齐子载波格点，能量漏进相邻车道（子载波间干扰 ICI）；更直观的是最后一行：不补偿的话，一个 3.2 µs 符号内星座图整体旋转约 111°，64QAM 的点本来就很密，转三分之一圈等于全员搬家，解调直接崩。对比串口的「采样窗漂移」——同一个病，载波域的症状重得多，因为消费这个时钟的电路要求到了 0.01% 量级。

> [!tip] 为什么标准偏偏卡这么紧
> 802.11 标准对发射中心频率容差有明确的 ppm 级规定（11b 与 OFDM 各有条款，数值档位：**待核对**，未核到标准原文）；乐鑫的工程口径比标准留裕量：晶振 ±10 ppm 以内（设计指南），而上表按 40 ppm 算已经是「选型或负载电容出问题之后」的事故量级。

## 11.3 频偏如何毁掉一条连接

### 1. 从晶振到掉线的完整链路

```text
晶振偏差（选型超差 / 负载电容错配 / 温漂）
  → PLL 倍频后本振（LO）同比例偏差：40 ppm = 载波偏 96 kHz
  → 发射端：发出的载波整体偏 96 kHz
  → 接收端：下变频后基带带着 -96 kHz 的载波频偏（CFO）
  → 基带用前导码（STF/LTF 训练序列）估计频偏并补偿（AFC）
  → 补偿不掉的残余频偏 → FFT 窗内相位旋转 + 子载波正交性破坏（ICI）
  → EVM 恶化（第四章：64QAM 只有 -27 dB 的调制质量余量）
  → SNR 不够 → 降 MCS → 偏得再狠就掉线
```

### 2. AFC：射频世界的波特率追踪

上面的「估计频偏并补偿」有个经典名字：**AFC（Automatic Frequency Control，自动频率控制）**。它的软件原型你一定写过或用过：串口接收端的波特率自动追踪、SerDes 里的时钟数据恢复（CDR）、音频里的采样率自适应——都是「先用训练序列量出双方的钟差，再把本地钟调过去」。802.11 的每个包开头都带前导训练序列（STF/LTF），相当于**每帧开头先发一段波特率校准 pattern**，接收端逐包做粗估+细估两步校正。

AFC 的极限也要认清，三件事它救不了：

1. **估计本身要信噪比**：信号差的时候训练序列都解糊了，频偏估计跟着糊——弱信号与频偏是互相放大的恶性循环；
2. **追不了快变**：AFC 逐包校正，温漂这种秒级慢变能追，但温度快速变化（设备刚开机自暖、户外日晒切换）期间的性能低谷躲不掉；
3. **校正不是万能修**：AFC 修的是「知道偏多少就补多少」，若偏差大到前导都认不出（比如 CL 错配叠上低温），包根本进不了校正流程——先有鸡才有蛋。

### 3. 一个指纹级症状：scan 得到、连不上

频偏故障有个特征性表现：**扫描能看到 AP，关联却失败或连上即断**。机制：AP 的 beacon/探测响应按最低基础速率发送（1 或 6 Mbps 的低阶调制），低阶调制对频偏的容忍度大；而关联后的数据帧走高阶 OFDM 调制，频偏余量最先被吃光。于是「低速率管理帧通、高速率数据帧崩」——扫得到连不上，是频偏故障的典型指纹之一（注意不是唯一原因，功率不足、灵敏度问题也会这样，实测甄别留给第十五章）。

## 11.4 出厂校准：你烧录时见过的东西，终于有名字

### 1. 三个「眼熟但没深究」的东西

翻你任何一次 ESP32 烧录后的启动日志与分区表，有几样眼熟但没深究过的东西：日志里一行 `phy_version ...`；分区表里一块叫 `phy_init` 的分区；NVS 里一个叫 `phy` 的命名空间。它们全是本章的主角——**RF 校准体系**的三件套。以下全部出自本机 ESP-IDF v6.0.2 `components/esp_phy` 源码实读。

### 2. 校准数据长什么样、存在哪

```c
// include/esp_phy_init.h —— 结构体原文
typedef struct {
    uint8_t version[4];                     /*!< PHY version */
    uint8_t mac[6];                         /*!< The MAC address of the station */
    uint8_t opaque[1894];                   /*!< calibration data */
} esp_phy_calibration_data_t;

// src/phy_init.c —— 存储位置原文
static const char* PHY_NAMESPACE = "phy";
static const char* PHY_CAL_VERSION_KEY = "cal_version";
static const char* PHY_CAL_MAC_KEY = "cal_mac";
static const char* PHY_CAL_DATA_KEY = "cal_data";
```

三个读码收获：**约 1.9 KB 的不透明 blob**（校准项内容在闭源 libphy 里，开源部分管入口和存储）；**绑定 MAC**——加载时会和 efuse 里的 STA MAC 比对，不同芯片的校准数据互相无效，这是「每颗芯片一份的私货」，像出厂时按设备序列号 provision 的参数文件；**带版本**——PHY 库版本升级后旧数据作废，自动重算。另外别混淆：`phy_init` 分区存的是**芯片族的默认参数**（`esp_phy_get_init_data` 从那里读，还能按国别法规切多份 bin），NVS 的 `phy` 命名空间存的是**你这颗芯片的校准结果**——一个是模板，一个是实例。

### 3. 三档校准模式与启动流程

```c
// esp_phy_init.h —— 枚举注释原文
PHY_RF_CAL_PARTIAL = 0x00000000, /*!< Do part of RF calibration.
                                     This should be used after power-on reset. */
PHY_RF_CAL_NONE    = 0x00000001, /*!< Don't do any RF calibration. This mode is
                                     only suggested to be used after deep sleep reset. */
PHY_RF_CAL_FULL    = 0x00000002  /*!< Do full RF calibration. Produces best results,
                                     but also consumes a lot of time and current.
                                     Suggested to be used once. */
```

`esp_phy_load_cal_and_init()` 的流程（phy_init.c 实读）：上电复位走 PARTIAL（默认档）；深睡唤醒走 NONE——校准结果还在，不用重算；NVS 里读不到校准数据时兜底转 FULL，算完写回 NVS。源码里的日志调用原文（真机上你见过它们渲染出来的样子）：

```c
ESP_LOGI(TAG, "phy_version %s", phy_version);
ESP_LOGW(TAG, "failed to load RF calibration data (0x%x), falling back to full calibration", err);
```

FULL 的代价 Kconfig 写得直白：「Full calibration takes about 100ms more than partial calibration」——多花约 100 ms 启动时间和大电流。这就是为什么默认档是 PARTIAL、FULL 只在首次或数据丢失时触发：**校准是拿启动时间换射频成色的一次性投资**。

### 4. 温漂的运行时对策：每秒一次的 PLL 跟踪

校准解决「出厂时刻」，温度会漂走。esp_phy 的对策是一个后台周期任务（Kconfig 原文）：

```text
config ESP_PHY_PLL_TRACK_PERIOD_MS
    int "Set the period of the pll track"
    default 1000
    ...
config ESP_PHY_DISABLE_PLL_TRACK
    bool "Disable phy pll track(only for experimental)"
    help
        PLL track helps the PHY module adapt to temperature changes, ensuring
        stable performance.
```

默认每 1000 ms 跑一次 `phy_track_pll`（phy_common.c），调 `phy_param_track_tot()` 重新调整 PLL 参数——**温度补偿不是玄学，是个每秒跑一次的后台任务**。一个漂亮的平台差异：phy_init.c 注释「ESP32 will track pll in the wifi/BT modem interrupt handler」——经典 ESP32 把跟踪挂在 modem 中断里做，其余芯片才用 esp_timer 周期任务。同一个需求，两套调度载体。

### 5. 产线校准工位：频偏的硬件侧终点

固件校准之外，设计指南还定义了产线上的频偏工序：用乐鑫 Certification and Test Tool 让设备进入 TX tone（单音发射）模式，频谱仪解调 2.4 GHz 信号的频偏，然后「Adjust the frequency offset to be within ±10 ppm (recommended) by adjusting the external load capacitance」——**物理调电容，把频偏调进 ±10 ppm**。软件类比：这就是「出厂基准测试 + 按台写回校准值」，像手机出厂逐台做屏幕色彩校准再写入 OTP；只不过这里的「旋钮」是烙铁上的电容。

一条工程边界要说清：校准（固件侧）与调电容（硬件侧）修的是两层。校准基于晶振这个基准去修射频链路的个体差异——**基准本身歪了（CL 错配 30 ppm），校准量再准也是在歪的尺子上刻度**。所以 11.5 的案例里，软件三板斧救不了硬件层的错配。

## 11.5 故障案例集：温漂与负载电容的四种死法

以下案例一的原始条目出自 ESP-FAQ 真实问答，二、三按其素材框架与官方文档证据改写，四出自模组 datasheet 原文。

### 案例一：自制板怎么都连不上路由器（ESP-FAQ 原条目）

ESP-FAQ 原题：「使用 ESP32 芯片设计的 PCB 无法正常连接到路由器，什么原因？」官方答复两板斧：其一，「请在 XTAL_P 上串联 24 nH 电感」（压晶振谐波，见 11.1.3）；其二，按原理图检查清单的步骤**调节晶振两边的电容**——正是 11.4.5 的产线频偏调谐程序。翻译成人话：扫描能看到路由器、就是关联不上或秒断，官方第一嫌疑就是**频偏超差**，先压谐波、再调负载电容把频偏拉回 ±10 ppm。一个纯软件背景的团队拿到这个答复前，大概率已经在 Wi-Fi 驱动、密码、DHCP 上绕了三天。

### 案例二：冬天户外的设备，开机几分钟后「自愈」

现象框架：户外设备冬天批量复现「刚开机连不上，过几分钟自己好了」。机制是晶振温漂：常用 AT 切型石英的频率-温度曲线近似抛物线，在「转折点」温度附近最平缓、离开转折点按平方规律变差——设备冬天冷启动时晶振频率偏得最狠，开机后电路自热把温度拉回转折点附近，频偏回落，连接恢复。量级口径：常见 40 MHz 晶振全工业温区的频稳在十几到几十 ppm 量级，**具体数值待核对**（以所选晶振 datasheet 的温度曲线为准）。这个案例的软件侧对照就是 11.4.4 的 PLL 跟踪任务——它追的就是这类秒级慢漂；但「开机最初几分钟」的窗口期，只能靠选对转折点温度档位的晶振来兜底。

### 案例三：换料后产线频偏超标、市场端丢包

现象框架：40 MHz 晶振缺货，BOM 换了「同频同精度」的另一品牌，产线频偏测试开始超差，市场端丢包率上升。机制：两颗晶振标称都是 40 MHz ±10 ppm，但 **CL 规格不同**（比如一颗 9 pF、一颗 12 pF），负载电容照抄上一版，实际 CL 偏离新晶振的标称工况，谐振频率整体偏移。官方证据就在模组 datasheet 里——WROOM-1 v1.8 参考原理图对 C1/C4 的注记原文：「The values of C1 and C4 vary with the selection of the crystal」。软件类比：这是 binary compatibility 的坑——接口签名（频率/精度）相同，隐式契约（CL）不同，链接能过、运行时炸。

### 案例四：过超声波焊接台后模组失灵（模组 datasheet 原文）

WROOM-1/1U datasheet v1.8 §12.4「Ultrasonic Vibration」原文警告：避免让模组暴露于超声波设备的振动，「This vibration may induce resonance in the in-module crystal and lead to its malfunction or even failure」——超声波会让模组内置晶振共振，轻则失灵、重则物理损坏。产线上的超声波焊接/清洗工序因此成了「良率玄学」的固定来源：晶振是被机械共振打伤的，外观检查什么也看不出来。

## 11.6 软件工程师的诊断位

### 1. 症状指纹表

| 症状指纹                  | 为什么指向时钟/频偏          | 下一动作                  |
| ------------------------- | ---------------------------- | ------------------------- |
| scan 得到、关联失败或秒断 | beacon 低速率容偏差，OFDM 崩 | 先看 11.4 校准日志        |
| RSSI 很强仍频繁降速丢包   | SNR 够但 EVM 崩，频偏嫌疑    | 对比同批好板              |
| 同批固件，部分板子复现    | 元件个体差异（CL/晶振批次）  | 抄板对比负载电容          |
| 特定温度环境批量复现      | 温漂：低温/高温越出转折点    | 看 PLL track 日志（11.4） |
| 换一块板立刻好            | 硬件个体问题，软件洗不掉     | 走硬件排障流程（11.5）    |

第一行是本章的招牌指纹（11.3.3）；第二行要会读——RSSI 强说明「收到得够多」，仍降速丢包说明「解得不好」，SNR 与 EVM 是两个维度，EVM 崩而 RSSI 好，嫌疑集中在频偏、相位噪声这类「质量型」问题（对照 [[ch05-rx-chain-sensitivity|第五章]]的灵敏度账本）。

### 2. 排障问题清单

- 启动日志里 `phy_version` 之后有没有「failed to load RF calibration data」？（NVS 校准数据缺失/失效，已自动 full cal 重算）
- 是这块板一直坏，还是同批的一部分坏？（个体 vs 批次：批次问题先查 BOM 变更）
- 换一块同固件的板子立刻好？（好——硬件个体，软件止损到此为止）
- 复现是否与温度、开机时长相关？（冷启动几分钟自愈 → 温漂画像）
- 能拿到原理图吗？晶振型号的 CL 是多少、两侧电容多大——按 11.1.3 公式算一遍，差得远就别在软件里找了。

### 3. 软件三板斧（与它们的边界）

```c
#include "esp_phy_init.h"

// esp_phy_init.h 注释原文定位：last-resort remedy（最后一招）
// "It can be called in the application based on some conditions
//  (e.g. an option provided in some diagnostic mode)."
esp_phy_erase_cal_data_in_nvs();   // 只擦 NVS 的 "phy" 命名空间，
                                   // 下次启动触发全量校准重算
```

三板斧：其一，诊断模式里调 `esp_phy_erase_cal_data_in_nvs()` 触发 full cal 重算（官方定位就是「最后一招」，注意它只擦 `phy` 命名空间，不动其他 NVS 数据）；其二，menuconfig 把校准档切到 `ESP_PHY_RF_CAL_FULL`，用约 100 ms 启动时间换全量校准；其三，开 `ESP_PHY_PLL_TRACK_DEBUG` 看跟踪日志。边界同样重要：**三板斧只能重跑校准，修不了 CL 错配与晶振超差**——那是改电容、换料的事（11.4.5 的两层论）。

| 流传说法                       | 错在哪                                         | 正确姿势                         |
| ------------------------------ | ---------------------------------------------- | -------------------------------- |
| 「晶振随便换，频率对就行」     | CL 不同则负载电容错配，频偏立刻超标            | 换晶振必重算 CL 并重调两侧电容   |

| 「32 kHz 晶振管载波精度」      | 32 kHz 只供 RTC，载波来自 40 MHz 主晶振        | 分清主晶振与 RTC 晶振的职责      |

## 11.8 小结

- **一个源头**：全芯片的每一拍来自 40 MHz 主晶振（WiFi/BT 场合唯一可选频率，ESP32 datasheet 与 S3 设计指南双源核实）；CPU 时钟与 2.4 GHz 载波同源不同命——倍频复制相对误差，绝对值放大 60 倍。
- **一笔账**：40 ppm 在 CPU 域是每秒 40 µs（无所谓）、在串口域是 4.6 波特（无所谓）、在信道 1 载波域是 96.5 kHz（吃掉子载波间隔的 31%，一个符号内星座旋转约 111°）——**同一个误差，按消费者算命运**。
- **两个硬件旋钮**：负载电容成对出现是振荡器结构所定，CL = (C1 × C4)/(C1 + C4) + C_stray（设计指南原文），调它们就是调频偏；XTAL_P 串 24 nH 电感压谐波（40 MHz 的 60 次谐波正好是 2400 MHz）。
- **两套校准**：固件侧 esp_phy 三档校准（PARTIAL 默认 / NONE 深睡 / FULL 全量慢 100 ms），结果以约 1.9 KB blob 存 NVS `phy` 命名空间、按 MAC 绑定；运行时每秒一次 PLL 跟踪补温漂。硬件侧产线 TX tone + 频谱仪 + 调电容进 ±10 ppm。
- **一层边界**：校准修的是射频链路个体差异，修不了晶振基准本身的错配——CL 选错 30 ppm，全量校准也救不了，那是烙铁的活。
- **一个招牌指纹**：scan 得到、连不上——beacon 低速率宽容、OFDM 高速率先崩；配上「RSSI 强仍丢包」「低温冷启动自愈」「换板即好」三条辅证，频偏类问题软件侧就能框定到八成。
- **类比的边界**：频偏=时钟漂移的类比到「双方节拍不一致导致解码失败」为止；差异是串口按帧采样（容忍百分比级），载波按符号正交采样（只容忍 ppm 级）——类比帮记忆，容差要按域算。

下一章从「时间准不准」转到「电够不够」：WiFi 发射瞬间的数百 mA 毛刺、LDO 与 DCDC 的性格差异、为什么电源不好先丢包后 brownout——晶振决定「拍子准不准」，电源决定「有没有力气打拍子」。见[[ch12-power-supply|第十二章：WiFi 的电源性格]]。
