# ex13 tcp-hostlink —— QEMU 与宿主双向 TCP 交互模板

lwIP 示例套件 ex13：**一个固件同时演示两个发起方向的 TCP 应用**，证伪"SLIRP 下只能
单向通信"的常见误解。入向是一条一行式命令服务（宿主机连 guest 的 8300），出向是周期
心跳（guest 每 5s 主动连宿主机 loopback 8301，收到 `ACK` 即断）。两个方向跑在各自的
FreeRTOS 任务里，`run.log` 时间线可以证明它们并发运行、互不阻塞。

固件从《lwIP 深度解析》实验沉淀的纪律已固化进代码结构（`main/main.c` 文件头有完整注解）：

| 纪律                                                                        | 出处          | 本模板的落法                                                        |
| --------------------------------------------------------------------------- | ------------- | ------------------------------------------------------------------- |
| 单任务串行 accept 必须先收后回、数据驱动推进                                | ch23 结论 a   | 命令面逐连接"阻塞 recv → 按行分发 → 回写"，FIN/RST/空闲超时立即回收 |
| listen backlog 显式设足                                                     | ch23 结论 b   | `listen(fd, 8)`，注释写明与 `CONFIG_LWIP_MAX_ACTIVE_TCP(16)` 关系   |
| 跨线程读 lwip_stats 必须回到 tcpip_thread；且 `tcpip_callback()` 是异步投递 | 本仓实录      | 快照用"回调内 give 信号量 + 调用方带超时 take"保同步取齐            |
| 失败分支打印 errno + 符号名 + 耗时                                          | ch16 错误账本 | 连接拒绝实测落 errno=104（lwIP 无 ECONNREFUSED 映射），如实打印     |
| RTOS 原语契约必须照办                                                       | 本仓实录      | `vTaskDelayUntil` 锚点必须取当前 tick——详见排障节的踩坑实录         |

## 网络拓扑

```text
        宿主机 (Fedora)                                QEMU guest (esp32)
┌───────────────────────────────┐               ┌─────────────────────────────────┐
│ tools/reverse_heartbeat.py    │◄──tcp:8301────┤ SLIRP user-net                  │
│ (收 JSON 校验→回 ACK→断开)     │   出向心跳     │   10.0.2.2 = 宿主 loopback     │
│       ▲ ACK                   │   (guest 发起) │                                 │
│       │                       │               │   ┌─────────────────────────┐   │
│ tools/hostlink.py             │               │   │ ex13_tcp_hostlink 固件   │   │
│ PING/ECHO/STATS/TIME ─────────┼──tcp:8300────►│   │  入向: cmd_srv :8300     │   │
│ 未知命令                      │ hostfwd(入向) │   │  出向: hb_cli →10.0.2.2  │   │
└───────────────────────────────┘               │   │  openeth MAC            │   │
                                                │   │  52:54:00:12:34:56      │   │
   guest IP 由 SLIRP DHCP 固定分配               │   └───────────┬─────────────┘   │
   10.0.2.15/24, 网关 10.0.2.2                  └───────────────┼─────────────────┘
                                                                │ lwIP socket API
                                                          DHCP 得 10.0.2.15
```

- **入向**：宿主只能经 **hostfwd** 一条路访问 guest（`hostfwd=tcp::8300-:8300`）。
  主机直发 ICMP 到 10.0.2.15 恒不通、也没有别的端口通路——这是 SLIRP 的硬边界，
  不是本模板的限制。
- **出向**：guest 发往网关 `10.0.2.2:P` 的 TCP 被 SLIRP 落到**宿主机 loopback 同端口**
  （127.0.0.1:P），因此心跳接收器只是个普通 python 监听器，QEMU 参数无需任何配合，
  先于固件启动或中途换模式都行。
- 端口约定见套件 SPEC §4：ex13 号段 8300/8301，两方向各占一个。

## 双向并发模型

两个任务在拿到 IP 后并行创建，互不为对方前置：

- `ex13_cmd_srv`（入向命令面）：单任务 accept 循环，逐连接串行处理，一次只服务一条
  连接；第二条连接的握手会完成并挂在 backlog 里排队（排队不拒的行为见 ex02 README），
  接受的 socket 带 `SO_RCVTIMEO=30s` 兜底，哑客户端不会把 accept 循环拖死。
- `ex13_hb_cli`（出向心跳面）：`vTaskDelayUntil` 绝对节拍，每拍一条独立 TCP 会话；
  connect 失败、发送失败、等 ACK 超时都只计数告警（streak），绝不影响命令面。
- 共享状态只有几个字宽计数器（conn_total / replies / hb_ok / hb_fail …），由每 15s
  打一行的观测任务汇总成 `$$$ EX13STATS` 行，可 grep 做 CI 断言。

### 入向命令协议（每行一条，响应以 `\n` 分帧）

| 命令          | 响应                                         |
| ------------- | -------------------------------------------- |
| `PING`        | `PONG`                                       |
| `ECHO <data>` | `<data>` 原样返回（缺参回空行）              |
| `STATS`       | 单行 JSON：lwip_stats TCP 段 + heap + uptime |
| `TIME`        | `up_ms=<毫秒> up_s=<秒>`                     |
| 其他任何行    | `ERR unknown`                                |

健壮性三件套：

1. **命令超长截断保护**：行缓冲上限 255 字节，超限字节被丢弃并打 `$$$ EX13TRUNC`
   标记，到换行为止按截断后的残行走正常命令分发——协议永不被灌爆。
2. **客户端突然断开不崩溃**：对端 RST 在 recv 上表现为 `errno=104`，记录后 close，
   服务继续（下文有实测摘录）。
3. **心跳失败只计数告警**：无监听 → connect 硬失败；接通不回话 → `SO_RCVTIMEO(3s)`
   到期 EAGAIN；两种掉线都打 `$$$ EX13HBDROP` 并累加 streak，不影响 `hb_period_ms`
   节拍与命令面延迟。

## 构建命令

```bash
cd practice/lwip-examples/ex13-tcp-hostlink
. ~/esp/esp-idf/export.sh
idf.py set-target esp32        # 仅首次
idf.py build                   # MINIMAL_BUILD ON，只编最小组件集
```

`sdkconfig.defaults` 只有两条：`CONFIG_ETH_USE_OPENETH=y`（必填）和
`CONFIG_LWIP_STATS=y`（给 STATS 命令提供真实 TCP 计数；关掉则 JSON 里 `"tcp":null`
降级，服务不受影响）。注意改 defaults 后必须删 sdkconfig 重新生成。

## 运行命令

```bash
# 生成 QEMU 镜像（monitor 因无 TTY 失败属预期，镜像已生成）：
idf.py qemu monitor < /dev/null || true
ls build/qemu_flash.bin build/qemu_efuse.bin   # 必须存在

# 启动（tools/run_qemu.sh 内核 = 去 efuse -global 行的标准形态 + hostfwd 8300，
# 输出 tee 到 run.log；timeout 到点退出码 124 属正常截停）：
tools/run_qemu.sh [秒数]                       # 默认 600s
```

等日志出现机器可读 READY 行即可开始连接：

```text
$$$ EX13READY port=8300 backlog=8 hb_target=10.0.2.2:8301 hb_period_ms=5000 cmd_max=255 idle_rcvtimeo_s=30
```

机器可读标记清单（CI 可逐条 grep 断言）：`EX13BUILD` / `EX13NETUP` / `EX13READY` /
`EX13CONN` / `EX13REPLY`（附 us 级处理耗时）/ `EX13TRUNC` / `EX13CLOSE` /
`EX13HB`（ACK 成功）/ `EX13HBDROP`（含 errno 与 streak）/ `EX13STATS`（存活心跳）/
`EXFAIL`（仅 DHCP 失败时）。

### 角色一：只复现入向命令面（不起接收器）

```bash
python3 tools/hostlink.py -c PING -c "ECHO hello-from-host" -c STATS -c TIME \
  -c "FROBNICATE warp=9"
```

此时 `run.log` 会持续刷心跳掉线告警——这本身是演示的一部分（见下文掉线分支摘录：
命令响应完全不受影响）。

### 角色二：双向全量（先起接收器再连命令口）

```bash
# 终端 A：出向心跳接收器（校验 JSON、回 ACK、即断）
python3 tools/reverse_heartbeat.py                 # 默认 127.0.0.1:8301 normal

# 终端 B：入向命令客户端（交互 REPL：直接敲命令行；.help/.quit 本地元命令）
python3 tools/hostlink.py
```

其余现成场景开关：`--oversize 500`（超长行截断保护演示）、`--rst-after-ping`
（PING 之后 SO_LINGER(1,0)+close 强发 RST）；接收器侧 `--mode noack` 是故障注入
（收下心跳故意不回 ACK，触发 guest 侧等待超时分支）。

## 真实输出摘录

以下 guest 侧行全部逐字摘自本工程入库的 `run.log`（2026-08-27 一次完整独立复验运行，

### 出向心跳面 A：宿主无监听时的掉线分支（前 ~23s 特意未启动接收器）

```text
W (7657) ex13: HB #1 target 10.0.2.2:8301 CONNECT-FAIL errno=104(ECONNRESET) streak=1 -- service plane unaffected
$$$ EX13HBDROP seq=1 result=CONNECT_FAIL errno=104 name=ECONNRESET elapsed_ms=6 streak=1 conn_total=0
...
W (22657) ex13: HB #4 target 10.0.2.2:8301 CONNECT-FAIL errno=104(ECONNRESET) streak=4 -- service plane unaffected
$$$ EX13HBDROP seq=4 result=CONNECT_FAIL errno=104 name=ECONNRESET elapsed_ms=1 streak=4 conn_total=0
```

教学点：Linux 教科书说"连接被拒"是 `ECONNREFUSED(111)`，但 lwIP err.c 映射表没有这个
条目，SLIRP 对无监听端口的代答 RST 经 ERR_RST 映射后落到 **104/ECONNRESET**——错误
账本必须按实测写。掉线只累计 streak（`hb_fail`），节拍照旧 5s 一拍。

### 入向命令面：五种命令各一次的真实往返

宿主机 `hostlink.py -c PING -c "ECHO hello-from-host" -c STATS -c TIME -c "FROBNICATE warp=9"` 输出
（箭头行带墙钟时间戳与 RTT）：

```text
[15:01:27.404] ## connected guest:8300 reply_timeout=5.0s
[15:01:27.404] >> PING
[15:01:27.412] << PONG   (8.4 ms)
[15:01:27.412] >> ECHO hello-from-host
[15:01:27.414] << hello-from-host   (1.6 ms)
[15:01:27.414] >> STATS
[15:01:27.417] << {"tcp":{"rx":34,"tx":32,"drop":0,"memerr":0},"heap":{"free":257204,"largest":131072,"min":250876},"up_s":48}   (3.3 ms)
[15:01:27.417] >> TIME
[15:01:27.420] << up_ms=48408 up_s=48   (2.2 ms)
[15:01:27.420] >> FROBNICATE warp=9
[15:01:27.421] << ERR unknown   (1.8 ms)
HLK-SUMMARY sent=5 replied=5 lost=0 result=OK
```

- 五条命令全部毫秒级往返（SLIRP + lwIP 事务型小流量的正常水位），第一条含 TCP 握手
  故略高；
- STATS JSON 字段口径：`tcp.{rx,tx,drop,memerr}` 来自 `lwip_stats.tcp`（快照经
  tcpip_thread 取齐）；`heap.{free,largest,min}` 为 heap_caps 三件套（min 是多区域
  sum-of-minima 历史极值，只会往下走，别跨阶段取差）；`up_s` 用 esp_timer。
- `ECHO` 回的是**去掉 `ECHO ` 前缀后的原样字节流**（含 UTF-8 中文在内逐字节返回），
  关键词大小写不敏感，多行按行各自响应；`PING` 的尾随参数被忽略（见下文故障窗里的
  `PING during-hb-outage-t1` 照样回 `PONG`）。

### 健壮性场景摘录（同一 run.log）

超长行截断（`--oversize 500`：`ECHO `+500B 数据 = 505B 一行，超出 255B 行缓冲后
超限字节被丢弃，只剩前 250B 数据被原样回显，连接干净收尾）：

```text
W (61967) ex13: conn #2 line too long (>=256 B), truncating until LF
$$$ EX13TRUNC idx=2 n=1 kept=255 limit=255
I (61967) ex13: conn #2 cmd[1] ECHO req=255 resp=251 proc=223us
I (61967) ex13: conn #2 from 10.0.2.2:36002 CLOSED why=FIN srv=0ms msgs=1 (506 B in)
$$$ EX13CLOSE idx=2 reason=FIN msgs=1 bytes=506 ms=3
```

客户端粗暴离场两连（都不崩溃、都及时回收）：

1. **SIGKILL 客户端（发完 PING 不 close）**：客户端进程被 kill -9，socket 里还压着
   未读的 PONG，内核代为关 fd 时直接发 RST——guest 在 `recv` 上看到 errno=104 并正常
   关闭会话：

   ```text
   I (61987) ex13: conn #3 cmd[1] PING req=4 resp=5 proc=137us
   $$$ EX13REPLY idx=3 n=1 cmd=PING req_len=4 resp_len=5 us=200
   W (62587) ex13: conn #3 recv failed errno=104(ECONNRESET)
   I (62587) ex13: conn #3 from 10.0.2.2:36006 CLOSED why=ERR srv=0ms msgs=1 (5 B in)
   $$$ EX13CLOSE idx=3 reason=ERR msgs=1 bytes=5 ms=600
   ```

2. **SO_LINGER(1,0)+close 强发 RST**（tools/hostlink.py --rst-after-ping）：

   ```text
   I (78547) ex13: conn #4 cmd[1] PING req=4 resp=5 proc=263us
   W (78547) ex13: conn #4 recv failed errno=104(ECONNRESET)
   I (78547) ex13: conn #4 from 10.0.2.2:43184 CLOSED why=ERR srv=0ms msgs=1 (5 B in)
   $$$ EX13CLOSE idx=4 reason=ERR msgs=1 bytes=5 ms=3
   ```

心跳目标不可达 34s 窗口（对抗三之三）：命令面存活证据见上文"双向并发时间线证据二"，
全程 6 拍 CONNECT_FAIL（streak=1..6），期间两次入向探测毫秒级应答；接收器重启后第一拍
即恢复 ACK。另一现成故障注入是接收器侧 `--mode noack`：收下心跳故意不回 ACK，触发
guest 侧 `SO_RCVTIMEO(3s)` 超时的 NO_ACK/EAGAIN 分支（本轮复验未跑该注入，工具已内置，
一条命令即可复现）。

```text

```

## 已知边界 / 排障

- **SLIRP 入向只有 hostfwd 一条路**：本示例入向依赖 `hostfwd=tcp::8300-:8300`。
  主机直 ping 10.0.2.15 不通是 SLIRP 硬边界（ICMP 只能 guest 发起）；guest 出向则
  无需任何配置，`10.0.2.2:P` 就是宿主 `127.0.0.1:P`。想换入向端口要同时改
  `main.c` 的 `CMD_PORT` 和 `tools/run_qemu.sh` 的 hostfwd。
- **vTaskDelayUntil 锚点契约坑（本仓库实录，值得记住）**：周期任务的唤醒锚点写成了
  `wake = xTaskGetTickCount() + period`，结果内核认为 tick 已经回卷、判定"无需延时"
  当拍返回，心跳风暴式重试（数千拍挤在同一秒）。契约要求 `*pxPreviousWakeTime` 是
  "上一次醒来的时刻"——不超过当前 tick。正确姿势见 `heartbeat_task` 注释。另外周期
  收口放在循环顶部（所有 continue 分支都会绕回顶部过节拍），错误路径不可能绕过周期。
- **errno 对照速查（newlib 值域，非 Linux）**：本环境高频值是 EAGAIN=11、EPIPE=32、
  ECONNRESET=104、ECONNABORTED=113、ENOTCONN=128；connect 被拒不产生 Linux 教科书的
  ECONNREFUSED(111)。排错时以 `err_name()` 打印为准，不要背 Linux 数字。
- **空闲连接 30s 自动放行**：accepted socket 带 `SO_RCVTIMEO=30s`，哑客户端到期会
  以 `reason=IDLE-TIMEOUT` 被 close（本次运行没有触发该分支；要想看到可以 telnet
  上去不发话）。
- **并行实验端口冲突**：启动失败先确认 8300 是否被其他 QEMU 占住。按 hostfwd 特征
  精确 kill，禁止 pkill（有并行作者实例在跑）：

  ```bash
  for p in $(pgrep -f '^/home/huanglin/.espressif/tools/qemu-xtensa'); do
    tr '\0' ' ' < /proc/$p/cmdline | grep -q 'tcp::8300' && kill $p || true
  done
  ```

- **镜像陈旧**：重复构建后 `idf.py qemu monitor` 可能静默不更新镜像，核对启动日志里
  `build@"__DATE__ __TIME__"` 指纹；必要时手动合并：

  ```bash
  cd build && python -m esptool --chip esp32 merge-bin \
    -o qemu_flash.bin --pad-to-size 2MB @flash_args
  ```

- **日志体量**：本示例日志以事件为主，整轮 ~135s 仅 ~13KB（183 行），远低于 1MB 截断
  红线；若做长压测请自行加截断（首 N 千行 + `$\$\$` 标记行 + 尾行，见套件 SPEC §6 政策）。
- **串行 accept 的排队语义**与本模板一致，深度分析见 ex02 README；这里两方向独立
  任务，入向即使被哑客户端占满 30s，也只影响命令面自身，心跳照打。
