# ch07-pacing-harness —— 发送节奏整形 × 到达间隔统计

把 [[ch07-pacing-and-structure|第七章：釜底抽薪]] 的核心论断做成可运行的测量工具：**同一个
UDP 发送端，burst（连续尽快发）与 paced（令牌桶限速）两种模式各跑一遍，接收端对每个到达包打
单调时钟时间戳，统计包间隔 gap 的 min/avg/p99/max、标准差、RFC3550 抖动 J 与直方图，最后打印
对比表**。burst 与 paced 的到达节奏差异（µs 级聚簇 vs 钉在 1/pps 附近）一目了然。

单文件 `pacing.c`（C11 零依赖，跨平台垫层 `net_compat.h` 原样拷贝自
`p2p-labs/ch02-lan-direct`），收发线程在同一进程内经回环对接。完整源码见
[代码浏览器](/static/code/#/wifi-airtime-labs/ch07-pacing-harness/pacing.c)。

## 拓扑

```text
单进程（默认，回环自发自收）：
  发送线程 ──burst: 2000×1316B 连发──▶ 接收线程 (0.0.0.0:13201)
          └─paced: 令牌桶 500pps─────▶   recvfrom 返回即打 QPC 单调时间戳
                                          → gap min/avg/p99/max + σ + RFC3550J + 直方图

双进程（--rx-only，真机形态的预演）：
  设备侧: ./pacing --ip <PC> --pps 500 ──WiFi/回环──▶ PC 侧: ./pacing --rx-only 15
```

## 编译

```bash
~/zig/zig cc -O2 -o pacing pacing.c -lws2_32   # Windows（任何 cc 皆可）
zig cc -O2 -o pacing pacing.c                  # Linux/macOS 去掉 -lws2_32
```

## 复现

```bash
./pacing                            # 默认：2000 包 × 1316B → 127.0.0.1:13201，paced 500pps
./pacing --count 600 --pps 250      # 令牌桶随 argv 收紧/放宽（--depth 桶深亦可调）
./pacing --rx-only 15 --count 600 & # 双进程：接收器只收不发（PC 侧角色）
./pacing --count 600 --pps 500 --port 13202 --dport 13201   # 发往上面那个接收器
```

完整真实输出（含逐桶直方图与三组运行）见 `run.log`。

## 两种模式

- **burst**：`sendto` 循环里不做任何等待。回环上 2000 包约 26ms 发完（≈7.6 万 pps），到达 gap
  几乎全部落在 1–20µs——**这就是突发形态本身**：包挤成一坨，中间没有呼吸。
- **paced**：令牌桶，速率 `--pps`（默认 500）、桶深 `--depth`（默认 1，即最严格的"攒够一个令牌
  才准发"，不蓄突发信用）。等待实现是 Win10 1803+ 高精度可等待定时器粗睡 + 末段 600µs 自旋
  收尾（POSIX 用 `clock_nanosleep`；无高精度定时器的旧系统退回实测过粒度的 `Sleep(1)`，再不行
  纯自旋）。末段不用 yield 的原因见源码注释——`SwitchToThread` 会让出整个调度节拍，实测产生
  5–8ms 的尾部毛刺。

## 输出怎么读

对比表各列（接收端到达 gap，单位 µs）：

| 列              | 含义                                                            |
| --------------- | --------------------------------------------------------------- |
| rx/loss         | 收到包数/丢包率（burst 需大 SO_RCVBUF，启动时会回显实得值）     |
| rx_pps          | (n-1)/首尾到达跨度，接收侧实际节奏                              |
| min/avg/p99/max | gap 的四分位画像（p99 为最近邻法）                              |
| sigma           | gap 标准差，节奏稳定度                                          |
| J3550           | RFC3550 到达间抖动（到达差-发送差的指数平滑，需包内发送时间戳） |
| <100us          | gap<100µs 占比——burst 的"聚簇度"指标                            |

## 真实数字（摘自 run.log §1，默认参数）

```text
mode        rx/loss     rx_pps      min      avg      p99        max    sigma    J3550  <100us
burst     2000/0.0%      76598     1.10     13.1     73.6      349.9     17.9     4.10   99.5%
paced     2000/0.0%      437.5     23.9     2286     6286      64736     2630     24.0    0.1%
```

- burst：99.5% 的到达 gap < 100µs，直方图聚在 5–20µs 两桶——突发聚簇的直接证据；
- paced（目标 2000µs）：79.2% 的 gap 落在 1900–2100µs，均值 +14.29%——令牌桶把节奏钉在目标
  附近，但尾部有 10–65ms 的毛刺（宿主负载把自旋线程整个饿了一拍），这是**用户态整流的常态
  限制**：均值可控、尾延迟靠 OS 调度赏饭。真要微秒级尾延迟得下沉到内核/硬件（ETF/FQTSS）。
- 调参与双进程（§2/§3）：250pps 时均值偏差 +6.62%；双进程下发送端 TX avg 2070µs 与接收端
  RX avg 2070µs 完全一致——回环不引入节奏失真，工具链自证清白。

## 诚实边界：回环验证什么、不验证什么

- **回环验证的是整流工具链与 gap 统计本身**：令牌桶→定时器→时间戳→统计整条链路的正确性，
  以及统计口径（p99/σ/J3550/直方图）能否分辨两种节奏形态。回环上 burst 的 gap 聚簇即突发
  形态证据；回环无丢包、无排队竞争，paced 的毛刺全部来自本机调度。
- **回环不验证空口行为**：WiFi 的 MAC 排队、CSMA/CA 退避、重传、信标打断等介质竞争效应在
  回环上一概不存在，这里的数字不能当作空口画像引用。
- **真机 WiFi 上同一命令即得空口节奏画像（待真机）**：设备侧
  `./pacing --ip <PC地址> --pps 500 --count 5000`，PC 侧 `./pacing --rx-only 30 --count 5000`，
  对比表就是空口对整流的"还原度"成绩单。届时注意：J3550 依赖对端时钟，跨机晶振频偏（ppm
  级）会带来少量偏差；接收端打点在用户态 `recvfrom` 返回处，含唤醒延迟。
